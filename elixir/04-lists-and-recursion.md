# 04 — Cons cells, recursion, structural induction

## Concept

A list is not an array. It is an **inductively defined** type with exactly two
constructors:

```
xs ::= []            -- the empty list
     | [h | t]       -- a cons cell: head h, tail t (itself a list)
```

That is the entire definition. `[1, 2, 3]` is sugar for `[1 | [2 | [3 | []]]]`,
three cons cells chained by their tails:

```
[1|•] ──▶ [2|•] ──▶ [3|•] ──▶ []
```

Because the definition has two cases, every function over lists has two cases
and every proof about lists has two cases. That correspondence is this
lesson's subject.

### Primitive operations and their costs

```elixir
iex> [1 | [2, 3]]      # cons: O(1), allocates one cell
[1, 2, 3]
iex> hd([1, 2, 3])     # O(1)
1
iex> tl([1, 2, 3])     # O(1), allocates nothing (the tail is shared)
[2, 3]
iex> length([1, 2, 3]) # O(n) — it walks the spine. There is no stored size.
3
iex> [1, 2] ++ [3, 4]  # O(n) in the LEFT list
[1, 2, 3, 4]
```

Prefer matching to `hd`/`tl`: `def f([h | t])` gives you both, cannot raise
(`hd([])` does), and makes the empty case a separate clause.

### `++` and why appending in a loop is a trap

`++` must rebuild its left argument, because the last cons cell of `xs` has to
point at `ys` and cons cells are immutable:

```elixir
def append([], ys), do: ys
def append([h | t], ys), do: [h | append(t, ys)]
```

So `xs ++ ys` costs O(length(xs)) cells, independent of `length(ys)` — the
right list is shared wholesale, not copied. Consequences: `list ++ [x]` is
O(n), so doing it in a loop is O(n²); `[x | list]` is O(1), so build backwards
and reverse once (two O(n) passes); and `xs ++ ys ++ zs` parses as
`xs ++ (ys ++ zs)`, the cheap association — do not force the other one.

### Recursion over a list

```elixir
def sum([]), do: 0
def sum([h | t]), do: h + sum(t)
```

Two rewrite rules: the first is the base case, the second reduces the problem
to a strictly smaller list. Every list is built from `[]` by finitely many
conses, so the second rule fires finitely often before the first applies.
Termination is not a hopeful claim; it follows from the type's definition.

Two more with the same skeleton:

```elixir
def len([]), do: 0
def len([_h | t]), do: 1 + len(t)

def reverse([]), do: []
def reverse([h | t]), do: append(reverse(t), [h])
```

(That `reverse` is O(n²): `append` is O(n) and runs n times. Lesson 5 fixes it
with an accumulator and *proves* the fixed version equal to this one; keep the
naive one, it is the one the proofs below mirror.)

Note the shape of every clause pair:

| | data | function | proof |
|---|---|---|---|
| base | `[]` | the `[]` clause | base case |
| step | `[h \| t]` | the `[h \| t]` clause, calling itself on `t` | inductive step, using IH about `t` |

## Grounding: structural induction

### The principle

Lists are generated by `[]` and `[h | t]` and nothing else. "Nothing else" is
the strong part: the set of lists is the *smallest* set closed under those two
constructors. So if S is any set with `[] ∈ S` and `∀ h, t. t ∈ S ⇒ [h|t] ∈ S`,
every list is in S; taking S = `{xs | P(xs)}` gives the proof principle:

```
      P([])        ∀ h, t.  P(t) ⇒ P([h | t])
     ─────────────────────────────────────────  (list induction)
                    ∀ xs.  P(xs)
```

To prove a property of all lists: prove it for `[]`, then prove it for
`[h | t]` *assuming it for `t`*. The assumption `P(t)` is the **induction
hypothesis** (IH).

This is ordinary mathematical induction with "size" replaced by "structure",
and it is available for any inductively defined type — trees in lesson 12 get
the same treatment, one hypothesis per recursive subterm.

Throughout, `++` is the `append` above, `length` is `len`, and every function
is total on lists, so each expression below denotes a value and `≡` is
equality of terms. The licence to rewrite a call by its definition in any
context comes from lesson 3.

### Proof 1: `length(xs ++ ys) ≡ length(xs) + length(ys)`

`P(xs) :≡ ∀ ys. length(xs ++ ys) ≡ length(xs) + length(ys)`. Induct on `xs`,
the argument both `++` and `length` recurse on.

**Base**, `xs = []`:

```
   length([] ++ ys)
≡  length(ys)                     -- append clause 1: [] ++ ys ≡ ys
≡  0 + length(ys)                 -- arithmetic
≡  length([]) + length(ys)        -- fold length clause 1: length([]) ≡ 0
```

**Step**, `xs = [h | t]`, IH: `∀ ys. length(t ++ ys) ≡ length(t) + length(ys)`:

```
   length([h | t] ++ ys)
≡  length([h | (t ++ ys)])            -- append clause 2
≡  1 + length(t ++ ys)                -- length clause 2
≡  1 + (length(t) + length(ys))       -- IH, instantiated at this ys
≡  (1 + length(t)) + length(ys)       -- associativity of +
≡  length([h | t]) + length(ys)       -- fold length clause 2
```

Both obligations discharged, so `P(xs)` holds for all `xs`. ∎

Observe the shape: one proof case per clause, each unfolding exactly the
clauses that fire. The proof is the program, read declaratively.

### Proof 2 (lemmas about `++`)

Two facts the later proofs need.

**Lemma 2a.** `∀ xs. xs ++ [] ≡ xs`. The mirror fact `[] ++ ys ≡ ys` is
clause 1 of the definition and needs no proof; this one does, because `++`
recurses on its *left* argument.

**Base**, `xs = []`: `[] ++ [] ≡ []` by append clause 1. ✓

**Step**, `xs = [h | t]`, IH: `t ++ [] ≡ t`:

```
   [h | t] ++ []
≡  [h | (t ++ [])]        -- append clause 2
≡  [h | t]                -- IH, rewriting under the cons constructor
```
∎

**Lemma 2b (associativity).** `∀ xs, ys, zs. (xs ++ ys) ++ zs ≡ xs ++ (ys ++ zs)`.

Induct on `xs`.

**Base**, `xs = []`:

```
   ([] ++ ys) ++ zs
≡  ys ++ zs               -- append clause 1 (inner)
≡  [] ++ (ys ++ zs)       -- fold append clause 1
```

**Step**, `xs = [h | t]`, IH: `(t ++ ys) ++ zs ≡ t ++ (ys ++ zs)`:

```
   ([h | t] ++ ys) ++ zs
≡  [h | (t ++ ys)] ++ zs        -- append clause 2 (inner)
≡  [h | ((t ++ ys) ++ zs)]      -- append clause 2 (outer)
≡  [h | (t ++ (ys ++ zs))]      -- IH, under the cons
≡  [h | t] ++ (ys ++ zs)        -- fold append clause 2
```
∎

So `(lists, ++, [])` is a monoid. Lemma 2a is the right identity law, and it
cost a whole induction — "obvious" facts about recursive functions still need
the recursion unrolled.

### Proof 3 (the lemma): `reverse(xs ++ ys) ≡ reverse(ys) ++ reverse(xs)`

Induct on `xs`.

**Base**, `xs = []`:

```
   reverse([] ++ ys)
≡  reverse(ys)                          -- append clause 1
≡  reverse(ys) ++ []                    -- Lemma 2a, backwards
≡  reverse(ys) ++ reverse([])           -- fold reverse clause 1
```

The base case needed Lemma 2a: the `++ []` that appears for free on one side
has to be manufactured on the other.

**Step**, `xs = [h | t]`, IH: `reverse(t ++ ys) ≡ reverse(ys) ++ reverse(t)`:

```
   reverse([h | t] ++ ys)
≡  reverse([h | (t ++ ys)])                    -- append clause 2
≡  reverse(t ++ ys) ++ [h]                     -- reverse clause 2
≡  (reverse(ys) ++ reverse(t)) ++ [h]          -- IH
≡  reverse(ys) ++ (reverse(t) ++ [h])          -- Lemma 2b
≡  reverse(ys) ++ reverse([h | t])             -- fold reverse clause 2
```
∎

### Proof 4: `reverse(reverse(xs)) ≡ xs`

Induct on `xs`.

**Base**, `xs = []`: `reverse(reverse([])) ≡ reverse([]) ≡ []`. ✓

**Step**, `xs = [h | t]`, IH: `reverse(reverse(t)) ≡ t`:

```
   reverse(reverse([h | t]))
≡  reverse(reverse(t) ++ [h])                       -- reverse clause 2
≡  reverse([h]) ++ reverse(reverse(t))              -- Proof 3, with xs := reverse(t), ys := [h]
≡  reverse([h]) ++ t                                -- IH
≡  [h] ++ t                                         -- reverse([h]) ≡ reverse([]) ++ [h] ≡ [] ++ [h] ≡ [h]
≡  [h | t]                                          -- append clause 2 then clause 1
```
∎

Four proofs, one method:

1. Induct on the variable the outermost recursive function destructures.
2. Base case: unfold the `[]` clauses on both sides until they meet. If they
   do not, you need a lemma (that is how Lemma 2a was discovered).
3. Step case: unfold the `[h | t]` clauses until a recursive call appears,
   rewrite it with the IH, then **fold** back up using the same definitions
   in reverse.
4. Every rewrite replaces a subexpression by an equal one — licensed by
   lesson 3.

### Why the program's shape is the proof's shape

```elixir
def len([]), do: 0                     # base case of the proof
def len([_h | t]), do: 1 + len(t)      # step: uses the answer for t
```

The recursive call `len(t)` is precisely where the proof appeals to the
induction hypothesis. If a function recurses on a substructure, the proof
inducts on that same substructure and the cases line up one for one. This is
not an analogy: both are instances of the same elimination principle for the
inductive type.

Practical payoff — when you cannot write a recursive function, ask what the
proof would look like; when you cannot finish a proof, the missing lemma
usually shows that the function needs another clause or another argument
(exactly how the accumulator in lesson 5 arises).

## Worked examples

```elixir
iex> [1, 2, 3] === [1 | [2 | [3 | []]]]
true
iex> [1, 2] ++ [3]        # O(2): rebuilds two cells, shares [3]
[1, 2, 3]
iex> [0 | [1, 2]]         # O(1): one new cell
[0, 1, 2]
```

Building a list (`map`, by hand) — the cons happens *outside* the recursive
call, so the result is assembled on the way back up, one cell per element:

```elixir
def double([]), do: []
def double([h | t]), do: [h * 2 | double(t)]
```

Tracing a recursion by hand — worth doing once, in full:

```
sum([1, 2, 3]) = 1 + sum([2, 3])
               = 1 + (2 + sum([3]))
               = 1 + (2 + (3 + sum([]))) = 1 + (2 + (3 + 0)) = 6
```

The stack grows to depth n: each pending `+` waits for the recursive call to
return. Lesson 5 is the transformation that removes that stack.

Check laws in `iex` before proving them — a counterexample is far cheaper to
find than a failed proof is to write:
`Enum.reverse(xs ++ ys) == Enum.reverse(ys) ++ Enum.reverse(xs)`.
