## Exercise

### 1. Establish the two views

A PID namespace gives processes a distinct set of process IDs. The mount namespace here keeps the experiment's `/proc` view separate from the VM's normal one. Open a second Ubuntu terminal for outside observations. In the first, from the repository root:

```sh
readlink /proc/self/ns/pid
unshare --user --map-root-user --pid --fork --mount-proc --kill-child /usr/bin/python3 -c 'import os,time; print("syllabus-m1-22", os.getpid(), os.getuid(), flush=True); time.sleep(15)'
```

`--user --map-root-user` maps your ordinary account to root within a new user namespace; it does not make you root on the VM. The PID/mount flags establish the views, `--fork` starts the child inside them, and `--kill-child` bounds its lifetime if the wrapper exits. This is a worked experiment; predict before running and retain the actual output.

### 2. Inspect from outside

While it sleeps, in the second terminal run `ps -u ubuntu -o pid,ppid,comm,args` and find the Python command containing `syllabus-m1-22`. Record that fresh PID. Use `cat /proc/PID/status`, replacing PID with the observed number, and compare its Pid/NSpid fields with the number printed inside. Use `readlink /proc/PID/ns/pid` to compare namespace handles. These are observations, not signal targets.

### 3. Handle a permission refusal

If unprivileged user namespaces are refused, retain the command/error first. On this authorized VM the operator may repeat with `sudo unshare --pid --fork --mount-proc --kill-child --setgid "$(id -g)" --setuid "$(id -u)" /usr/bin/python3 -c 'import os,time; print("syllabus-m1-22", os.getpid(), os.getuid(), flush=True); time.sleep(15)'`. This performs setup with authority and drops the workload to the ordinary user's numeric identity. Record which route actually ran; do not change AppArmor or kernel policy. If it still fails, the experiment remains blocked.
