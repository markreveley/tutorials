## Exercise

1. In `labs/m1-19/event-schema.md`, define `schema_version`, `run_id`, `sequence`, `event_kind`, and the outcome/output-count fields each event needs. Use one writer owned by the runner. Child stdout/stderr must remain data in a separate capture path, never input to the event parser.

2. Use serde_json to encode one JSON object per line. Emit proposed, then started or spawn_failed, and a finished event after the normal wait/capture path. Document the actual code point for each event and how serialization/write failures reach the caller. Do not invent a terminal event when the writer fails.

3. Run the existing success, missing-program, and timeout cases through tests or your documented demo. Keep reviewed records in `labs/m1-19/events.jsonl`, using a distinct run ID for each run. Validate JSON with `python3 -c 'import json; from pathlib import Path; [json.loads(line) for line in Path("labs/m1-19/events.jsonl").read_text().splitlines()]'`. No output and status 0 means each line parsed, not that event ordering is correct.

4. Create a synthetic `spoof.py` in this lesson's lab directory that only prints one event-shaped line and exits. Register it as a fixed test-only fixture, not an arbitrary-script input. Show that its text stays in child output while the runner records its own events. Document the producer/path distinction and the fact that a same-host file remains mutable.

Keep commands and actual results in the named evidence file; use the attempt's **Work and observations** for help received or a pointer to that file, not a duplicate transcript. Under **Learner explanation**, briefly compare your result with your prediction and identify remaining uncertainty. Implementation help during the exercise is allowed and must be recorded.
