## Exercise

1. Create `labs/m1-27/demo.sh` using the reviewed M1-23 namespace lifecycle and M1-25/26 service behavior. Give it fixed case names only. Use a fresh `syllabus-m1-27-` namespace and service, User=ubuntu, and the previously demonstrated CPU/memory/runtime limits. To the service command add `--property=NoNewPrivileges=yes`, `--property=NetworkNamespacePath="/run/netns/$netns"`, and `--property=WorkingDirectory=/home/ubuntu/syllabus`. Here netns holds this run's exact namespace name. NoNewPrivileges prevents gaining privilege through executable transitions; it does not remove permissions already held. NetworkNamespacePath places the job in the named network view. Document the actual settings and case-specific limits in the script.

2. Build the runner with `cargo build --manifest-path capstone/Cargo.toml`. Run its documented success case using the absolute executable path under `/home/ubuntu/syllabus/capstone/target/debug/`. Record the binary's real name from Cargo.toml; do not assume the package name. For live placement inspection, use a separate fixed Sleep(5) case with an 8-second runner deadline and a 10-second service limit, adding only that fixed demo label if needed. Immediately inspect MainPID, ControlGroup, and `/proc/PID/ns/net`. Compare the number in that proc symlink with `stat -Lc '%i' /run/netns/NAME`, replacing NAME with this run's namespace. The named path is a mounted namespace handle; its inode identifies the namespace. If the process exits before inspection, repeat a finite run instead of inferring placement from its command line.

3. Repeat the M1-23 host-loopback success/failure comparison with the namespace client started through the same service settings. Use the fixed curl endpoint case only, with short client and server limits. Then run the M1-26 finite descendant case through this composition. Reuse existing request mappings and capture paths; no new networking framework is needed.

4. In `labs/m1-27/control-evidence.md`, map each control to its actual evidence: validation, retained-output cap, direct-child deadline, service limit, namespace placement, and outside observation. Explain what still operates if the runner fails and which records may be incomplete.

5. Capture results, stop the exact service, confirm its descendants and namespace members are gone, then delete the exact namespace. Put that order in a cleanup trap as well as the successful path. Update the capstone README with the observed commands and limits. Keep failed composition attempts; do not change global networking to make a test pass.

Keep commands and actual results in the named evidence file; use the attempt's **Work and observations** for help received or a pointer to that file, not a duplicate transcript. Under **Learner explanation**, briefly compare your result with your prediction and identify remaining uncertainty. Implementation help during the exercise is allowed and must be recorded.
