## Exercise

1. In `labs/m1-02/comparison.md`, make one row each for E2B, Fly.io Sprites, and Firecracker. Firecracker is included as a component comparison, not assumed to be a hosted service. For each, record who operates it, where it runs, what the provider can access, and a dated link supporting each claim. Mark undocumented items as unknown.

2. Use these definitions while comparing: a control plane starts/manages workloads; BYOC means deployment into a customer's cloud account; on-premises means customer-controlled physical premises. These distinctions matter because control of an account does not by itself prove control of updates, keys, or telemetry. Add those three columns and customer-hardware installation evidence to your comparison.

3. Create `labs/m1-02/threat-model.md`. For a hypothetical product that runs one customer's finite task, draw the requester, runner, operating-system kernel, input files, credentials, and results. A threat model names what needs protection, from whom, and what is trusted. State assumptions as provisional; M1-01 supplied no customer deployment requirements.

4. Write five candidate promises, each with a concrete failure example that would disprove it or an unanswered requirement. Update only the relevant product rows in `curriculum/open-questions.md`. Treat Sprites here as Fly.io's named service; whether a proposed product uses it is an open design choice. The step is finished when every claim has a source or an explicit unknown; polished vendor language is not evidence.

Keep commands and actual results in the named evidence file; use the attempt's **Work and observations** for help received or a pointer to that file, not a duplicate transcript. Under **Learner explanation**, briefly compare your result with your prediction and identify remaining uncertainty. Implementation help during the exercise is allowed and must be recorded.
