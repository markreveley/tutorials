## Predict before reading

Ask this one question and wait:

> When a program finishes, what do you think its exit code tells the shell?

Accept uncertainty. Preserve the learner's actual answer before explaining. If that prediction is already recorded, use it without asking again.

## Prescribed reading, in order

No separate reading assignment. After the prediction, explain these terms in the conversation as they become necessary:

- The shell interprets commands typed in Terminal.
- A program can send messages through normal output (stdout) and diagnostic output (stderr). Both normally appear in Terminal; a message's channel alone does not establish success or failure.
- On normal exit, a program supplies a numeric exit status. Conventionally 0 reports success and a nonzero value reports an unsuccessful outcome; the meaning of a particular nonzero value depends on the program.
- An exit status is a report from the program, not independent proof that it accomplished the intended task.

Use short explanations and pause for questions. These are teaching points, not an answer to a fresh independent check. Rust reading belongs to the first Rust lesson; Git is introduced only when saving this work below.

## Exercise

### Run and observe

Introduce labs/fixtures/workload.py as a supplied test program whose output we control. In its exit mode, --code chooses the status it reports; it does not perform a real job whose success has been independently checked.

Give the learner this pair of commands, to run one line at a time from the repository root:

```sh
python3 labs/fixtures/workload.py exit --code 0
echo $?
```

Explain that $? holds the previous command's status and echo displays it. Ask the learner to paste the messages and numeric result here; the agent records them once. An intervening command changes $?.

After discussing that observation, ask what they expect to change if the requested code becomes 7. Wait before presenting:

```sh
python3 labs/fixtures/workload.py exit --code 7
echo $?
```

For the agent's comparison: each supplied run prints synthetic stdout and synthetic stderr, then echo should show the requested number. These are expected values, not observed evidence. Preserve differences and investigate them.

If both runs/statuses are already recorded, move to the explanation. If only stream text is missing, explain that gap and request one focused rerun when needed; do not restart setup or erase earlier observations.

### Explain the observed result

Use the learner's existing explanation to identify the next teaching point. Ask one question at a time about the result: distinguish what the Python program reports, what echo displays, and what those observations establish. Supply an explanation for a named uncertainty before asking the learner to reconsider it; this is guided practice, not an independent check.

For the current learner, statuses 0 and 7 and uncertainty about their meaning are already recorded. Explain the success/nonzero convention and that this fixture deliberately chooses its report. Then ask:

> If this program prints a message on stderr, does that alone tell you it failed, or would you look at something else?

Wait for the answer. Do not generate an explanation in the learner's voice or mark the question independently passed. After this discussion, recover any missing actual stream observation with a single focused run, then offer the fresh check.

## Independent understanding check

Offer the check in the conversation when guided practice is understood. No special request phrase or separate file is needed from the learner.

Assign a fresh exit-code value within the fixture's 0–125 range, different from the worked values. Ask the learner to predict the result and provide their own command to run it and inspect its status. Obtain that attempt before hints or repairs.

After execution, ask the learner to distinguish the printed messages from the numeric status and explain whether the status independently proves useful work was accomplished. Use the actual result and explanation to assess understanding, not command success alone.

Record the case, prediction/command, actual result, explanation, assistance and assessment in the active session record. A hinted attempt is assisted; teach the gap, then assign a different case. File selection, Git terminology and Rust examples are not part of this lesson's independent check.
