## Exercise

1. In `capstone/src/lib.rs`, implement the run function for the fixed Exit fixture using `Command::spawn` and `Child::wait`. Inherit output streams for this lesson. Keep validation errors, spawn errors, wait errors, and a child's unsuccessful exit distinguishable at the public boundary.

2. Add `capstone/src/main.rs` as a small demonstration: accept only the fixed case labels `exit-zero`, `exit-seven`, and `missing-program`. The first two run the supplied fixture; the last tries `/home/ubuntu/syllabus/scratch/m1-11/absent-python`, which the preflight confirms is absent. No arbitrary executable input is required. Document the exact case-label mapping in `labs/m1-11/outcomes.md`.

3. Run `cargo run --manifest-path capstone/Cargo.toml -- exit-zero`, then repeat with `exit-seven` and `missing-program`. The first two should start a child and report its status; the third should report an OS launch error. Record actual stdout/stderr and your runner's reported result for each. The Cargo command's status is not automatically the child's status; state how your demo maps outcomes.

4. Trace who owns the request data and child handle, and list every operation that may fail. Explain the normal wait/reap obligation and what an early return would leave behind. Keep the model limited to one finite child; output capture and deadlines are not implemented today.

Keep commands and actual results in the named evidence file; use the attempt's **Work and observations** for help received or a pointer to that file, not a duplicate transcript. Under **Learner explanation**, briefly compare your result with your prediction and identify remaining uncertainty. Implementation help during the exercise is allowed and must be recorded.
