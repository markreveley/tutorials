Module 3 · Models as objects

The same activation in transformers, TransformerLens 4, and nnsight

Three toolkits, one residual stream. Two of them agree to the last bit; the third agrees only after you understand what its compatibility mode changed.

Why you need all three

Papers and notebooks use whichever toolkit their authors used. TransformerLens gives named hook points and an ActivationCache; nnsight gives a tracing context that works on any Hugging Face model and can run remotely; raw hooks give you control and no dependency. You will read all three, and the readiness review asks you to reconcile them. The script below captures the residual stream after block 5 for the same prompt each way and compares the numbers.

TransformerLens 4: TransformerBridge

TransformerLens 4.0 removed the legacy HookedTransformer stack; the replacement is TransformerBridge.boot_transformers(name), optionally followed by enable_compatibility_mode() [TransformerLens: migrating to 4.0]. The bridge wraps the Hugging Face model and exposes TransformerLens names; run_with_cache(prompt) returns logits and a cache keyed by strings such as blocks.5.hook_resid_post, 493 entries for GPT-2 small. That key worked unchanged in the installed 4.2.0; the migration page does not promise it, so the transcript is the evidence.

Without compatibility mode the bridge uses the raw Hugging Face weights, and hook_resid_post matches the transformers hook to 2e-5: float32 noise from a different order of operations. With compatibility mode the difference is 4.64, which looks like a bug and is not. Compatibility mode reproduces HookedTransformer's default weight processing: LayerNorm folding, center_writing_weights, and center_unembed [TransformerLens: migrating to 4.0]. Centring the writing weights makes every vector written to the residual stream have zero mean over d_model, which is harmless to the model (LayerNorm removes the mean anyway) and changes every cached residual by exactly that mean. Subtract the mean over the last axis from the transformers activation, as the next line does, and the two agree to 5e-4. center_last_axis in the shape lab is this operation.

The logits differ for the same reason: center_unembed subtracts the mean logit, which leaves the softmax and the argmax unchanged. And prepend_bos defaults to true, so the default call gives a sequence of 6, not 5; pass prepend_bos=False when comparing with other toolkits, and say which you used in your manifest.

nnsight: trace and save

LanguageModel("gpt2") wraps the model, and the module tree keeps Hugging Face's names. Inside with model.trace(prompt):, model.transformer.h[5].output refers to that module's forward-pass return value, and .save() marks it to be returned after the trace [nnsight: getting activations]. The body of the block is captured and run through the backend rather than executed inline [nnsight: tracer]; saved values are real tensors once the block exits, which is why the print is after the with. The numbers are bit-identical to the raw hook, because nnsight is running the same model with no weight processing.

Two behaviours follow from "captured, not executed". Access modules in forward order inside one trace: saving wte.output after h[5].output raises an out-of-order error, because the model has already run past the embedding when the request is made. And a trace block must live in a file or a notebook cell; typed into an interactive python3 prompt it fails, because the tracer needs the source of the block. The roadmap recorded both when verifying the toolchain.

In eval and interpretability work

When a notebook's numbers do not match yours, the first three questions are: was a BOS token prepended, was compatibility mode on, and which layer convention was used. All three change the tensor without changing the model, and all three belong in a manifest.

Pitfall

Comparing a TransformerLens cache in compatibility mode with raw hidden states and concluding the model is "different". It is the same model with centred writing weights. Centre the raw activation over d_model before comparing, or load the bridge without compatibility mode when you want raw numbers.

Check your understanding

A TransformerLens notebook reports that the residual stream at blocks.5.hook_resid_post has a mean of exactly zero across features at every position. Your transformers hook gives a mean of about 0.07. Which is "right", and what claim would be wrong to make?

Reveal the reasoning

Both are right for what they are. The bridge in compatibility mode centred the writing weights, so a zero feature-mean is a property of its representation, not of GPT-2. A claim such as "GPT-2's residual stream is centred" is wrong; "after centring, these two directions are orthogonal" is fine if you say you centred. Record the mode.

What to look for

Identical still, for nnsight; the mechanism does not depend on the layer. The compatibility-mode difference grows with the residual norm, which lesson 12 showed climbing to several hundred by block 11, and still vanishes after centring. If you also compare ln_final.hook_normalized with hidden_states[12], expect a scale difference from folded LayerNorm weights.
