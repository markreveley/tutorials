Module 0 · Orientation and setup

Lab setup: a CPU-only toolchain you can trust

A virtualenv, a CPU build of torch, pinned versions you can report, GPT-2 small in the local cache, and the habit of checking shapes interactively.

Why a local, CPU-only setup is enough

GPT-2 small has 124 million parameters and runs a five-token prompt on a laptop CPU in well under a second. Everything in this course, and most of the next three, fits in a few gigabytes of RAM with no GPU. A free Colab notebook works too and is covered below, but a local virtualenv is worth having because it is the environment you will run tests in, and tests are how this course checks you.

The authoring environment is recorded at the top of the transcript: Python 3.13, torch 2.14.1 CPU build, transformers 5.20.2, transformer_lens 4.2.0, nnsight 0.8.1, numpy 2.5.4. You do not need those exact versions, but when an output differs from the lesson, compare versions first.

Create the environment

From the course directory. These are instructions, not a transcript: the verifier does not run installers, and the only outputs shown on this page are from the two commands at the bottom.

python3 -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
python3 -m pip install --upgrade pip
python3 -m pip install numpy
python3 -m pip install torch --index-url https://download.pytorch.org/whl/cpu
python3 -m pip install transformers safetensors
python3 -m pip install transformer-lens nnsight   # for lesson 14; optional until then
python3 -m pip freeze > research/my-versions.txt   # what you actually got

Three things deserve a sentence each. The --index-url for torch selects the CPU wheel; the default PyPI wheel on Linux pulls in several gigabytes of CUDA libraries you cannot use without a GPU. If you install torchvision later for the interpretability course, install it from the same CPU index in the same command, because a torchvision built for CUDA will fail to import against a CPU torch. And pip freeze is the cheapest reproducibility habit there is: a file you can paste into a bug report.

The .venv directory is ignored by git in this course. Never commit it, and never install into a virtualenv someone else's tests depend on without asking.

The Colab alternative

A free Colab runtime already has torch and transformers installed. Upload or clone this repository, open a notebook, and run !pip install transformer-lens nnsight in the first cell. Two differences matter. Colab's torch is usually a CUDA build, so torch.cuda.is_available() may be true and tensors created on the GPU must be moved with .cpu() before .numpy(). And a notebook cell is a file for nnsight's purposes, so its trace blocks work there, while pasting one into an interactive python3 prompt does not (lesson 14 explains why).

Get GPT-2 small into the cache once

The first time AutoModelForCausalLM.from_pretrained("gpt2") runs it downloads about 550 MB into ~/.cache/huggingface/hub. After that, set HF_HUB_OFFLINE=1 in your shell so that later runs never touch the network, which makes them faster, deterministic, and runnable on a train. The example scripts set that variable themselves if you have not. If a script fails with a message about not being able to reach the Hub, run it once without the variable to download, then set it again.

Check shapes interactively

You will spend a lot of time at a prompt asking tensors what they are. Three habits make that fast. Start python3 -i labs/examples/check_setup.py to run a script and drop into a prompt with its variables alive. At the prompt, x.shape, x.dtype and x.device answer the three questions that matter; type(x) tells you whether you hold a tensor, a tuple of tensors, or a ModelOutput. And a one-line assert, assert x.shape == (2, 5, 768), x.shape, is cheaper than any amount of printing: it fails loudly, and the message tells you what you had.

Two shell variables are worth setting while you learn: HF_HUB_DISABLE_PROGRESS_BARS=1 keeps progress bars out of transcripts, and TRANSFORMERS_VERBOSITY=error hides advisory warnings so a real one stands out.

Verify the setup

Run the check script, then the environment tests. The test file ships passing; it tests your machine, not you. If torch is missing the torch tests skip with a message that says so instead of failing, which is the behaviour every lab test in this course has.

$ python3 labs/examples/check_setup.py
python 3.13.16
numpy 2.5.4
torch 2.14.1+cpu | cuda available: False
transformers 5.20.2
a batch of 2 prompts, 5 tokens each, 768 numbers per token: (2, 5, 768)
x.shape[0] is the batch: 2 | x.shape[-1] is d_model: 768
$ python3 -m unittest discover -s labs -p 'test_environment.py' -v
(no output)

Read the names of the tests as a preview: thirteen hidden states of (batch, seq, 768), logits of (1, 5, 50257), and a config of 12 layers, 768 features and 12 heads. Those are the numbers of GPT-2 small, and lesson 12 explains each.

In eval and interpretability work

A result you cannot reproduce on a second machine is a result you cannot defend. The habit starts here: one environment file, offline runs by default, and a test you can run on arrival that says whether the machine is ready.

Pitfall

Installing torch from PyPI on a Linux box without a GPU, waiting for several gigabytes, and then installing torchvision from a different index. The CPU index exists to avoid both problems; use it for every torch-family package at once.

Check your understanding

Your laptop and a colleague's produce slightly different hidden-state values for the same prompt, around 1e-6 apart. Is the setup broken?

Reveal the reasoning

Probably not. Floating-point results are not guaranteed identical across platforms, BLAS libraries, or torch versions; the reproducibility notes say so explicitly. A difference of 1e-6 in float32 with identical argmax is normal. A difference of 1e-1, or a different top token, is a real bug: different weights, different tokenization, or a hook changing something.

Practice

Run the environment tests with -v and then deliberately break something: unset HF_HUB_OFFLINE and rename your Hugging Face cache directory temporarily, and run again. Read how the GPT-2 tests report it. Restore the cache afterwards.

$ python3 -m unittest discover -s labs -p 'test_environment.py' -v
(no output)
What to look for

The GPT-2 tests should skip with a message naming the cache, not error. A test suite that distinguishes "cannot run here" from "wrong" is one you can trust in a CI log. Notice also that the NumPy and torch tests still ran: the skip is per class.
