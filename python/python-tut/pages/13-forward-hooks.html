Module 3 · Models as objects

Forward hooks: registering, capturing, and caching activations with shapes asserted

A hook is a function the model calls for you after a module runs. Register it, copy what you need, assert the shape, and remove it. Every step has a way to go wrong.

The API in one paragraph

module.register_forward_hook(hook) registers a function with signature hook(module, args, output) -> None or modified output, called every time after forward() has computed an output; it returns a handle, and handle.remove() unregisters it [PyTorch: nn.Module]. The hook can return a modified output, which is how interventions are done; for caching you return nothing. register_forward_pre_hook runs before forward with the inputs, and with_kwargs=True passes keyword arguments too. That is the entire mechanism under TransformerLens's HookPoints and most of nnsight.

$ python3 labs/examples/hooks_cache.py
hooks registered: 12 | handle type: RemovableHandle
captured: ['block.0', 'block.1', 'block.2'] ... block.11
every block output has shape (1, 5, 768)
block.5 equals hidden_states[6]: True
block.11 equals hidden_states[12]: False (ln_f applied to [12])
saved and reloaded: 12 tensors, 188 kB, block.5 identical: True
forgot h.remove(): a second forward still fires the hook -> True

Read the script

make_hook(name) is a closure factory from lesson 05: each call returns a hook that remembers its own name, so a list comprehension registers twelve distinct hooks in one line. Inside, output[0] if isinstance(output, tuple) else output normalises: in this transformers version a GPT2Block returns the residual-stream tensor directly, but other modules and other versions return tuples, and a hook that assumes one form breaks on the other. Then .detach().clone(), lessons 09 and 02: cut from the graph, and own the memory.

The forward pass runs inside try and the removal inside finally, so a failing forward cannot leave hooks behind. The output then checks every captured tensor against (batch, seq, 768), float32, no grad, and finite. Those four asserts are the shape discipline of the course in four lines; put them in a function and call it after every capture.

Which tensor did you capture?

The two equality lines are the point of the script. block.5 is identical to hidden_states[6], confirming the convention from lesson 12. block.11 is not identical to hidden_states[12], because the tuple's last entry has ln_f applied and the block output does not. A hook on transformer.drop captures hidden_states[0], the embedding output. With that mapping you can produce the whole hidden_states tuple from hooks, and the cache_residual_stream stub in labs/hooks.py asks you to do exactly that, with a test that checks the mapping entry by entry.

Hooks go anywhere in the tree, which is their advantage over output_hidden_states. transformer.h.5.mlp gives the MLP's contribution before it is added to the residual stream; transformer.h.5.attn gives attention's; transformer.h.5.ln_1 gives what attention actually read. Those are the hook_mlp_out, hook_attn_out and ln1.hook_normalized of TransformerLens, and the table in lesson 14 maps them.

To disk and back

torch.save(dict_of_tensors, path) and torch.load round-trip the cache; 188 kB for twelve (1, 5, 768) float32 tensors, which is 12·5·768·4 bytes plus headers. torch.load uses pickle, so loading a file you did not produce executes whatever it contains; lesson 15 switches to safetensors for files that leave your machine. Either way, save the detached clones, never the raw outputs, and save a manifest beside the file that says which prompts, which blocks, and which convention.

The leaked hook

The last lines register a hook, run a forward pass, and run another without removing it. The hook fires again. Nothing warns. In a notebook, where a cell is re-run ten times, that is ten hooks on one module, each appending to a list, and a cache that grows and slows with no error. The remedy is structural: register in a function that removes in finally, or use the context-manager idiom from lesson 05, and never register a hook at top level in a notebook. The lab test that counts hooks before and after your function is there to make the discipline mechanical.

In eval and interpretability work

The prediction-test habit from the roadmap starts here: before you look at an activation, write the assert that says what shape it must have and which block it came from. A cache that passes assert_cache_shapes is a cache you can make claims about; one that does not is a bug report.

Pitfall

Storing output without detach() under a forward pass that was not in no_grad. The cache then holds the whole autograd graph of the forward pass, memory climbs with every prompt, and torch.save writes the graph's saved tensors too.

Check your understanding

A colleague's hook is lambda m, a, o: cache.append(o), registered on every block, run over 100 prompts in a notebook. The cache has 1,200 entries the first time and 2,400 after re-running the cell. Explain both numbers and fix the hook in three changes.

Reveal the reasoning

1,200 is 12 blocks times 100 prompts. 2,400 means the first set of hooks was never removed, so the re-run registered a second set and each block fired twice. Changes: store o.detach().clone() rather than o; key the cache by block and prompt rather than appending; and register inside a function that removes the handles in finally.

Practice

Implement cache_residual_stream and assert_cache_shapes in labs/hooks.py and make test_hooks.py green. One test feeds an out-of-vocabulary id to make the forward pass fail; your hooks must still be gone afterwards.

$ python3 -m unittest discover -s labs -p 'test_hooks.py' 2>&1 | tail -1
FAILED (errors=14)
What to look for

The embedding lookup raises on id 1,000,000, so the exception propagates through your function; finally runs; the hook counts match. The equality tests then confirm your mapping: embed from transformer.drop, block.i equal to hidden_states[i + 1] for i up to 10, and block.11 differing from hidden_states[12] by ln_f.
