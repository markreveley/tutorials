Module 1 · Python for someone who writes Elixir and Rust

Names bind to objects; mutation is visible through every name

Python has no immutability by default and no ownership. A name is a label on an object, and whoever holds a label can change the object.

The model you must replace

In Elixir, list = [1, 2] followed by other = list gives two names for a value that nobody can change; [0 | list] is a new list. In Rust, let other = list; moves ownership and the compiler stops you using list again. Python does neither. Assignment binds a name to an object; the object has an identity, a type, and a value, and only the value can change [Python: data model]. Two names bound to one mutable object are two doors into the same room.

The language reference puts it in one sentence: numbers, strings and tuples are immutable, while dictionaries and lists are mutable. Add to the mutable side everything that matters in this course: NumPy arrays, torch tensors, nn.Modules, and the dictionaries that hold activation caches.

Read the output line by line

same = scores creates no list. same.append(0.9) mutates the one list, so scores sees it, and scores is same is true because is compares identity, the thing id() returns. list(scores) builds a new list with the same elements, so appending to fresh leaves scores alone; is is now false even though the first three elements are equal. That is the whole difference between is and ==: identity versus value.

The shallow copy of run is a new dict, but its "prompts" value is the same list object as the original's. Appending through the copy changes the original. copy.deepcopy copies recursively and breaks the sharing. You will meet exactly this when you copy a config dict, edit a nested list of hook names, and discover the original config changed too.

The tuple line shows what immutability looks like when you do have it: t + (3,) is a new object, t is untouched. The integer line shows the same for numbers, and explains why b += 1 did not change a: there is no integer to mutate, so += rebinds b to a new int. On a list, b += [1] mutates in place. Same operator, two behaviours, decided by the type.

The mutable default argument

def record(result, log=[]) evaluates [] once, when the function is defined, and every call without a log argument shares that one list. The output shows the second call returning both results. The idiom is log=None and log = [] if log is None else log inside the body. The dataclass module raises an error for a list default for exactly this reason, which lesson 05 shows.

Where this bites in model work

A hook that stores output in a dict stores a reference to the tensor the model is still using; if a later in-place operation touches that tensor, your cache changes after the fact. Lesson 13's hooks call .detach().clone() for that reason. A function that "returns" a modified dict by mutating its argument changes the caller's object; the eval-pipeline spec forbids mutating inputs precisely so results stay comparable. And a = b = torch.zeros(3) gives two names for one tensor, not two tensors.

The habit from Rust that transfers best is asking "who else holds this?" before mutating. Python does not answer the question for you, so answer it by convention: functions that take data return new data unless their name says otherwise (sort() mutates and returns None; sorted() returns a new list), and anything you cache gets copied on the way in.

In eval and interpretability work

The eval-pipeline tests check that score_ticket and summarize_run do not mutate their inputs. That is not pedantry: a grader that normalises a prediction in place changes the record that gets logged, and the log no longer shows what the model said.

Pitfall

Using is to compare values. x is 5 and s is "gpt2" happen to work for small ints and short strings because the interpreter caches them, and silently fail elsewhere. Use == for values and reserve is for None, True, False, and genuine identity questions.

Check your understanding

A function receives a list of result dicts and must return the same list with a "passed" field added to each. A colleague writes for r in results: r["passed"] = grade(r) and returns results. What has changed for the caller, and is that acceptable?

Reveal the reasoning

Every dict the caller holds now has a new key, because the loop mutated the shared objects; the list itself was also returned unchanged in identity. Whether that is acceptable depends on the contract. If the caller logged the raw results first, the log is now stale. The safer default is [{**r, "passed": grade(r)} for r in results]: new dicts, originals untouched, and the function name can then promise it.

What to look for

The common misses are the shallow copy sharing the inner list, and b += 1 not affecting a. Both come from the same rule: assignment and augmented assignment act on names and on the object's type; they never copy.
