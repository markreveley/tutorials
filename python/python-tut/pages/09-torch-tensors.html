Module 2 · Arrays and tensors

torch tensors: dtype, device, views versus copies, in-place ops, no_grad

A tensor is a NumPy array with three extra facts attached: a device, a dtype that is enforced rather than promoted, and an optional autograd history.

The three facts to check

Every tensor answers t.shape, t.dtype, and t.device. Shape works as in NumPy; torch.Size is a tuple subclass, so t.shape == (3, 4) is a valid comparison and t.shape[-1] is the last size. The default float dtype is float32, not NumPy's float64, and models are stored in it. The device is cpu throughout this course; on a GPU box you move tensors with .to("cuda") and must move them back with .cpu() before .numpy().

dtype is enforced

NumPy promoted float32 plus float64 to float64. Torch raises for a float32 matrix product with a float64 operand, as the third line shows. This is the right behaviour for model code, where an accidental promotion would double memory and halve speed, but it means a NumPy array you convert with torch.from_numpy arrives as float64 if that is what NumPy made, and the model refuses it. Convert with .float() or .to(torch.float32), and keep .half() for when you know the model was trained or quantised in half precision.

Views, contiguity, and the two reshape methods

A view shares the underlying data with its base tensor, so writing through the view changes the base [PyTorch: views]. a.view(6) above is a view: a[0, 0] became 7 and data_ptr() is the same address. transpose, permute, squeeze, and basic slicing return views too. A view of a contiguous tensor can be non-contiguous; the transpose shows is_contiguous() false, and .view then fails because it needs a contiguous buffer. .reshape returns a view when it can and a copy when it must, so code should not assume either [PyTorch: views]; .contiguous() returns the tensor itself if already contiguous and a copy otherwise.

The practical rule: use .reshape unless you specifically need the guarantee that no copy happened, and call .clone() on anything you cache. Lesson 13's hooks do exactly that, because the alternative is a cache that aliases the model's working memory.

In-place operations

A trailing underscore means in place: b.add_(1) changes b's storage and returns it. Every alias sees it; c.mul_(2) doubled b. In-place ops save memory and are everywhere in model code (x.masked_fill_, param.data.zero_()), and they have two costs. They interact badly with autograd, which may need the overwritten value for a gradient and will raise if a saved tensor was modified [PyTorch: autograd]. And they cannot change shape through a broadcast. Default to the out-of-place form and reach for the underscore when you have measured a need.

torch.from_numpy shares memory with the array, and .numpy() shares it back: changing one changes the other, as the n[0] = 5 line shows. That is a view across libraries, and the same aliasing rules apply.

requires_grad, no_grad, and detach

w = torch.ones(3, requires_grad=True) asks autograd to record operations on w. The result y then has requires_grad true and a grad_fn, the node that knows how to differentiate a sum. Inside torch.no_grad() the same computation is not recorded: z.grad_fn is None. The autograd notes describe no-grad mode as making computations behave as if none of the inputs require grad, and recommend it for operations that should not be recorded [PyTorch: autograd]. Every forward pass in this course whose gradients you do not need runs under it, which is all of them except the fit in lesson 10.

detach() returns a tensor sharing data with the original but cut from the graph. It is what you call on a captured activation before storing it, and before .numpy(): the output shows w.numpy() refusing because the tensor requires grad, and w.detach().numpy() working. .item() extracts a one-element tensor as a Python number, and .tolist() converts a whole tensor; both are how a tensor becomes something json.dumps accepts.

In eval and interpretability work

A cache that holds tensors with requires_grad=True keeps every intermediate of the forward pass alive through their grad_fn chains. The memory does not come back until the cache is dropped, and torch.save of such a tensor is larger and slower. no_grad on the way in and detach().clone() on the way out is the whole discipline.

Pitfall

Calling .view(-1) on a transposed or permuted tensor, getting a RuntimeError about strides, and "fixing" it by sprinkling .contiguous() everywhere. Understand why the tensor was non-contiguous first; usually a permute produced it and .reshape is the honest call.

Check your understanding

A hook stores output directly in a dict during a forward pass under torch.no_grad(). Later, a different part of the code runs x.add_(bias) on what turns out to be the same storage. Which lesson-02 rule applies, and what should the hook have done?

Reveal the reasoning

Aliasing: the dict holds a reference to the model's tensor, not a copy, so the in-place add changes the cache after the fact. The hook should store output.detach().clone(). no_grad solved the autograd half of the problem, not the identity half; they are separate.

Practice

At a prompt, build t = torch.arange(6.0).reshape(2, 3). Predict and then check: whether t.t() is contiguous; whether t.t().view(6) raises; whether t.t().reshape(6) shares storage with t (data_ptr()); and whether t[0].add_(1) changes t.

What to look for

Not contiguous; raises; does not share storage because reshape had to copy; and yes, because t[0] is a view and add_ writes through it. If any prediction was wrong, re-read the views section before moving on; lesson 13 relies on all four.
