Spec-first testing with unittest: the three eval-pipeline labs

You already write the test first. Here is how that habit looks in Python, using the three functions whose tests are waiting for you.

unittest in five lines

A test is a method starting with test_ on a class that subclasses unittest.TestCase. Assertions are methods: assertEqual, assertIs, assertTrue, assertRaises. Discovery runs every file matching a pattern under a start directory: python3 -m unittest discover -s labs -p 'test_*.py', where -s is the start directory and -p the file pattern [Python: unittest]. Add -v to see each test's name and result. There is no fixture magic to learn beyond setUp, which runs before each test, and setUpClass, which runs once per class and is where expensive things like loading GPT-2 belong.

import unittest
import shapes

class RowNormalizeTests(unittest.TestCase):
    def test_zero_rows_stay_zero_without_nan(self):
        x = np.array([[3.0, 4.0], [0.0, 0.0]])
        np.testing.assert_allclose(shapes.row_normalize(x), [[0.6, 0.8], [0.0, 0.0]])

    def test_mismatch_raises_value_error(self):
        with self.assertRaises(ValueError):
            shapes.broadcast_shape((4, 3), (4,))

Two idioms matter more than the rest. assertRaises as a context manager wraps exactly the call that should fail, so a typo on the line before cannot pass the test by accident. And subTest labels each case of a parameterised loop, so when the loop fails you are told which input did it rather than just that the first one did. The eval-pipeline tests use both, heavily.

The three functions and what their tests say

The spec is labs/ASSESSMENTS.md and the tests are dag-tests/test_python_evals.py at the repository root. Read the tests as the specification they are, the way you would read a Rust test module before touching the implementation.

score_ticket(prediction, reference) -> bool. A malformed reference is an evaluation defect and raises ValueError; a malformed prediction is a candidate failure and returns False. The pass condition is exact: same key set, and for each key the same type and the same value. The tests include reference(urgent=1), which is == to the reference and must still fail, and reference(category="refund "), which is not trimmed. Return True and False themselves: assertIs rejects a truthy 1.

load_cases(path) -> list[dict]. Read UTF-8 JSONL, validate every record and its nested reference, reject duplicate JSON keys at any depth and duplicate case ids, and raise ValueError with line N in the message, where N is the physical line. Keep FileNotFoundError distinct. Everything you need was in lesson 03: enumerate(f, start=1), object_pairs_hook, and the type checks.

summarize_run(scheduled_ids, results) -> dict. Account for every scheduled case as scored, errored, or missing; counts are int, rates are float or None when the denominator is zero; duplicates and unknown ids raise. The tests check type(result["scored"]) is int, so do not let a numpy.int64 or a bool leak in, and check the identities passed + failed == scored and scored + errors + missing == scheduled hold for your output before the tests do.

Run them red first

From the repository root. The stubs raise NotImplementedError, so every test errors. That is the starting state, and the last three lines of the output are the ones to watch as you work.

$ cd ../.. && python3 -m unittest discover -s dag-tests -p 'test_python_evals.py' 2>&1 | tail -3
Ran 22 tests in 0.083s

FAILED (errors=65)

Work one class at a time: ScorerTests, then LoaderTests, then ReportingTests. Run a single class with python3 -m unittest dag-tests.test_python_evals.ScorerTests from the root if your layout allows it, or simply filter by eye with -v. Each time a test goes green, read its name again and ask whether your code passes it for the stated reason or by coincidence.

The same pattern in this course's labs

The labs under labs/ follow the same rule: a stub, a test file, and a spec section in ASSESSMENTS.md. The shape lab is red now too, and will stay red until lesson 07.

One habit from spec-first work in any language transfers unchanged: when a test is hard to make pass, the test is telling you about the design. summarize_run is easier with a Counter and a set of seen ids than with nested ifs, and the "do not mutate inputs" tests are trivially satisfied by never writing to the arguments.

In eval and interpretability work

The three functions are an eval runner in miniature: a scorer with an explicit policy, a loader that refuses bad data loudly, and a report that keeps failures in the denominator. Every eval harness you will meet has the same three parts, and the same three ways to be quietly wrong.

Pitfall

Reading the test, writing code that mirrors the test's example data, and calling it done. The held-out variants a tutor will give you change the schema, the loader, and the denominator; the published tests are practice, and ASSESSMENTS.md says so.

Check your understanding

test_python_equal_values_can_still_have_wrong_types first asserts that reference(urgent=1) == reference(). Why does a test assert something about Python before asserting anything about your code?

Reveal the reasoning

It documents the trap in the test itself: the equality that would make a naive implementation pass is real, so a reader who sees the test later understands why the strict type check exists. A test that encodes the reason for a rule is worth more than a comment, because it fails if the reason stops being true.

Practice

Implement score_ticket only, run the scorer tests, then write one additional test of your own for a false pass that plain dict equality would admit and your implementation rejects. Keep it in a separate file so the published tests stay unchanged.

FAILED (errors=65)
What to look for

A good extra test is order_id=42 against "42" (type), or a key set that is a superset (extra field). The exercise is to state the rule in test form before writing the code that enforces it; the spec asks you to explain exactly such a case to a tutor.
