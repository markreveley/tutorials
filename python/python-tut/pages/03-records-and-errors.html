Module 1 · Python for someone coming from Elixir and Rust

Dicts, lists, JSON and JSONL, and exceptions as the error channel

The records you will read all day are dicts and lists that came from JSON. Errors arrive as exceptions, not as a second return value.

A record is a dict

An eval case, a hook configuration, a run manifest, a Hugging Face config: in Python they are all dicts, usually produced by json.loads. Keys are strings, values are strings, numbers, booleans, None, lists, or more dicts. Access is row["id"], which raises KeyError when the key is absent, or row.get("id"), which returns None. Prefer the first in loaders: a missing field is an error you want to see, not a None that travels three functions before something divides by it.

JSON round trips and the three traps

json.dumps turns True into true and None into null, and json.loads turns them back [Python: json]. Dict equality ignores key order, as the second line shows. Then come the traps the eval-pipeline spec is written around.

One: 1 == True. bool is a subclass of int, so a prediction with "urgent": 1 compares equal to a reference with "urgent": true. An exact-schema scorer must check type(value) is type(expected) as well as equality, and the output shows that type(1) is bool is false while type(True) is bool is true. This is the false pass that score_ticket's tests exist to catch.

Two: duplicate keys. The json module accepts repeated names in an object and keeps the last value by default. The documented remedy is object_pairs_hook, a function called with the ordered list of (key, value) pairs for every object at every depth; the example rejects the duplicate with a ValueError. load_cases needs this, because a case file with "reference" written twice would otherwise grade against whichever came last, with the row count unchanged.

Three: physical line numbers. A JSONL file is one JSON value per line [Python: json]. The loop uses enumerate(f, start=1) so the number it reports is the line in the file, and it skips blank lines after counting them: line 3 holds the second record and line 4 holds the bad one. JSONDecodeError is a subclass of ValueError and carries msg, lineno and colno, but note that its lineno is relative to the string you passed, which is one line; the file line number is yours to track.

Exceptions are the error channel

In Elixir you return {:ok, value} or {:error, reason} and pattern-match; in Rust you return Result and use ?. Python raises. An exception is an object that unwinds the stack until an except clause whose type matches catches it. Uncaught, it ends the program with a traceback, which is the correct behaviour for a bug and the wrong one for an expected condition like a missing file.

The idiom is to catch the narrowest type that means what you expect. FileNotFoundError is a different class from the ValueError you raise for bad data, and the spec for load_cases requires keeping them distinct so a caller can tell "no file" from "bad file". try / except / else / finally reads as: attempt, handle this failure, run this only on success, and always run this. The last clause is where hooks get removed in lesson 13.

Raise with a message that names the location: raise ValueError(f"line {lineno}: duplicate case id {case_id!r}"). The !r asks for the repr, which shows quotes and makes a trailing space visible. Re-raising with context, raise ValueError(...) from exc, keeps the original traceback attached.

Lists, tuples, sets, and the operations you will reach for

A list is an ordered, mutable array of references: append, indexing, slicing (rows[1:3], a new list), and len. A tuple is the immutable version and is what shapes are. A set holds unique hashable values, so len(set(ids)) == len(ids) is the one-line duplicate check, and set(prediction) == set(reference) compares key sets. A list comprehension, [r["id"] for r in rows if r["status"] == "scored"], replaces most loops that build a list. Sorting is sorted(rows, key=lambda r: r["id"]), stable, and non-mutating.

In eval and interpretability work

summarize_run must raise for a duplicate terminal result rather than count it twice. The alternative, silently keeping one, changes the denominator without changing the number of rows anyone looks at. The sibling statistics course calls that an inclusion-policy change; here it is a loader bug.

Pitfall

except Exception: pass. It turns a bad line into a silently shorter dataset, and the eval runs on fewer cases than were scheduled. If you must continue past a bad record, record where and why, and report the count.

Check your understanding

A loader reads 1,000 lines, reports 998 cases, and raises nothing. Name two ways that could happen with the code you have seen, and what each does to the eval.

Reveal the reasoning

Two blank lines, which is fine and should be visible as line numbers skipping. Or two records with duplicate ids kept by a dict keyed on id, which silently replaces earlier cases with later ones; or two malformed lines swallowed by a broad except. The first changes nothing. The others change which cases are graded while the headline count looks plausible, which is why the spec requires raising with the line number.

What to look for

The hook runs for every object literal at every depth, so one function covers both the duplicate at the top level and the duplicate inside "reference". Wrap the ValueError it raises so the message carries the physical line number; the hook itself cannot know it.
