Module 0 · The object of study

Tokenization: byte-pair encoding and the GPT-2 vocabulary

The tokenizer is a fixed procedure outside the network. Knowing how it splits text tells you which ids the model actually sees, and whether a claim about a word is even well-formed.

Byte-pair encoding in three merges

A byte-pair tokenizer is built by counting. Start with a corpus split into characters, count every adjacent pair of symbols weighted by word frequency, merge the most frequent pair everywhere, and repeat. The ordered list of merges is the tokenizer; applying the merges in the same order to new text reproduces the segmentation. Sennrich et al. introduced the method for translation, so that rare words become sequences of learned sub-word units instead of an unknown-word symbol [Sennrich 2015].

Here is a corpus small enough to tokenize with a pencil: hug ×10, pug ×5, pun ×12, bun ×4, hugs ×5. Count the pairs. The pair u g appears in hug, pug, and hugs: 10 + 5 + 5 = 20. The pair p u is in pug and pun: 17. u n is in pun and bun: 16. h u is in hug and hugs: 15. The first merge is therefore ug. Recount with ug as one symbol: u n still has 16, h ug has 15, so the second merge is un, and the third is hug. The tool does exactly this bookkeeping:

python labs/anatomy.py bpe-demo
corpus (word: count): {'hug': 10, 'pug': 5, 'pun': 12, 'bun': 4, 'hugs': 5}
step 1: pair counts ug=20, pu=17, un=16, hu=15 -> merge 'u'+'g'
        words now: {'h ug': 10, 'p ug': 5, 'p u n': 12, 'b u n': 4, 'h ug s': 5}
step 2: pair counts un=16, hug=15, pu=12, pug=5 -> merge 'u'+'n'
        words now: {'h ug': 10, 'p ug': 5, 'p un': 12, 'b un': 4, 'h ug s': 5}
step 3: pair counts hug=15, pun=12, pug=5, ugs=5 -> merge 'h'+'ug'
        words now: {'hug': 10, 'p ug': 5, 'p un': 12, 'b un': 4, 'hug s': 5}

After three merges the word hugs is hug s and a never-seen word bug would be b ug. Nothing about meaning entered the procedure; frequency alone decided that ug is a unit.

The GPT-2 tokenizer

GPT-2's tokenizer runs the same idea on bytes rather than characters, so any UTF-8 string can be encoded with no unknown symbol. The vocabulary has 50,257 entries: 256 single bytes, 50,000 learned merges, and one special token, <|endoftext|>, id 50256 [Radford 2019]. The merges file in the Hugging Face cache lists exactly 50,000 merge rules; this was checked by counting its lines.

Two display conventions matter when you read tokenizer output. Internally a leading space is stored as the character Ġ, so the raw token for " the" is Ġthe. And the tokenizer treats a word with a leading space as a different token from the same word without one:

python labs/anatomy.py tokens "The cat sat on the mat" --compare "the" " the"
'The cat sat on the mat': 6 tokens
   0  id=464    piece='The'  raw='The'
   1  id=3797   piece=' cat'  raw='Ġcat'
   2  id=3332   piece=' sat'  raw='Ġsat'
   3  id=319    piece=' on'  raw='Ġon'
   4  id=262    piece=' the'  raw='Ġthe'
   5  id=2603   piece=' mat'  raw='Ġmat'
'the' -> [1169]   ' the' -> [262]

Token 262 (" the") and token 1169 ("the") have different embedding rows and the model has learned different things about each. "The" at the start of the prompt is a third token, 464. A claim about "the token for the" has to say which one.

Token counts are not word counts

Common words with a leading space are usually single tokens; rare words, capitalised variants, and numbers split unpredictably:

python labs/anatomy.py tokens "Unbelievable" " unbelievable" "tokenization" "12345" " 2024"
'Unbelievable': 4 tokens
   0  id=3118   piece='Un'  raw='Un'
   1  id=6667   piece='bel'  raw='bel'
   2  id=11203  piece='iev'  raw='iev'
   3  id=540    piece='able'  raw='able'
' unbelievable': 1 tokens
   0  id=24479  piece=' unbelievable'  raw='Ġunbelievable'
'tokenization': 2 tokens
   0  id=30001  piece='token'  raw='token'
   1  id=1634   piece='ization'  raw='ization'
'12345': 2 tokens
   0  id=10163  piece='123'  raw='123'
   1  id=2231   piece='45'  raw='45'
' 2024': 1 tokens
   0  id=48609  piece=' 2024'  raw='Ġ2024'

The same word is one token with a space and four without. The number 12345 is split as 123 + 45, which is why arithmetic claims about GPT-2 are really claims about how it handles arbitrary digit chunks. None of this is a property of the network; it is a property of which merges happened to be frequent in the training corpus of the tokenizer.

What a token boundary does to a claim

Suppose you want to test "attention head H attends from mat back to cat." In the running prompt, cat is exactly token 1, " cat", including its leading space; the span of characters 4–7 (cat without the space) is inside token 1 but does not start on a token boundary. The claim is fine for the prompt as written. Now change the prompt to "The cat, the mat", or capitalise Cat, and the tokens change. A claim stated in terms of words silently depends on the tokenization of every prompt it is tested on. The lab's token_span function returns which tokens cover a character span and whether the span is aligned to token boundaries, so your test harness can refuse misaligned spans instead of quietly attributing a word to the wrong token.

In interpretability work

Write claims in token ids, not words. "Head 5.1 attends to token 464 at position 0" is checkable; "attends to the first word" is not, because the first word may be several tokens and the model may attend to any of them. When you build a dataset of prompts for a prediction test, record the token ids and assert their count, so that a tokenizer update or a stray space cannot change the experiment behind your back.

Pitfall

Prepending a space by hand to "fix" a tokenization. " cat" and "cat" are different tokens with different embeddings; which one the model usually sees in running text is the one with the space. Choose the variant your deployment and your dataset actually produce, and state it.

Check your understanding

Your prompt set contains "A cat sat" and "The Cat sat". Someone proposes to measure "the activation at the cat token" across both. What goes wrong, and what should the harness check?

Reveal the reasoning

"cat" with a lowercase c and a leading space is one token; " Cat" may be a different single token or a split. The two prompts do not share a token id at that position, so a per-token measurement averages over different inputs. The harness should tokenize each prompt, locate the span with offsets, require that the span is aligned to token boundaries, and either require the same token id across prompts or report the ids per prompt so the claim is stated honestly.

Practice

Compare the four spellings of cat. Then implement the toy BPE functions and the two GPT-2 drills in labs/tokens.py until the tokenization tests pass; the pencil corpus above is the test fixture.

python labs/anatomy.py tokens " cat" "cat" " Cat" "Cat"
python -m unittest discover -s labs -p 'test_tokens.py' -v
What to look for

The test for train_bpe expects exactly [(u,g), (u,n), (h,ug)]. For token_span, text[3:7] = " cat" in the running prompt should return (1, 1, True) while text[4:7] = "cat" returns (1, 1, False): same token, but the span is not aligned. Before implementing, the tests fail with NotImplementedError; that is the expected starting state.
