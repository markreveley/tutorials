Layer norm: what it does, where GPT-2 puts it, and folding it away

A normalisation step sits in front of every attention layer, every MLP, and the unembedding. It is simple arithmetic with two consequences interpretability tools exploit.

The arithmetic on a four-vector

Layer norm takes one residual vector, subtracts its mean across the 768 coordinates, divides by its standard deviation (with a small ε inside the square root so nothing divides by zero), and then applies a learned per-coordinate weight γ and bias β:

LN(x) = (x − mean(x)) / √(var(x) + ε) · γ + β

The variance is the population variance (divide by d_model, not d_model − 1), and GPT-2's ε is 1e-5, from the config. On the vector [1, 3, 5, 7]: the mean is 4, the deviations are [−3, −1, 1, 3], their squares average to (9 + 1 + 1 + 9)/4 = 5, and the standard deviation is √5 ≈ 2.2361. Dividing gives [−1.3416, −0.4472, 0.4472, 1.3416]:

python labs/anatomy.py layernorm-demo
x = [1.0000, 3.0000, 5.0000, 7.0000]  mean = 4.0000  variance (population) = 5.0000  std = 2.2361
LayerNorm(x) with gamma=1, beta=0, eps=1e-5 = [-1.3416, -0.4472, 0.4472, 1.3416]
torch.nn.functional.layer_norm agrees: [-1.3416, -0.4472, 0.4472, 1.3416]
RMSNorm(x) with weight=1: rms = 4.5826, output = [0.2182, 0.6547, 1.0911, 1.5275]
folding: (ln*gamma+beta) @ W + b  = [-1.2764, 0.4348]
         ln @ (gamma[:,None]*W) + (beta@W + b) = [-1.2764, 0.4348]

The RMSNorm line previews lesson 14: Llama-style models skip the mean subtraction and divide by the root mean square, √((1 + 9 + 25 + 49)/4) = √21 ≈ 4.5826.

Where GPT-2 puts it

The original Transformer normalised after each residual addition. GPT-2 moved layer normalisation to the input of each sub-block and added one more after the final block [Radford 2019]. In the installed code this is ln_1 before attention, ln_2 before the MLP, and ln_f before the unembedding; the residual additions themselves are unnormalised [transformers GPT-2 code]. This "pre-LN" placement is why lesson 03 could treat the stream as a plain sum: the normalisation happens on a copy that feeds the sub-block, and the stream that gets added to is never rescaled.

resid ──┬──────────────────────────────► + ──┬──────────────────────────► + ──► resid_post │ ln_1 → attention → attn_out ──┘ │ ln_2 → MLP → mlp_out ──┘ └────────────────────────────────────┘

Two consequences

Scale invariance. Layer norm of 2x equals layer norm of x (up to ε). So the sub-blocks see only the direction of the stream, not its length. The growth of norms in lesson 03 does not by itself change what attention or the MLP compute; what matters is the relative size of the components within a vector. This is also why the position-0 vector with norm 3,000 is not "louder" to the next block than a vector with norm 60.

Mean removal. Any component of a write that is a multiple of the all-ones vector [1, 1, …, 1] is deleted by the next layer norm's mean subtraction and never reaches a sub-block. Writes along that direction are invisible to the rest of the model except through the bias β.

Folding γ and β into the next matrix

The last two lines of the demo show an identity. If a layer norm's output (normalised n, then n·γ + β) feeds a linear map W with bias b, then (nγ + β)W + b = n(γcol ⊙ W) + (βW + b): scale each row of W by the matching γ entry and absorb βW into the bias. The function is unchanged, and the layer norm becomes a parameter-free normalisation. TransformerLens does this at load time when you call enable_compatibility_mode() with its default fold_ln=True, together with two further rewrites, centering the writing weights and centering the unembedding [TransformerLens compatibility mode]. The documentation is explicit that after folding, logits will not match Hugging Face's; lesson 13 shows exactly how they differ (by a per-position constant) and how to turn processing off with no_processing=True when you need a bit-for-bit comparison.

Why fold at all? After folding, the matrices W_Q, W_K, W_V, and W_in act directly on the normalised stream, so a direction in the stream maps to a query, key, or neuron input through one matrix with no per-coordinate rescaling in between. Every "which direction does this head read?" question becomes a question about one matrix.

One naming trap

TransformerLens exposes ln1.hook_normalized, ln2.hook_normalized, and ln_final.hook_normalized. These are the values before γ and β are applied, even when the weights are not folded; the value after the affine step is hook_out. The names command in lesson 13 checks this: multiplying ln_final.hook_normalized by ln_f.weight and adding ln_f.bias reproduces Hugging Face's hidden_states[12] to 3.8e-05.

In interpretability work

Direct logit attribution through ln_f is only exact if you fix the normalisation scale. The standard trick is to treat the final layer norm's scale as a constant computed from the full stream and apply it to each write; then the logit is again a sum over writes. Folding and centering, which compatibility mode does for you, keep that computation honest. State which processing mode your numbers came from.

Pitfall

Using torch.var with its default, which divides by n − 1. The layer norm formula divides by n. On a 768-vector the difference is tiny, about 0.07%, but it is the kind of systematic error that leaves your from-scratch logits off by a fixed amount you cannot explain. Pass unbiased=False or correction=0.

Check your understanding

A write of [c, c, …, c] (the same value in all 768 coordinates) is added to the residual stream by some head. What does the next sub-block see of it, and could it still affect the logits?

Reveal the reasoning

The next layer norm subtracts the mean, which removes it entirely, so the next sub-block sees nothing of it directly. The same is true of ln_f, so it cannot reach the logits through the unembedding either. Its only effect is indirect: it changes the mean and variance of the stream vector, which slightly changes the normalisation of the other components. TransformerLens's center_writing_weights removes exactly this invisible component from every writing matrix.

Practice

Recompute the RMSNorm line by hand: square each entry of [1, 3, 5, 7], average, take the square root, divide. Then write the layer_norm function in labs/gpt2_from_scratch.py and run the layer-norm test.

python labs/anatomy.py layernorm-demo
What to look for

Squares 1, 9, 25, 49 sum to 84; divided by 4 is 21; √21 = 4.5826; 1/4.5826 = 0.2182 matches the first printed entry. The test checks the [1, 3, 5, 7] case with eps=0 against [−3, −1, 1, 3]/√5 and a weighted case against torch.nn.functional.layer_norm.
