Module 3 · Respect the data structure

Repeated runs and related tasks

Count independent evidence at the level your claim requires, while retaining what repeated attempts teach you.

Draw the hierarchy first

The second fixture has 30 repositories, four tasks per repository, and three attempts per version per task. That means 120 tasks and 360 attempts per version. It does not mean 360 independent samples of repositories. Tasks from one repository share patterns; repeated attempts also share a task.

30 repositories └─ 4 tasks each: 120 task pairs └─ 3 attempts/version/task: 360 outcomes per version

A cluster is a group whose observations can be related. If your inference concerns newly sampled repositories, preserve repositories as the independent sampling units. If relatedness instead crosses repositories through a common template or shared outage, repository grouping alone may be insufficient. The grouping variable should reflect the dependency you need to model.

What does another attempt buy?

For task i, imagine a stable success probability pᵢ under the run policy. Repeating the task estimates pᵢ more precisely. Sampling new tasks teaches you how pᵢ varies across the population. For n independent tasks and k conditionally independent attempts per task, a useful variance decomposition is:

Var(overall mean) = Var(pᵢ)/n + E[pᵢ(1−pᵢ)]/(n k)

The first term is variation from selecting tasks; the second is variation from finite attempts on those tasks. Increasing k reduces only the second term in this model. The decomposition needs independently sampled tasks, a stable per-task probability, and independent attempts conditional on task. It does not model arbitrary shared outages. [Error bars]

Averaging and resampling in the lab

The lab first averages each version’s attempts within a task, then computes that task’s B−A difference. With --unit task, it resamples those task differences independently. With --unit cluster, it resamples repository groups, keeping all task differences inside each selected repository together.

This estimates a task-weighted population contrast under independent sampling of the chosen top-level units. Within-task noise is already present in the observed task means. The lab does not add a second bootstrap of attempts. If the target instead keeps these exact tasks fixed and asks about future attempts only, use an analysis conditional on those tasks rather than task-population resampling.

Same estimate, different precision

The candidate’s observed gain is ten percentage points. The task bootstrap gives approximately +5.56 to +14.44 points; the repository bootstrap gives approximately +1.11 to +18.89 points with the course’s fixed seed. The estimate does not change. The interval changes because the analysis recognizes how much independent evidence was collected.

The fixture intentionally makes tasks within repositories strongly related. It demonstrates a mechanism, not an empirical estimate of real repository correlation. Thirty repositories still leave limitations; the sensitive slice contains only ten, so its bootstrap interval deserves additional caution.

In eval work

Show counts at every level. “30 repositories, 120 tasks, three attempts per model per task” lets readers evaluate a claim that “360 samples” obscures.

Pitfall

Pseudoreplication occurs when correlated measurements are counted as independent evidence. Repeated runs are valuable, but their value does not come from relabeling them as new tasks.

Check your understanding

A launch rule requires the lower endpoint to exceed +3 points. The task interval clears it; the repository interval does not. Which should drive the rule?

Reveal the reasoning

Use the analysis matching the predeclared sampling design and intended population. If repositories are the independent sampled units, the repository result leaves the required gain unresolved. Choosing the narrower method because it passes is outcome-driven selection.

Practice

Predict which numbers remain identical. Compare estimates, interval widths, and independent-unit counts. Explain the task-mode caution message.

python3 labs/stats_lab.py compare --data labs/data/clustered_tasks.jsonl --unit task
python3 labs/stats_lab.py compare --data labs/data/clustered_tasks.jsonl --unit cluster
What to look for

The observed mean stays at +10 points. Repository resampling widens this fixture’s interval because related tasks move together. The task-mode result is intentionally provided as a comparison, not as a justified default for clustered data.
