Module 0 · Ask a measurable question

Name the quantity before calculating it

A fraction is only meaningful when you know what its numerator and denominator count.

The target has a name

An estimand is the exact quantity you want to learn. “Agent quality” is too broad. “Probability that this agent completes a newly sampled support task within two minutes, with at most one retry, judged by rubric version 3” specifies a measurable target. The observed result is an estimate of that target.

Write down the population, unit, outcome, run policy, and aggregation. If the unit is a user session, ten tool calls inside that session are not ten independent sessions. If the outcome is successful completion before a deadline, passing after the deadline is not the specified success. If you change the retry budget, you are evaluating a different procedure.

Rates, percentages, and percentage points

A = 144 / 200 = 0.72 = 72%
B = 156 / 200 = 0.78 = 78%
Absolute change = 78% − 72% = 6 percentage points

Divide passes by eligible tasks to get a rate. Multiply by 100 to express it as a percentage. Subtract percentages to get percentage points. The relative improvement is (0.78 − 0.72) / 0.72 ≈ 8.3%. The same result therefore has a six-point absolute improvement and an approximately 8.3% relative improvement. Label the scale.

Relative error reduction uses another denominator. Errors fall from 28% to 22%, so relative error reduction is (0.28 − 0.22) / 0.28 ≈ 21.4%. These are three descriptions of the same observations. None supplies uncertainty, and the biggest-looking number is not automatically the most useful one.

A denominator is an inclusion policy

Imagine 100 scheduled tasks: 72 pass, 18 complete and fail, and 10 time out. The completed-only success rate is 72/90 = 80%. The scheduled-task success rate, counting timeouts as unsuccessful, is 72/100 = 72%. Both arithmetic operations are correct. They answer different questions.

QuestionNumeratorDenominator
Delivered success under the deadline72 passes100 scheduled tasks
Success among completed tasks72 passes90 completed tasks
Completion rate90 completions100 scheduled tasks

Do not automatically classify every infrastructure error as a model failure. Define the system boundary first. A delivered-service metric can include service failures; a capability study may separately diagnose broken task environments and rerun them under a documented, symmetric rule. The key is preserving every scheduled case and explaining its disposition.

A fixed set and future tasks are different targets

If the question is simply “what fraction of these recorded outcomes passed?”, the arithmetic is exact once the labels are fixed. An interval becomes relevant when you generalize: to new tasks, future stochastic runs on these tasks, new graders, or a changing deployment population. State which source of variation you are modeling. Different questions need different repeated experiments.

In eval work

Before a launch comparison, write: “Equal-task average success over newly sampled tasks from the declared workload, three attempts per task, with timeouts counted under policy X.” That sentence determines what your analysis must preserve.

Pitfall

A cleaner denominator can create an apparent improvement without changing a single successful outcome. Always display scheduled, completed, excluded, and scored counts beside a rate.

Check your understanding

Version B gets 80% after dropping timeouts; A gets 72% with timeouts included. Is that evidence of improvement?

Reveal the reasoning

The reports use different inclusion policies. Recompute both under the same declared policy and compare completion rates. If B disproportionately times out on difficult cases, completed-only accuracy is a selected subset.

Practice

Write an estimand for an agent that edits repositories. Include population, time budget, retries, scoring, and weighting. Then rewrite it for the question “How reliable is it on these exact ten regression cases?”

What to look for

The first target concerns new tasks from a defined population. The second keeps tasks fixed and concerns future attempts under a fixed policy. A task bootstrap addresses the first kind of sampling uncertainty, not automatically the second.
