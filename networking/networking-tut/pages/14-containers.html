Containers: whose network is this?

Most beginner container-networking failures are destination mistakes. Identify the network environment before changing the application.

A container gets a network view

With ordinary container isolation, a process sees its own interfaces, loopback, routes, and ports through a network namespace. Two containers can both listen on port 8000 without conflict because those listeners are in different environments. Containers sharing a network namespace are an exception; configuration determines the boundary.[docker]

On a Docker user-defined network, containers can find one another using container names or aliases. A host-port publication is a separate way for traffic from the host or elsewhere to enter the container. It does not change the port the process listens on inside the container.

Read a mapping from outside to inside

127.0.0.1:8080:8000
└ host bind address
          └ host port
               └ container port

This describes a host-loopback publication of container port 8000 at host port 8080. It is not an application command and does not start a listener. The containerized application must listen on an appropriate interface, often 0.0.0.0:8000. The worker on the same container network normally calls http://model:8000, while the host calls http://127.0.0.1:8080.[ports]

A container image’s EXPOSE declaration documents intended ports; it does not by itself publish them to the host. Docker Desktop also introduces a virtual-machine boundary on common desktop platforms, so a Linux-host recipe may not map exactly onto macOS. Recognize the boundary and consult the platform’s supported host-access mechanism.

Observe before editing

docker ps
docker port MODEL_CONTAINER
docker inspect --format '{{json .NetworkSettings.Networks}}' MODEL_CONTAINER

These are optional read-only Docker commands. Replace MODEL_CONTAINER with the actual container name; the core course lab does not require Docker. The first command identifies running containers and published ports, the second lists port mappings, and the third shows network attachments. Avoid treating a remembered internal IP as a stable service identity.

A worked diagnosis

The host can call localhost:8080. A worker container cannot call the same URL. First note that localhost now refers to the worker container. Check that both containers share the intended network, that the model name resolves there, and that the model is listening on its container port. Use a diagnostic command inside the worker’s environment if available; host success is only evidence about the host path.

For an eval deployment

Document the endpoint separately for host development, container-to-container calls, and cloud execution. A configuration variable called MODEL_URL is useful only if each environment gives it a valid value. Copying a working local URL unchanged is not a deployment strategy.

Check your understanding

You publish 9000:8000 and the model listens on 8000. Which port should another container on the same user-defined network use to reach the model by name?

Reveal the reasoning

Normally 8000, the container service port. Port 9000 is the published host port. The exact supported route depends on configuration, but you should choose the intended service-to-service path rather than assuming every caller uses the host mapping.
