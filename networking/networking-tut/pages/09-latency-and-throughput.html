Latency, throughput, and bottlenecks

“The network is slow” is the beginning of a question. Break elapsed time into parts before deciding what to change.

Start with quantities and units

Latency is elapsed time for a specified operation. RTT is the round-trip time for a network exchange. Bandwidth is a capacity, commonly in bits per second. Throughput is the achieved rate of useful work, such as bytes per second or completed eval samples per minute. Eight bits make one byte: 100 megabits/s is at most 12.5 megabytes/s before overhead, using decimal units.[foundation]

A hypothetical 100 MB file requires at least 8 seconds to serialize through a 100 Mb/s bottleneck. That calculation excludes setup, propagation, contention, protocol overhead, and server delays. A tiny prompt may spend almost no time being transmitted while waiting seconds for model computation. More network bandwidth does not eliminate that computation.

Account for the whole request

curl timing fields are cumulative from the start of a transfer. On a simple fresh HTTPS request without redirects or proxies, time_connect − time_namelookup roughly isolates TCP setup; time_appconnect − time_connect roughly isolates TLS setup. Reused connections, redirects, proxies, and different HTTP versions complicate those interpretations. time_starttransfer includes preceding work and server time; it is not a pure network measurement.[curl]

The slow tail changes a batch

The median describes a typical observation. The 95th percentile, p95, is a value at or below which roughly 95% of observations fall under your chosen quantile convention. A mean can hide a small but important set of very slow requests. Report the sample count, errors, and timing definition alongside percentiles. A p99 from a handful of requests is not strong evidence about the tail.

For an eval, record latency by relevant conditions: prompt/output length, model, region, concurrency, connection reuse, and attempt number. Compare like with like. A run whose longest prompts time out can appear faster if you compute latency only over successful responses.

A useful capacity relationship

In a stable system over a suitable observation interval, average in-flight work is approximately throughput multiplied by average time in the system: L = λ × W. The important part is matching boundaries and populations. If you measure completed attempts per second, use attempt latency and attempt concurrency. Do not mix logical samples with retries.

For a hypothetical workload with 20 requests/s and a 3-second mean request lifetime, about 60 requests are in flight on average. This is a sizing estimate under stable conditions, not a promise that setting concurrency to 60 produces 20 requests/s. Provider limits, CPU, connection capacity, queueing, and token budgets can prevent it.

The network calculators let you vary transfer size, link rate, mean request time, and target throughput. Each result names the assumptions instead of presenting an unconditional performance prediction.

Check your understanding

After doubling concurrency, throughput barely changes but p95 latency triples. What does that suggest?

Reveal the reasoning

A constrained resource may already be saturated, so additional work waits rather than finishing faster. Investigate client pools, provider limits, server queues, CPU/GPU capacity, and network bottlenecks. Measure where waiting increases before choosing a fix.
