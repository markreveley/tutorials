Read a Kubernetes network diagram

You need a working map of the objects and paths before you need to administer a cluster.

Learn four objects first

ObjectNetwork role
PodOne or more containers sharing a network namespace and ports. Pod instances can be replaced.
ServiceA stable access abstraction for a set of backends; a typical ClusterIP Service exposes a cluster-internal address.
EndpointSliceA representation of backend endpoints associated with a Service.
Ingress / GatewayConfiguration for traffic entering services, implemented by a controller or supporting infrastructure.

A Service gives clients a stable way to refer to changing backends. A typical selector-based Service tracks matching Pods through endpoint objects. It is not necessarily a proxy process running on a machine with the Service IP. Cluster networking implements the forwarding. A Service existing in the API does not prove it has a ready backend.[k8s]

Names carry context

A name like grader can resolve within the caller’s namespace. A longer name such as grader.evals.svc.cluster.local makes the Service and namespace explicit in a cluster using the common cluster.local domain. The cluster domain is configurable. Your laptop’s resolver usually does not know these names or have the internal route.[k8sdns]

Reachability is also a policy question

NetworkPolicy can constrain traffic to and from selected Pods, provided the cluster’s network plugin enforces it. With no selecting policy for a direction, Pods are generally non-isolated for that direction. In an isolated setup, both source egress and destination ingress rules can matter. A policy file existing is not proof of enforcement or of the intended permissions.[policy]

A worker may need DNS access, model API access, artifact storage, and a grading service. A rule that permits only HTTPS to one destination can accidentally break name resolution or storage. Conversely, allowing arbitrary egress because one dependency failed hides the original problem and broadens the trust boundary. Identify each required flow.

A minimal read-only investigation

kubectl -n evals get pods
kubectl -n evals get service grader
kubectl -n evals get endpointslices -l kubernetes.io/service-name=grader
kubectl -n evals get networkpolicy

These optional commands require access to the intended cluster. First confirm your current context using kubectl config current-context; use the correct namespace. You are looking for healthy backends, the Service’s port and selector, and relevant policies. Commands from your laptop inspect cluster state but do not reproduce a worker’s data path.

A port-forward can help isolate an application, but it creates a different path. Success through port-forward does not prove Service routing, DNS, ingress, or NetworkPolicy behavior along the normal production path. Report exactly which path you tested.

Check your understanding

The Service name resolves and kubectl shows the Service exists, but requests fail. What is the next useful distinction?

Reveal the reasoning

Check whether the Service has ready backend endpoints and whether its target port matches the application listener. Then inspect the source/destination network policy and the worker’s actual path. A DNS answer and a Service object alone do not prove a usable backend.
