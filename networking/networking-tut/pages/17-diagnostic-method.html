Module 5 · Investigate failures

A diagnostic method you can repeat

The goal of troubleshooting is to reduce uncertainty with evidence. Start with the exact caller, destination, and last successful stage.

First, make the report reproducible

Write down the timestamp and time zone, worker environment, hostname, port, protocol, endpoint path, example size, timeout settings, concurrency, and error. Redact credentials and sensitive prompt content. Establish the scope: one worker or all workers, one region or all regions, one example type or every request. A recent change is a hypothesis to investigate, not proof of causation.

Climb the evidence ladder

The last successful stage helps you choose the next experiment. If DNS fails, tuning generation parameters is irrelevant to that attempt. If a gateway returns 429, a packet-level investigation is rarely the first useful step. If the answer arrives but persistence fails, the model path may be fine while the artifact path is not.

Use commands to test a hypothesis

curl -v --connect-timeout 5 --max-time 15 https://example.com/

This live, credential-free request can show the selected address, proxy use, TLS verification, and HTTP exchange. It tests the environment where curl runs. To investigate a container or CI worker, use an approved diagnostic method in that environment or record why your test differs. Never paste full authenticated verbose output into an incident channel.

ping tests an ICMP exchange, which can be blocked while HTTPS works. A failed ping does not establish an application outage. traceroute can reveal responding hops, but nonresponding hops are not automatically failed hops, and probes can take a different path from the application. Use these tools as evidence with limits, not pass/fail oracles.[ops]

Change one thing when possible

Compare a small and a large request, the failing worker and a known-good worker, IPv4 and IPv6, or the ordinary DNS answer and a controlled address override. Hold other variables steady. A successful test should distinguish hypotheses: changing region, client library, payload, model, and timeout together gives you little causal information.

For a reproducible large-transfer stall, MTU can become relevant. The maximum transmission unit limits packet size on a link; encapsulation can reduce the usable size. Path-MTU problems are a possible later investigation when the evidence fits, not a reason to begin every HTTP incident with packet captures.

A strong escalation

“At 14:05 UTC, workers in subnet A resolve the endpoint to X but connection setup reaches its 5-second limit. Subnet B completes the same credential-free health request. No HTTP response exists. The failure began after the outbound-route change. Here are the route and gateway observations.”

Check your understanding

Ping fails, but curl returns the expected HTTPS response. Is that contradictory?

Reveal the reasoning

No. ICMP and HTTPS are different traffic and can be governed by different rules. The successful curl exchange is direct evidence for that HTTPS path; ping’s failure only describes the tested ICMP behavior.
