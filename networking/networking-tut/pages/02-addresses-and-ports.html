Addresses, ports, and localhost

An address tells the system where to send traffic; a port helps it deliver traffic to the right service. The meaning of “here” is just as important.

Read an endpoint carefully

https://models.example.test:8443/v1/evaluate?stream=true
└scheme └──── hostname ────┘└port┘└── path ─┘└─ query ─┘

This is a fictional endpoint, not a working service. The hostname is a name to resolve. An IP address identifies a network interface or a logical destination in some routing context. A port is a transport-level number used to distinguish communication endpoints. TCP port 443 is conventionally used for HTTPS; the URL above explicitly selects 8443. A path such as /v1/evaluate is interpreted by the HTTP service after the connection reaches it.

Your operating system gives a client connection a source port, typically from an ephemeral range. A TCP connection is distinguished by source address, source port, destination address, and destination port. Add the transport protocol and you have the common five-tuple. Thousands of clients can connect to one destination port because their complete tuples differ.[tcp]

A server must listen

A running process does not automatically accept network connections. It must bind an address and port and listen. Binding to 127.0.0.1:8000 limits this listener to IPv4 loopback in its network environment. Binding to 0.0.0.0:8000 means listening on all local IPv4 interfaces. It does not, by itself, create a route, publish a container port, or grant firewall access.

Localhost is a point of view

On your laptop, localhost normally resolves to loopback addresses. Inside a container, it ordinarily means that container’s network namespace. Inside a Kubernetes Pod, containers share the Pod’s network namespace, so localhost can reach another container in the same Pod. It does not mean another Pod or your laptop. Network namespaces create separate views of interfaces, routes, and sockets; you will revisit them in the container lesson.

A common deployment failure

A worker runs in one container, but its model URL is http://localhost:8000. The model server runs in a different container. The URL points back at the worker’s own environment. Use the appropriate service name and port on a shared network. Increasing the timeout does not fix the destination.

First local observation

Later the lab will start a server bound to 127.0.0.1:8765. You will run curl http://127.0.0.1:8765/ok and inspect the response. The address, port, and path each have a separate job. If the service uses plain HTTP, asking curl for HTTPS on that port attempts the wrong protocol even though the address and port are correct.

Check your understanding

A server listens on 127.0.0.1:8000 inside a container. You publish the container’s port 8000 to a host port. Why might the host still fail to connect?

Reveal the reasoning

The forwarded connection generally arrives through a container interface, while the process listens only on the container’s loopback interface. The process must listen on an appropriate container interface, often 0.0.0.0, and the host mapping and network policy must also permit the path.
