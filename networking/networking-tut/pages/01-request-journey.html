Module 1 · Follow one request

Follow an eval request

A method call in your program can set a chain of machines in motion. Start by making that hidden chain visible.

Programs, machines, and messages

A host is a computer participating in a network, such as your laptop or a cloud virtual machine. A process is a running instance of a program on that host. For this example, imagine a Python program on a cloud virtual machine that reads a test prompt, sends it to a model API, and saves the answer. That running program is our eval worker; the virtual machine is its host.

TermMeaning in this course
Eval harnessThe software that organizes an evaluation: loading test cases, configuring runs, assigning work, collecting results, and arranging scoring. It can be a single program or a system with many workers.
Eval workerThe part of the eval harness that executes assigned test cases. In this example it is one Python process that sends prompts and records responses, timing, and failures.
AgentA model-driven system that can choose actions, use tools, and use their results to continue a task. In an agent evaluation, this is the system being tested; the worker starts or drives a test task and records what happens. A simple prompt-and-answer eval needs no agent loop.
Model gatewayAn intermediary service that accepts model API requests and forwards them to a suitable model-serving service. It may check API keys, enforce rate limits, or select a backend. Here it is an API gateway for model calls; it does not itself run the model.
Inference backendThe service behind the gateway that runs the trained model to generate output. “Inference service” and “model server” refer to this same role in our example.

The word harness needs context. An agent harness is the code around a model that manages the action loop, tool execution, and task state. An eval harness runs and measures tests of a model or agent. A worker may run an agent harness in its own process or control one running elsewhere. These responsibilities do not require one process or machine each.

Client and server describe each exchange

For the HTTP API calls in this example, a client sends a request for work and receives the response. A server accepts the request and sends a response. Both sides send and receive data. A server returning an answer, including streaming it in pieces, is still acting as the server. The roles describe who requests the work and who serves that request, not a one-way flow of data. The same program can serve requests on one connection while making requests on another.[http]

ExchangeClientServer
Worker asks the gateway to generate an answerEval workerModel gateway
Gateway asks the backend to perform generationModel gatewayInference backend

The worker and backend therefore communicate through the gateway in this example. The worker receives the gateway’s response, which carries output obtained from the backend. If the worker calls the backend directly instead, the worker is the client and the backend is the server. If a backend makes a separate request to a worker’s callback endpoint, the backend is a client and the worker is a server for that separate exchange. Simply returning the model’s answer does not reverse their roles.

Check your understanding

The backend streams generated text to the gateway, which streams it to the worker. Has the worker become a server?

Reveal the reasoning

No. Those messages are responses to requests already made. The worker remains the client of the gateway, and the gateway remains the client of the backend. To identify the roles, ask who requests work on each connection, not who is currently sending bytes.

Messages travel in packets

A network moves data between hosts over links. It breaks large transfers into manageable pieces called packets. Devices forward those pieces toward their destinations. Sending a million-byte prompt does not create one giant indivisible Internet message. Your software sees a higher-level abstraction built over many transfers.[foundation]

This order is a teaching model for a new HTTPS connection using TCP. DNS answers and connections can be reused; proxies add stages; HTTP/3 uses QUIC. You will learn these variations after the basic path is familiar. The essential habit survives every variation: identify which component was responsible for the next step.

Why engineers talk about layers

A protocol is an agreement about messages and behavior. HTTP describes requests and responses. TCP supplies an ordered byte stream. IP addresses and forwards packets. Ethernet or Wi-Fi carries traffic over a local link. Each protocol can add its own header around data from the layer above; that wrapping is encapsulation. The receiver interprets and removes the wrappers in reverse order.[foundation]

The seven-layer OSI vocabulary appears in infrastructure discussions. “Layer 3” usually concerns IP routing; “Layer 4” concerns transport addresses and ports; “Layer 7” concerns application messages such as HTTP. Treat these as clues to what a device inspects. Memorizing a seven-word list does not tell you why a request failed.

For an eval review

For every arrow in a design, ask: who initiates it, what name and port are used, what identity is checked, what deadline applies, and where the outcome is recorded? These questions turn an attractive diagram into an operational description.

Check your understanding

Your worker receives HTTP 401. Which early stages probably succeeded, and what is still uncertain?

Reveal the reasoning

It reached an HTTP-speaking component. If HTTPS certificate verification was enabled and succeeded, it also established TLS to that component. The model backend may never have seen the request: a gateway could have rejected authentication. Investigate credentials, endpoint, and response provenance before blaming routing.
