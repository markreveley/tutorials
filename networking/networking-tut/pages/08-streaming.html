Streaming and partial responses

Seeing the first token is useful. Knowing whether the response completed is essential for a trustworthy evaluation.

A stream is still a protocol

A non-streaming API commonly returns one completed response body. A streaming API makes pieces available over time. Server-sent events, or SSE, use a text event stream with fields such as data: and blank lines between events. WebSockets provide a different, bidirectional message channel. Neither is the same thing as a TCP packet.[sse]

event: token
data: {"text": "Hello"}

event: done
data: {"complete": true}

This is the local lab’s original event format. A real model provider defines its own event schema and terminal signal. Do not assume that every API uses a particular marker. Also do not assume one socket read contains one event: network reads, HTTP frames, SSE events, and model tokens have different boundaries.

Measure the experience at several points

MetricMeaning
Time to first byteWhen any response byte arrives; this may be a header or heartbeat.
Time to first tokenWhen the client can identify the first generated token/content event. Define exactly what counts.
Inter-event gapElapsed time between parsed stream events; buffering can change it.
Completion latencyWhen the documented terminal state is received and the response is usable.

First-token latency can include queueing, connection setup, prompt processing, and initial generation. Later generation can dominate total time. Comparing first-token latency in one run to total response latency in another is not a fair comparison. Record your timing boundaries, connection reuse, and any retries.

Intermediaries affect what you observe

A reverse proxy may buffer data, hold it until a buffer fills, or impose an idle timeout. Your client may buffer printed output too. If a stream appears all at once, investigate where flushing stops. The lab uses curl -N to disable curl’s output buffering. That option cannot force an upstream server or proxy to flush.

A stream that begins with HTTP 200 can still be interrupted. Once headers are sent, a later failure may appear as an error event, an incomplete body, or a connection closure rather than a new HTTP error status. EOF is not necessarily a documented successful finish. Store whether the terminal signal was seen and whether parsing completed.

An eval policy to write down

For a capability score, an interrupted answer might require an explicit infrastructure-failure classification and a predefined retry policy. For a product reliability eval, interruption may itself count as product failure. State the target metric first; never silently treat a truncated answer as a completed sample.

Cancellation is a request, not proof

If a client closes a stream after its deadline, the remote service might already have generated or billed more work. Some systems propagate cancellation; others do not stop promptly. Track the local outcome separately from any server-reported usage. A retry can create another generation even if the original one is still running.

Check your understanding

The first token arrives in 0.8 seconds, but no terminal event arrives before your 30-second deadline. What do you record?

Reveal the reasoning

Record first-token latency, the partial-response state, elapsed time, the deadline exceeded, and the absence of a terminal event. Do not label 0.8 seconds as completion latency. Whether and how you retry follows the evaluation’s policy, with a separate attempt ID.
