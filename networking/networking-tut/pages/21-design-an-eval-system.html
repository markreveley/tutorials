Module 7 · Design and defend

Design an eval system you can explain

Combine the pieces into a small, reviewable architecture. Start with the required flows and failure accounting, then choose infrastructure to support them.

An explicit example brief

Design a hypothetical nightly evaluation of 10,000 examples against a hosted model API. Some examples include images. A separate grader processes completed answers. Results must be recoverable after a worker crash, and a report must distinguish model quality from infrastructure outcomes. These are exercise requirements, not a prescription for every team.

Describe every connection

FlowDetails a reviewer needs
Worker → modelHostname, TLS identity, outbound route, region, API identity, quotas, connection reuse, deadlines.
Worker → data/storageDataset version, access identity, object sizes, encryption, bandwidth, retries, and durable write behavior.
Worker → queueDelivery semantics, lease/visibility timing, acknowledgment policy, and recovery after failure.
Grader → dependenciesThe same model/network rules if grading calls another model; do not hide this second workload.
Telemetry → collectorIdentifiers, redaction, retention, failure buffering, and what can be reconstructed if telemetry is delayed.

Give each sample a durable history

Assign a run ID, logical sample ID, and distinct attempt IDs. Keep an explicit state such as queued, running, completed, infrastructure-failed, or outcome-unknown. Persist the received answer before marking the logical work complete. The exact queue and storage transaction design depends on the platform, but a worker crash between “remote work completed” and “result stored” must have a documented recovery path.

A queue that can redeliver work is useful for recovery, but redelivery can duplicate model calls. Local deduplication of stored results does not undo remote charges or side effects. Use documented idempotency support where available and record uncertain attempts when it is not. Do not claim exactly-once end-to-end processing just because a database row is unique.

Make capacity a measured choice

For an invented sizing example, suppose each request takes 5 seconds on average and you want 4 completions/s. About 20 in-flight requests are a starting estimate under stable conditions. Confirm shared request/token limits, workload sizes, and failure rates. A grader that makes another model call adds its own traffic and can be the bottleneck. Sweep concurrency conservatively and record throughput and tail latency together.

Review failure paths before the happy path

What if the provider returns 429 for ten minutes? What if a worker loses its response after generation completes? What if storage is down? Bound retries, pause admission when appropriate, and make unfinished work visible. A circuit breaker temporarily stops calls to a failing dependency according to a measured policy; it still needs a recovery check and honest run accounting.

A concrete review deliverable

Produce the diagram, a flow table, the timeout/retry policy, a sample attempt record, and a failure matrix. Together these let a teammate understand how the system behaves when a request stops halfway through.

Check your understanding

Why is “retry the whole sample whenever anything fails” an incomplete recovery policy?

Reveal the reasoning

Failure may occur after the model already completed, during storage, or during grading. Retrying everything can regenerate a new answer, duplicate cost, and alter the sample. Preserve stage-specific state and retry the failed operation when the contract and stored evidence make that safe.
