HTTP: read the actual exchange

An SDK wraps HTTP messages. When something goes wrong, being able to read the method, URL, headers, status, and body makes the wrapper less mysterious.

A request is structured data

POST /v1/evaluate HTTP/1.1
Host: models.example.test
Content-Type: application/json
Authorization: Bearer <redacted>

{"prompt": "Explain DNS", "stream": false}

This is a simplified HTTP/1.1 illustration, not a runnable provider request. The method describes an operation, the target identifies a resource, headers carry metadata, and the body carries content. JSON is one possible content format. HTTP/2 uses binary framing and streams, so its wire representation differs while many of these semantics remain.[http]

An API contract adds rules above HTTP: required fields, model identifiers, quotas, response schemas, and completion conditions. An HTTP success status does not certify that the answer is valid for your evaluation. A JSON decoder can fail on a 200 response, and a valid JSON body can contain a task failure.

Treat status codes as evidence

ResponseFirst investigation
400 / 422Validate fields and schema using this API’s documentation.
401Check authentication credentials and the intended account or endpoint.
403Inspect authorization or gateway policy; do not assume a transport failure.
404Check the route, resource, model name, and API version.
429Inspect the provider’s limit category, response body, and retry instructions.
500 / 503Locate the responder and inspect a server failure or unavailability.
502 / 504A gateway reports an upstream response problem or timeout. Identify that gateway and its upstream.

These are diagnostic starting points, not a lookup table of proven root causes. Services can return custom error bodies and sometimes misuse status codes. Save the status, a redacted body, relevant headers, and a request ID together. The body may distinguish a quota exhausted for the day from a temporary request-rate limit.

Look at headers as well as the body

curl -i --connect-timeout 5 --max-time 15 https://example.com/

This sends a live GET to a public example site. -i includes response headers; --connect-timeout bounds connection setup; --max-time bounds this transfer. curl normally treats an HTTP 500 as a completed transfer rather than a process error. Use --fail-with-body when you want supported curl versions to return a failing exit code for HTTP errors while preserving the body. Exit status and HTTP status answer different questions.[curl]

Other API shapes you will encounter

A REST-style API commonly exposes resource-oriented HTTP endpoints. An RPC interface looks more like calling a remote function. gRPC usually uses HTTP/2 and Protocol Buffers, and communicates an application status that is not captured by checking the HTTP status alone. The debugging habit is the same: understand the protocol’s actual success condition.[rpc]

Browser-based tools also encounter CORS: browser rules governing whether a page can access a cross-origin response. A successful curl call does not establish that browser JavaScript is allowed to read that response. A CORS error is not proof that the server is unreachable, and adding credentials to an arbitrary proxy is not a sound diagnosis.
