Module 7 · Design and defend

Trust boundaries and eval validity

Network access is part of the experiment. It determines what an agent can observe or change and which failures enter your score.

An agent’s tool access changes the design

A simple model call sends a prompt to a known endpoint. An agent that runs tools may fetch URLs, execute code, access a database, or browse a site. Its network permissions become part of the task environment. Draw the boundary between the eval controller, the agent sandbox, the model provider, and services the agent can reach.

Give the sandbox only the identities and reachable services needed for the task. Treat model output and retrieved pages as untrusted inputs to tool execution. A proxy or allowlist can help constrain egress, but the whole design must account for redirects, DNS behavior, alternate addresses, and service-specific access. A private address is not a reliable label for “safe to contact.”

Keep powerful services out of the task environment

Internal admin endpoints, cloud instance metadata, credentials, and grader internals should not become reachable simply because an agent can request a URL. Keep the controller’s credentials outside the sandbox where possible. The goal is to make task permissions explicit and enforceable, not to rely on the agent remembering an instruction.

Network isolation and application authorization complement each other. A network control can block a connection; a reached service must still validate identity and scope. TLS protects a link, while the service at termination can read the request. Decide where sensitive datasets and outputs may travel and what gets retained in logs.

Access can change what the eval measures

If a benchmark intends to test unaided reasoning, allowing Internet retrieval changes the available information. If it intends to test web-agent ability, blocking all egress destroys the task. Record allowed services, Internet access, cached data, snapshots, DNS/proxy configuration, and relevant versions so the environment can be interpreted later.

Changing an external site can change a browsing task between runs. A request failure might come from your infrastructure, an external rate limit, or the task’s expected obstacle. The rubric should distinguish these where the evaluation objective requires it. Preserve enough evidence to classify outcomes without exposing more sensitive content than needed.

Make failure accounting visible

Metric in a hypothetical reportInterpretation
800 correct / 1,000 scheduled = 80%An end-to-end success definition where all other outcomes are unsuccessful.
800 correct / 900 completed ≈ 88.9%Quality conditional on completion, with 100 incomplete samples disclosed.
900 completed / 1,000 scheduled = 90%Completion rate under the stated deadlines and retry policy.

These figures describe different questions using the same invented run. None should be relabeled as the others. Conditional quality can be biased if difficult or long examples are more likely to fail. Report distributions and failure categories, and choose the primary metric before looking at results.

Check your understanding

A new runner improves “accuracy” by dropping all samples that time out. What would you ask in review?

Reveal the reasoning

Ask whether the target metric changed, how many samples were excluded, whether exclusions correlate with task difficulty or size, and whether the policy was predefined. Request both full-run accounting and any explicitly conditional score. Then investigate the failures rather than treating missing samples as irrelevant.
