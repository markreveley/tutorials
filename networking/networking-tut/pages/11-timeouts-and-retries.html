Timeouts, retries, and uncertain outcomes

A timeout tells you that a caller stopped waiting. It does not tell you that the remote operation never happened.

Define which clock is running

BudgetWhat it bounds
Queue / pool waitTime before obtaining permission or a connection.
Connection setupEstablishing a usable connection; exact DNS/TLS coverage depends on the client.
Read / idle timeoutTime without expected incoming data; often resets as data arrives.
Total attempt deadlineElapsed time for one complete attempt.
Logical sample deadlineAll attempts, waits, and backoff for one sample.
Run budgetThe whole evaluation, including result persistence.

Client libraries use these terms differently. Read the actual configuration semantics. An idle timeout can allow an endless trickle of data; a total deadline cannot. In curl, --connect-timeout includes DNS and the requested connection handshakes, while --max-time limits the transfer. Retry behavior adds another budget to inspect.[curl]

The lost-response problem

Repeating an operation is safe only under a defined contract. An idempotent operation has the same intended effect when repeated as when performed once. That does not mean identical response bytes or zero extra work. HTTP does not make arbitrary POSTs idempotent. A provider may support an idempotency key with explicit scope, expiration, and replay behavior; verify those details before relying on it.[http][rpc]

Generating another answer can incur another charge and produce a different sample. Even without an external side effect, repeatedly retrying until the model gives a satisfactory answer changes the experiment. Retrying a transport failure and retrying a low-quality answer are different policies.

Write a bounded retry policy

Define which failures are candidates for retry, a maximum attempt count, a remaining logical-sample deadline, and an overall retry budget. Use increasing delays with randomness so many workers do not retry in lockstep. Honor applicable server retry instructions. Authentication or malformed-input errors normally require a configuration or input change, not repetition.

example policy, not a provider default:
  logical sample budget: 90 seconds
  maximum attempts: 3 total (first attempt + at most 2 retries)
  retry: documented transient errors / selected transport failures
  before retry: check remaining time, quota, and outcome ambiguity
  delay: random between 0 and min(cap, base × 2^retry_index)
  record every attempt; never keep only the fastest successful one

Avoid independent retry loops in every layer. If an SDK makes three total attempts and your wrapper repeats that whole call three times, a sample can cause nine remote attempts. Repeated layers can amplify load exactly when a dependency is struggling. Identify the owner of retries and expose the actual attempt count.

Keep the evidence

Record logical sample ID, attempt ID, timeout phase, elapsed time, error/status, request ID, partial-response state, retry decision, and known usage. If the outcome is ambiguous, label it ambiguous. A timeout is not proof of zero cost or zero remote effect.

Check your understanding

A gateway stops waiting at 30 seconds while your client deadline is 90 seconds. Will raising the client deadline to 180 seconds fix a 504?

Reveal the reasoning

Not by itself. The gateway’s upstream budget can still expire at 30 seconds. Identify every deadline along the path, decide which component should own the budget, and verify whether the backend continues working after the gateway stops waiting.
