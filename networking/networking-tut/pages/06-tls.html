TLS: encryption and identity

HTTPS protects a connection and helps authenticate the server. It does not replace API authorization or define who can read data after termination.

What TLS contributes

TLS establishes cryptographic keys, protects data against eavesdropping and tampering in transit, and ordinarily lets the client authenticate the server. A certificate binds an identity to a public key under a trust system. A normal HTTPS client checks that the certificate is valid for the URL hostname, within its validity period, and chains to a trusted authority.[tls]

These checks are distinct from sending an API key. TLS can succeed and HTTP authorization can fail. Conversely, a valid API key does not repair a certificate mismatch. In mutual TLS, the server also authenticates a client certificate; that is another identity mechanism, not an automatic feature of every HTTPS connection.

Why the hostname matters

Multiple services can share an IP address. Server Name Indication, or SNI, lets a TLS client indicate the intended hostname during connection setup. The later HTTP request also identifies its target authority. Simply replacing https://api.example.test with an IP address can change both certificate validation and virtual hosting behavior. Preserve the hostname when you are isolating a DNS issue.

A browser, curl, and a language runtime can use different trust stores and proxy settings. “It works in my browser” does not prove the worker is configured the same way. Identify the actual executable and environment that fails. Verbose diagnostic output can include sensitive headers; use a credential-free endpoint when possible and redact before sharing logs.

TLS termination defines a boundary

A load balancer may terminate client TLS, read HTTP, and create a new connection to a backend. Ask whether that second hop is also encrypted and authenticated. A private subnet alone does not encrypt it. A network diagram labeled “HTTPS” on only the external arrow leaves an important part of the design unspecified.

Avoid making the test meaningless

Disabling verification with curl -k removes certificate checks and can conceal a wrong destination or trust problem. Keep verification enabled in the normal path. Diagnose the URL, chain, hostname, and trust configuration instead of copying an insecure workaround into the runner.

Check your understanding

Your TLS handshake succeeds, but the gateway returns HTTP 403. Should you change the certificate configuration first?

Reveal the reasoning

No. Successful verified TLS establishes a secure connection to that endpoint. A 403 concerns refusal to fulfill the HTTP request and can come from application authorization or gateway policy. Inspect the responder, credentials, account/project permissions, and policy evidence.
