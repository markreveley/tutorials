TCP, UDP, and QUIC

A transport protocol gives programs a way to exchange data. Knowing its promise helps you understand what it cannot guarantee.

TCP provides an ordered byte stream

TCP tracks sequence numbers, acknowledges received data, and retransmits when necessary. If a connection succeeds, the receiving application reads an ordered stream of bytes rather than a bag of out-of-order packets. TCP does not preserve your application’s write boundaries: a JSON message can arrive across several reads, and one read can contain parts of multiple messages.[tcp]

The initial handshake takes time. Reusing a connection through a client pool can avoid repeating connection establishment and, for HTTPS, much of the security setup. A pool holds reusable connections with finite capacity and lifetimes. Waiting for a free pool slot is client-side waiting, not necessarily slow server processing.

Reliable transport has limits

A TCP acknowledgment says something about bytes reaching the receiving TCP implementation. It does not certify that your inference finished, that a database committed, or that a response was stored. A broken connection can leave the client uncertain whether the server completed a request. That uncertainty is the reason retry design is an application concern.

Flow control protects the receiver from receiving more data than it can buffer. Congestion control adjusts sending to the network’s shared capacity. Neither is your provider’s requests-per-minute quota. Raising an API concurrency limit is not the same action as changing a TCP window.[congestion]

UDP and QUIC

UDP supplies datagrams with relatively little transport machinery. It does not itself guarantee delivery, ordering, or retransmission. Applications can build those functions above it. DNS frequently uses UDP, but also uses TCP and encrypted transports; blocking TCP DNS merely because “DNS uses UDP” is a poor assumption.

QUIC runs over UDP and supplies reliable streams, congestion control, and integrated TLS-based security. HTTP/3 uses QUIC. Independent QUIC streams avoid making one stream’s missing data hold up delivery on another stream in the same way that a shared TCP byte stream can. Shared bandwidth and connection-level resources still matter. HTTP/3 is therefore not “unreliable HTTP.”[http3]

Read transport symptoms carefully

SymptomReasonable interpretation
Connection refusedAn active rejection arrived; a missing listener is one possibility. Check the address, port, and rejecting component.
Connect timeoutThe connection did not become usable within the limit. Packet drops, routing, filtering, or overload are candidates.
Connection resetA connection was abruptly terminated by a peer or intermediary. Look for server/proxy events and request state.
Pool timeoutThe client could not obtain a usable connection slot in time. Inspect pool limits and unreleased responses.
Check your understanding

A TCP connection is reliable, so can you automatically retry any model POST after its connection resets?

Reveal the reasoning

No. The server may have accepted and performed the request before the response was lost. A retry can duplicate work or charges and can produce a different sample. You need an explicit attempt policy and any documented server-side idempotency support.
