Concurrency, queues, and rate limits

How many requests you start, how many are in flight, and how much work they contain are three different controls.

Separate the knobs

ControlQuestion it answersExample setting
Concurrency limitHow many operations may be active at once?At most 20 model attempts in flight.
Rate limitHow quickly may new work start over time?At most 120 attempts per minute under an example policy.
Token budgetHow much model input/output work may be used?A shared budget based on the provider’s documented accounting.
Queue capacityHow much not-yet-started work may accumulate?Stop accepting new local tasks when 200 are waiting.
Connection-pool limitHow many connections may this client manage?A finite pool; HTTP/2 can carry multiple streams per connection.

These example values are invented for teaching; they are not provider quotas. A concurrency limit of 20 permits a high start rate when requests finish quickly and a low start rate when they are slow. A rate limiter controls starts more directly. A prompt with 50,000 input tokens can consume much more budget than a short prompt even though each is one HTTP request.

Queues move waiting rather than remove it

Imagine a worker reads 10,000 examples and launches one asynchronous task per example. The code looks concurrent, but waiting is now hidden in the connection pool, the event loop, memory, or the remote gateway. Bounded work admission makes the waiting visible and prevents unbounded accumulation. Backpressure is the idea that a downstream constraint should slow upstream production.

Use a queue of pending samples and a fixed number of consumers. Before each attempt, obtain the relevant rate/token permission and an in-flight slot. Release resources on success, error, and cancellation. A task that leaks a connection by never consuming or closing a response can starve the pool even when the network is healthy.

Limits often span workers

If ten workers each enforce “120 requests per minute,” together they can start 1,200. A project-wide budget needs coordination, partitioned allowances, or a shared scheduler. Count retries too. A retry storm is real traffic and consumes the same scarce capacity as first attempts.

An HTTP 429 is evidence of a rate-limiting decision, but the relevant dimension can vary: requests, tokens, concurrent requests, organization quota, or a provider-specific policy. Inspect the response body and documentation. If a Retry-After field is present, it can specify a delay or a date; treat it as part of the service contract rather than hard-coding an arbitrary one-second loop.[http]

Preserve a fair experiment

A limiter can change which examples finish first. If you stop after a wall-clock budget, short examples may be overrepresented. Predefine sampling, ordering, retry, and stopping rules. Keep the original logical sample ID even when it produces multiple attempts, and record the scheduler wait separately from remote request time.

A useful engineering sentence

“We cap in-flight attempts separately from the shared request and token budgets, count retries against those budgets, and log queue wait so a slower run does not silently change our evaluation population.”

Check your understanding

You increase an HTTP client pool from 10 to 100 connections and see more 429s. What changed, and what did not?

Reveal the reasoning

You removed one local constraint on simultaneous traffic. You did not increase the remote service’s quota. Add or adjust a coordinated request/token limiter and choose a measured concurrency level; do not interpret the extra connections as extra provider capacity.
