Collect evidence that explains an eval

A useful result record describes both the model output and the path that produced it. Design that record before a failure forces you to improvise.

Logs, metrics, and traces

A log records an event. A metric aggregates a quantity over observations or time. A trace represents a request’s path as related spans: timed operations such as queue wait, model request, or result upload. Propagated trace context allows participating components to relate their spans. Instrumentation and context propagation must be present; the network does not automatically create a complete trace.[otel]

A minimal attempt record

{
  "run_id": "example-run",
  "sample_id": "0042",
  "attempt_id": "0042-b",
  "worker_region": "example-region",
  "endpoint_host": "models.example.test",
  "queue_ms": 240,
  "attempt_ms": 8200,
  "http_status": 200,
  "provider_request_id": "if-supplied",
  "terminal_event_seen": true,
  "outcome": "completed",
  "retry_count_before_attempt": 1
}

This is a hypothetical schema and invented data. Add the model/version, client version, request parameters, input/output lengths, timeout policy, and known token usage where appropriate. Store timestamps with an explicit time zone and use a monotonic clock for local durations so wall-clock adjustments do not corrupt elapsed-time measurements.

Classify without erasing ambiguity

OutcomeWhat to preserve
CompletedValid response and documented completion. Grade it under the task rubric.
Protocol / schema failureHTTP or parsing evidence and any partial body.
Transport / deadline failurePhase, exception, elapsed time, and known remote request ID.
Unknown remote outcomeA timeout/reset after submission without authoritative completion evidence.
Persistence failureWhether a response existed and whether it can be recovered.

The labels should match your evaluation target. A product test may count infrastructure failures in its end-to-end reliability metric. A model-capability analysis might also report a separately labeled completed-sample score. In both cases, retain counts and denominators so readers can see the missingness and retry policy.

Useful telemetry can be selective

Prompt bodies, model outputs, authorization headers, signed URLs, and proxy credentials can be sensitive. Prefer identifiers, sizes, status, bounded redacted error excerpts, and timing fields for routine networking diagnostics. If content is required to reproduce a problem, handle it under the dataset’s access and retention rules. More logging is not automatically more useful evidence.

Avoid putting sample IDs into every metric label when that creates a separate time series per sample. Aggregate metrics by a small set of useful dimensions; put high-cardinality identifiers into logs or traces. Sampling a trace stream can omit rare failures, so ensure run accounting and durable result records remain complete enough for your analysis.

Check your understanding

The dashboard shows 95% accuracy but no count of timed-out samples. What is missing?

Reveal the reasoning

The denominator and failure population. You need total scheduled samples, attempted/completed/failed counts, the retry policy, and whether infrastructure failures were excluded. Without that information, 95% can describe a selectively completed subset rather than the intended evaluation.
