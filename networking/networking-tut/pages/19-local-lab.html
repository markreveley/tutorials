Module 6 · Practice on a real service

Lab: observe a real HTTP service

Use two terminal windows to run a tiny service and investigate it. Everything stays on your computer; the examples need no API key or Internet connection.

Start the service

You need Python 3 and curl. Check with python3 --version and curl --version. The commands below assume a macOS or Linux shell. A terminal is a text interface for running programs; leave the first terminal open because its server process must keep running while the second terminal makes requests.

cd /Users/mark/dev/repos/_do/evals/domains/networking/networking-tut
python3 labs/server.py

If you move the course, change the folder in the first command. The service prints http://127.0.0.1:8765 and waits for requests. If that port is occupied, use python3 labs/server.py --port 8766 and change the client URLs accordingly. Stop it with Ctrl-C. It binds only to loopback, stores experiment counters in memory, and makes no external requests. This is a teaching server, not a production deployment.[python]

1. Read a successful exchange

curl -i http://127.0.0.1:8765/ok

Expect HTTP 200, a JSON content type, and a body whose outcome is complete. Identify the address, port, path, status, and body. Now request /missing. Expect 404: you reached a working HTTP service, but it does not recognize that route. This contrasts with stopping the server and seeing a connection refusal. Restart it before continuing.

2. Separate HTTP status from process exit status

curl -i http://127.0.0.1:8765/status/429
echo $?

Expect an HTTP 429 with Retry-After: 2, but normally shell exit status 0: curl successfully transferred an HTTP error response. The $? expression reports the preceding command’s exit status. Run the next command separately:

curl --fail-with-body -i http://127.0.0.1:8765/status/429
echo $?

With curl versions supporting this flag, expect exit status 22 while keeping the error body. On older curl, use --fail, which suppresses the response body. This simulated endpoint always returns 429, even if you wait. Its purpose is to expose status and headers, not to model a recovering quota.

3. Watch work outlive a client deadline

curl --max-time 1 "http://127.0.0.1:8765/slow?seconds=3&key=late"
echo $?

Expect curl to stop after approximately one second with exit status 28. Wait at least three seconds from when you started the request, then inspect the server’s record:

curl http://127.0.0.1:8765/stats

The slow_completed object should include "late": 1 on a fresh server. The client timed out, but the server still finished its simulated work. Repeating the experiment increments the count. This is evidence of an ambiguous outcome at timeout time, later resolved by an authoritative server record.

4. Observe separate attempts

curl -i "http://127.0.0.1:8765/flaky?key=exercise-one"
curl -i "http://127.0.0.1:8765/flaky?key=exercise-one"

For a new key, the first request returns 503 and the second 200 with attempt: 2. The lab does not automatically retry. Use a new key or restart the server to reset the scenario. Write two attempt records under one logical sample rather than pretending there was one flawless request.

5. Check stream completion

curl -N http://127.0.0.1:8765/stream
curl -N "http://127.0.0.1:8765/stream?cut=1"

The complete stream emits three token events and then an event: done. The cut stream emits one token and closes without done. Both start with HTTP 200, and curl can exit successfully on both because this HTTP body is delimited by connection closure. Your application must enforce its own completion contract. -N disables curl output buffering, making the arriving events easier to see.

Check your understanding

Write a six-line incident report for the slow endpoint. Include the request, the client deadline, the observed error, the later server evidence, what you learned, and a remaining limitation.

Reveal the reasoning

A good answer says the local request exceeded a one-second client deadline, curl exited 28, and /stats later recorded completion. This demonstrates that stopping the caller does not necessarily stop server work. The lab does not reproduce provider billing, TLS, DNS, gateway behavior, or a real model; those would require separate evidence.
