Module 5 · Statistics for Evals

pass@k done right

pass@k — the probability that at least one of k attempts succeeds — is the workhorse metric of code and agent evaluation, and it harbors a famous statistical subtlety: the obvious way to compute it is biased. This page tells the story as the HumanEval authors documented it, with every number verified against the paper.

Why the metric exists

When candidate outputs can be checked mechanically — code against tests — generating several and keeping a winner is a legitimate deployment strategy, so the eval should measure it: pass@k, the probability that at least one of k samples solves the problem. The metric predates the estimator drama: Chen et al. attribute it to Kulal et al. (2019), whose procedure was literal — generate exactly k samples, count the problem solved if any passes.[HumanEval] Two warnings before the math. First, pass@k is an oracle metric: it assumes something can pick the winning sample, with "prior knowledge of the unit tests." Without that oracle, the deployable alternative — reranking by mean log-probability — recovers much less: for the Codex-S model, 77.5% (oracle pass@100) versus 44.5% (reranking) versus 37.7% (pass@1).[HumanEval] Second, if every attempt faces a user rather than a test suite, the metric you want is pass^k, its reliability-measuring mirror.

The naive estimator, and which way it lies

The literal run-k-and-check procedure is an unbiased estimate but has high variance — with one batch of k samples per problem, luck dominates. The tempting fix: estimate the per-sample success rate p̂ = c/n from n samples, then plug into the formula for "at least one success in k independent tries":

naive pass@k = 1 − (1 − p̂)k

This is biased, and the direction is the opposite of what most people guess: it is "a consistent underestimate" of the true pass@k. The gap "doesn't fully close even when n > 5k, and results can seem better with more samples" — meaning two papers using different n aren't even wrong by the same amount.[HumanEval] The intuition (full derivation in Appendix D): plugging an estimate into a curved formula doesn't average out, because the formula amplifies one side of the estimate's wobble more than the other.

The unbiased estimator

Chen et al.'s contribution is the estimator everyone now uses: generate n ≥ k samples per problem, count the c that pass, and compute the probability that a random subset of k of your n samples contains no passing sample — drawing without replacement, which is the move that kills the bias:[HumanEval]

pass@k = Eproblems[ 1 − C(n−c, k) / C(n, k) ]

Worked instance (recomputable by pencil; more in Appendix D): n = 10 samples, c = 3 passing, k = 5 → C(7,5)/C(10,5) = 21/252 = 1/12, so pass@5 ≈ 0.917 — where the naive formula with p̂ = 0.3 says 0.832. Computing the binomial coefficients directly overflows for real n, so the paper ships a numerically stable product form — reproduced here as published, since this snippet is the field's reference implementation:[HumanEval] 

def pass_at_k(n, c, k):
    """
    :param n: total number of samples
    :param c: number of correct samples
    :param k: k in pass@$k$
    """
    if n - c < k: return 1.0
    return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))

The metric reaches back into the experiment

A subtlety that catches even careful readers: pass@1 and pass@100 from the same paper are usually not the same run summarized two ways. Because pass@k "rewards only whether the model generates any correct solution," diversity helps at large k and hurts at small k — so the optimal temperature depends on k. Verified from the paper: T* = 0.2 for pass@1 but T* = 0.8 for pass@100 (for a 679M-parameter model).[HumanEval] Each headline number gets its own decoding configuration. That's legitimate — each k models a different deployment — but it means "pass@1" comparisons across papers are also comparing sampling strategies, one more entry for the reproducibility ledger.

Keeping the headline numbers straight

The HumanEval paper's own results are a worked example in careful attribution, and they're routinely misquoted. Verified: 28.8% pass@1 is Codex-12B — GPT-3 proper scored ~0%. 70.2% with 100 samples is Codex; 77.5% within 100 samples is Codex-S, the fine-tuned variant, whose pass@1 is 37.7%. Different models, different k, different temperatures — five numbers that blur into "Codex solved 70% of HumanEval" in casual retellings.[HumanEval]

Pitfall

Treating pass@k as exempt from error bars. The estimator is unbiased per problem, but the reported number is still a mean over a finite problem set — and HumanEval has only 164 problems, a size at which EleutherAI showed touted improvements can wash out under resampling.[Eleuther] Small-n caveats stack with small-problem-set caveats: an unbiased estimator of a noisy quantity is still noisy.

Key idea

pass@k is three lessons in one metric: estimators can be biased even when the data is clean (the with/without-replacement distinction); the metric's definition reaches back into experiment design (temperature per k); and an oracle assumption (someone picks the winner) can sit silently inside a headline number. When you meet any derived metric, ask the same three questions — estimator, experimental coupling, hidden oracle.
