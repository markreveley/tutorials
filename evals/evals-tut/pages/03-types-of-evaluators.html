Three kinds of graders

Everything hard about evaluating LLM systems concentrates in one box of the machine: the grader, the thing that looks at a single output and says pass or fail. There are exactly three kinds — code, humans, and models — and choosing among them is an engineering trade-off you'll make over and over.

Why grading LLM output is the hard part

For a sorting function, the grader is trivial: assert the output is sorted. For "write a friendly reply to this customer," there is no assertion. The EleutherAI reproducibility paper states the core difficulty precisely: many syntactically different strings are semantically equivalent, and "our best automated tools for determining whether two sentences are semantically equivalent are the very models we are seeking to evaluate."[Eleuther] Every grading strategy in use is a workaround for that circularity, with different costs.

One distinction cuts across all three grader types before we start. A reference-based grader compares the output against a known-good answer (the ground truth); a reference-free grader judges the output on its own merits — essential in production, where no answer key exists for live user requests.

Grader 1: code

The cheapest, fastest, most trustworthy grader is a deterministic check — an assertion. It can't evaluate "is this reply friendly?", but a surprising amount of quality decomposes into properties code can check:

  • Execution checks — run the generated code against unit tests. This is HumanEval's grader, chosen over text similarity because actually running the code measures the thing that matters.[HumanEval]
  • Format and content assertions — valid JSON, required fields present, no leaked internals. Husain's canonical example from the Rechat case study: a regex asserting that responses contain no raw UUIDs.[Husain, Evals]
  • Classification metrics — when the task is classification-shaped (toxicity detection, document routing, extractive QA), grade it like the classifier it is. Eugene Yan: use "standard classification metrics such as recall, precision, PRAUC" — and never bare accuracy, which is "too coarse a metric to be useful."[Yan] (New to these metrics? Appendix E teaches them from zero.)

Code graders should be your default wherever they apply, and well-built ones earn their keep beyond evals: Husain notes that LLM unit-test assertions should be organized for reuse "in places beyond unit tests, such as data cleaning and automatic retries" — the same UUID check that fails an eval can block a bad response in production. Rechat accumulated hundreds of such assertions, continuously updated from observed failures.[Husain, Evals]

Grader 2: humans

Humans are the gold standard for "is this output actually good?" — by definition, for a product: quality means what your users and domain experts judge it to mean. Human grading (annotation) has two structural problems: it's slow and expensive, so it can't run in CI on every commit; and humans disagree with each other, so "the" human label is partly a fiction unless you manage it.

The practitioner solution to disagreement is organizational, not statistical: appoint one principal domain expert whose judgment is definitive. The Husain/Shankar FAQ recommends that "for most small to medium-sized companies, appointing a single domain expert as a 'benevolent dictator' is the most effective approach," reserving multi-annotator setups — with agreement measured by Cohen's kappa — for larger, multi-domain organizations.[Evals FAQ] The same source warns that outsourcing labeling to third parties is "usually a big mistake": the expert's tacit knowledge of what good looks like in your domain is the asset being encoded.

What to ask humans for

A recurring position across this course's spine sources: ask for a binary pass/fail plus a written critique, not a 1–5 score. The FAQ's reasoning — the difference between a 3 and a 4 "is subjective and inconsistent across annotators," detecting differences on scales needs larger samples, and "annotators often default to middle values to avoid making hard decisions."[Evals FAQ] Binary forces a decision; the critique captures the nuance the scale was pretending to capture. Module 2 returns to this in depth.

Grader 3: models (LLM-as-judge)

The third grader uses an LLM to judge LLM output — LLM-as-judge. It promises the coverage of code with something approaching the judgment of humans, and it's the only way to grade subjective quality at production scale. It is also the easiest grader to fool yourself with, because its failure modes are invisible in any single output: systematic biases (most judges favor whichever answer they see first[MT-Bench]), and real detection gaps. On factual-consistency grading, Yan reports an LLM evaluator that identified over 95% of consistent summaries but only 30–60% of inconsistent ones — a judge that looks accurate while missing half the actual failures.[Yan] On hallucination detection, the best model tested on the HaluEval benchmark managed 58.5% accuracy — "barely above chance."[Yan]

The discipline that makes judges usable is validating the judge against human labels before trusting it — measuring its true positive and true negative rates on a held-out, human-labeled set, exactly as you'd validate any classifier.[Evals FAQ] All of Module 3 is about doing this properly.

A judge doesn't have to be a frontier LLM, either. For narrow recurring checks, Yan's evidence favors small fine-tuned classifiers: a compact NLI model fine-tuned on a few hundred task-specific examples "likely outperforms n-gram, similarity, and LLM-based evals" for factual consistency, and with a thousand-plus examples becomes "good enough as a hallucination guardrail."[Yan] The general-purpose judge is a starting point, not a destination.

The practitioner ordering is explicit in the FAQ: cheap code assertions first; an LLM judge is an investment reserved for "persistent, subjective failures," because each judge realistically requires "100+ labeled examples, ongoing weekly maintenance, and coordination between developers, PMs, and domain experts."[Evals FAQ] A useful mental model: humans define quality, judges scale it, code locks it in. Human review discovers what failure looks like; a validated judge automates that judgment over thousands of outputs; and wherever a failure mode turns out to be mechanically checkable, it graduates to an assertion and runs forever for free.

Pitfall

Reaching for an LLM judge first — because it's one API call — and skipping straight past code and humans. Teams end up with a judge nobody validated, scoring outputs nobody reads, optimizing a number nobody can interpret. The grader hierarchy runs on evidence from human review; without that foundation, a judge is an unvalidated instrument wired directly into your decisions.
