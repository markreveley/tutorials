Module 4 · Evaluating Agents

What makes agents different

When a model stops just answering and starts acting — calling tools, editing files, conversing across turns, changing the state of the world — five assumptions baked into everything we've covered so far quietly break. This page names them; the rest of the module rebuilds the machinery around them.

"Agent" is a spectrum, not a category

The field never settled on a crisp definition, and the spine sources for this module deliberately avoid one. Shankar and Husain "use 'agent' broadly," covering "the full range from a single LLM call with no tools (the simplest case) to a system that runs in a loop, calls many tools, and makes many decisions per request."[Evals Book] The Princeton "AI Agents That Matter" team likewise treats agency as a spectrum with several contributing factors — the complexity of environment and goals, the interface and degree of human supervision, and the system's design (planning, tool use, control flow).[Agents That Matter] For evaluation purposes the operative question isn't "is it an agent?" but "which of the following five complications does it have?"

1. The output is a trajectory, not a string

An agent's "output" is the whole trajectory: a sequence of model decisions, tool calls, tool results, and messages, often dozens of steps long.

single LLM call: prompt ──────────────▶ text (grade the text) agent episode: goal ─▶ think ─▶ tool ─▶ result ─▶ think ─▶ tool ─▶ … │ │ ▼ ▼ environment state ───────────▶ changed environment (grade THIS — and maybe the path too)

This forces a choice that didn't exist before. Outcome-based evaluation grades only the end result — did the issue get fixed, the refund processed, the file created? Process-based evaluation grades the path — did the agent follow policy, avoid dangerous calls, use the budget sensibly? Outcomes are what users care about and are far easier to check mechanically; processes matter when a right answer reached the wrong way is still a liability. The benchmarks dissected in pages 12–13 are almost all outcome-based, and the gaps that choice leaves are a running theme.

2. The environment is now part of the eval

An agent needs something to act on — a repo, a browser, a database, an OS. So every agentic eval ships an environment, and the environment's engineering becomes part of the measurement. It must be reset to a known state per attempt, isolated in a sandbox (agents execute code — the HumanEval authors already needed gVisor containers and firewall rules in 2021[HumanEval]), and faithful enough that success in it predicts success in reality.

When the environment misbehaves, it grades the wrong thing. A verified example from the Princeton reproducibility analysis: WebArena's Reddit clone enforces rate limits, so "if the tasks involving Reddit posts are evaluated one after another, they are much more likely to fail" — task ordering, not agent quality, moves the score.[Agents That Matter] The harness-reading checklist from page 2 gains a new question: what does the environment do between attempts?

3. Grading means checking the world, not the words

The cleanest agentic grading idea is state-based evaluation: compare the state of the environment after the episode against an annotated goal state. tau-bench (page 14) is the canonical example: a customer-service agent manipulates a mock company database while conversing with a simulated user, and the reward checks both that "the final database is identical to the unique ground truth outcome database" and that the agent's replies contained the required information.[tau-bench] To make that comparison meaningful, the benchmark's authors deliberately constructed every task so that "only one database outcome is possible," trading slow annotation for objective grading — and capping the benchmark at 165 tasks total.[tau-bench]

Caveat — even clean outcome grading leaks

tau-bench's own authors flag that a perfect reward is "necessary but not sufficient": an agent can reach the correct final database state while violating policy along the way — for example, "the agent might issue the return without explicit user confirmation," and still score 1.[tau-bench] Outcome-based grading is blind to how — which is exactly the gap process-based checks exist to fill. Knowing what your grader cannot see is part of knowing what your score means.

4. Sometimes the eval needs a fake human

Many agents work with a user mid-task, so the eval must supply one: user simulation, typically an LLM playing a customer with a goal and personality. tau-bench uses GPT-4 as the simulated user.[tau-bench] This buys realism — multi-turn clarification, underspecified requests — at the price of a new validity question: the simulator is itself an LLM with quirks, and its behavior is part of what's being measured. Meanwhile the absence of any human in the loop biases the other way: the Princeton team highlights evidence that "simple feedback increases the performance of GPT-4 from 0% to over 86% on challenging programming problems" — so benchmarks with no human involvement can badly underestimate an agent's real-world usefulness.[Agents That Matter]

5. Stochasticity compounds — and cost stops being constant

A single model call is somewhat random; an agent is a chain of model calls, where each sampled decision changes everything downstream. Two runs on the identical task diverge early and end in different places. The measured consequence (the full story is page 14): the best agent on tau-bench's retail domain succeeds 61.2% of the time on average — but succeeds eight-for-eight on the same tasks less than 25% of the time.[tau-bench] Average success and dependable success are different quantities, and one number cannot report both.

Cost breaks symmetrically. A fixed prompt costs roughly the same every time; an agent decides at runtime how many steps to take, and architectures differ in cost by orders of magnitude at the same accuracy (page 15). Worse, expensive evaluation degrades measurement itself: with SWE-bench-scale evaluations costing thousands of dollars per full run, error bars become a luxury — the Princeton team found published agent results they could not reproduce within the spread of five of their own runs.[Agents That Matter]

Pitfall

Evaluating an agent like a chatbot — grading only its final message with the judge machinery of Module 3. A polished closing summary can sit on top of a trajectory that mangled the database, and a final-message judge will pass it. For agents, the words are testimony; the environment state is evidence. Grade the evidence.

Key idea

Five new facts: the output is a trajectory; the environment is part of the instrument; grading checks world-state, not text; users may need simulating; randomness and cost compound across steps. Every agentic benchmark is a bundle of design answers to these five — which is why this module reads benchmarks as artifacts to dissect, starting with the most famous one: SWE-bench.
