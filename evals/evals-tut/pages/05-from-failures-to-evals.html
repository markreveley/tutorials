Module 2 · The Eval Process

From failure modes to evals

Error analysis left you holding a failure taxonomy with counts. This page turns it into eval machinery: a structured test dataset, a grading scheme (binary, with critiques), and a decision about which failure modes deserve automated graders at all.

Each failure mode becomes a set of test cases

A failure mode like "dietary constraint ignored" from the previous page becomes an eval the moment you collect inputs that probe it and define what passing looks like. The inputs come from two sources, used together:

  • Real traces — the actual failures you found. These are gold: verified-real user behavior, already labeled by your own analysis.
  • Synthetic data — LLM-generated inputs that extend coverage to cases you haven't seen yet. Husain bootstrapped Lucy's eval suite this way before launch, prompting a model to "write 50 different instructions that a real estate agent can give to his assistant" per feature.[Husain, Evals]

The mistake with synthetic data is asking for it unstructured. The FAQ's verified method is a two-step recipe: first define dimensions along which inputs vary (feature, scenario, persona), hand-write ~20 example tuples, have the LLM generate more tuples — then a separate prompt converts each tuple into a natural-language query. Prompting an LLM to just "give me test queries" produces "generic, repetitive outputs."[Evals FAQ] The same source lists where synthetic data is unreliable: complex domain-specific content, low-resource languages, unverifiable claims, high-stakes domains like medicine and law, and underrepresented user groups.[Evals FAQ]

Worked example — the dimension/tuple recipe for the recipe-bot:

dimensions:  feature   × scenario          × persona
hand-write:  (substitution, allergy-driven,  anxious first-timer)
             (meal plan,    vegan household,  busy parent)
             (unit convert, metric request,   precise baker)
             … ~20 such tuples, then LLM generates more tuples …

convert:     (substitution, allergy-driven, anxious first-timer)
             → "My kid is allergic to peanuts — is it safe to swap
                almond butter into this cookie recipe??"

Structure first, language second. The variation you get is the variation you designed.

How big should the dataset be? Husain's heuristic for judge-building datasets: "start with around 30 examples and keep going until I do not see any new failure modes. From there, I keep going until I'm not learning anything new" — with examples deliberately spread across the dimensions.[Husain, Judge] Note the shape of the rule: it's the saturation logic from error analysis again, applied to dataset construction.

Grade binary, capture nuance in critiques

Now the grading scheme. The unanimous position across this course's spine sources is to make every judgment a binary judgment — pass or fail — rather than a Likert scale (1–5 rating). The reasoning, assembled from its three independent sources:

Problem with 1–5 scalesVerified statement
Adjacent points are meaningless"The difference between adjacent points (like 3 vs 4) is subjective and inconsistent across annotators"[Evals FAQ]
Not actionable"People don't know what to do with a 3 or 4"[Husain, Judge]
Statistically weaker"Detecting statistical differences requires larger sample sizes"[Evals FAQ]
Annotators dodge decisions"Annotators often default to middle values to avoid making hard decisions"[Evals FAQ]
Judges grade better in binary"Where possible, I have my evaluators return binary outputs. This improves model performance while making it easier to apply classification metrics"[Yan]

Husain's sharpest version of the argument targets metric sprawl: "if someone says you need to measure 8 things on a 1-5 scale, they don't know what they are looking for. They are just guessing."[Husain, Judge] Two important refinements keep this from becoming dogma. First, binary doesn't mean information-poor: every pass/fail comes with a written critique — "detailed enough that a new employee could understand it"[Husain, Judge] — which later becomes few-shot material for judges (page 10). Second, when you genuinely need to track gradual improvement, decompose the quality into multiple binary sub-checks ("4 of 5 expected facts present" as five separate checks) rather than reaching for a scale.[Evals FAQ] The FAQ's framing is "start binary": numeric labels are "advanced and usually not necessary."

Not every failure mode gets an automated grader

For each taxonomy category, run it through the grader hierarchy from page 3:

  • Mechanically checkable? → code assertion. "Metric units requested, gave cups" is a parser and a unit table. Cheap, permanent, runs in CI.
  • Subjective and recurring? → candidate for an LLM judge — but remember the verified price tag: "100+ labeled examples, ongoing weekly maintenance, and coordination between developers, PMs, and domain experts." The FAQ's rule: "Only build expensive evaluators for problems you'll iterate on repeatedly."[Evals FAQ]
  • Rare, or fixable at the root? → sometimes the right response to a failure mode is a fix plus a handful of regression cases, not a standing evaluator. A bug you'll never reintroduce doesn't need a permanent meter.
Should evals come first, like TDD?

A tempting transplant from software engineering — write the evals before the feature. The FAQ's verified answer is "generally no": eval-driven development "creates more problems than it solves," because of the catch-22 documented on the next page — you can't define good criteria before seeing real outputs. The carve-out: constraints you know exactly in advance, like "never mention competitors," can be written as checks up front.[Evals FAQ]

Keep a held-out set, even here

One habit from classical machine learning survives intact: don't evaluate your evaluator on the data you built it with. When you label examples to construct a judge, reserve a held-out split of human-labeled cases the judge never saw during prompt iteration — that's where its true positive and true negative rates get measured (page 10), and the FAQ specifies "a held out labeled test set" for exactly this purpose.[Evals FAQ] The same logic at benchmark scale — holdouts protecting against overfitting — returns as a major theme in Module 4 and Module 6.

Pitfall: the suspiciously perfect suite

If your new eval suite passes 100%, the suite is probably wrong — too easy, mis-graded, or testing the cases you already fixed. Verified guidance: "If you're passing 100% of your evals, you're likely not challenging your system enough. A 70% pass rate might indicate a more meaningful evaluation that's actually stress-testing your application."[Evals FAQ] An eval's job is to find failures while they're cheap; a suite that can't fail is decoration.

Key idea

The pipeline so far: traces → taxonomy → structured dataset → binary labels with critiques → graders matched to failure modes. Every artifact is downstream of looking at real data, and every judgment is binary-with-critique. One link is still unexamined: the graders themselves. Who checked them? That's the next page.
