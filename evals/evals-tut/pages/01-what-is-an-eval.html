What is an eval?

The word covers everything from a one-line regex check to a benchmark that moves billion-dollar valuations. Underneath, it's always the same four-part machine. This page defines that machine, then draws the distinctions — eval vs benchmark, capability vs product, offline vs online — that the rest of the course depends on.

The four-part machine

An eval is a repeatable measurement procedure for an AI system. Strip away the tooling and every eval consists of:

┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ 1. TASK │ → │ 2. DATA │ → │ 3. GRADER │ → │ 4. METRIC │ │ what the │ │ the inputs │ │ scores one │ │ aggregates │ │ system │ │ you test │ │ output: │ │ scores into│ │ must do │ │ it on │ │ pass/fail, │ │ a number │ │ │ │ (samples) │ │ 0–1, A>B… │ │ you report │ └────────────┘ └────────────┘ └────────────┘ └────────────┘
  • A task definition — what the system is being asked to do, stated precisely enough that "did it succeed?" has an answer.
  • A dataset — the collection of inputs (each one a sample) the task is attempted on. Sometimes each sample carries an expected answer — a ground truth — and sometimes it can't.
  • A grader — the thing that looks at one output and produces a judgment. It might be five lines of Python, a human expert, or another LLM. Choosing and validating graders is most of Modules 2 and 3.
  • A metric — the rule that turns many per-sample judgments into the number you report: percent passing, average score, win rate.

The "repeatable" in the definition is load-bearing. A colleague pasting prompts into a chat window and nodding is performing assessment, but not an eval: nothing guarantees that next month's nod measures the same thing as today's. Repeatability is what lets you compare two prompts, two models, or two weeks — and comparison is the entire point.

Key idea

Once you see the four-part shape, you can decompose any eval you meet — and every dispute about an eval's trustworthiness is a dispute about one of the four parts. Is the data representative (or leaked into training)? Is the grader right (or biased)? Does the metric summarize honestly (or hide variance)? Does the task measure what we actually care about? Those four questions generate Modules 2 through 6 of this course.

One eval, dissected: HumanEval

To make the anatomy concrete, here is one famous eval taken apart. HumanEval, introduced by OpenAI alongside the Codex model in 2021, measures whether a model can write working Python functions.[HumanEval]

Task: given a function signature and docstring, write the function body.

Data: 164 hand-written programming problems. Hand-written for a reason the authors state plainly: models train on huge swaths of GitHub, "which already contains solutions to problems from a variety of sources" — reusing existing problems would test memory, not ability.[HumanEval] (This is your first sighting of contamination, the subject of Module 6.)

Grader: run the generated code against unit tests — an average of 7.7 tests per problem. The output passes or it doesn't. No human opinion involved.

Metric: the fraction of problems solved, reported as pass@k — the probability that at least one of k attempts passes (Module 5 covers how to estimate it without fooling yourself).

The most instructive part of the paper is a road not taken. The obvious cheap grader for generated code is textual similarity to a reference solution — the BLEU score, borrowed from machine translation. The authors tested it and showed that the BLEU scores of correct and incorrect solutions to the same problem overlap heavily — incorrect solutions can look textually closer to the reference than correct ones — concluding that "improvements in BLEU score may not indicate improved rates of functional correctness in practice."[HumanEval] The grader they shipped instead — actually executing the code — is more expensive and required a sandbox, but it measures the thing that matters.

Pitfall

Choosing a grader because it's easy to compute rather than because it tracks success is the original sin of evaluation. Surface similarity between an output and a reference — BLEU, ROUGE, embedding cosine — rarely separates good outputs from bad ones in real applications. Practitioner consensus has converged on the same verdict as the HumanEval authors: similarity metrics are "not useful for evaluating LLM outputs in most AI applications," surviving mainly as debugging signals for retrieval.[Evals FAQ]

Eval vs benchmark

A benchmark is an eval that has been standardized and shared so that results are comparable across teams, models, and papers. HumanEval is a benchmark; the regex suite your team runs in CI is an eval but not a benchmark. The distinction matters because sharing changes the incentives: once a benchmark is public, models are tuned toward it, its data leaks into training corpora, and its numbers become marketing — pressures a private eval never faces. Benchmarks are scientific instruments operating in a hostile environment, which is why this course spends a whole module (Module 6) on how they degrade.

Capability evals vs product evals

The deeper split is in what question the eval answers.

Capability evalProduct eval
QuestionHow good is the model?Does my application work for my users?
Data comes fromCurated public task setsYour own users' real interactions
Definition of "good"Fixed by benchmark authorsYour domain expert's judgment
Comparable across teams?Yes — that's the pointNo — and it doesn't matter
Main threatsContamination, saturation, gamingUnrepresentative data, unvalidated graders

These two cultures barely overlap, and advice from one can be wrong in the other. The most common crossover mistake is grabbing generic, capability-style metrics off the shelf — "helpfulness," "coherence" — and using them as product evals. Eugene Yan, whose practitioner writing is a spine source for this course, tested this directly and found that off-the-shelf evals "barely correlate with application-specific performance and aren't discriminative enough to use in production."[Yan] Husain and Shankar's FAQ is blunter still: generic ready-made metrics "waste time and create false confidence," with one carve-out — using them as exploration signals to surface interesting traces, never as quality measures.[Evals FAQ]

Why this matters

When someone says "the new model scored 92," your first response should be: on which layer? A capability score predicts your product's behavior only loosely — your prompts, data, tools, and definition of success all differ from the benchmark's. High benchmark scores get models onto your shortlist; only your own product eval decides which one ships.

Offline vs online

One more axis. An offline eval runs against a fixed dataset before deployment — in development, in CI, on demand. An online eval measures the live system on real traffic: sampled production scoring, user feedback signals, or a full A/B test. Husain's three-level scheme for product evaluation maps onto this axis: Level 1, unit-test-style assertions; Level 2, human and model evaluation of logged traces; Level 3, A/B testing — with Level 3 explicitly deferred until "your AI product is suitable for showing to real users."[Husain, Evals] Offline evals are fast, cheap, and safe; online evals are the only ground truth about real users. Mature teams run both, wired together: production failures become offline test cases (page 7).
