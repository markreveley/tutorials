Module 2 · The Eval Process

Evals in the development lifecycle

Datasets, graders, judges — now where do they all run? This page places the eval machinery into the development loop: continuous integration, runtime guardrails, production monitoring, and eventually A/B tests — and shows why a working eval system pays compound interest.

The shape of the loop

Shankar and Husain's book organizes everything this module has covered into a three-phase cycle they call the LLM evaluation lifecycle: Analyze (understand failure modes via error analysis), Measure (implement metrics and automated evaluators), and Improve (change the system based on what you measured).[Evals Book] The crucial property is that it's a cycle: improving the system changes its failure distribution, which demands fresh analysis, which updates the measures.

┌─────────────┐ ┌───▶│ ANALYZE │ read traces, build the │ │ │ failure taxonomy (page 4) │ └──────┬──────┘ │ ▼ │ ┌─────────────┐ datasets, assertions, │ │ MEASURE │ validated judges │ │ │ (pages 5–6) │ └──────┬──────┘ │ ▼ │ ┌─────────────┐ fix prompts, code, models; │ │ IMPROVE │ ship — which changes what └────┤ │ fails next └─────────────┘

Husain's three levels from page 1 describe where the Measure phase physically runs: Level 1 unit tests in CI, Level 2 human and model evaluation over logged traces, Level 3 A/B testing in production.[Husain, Evals] Take them in order.

Level 1: assertions in CI

Your code-based graders — the cheap, deterministic assertions from page 3 — belong in regression testing, run on every meaningful change. Rechat runs its hundreds of assertions through ordinary CI infrastructure (GitHub Actions), with one practical wrinkle Husain flags: track the eval metrics and the versions of prompts and tests outside the CI system, so you can analyze trends rather than just see red/green; the tooling here "is nascent and evolving rapidly," so "orchestrate tests that involve the least friction in your tech stack."[Husain, Evals]

What goes into the CI dataset? Small and purpose-built. The FAQ describes CI datasets of around "100+ examples" curated to cover known failure modes, and recommends favoring "assertions or other deterministic checks over LLM-as-judge evaluators" in this loop — CI runs constantly, and you want its verdicts cheap, fast, and stable.[Evals FAQ] Every newly discovered failure mode from the Analyze phase deposits a few regression cases here: the suite is the fossil record of every bug you've understood.

A fork in the road: evals vs guardrails

A check that runs offline against a dataset is an eval. The same check running inline on live traffic, blocking or retrying a bad response before the user sees it, is a guardrail. The code can be identical — Husain notes that well-organized assertions get reused for "data cleaning and automatic retries"[Husain, Evals] — but the roles differ in ways that matter for design:

EvalGuardrail
RunsOffline, on datasetsInline, on every live request
PurposeInform decisionsPrevent bad outputs
Latency budgetGenerousMilliseconds matter
False-positive costA mislabeled rowA blocked good answer, a retry loop

The distinction stops teams from making two symmetric mistakes: shipping an expensive judge as a latency-critical guardrail, and believing that having guardrails means they've "done evals." Guardrails reduce harm from failure modes you know about; evals are how you find out what your failure modes are.

Level 2 in production: monitoring live traffic

Once real users arrive, the eval system extends over live traffic. The verified pattern from the FAQ: sample production traces and score them asynchronously — off the request path — using reference-free evaluators (there's no answer key for live requests), typically LLM judges that were validated offline first; and report the resulting metrics with confidence intervals, since you're estimating a rate from a sample.[Evals FAQ] (Why the error bars are non-optional is Module 5's opening argument; the infrastructure that runs this — tracing, scores attached to production traces — is Module 7's.)

Production monitoring and the Analyze phase feed each other: monitoring flags traces that look bad; those traces enter the next error-analysis batch (the FAQ's cadence: a fresh 100+ traces every 2–4 week cycle, 10–20 weekly in between[Evals FAQ]); confirmed new failure modes become regression cases in CI and, where stakes demand, guardrails.

Level 3: A/B testing — last, deliberately

The final authority on whether a change helps users is an A/B test on real traffic. It sits at Level 3, not Level 1, because it's slow (weeks per answer), needs traffic volume, and exposes users to the variant being tested. Husain's verified position is not "skip it" but "defer it": it's "okay to put this stage off until you are sufficiently ready and convinced that your AI product is suitable for showing to real users" — appropriate "for more mature products."[Husain, Evals] Offline evals exist precisely to make most decisions before anything reaches an A/B test; the experiment then confirms the few changes big enough to warrant it. (Module 5 covers the statistics of comparing variants — the same machinery governs offline comparisons and A/B tests.)

The flywheel: what the eval system buys you later

The reason to build all this is iteration speed today — but Husain documents a second-order payoff he calls "superpowers for free." A mature eval system is a curated-data engine: "If you have a robust evaluation system, you already have: a database of traces that you can search and filter. A set of mechanisms (assertions, tests, etc) that can help you flag errors and bad behaviors." And since "99% of the labor involved with fine-tuning is assembling high-quality data," the eval system doubles as the fine-tuning data pipeline, the synthetic-data curation filter, and the debugging rig.[Husain, Evals] Teams that invested early get to make moves — model swaps, fine-tunes, aggressive refactors — that un-instrumented teams can't risk, because every move is measured.

Pitfall: the static suite

The lifecycle's most common failure is freezing it: a suite built once, passing forever, while the product and users move on. A 100%-green eval suite is a warning sign, not a trophy (page 5) — and a suite nobody has added a case to in months means the Analyze phase has quietly stopped. The system is healthy only while the loop is turning: traces in, failure modes out, cases added, criteria re-validated.

Key idea

One pipeline, four deployment points: the same graders run as CI regression checks, as runtime guardrails, as asynchronous production monitors, and as the offline gate before A/B tests. Build the grader once, validate it once, deploy it everywhere — and keep the analyze→measure→improve loop turning so the graders keep describing the system you actually have.
