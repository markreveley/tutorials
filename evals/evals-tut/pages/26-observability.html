Module 7 · Tooling

Tracing and online evaluation

Everything in this course runs on one raw material: traces. The final page covers the infrastructure layer that produces and scores them — using Langfuse and Braintrust as the two best-documented exemplars — and the unifying idea both teach: offline experiments and online monitoring are one system, not two.

The tracing data model

Module 2's instruction was "log everything and look at it." Observability platforms give that instruction a schema. Langfuse's data model is representative and worth learning by name:[Langfuse/Braintrust]

Session (optional) groups traces from one user interaction └─ Trace one complete request/response cycle └─ Observations the steps inside — nested to any depth: ├─ Span a generic operation (retrieval, parsing…) ├─ Generation an LLM call — a specialized span carrying │ model, parameters, token usage, cost └─ Event a point-in-time action

Two details matter beyond vocabulary. Generations are not just spans: the LLM-call subtype carries model name, parameters, token usage, and cost details, which is what makes per-call cost and latency attribution automatic[Langfuse/Braintrust] — the bookkeeping Module 4's cost-controlled evaluation needs, for free. And observations nest arbitrarily, so an agent's tool-call tree or a RAG pipeline's retrieve-then-generate structure is represented faithfully, with parent-child timing[Langfuse/Braintrust] — the trajectory from page 11, as a data structure.

Scores: evaluation results as attached data

The second primitive: a score, attachable to traces, sessions, and individual observations — from any grader type: "model-based evaluations (LLM-as-a-Judge), human annotations or fully custom evaluation workflows via API/SDKs."[Langfuse/Braintrust] That's the grader taxonomy of page 3 as a storage schema: code checks, judge verdicts, and expert labels land in one place, attached to the evidence they judged. The granularity detail has practical teeth: Langfuse's recommended production pattern has shifted to observation-level evaluators — scoring individual steps rather than whole traces — because they "complete evaluation in seconds, not minutes."[Langfuse/Braintrust] Step-level scoring also localizes failures the way error analysis wants: "retrieval returned junk" rather than "trace bad."

Experiments: comparisons you can trust later

Braintrust's contribution to the vocabulary is the experiment: "an immutable snapshot of an evaluation run — permanently stored, comparable over time, and shareable across your team," built from versioned datasets ("experiments can pin to specific versions") and scorers returning 0–1 values, with a pre-built scorer library (autoevals) and a deliberately separate, ephemeral playground for quick iteration.[Langfuse/Braintrust] The design encodes two course lessons. Immutable run + pinned dataset version = the reproducibility bundle of page 19: a comparison between experiments run weeks apart provably used identical test cases. And the playground/experiment split institutionalizes the difference between exploring and measuring — the same line page 17 drew statistically.

A practical judge note

Autoevals — Braintrust's scorer library — defaults to OpenAI's API for its LLM-as-judge scorers, redirectable via environment configuration.[Langfuse/Braintrust] Beyond the deployment surprise, that's a judge-identity decision being made by a default — and Module 3's self-preference findings say judge identity is not a neutral choice when the judged model is from the same family. Know which model your metric library is quietly calling.

The unified loop: offline and online are one system

The deepest concept this layer teaches is stated by both vendors in their own words. Langfuse: evaluation "happens both online, on live production traces, and offline, before you ship a change."[Langfuse/Braintrust] Braintrust, structurally: "Logs use the same data structure as experiments, which means: instrumentation code works for both logging and evaluation … scores and feedback apply to both logs and experiments … production data seamlessly becomes evaluation datasets."[Langfuse/Braintrust] Online scoring runs asynchronously, off the request path, with no latency impact[Langfuse/Braintrust] — exactly the production-monitoring pattern page 7 prescribed.

Put together, this is Module 2's flywheel with the plumbing made explicit: production traces flow in; sampled traces get scored (by validated judges) and reviewed (by humans, during error analysis); interesting failures graduate into versioned datasets; datasets feed offline experiments that gate the next change; the change ships, instrumented identically, and the loop repeats. One schema — traces, scores, datasets, experiments — carries the whole course's process.

Pitfall

Mistaking the platform for the practice. A tracing platform makes data available; it doesn't make anyone look at it, validate a judge, or run error analysis — and an unvalidated LLM-as-judge evaluator wired to production traces is the same unvalidated judge from page 10, now generating authoritative-looking dashboards at scale. Remember the verified practitioner warning that predates all these tools: "Don't buy fancy LLM tools. Use what you have first" — the discipline transfers; the tooling only amplifies whichever discipline (or absence) it finds.[Husain, Evals]

Key idea — and the close of the course

The course began with a four-part machine: task, data, grader, metric. It ends with that machine industrialized — traces as the data, validated judges and assertions as the graders, experiments as the comparisons, error bars on the metrics, validity audits on the whole — running continuously on live traffic. None of the infrastructure replaces the two disciplines everything depended on: look at your data, and validate your validators. Tools change yearly; those don't.
