A guided descent

From Elixir down to the metal

You already write Elixir. This wiki extends that mental model downward — through the bytecode your code compiles to, into how values are laid out in memory, and finally to how the running VM reads those bytes back. One ladder, top to bottom.

The one question underneath everything here:

When you write {m, :a, :b} in Elixir, what literally exists in memory — and what does the BEAM do with it?

The chapters build on each other. Each rung answers a question the previous one raises, and every claim about the runtime is checked against The BEAM Book (citations like Ch.4.2 link to the relevant section). Wherever it helps, there's something interactive to poke — not for decoration, but because these ideas are spatial and a static paragraph hides the shape.

Memorised rules vs. derived ones Most of us carry the BEAM's rules as standalone facts: "data is immutable," "atoms aren't garbage-collected," "don't send giant structures between processes." Memorised, they hold up for years of ordinary work — until an edge case (a GC pause, a copying bottleneck, atom-table exhaustion) lands somewhere the rule doesn't reach. The point of going down the ladder is to convert each rule into one you can re-derive: not "atoms aren't GC'd, because reasons," but "an atom is an index into a single global table — therefore creating them without bound leaks." A derived rule tells you what to do when it breaks; a memorised one only tells you that it did.

Conventions

  • Ch.x markers cite The BEAM Book (Erik Stenman). Implementation details (exact bit layouts, the 60-bit small-int range) are how it works today, not language guarantees — they can shift across OTP versions and 32/64-bit. The observable Elixir behavior is stable.
  • Colour throughout: green = an immediate value, blue = a pointer / arrow, amber = tag bits, rose = a list / cons cell.
  • The conversation that seeded this wiki is preserved as THREAD.md.
