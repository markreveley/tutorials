From Elixir to Bytecode

Before we can ask what a value looks like in memory, we have to be honest about one thing: the BEAM never runs your Elixir. It runs bytecode that a chain of compilers produced from your Elixir — rewriting and lowering it along the way. The shape changes. Knowing how it changes is what lets the rest of the ladder make sense.

It is a translation, not a transliteration

It's tempting to imagine each line of Elixir becoming one line of bytecode. It doesn't. Your source passes through several intermediate forms, and at each step it's rewritten while preserving behavior — not structure: 

Elixir source
   │   macros expand · if→case · |> rewritten to nested calls
   ▼
Elixir AST  ──►  Erlang Abstract Format
   │   lowering
   ▼
Core Erlang        a small, explicit functional core
   │
   ▼
SSA-based forms    optimisation: dead-code elim, inlining, register reuse
   │
   ▼
BEAM bytecode      a register machine the emulator executes

Two consequences matter for everything that follows. First, one line of Elixir may become many instructions, or several lines may collapse into fewer. Second, the bytecode speaks a lower-level vocabulary than you ever wrote: it talks about registers, allocating heap, and loading literals — concepts absent from your source. It's a register machine Ch.5.

"Build a tuple from these values"

    

      Look at the last stage above. Where your Elixir said {result, :ok}, the bytecode says
      something closer to: allocate a tuple object on the heap with a header marking it a tuple of arity
      2, then fill its two slots with the current values in registers.
    

    

      That phrasing is the hinge into the next rung. "Fill its slots with the current values" hides a
      question: what is a value, sitting in a register, about to be written into a tuple slot? For a
      small integer it's the number itself. For anything larger — another tuple, a map, a string — the slot
      receives a pointer to where that thing already lives. The tuple references its
      elements; it does not embed copies of them.
    


    

      So the compiler does what, exactly?
      It bakes compile-time constants (a literal 42, :ok, or a
      literal tuple) into already-tagged form in the module's literal area, and it emits the
      build-instructions for everything assembled at runtime. The actual allocation, tagging, and
      pointer-writing happens later, in the running VM — see rung 7.
    


    
Where this leaves us

    

      We now have a concrete handle: the program that runs is a stream of low-level instructions, and the
      interesting ones construct and read values in memory. To follow them, we need to know
      what a single value looks like as bits. That's rung 2.
