How the Runtime Reads It

We've built values up from bits. Now run the tape backwards: given a word in a register or a slot, what does the BEAM actually do to make sense of it? And where does this program get memory in the first place? This is where "the runtime" stops being a vague word.

Decoding a word, step by step

At execution time the BEAM is a native program inspecting one word at a time, reading its tag, and branching. Step through a few:

    Decode order per BEAM Book Ch.4: primary tag → (immediate decoded in place | pointer masked & followed → header read).
    Two different "type" mechanisms Immediates are typed by their tag bits alone — a hardcoded switch in the C emulator, no lookup. Boxed objects need a second read: the header word encodes the exact subtype + arity directly in its bits (again, hardcoded interpretation — not a table). The only genuine table is the atom table, which exists solely to map a compact index to a variable-length name.

    So what is "the runtime"? A program.

    The BEAM runtime is a native executable — a C program compiled for your OS and CPU. "Running Elixir" launches this program; it loads your compiled .beam bytecode and executes it, providing the entire managed world: the tagged-value model, garbage collection, the lightweight-process scheduler, message passing, the atom table, timers, I/O. Strictly, BEAM is the abstract machine (Bogdan/Björn's Erlang Abstract Machine); the emulator is the concrete C program that emulates it — the way an NES emulator is a real program emulating an abstract console. ERTS (Erlang Run-Time System) is the whole bundle: emulator + allocators + schedulers + built-ins Ch.5.

    Where the memory comes from — two levels

    The BEAM doesn't conjure memory; it's an ordinary OS process. The OS hands it a virtual address space (via mmap/malloc); the BEAM grabs big regions and then plays "operating system" to its own world, sub-allocating per-process heaps and boxed objects inside what it owns. "Reading memory" is just normal C pointer dereferencing inside that owned space.

    A BEAM process is "four blocks of memory: a stack, a heap, a message area, and the Process Control Block" Ch.3.2. The stack and heap share one region and grow toward each other Ch.3. Two design consequences follow directly from private heaps:

    • Per-process garbage collection. The GC is a "per process copying generational" collector Ch.3. When one process collects, it pauses only itself — no global stop-the-world across millions of processes. This is a big reason for the BEAM's low, predictable latency.
    • Message passing copies. Because a process can only safely reference its own heap, sending a message generally copies the data into the receiver's heap. The big exception: large binaries (>64 bytes) live off-heap in a shared, reference-counted area and are passed by reference Ch.4.5. So "no copying, just sharing" is a within-process guarantee.
    The whole ladder in one breath Your Elixir is compiled to register-machine bytecode. Its instructions build values as tagged words — immediates inline, boxed terms as pointers to header-led heap blocks. The BEAM, a native program holding memory from the OS, executes those instructions by reading tags, masking pointers, and following them, all inside per-process heaps it collects independently. Nothing "out there somewhere" — every layer has an address.
