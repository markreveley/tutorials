Atoms & the Atom Table

An atom is the strangest of the immediates: a value that is its own identity. :ok isn't a pointer to the string "ok", and it isn't a small integer. It's a name, interned exactly once into a table the whole VM shares. Understanding that unlocks why atom comparison is nearly free — and why atoms are a footgun.

The word holds an index, not the name

Recall from rung 2: an atom is an immediate. Its word's low six bits are the tag 00 10 11 ("atom"), and the remaining bits are an index into the global atom table Ch.4.2. There's no "following memory" to dereference for the identity — the word is the atom. The table, elsewhere in VM memory, stores the actual definition (name, length, an ordinal for fast ordering): 

typedef struct atom {
    IndexSlot slot;   // position in the table
    int len;          // length of the name
    int ord0;         // first bytes, for cheap ordering
    byte* name;       // "ok"
} Atom;

Interned once, shared by everyone

The table is VM-wide, and atoms are interned: every occurrence of :ok anywhere, in any process, resolves to the same index. Try it — intern the same name from two different processes and watch them land on one table slot.

Global identity, not a global variable Because two atoms are equal iff their indices are equal, comparing :ok == :ok is a single integer comparison — no string walk. But that's the only sense in which atoms are "global." An atom carries no mutable state; you can't set it or read a value out of it. It's a globally-shared constant/symbol, not a variable. Processes don't communicate through atoms — they merely all agree that :ok means the same symbol.

The footgun

Two facts combine into a real hazard: the atom table is never garbage-collected (atoms live forever once created), and it has a fixed maximum size (~1,048,576 by default). So:

Never create atoms from untrusted input String.to_atom/1 on user-supplied data (request params, file contents, message fields) can exhaust the table and crash the entire VM — every process, not just yours. When you must convert a string you expect to already be a known atom, use String.to_existing_atom/1, which raises instead of minting a new permanent entry.

This is the flip side of interning's elegance: the thing that makes atoms cheap to compare (a permanent, shared, integer-indexed identity) is exactly what makes uncontrolled creation dangerous.
