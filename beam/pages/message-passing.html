Message Passing & Copying

The private heaps that make GC cheap (rung 8) and structural sharing safe (rung 4) come with a bill, and this is where it's paid. A process can only safely touch its own heap — so to hand data to another process, the data is copied. Understanding that copy (and its one big exception) explains a whole class of BEAM performance surprises.

Sending = deep-copying into the receiver's heap

When process P1 sends a message M to a local P2, P1 computes the flat size of M, allocates a message buffer (a heap fragment) of that size, and copies M into it Ch.11. P2 then owns its own independent copy; the original on P1's heap is untouched. This same deep copy is used for I/O, ETS, and binary_to_term Ch.11.

The catch: deep copy doesn't preserve sharing

Inside one heap, a heavily-shared term is compact (rung 4). But a default deep copy expands that sharing — each arrow becomes its own full copy on the far side. The BEAM Book's own example shows a term whose shared size is 19386 words ballooning to a flat size of 94110 Ch.11: 

> share:size().
{{size,19386}, {flat_size,94110}}   # ~5× bigger once copied

So a term that's cheap to hold can be expensive to send, and expanding a highly-shared term across messages can bring a node down. (ERTS can be built with --enable-sharing-preserving, but it's off by default because it slows the common no-sharing case Ch.11.)

The exception: large binaries are shared, not copied

Binaries over 64 bytes are refc binaries: the payload lives in a shared, off-heap, reference-counted area, with only a small ProcBin reference on the process heap Ch.4.5. Sending such a binary copies only the tiny reference and bumps the refcount — the bytes themselves never move. That's why passing a 10 MB binary between processes is cheap, while passing a deeply-shared nested term might not be.

The sub-binary gotcha Matching <<_:32, rest/binary>> makes rest a sub-binary that still references the original large binary — great for avoiding copies, until you've accidentally kept a giant binary alive just to hold a few bytes. :binary.copy/1 (Elixir :binary.copy/1) detaches it Ch.11.
The trade, stated plainly Isolation buys you cheap per-process GC and safe sharing — and charges you a copy at every process boundary. The runtime softens the worst case (huge binaries) by sharing them off-heap. Knowing which side of that line your data is on is most of BEAM performance intuition.
