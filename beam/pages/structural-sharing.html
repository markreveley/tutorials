Structural Sharing

One sentence in the Elixir docs does a lot of quiet work: "the elements themselves are not copied." It's easy to nod past it and still have no idea where the not-copied elements actually are. This page exists to give that "somewhere" a concrete address.

The misframe, and the fix

The instinct is to picture a tuple as a box that contains its elements, the way a physical box contains physical things. With that picture, "shared, not copied" is genuinely confusing — if the element isn't in this box and isn't in that box, where is it?

The fix is to drop the nesting picture entirely. A tuple is not a container holding its elements. It is a small block whose slots hold pointers — drawn here as arrows — to where each element already lives. The element exists once, at one heap address. "Sharing" just means more than one arrow points at that address.

Two clarifications make that picture exact — both inherited from rung 2:

  • The "arrow" is the slot — it isn't a third thing between them. A slot is one word. For a pointer, that word's bits are the element's heap address (low bits tagged 10, "boxed"). "Following the arrow" just means read that one word as an address and go there. So the diagram's slot → map is really two things, slot-word and map, not three (slot → arrow → map): the arrow is just the slot-word, drawn.
  • Only boxed elements get an arrow. If an element is an immediate — a small integer, an atom, [], a pid — its bits sit in the slot itself, so there's nothing elsewhere to point at and nothing to share. Arrows, and therefore sharing, happen only for boxed elements: maps, tuples, binaries, bignums, floats. The example below is a tuple of maps exactly so every slot is a boxed pointer worth sharing — a slot holding :a would just carry the atom inline, no arrow.

The concrete story, in addresses

Strip it to two tuples and one shared map and it's unambiguous: 

M  # a big map, living at heap address 1000
t1 = {M, :a}        # new block at 2000: slot0 = 1000 (arrow to M), slot1 = :a (immediate, inline)
t2 = put_elem(t1, 1, :b)
                    # new block at 3000: slot0 = 1000 (SAME arrow to SAME M), slot1 = :b

Now build it one allocation at a time and watch the addresses fill in:

walkthrough · M at 1000, then t1, then t2
3-word blocks (header + 2 slots) at illustrative addresses. :a/:b are immediates — inline in the slot; only M is boxed, so only it is reached by an arrow.

M never moved and was never duplicated. It is the one block at 1000, now with two arrows aimed at it — one from t1, one from t2. That is "shared, not copied," exactly and physically.

Why this is safe In a mutable language, two structures sharing a pointer is a real hazard: mutating M through t1 would be visible through t2 as well. Elixir removes that hazard with immutability: M can never be mutated in place, so it doesn't matter that two tuples point at it. Sharing is only possible because nothing can change underneath a reference. The cost of an "update" is proportional to the container, never to the contents.

The model to carry forward

Stop imagining containers nested inside containers. Imagine a graph of small blocks connected by arrows, where leaf values exist once and many arrows can point at them. "Copied" = a new leaf block was allocated. "Shared" = no new leaf — just another arrow to the block that's already there. The element is never "out there nowhere"; it's at a definite address, and sharing means more than one arrow targets it.
