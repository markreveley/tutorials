Tuples vs Lists in Memory

Now that a value is "a word, sometimes a pointer," we can build the two workhorse collections and see exactly where their famous performance characteristics come from. They aren't arbitrary rules to memorise — they fall straight out of the memory layout.

A tuple is a contiguous block

A tuple is a single block on the heap: a header word (it's a tuple, arity N) followed by N slots, one per element, at fixed evenly-spaced offsets Ch.4.5. Two things become cheap:

  • tuple_size(t) reads the number recorded in the header — O(1), whether the tuple has 4 elements or 4,000.
  • elem(t, i) is arithmetic: start of block + (i+1) words. The machine jumps straight there — O(1), any index.

boxed pointer ──▶ lands at the base; every element is a fixed offset away
└──────────────── one contiguous block, 5 words ────────────────┘
Header records {tuple, arity 4}; the N slots follow at base + (i+1) words, evenly spaced (Ch.4.5). Addresses illustrative; one word = 8 bytes on 64-bit.

The diagram leans on one fact worth stating outright: every slot is exactly one word — never larger. That uniformity is what licenses the base + (i+1) words arithmetic; if slots could vary in size, reaching element i couldn't be a single jump.

What varies isn't the slot's size, it's what the word holds — the immediate-vs-boxed split from rung 2. A value that fits in a word sits in the slot directly; anything bigger (a nested tuple, a map, a float, a bignum, a binary) lives as its own boxed object elsewhere on the heap, and the slot holds a one-word pointer to it. So {:ok, 42, %{a: 1}, 3.14} is still 5 words: the map and float aren't fattening their slots — slot 2 points at the map's block, slot 3 at a boxed float (whose own object is header + the full 64-bit double, stored full-width — just off in its own block, not in the slot).

This is the opposite of a C struct or a numeric array, where an 8-byte double really does occupy 8 contiguous bytes inline and nested structs nest their storage. A BEAM tuple never inlines a multi-word value; size is always escaped through a pointer. The cost is one extra indirection to reach a boxed element; the payoff is that the contiguous-block model and O(1) indexing hold no matter what the tuple contains.

A list is a chain of cons cells

A list is built from cons cells — each just two words on the heap: a head (the value) and a tail (a pointer to the next cell, or [] to end) Ch.4.3. A cell needs no header word — the 01 tag in the pointer already says "this is a list node," which is why a cons cell uses 33% less memory than a boxed 2-tuple. But to reach the Nth element you must follow the chain from the front: O(n).

It's worth seeing that on the heap, in the same word-cells the tuple used above. Each cons cell is a tiny 2-word block — a head word and a tail word — and, crucially, the cells need not sit next to each other. The tail word is the only thing linking them.

a cons cell is two words

And updates? That's the next rung's question

Because data is immutable, put_elem(t, i, v) can't overwrite a slot — it allocates a new tuple block. That sounds expensive (O(n) to build the new block), and it is — but the elements inside are not re-copied. The new block's other slots just point at the same values the old one did.

That single sentence — "the elements themselves are not copied" — is the one most worth getting concrete about. It's the whole of the next rung.
