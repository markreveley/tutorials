Maps: Flat & Hashed

%{} is one syntax, but the BEAM stores maps in two completely different shapes depending on size — and the switch is invisible to you. Both reuse the structural-sharing idea from rung 4; they just arrange it differently. This is the last data-structure rung before we drop to the metal.

A map is a boxed term — its header carries the MAP subtag Ch.4.5. What sits behind that header depends on how many keys it has:

  • Small map → flatmap (up to ~32 keys): keys and values stored in flat, sorted arrays.
  • Large map → hashmap (more than ~32 keys): a Hash Array Mapped Trie (HAMT), a shallow tree indexed by slices of each key's hash.

The MAP boxed tag is per BEAM Book Ch.4.5. The flatmap/HAMT split and the ~32-key threshold are the OTP implementation (erl_map.h, MAP_SMALL_MAP_LIMIT) — the book's data-structures chapter is still WIP, so treat these as current-implementation detail.

Flatmap: sorted arrays, shared keys

A flatmap is essentially two arrays behind the header: a tuple of keys in term order and a parallel array of values. Lookup searches the sorted keys; because they're sorted, two flatmaps with the same key set can share the very same keys tuple. So updating a value (keys unchanged) allocates a new values array but reuses the keys tuple — the same "new container, shared contents" move from rung 4. Adding or removing a key needs a new keys tuple too.

Hashmap: a shallow trie indexed by hash

Past the threshold, scanning a sorted array gets slow, so the map becomes a HAMT. Each node is a small array; to find a key you hash it and use successive slices of that hash to pick a slot at each level, descending until you hit the leaf. The tree is wide and shallow, so lookups and updates are effectively constant-ish (≈ log₃₂ n levels).

The payoff for immutability is path copying: updating one key copies only the nodes along the path from the root to that leaf — every untouched subtree is shared with the old map, pointer-for-pointer. A big map update touches a handful of nodes, not the whole structure. Step through a lookup and an update above to see which nodes get copied and which are shared.

The through-line Tuple update, flatmap value update, HAMT key update — all three are the same principle wearing different clothes: allocate a new spine, share everything you didn't touch. Immutability is what makes the sharing safe; the data structure just decides how big the "spine" is.
