Appendix B

Exit codes and signals

The lookup tables behind page 10: what each number in a log means, which layer produced it, and how the same death is spelled by the shell, by Python, and by Docker. Every value here was either produced in an Ubuntu 24.04 container or is cited to its documentation.

First question: which layer wrote this number?

An exit status is 8 bits, 0–255, because only the low byte of what a program passes to exit reaches its parent.[exit(3)] Several layers share that small space, and each wraps the one inside it:

harness ──▶ docker run/exec ──▶ timeout ──▶ bash -c ──▶ the program 125 126 127 124 125 126 127 0, 1, 2, … 126 127 137 128+N (its own meanings) A number is passed outward unchanged unless a wrapper has something of its own to report. Read a code from the outside in: could the outermost layer have produced it? If not, move one layer in.

Pitfall

exit 256 is success. A test script that exits with "the number of failed tests" reports 0 when exactly 256 fail. Exit with 0 or 1 and put counts in the output.

Going the other way, bash does the subtraction for you: kill -l 137 prints KILL and kill -l 143 prints TERM. SIGKILL and SIGSTOP are the only signals that cannot be caught, blocked, or ignored.[signal(7)]

Caveat — a signal sent is not a signal that kills

The table shows what happens when the default action applies. Three real cases where it did not, all met while building this appendix. (1) A process may ignore a signal, and ignored signals stay ignored across exec:[signal(7)] Python ignores SIGPIPE and SIGXFSZ at start-up (SigIgn: 0000000001001000 in its /proc/self/status), so a Python process sent SIGPIPE simply carried on and exited 0. (2) Background jobs started with & by a non-interactive bash — every bash -c tool call — ignore SIGINT and SIGQUIT;[Bash Manual] we read SigIgn: 0000000000000006 on such a job, and kill -INT will not stop it. (3) PID 1 of a container receives only signals it has handlers for: under docker run ubuntu:24.04 bash -c 'kill -SEGV $$; echo still here' the shell printed still here and exited 0; with --init the same command exited 139. In each mask, bit N−1 stands for signal N.

In eval work

A harness written in Python that checks returncode == 137 to count kills will miss every direct child that died of SIGKILL (those are -9), and one that checks returncode < 0 will miss every kill that happened behind bash -c or docker exec (those are 137). Normalise once, at ingestion — if rc < 0: sig = -rc; elif rc > 128: sig = rc - 128 — and store the signal, the raw code, the duration and the layer that reported it. Then count by cause, as in page 10's failure accounting.
