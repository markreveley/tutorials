Appendix D

Regular expressions

A regular expression is a pattern that describes a set of strings. grep, sed, awk, jq and Python all take them — in three slightly different dialects, which is where most of the pain comes from. This appendix covers the pieces you need for log work, the dialect differences that actually bite, and ten patterns worth keeping.

Every example below was run in the container lab (GNU grep 3.11 on Ubuntu 24.04) against this twelve-line file, agent.log — a made-up harness log whose last line ends in three trailing spaces — or against results.jsonl from page 5. The first command is the everyday regex bug in eval work: a search for "exit code 1" that quietly includes 127, 137 and 124. Say where the number ends — 'exit code 1:' here, or -w/\b (a word boundary) in general.

Three dialects

The same pattern means different things depending on the tool and flag.

DialectWhereWhat differs
BRE (basic)grep, sed by default+ ? | ( ) { } are literal characters. GNU tools accept them as operators when backslashed (\+, \|, \(…\)).
ERE (extended)grep -E, sed -E, awkThose characters are operators; backslash makes them literal. No \d, no lazy quantifiers.
PCRE-stylegrep -P (GNU only), Python re, jq, most programming languagesAdds \d \s \w, lazy *? +?, lookarounds, \K.
$ grep -c 'WARN|ERROR' agent.log        # BRE: looks for the literal text WARN|ERROR
0
$ grep -c -E 'WARN|ERROR' agent.log
5
$ grep -o 'exit code [0-9]+' agent.log | head -n 2      # BRE: + is a literal plus; no output
$ grep -o -E 'exit code [0-9]+' agent.log | head -n 2
exit code 127
exit code 1
$ echo 'a+b' | grep -c -E 'a+b'          # and the reverse: in ERE, a+b means "one or more a, then b"
0
$ echo 'a+b' | grep -c -F 'a+b'          # -F: fixed string, no regex at all
1

Two rules remove most of the confusion: always use -E (with both grep and sed), and when you are searching for a literal string full of punctuation — a file path, an error message with brackets — use grep -F.

Pitfall

\d is not portable, and fails silently. Models and people arriving from Python write \d+ everywhere. GNU grep and sed in ERE mode treat \d as the letter d — no error, just wrong output:

$ echo 'exit code 137' | grep -o -E '\d+'
d
$ echo 'exit code 137' | sed -E 's/\d+/N/'
exit coNe 137
$ echo 'exit code 137' | grep -o -P '\d+'
137

-P fixes it on Ubuntu, but it is a GNU extension. On Alpine, whose grep is BusyBox's, we got grep: unrecognized option: P (exit status 2); the Mac's BSD grep says invalid option -- P — yet that same Mac grep does accept \d under -E and printed 137. One pattern, three machines, three behaviours. [0-9] works on all of them. In a transcript, an agent whose grep '\d+' "finds nothing" and which then concludes the log is clean has made a Linux-fluency error, and the conclusion it drew is unsupported (page 27).

Greedy matching

Quantifiers are greedy: they match as much as they can while still letting the whole pattern succeed. "A quoted string" written as ".*" therefore runs from the first quote on the line to the last: 

$ echo 'cmd="a" arg="b"' | grep -o '".*"'
"a" arg="b"
$ echo 'cmd="a" arg="b"' | grep -o '"[^"]*"'       # portable fix: "anything that is not a quote"
"a"
"b"
$ echo 'cmd="a" arg="b"' | grep -o -P '".*?"'      # PCRE-only fix: lazy quantifier
"a"
"b"

Python's re.findall(r'".*?"', s) gives the same two matches. Prefer the negated class [^"]*: it works in every dialect and says what you mean.

Quoting patterns from the shell

Before grep sees a pattern, the shell has had a go at it (quoting is covered on page 6). Unquoted, [0-9]* is a glob and is replaced by any matching file names; inside double quotes, $5 is a shell variable (empty), and an empty pattern matches every line: 

$ mkdir -p q; cd q; touch 5
$ echo 'exit 137' | grep -o [0-9]*       # shell turned the pattern into the file name "5": no match
$ echo 'exit 137' | grep -o '[0-9]*'
137
$ echo 'cost: 9' | grep -c "$5"          # pattern became the empty string: matches anything
1
$ echo 'cost: 9' | grep -c '\$5'
0

The first failure depends on what files happen to be in the current directory — so the same command works in one rollout and not in another. Single-quote every pattern.

Ten patterns for log work

All ERE (grep -E / sed -E) unless marked.

#GoalPattern
1Extract exit codesgrep -o -E 'exit code [0-9]+'

3IPv4-shaped strings'[0-9]{1,3}(\.[0-9]{1,3}){3}'
4ISO-8601 UTC timestamps'[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z'
5Log lines at WARN or above'^[0-9-]+T[0-9:]+Z (ERROR|WARN) '

7The final exception line of a traceback'^[A-Za-z]+(Error|Exception):'

Notes on three of them. Pattern 2 shows how awkward numeric ranges are in a language that only knows characters: for "exit code ≥ 126", extract the number with pattern 1 and compare it in awk. Pattern 3 matches the shape of an address — it would accept 999.999.999.999 — which is fine for finding candidates in a log and wrong for validating input. In pattern 8, sed -n with the p flag prints only lines where the substitution happened, and \1 is whatever the first ( ) group captured.

Caveat

Don't parse JSON with a regex. The [^"]* trick works on results.jsonl only because no value in it contains a quote. The sample log has one that does:

$ grep -o 'note="[^"]*"' agent.log
note="model said \"
$ grep -o -E 'note="([^"\\]|\\.)*"' agent.log
note="model said \"done\" early"

The second pattern ("any character that isn't a quote or backslash, or a backslash followed by anything") is correct and unreadable, and JSON has more escapes than that. Model output is exactly where embedded quotes, newlines and backslashes turn up. For JSON use jq (page 5), which parses rather than pattern-matches; keep regexes for unstructured text.

In eval work

A regex in a grader is part of the measuring instrument. Many scorers extract the model's answer with a pattern — ANSWER: (\d+), a fenced code block, the last number in the output. Each mistake on this page has a scoring consequence: an unanchored pattern accepts 137 when the expected answer is 1; a greedy .* swallows two answers into one; trailing whitespace fails an exact match on a correct answer; a dialect slip makes the extractor return nothing, and "no answer found" is recorded as "wrong". When you review a scorer, read its regexes as carefully as its logic, and test them against real transcripts, including the ugly ones. A rollout whose answer the extractor could not find is a different outcome from a wrong answer, and should be counted separately until someone has looked.

Practice

Lab

Container lab, with agent.log as above and results.jsonl from page 5.

  1. Predict the output of grep -c 'exit code 1$' agent.log. Why is it not 1?

    Solution

    It prints 0. $ anchors to the end of the line, and no line ends right after exit code 1: that line continues with : Traceback…. To match the code 1 exactly, use 'exit code 1:' or -E 'exit code 1\b'.

  2. Count the rollouts in results.jsonl that ended with exit code 124 or 137 using one grep -E. Why does the pattern need the trailing comma (or a \b)?

    Solution 
    $ grep -c -E '"exit_code": (124|137),' results.jsonl
13

    Without something after the group, (124|137) would also match the start of a longer number such as 1240. It can't occur in this file; in a real one you don't know. (The jq version on page 5 compares numbers and has no such problem.)

  3. Extract just the numbers from the exit code N lines of agent.log — once with sed -E and a capture group, once with grep -P and \K ("forget everything matched so far").

    Solution 
    $ echo 'exit code 137' | sed -E 's/exit code ([0-9]+)/status=\1/'
status=137
$ grep -o -P 'exit code \K\d+' agent.log
127
1
137
0
124

    For the whole file with sed: sed -n -E 's/.*exit code ([0-9]+).*/\1/p' agent.log. The -P form is shorter and will not run on Alpine or macOS.
