Appendix G

Skills checklist and portfolio labs

The finish line, stated as things you can demonstrate. Use the checklists to find your next gap, the questions to rehearse explaining out loud, and the portfolio labs to turn the course into work someone else can inspect.

An honest finish line

This is the Linux component of preparing for evaluation work, not a promise of employment, and the checklists below are an original self-assessment, not an industry certification. What they give you is a way to tell "I read about it" from "I can do it with someone watching". Every item is phrased so that a second person could check it.

How to use this page

Work through a module's checklist in a fresh lab container (page 1), without the course open. An item counts when you can do it from memory or find the answer with man and --help inside two minutes (Appendix F) — looking things up is a skill, guessing is not. Each module ends with its "deep enough when" test: a single task that needs the whole module at once.

The three abilities from the course home run through every list: discuss (explain the mechanism and what it does to a score), navigate (investigate from inside the box and bring evidence), design (choose and defend an environment policy).

Module 1 · The shell

  • Explain what happens between pressing Enter and seeing output: the shell parses the line, finds the program on PATH (or runs a builtin), starts a process, waits, and records an exit status.
  • Say why a command that works in your interactive terminal can be "not found" when a harness runs it, and name the dependable fix.
  • Find every file under /app changed since a marker moment, and say why a timestamp-based answer can be fooled.
  • Draw the three standard streams as numbered file descriptors and predict the difference between cmd >out 2>&1 and cmd 2>&1 >out before running them.
  • From a JSONL results log, produce the pass rate per model, the most common exit codes among failures, and the tasks that never pass — using only jq, sort, uniq -c, and grep.
  • Read a 25-line bash script and say what its exit status will be when the third command fails, with and without set -euo pipefail.
  • Run shellcheck on a script, and explain the unquoted-variable warning with a filename that contains a space.

Deep enough when: handed page 5's results.jsonl cold, within fifteen minutes you can say which model is ahead, which task is broken rather than hard, and what fraction of failures are not test verdicts at all — and show the pipelines that say so.

Module 2 · Identity & permissions

  • Show who a process is (id, /proc/PID/status) and explain why the kernel cares about the number, not the name.
  • Read -rwxr-x--- aloud, convert it to octal, and predict who can read the file — including the case where the owner is denied and everyone else is not.
  • Explain why deleting a file is a question about the directory's permissions.
  • Protect a grader directory from a non-root agent with ownership and mode bits, prove it from the agent's shell, then name three ways that protection silently fails.
  • Find every setuid binary on a box and say why the list is an audit item.
  • Tell Permission denied from Operation not permitted and say which layer produced each.

Deep enough when: you can look at a task image and answer "could the agent have read or rewritten the tests?" with commands run as the agent's uid, not by reading the Dockerfile.

Module 3 · Processes

  • Print the process tree and point to PID 1, to anything left running from an earlier step, and to any process that is not the agent's.
  • Decode exit statuses 0, 1, 2, 124, 126, 127, 130, 137, 139, 143 without notes, and do the 128+N arithmetic for a signal you have not memorised (Appendix B).
  • Explain why exit 137 is not proof of an out-of-memory kill, and list the evidence that would settle it either way.
  • Explain why an application running as PID 1 in a container can take ten seconds to stop, and two ways to fix it.
  • List every place a secret passed as an environment variable can be read, from inside the box and from outside it.
  • Read a cgroup's memory, CPU, and PID limits from inside a container, and show that free and nproc do not reflect them.
  • Produce, for real, the symptom of each exhaustion — memory, CPU cap, disk, inodes, PIDs — and say how each should be recorded in a results file.
  • Say where logs live on a VM with systemd versus in a container, and why docker logs can be empty for a rollout driven through docker exec.

Deep enough when: given a rollout that "failed", you can classify it as a test verdict, a timeout, a resource kill, or an environment defect from the exit code, the last lines of stderr, the duration, and the cgroup counters — and you report it in the right row of the accounting table (page 10).

Module 4 · Storage & software

  • Print the mount table as a tree, find what backs a given path, and list what is mounted read-only.
  • Distinguish three refusals to write: mode bits, a read-only mount, and a missing capability — by their error messages.
  • Explain why a read-only mount protects tests from tampering but does nothing about them being read.
  • Explain why a file deleted in a later image layer is still in the image, and show how you would check.
  • Pin a base image by digest and say what is still free to drift after you have.
  • Recognise in a transcript: a missing apt-get update, an interactive prompt hang, the dpkg lock, externally-managed-environment, and an install attempted with no network.
  • Fingerprint an environment (packages and versions) and diff two builds.

Deep enough when: you can explain to a teammate why "we used the same Dockerfile" does not establish "we ran the same environment", and what you would publish alongside results so that someone else can tell.

Module 5 · Networking for sandboxes

  • From inside a box, state its addresses, its default route, and what is adjacent: the gateway, neighbouring containers, a metadata address.
  • List what is listening, on which address, owned by which process — and explain why 127.0.0.1:8000 and 0.0.0.0:8000 are different exposures.
  • Tell refused from timed out from unresolvable, say which layer each points at, and say why "refused" cannot distinguish a closed port from a rejecting firewall.
  • Use curl's exit code and -v output to name the last stage that worked: name resolution, connection, TLS, HTTP.
  • Explain why HTTPS can fail in a minimal image for a reason that has nothing to do with the network.
  • Run the reachability probe (page 19) under no network, an internal network, and the default bridge, and explain each verdict.
  • Explain why supplying your own compose file to a harness can silently turn a no-network sandbox into an open one.

Deep enough when: you can write five commands, run from inside a sandbox, that show whether it can reach the internet, a neighbouring sandbox, and services on its host — always with timeouts, and you can say what each result does and does not establish. For the concepts underneath, the sibling course Networking for LLM Evals is the companion.

Module 6 · Containers & isolation

  • Explain a container as an ordinary process with a restricted view (namespaces), a restricted budget (cgroups), its own root filesystem, and reduced privileges — and show each with a command.
  • Show that two containers and their host share one kernel, and say why that fact organises the whole isolation discussion.
  • Read a process's effective capabilities and decode them; explain why root in a default container still cannot mount a filesystem.
  • Write a Dockerfile for a task environment: pinned base, packages installed in one layer, non-root user, exec-form command — and justify each line.
  • Take a default docker run to a locked-down one knob by knob, saying for each knob what it blocks, how to verify it from inside, and what legitimate task behaviour it can break.
  • Re-validate the oracle solution under the hardened policy, and explain why that step is not optional.
  • Place containers, gVisor, microVMs, and full VMs on the isolation ladder and say what goes up with each rung: isolation, cost, startup time, compatibility risk.
  • Name the four boundaries — isolation, egress, tenancy, secrets — and one check per boundary that would show it failing.

Deep enough when: the running example runs in a locked-down container you configured by hand, an inside-out verification script passes, the oracle still passes, and you can state which threats the setup does not address.

Module 7 · Linux in eval harnesses

  • In an unfamiliar benchmark's repository, find five things: the image definition, the exec path, the timeouts and limits, the network policy, and where grading runs.
  • Map harness features to Linux mechanisms: exec-per-call to a non-interactive shell, the stdout/stderr split, timeouts to signals, a user parameter to a uid, limits to cgroups.
  • Walk the seven integrity surfaces (page 26) against a task image and report what you checked, what you found, and what you could not check.
  • Read a terminal transcript and code each failed rollout as model capability, model Linux fluency, environment defect, harness defect, or integrity violation — separating what you observed from what you suppose.
  • Report one run three ways — correct/scheduled, correct/completed, completed/scheduled — and say which one was the primary metric before you looked.
  • Perform the ten-minute audit on a box you have not seen, and write it up as findings, validity impact, fix, residual risk.

Deep enough when: someone hands you shell access to a task environment and asks "can we trust scores from this?", and ten minutes later you have an answer with evidence attached.

Questions to answer out loud

Say your answer before opening the reasoning. These are judgment questions: a good answer names what you would establish first, what evidence would discriminate between causes, and how the outcome bears on the reported number.

Check your understanding

A benchmark's pass rate drops six points after the team moves rollouts from one large machine to many small ones. Nothing about the model changed. What do you establish before anyone says "regression"?

Reveal the reasoning

Whether the same tasks completed. Compare, per task, exit codes, durations against the timeout, and the resource counters: memory.events for oom_kill, cpu.stat for throttling, disk and PID limits. A smaller machine or higher packing changes per-sandbox memory and CPU, which converts some capable rollouts into kills and timeouts. Then check the environment itself: same image digest, same network policy, same harness version. Report completed/scheduled next to the pass rate for both configurations. If the drop lives entirely in rollouts that did not complete, it is an observation about the infrastructure, and the honest headline is that the two numbers are not comparable yet.

Check your understanding

An agent's final message says "All tests pass." The harness recorded exit code 0 for the test command and an empty stdout. Do you believe it?

Reveal the reasoning

Not yet; the message is testimony and the exit code is only as good as the command that produced it. Look at the exact command: a pipeline such as run-tests | tee log reports the status of tee unless pipefail is set, and a script whose last line is echo done exits 0 whatever happened above it. Empty stdout with a test runner that normally prints a summary is itself evidence — check stderr, which the harness captures separately, and check whether output was truncated. The discriminating test is to re-run the tests yourself, as the same user, against the final state of the box — or better, against a copy of it in a fresh container the agent never touched.

Check your understanding

A colleague proposes hiding the expected answers inside the task container at /opt/grader, owned by root with mode 700, and running the agent as a non-root user. Is that enough?

Reveal the reasoning

It is a real protection with known ways to fail, so the answer depends on checks rather than on the design's intent. Verify as the agent's uid that the directory cannot be listed or traversed. Then look for the bypasses: is the agent actually non-root in every exec path the harness uses, including setup and tool calls with a user override; is there sudo, a setuid binary, or an added capability; was the same material also left in an earlier image layer, in git history, in an environment variable, or in a process the agent can inspect? And consider the stronger design: answers that are never in the box cannot be read from it. Grade outside, after the agent exits, on a copy of the artifacts. Permissions then become defence in depth instead of the only wall.

Check your understanding

A rollout log shows curl: (6) Could not resolve host: pypi.org, after which the agent gave up installing a dependency and the task failed. Whose failure is it?

Reveal the reasoning

First establish the intended policy. If the task is specified as no-network, the environment behaved as designed and the question becomes whether the task is solvable without that dependency — which the oracle solution, run under the same policy, answers. If the oracle needs the network too, this is an environment defect and every rollout on that task is uninformative about the model. If the policy was supposed to allow the package index, then resolution failing is an infrastructure fault: check the resolver configuration inside the sandbox and whether the failure is constant or intermittent across rollouts. In no case is "the model failed the task" established by this log alone. Record the outcome in its own category, keep it in the scheduled denominator, and fix the environment before re-running.

Check your understanding

Your team wants stronger isolation and proposes switching every sandbox from containers to microVMs. What do you ask?

Reveal the reasoning

What threat the change is meant to address. A shared kernel is the container's structural weakness, so if the concern is code-execution escape by an adversarial guest, moving up the ladder is a relevant answer. If the concern is agents reaching the internet, reading answer keys, or seeing each other's state, the isolation technology is not the control that matters: egress policy, where grading runs, and per-rollout freshness are. Then ask what it costs: hosts with hardware virtualisation available, startup time and memory per rollout, and — for measurement — whether task outcomes change under the new runtime, which you check by re-validating oracle solutions and comparing a fixed model across both. Change one thing at a time, or call the comparison what it is: two deployment bundles.

Portfolio labs

Five projects, each small enough for a few evenings and each leaving behind something a reviewer can read in ten minutes. Write every one up the same way: what you set out to establish, what you ran, what you observed, what you concluded and what you could not conclude. Publish the commands.

1 · Audit a public benchmark's task environment

Pick one task from an open agentic benchmark whose environment you can build locally. Run the ten-minute audit inside it and the outside-the-box half (docker inspect, image history) around it. Write up findings in the capstone's template: finding, validity impact, fix, residual risk. If you find a real defect, report it to the maintainers privately or through their issue tracker as they prefer, and say so in the write-up.

Shows: navigate, and the judgment to separate "this is unusual" from "this affects scores".

2 · A hardened sandbox with an inside-out self-test

Take a small task of your own (or the course's running example) and produce: a Dockerfile pinned by digest, a locked-down run configuration, a script that verifies every hardening property from inside the box and prints PASS/FAIL per line, and evidence that the oracle solution still passes under the policy. Include a table of each knob, what it blocks, and what it could break.

Shows: design, and that you test your environment the way you would test your code.

3 · A reachability probe as an environment check

Turn page 19's probe into a check that runs before every eval: it starts a sandbox under the intended network policy, probes the internet, a neighbour, the host gateway, and the metadata address with timeouts, and fails the run if any verdict differs from the declared policy. Demonstrate it catching a deliberately misconfigured compose file.

Shows: that you treat the network policy as part of the experiment's configuration.

4 · A history-leak detector for task repositories

Write a short tool (Python, calling git) that, given a task repository and the commit a task is supposed to start from, reports anything reachable or recoverable beyond it: other refs, tags, reflog entries, dangling objects. Test it on a repository you construct with a known leak and on the same repository after cleaning, and document what "clean" means (page 26).

Shows: you can turn a published incident into a repeatable check.

5 · Failure coding over real transcripts

Take a set of publicly available agent rollout logs for terminal or coding tasks. Code each failure with the scheme from page 27, using page 5's tools for the first pass and reading for the rest. Report the distribution, the three accounting ratios, examples of each category with the evidence that placed them there, and the cases you could not classify. If you are new to error analysis, the sibling course's page on it is the method.

Shows: the core applied-evals skill, on the kind of data the job actually has.

Choosing what to learn next

If the shell still feels slow, repeat the labs of Module 1 until the pipelines come without thought; everything else rests on them. If exit codes and signals are vague, redo page 10's lab and keep Appendix B open while reading real transcripts. If containers still feel like magic, rebuild one by hand with unshare (page 20). When the Linux side is steady, the measurement side is in Understanding LLM Evals, the infrastructure side in Networking for LLM Evals, and the harness itself in the documentation that page 25 cites.
