Appendix F

Man pages and getting help

The course teaches about seventy commands and promises you can find the rest. This appendix is how: the manual and its numbered sections, reading a SYNOPSIS, the three other places help lives, what to do in a minimal image where the manual has been deleted, and what a citation like [signal(7)] means.

Four places help lives

AskAnswers forPresent in a minimal image?
man namePrograms, system calls, file formats, concepts — the reference manualUsually not (see below)
command --helpThat one program's options, in briefYes: it is built into the program
help nameCommands that are part of bash itself (cd, export, set, trap …)Yes, wherever bash is
type nameNot help, but the question before help: what is this name?Yes

Start with type, because it tells you which of the others to use:

$ type cd kill ls timeout
cd is a shell builtin
kill is a shell builtin
ls is /usr/bin/ls
timeout is /usr/bin/timeout
$ type -a kill
kill is a shell builtin
kill is /usr/bin/kill
kill is /bin/kill
$ man cd
No manual entry for cd
$ help cd | head -2
cd: cd [-L|[-P [-e]] [-@]] [dir]
    Change the shell working directory.

A builtin is a command implemented inside the shell rather than as a separate program (page 2 explains why cd has to be one). Builtins have no man page of their own; help documents them. kill is both: bash has its own, and there is also a program /usr/bin/kill. When you type kill you get the builtin, but man kill describes the program. The two agree on the basics and differ at the edges, which is worth knowing before you trust either page about an edge.

The manual and its sections

The manual is divided into numbered sections, because the same name can mean different things. The list, from man man on Ubuntu 24.04: 

       1   Executable programs or shell commands
       2   System calls (functions provided by the kernel)
       3   Library calls (functions within program libraries)
       4   Special files (usually found in /dev)
       5   File formats and conventions, e.g. /etc/passwd
       6   Games
       7   Miscellaneous  (including  macro  packages  and  conventions), e.g.
           man(7), groff(7), man-pages(7)
       8   System administration commands (usually only for root)
       9   Kernel routines [Non standard]

A man page is always named with its section in parentheses, and the convention is used everywhere in Linux writing, including this course. Three pages about ending a process show why the number matters:

PageSectionWhat it documentsYou read it when
kill(1)1 · programsThe kill command and its optionsyou want to send a signal from the shell
kill(2)2 · system callsThe kernel service the command uses; permission rules, error codesyou need to know who is allowed to signal whom, or what EPERM means here
signal(7)7 · overviewsThe concept: the list of signals, their numbers and default actions, which cannot be caughtyou are decoding an exit status (page 10)

For an evals engineer the sections that pay are 1 and 8 (commands), 5 (file formats: passwd(5), resolv.conf(5)) and 7 (the overviews this course cites most: signal(7), capabilities(7), namespaces(7), cgroups(7)). Sections 2 and 3 are written for C programmers; learn to recognize them and to mine them for one fact — an error's meaning, a permission rule — without reading the rest.

Ask for a section by putting the number first. If you leave it out, man shows the first match in its search order, which is not always the one you meant. (This session is from a lab container with the programmer's pages, manpages-dev, also installed, as they are on most full systems; without them sections 2 and 3 are simply absent.) 

$ man -f kill                # -f: which sections have a page by this name? (same as: whatis kill)
kill (1)             - send a signal to a process
kill (2)             - send signal to a process
$ man -w signal              # -w: which file would be shown?
/usr/share/man/man2/signal.2.gz
$ man -w 7 signal
/usr/share/man/man7/signal.7.gz
Pitfall

man signal opens signal(2), a C function, and a beginner looking for the table of signal numbers concludes the manual is useless. The table is in man 7 signal. The same trap: man passwd is the command; the file format is man 5 passwd. When a page seems to be about the wrong thing, run man -f name and check for another section.

Finding a page when you do not know its name

$ man -k "send a signal"     # -k: search names and one-line descriptions (same as: apropos)

pthread_kill (3)     - send a signal to a thread

$ apropos -s 1 signal          # restrict to section 1: commands only

The search covers only the one-line descriptions, so use plain words a description would contain ("signal", "mount", "list open"), and narrow with -s.

Reading a SYNOPSIS

Every page in sections 1 and 8 opens with a SYNOPSIS: the command's grammar in a compact notation. Two real ones: 

$ man timeout
SYNOPSIS
       timeout [OPTION] DURATION COMMAND [ARG]...
       timeout [OPTION]
$ man cp
SYNOPSIS
       cp [OPTION]... [-T] SOURCE DEST
       cp [OPTION]... SOURCE... DIRECTORY
       cp [OPTION]... -t DIRECTORY SOURCE...
NotationMeaningIn the examples
[ ]Optional[OPTION]: options may be omitted
...The thing before it may repeatSOURCE...: one or more sources; [ARG]...: zero or more
UPPERCASE (underlined in a terminal)A placeholder you replaceDURATION becomes 30s
lowercase, literal punctuationType exactly as shown-t, cp
a | bOne or the otherkill [-s sigspec | -n signum | -sigspec] in help kill
Several linesSeparate forms of the commandcp has three: file to file, files into a directory, and the same with the directory named first

Order matters in a synopsis. timeout [OPTION] DURATION COMMAND [ARG]... says options for timeout go before the duration, and everything after COMMAND belongs to the command being run. That is why timeout 5 ls -l works as hoped and -l is not taken as an option to timeout.

After SYNOPSIS come DESCRIPTION and the option list, then the sections people skip and should not: EXIT STATUS (what the numbers mean — see the lab), FILES and ENVIRONMENT (what the program reads without being told), SEE ALSO (the next page to read).

Moving around inside a page

man displays pages through a pager called less. The same keys work whenever you run less on a log file. From less --help: 

  h  H                 Display this help.
  q  :q  Q  :Q  ZZ     Exit.
  b  ^B  ESC-v      *  Backward one window (or N lines).
  /pattern          *  Search forward for (N-th) matching line.
  ?pattern          *  Search backward for (N-th) matching line.
  g  <  ESC-<       *  Go to first line in file (or line N).
  G  >  ESC->       *  Go to last line in file (or line N).

The working set: Space forward a screen, b back, / then a word and Enter to search, n for the next match, q to quit. To find an option, search for it with leading spaces so you land on its definition instead of a mention: / -k. Or skip the pager: man timeout | grep -A3 -- -k.

In eval work

A pager waits for keys. When man writes to a pipe or a file instead of a terminal it prints the whole page and exits — man timeout | wc -l printed 95 in our lab container with nobody pressing anything. But a harness that gives the agent a real terminal (Terminal-Bench's reference agent drives a tmux session[Terminal-Bench]) will leave it sitting inside less until it sends q. In a transcript, a man, git log or systemctl status call followed by garbled output or a timeout is often exactly this. It is an agent-fluency failure you can design around: task images that set PAGER=cat and MANPAGER=cat remove the trap for every agent equally (page 27).

--help, and help for Docker

Nearly every GNU program answers --help with a usage line, its options, and often its exit statuses. It is shorter than the man page, always matches the installed version, and is there when the manual is not. A mistyped option points you at it: 

$ ls --hepl
ls: unrecognized option '--hepl'
Try 'ls --help' for more information.
$ timeout --help | head -3
Usage: timeout [OPTION] DURATION COMMAND [ARG]...
  or:  timeout [OPTION]
Start COMMAND, and kill it if still running after DURATION.

Docker has no man pages on a Mac; its help is a tree you walk with --help at each level. docker --help lists commands; docker command --help gives that command's synopsis and options: 

$ docker run --help | head -3
Usage:  docker run [OPTIONS] IMAGE [COMMAND] [ARG...]

Create and run a new container from an image
$ docker run --help | grep -E -- ' --(rm|memory|network|read-only) '
  -m, --memory bytes                     Memory limit
      --network network                  Connect a container to a network
      --read-only                        Mount the container's root
      --rm                               Automatically remove the

The synopsis rule from above explains a classic mistake: [OPTIONS] come before IMAGE, and everything after the image is the command to run inside. docker run ubuntu:24.04 --rm bash tries to execute a program called --rm and fails with exec: "--rm": executable file not found in $PATH, exit status 127. The word after an option's name (bytes, network) is the type of value it takes; options with no such word are on/off switches. With about a hundred options, grep is how you read this page. The full semantics are in the online reference that the course cites as [Docker: run].

Minimal images have no manual

Container images are trimmed for size, and documentation goes first. The three base images the course uses: 

$ docker run --rm ubuntu:24.04 man ls
This system has been minimized by removing packages and content that are
not required on a system that users do not log into.
…
$ docker run --rm debian:bookworm-slim man ls
docker: Error response from daemon: … exec: "man": executable file not found in $PATH: unknown
$ docker run --rm alpine:3.20 sh -c 'ls --help 2>&1 | head -3'
BusyBox v1.36.1 (2025-11-23 14:32:18 UTC) multi-call binary.

Usage: ls [-1AaCxdLHRFplinshrSXvctu] [-w WIDTH] [FILE]...

Ubuntu's image has a stub that prints a notice; Debian's slim image and Alpine have no man at all. Alpine's ls is not GNU's: it is BusyBox, one small program standing in for hundreds of commands, with fewer options, and its --help is the only documentation on board. What to do, in order of effort:

  1. Use --help and help. They are always there.
  2. Read the page online. man7.org publishes "HTML renderings of the man pages from the Linux man-pages project as well as a curated collection of pages from various other free software projects."[man7.org] Its addresses are predictable: signal(7) is at man7.org/linux/man-pages/man7/signal.7.html. For Debian- and Ubuntu-specific tools such as apt-get(8), use manpages.debian.org or manpages.ubuntu.com, which let you pick the release.
  3. Read it in your lab container, where page 1 restored the manual with unminimize. Install manpages-dev as well if you want sections 2 and 3.
Caveat — which version are you reading?

The manual describes the software it shipped with. man7.org renders the newest release of the man-pages project (each page's COLOPHON, at the bottom, names it: 6.19 when this was written), while Ubuntu 24.04 installs version 6.7. For long-stable material such as signal numbers the difference is nil; for newer kernel features, check the COLOPHON, and treat the box in front of you as the authority — --help cannot be out of date. The same caution applies more strongly to your Mac: man ls in macOS's Terminal documents the BSD ls, and man timeout there opens a C library page (curs_inopts(3X)), because macOS has no timeout command. Read Linux manuals on Linux or online (Appendix E).

Two more tools you will see mentioned. info is the GNU project's own manual system; some GNU man pages end by pointing to it for the full text, and the same manuals are on the web (the course cites the Bash one as [Bash Manual]). tldr is a community collection of short example-only pages. Neither is installed in the lab image; neither is needed for the course. Recognize the names.

How this course cites

Every bracketed superscript is a link to the primary source for the sentence it follows, and the box at the foot of each page lists them in full.

TagRead it asLinks to
[signal(7)], [capabilities(7)], [proc(5)]The man page of that name and sectionman7.org
[apt-get(8)]A distribution-specific man pagemanpages.debian.org
[Kernel: cgroup-v2]The kernel's own documentationdocs.kernel.org
[Docker: run], [Docker: security]A page of Docker's documentationdocs.docker.com
[Bash Manual], [POSIX], [RFC 1918]A reference manual or standardgnu.org, the Open Group, rfc-editor.org
[Inspect], [Terminal-Bench], [SWE-bench], [METR] …Harness documentation, papers, incident reportsthe project or publisher

Two kinds of statement carry no tag. Terminal output needs none: it was produced by running the command shown, and you can run it again. General explanation (what a process is, how a pipe joins two programs) needs none either. Everything else — a default, a limit, a guarantee, a number, an incident — has a tag, and if you ever need to rely on such a fact at work, follow the link and read the sentence in its original context. That habit is the evidence-versus-hypothesis discipline applied to reading: a man page quoted from memory is a hypothesis; the page on the box is evidence.

Lab

Where: the container lab from page 1, built from the lt-lab image so that man pages are present. For exercise 2's section 7 pages nothing extra is needed.

1. Find the right section. Which man page documents the format of /etc/shadow? Find out without opening any page.

Solution 
$ man -f shadow
shadow (5)           - shadowed password file

Section 5 is file formats, so man 5 shadow. (Page 7 reads it.)

2. Predict, then verify. A process writes to a pipe whose reader has gone away and receives SIGPIPE. Before looking: what is that signal's number, and does it kill the process by default? Now find both answers in the manual with one grep and no pager.

Solution 
$ man 7 signal | grep -E '^ +SIGPIPE'
       SIGPIPE      P1990      Term    Broken pipe: write to pipe with no
       SIGPIPE         13          13      13      13

Term is the default action — terminate — and the number is 13 on every architecture column. A program killed this way reports exit status 128 + 13 = 141, which is what yes | head -1; echo "${PIPESTATUS[0]}" prints for yes (page 4). Note that man signal without the 7 would have searched the wrong page.

3. An eval-flavoured one. In a transcript, an agent inside a stock ubuntu:24.04 task image runs man timeout, gets the "minimized" notice, and then guesses that a timed-out command exits with status 1. Its script treats 124 as a crash and the rollout fails. In a fresh ubuntu:24.04 container, find the authoritative list of timeout's exit statuses without any man page. Then: is this failure the model's or the environment's?

Solution 
$ docker run --rm ubuntu:24.04 bash -c 'timeout --help | grep -A6 "^Exit status"'
Exit status:
  124  if COMMAND times out, and --preserve-status is not specified
  125  if the timeout command itself fails
  126  if COMMAND is found but cannot be invoked
  127  if COMMAND cannot be found
  137  if COMMAND (or timeout itself) is sent the KILL (9) signal (128+9)
  -    the exit status of COMMAND otherwise

The information was one --help away, so the primary classification is model Linux-fluency: the agent had a working route to the fact and guessed instead. But record the environment observation too — the image's manual is a stub — because it applies to every agent on every task, and whoever maintains the benchmark may decide that an image meant to resemble a developer's machine should have its documentation. One failure, two findings, neither dropped.
