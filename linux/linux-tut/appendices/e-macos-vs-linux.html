Appendix E

macOS vs Linux

Your Mac's terminal looks like Linux and is not. The shell is different, the everyday commands are a different family with different flags, and the kernel features this course is about do not exist there. This appendix lists the differences that actually bite, each one run for real on both sides, so you know why a command from this course (or from an agent's transcript) fails on your laptop — and why scripts you test on your laptop fail in the box.

The one rule

Run the course's commands in the container lab (page 1), not in the Mac's own terminal. And test anything that will run inside an eval environment — setup scripts, graders, reset hooks — inside the image it will run in. The Mac is where you type docker; it is not a model of the sandbox.

How this page was made

The macOS side: macOS 15.4.1 on Apple Silicon (uname -sm prints Darwin arm64), default zsh, stock Apple tools, no GNU tools installed. The Linux side: docker run --rm ubuntu:24.04 on the same machine (Linux aarch64). Output is pasted from those runs, trimmed with …. Apple changes its tools between releases: several differences that older guides list have disappeared (see below), so when in doubt, run it.

The shell: zsh vs bash

macOS 15.4Ubuntu 24.04
echo $SHELL/bin/zsh (zsh 5.9)/bin/bash
/bin/bash --versionGNU bash, version 3.2.57GNU bash, version 5.2.21

Two consequences. Interactive habits mostly transfer, because zsh and bash share the basics taught on page 2; their startup files do not (zsh reads ~/.zshrc, not ~/.bashrc). And a script with #!/bin/bash runs under a very old bash on a Mac, so a script that works in the container can fail on the laptop: declare -A m (an associative array) works in Ubuntu's bash and gets declare: -A: invalid option from the Mac's. (This Mac also has a newer Homebrew bash at /opt/homebrew/bin/bash — earlier on PATH, but not what #!/bin/bash names. Page 2 explains why those differ.)

BSD userland vs GNU userland

"Userland" means the ordinary commands: ls, sed, date, stat. Ubuntu's come from the GNU project (GNU coreutils and friends); Apple's descend from BSD. Same names, same core behaviour as far as POSIX specifies it, different everything else — and agents, trained mostly on Linux transcripts, write the GNU dialect. The first tell is that BSD tools don't know long options: 

mac$ sed --version
sed: illegal option -- -
usage: sed script [-EHalnru] [-i extension] [file ...]

Pitfall — the sed -i error doesn't mention -i

BSD sed -i requires an argument (a backup suffix, '' for none). Given the GNU form, it swallows your s/fail/pass/ as the suffix, takes the file name as the script, and complains about stdin. Given the BSD form, GNU sed takes ''… as an empty script and your script as a file name. Neither message points at the cause. There is no spelling of in-place sed that works on both; in anything that must run in both places, write to a new file and mv it, or use Python.

Not different any more (on macOS 15.4)

Older cheat-sheets — and this course's own plan — list these as macOS gaps. On this Mac they all worked: readlink -f link.txt and realpath print the resolved absolute path; base64 -d decodes (as does the BSD -D); ls --color=auto is accepted; md5sum exists alongside shasum. Don't assume they work on a colleague's older macOS.

Homebrew's g-prefixed GNU tools

If you want GNU behaviour on the Mac itself, Homebrew's coreutils formula installs it under new names. Its own install notes say: "Commands also provided by macOS … have been installed with the prefix 'g'", with an optional gnubin directory you can put on your PATH to get the normal names.[Homebrew: coreutils] So GNU date is gdate, GNU timeout is gtimeout. (That formula covers coreutils only; GNU sed, grep, and find are separate formulae. This Mac has none of them installed, so those are not executed here.) Useful for your own convenience — but a script that calls gdate now runs only on Macs with Homebrew.

What macOS doesn't have at all

mac$ ls /proc
ls: /proc: No such file or directory
mac$ which ip ss
ip not found
ss not found
mac$ which ps top lsof netstat ifconfig
/bin/ps
/usr/bin/top
/usr/sbin/lsof
/usr/sbin/netstat
/sbin/ifconfig

No /proc, so nothing from pages 9–12 that reads it; no ip or ss (Module 5), only the older ifconfig/netstat family. More fundamentally, macOS is not Linux underneath: namespaces, cgroups, seccomp, and the other mechanisms of Module 6 are Linux kernel features. That is why Docker Desktop on a Mac runs a small Linux virtual machine and puts your containers inside it: the kernel a container reports is that VM's (cat /proc/version in the lab says linuxkit), and "the Docker host" in later pages means that VM, not your Mac.

A case-insensitive filesystem

mac$ touch Readme.md; ls readme.md README.MD
readme.md
README.MD
mac$ echo one > Notes.txt; echo two > notes.txt; ls; cat Notes.txt   # in an empty directory
Notes.txt
two                                    # one file; the second write went into the first
# touch Readme.md; ls readme.md README.MD
ls: cannot access 'readme.md': No such file or directory
ls: cannot access 'README.MD': No such file or directory
# echo one > Notes.txt; echo two > notes.txt; ls; cat Notes.txt
Notes.txt
notes.txt
one                                    # two different files

The Mac's default filesystem preserves case but ignores it when matching names; Linux filesystems treat names as plain bytes. Code with import Utils against utils.py passes on the Mac and fails in the container; two files whose names differ only in case — legal in a Linux image or a git repository — collapse into one on the Mac, as Notes.txt just did.

Line endings

Not a macOS difference as such (macOS and Linux both end lines with a single newline), but it arrives by the same road: a file edited on someone's laptop, copied into an image. Windows editors end lines with carriage-return + newline (CRLF), and Linux treats the carriage return as part of the line: 

# printf '#!/bin/bash\r\necho hi\r\n' > crlf.sh; chmod +x crlf.sh
# ./crlf.sh
bash: ./crlf.sh: cannot execute: required file not found
# echo $?
127
# cat -A crlf.sh                          # -A: show invisibles; ^M is the carriage return
#!/bin/bash^M$
echo hi^M$
# sed -i 's/\r$//' crlf.sh
# ./crlf.sh
hi

The kernel looked for an interpreter literally named /bin/bash\r. The file that is "not found" is not the script you can plainly see — which is what makes this one expensive. cat -A is the discriminating test.

Architecture: arm64 laptops, amd64 images

Apple Silicon Macs are 64-bit ARM. Most cloud eval infrastructure, and many published task images, are x86-64 (amd64). Docker picks the variant matching your machine when an image offers one, and can run the other under emulation if you ask with --platform: 

mac$ uname -m
arm64
mac$ docker run --rm busybox:1.36 uname -m
aarch64                                # Linux's name for the same architecture
mac$ docker run --rm --platform linux/amd64 busybox:1.36 uname -m
x86_64
mac$ time docker run --rm busybox:1.36 sh -c 'i=0; while [ $i -lt 2000000 ]; do i=$((i+1)); done'
  0.02s user 0.01s system 0% cpu 4.247 total
mac$ time docker run --rm --platform linux/amd64 busybox:1.36 sh -c 'i=0; while [ $i -lt 2000000 ]; do i=$((i+1)); done'
  0.02s user 0.02s system 0% cpu 32.367 total

Same image tag, same loop, about eight times slower under emulation — one run each on this machine, so treat the ratio as an observation, not a constant. Check what you actually have with docker image inspect --format '{{.Os}}/{{.Architecture}}' ubuntu:24.04 (here: linux/arm64).

In eval work — where these differences reach a score

Timeouts. A task tuned to finish inside a 60-second limit on amd64 servers can blow through it when you reproduce the benchmark under emulation on a laptop. The failures you then see (exit 124 or 137 — page 10) are observations about your run, not the model: record them as infrastructure outcomes, keep them out of neither the numerator nor the denominator silently, and don't compare a laptop pass rate with a published one until the platform matches. Glue scripts. A grader or setup script developed at the Mac prompt and first executed inside the image at eval time fails on sed -i '', date -j, or stat -f — for every sample, identically, which at least makes it easy to spot: a failure rate of exactly 100% on one task is a property of the environment until proven otherwise. Reading transcripts. An agent's grep -P or date -d failing on your Mac when you replay it tells you nothing about what happened in the sandbox. Replay in the task image.
