Reference

Annotated bibliography

The course's complete citation universe. Every default, number, guarantee and incident in the pages traces to one of these sources, each fetched and checked rather than recalled. Entries show the inline tag the pages use (e.g. [signal(7)]) so you can map a citation to its source; annotations say what each source uniquely teaches and, where verification caught the record diverging from the folklore, what to watch for.

How these were verified

The course holds two kinds of statement to two standards. Mechanics — how a command behaves, what a file contains, what an error looks like — were executed in real Docker containers (ubuntu:24.04, debian:bookworm-slim, alpine:3.20 on an aarch64, cgroup v2 Docker Desktop host), and the commands with their real output are recorded in research/verify/. Facts about the world — defaults, guarantees, numbers, history, incidents — were verified against fetched primary sources (man pages, kernel and Docker docs, RFCs, papers, system cards) in September 2026; each claim was confirmed, corrected, or marked unverifiable, and the structured notes with exact quotes and locations live in research/sources/. Corrections worth knowing are flagged ⚠ below. Where a note says a fact was established by execution rather than by the document, the annotation says so.

Shell & files

[Bash Manual] Chet Ramey & Brian Fox, GNU Bash Reference Manual (Edition 5.3), Free Software Foundation, 2025. gnu.org/software/bash/manual
Authoritative for every shell mechanic the course asserts: expansion order, startup files, errexit, pipefail. ⚠ set -e does not stop on "any error" — its exception list covers functions called from if/&&/|| contexts and command substitutions; pipefail returns the last (rightmost) non-zero status, not the first; a harness's bash -c reads only $BASH_ENV, not .bashrc. The manual's examples of builtins that must be builtins are cd, break, continue, exec (not export/source). The reference system runs bash 5.2.21.

[POSIX] The Open Group / IEEE, Base Specifications Issue 8 (IEEE Std 1003.1-2024), Shell Command Language and Base Definitions, 2024. pubs.opengroup.org/…/V3_chap02.html
The portable shell language, and the normative home of the one-permission-class rule and the uppercase environment-variable convention. ⚠ "pipefail is a bashism" is out of date: set -o pipefail entered POSIX.1-2024 (Defect 789) with bash's semantics — but dash on Ubuntu 24.04 / Debian 12 still rejects it (executed), so #!/bin/bash remains the practical advice. POSIX only guarantees ">128" for signal deaths; 128+N is shell behaviour.

[Coreutils] Free Software Foundation, GNU Coreutils manual (for 9.12). gnu.org/software/coreutils/manual
The timeout exit-status table (124 timed out, 125 timeout failed, 126/127, 137 for KILL) is the most reusable fact for harness authors; the sort-is-locale-dependent footnote justifies LC_ALL=C in graders. ⚠ BusyBox timeout on Alpine returned 143, not 124 (executed); the online manual tracks 9.12 while Ubuntu 24.04 ships 9.4, which lacks the short options -p/-f.

[jq Manual] jq contributors, jq 1.8 Manual, jqlang.org, 2025. jqlang.org/manual
The reference for filtering JSON and JSONL transcripts. ⚠ The manual never says "JSONL" — only "whitespace-separated JSON values"; jq length file.jsonl counts keys per object, not records; exit status 5 on a malformed line (after earlier output) is observed behaviour, not documented in the -e paragraph.

[ShellCheck] Vidar Holen and contributors, ShellCheck README, manual and wiki (SC2086, SC2164, SC2046, SC2155). shellcheck.net/wiki
Each code maps onto a bash-manual fact (word splitting, set -e's blind spots, masked exit status). ⚠ SC2086 is only "info" severity, and SC2164 switches itself off when a script contains set -e even though the wiki admits set -e "won't necessarily prevent the issue".

[FHS] LSB Workgroup, The Linux Foundation, Filesystem Hierarchy Standard 3.0, 2015. refspecs.linuxfoundation.org/FHS_3.0
The intent behind the directory tree, last revised 2015 — before the /usr merge. ⚠ FHS does not say /tmp is wiped on reboot (clearing is only recommended; programs must not assume persistence), whereas /var/tmp "must not be deleted" at boot.

[hier(7)] Linux man-pages project, hier(7); systemd file-hierarchy(7); UAPI Group, UAPI.9 Linux File System Hierarchy, man-pages 6.19, 2026. man7.org/…/hier.7.html
The Linux-specific tree including /run, /proc and /sys; UAPI.9 adds operational properties (tmpfs /tmp and /run, read-only /usr and /sys in containers). ⚠ hier(7) says nothing about the /usr merge, and file-hierarchy(7) is now a stub pointing to UAPI.9. Executed: Ubuntu 24.04 and Debian 12 are merged (/bin -> usr/bin); Alpine 3.20 is not.

[inode(7)] Linux man-pages project, inode(7), symlink(7), path_resolution(7), unlink(2), link(2), man-pages 6.19. man7.org/…/inode.7.html
What an inode holds, and — via unlink(2) — the exact two-condition rule behind "rm didn't free the space" (diagnose with the (deleted) marker in /proc/PID/fd). ⚠ inode(7) never says the name is not in the inode; that half comes from symlink(7). Also cited as [symlink(7)], [unlink(2)].

Identity & permissions

[chmod(2)] Linux man-pages project, chmod(2), umask(2), chown(2), execve(2), path_resolution(7); GNU coreutils chmod(1), man-pages 6.19. man7.org/…/chmod.2.html
The octal table, the one-class permission rule (path_resolution(7)), the worked 0666 & ~022 = 0644 umask example, and setuid semantics. ⚠ umask is AND-NOT, not subtraction, and only removes bits the program requested; the sticky bit restricts rename/delete, not modification; execve ignores setuid under no_new_privs, on nosuid mounts, and when being ptraced. Also cited as [execve(2)].

[credentials(7)] Linux man-pages project, credentials(7), passwd(5), group(5); shadow-utils shadow(5), man-pages 6.19. man7.org/…/credentials.7.html
Real, effective, saved and filesystem IDs of a process. ⚠ The "UID 0 is superuser" sentence lives in capabilities(7) and passwd(5), not here; /etc/shadow being 640 root:shadow is distro packaging (observed), not man-page text; ubuntu:24.04 already contains user ubuntu at UID 1000.

[sudo(8)] Todd C. Miller, sudo(8) and sudoers(5), sudo.ws. sudo.ws/docs/man/sudo.man
sudo is a setuid-root binary, so nosuid mounts and no_new_privs switch it off — the manual itself names containers as the usual cause. env_reset and secure_path explain why a tool "works without sudo but not with it"; use sudo -n in anything non-interactive. Minimal images have no sudo at all, so "sudo: command not found" in a transcript is an environment fact.

Processes, signals, resources, logs

[fork(2)] Linux man-pages project, fork(2), execve(2), wait(2), exit(3), environ(7), man-pages 6.19. man7.org/…/fork.2.html
The whole process life cycle in citable sentences, including fork's EAGAIN naming cgroup pids.max. ⚠ Zombies are not "no memory": they hold a process-table slot and PID, and the stated risk is table exhaustion; the uppercase-names convention is POSIX, not environ(7); 0–255 comes from status & 0xFF, and 128+N is bash's encoding of a separate wait status. Also cited as [wait(2)], [exit(3)], [environ(7)], [execve(2)].

[signal(7)] Linux man-pages project, signal(7), kill(2); util-linux kill(1), man-pages 6.19, 2026. man7.org/…/signal.7.html
The authority on which signals exist, their numbers and default actions; SIGKILL and SIGSTOP cannot be caught, blocked, or ignored. ⚠ Numbers are architecture-specific (qualify "on x86/ARM"); there are five default actions including Cont; the permission rule compares the sender's real/effective UID with the target's real or saved UID, with CAP_KILL evaluated in the target's user namespace; ignored dispositions survive execve. Also cited as [kill(1)], [kill(2)].

[pid_namespaces(7)] Linux man-pages project, pid_namespaces(7); Docker run/stop reference; tini README, 2026. man7.org/…/pid_namespaces.7.html
Why a container takes 10 s to stop: PID 1 receives no signal it has not installed a handler for, so SIGTERM is dropped and only SIGKILL/SIGSTOP are forced from the parent namespace — hence docker stop = 10 s wait then 137. --init is tini (as docker-init) and fixes both signalling and reaping. ⚠ 137 therefore does not by itself mean OOM.

[proc(5)] Linux man-pages project, proc(5) and sub-pages; ptrace(2) access-mode checking; kernel "The /proc Filesystem", man-pages 6.19. man7.org/…/proc.5.html
The secrets story: argv is public (cmdline 0444), the environment is an exec-time snapshot readable after a ptrace READ check. ⚠ "Same user or root" is imprecise — the target's real, effective and saved UIDs must all match, or you need CAP_SYS_PTRACE, which Docker drops, so root in a default container cannot read another user's environ (executed); /proc/meminfo and loadavg describe the host, not the container's cgroup. Also cited as [proc_pid_environ(5)], [proc_pid_cmdline(5)], [proc_pid_status(5)], [proc_loadavg(5)], [ptrace(2)], [Kernel: procfs].

[ps(1)] procps-ng project, ps(1), top(1), free(1), uptime(1), pgrep(1)/pkill(1). man7.org/…/ps.1.html
ps %CPU is a lifetime average; pkill matches only 15 characters of the name unless -f. ⚠ "buff/cache is reclaimable" overstates — the available column exists because only part of it is, and procps-ng 4 computes used = total − available; ps is often absent (slim images) or BusyBox (Alpine). Also cited as [top(1)], [free(1)], [uptime(1)], [pgrep(1)].

[getrlimit(2)] Linux man-pages project, getrlimit(2)/setrlimit(2)/prlimit(2); bash ulimit builtin, man-pages 6.19. man7.org/…/getrlimit.2.html
Soft/hard mechanics and per-limit behaviour; rlimits are per-process copies, cgroup limits a shared budget. ⚠ ulimit -t N sets soft and hard together, so the process is SIGKILLed (137); RLIMIT_NPROC is per real UID system-wide and ignored for root — not a fork-bomb defence (use pids.max); there is no usable RSS rlimit.

[Kernel: cgroup-v2] Tejun Heo et al., "Control Group v2" (kernel admin guide); Docker "Resource constraints"; proc_pid_oom_score(5), 2026. docs.kernel.org/admin-guide/cgroup-v2.html
memory.max, memory.events, memory.peak, cpu.max and cgroup.kill — the evidence chain for resource failures. ⚠ Exit 137 ≠ OOM. 137 means "died of SIGKILL" from any source (docker stop timeout, RLIMIT_CPU, a human); State.OOMKilled=true means some process in the container was OOM-killed — and the container can exit 0 if the victim was a child (executed). CPU limits only throttle; Docker's --memory-swap is memory+swap while cgroup v2's memory.swap.max is swap-only. Also cited as [Docker: resource constraints], [dmesg(1)], [Kernel: sysctl].

[systemd] systemd project, systemd(1), systemctl(1), journalctl(1), systemd.unit(5), systemd.service(5), systemd.kill(5), journald.conf(5), freedesktop.org, 2026. freedesktop.org/…/systemd.html
Units, journalctl flags, and the 90 s DefaultTimeoutStopSec; systemd kills the whole cgroup on stop. ⚠ Version trap: "latest" is systemd 261 but Ubuntu 24.04 ships 255, where journald Storage= defaults to auto (persistent only if /var/log/journal exists), not persistent.

[strace(1)] strace project, strace(1); man-pages syscalls(2), ptrace(2); Docker seccomp docs and moby profile, 2026. man7.org/…/strace.1.html
Reading real syscall names (openat, clone3, execve) in agent transcripts. ⚠ "Add SYS_PTRACE or seccomp=unconfined to run strace" is pre-4.8-kernel folklore — Docker's profile allows it on kernel ≥ 4.8; only attaching to another UID's processes still needs CAP_SYS_PTRACE.

Mounts & packages

[mount(8)] util-linux project, mount(8), findmnt(8); man-pages tmpfs(5), proc_pid_mountinfo(5), chroot(2), pivot_root(2), 2026. man7.org/…/mount.8.html
Bind mounts, read-only remounts, tmpfs, and the mount table as audit evidence. ⚠ A read-only bind mount makes only the new mountpoint read-only ("the olddir will be writable") and submounts are not covered without ro=recursive; tmpfs's 50%-of-RAM default is capped in practice by the memory cgroup; chroot(2) is "not intended to be used for any kind of security purpose"; noexec only stops direct execution. Also cited as [findmnt(8)], [tmpfs(5)], [proc_pid_mountinfo(5)], [chroot(2)], [pivot_root(2)], [runc].

[apt-get(8)] Debian APT/dpkg/debconf developers, apt-get(8), apt(8), dpkg(1), debconf(7), sources.list(5); snapshot.debian.org; Ubuntu Snapshot Service, 2023–2026. manpages.debian.org/…/apt-get.8
Why scripts call apt-get (apt(8) "may change behavior between versions"), and snapshot archives for reproducible rebuilds. ⚠ No source states "repos carry only the current version" — it is shown by execution (Version '…' was not found, exit 100), and pinning one package fails on version-locked dependencies. Ubuntu snapshots start 1 March 2023, are on by default in 24.04 via --snapshot, and promise only ~2 years retention; -y does not suppress debconf prompts. Also cited as [apt(8)], [debconf(7)], [Debian snapshots], [Ubuntu snapshots].

[pip] pip developers, "Repeatable Installs" and "Secure installs"; PEP 668; Python venv docs, 2021–2026. pip.pypa.io/…/repeatable-installs
Hash-checking is all-or-nothing and needs every transitive dependency pinned; pip by default runs arbitrary code from distributions; venvs are non-portable because of absolute shebangs. ⚠ The helpful "externally-managed-environment" text comes from the distro's marker file, not pip; Ubuntu 24.04 ships pip 24.0 while the docs describe 26.2.1. Also cited as [PEP 668], [Python: venv].

[Alpine] Alpine Linux team, "About Alpine Linux" and wiki; musl "Functional differences from glibc"; BusyBox; PEP 656, 2021–2026. alpinelinux.org/about
"Built around musl libc and busybox"; manylinux wheels cannot be used on musl, hence PEP 656's musllinux tag. ⚠ The musl page never says glibc binaries won't run — that was shown by execution, with the confusing symptom not found + exit 127 for a file that exists; BusyBox's problem for agents is missing options, not different semantics. Also cited as [PEP 656].

Networking

[ip(8)] iproute2 ip(8), ip-address(8), ip-route(8), ip-link(8), ss(8); man-pages veth(4), ip(7), proc_sys_net_ipv4(5), 2026. man7.org/…/ip.8.html
Reading the box's interfaces, routes and sockets. ⚠ "Ports below 1024 need root" is false inside Docker containers: Docker sets ip_unprivileged_port_start=0, and a capability-less uid 65534 bound port 80 (executed); ip(7) no longer documents the sysctls; net-tools is "legacy", not unmaintained; stock ubuntu:24.04 has neither ip nor ss. Also cited as [ip-route(8)], [veth(4)], [net-tools].

[tcp(7)] man-pages tcp(7), udp(7), connect(2); RFC 9293; RFC 768; RFC 6335; kernel IP sysctl docs. man7.org/…/tcp.7.html
What "refused" and "timed out" actually mean. ⚠ A firewall REJECT gives the same client symptom as no listener; "no route" fails instantly (ENETUNREACH), and only silent drops time out — after about two minutes of SYN retries by default; Linux ephemeral ports are 32768–60999, not IANA's range.

[resolv.conf(5)] man-pages resolv.conf(5), hosts(5), nsswitch.conf(5), getent(1); BIND dig(1); systemd-resolved; Docker DNS docs; RFC 1035, 2026. man7.org/…/resolv.conf.5.html
Executed resolv.conf files for Docker's three network cases, including the 127.0.0.11 embedded resolver and ndots:0 on user-defined networks. ⚠ getent hosts can bypass an IPv4-only /etc/hosts override via IPv6-first lookup (use getent ahosts); DNS leaving the sandbox depends on the setup — --internal and default-drop output rules blocked it in execution.

[curl(1)] Daniel Stenberg and the curl project, curl(1), libcurl error codes, Everything curl, 2026. curl.se/docs/manpage.html
Exit codes as a symptom map: 6 resolve, 7 connect, 28 timeout, 35 TLS handshake, 60 untrusted certificate. ⚠ A missing CA bundle (fresh ubuntu:24.04) gives exit 77, not 60; 7 and 28 each have two causes, and a configured proxy shifts 5/7 to mean the proxy. Always teach -sS: -s alone prints nothing on failure.

[RFC 8446] E. Rescorla, RFC 8446 (TLS 1.3); RFC 9110 (HTTP Semantics); RFC 6066; RFC 8744; Debian update-ca-certificates(8). rfc-editor.org/rfc/rfc8446
The protocol references plus how Debian/Ubuntu build /etc/ssl/certs/ca-certificates.crt (local certs must end .crt). ⚠ The base image has no /etc/ssl/certs; HTTPS fails only when recommends are skipped, and with exit 77, not a verify error; RFC 8744, not RFC 6066, is the citable statement that SNI is cleartext.

[RFC 1918] Y. Rekhter et al., "Address Allocation for Private Internets", RFC 1918 / BCP 5, IETF, 1996. rfc-editor.org/rfc/rfc1918
The exact private ranges — note 172.16/12 stops at 172.31.255.255, and Docker's 172.17.0.0/16 sits inside it. ⚠ RFC 5735 is obsolete (cite RFC 6890); RFC 4632 never states the "2n − 2 usable hosts" folklore. Also cited as [RFC 6890], [RFC 4632].

[tcpdump(1)] Tcpdump Group tcpdump(1), pcap-filter(7); iputils ping(8); traceroute(8); icmp(7), 2026. tcpdump.org/manpages/tcpdump.1.html
Packet capture and ICMP probes. ⚠ "ping needs CAP_NET_RAW" is false in Docker, which widens ping_group_range; conversely --cap-drop NET_RAW makes Ubuntu's ping (file capability cap_net_raw=ep) un-executable, exit 126 (executed). "ICMP blocked ≠ host down" rests on traceroute(8)'s firewall sentence, not ping(8).

[nftables] Netfilter project, nftables wiki; iptables(8); Docker "Packet filtering and firewalls", bridge/none drivers, docker network create, 2026. wiki.nftables.org
Egress enforcement and Docker's firewall integration. ⚠ DOCKER-USER exists only with the iptables backend; --internal does not block the host gateway address; the docs say --network none has no IPv6 loopback but Docker 28.1.1 showed ::1; inter-container communication on the default bridge is on by default. Host-side behaviour is docs-backed only. Also cited as [Docker: bridge], [Docker: none], [Docker: network create], [Docker: networking].

[AWS: IMDS] Amazon Web Services, EC2 User Guide: instance metadata and IMDS options, 2026. docs.aws.amazon.com/…/ec2-instance-metadata.html
The metadata endpoint at 169.254.169.254 (shared with GCP) that a sandbox must not reach. ⚠ IMDSv2's hop limit of 1 protects nothing unless IMDSv2 is required: by default "you can use either IMDSv1 or IMDSv2", and v1 is one unauthenticated GET; AMIs registered with ImdsSupport v2.0 default to hop limit 2.

Containers: kernel features

[namespaces(7)] Linux man-pages project, namespaces(7) and the pid/network/mount/user/uts/ipc/cgroup/time namespace pages; util-linux unshare(1), nsenter(1), lsns(8), 2026. man7.org/…/namespaces.7.html
"One use of namespaces is to implement containers." ⚠ A new network namespace is not documented as "only a down loopback" — executed: lo down, no routes, plus fallback tunnel devices on some kernels; time namespaces cannot fake the wall clock; Docker creates no user or time namespace by default, so root in a default container is host UID 0. "There is no container object in the kernel" is framing, not a quotable fact. Also cited as [user_namespaces(7)], [network_namespaces(7)], [mount_namespaces(7)], [time_namespaces(7)], [nsenter(1)], [Kernel: sysctl/net], [Docker: what-is-a-container].

[cgroups(7)] Linux man-pages project, cgroups(7), man-pages 6.19. man7.org/…/cgroups.7.html
Control groups as the resource half of a container. ⚠ cgroup limits are invisible to /proc: a container limited to 1.5 CPUs and 256 MiB still reported 10 CPUs and ~8 GB (executed) — the truth is in /sys/fs/cgroup; the man page's /sys/fs/cgroup/unified describes the old hybrid layout.

[capabilities(7)] Linux man-pages project, capabilities(7), man-pages 6.19. man7.org/…/capabilities.7.html
How root's power is split, and why CAP_SYS_ADMIN is (hedged) "the new root". Docker's default set is exactly 14, triple-checked (docs table, moby source, live CapEff a80425fb). ⚠ --user 1000 empties CapEff but leaves CapBnd intact, whereas --cap-drop ALL empties both; /proc status fields belong to proc_pid_status(5).

[seccomp(2)] man-pages seccomp(2); kernel "Seccomp BPF" and "No New Privileges Flag"; Docker "Seccomp security profiles", 2026. man7.org/…/seccomp.2.html
Syscall filtering and no_new_privs; the kernel doc's line "System call filtering isn't a sandbox." ⚠ Docker's "around 44 out of 300+" blocked syscalls is Docker's wording, not a countable fact; Docker Desktop on the authoring Mac runs seccomp unconfined by default — use --security-opt seccomp=builtin and check docker info. Also cited as [Docker: seccomp], [Kernel: seccomp], [Kernel: no_new_privs].

[Docker: AppArmor] Docker Inc., "AppArmor security profiles for Docker", 2026. docs.docker.com/engine/security/apparmor
A third, path-based layer over capabilities and seccomp (deny mount, /proc and /sys write denials). ⚠ Only present where the host kernel enables it (not in Docker Desktop's VM); the template moved to moby/profiles, and Engine 29.8 allows a custom docker-default template.

[OCI Runtime Spec] Open Container Initiative, Runtime Specification and Image Format Specification; runc and containerd READMEs, 2026. github.com/opencontainers/runtime-spec
config.json is literally the list of kernel features that together make "a container"; eight namespace types, and an unlisted type means sharing the runtime's (the precise meaning of --network host). ⚠ Capabilities, noNewPrivileges and LSM labels live in config.md's process section, not config-linux.md.

Docker

[Docker: run] Docker Inc., docker container run reference; "Running containers"; exec; stop, 2026. docs.docker.com/…/container/run
Exit codes 125/126/127, the 14 default capabilities, the seven-point --privileged list, and "the default user within a container is root (uid = 0)". ⚠ The exec page never mentions namespaces or the default user (verified by running); --ulimit nproc is per-user, not per-container (use --pids-limit); the docs still cite a cgroup-v1 memory path.

[Docker: security] Docker Inc., "Docker Engine security"; Rootless mode; userns-remap; "Protect the Docker daemon socket", 2026. docs.docker.com/engine/security
The daemon-is-root argument in Docker's own words: "only trusted users should be allowed to control your Docker daemon"; "The docker group grants root-level privileges to the user". ⚠ Rootless's known-limitations list moved to the Troubleshooting page; user-namespace remapping is "available but not enabled by default"; some prose on the page is dated.

[Docker: storage] Docker Inc., Storage; Volumes; Bind mounts; tmpfs mounts, 2026. docs.docker.com/engine/storage
"Bind mounts have write access to files on the host by default." ⚠ tmpfs can be swapped and counts against --memory; named volumes survive --rm (a cross-run state leak); -v silently creates a missing host path as root-owned; --tmpfs mounts appear under HostConfig.Tmpfs, not .Mounts.

[Kernel: overlayfs] Neil Brown et al., "Overlay Filesystem" (kernel docs); Docker storage-driver and containerd image store docs, 2026. docs.kernel.org/filesystems/overlayfs.html
lowerdir/upperdir/workdir and copy-up — triggered even by metadata changes and O_RDWR opens. ⚠ "Docker uses overlay2" is now folklore for new installs: the containerd image store (overlayfs snapshotter) is the default for fresh Docker Engine 29.0+ installs; upgraded hosts keep overlay2, and docker info reports overlayfs. The mechanism is identical either way.

[Docker: Dockerfile] Docker Inc., Dockerfile reference; build best practices; build secrets; multi-stage builds; build cache, 2026. docs.docker.com/reference/dockerfile
Cache rules, the apt-get update && install rationale, and "tags are mutable". A file deleted in a later layer "will still be available in the previous layer" — the solution-leakage lesson. ⚠ "Only RUN, COPY, ADD create layers" is gone from the docs; the USER section does not say the default is root; Docker's apt advice optimises freshness, the opposite of benchmark reproducibility.

[Compose] Docker Inc., Compose file reference: services, networks, networking, 2026. docs.docker.com/reference/compose-file/services
A 1:1 key for every hardening flag (read_only, cap_drop, pids_limit, network_mode: none, networks.internal). ⚠ command is not shell-interpreted; short-syntax depends_on gives order, not readiness; user unset means root; unquoted yes/no are YAML booleans. Doc-backed only — nothing here was run.

[Docker: logs] Docker Inc., container logs, logging drivers, JSON File driver, docker inspect, 2026. docs.docker.com/engine/logging
The json-file driver does not rotate by default — a chatty agent can fill the host disk; the default blocking mode can stall the application's writes. ⚠ The inspect reference lists no schema, so field names (State.OOMKilled, HostConfig.ReadonlyRootfs, Mounts[].RW) come from executed output.

Isolation technologies

[gVisor] The gVisor Authors, gVisor documentation (What is gVisor?, Security Model, Performance Guide, Platform Guide), gvisor.dev, 2026. gvisor.dev/docs
An application kernel in Go that intercepts syscalls; unusually candid about what a sandbox does not do — "A sandbox is not a substitute for a secure architecture." ⚠ Not "slow at I/O": raw disk I/O is near native; the costs are per-syscall, VFS-heavy file operations and networking; "gVisor uses ptrace" is obsolete (systrap is default).

[Firecracker] A. Agache, M. Brooker, et al., "Firecracker: Lightweight Virtualization for Serverless Applications", NSDI '20; plus project docs. usenix.org/conference/nsdi20/presentation/agache
The citable shared-kernel argument (§2.1) and the microVM design. ⚠ The headline numbers are conditional: ≤125 ms is InstanceStart to guest /sbin/init for a minimal kernel, 1 vCPU/128 MiB; <5 MiB is VMM overhead on top of guest RAM (the paper measured ~3 MB); 150/s is per host. The device model is now five (with virtio-vsock); "no PCI" is the 2020 paper only; seccomp is installed by Firecracker itself, not the jailer. Snapshots write full guest memory — any secret in RAM being in the file is inference.

[Kata] Kata Containers community, Architecture docs; Cloud Hypervisor README, 2026. github.com/kata-containers/…/architecture
A container inside a lightweight VM: the guest kernel still builds namespaces and cgroups, the VM is a second layer of defence. ⚠ The hypervisor list is five (QEMU, Cloud Hypervisor, Firecracker, Dragonball, StratoVirt), not three.

[Kernel: KVM] Linux kernel docs, "The Definitive KVM API Documentation", "Running nested guests with KVM"; linux-kvm.org, 2026. docs.kernel.org/virt/kvm/api.html
Hardware virtualization behind Firecracker and Kata; ls -l /dev/kvm tells you whether a box can host such guests. ⚠ The ARM half of "KVM uses VT-x/AMD-V/ARM extensions" is unverifiable from these pages; avoid "type-1 hypervisor" and blanket claims about which clouds allow nesting.

[AISI: Sandboxing] UK AI Security Institute, "The Inspect Sandboxing Toolkit" (blog, 7 Aug 2025) and "Technical guidance: sandboxing configurations for agentic evaluations" (PDF). aisi.gov.uk/blog/…, Technical Guidance.pdf
Three axes — tooling, host isolation, network — combined as a Tx.Hx.Nx "sandbox profile". ⚠ The level definitions live in the Technical Guidance PDF, not the blog; they are zero-based (T0–T2, H0–H3, N0–N2, higher = more restrictive) though the prose says "1-3"; AISI never makes the shared-kernel argument itself (cite Firecracker or gVisor); its own hostile-agent example sits at H2 (Kubernetes), not a VM; Windows is a plugin capability, not a stated motivation. Not official government guidance.

Eval harnesses & benchmarks

[Inspect] UK AI Security Institute, Inspect AI documentation (Sandboxing, Tools, Limits, Scorers, Agent Bridge) and source, inspect.aisi.org.uk, 2026. inspect.aisi.org.uk/sandboxing.html
The harness–sandbox interface: exec() returning success/returncode/stdout/stderr, read_file/write_file. ⚠ exec output over 10 MiB is silently front-truncated, not an exception; the default sandbox is aisiuk/inspect-tool-support with network_mode: none, init: true and no CPU/memory limits; supplying your own compose file replaces that config, losing network_mode: none — and Compose's default network has outbound access.

[Terminal-Bench] Mike A. Merrill, Alexander G. Shaw, Nicholas Carlini, et al., "Terminal-Bench: Benchmarking Agents on Hard, Realistic Tasks in Command Line Interfaces", arXiv:2601.11868, January 2026. arxiv.org/abs/2601.11868
The number tying Linux fluency to agent failure: 24.1% of sampled failed commands were an executable not installed or not on PATH; per-command error rates 9.2%–26.7%; a failure taxonomy that reads like this course's contents. ⚠ Tests are uploaded after the run but by default execute in the same container the agent had; the "<65%" headline is Terminal-Bench 2.0 in January 2026 — history, not the present state.

[SWE-bench] Carlos E. Jimenez, John Yang, et al., "Containerized Evaluation Harness" report (27 June 2024) and SWE-bench docs. swebench.com/SWE-bench/guides/docker_setup
The primary-source case that conda environments were "underspecified" and per-task Docker images the fix — with gold patches resolving 99.78% (2289/2294), so even the fixed harness is imperfect. The current harness separates unresolved from likely infrastructure failures. ⚠ The report's original path is dead on main (cite the v3.0.0 tag); max_workers guidance changed from 28 to 24.

[HumanEval] Mark Chen, Jerry Tworek, et al. (OpenAI), "Evaluating Large Language Models Trained on Code", arXiv:2107.03374, 2021. arxiv.org/abs/2107.03374
The earliest widely cited statement that an eval harness needs a real sandbox (gVisor plus eBPF firewall rules), with a four-part threat list — modifying, gaining persistence, accessing sensitive resources, exfiltrating. ⚠ Say "blocked connections except those required for experiment control", not "no network".

[OSWorld] Tianbao Xie et al., "OSWorld: Benchmarking Multimodal Agents for Open-Ended Tasks in Real Computer Environments", NeurIPS 2024 D&B (arXiv:2404.07972). arxiv.org/abs/2404.07972
The VM end of the spectrum: real OSes with GUIs, snapshot reset, grading from state pulled out to the host. ⚠ The paper never argues "VMs rather than containers" — its reasons are real-OS support, host safety and snapshot reset; its Docker provider runs the VM inside a container and needs KVM. The 72.36% human vs 12.24% model figures are from 2024.

[Anthropic: Agent Evals] Anthropic, "Demystifying evals for AI agents", anthropic.com/engineering, 9 January 2026. anthropic.com/engineering/demystifying-evals-for-ai-agents
A clean environment per trial (leftover files, cached data, resource exhaustion, correlated failures) and outcome defined as the final state of the environment. ⚠ Its git-history anecdote is cross-trial leakage from a reused workspace — distinct from SWE-bench #465's future history shipped in the image; the post gives no infrastructure-noise numbers.

[Anthropic: Infra Noise] Gian Segato (Anthropic), "Quantifying infrastructure noise in agentic coding evals", anthropic.com/engineering, 5 February 2026. anthropic.com/engineering/infrastructure-noise
Resource configuration alone moves scores: on Terminal-Bench 2.0, infra errors fell from 5.8% to 0.5% and success rose 6 points from strict limits to uncapped; +1.54 on SWE-bench; "leaderboard differences below 3 percentage points deserve skepticism". ⚠ The post never says cgroup, requests or limits — mapping its "guaranteed allocation" and "hard limit" to those is the course's job.

Environment integrity & reward hacking

[o1 System Card] OpenAI, "OpenAI o1 System Card", §4.2.1 Observation of Reward Hacking on Cybersecurity Task, version dated 12 September 2024. cdn.openai.com/o1-system-card.pdf
o1-preview (pre-mitigation), facing a broken CTF container, found a network-reachable Docker API and used it to start a new instance of the challenge container with a command that printed the flag, then read it from the container logs. ⚠ The section exists only in the September 2024 card (the December card and arXiv version dropped it). OpenAI does not say a VM boundary contained it: it says its infrastructure "does not rely on the Docker container-to-host isolation or the virtual machine boundary for security" and remained secure, without saying what it does rely on. The card never says "escape"; port number and flags are not stated.

[SWE-bench #465] Jacob Kahn et al., "Repo State Loopholes During Agentic Evaluation", SWE-bench GitHub issue #465, opened 3 Sep 2025, closed 24 Mar 2026. github.com/SWE-bench/SWE-bench/issues/465
The flagship "the box leaked the answer" incident: future commits were in the image's .git. The fix — reset, drop origin, delete future tags, expire the reflog, gc --prune=now, then assert git log --all --since=<base> is empty — is a build verifying its own integrity. ⚠ The maintainers' estimate of scale was small (5 of ~10,000 trajectories; ~1.2 points; no top-4 rank changes); do not present it as invalidating the leaderboard.

[Pro Git] Scott Chacon & Ben Straub, Pro Git (2nd ed.) ch. 10, plus git reference manual (git-gc, git-reflog, git-fsck), git-scm.com. git-scm.com/book/…/Maintenance-and-Data-Recovery
Why deleted history is still recoverable: hidden from --all, still in the reflog, still readable by hash until gc prunes it (each step executed). ⚠ Use the manual for numbers: unreachable objects pruned after 2 weeks, reflog 90 days (30 if unreachable), auto-gc at 6700 loose objects; --depth 1 alone does not fix future leakage.

[METR] Sydney Von Arx, Lawrence Chan, Beth Barnes, "Recent Frontier Models Are Reward Hacking", METR blog, 5 June 2025. metr.org/blog/2025-06-05-recent-reward-hacking
o3 reward-hacked 30.4% of RE-Bench runs, where the scorer was visible and importable, vs 0.7% on HCAST; "please do not cheat" had essentially no effect. ⚠ All numbers are for one pre-deployment o3 checkpoint; the link to permissions and separate grading processes is the course's inference, not METR's remedy.

[ImpossibleBench] Ziqian Zhong, Aditi Raghunathan, Nicholas Carlini, "ImpossibleBench: Measuring LLMs' Propensity of Exploiting Test Cases", arXiv:2510.20270, October 2025. arxiv.org/abs/2510.20270
The one controlled experiment varying test-file access (open / read-only / hidden): read-only is decisive for models that cheat by editing tests (Opus 4.1: 50% → 1%) and weak for others (GPT-5: 54% → 39%); hiding tests costs legitimate performance. ⚠ The paper's "read-only" is a harness-side revert of modified tests at scoring time, not chmod or a :ro mount — a Linux implementation is the course's, not the paper's.

[Hacker-Fixer] Ziqian Zhong, Ivgeni Segal, et al., "Hardening Agent Benchmarks with Adversarial Hacker-Fixer Loops", arXiv:2606.08960 (preprint), June 2026. arxiv.org/abs/2606.08960
A catalogue of pure-Linux exploits (fake .deb packages, a shell-script /usr/bin/xrandr, reading unguarded answer files) and the blunt observation that tests share the agent's container and permissions by default; 16% of 1,968 terminal tasks hackable from the description alone. ⚠ It hardens verifiers and runs no sandbox-policy experiment. The separate [RewardHackBench] repo (islo-labs/reward-hack-bench) is a vendor benchmark — 8 tasks × 7 network-egress policies × 3 trials, one model, LLM-judged; its robust lesson is that network: none stops retrieval cheating but also cuts the agent off from its model.
