Linux for Evals Engineers

When you evaluate an AI agent, the thing being tested is a model typing commands into a Linux box, and the thing doing the testing is more Linux: containers, mounts, users, timeouts, firewalls, scripts that check the wreckage afterwards. This course teaches Linux from zero, with one question deciding what gets taught: does an evals engineer need this to build, debug, audit, or harden an evaluation environment?

The premise of this course

In an agentic eval, the environment is part of the measuring instrument. If the sandbox runs out of memory, the score drops and the model gets the blame. If the answer key is readable, the score rises and the model gets the credit. If the box can reach the internet, you may be measuring the agent's ability to download the fix. Every one of those is a plain Linux fact — a limit, a permission bit, a route — and you cannot vouch for a number produced by a machine you cannot read.

The target: the ten-minute audit

The course aims at one concrete, testable competence. Dropped into an unfamiliar Linux box as root, within ten minutes you can answer five questions — and say why each answer matters for whether a score from this box can be trusted:

#QuestionWhy an eval depends on itTaught in
1What is running?Leftover processes are shared state between rollouts; a grader in the agent's process tree is attackable.Modules 3, 5
2What is mounted, and is it read-only?Writable tests get rewritten; a host bind mount is a hole in the sandbox wall.Module 4
3Who owns what?An agent running as root voids every permission-based protection in the box.Module 2
4What can it reach?Open egress turns "solve the task" into "find the solution online".Module 5
5Where are the logs?Separating a model failure from an infrastructure failure needs evidence from outside the transcript.Modules 3, 7

The capstone assembles them into a timed procedure, an audit script, and a write-up template — a portfolio-grade artifact.

What you'll be able to do

The abilities are framed the way a job uses them.

AbilityA useful demonstration
DiscussExplain, in plain language, why "exit code 137" is not evidence that a model failed a task; what a container is made of; why a read-only mount protects tests from tampering but not from being read.
NavigateFrom a shell inside a task environment, establish what is running, mounted, owned, reachable, and logged; read an agent's terminal transcript and separate what was observed from what is supposed; name the next test that would discriminate between causes.
DesignChoose and defend a sandbox policy — user, mounts, limits, capabilities, network, isolation technology, where grading runs — knowing what each choice costs the task and what it does to the score's meaning.

Concretely, you will:

  • Work fluently in a shell: files, pipes, redirection, and the text tools that let you interrogate ten thousand rollout logs from the terminal.
  • Decode how a process ended — exit 127, 137, 143, a timeout, an OOM kill — and account for it honestly: an infrastructure failure is an observation about the run, and it belongs in the report, not silently out of the denominator.
  • Read and set permissions, mounts, and resource limits, and use them to protect a grader and an answer key.
  • Prove from inside a sandbox what it can reach on the network, and understand how default-deny egress is enforced from outside.
  • Explain what a container actually is — namespaces, cgroups, capabilities, seccomp — and lock one down knob by knob.
  • Choose between containers, gVisor, and microVMs from a threat model rather than from habit.
  • Read how real harnesses (Inspect, Terminal-Bench, SWE-bench) drive a Linux sandbox, and find where a benchmark's environment can leak its answers.

How to use this course

Read in order if you are new to Linux; every page ends with a lab, and the labs are the course — Linux is learned with fingers. Set up the lab on page 1 first (it takes ten minutes and everything in it is disposable). Plum boxes labelled In eval work tie each mechanism to evaluation practice; if you already know Linux, reading only those and Modules 6–7 is a legitimate fast path.

The course is deliberately narrow. It teaches about seventy commands, deeply, and how to find the rest. It stops shell scripting at thirty lines and tells you to switch to Python. It skips everything a sysadmin certification would cover that an evals engineer will not touch. Eval concepts themselves — graders, error analysis, error bars, contamination — belong to the sibling course Understanding LLM Evals; networking concepts — the request journey, DNS, TLS, HTTP, deadlines and retries — belong to Networking for LLM Evals. This course links to both wherever they meet, and its own networking module stays on the Linux side: the commands, namespaces, Docker networks, and firewalls that decide what a sandbox can reach.

A note on provenance

Two standards, stated up front. Anything you can run, we ran: every command and every line of terminal output in the course was executed in a real Linux container (Ubuntu 24.04 unless the page says otherwise), not written from memory. Anything about the world, we checked: every default, guarantee, number, and incident was verified against its primary source — the man page, the kernel or Docker documentation, the RFC, the paper — and carries an inline citation like [signal(7)]. Each page ends with a source box. A course about trustworthy measurement should be able to show its own work.

This is the Linux component of professional preparation, not a promise of employment. The skills checklist states the finish line as things you can demonstrate.
