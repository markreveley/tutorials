Module 6 · Containers & Isolation

Cgroups, capabilities, and seccomp

Namespaces decide what a container can see. Three other kernel mechanisms decide how much it may use, which of root's powers it holds, and which requests it may make of the kernel at all. Each is a few lines of text you can read from inside the box — and each changes either what an eval measures or what an agent can get away with.

Three more walls, three more files to read

Page 20 took "container" apart into a restricted view, a restricted budget, a different root filesystem and reduced privilege. This page covers the budget and the privilege. A slogan helps, as long as you know it is this course's framing and not a quotation: namespaces limit what a process can see; cgroups limit what it can use; capabilities and seccomp limit what it can do. Docker's own security page draws the same line — control groups "do not play a role in preventing one container from accessing or affecting the data and processes of another container, [but] they are essential to fend off some denial-of-service attacks."[Docker: security]

The commands below use the lab image from page 1 (lt-lab: Ubuntu 24.04 plus libcap2-bin, iproute2 and the user learner, uid 1001), run from your Mac's terminal with different flags each time — the flags are the experiment.

Cgroups: the budget

Control groups "allow processes to be organized into hierarchical groups whose usage of various types of resources can then be limited and monitored," through "a pseudo-filesystem called cgroupfs."[cgroups(7)] So a cgroup is a directory; the processes in it are listed in a file; its limits are more files. Version 2, which Ubuntu 24.04 and current Docker use, has a single tree in which "every process in the system belongs to one and only one cgroup," and children start in their parent's cgroup[Kernel: cgroup-v2] — so everything an agent spawns stays inside the budget, with no way to opt out by forking. Limits apply down the tree: a child group cannot exceed its ancestors'.[cgroups(7)] The enforcing components are called controllers (memory, cpu, pids, io…). 

$ docker run --rm -it --memory 256m --cpus 1.5 --pids-limit 100 lt-lab bash

And without flags there is no budget: "By default, a container has no resource constraints."[Docker: resource constraints] A plain docker run shows memory.max: max, cpu.max: max 100000, pids.max: max.

What hitting each limit looks like

Page 12 introduced these symptoms; here they are as cgroup counters. CPU first — a busy loop under --cpus 0.5, stopped by timeout after 3 seconds: 

$ docker run --rm --cpus 0.5 lt-lab bash -c 'timeout 3 bash -c "while :; do :; done"; echo "loop exit=$?"; grep -E "nr_periods|nr_throttled|throttled_usec" /sys/fs/cgroup/cpu.stat'
loop exit=124
nr_periods 31
nr_throttled 30
throttled_usec 1498849
$ docker run --rm --pids-limit 10 lt-lab bash -c 'for i in $(seq 1 15); do sleep 2 & done 2>&1 | head -2; cat /sys/fs/cgroup/pids.events'
bash: fork: retry: Resource temporarily unavailable
bash: fork: retry: Resource temporarily unavailable
max 2

Throttled in 30 of 31 periods, for 1.5 of the 3 seconds: the loop did half the work and nobody was told. A CPU-starved agent does not crash; it runs out of wall-clock time. The pids limit is what contains a fork bomb, which "is likely to exhaust the number of tasks before hitting memory restrictions."[Kernel: cgroup-v2] Memory is the one that kills: 

$ docker run --name lt-oom --memory 64m --memory-swap 64m lt-lab bash -c 'tail /dev/zero; echo "child exit=$?"; grep oom_kill /sys/fs/cgroup/memory.events; echo "carrying on"'
bash: line 1:     7 Killed                  tail /dev/zero
child exit=137
oom_kill 1
carrying on
$ docker inspect lt-oom --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}'; docker rm lt-oom
ExitCode=0 OOMKilled=true

(tail /dev/zero buffers an endless line; setting --memory-swap equal to --memory means no swap, so the kill is prompt.) The OOM killer chose a process inside the cgroup — it "is not going to kill any tasks outside of this cgroup"[Kernel: cgroup-v2] — the child died with 137 (128 + 9, SIGKILL), the shell carried on, and the container exited 0.

In eval work — navigate: the OOM that exits 0

This is the common shape in agentic runs: the agent's pytest or compiler is OOM-killed, the agent's shell survives, the agent reads "Killed", flails, and the task is scored as a model failure with a clean container exit code. Exit code 137 alone would not have proved OOM anyway (a docker stop timeout also gives 137). The evidence is oom_kill in memory.events — "The number of processes belonging to this cgroup killed by any kind of OOM killer"[Kernel: cgroup-v2] — plus State.OOMKilled from outside and memory.peak against memory.max. Have the harness record all three, plus nr_throttled, at the end of every rollout. A rollout with oom_kill > 0 is an infrastructure failure until someone shows the task is supposed to fit in the limit: keep it in the scheduled denominator, report it separately from wrong answers, and never quietly drop it.

Pitfall — the limit is invisible where programs look for it

Cgroup limits do not show up in /proc. In a container limited to 256 MB and one CPU, nproc printed 10 and /proc/meminfo reported 8 GB — the machine's totals (page 20). A test suite that starts one worker per CPU, or a tool that sizes a cache from "free memory", overshoots and is killed for it. The truth is in /sys/fs/cgroup.

Capabilities: root, cut into pieces

Page 8's decision procedure had a first line: if the process is root, skip the checks. That is the traditional model — "Privileged processes bypass all kernel permission checks." The modern kernel is finer-grained: "Linux divides the privileges traditionally associated with superuser into distinct units, known as capabilities, which can be independently enabled and disabled."[capabilities(7)] Being uid 0 is how a process normally gets the full set; the checks themselves ask about one capability at a time. The kernel on this machine knows 41. A process's sets are hexadecimal masks in /proc/PID/status;[proc_pid_status(5)] two matter to you. CapEff, the effective set, is "the set of capabilities used by the kernel to perform permission checks." CapBnd, the bounding set, limits what can ever be gained by executing a program.[capabilities(7)] 

$ docker run --rm lt-lab bash -c 'grep -E "^Cap(Eff|Bnd)" /proc/self/status; capsh --decode=00000000a80425fb'
CapEff:	00000000a80425fb
CapBnd:	00000000a80425fb
0x00000000a80425fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap

Fourteen names — exactly the fourteen rows of Docker's table of capabilities "allowed by default."[Docker: run] Docker "drops all capabilities except those needed, an allowlist instead of a denylist approach," so that "'root' within a container has much less privileges than the real 'root'."[Docker: security] That is why root in a default container is refused things root is never refused: 

$ docker run --rm lt-lab bash -c 'id -u; mount -t tmpfs none /mnt; ip link set eth0 down; hostname x'
0
mount: /mnt: permission denied.
       dmesg(1) may have more information after failed mount system call.
RTNETLINK answers: Operation not permitted
hostname: you must be root to change the host name
$ docker run --rm --cap-add NET_ADMIN lt-lab bash -c 'ip link set eth0 down && ip -br link show eth0'
eth0@if639       DOWN           6e:0b:49:5d:ac:dc <BROADCAST,MULTICAST>

"Operation not permitted" is the error EPERM: not "the file's mode says no" (that is EACCES, "Permission denied") but "you lack the privilege for this operation" (mount words its EPERM message its own way). Three refusals, two missing capabilities: mounting and setting the hostname need CAP_SYS_ADMIN, interface configuration needs CAP_NET_ADMIN.[capabilities(7)] It works in the other direction too. Take one capability away from root and page 8's permission bits apply to uid 0: 

$ docker run --rm --cap-drop DAC_OVERRIDE lt-lab bash -c 'id -u; ls -ld /home/learner; ls /home/learner'
0
drwxr-x--- 2 learner learner 4096 Sep 21 11:09 /home/learner
ls: cannot open directory '/home/learner': Permission denied

In eval work — design: one capability can undo a mount option

A task mounts its hidden tests read-only and the author adds --cap-add SYS_ADMIN "because the agent needs to mount things". Run as root with a read-only volume at /tests:

# echo "assert True" > /tests/test_hidden.py
bash: /tests/test_hidden.py: Read-only file system
# mount -o remount,rw /tests; echo "remount exit=$?"
remount exit=0
# echo "assert True" > /tests/test_hidden.py && cat /tests/test_hidden.py
assert True

Without SYS_ADMIN the same remount fails (mount: /tests: permission denied, exit 32). A read-only mount protects the grader only from a process that cannot remount — so audit question 2 ("is it read-only?") is incomplete without reading CapEff. The opposite mistake costs validity instead: a network-debugging task family needs ping and tcpdump, hence NET_RAW; drop ALL and the oracle solution fails with a permission error that gets scored as model failure. Derive the policy per task family, and run the oracle under it.

Seccomp: a filter on the kernel's front door

Every request a program makes of the kernel is a system call (page 9). Seccomp in filter mode attaches a small program to a process that inspects each call's number and raw arguments and decides: allow, or fail with an error. Filters are inherited by children and "preserved across a call to execve,"[seccomp(2)] so there is no shaking one off. The point is a smaller attack surface: since all containers share one kernel, every reachable system call is a place a kernel bug could be. The kernel's own documentation is careful about the claim: "System call filtering isn't a sandbox. It provides a clearly defined mechanism for minimizing the exposed kernel surface."[Kernel: seccomp]

Docker's default profile "is an allowlist that denies access to system calls by default and then allows specific system calls"; in Docker's words it "disables around 44 system calls out of 300+" and is "moderately protective while providing wide application compatibility."[Docker: seccomp] Treat "around 44" as Docker's round figure, not a count to verify. The blocked list includes mount ("already gated by CAP_SYS_ADMIN"), reboot, unshare, clock_settime ("Time/date is not namespaced"), keyctl (the kernel keyring "is not namespaced"), and the io_uring calls, "Blocked due to security vulnerabilities that can be exploited to break out of containers."[Docker: seccomp] A process's state is two more lines in status: Seccomp is 0 (disabled), 1 (strict) or 2 (filter).[proc_pid_status(5)] 

$ docker run --rm --security-opt seccomp=builtin lt-lab grep -E 'Seccomp' /proc/self/status
Seccomp:	2
Seccomp_filters:	1
$ docker run --rm lt-lab unshare --user --map-root-user id                                  # no filter
uid=0(root) gid=0(root) groups=0(root)
$ docker run --rm --security-opt seccomp=builtin lt-lab unshare --user --map-root-user id   # Docker's profile
unshare: unshare failed: Operation not permitted
Caveat — check your daemon; Docker Desktop may differ from a server

On a stock Linux Docker Engine the built-in profile is the default and a plain docker run shows Seccomp: 2. The Docker Desktop install used to write this course reports name=seccomp,profile=unconfined under docker info --format '{{json .SecurityOptions}}', so plain containers there show Seccomp: 0 — hence the explicit seccomp=builtin above, which Docker documents for exactly this situation.[Docker: run] The lesson generalises: never assume a wall is up because it is "the default". Read the line.

Notice the blocked call returned the same EPERM as a missing capability. From a transcript you cannot tell which wall said no — and often both would have: the profile is capability-aware, so with --cap-add SYS_ADMIN the built-in profile lets mount through (run it: exit 0). Defence in depth means the dangerous calls are gated twice. Docker's advice on custom profiles is short: "It is not recommended to change the default seccomp profile."[Docker: seccomp]

no_new_privs: the one-way ratchet

One loose end from the capability table: a non-root agent with an intact bounding set gets everything back if it can run a setuid-root program (page 8). The no_new_privs bit closes that. Once set, "it is inherited across fork, clone, and execve and cannot be unset," and "the setuid and setgid bits will no longer change the uid or gid; file capabilities will not add to the permitted set."[Kernel: no_new_privs] A setuid-root copy of grep, run by learner to read its own capability mask, makes it visible: 

$ docker run --rm lt-lab bash -c 'cp /usr/bin/grep /usr/local/bin/suid-grep; chmod u+s /usr/local/bin/suid-grep; su learner -c "grep CapEff /proc/self/status; suid-grep CapEff /proc/self/status"'
CapEff:	0000000000000000
CapEff:	00000000a80425fb
$ docker run --rm --security-opt no-new-privileges lt-lab bash -c '…same…'
CapEff:	0000000000000000
CapEff:	0000000000000000

First run: the ordinary grep has nothing, the setuid one has all fourteen back. Second run: the setuid bit is ignored, and NoNewPrivs: 1 in status says why.

The cost, in Docker's words: "commands that raise privileges such as su or sudo no longer work."[Docker: run] The limit, in the kernel's: it "does not prevent privilege changes that do not involve execve()" — a process that is already root stays root.[Kernel: no_new_privs]

AppArmor and SELinux, in one paragraph

On hosts that have it (Ubuntu, Debian and SUSE servers; not Docker Desktop's VM, so nothing to demo here), AppArmor adds a path-based layer: "Docker automatically generates and loads a default profile for containers named docker-default,"[Docker: AppArmor] whose template denies, among other things, all mounts and writes to most of /proc and /sys. Red Hat-family hosts use SELinux labels for the same job. Docker calls these "an extra safety net (even though it overlaps greatly with capabilities)."[Docker: security] Recognise the name; denials show up in the host's kernel log with apparmor="DENIED", which is where to look when an operation fails with EPERM though capabilities and seccomp both allow it.

In eval work — discuss: the sandbox policy is part of the result

These knobs are the sandbox's policy, and every one has two faces. Validity: a memory limit converts big-but-correct solutions into failures; a CPU limit converts them into timeouts; a dropped capability breaks a legitimate tool. Integrity: a missing limit lets one rollout starve its neighbours; an extra capability lets the agent rewrite the grader's inputs. Two runs of "the same benchmark" under different policies are different measurements. So record the policy with the results — the limits, the decoded CapEff/CapBnd, Seccomp and NoNewPrivs, read from inside the running sandbox rather than copied from the config you meant to apply. Page 23 assembles the knobs into a policy and a self-test.

Depth triage

Learn to use: the three .max files and their events/stat counters; CapEff/CapBnd with capsh --decode; the table of a dozen capabilities; the Seccomp and NoNewPrivs lines. Recognize: the other thirty-odd capabilities (look them up in man 7 capabilities), the permitted/inheritable/ambient sets, file capabilities, memory.high and the io controller, AppArmor and SELinux. Leave to a specialist: writing seccomp profiles or LSM policy, and designing cgroup hierarchies for a cluster scheduler.

Check your understanding

To fit more rollouts per machine, a team changes its runner from --memory 8g --cpus 4 to --memory 2g --cpus 1. The pass rate on a 500-task coding benchmark drops from 41% to 33%, with no infrastructure errors reported: every container exited 0 or with the agent's own exit code. The lead wants to publish 33% as "the same benchmark, more efficiently run". What do you ask for?

Reveal the reasoning

Observed: an 8-point drop coinciding with a policy change, and clean container exit codes. Supposed: that clean exit codes mean no infrastructure failures. They don't: an OOM-killed child leaves the container exiting 0, and CPU throttling produces no error at all, only slowness that surfaces as harness or test timeouts. Discriminating evidence, per rollout: oom_kill from memory.events and State.OOMKilled; memory.peak against the 2 GB limit; nr_throttled/throttled_usec; and the share of failures that are timeouts before and after. If the newly failed tasks cluster on those signals, the drop is the environment, not the model. Also run the oracle solutions under the new policy — any oracle that fails marks a task the policy made unsolvable. Then report honestly: the policy is part of the benchmark's definition, so 33% and 41% are results on different instruments; give correct/scheduled alongside completed/scheduled with resource-killed rollouts counted as not completed, and decide which policy is canonical before looking at which number is nicer.

Lab

Container lab. All exercises start containers from the page-1 image lt-lab, from your Mac's terminal. Exercise 4 needs ping, which that image lacks; add it once with docker run --name lt-tmp lt-lab bash -c 'apt-get update && apt-get install -y iputils-ping' && docker commit lt-tmp lt-lab:ping && docker rm lt-tmp.

  1. Start a container with --memory 256m --cpus 1.5 --pids-limit 100 and read the three limit files. Then do the arithmetic: what would --memory 512m --cpus 0.25 write?
    Solution

    The first is the session in the cgroups section. For the second: 512 × 1024 × 1024 = 536870912 in memory.max, and a quarter of a 100000 µs period, 25000 100000, in cpu.max. Check with docker run --rm --memory 512m --cpus 0.25 lt-lab cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max.

  2. Predict, then verify: in the OOM demo, what is the container's exit code, and what does docker inspect say about OOMKilled?
    Solution

    Run the two commands from the enforcement section: child exit=137, oom_kill 1, then ExitCode=0 OOMKilled=true. The container's exit code belongs to its PID 1 (bash, which survived); OOMKilled says some process in the cgroup was killed. They are independent facts.

  3. Decode three masks with capsh --decode: a default container's CapEff, the same with --cap-drop ALL --cap-add NET_BIND_SERVICE, and the CapBnd of a container run with --user 1001.
    Solution

    Default: 00000000a80425fb, the fourteen names shown in the capabilities section. The --user 1001 container has CapEff: 0000000000000000 but CapBnd: 00000000a80425fb — the same fourteen, waiting for anything that becomes root. For the middle one, run docker run --rm --cap-drop ALL --cap-add NET_BIND_SERVICE lt-lab bash -c 'capsh --decode=$(grep CapEff /proc/self/status | cut -f2)'; it names exactly one capability, cap_net_bind_service.

  4. Predict: with --cap-drop ALL, what happens to ping -c1 127.0.0.1? Find the smallest policy that makes it work.
    Solution 
    $ docker run --rm --cap-drop ALL lt-lab:ping bash -c 'ping -c1 -W1 127.0.0.1 | tail -2'
bash: line 1: /usr/bin/ping: Operation not permitted
$ docker run --rm --cap-drop ALL --cap-add NET_RAW lt-lab:ping bash -c 'getcap /usr/bin/ping; ping -c1 -W1 127.0.0.1 | tail -2'
/usr/bin/ping cap_net_raw=ep
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 0.428/0.428/0.428/0.000 ms

    Ubuntu's ping carries a file capability (cap_net_raw=ep, shown by getcap) instead of being setuid. With NET_RAW outside the bounding set, the program could not even be started — the error comes from bash, not from ping. --cap-drop ALL --cap-add NET_RAW is the minimal policy for a task family that needs it.

  5. Eval task. A task author says: "the agent runs as a non-root user, so capabilities don't matter."
