Text-fu: reading logs at scale

An eval run leaves behind thousands of lines of text: one result record per rollout, plus transcripts and container logs. A dozen small programs, joined by pipes, let you ask those files questions — which model, which task, which exit code, how often — in seconds, from any box you can get a shell on. This page teaches that toolkit on a real results file.

Filter, extract, aggregate

Page 4 showed that a pipe connects one program's output to the next one's input. The Unix text tools are built for that: each reads lines, does one small thing, and writes lines. Almost every useful question about a log is three stages:

FILTER EXTRACT AGGREGATE keep the lines keep the part of count, sort, you care about each line you need sum grep, jq select() cut, awk, grep -o, sort | uniq -c | sort -rn awk '$4 == 137' jq -r .field, sed wc -l, awk '{s += $1} END …'

Build pipelines one stage at a time, looking at the output of each stage (through | head) before adding the next. When a pipeline gives a wrong answer, it is almost always because an early stage let through something you didn't expect.

The data

The course's running example, wordfreq-bench, comes with a generator that prints a results file for an imaginary run: 3 models × 8 tasks × 8 epochs, fixed random seed, so your numbers will match this page exactly. The format is JSONL — one JSON object per line — which is what most harnesses write, because a line-per-record file can be appended to safely and read by line-oriented tools. In the container lab (with python3 and jq installed, and gen_results.py copied in — see the lab): 

$ python3 gen_results.py > results.jsonl
$ wc -l results.jsonl
192 results.jsonl
$ head -n 2 results.jsonl
{"task": "wordfreq", "model": "model-a", "epoch": 1, "exit_code": 0, "passed": true, "stderr_tail": "", "duration_s": 72.7}
{"task": "wordfreq", "model": "model-a", "epoch": 2, "exit_code": 0, "passed": true, "stderr_tail": "", "duration_s": 87.4}
$ tail -n 1 results.jsonl
{"task": "symlinks", "model": "model-c", "epoch": 8, "exit_code": 2, "passed": false, "stderr_tail": "E: Could not get lock /var/lib/dpkg/lock-frontend", "duration_s": 77.1}

Three commands, three habits. wc -l counts lines, so on JSONL it counts records (strictly, it counts newline characters[Coreutils]): 192 = 3 × 8 × 8, so nothing is missing. head and tail show the first and last 10 lines unless told otherwise with -n. Each record carries the exit status of the task's test command, a pass flag, the last line of stderr, and the duration. For a file that is still being written, tail -f keeps printing new lines as they arrive (Ctrl+C to stop) — the normal way to watch a run.

grep: keep the lines that match

grep PATTERN file prints the lines containing the pattern. The flags worth knowing change what it prints instead: 

$ grep -c '"passed": true' results.jsonl     # -c: count matching lines
106
$ grep -c -v '"passed": true' results.jsonl  # -v: invert — lines that do NOT match
86
$ grep -n Killed results.jsonl | head -n 1   # -n: prefix the line number
87:{"task": "logrotate", "model": "model-b", "epoch": 7, "exit_code": 137, "passed": false, "stderr_tail": "Killed", "duration_s": 182.7}
$ grep -o '"exit_code": [0-9]*' results.jsonl | head -n 2   # -o: only the matched part
"exit_code": 0
"exit_code": 0

-o is what turns grep from a filter into an extractor. The pattern [0-9]* is a regular expression: "any run of digits". This page uses only a few ([0-9], ^ for start of line, . for any character, and -E with a|b for alternatives); Appendix D covers the rest. Always put patterns in single quotes, so the shell passes them through untouched.

The remaining flags are for searching many files and for context. -i ignores case; -r searches a directory tree; -l lists only the names of files that match; -A 2, -B 1, -C 3 print lines after, before, or around each match — essential for multi-line logs, where the line you can search for is not the line you need to read. For example, what has been installed in this box with apt-get, and when? 

$ grep -rl dpkg /var/log 2>/dev/null
/var/log/bootstrap.log
/var/log/apt/history.log
/var/log/dpkg.log
$ grep -B 1 -A 2 'Commandline: apt-get install -y' /var/log/apt/history.log | cut -c 1-90
Start-Date: 2026-09-21  11:02:46
Commandline: apt-get install -y -qq --no-install-recommends python3 jq
Install: python3.12:arm64 (3.12.3-1ubuntu0.17, automatic), netbase:arm64 (6.4, automatic),
End-Date: 2026-09-21  11:02:48

Run inside a finished task container, that is a forensic record of what an agent installed (page 13). cut -c 1-90 kept only the first 90 characters of each line — the standing fix for log lines too long to read.

sort | uniq -c | sort -rn

The most useful idiom in log analysis answers "how many of each?". uniq -c collapses repeated lines and prefixes a count — but it only notices repeats that are adjacent,[Coreutils] because it reads one line at a time and compares it with the previous one. Without a sort first it counts runs, not totals: 

$ grep -o '"exit_code": [0-9]*' results.jsonl | uniq -c | head -n 3
      6 "exit_code": 0
      1 "exit_code": 1
      2 "exit_code": 0
$ grep -o '"exit_code": [0-9]*' results.jsonl | sort | uniq -c | sort -rn
    106 "exit_code": 0
     56 "exit_code": 1
      9 "exit_code": 127
      8 "exit_code": 124
      5 "exit_code": 137
      4 "exit_code": 2
      4 "exit_code": 126

sort brings identical lines together, uniq -c counts them, and sort -rn orders the counts numerically (-n), largest first (-r). Without -n, sort compares text, and 100 sorts before 9. The other sort flags you will use: -k picks the column to sort by, -t sets the column separator, -u drops duplicates.

Already this is a finding. A third of the failures (30 of 86) are not exit 1 ("the tests ran and failed") but 127, 124, 137, 126 — codes that page 10 decodes as command not found, timed out, killed, not executable. Those describe the box as much as the model.

Pitfall

Sort order depends on the locale. sort (and uniq, and the order of ls) compare using the rules of the language setting in the environment.[Coreutils] The same file, the same command, two environments:

$ LC_ALL=C sort mixed.txt | tr '\n' ' '
10 9 A B _x a b
$ LC_ALL=en_US.UTF-8 sort mixed.txt | tr '\n' ' '
10 9 a A b B _x

The stock ubuntu:24.04 image has only the C locales, so this difference appears when the same script runs on a developer's Mac, a CI host, or an image with locales installed (we generated en_US.UTF-8 to show it). A grader that compares an agent's sorted output with an expected file is comparing two locales unless both sides pin one. Write LC_ALL=C sort in anything whose output is compared or published; the manual notes that setting LC_COLLATE alone does nothing if LC_ALL is set.

jq: grep, cut and group-by for JSON

grepping JSON works until a value contains a quote, a field moves, or a writer drops the space after the colon. jq parses the JSON instead. Its input is "a sequence of whitespace-separated JSON values", each passed through your filter in turn[jq Manual] — which is exactly a JSONL file. It is not in the base image: apt-get install jq. Four pieces cover most needs:

PieceDoes
.fieldExtracts a field from each record (null if absent — no error, so typos are silent).[jq Manual]
select(cond)Passes the record through unchanged if the condition is true, else prints nothing.
-rRaw output: strings without JSON quotes, ready for sort and uniq.
-cCompact output: one record per line (the default is pretty-printed).
$ jq -c 'select(.exit_code == 137)' results.jsonl | head -n 1
{"task":"logrotate","model":"model-b","epoch":7,"exit_code":137,"passed":false,"stderr_tail":"Killed","duration_s":182.7}
$ jq -r 'select(.passed) | .model' results.jsonl | sort | uniq -c
     45 model-a
     34 model-b
     27 model-c

Inside the quotes, | is jq's own pipe: filter, then extract. Outside, the shell's pipe takes over for the aggregate stage. Each model had 64 rollouts, so that is the first question answered: pass rates of 45/64, 34/64 and 27/64.

To aggregate inside jq, -s ("slurp") reads the whole input into one array and runs the filter once,[jq Manual] which makes group_by, length and add available: 

$ jq -sc 'group_by(.model) | map({model: .[0].model, n: length, passed: (map(select(.passed)) | length)})' results.jsonl
[{"model":"model-a","n":64,"passed":45},{"model":"model-b","n":64,"passed":34},{"model":"model-c","n":64,"passed":27}]
$ jq length results.jsonl | head -n 1
7
$ jq -s length results.jsonl
192

The last two are a classic trap: without -s, length is applied to each record and reports its seven keys. A second trap: jq stops at the first malformed line, having already printed results for the lines before it. It exited with status 5 when we fed it one — so check jq's exit status before trusting a count from a file a crashed process was writing.

cut, tr, awk, sed: columns and substitutions

Plenty of logs are not JSON. To practise on columns, flatten the results into space-separated text with jq's string interpolation: 

$ jq -r '"\(.task) \(.model) \(.epoch) \(.exit_code) \(.duration_s)"' results.jsonl > runs.txt
$ head -n 2 runs.txt
wordfreq model-a 1 0 72.7
wordfreq model-a 2 0 87.4
$ cut -d ' ' -f 1,4 runs.txt | head -n 1        # fields 1 and 4, delimiter = one space
wordfreq 0
$ tr ' ' ',' < runs.txt | head -n 1             # translate characters: instant CSV
wordfreq,model-a,1,0,72.7

cut is rigid — one delimiter character exactly, so columns padded with several spaces defeat it. awk splits on any run of whitespace, names the pieces $1, $2, …, and runs a tiny program of the form condition {action} on every line. Learn four shapes and stop: 

$ awk '{print $2, $5}' runs.txt | head -n 1                    # pick columns
model-a 72.7
$ awk '$4 == 137' runs.txt | head -n 2                         # filter on a column; default action: print
logrotate model-b 7 137 182.7
jsonfix model-b 8 137 169.5
$ awk '$4 == 0 {s += $5; n++} END {print n, s / n}' runs.txt   # sum and average
106 52.5283
$ awk -F: '{print $1, $7}' /etc/passwd | tail -n 1             # -F sets the separator
learner /bin/bash

Passing rollouts took 52.5 seconds on average. For a median there is no built-in, but a sorted column and a line number will do: with 192 values the median sits between the 96th and 97th. sed prints line ranges with -n 'A,Bp': 

$ jq '.duration_s' results.jsonl | sort -n | sed -n '96,97p'
67.0
67.3
$ jq '.duration_s' results.jsonl | sort -n | tail -n 2
300.0
300.0

The median is about 67 seconds; the maximum is a suspiciously round 300.0, and jq -r 'select(.exit_code == 124) | .duration_s' results.jsonl | sort | uniq -c confirms all eight exit-124 rows sit at exactly 300.0 — the harness's time limit, not a property of the model's solution. sed's other job is substitution: sed 's/model-/m/' runs.txt prints each line with the first model- replaced by m. Adding -i edits the file in place. That is the one sed flag that differs on the reader's Mac: BSD sed wants -i '', and the GNU spelling fails there with invalid command code (Appendix E). Agents trained on both spellings get this wrong in both directions; in a transcript it is a Linux-fluency slip, not an environment fault.

Worked example: first-pass error analysis

Pass rate per model and the exit-code table are done. Three questions remain.

Which tasks never pass?

$ jq -r 'select(.passed) | .task' results.jsonl | sort -u
csvsum
dedupe
jsonfix
logrotate
pathwalk
tzparse
wordfreq

Seven names; there are eight tasks. symlinks is missing: 0 passes in 24 rollouts across three models, while the next-hardest task, tzparse, passes 9 of 24. Observed: no model ever passes it. Hypotheses: it is very hard, or it is broken (a test that cannot pass). The results file cannot tell these apart. The discriminating test is to run the task's oracle solution through the same grader: if the reference answer fails too, the task is measuring nothing and its 24 rows belong in neither numerator nor denominator.

Why do rollouts fail?

The brief for this analysis might say: grep the stderr tails for Killed, Permission denied, command not found. 

$ grep -E -o 'Killed|Permission denied|command not found|No space left' results.jsonl | sort | uniq -c | sort -rn
      9 command not found
      9 Permission denied
      7 No space left
      5 Killed

Quick, and subtly wrong: keyword buckets merge things that differ. Pair the exit code with the whole message instead: 

$ jq -r 'select(.passed | not) | "\(.exit_code)\t\(.stderr_tail)"' results.jsonl | cut -c 1-60 | sort | uniq -c | sort -rn
     37 1	AssertionError: Lists differ: [('The', 3)] != [('the', 7)]
      9 127	bash: line 1: pytest: command not found
      8 124
      7 1	OSError: [Errno 28] No space left on device
      7 1	ModuleNotFoundError: No module named 'wordfreq'
      5 137	Killed
      5 1	PermissionError: [Errno 13] Permission denied: '/opt/grade
      4 2	E: Could not get lock /var/lib/dpkg/lock-frontend
      4 126	bash: line 1: ./run.sh: Permission denied

"Permission denied" was two different events: a script without its execute bit (exit 126), and a test process refused access to a file under /opt/grader (page 8) — five rollouts whose tests could not read their own expected output. Also visible: exit code 1 covers three unrelated causes, and eight timeouts left no stderr at all. Only 37 of 86 failures are the tests delivering a verdict on the model's code.

In eval work

This is first-pass error analysis — reading failures and sorting them into categories before trusting any aggregate (the sibling course's page 4 gives the full method). At the terminal its first product is a split between rollouts where the test delivered a verdict and rollouts where something else ended the run. Count a verdict as "pass, or an AssertionError", and report three quantities, not one:

$ jq -r '[.model, .passed, (.stderr_tail | startswith("AssertionError"))] | @tsv' results.jsonl \
    | awk '{n[$1]++; if ($2 == "true") p[$1]++; if ($2 == "true" || $3 == "true") v[$1]++}
           END {for (m in n) printf "%s scheduled=%d verdicts=%d passed=%d  passed/scheduled=%.1f%%  passed/verdicts=%.1f%%  verdicts/scheduled=%.1f%%\n",
                m, n[m], v[m], p[m], 100*p[m]/n[m], 100*p[m]/v[m], 100*v[m]/n[m]}' | sort
model-a scheduled=64 verdicts=55 passed=45  passed/scheduled=70.3%  passed/verdicts=81.8%  verdicts/scheduled=85.9%
model-b scheduled=64 verdicts=48 passed=34  passed/scheduled=53.1%  passed/verdicts=70.8%  verdicts/scheduled=75.0%
model-c scheduled=64 verdicts=40 passed=27  passed/scheduled=42.2%  passed/verdicts=67.5%  verdicts/scheduled=62.5%

The gap between model-b and model-c is 11 points on one denominator and 3 on the other. Neither is "the" answer: a quarter to a third of rollouts never reached a verdict, and the rate differs by model — which is itself a finding. Non-verdict endings are observations about the run until a transcript shows otherwise: pytest: command not found could be a bad image or an agent that broke its own PATH; a timeout could be a slow box or a model stuck in a loop. Decide the primary metric before looking, publish all three columns, and never let the non-verdict rows silently vanish.

xargs: from a list of names to a command

Real runs produce a directory of logs, not one file. xargs reads names from stdin and appends them as arguments to a command — the bridge from find (page 3) to everything on this page. By default it splits its input on whitespace, and file names may legally contain spaces: 

$ mkdir -p logs; cp results.jsonl "logs/run 1.jsonl"; cp results.jsonl logs/run2.jsonl
$ find logs -name '*.jsonl' | xargs wc -l
  192 logs/run2.jsonl
  192 total
wc: logs/run: No such file or directory
wc: 1.jsonl: No such file or directory
$ find logs -name '*.jsonl' -print0 | xargs -0 wc -l
  192 logs/run2.jsonl
  192 logs/run 1.jsonl
  384 total

The first version reported a total that silently left out half the data. -print0 and -0 make both sides use a zero byte — the one character a file name cannot contain — as the separator. Use the pair always; it costs nothing.

Caveat

When to stop and open Python. The terminal is for the first ten minutes: is the file complete, what are the categories, which tasks are broken, is anything absurd? A rule of thumb: as soon as the question needs more than one join between files, or any statistics — a confidence interval, a comparison between models — move to pandas. Shell pipelines have no types, no tests, and fail silently (every pitfall above). A pass-rate difference read off uniq -c has no error bar; the sibling course's page 16 explains why that matters with 64 samples per model.

Depth triage. Learn to use: grep with the flags above, sort | uniq -c | sort -rn, head/tail/wc -l, jq's .field/select/-r/-c/-s, awk's four shapes, sed's s/// and -n 'A,Bp', find -print0 | xargs -0. Recognise when an agent writes them: awk programs with loops and arrays (like the accounting command above — note how quickly it became hard to read), sed with hold space or multi-line scripts, jq's reduce and path(). Leave those to Python in your own work.

Check your understanding

A teammate's summary of the run above reads: "model-a 81.8%, model-b 70.8%, model-c 67.5%. Infrastructure failures were excluded." You have results.jsonl and ten minutes before the numbers go into a slide. What do you check, and what do you ask for?

Reveal the reasoning

Establish what was done. Those figures are passed / verdicts. Excluded: 9, 16 and 24 rollouts respectively — 14%, 25% and 37.5% of each model's sample. An exclusion that large, and that unequal, is not a footnote. Ask whether the exclusion rule was written down before anyone looked at the results, and what exactly it was (by exit code? by stderr keyword? The keyword route merged two different "Permission denied" events).

Evidence vs hypothesis. "Infrastructure failure" is a hypothesis about each excluded row. What is observed is an exit code and one line of stderr. Discriminating evidence is in the transcripts: did pytest exist at the start of the rollout (image defect) or did the agent uninstall or shadow it (model behaviour)? Did the timed-out rollouts stall on an interactive prompt, a slow box, or a loop? If weaker models trigger more "infrastructure" failures, some of those failures are probably the model's, and excluding them flatters the weaker model most — here it shrinks the b–c gap from 11 points to 3.

What to ask for. All three quantities on the slide (passed/scheduled, passed/verdicts, verdicts/scheduled); the symlinks task run against its oracle solution and, if broken, removed for every model alike; and a rerun of the rows that were genuine environment defects, rather than deleting them.

Lab

Container lab. As root: apt-get update && apt-get install -y python3 jq. From your Mac, copy the generator in: docker cp research/wordfreq-bench/gen_results.py lt-lab:/home/learner/. Then su - learner and python3 gen_results.py > results.jsonl. The seed is fixed: your numbers should equal the ones below.

  1. Confirm the file is complete (192 records), count the passes with grep -c, and count model-a's passes using two greps in a pipe.

    Solution 
    $ wc -l results.jsonl
192 results.jsonl
$ grep -c '"passed": true' results.jsonl
106
$ grep 'model-a' results.jsonl | grep -c '"passed": true'
45

  2. Predict, then run: what does printf '10\n9\n100\n' | sort print, and what changes with sort -n? Then predict the output of printf 'b\na\nb\nb\na\n' | uniq -c.

    Solution 
    $ printf '10\n9\n100\n' | sort | tr '\n' ' '
10 100 9
$ printf '10\n9\n100\n' | sort -n | tr '\n' ' '
9 10 100
$ printf 'b\na\nb\nb\na\n' | uniq -c
      1 b
      1 a
      2 b
      1 a

    Text comparison goes character by character, so 1 < 9 decides it. uniq only merges adjacent lines; with sort first you get 2 a / 3 b.

  3. Which model has the most rollouts that ended in a timeout (124) or a kill (137)? Use jq to filter and the counting idiom to aggregate.

    Solution 
    $ jq -r 'select(.exit_code == 124 or .exit_code == 137) | .model' results.jsonl | sort | uniq -c
      2 model-a
      5 model-b
      6 model-c

  4. Nine rollouts died with pytest: command not found. If one task's image were missing pytest, they would cluster on that task. Do they?

    Solution 
    $ jq -r 'select(.exit_code == 127) | .task' results.jsonl | sort | uniq -c | sort -rn
      2 wordfreq
      2 pathwalk
      2 jsonfix
      1 tzparse
      1 symlinks
      1 logrotate

    No: six tasks, never more than two each. Observed: the failure is spread across tasks, and the same tasks pass in other epochs. That rules out "this task's image lacks pytest" and leaves hypotheses such as an agent damaging its own environment or a per-rollout setup step that sometimes fails — the next evidence is the transcript of one of the nine.

  5. Eval task. You have established (by running its oracle solution) that the symlinks task is broken. Recompute each model's passed / scheduled without it, in one pipeline.

    Solution 
    $ jq -r 'select(.task != "symlinks") | "\(.model) \(.passed)"' results.jsonl \
    | awk '{n[$1]++; if ($2 == "true") p[$1]++} END {for (m in n) printf "%s %d/%d = %.1f%%\n", m, p[m], n[m], 100 * p[m] / n[m]}' | sort
model-a 45/56 = 80.4%
model-b 34/56 = 60.7%
model-c 27/56 = 48.2%

    Every model gains about ten points and the ranking is unchanged — a broken task depresses all scores, which is why it is removed for everyone and the removal is reported. (This awk is at the edge of what belongs in a shell; the pandas version is three readable lines.)
