Module 5 · Networking for Sandboxes

Ports, sockets, TCP and UDP

An address gets a packet to a box; a port gets it to a process. This page teaches you to list who is listening and on which address, to read the four ways a connection attempt fails, and to see why "it's running, I started it" and "the grader can't reach it" are so often both true.

This page finishes audit question 1 (what is running?) — a process with a listening socket is offering a service — and continues question 4 (what can it reach?). The concepts are taught in the sibling networking course (addresses, ports, and localhost; TCP, UDP, and QUIC; containers: whose network is this?). Here they get a paragraph; the rest is the Linux side. Sessions use the lt-net:local image built in page 16's lab (stock ubuntu:24.04 has no ss, nc, curl or python3), running as the non-root user learner.

The model: a socket is an endpoint a process holds

A port is a 16-bit number (0–65535) that the transport protocols add on top of IP so that one address can serve many conversations: "an IP socket address is defined as a combination of an IP interface address and a 16-bit port number."[ip(7)] A socket is the kernel object a process holds — a file descriptor, like any other — that is bound to such an address. A connection is identified by the full tuple: protocol, local address and port, remote address and port. That is why one server port can carry thousands of clients.

Two transport protocols matter, and their port spaces are separate (TCP 53 and UDP 53 are different doors):

TCPUDP
Service "a reliable, stream-oriented, full-duplex connection"; data "arrives in order" and lost packets are retransmitted[tcp(7)] "a connectionless, unreliable datagram packet service"; packets "may be reordered or duplicated"[udp(7)]
Before data flowsA handshake — so "can I connect?" has a yes/no answerNothing — silence is ambiguous

Port ranges. IANA divides the space into System Ports 0–1023, User Ports 1024–49151, and Dynamic Ports 49152–65535.[RFC 6335] Linux does not follow the last part: a client's source port (its ephemeral port) is drawn from ip_local_port_range, whose default is 32768–60999.[Kernel: ip-sysctl] You will see exactly that in connection listings below (:47856).

Pitfall

"Ports below 1024 need root" is false inside a Docker container. The classic rule is real: binding a port below 1024 requires the capability CAP_NET_BIND_SERVICE.[ip(7)] But the threshold is a per-network-namespace sysctl, ip_unprivileged_port_start, kernel default 1024,[Kernel: ip-sysctl] and inside a Docker container it reads 0:

$ cat /proc/sys/net/ipv4/ip_unprivileged_port_start
0
$ id -u; grep CapEff /proc/self/status
1001
CapEff:	0000000000000000
$ python3 -m http.server 80 &
$ ss -tlpn 'sport = :80'
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      5            0.0.0.0:80        0.0.0.0:*    users:(("python3",pid=53,fd=3))

Uid 1001 with no capabilities at all is serving on port 80. With the kernel default restored (docker run --sysctl net.ipv4.ip_unprivileged_port_start=1024 …) the same command fails with PermissionError: [Errno 13] Permission denied — which is what you get on a VM or bare host. So a task that "works in the container" can fail on a VM-based sandbox for this reason alone — and "it listens on port 80" proves nothing about privilege.

Reading ss -tulpn

ss ("socket statistics") lists the kernel's socket table. The five flags worth memorising as one word: -t TCP, -u UDP, -l listening only ("these are omitted by default"), -p show the owning process, -n numbers instead of service names.[ss(8)] In a container where learner has started two web servers and a UDP listener: 

$ ss -tulpn
Netid State  Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
udp   UNCONN 0      0         127.0.0.11:44963      0.0.0.0:*
udp   UNCONN 0      0            0.0.0.0:5005       0.0.0.0:*    users:(("nc",pid=19,fd=3))
tcp   LISTEN 0      4096      127.0.0.11:43993      0.0.0.0:*
tcp   LISTEN 0      5            0.0.0.0:8000       0.0.0.0:*    users:(("python3",pid=7,fd=3))
tcp   LISTEN 0      5          127.0.0.1:8001       0.0.0.0:*    users:(("python3",pid=13,fd=3))

The column that matters is Local Address:Port — and within it, the address half, which the next section is about. Peer is * for a listener (anyone may connect). Process gives the program, its PID, and which of its file descriptors is the socket (the header really does print "PortProcess" run together). The two 127.0.0.11 lines with no process are Docker's built-in DNS for user-defined networks; they belong to the Docker daemon, outside this container's process tree.

Caveat

An empty Process column does not mean "no process". ss -p can only name processes whose details you are allowed to read. Run the same command as a different user — and here, even as root in the same default container, where the servers belong to learner — and every Process cell comes back blank, with no error:

# ss -tlpn
State  Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
LISTEN 0      4096      127.0.0.11:43993      0.0.0.0:*
LISTEN 0      5            0.0.0.0:8000       0.0.0.0:*
LISTEN 0      5          127.0.0.1:8001       0.0.0.0:*

The listening lines themselves are always complete. For the owner, run ss as the user who started the service, or from outside with full privileges.

Drop the -l and you see live connections instead. Client side, then server side, of one connection:

$ ss -tn
State Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
ESTAB 0      0         172.20.0.3:47856   172.20.0.2:8000

$ ss -tnp
State Recv-Q Send-Q Local Address:Port Peer Address:Port Process
ESTAB 0      0         172.20.0.2:8000   172.20.0.3:47856 users:(("python3",pid=7,fd=4))

The same tuple seen from both ends; the client's port is an ephemeral one from the Linux range. In an audit, ss -tn answers "who is this box talking to right now?"

The bind address decides who can knock

When a server starts it binds: it picks a port and a local address. The bind address is a filter on which of the box's interfaces accept connections for it. 127.0.0.1 means loopback only; 0.0.0.0 is the "any" address — "the socket will be bound to all local interfaces."[ip(7)] The container above has one server of each kind. From a second container on the same Docker network: 

$ curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://lt-17-srv:8000/
200
$ curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://lt-17-srv:8001/
curl: (7) Failed to connect to lt-17-srv port 8001 after 0 ms: Couldn't connect to server
000
$ curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://localhost:8000/
curl: (7) Failed to connect to localhost port 8000 after 0 ms: Couldn't connect to server
000

Port 8001 is alive and healthy — curl http://127.0.0.1:8001/ inside the server container returns 200 — but from next door it is indistinguishable from a port with nothing on it. And the third command fails for the mirror-image reason: localhost is a point of view. Each container has its own network namespace, and a namespace isolates, among other things, "port numbers (sockets)".[network_namespaces(7)] The client's localhost:8000 is the client's own port 8000, where nothing listens.

container "app" (its own netns) container "db" (its own netns) ┌───────────────────────────────┐ ┌───────────────────────────────┐ │ lo 127.0.0.1 │ │ lo 127.0.0.1 ◀─ :8001 │ │ localhost:5432 ─▶ nothing │ │ (loopback only) │ │ eth0 172.20.0.3 ─────────────┼────┼─▶ eth0 172.20.0.2 │ │ db:5432 ─▶ reaches db │ │ ◀─ 0.0.0.0:8000, :5432 │ └───────────────────────────────┘ └───────────────────────────────┘

This is why an application configured with localhost:5432 cannot find its database in the next container, and why the Compose service name works: each service "is both reachable by other containers on that network, and discoverable by its service name", and service-to-service traffic uses the container port.[Compose: networking]

In eval work · navigate

"Build a web service" tasks fail on this constantly, in both directions. Many frameworks' development servers bind 127.0.0.1 by default; the agent's transcript shows Serving HTTP on 127.0.0.1 port 8000, the agent's own curl localhost:8000 succeeds, and a verifier connecting from another container or the host gets Connection refused. Is that a model failure? Only if the task statement made the requirement observable ("the service must accept connections from other hosts", or an explicit 0.0.0.0). If the grader's vantage point is an unstated detail of the harness, you are measuring whether the model guessed your infrastructure. Either state it, or grade from inside the same namespace (docker exec … curl localhost:8000). The one-line evidence is the Local Address column of ss -tln.

Four ways to fail, and what each proves

When a connection attempt fails, the error text tells you how far it got. All of these were produced for real; each is shown as curl and as nc -zv (-z: connect and close without sending, -v: say what happened, -w N: give up after N seconds).

You seeTimeWhat happenedWhat it does not prove
Connection refused
curl exit 7, "after 0 ms"		instant Something answered "no". A reachable host with no listener on that port replies with a TCP reset.[RFC 9293][connect(2)] That the host itself answered. A firewall REJECT rule sends back an error packet too — by default ICMP port-unreachable, optionally a TCP reset[iptables-extensions(8)] — and the client sees exactly the same thing. Nor that the service is down: it may be bound to loopback.
Connection timed out
curl exit 28; nc: "timed out"		as long as you allowed Packets left and nothing came back: silently dropped by a firewall, or sent toward an address nobody owns. Which hop dropped it. That needs a vantage point on the other side (page 19).
Network is unreachable
curl exit 7, "after 0 ms"		instant The kernel has no route (--network none). Nothing was sent. — This one is conclusive; check ip route.
No route to host
curl exit 7, "after 3111 ms"		~3 s The route says "directly connected", but no machine on the local subnet owns that address. That the service is broken: the container may simply not be up yet, or have a different address this run.
Could not resolve host
curl exit 6		instant (here) Never got as far as a connection: the name failed. Different layer — page 18. Anything about the port or the service.
$ nc -zv -w 3 lt-17-srv 8000
Connection to lt-17-srv (172.20.0.2) 8000 port [tcp/*] succeeded!
$ nc -zv -w 3 lt-17-srv 9999
nc: connect to lt-17-srv (172.20.0.2) port 9999 (tcp) failed: Connection refused
$ nc -zv -w 3 192.0.2.1 80
nc: connect to 192.0.2.1 port 80 (tcp) timed out: Operation now in progress
$ nc -zv -w 5 172.20.0.99 8000
nc: connect to 172.20.0.99 port 8000 (tcp) failed: No route to host
Key idea

Fast failures are answers; slow failures are silence. "Refused" and "unreachable" come back in milliseconds because something — the peer, a firewall, your own kernel — actively said no. A dropped packet says nothing, and by default Linux keeps retrying: six SYN retransmissions, about two minutes (tcp(7) says roughly 127 seconds, the kernel documentation 131).[Kernel: ip-sysctl][tcp(7)] So every network command in a harness, a grader, or a probe takes an explicit timeout — curl -m, nc -w, timeout. Without one, a firewalled sandbox turns each blocked call into two minutes of a rollout's time budget.

When the box has no tools: /dev/tcp

Minimal images have no nc or curl. Bash itself can open a TCP connection: a redirection to /dev/tcp/host/port is handled by bash, not the filesystem[Bash Manual] — there is no such file. In stock ubuntu:24.04: 

# ls -l /dev/tcp
ls: cannot access '/dev/tcp': No such file or directory
# (echo > /dev/tcp/lt-17-srv/8000) && echo open
open
# (echo > /dev/tcp/lt-17-srv/9999) || echo closed
bash: connect: Connection refused
bash: line 1: /dev/tcp/lt-17-srv/9999: Connection refused
closed
# timeout 3 bash -c 'echo > /dev/tcp/192.0.2.1/80'; echo "exit=$?"
exit=124

It has no timeout of its own — wrap it in timeout (124 = timed out). And it is a bash feature only: under sh on Ubuntu (dash) you get cannot create /dev/tcp/…: Directory nonexistent, and on Alpine (BusyBox ash) can't create /dev/tcp/…: nonexistent directory. Alpine's BusyBox does include an nc that accepts -zv. Agents use this trick routinely; now you can read it in a transcript.

Published ports: the host's side of the door

Everything so far was container-to-container. A container's ports are also reachable from the Docker host, but not from beyond it unless published: -p HOST:CONTAINER maps a port on the host to a port in the container. Docker's documentation does not soften the default: "Publishing container ports is insecure by default. Meaning, when you publish a container's ports it becomes available not only to the Docker host, but to the outside world as well"; with a 127.0.0.1: prefix "only the Docker host can access the published container port."[Docker: port publishing] 

$ docker run -d --name web -p 127.0.0.1:18080:8000 -p 18081:8000 lt-net:local python3 -m http.server 8000
$ docker port web
8000/tcp -> 0.0.0.0:18081
8000/tcp -> 127.0.0.1:18080

Three things about this that matter for a sandbox:

  • It is the bind-address question again, one level up. 0.0.0.0:18081 is every interface of the host — including the bridge gateway address. Verified: from an unrelated container, nc -zv 172.17.0.1 18081 succeeded while 172.17.0.1 18080 was refused. A port you published "for yourself" without the 127.0.0.1: prefix is reachable from every sandbox on the host.
  • Host firewalls may not apply. Docker routes published-port traffic in the nat table, so it "gets diverted before it goes through the ufw firewall settings."[Docker: firewalls] A host whose firewall "blocks everything" can still be serving a published port to the network. Page 19 covers where rules must go.
  • Publishing does not change the listener. If the process inside bound 127.0.0.1, the mapping leads to a door nobody opens. Here (Docker Desktop) the symptom was curl: (52) Empty reply from server; the exact symptom depends on how the host forwards the port, but the cause is the one ss -tln inside the container shows.
In eval work · design

Run ss -tulpn on the sandbox host, as root, as part of every environment audit. Every line whose Local Address is 0.0.0.0, *, [::], or a bridge address is a service your agents can reach through the gateway (page 16): a results database, a harness dashboard, another team's published port — or a Docker API. Docker warns that even a firewalled API endpoint "can be still accessible from containers, and it can easily result in the privilege escalation."[Docker: security] That is the o1 incident exactly: the model scanned the challenge network and found "the Docker daemon API running on the evaluation host VM was accessible due to a misconfiguration", then used it to list containers and start a new one with the command cat flag.txt.[o1 System Card] (The card does not say which port or how the scan was run.) One listening socket, on the wrong address, reachable from the wrong network. On Docker Desktop there is an extra door: the name host.docker.internal "resolves to the internal IP address of your host",[Docker Desktop: networking] and through it a container here reached even the port published on the Mac's 127.0.0.1. Sandboxes on a laptop can reach the laptop.

Probing a service the agent started

A grader that connects once, immediately, measures a race: servers take time to start, and "refused" in the first second means "not yet", not "never". The robust pattern is retry until a deadline, with a timeout on every attempt, and a distinct outcome for "never came up": 

#!/usr/bin/env bash
# wait-for-port.sh HOST PORT [DEADLINE_SECONDS] -- exit 0 when HOST:PORT accepts a TCP connection
set -u
host=$1 port=$2 deadline=${3:-30}
start=$SECONDS
while (( SECONDS - start < deadline )); do
  if timeout 2 bash -c "echo > /dev/tcp/$host/$port" 2>/dev/null; then
    echo "open after $(( SECONDS - start ))s"
    exit 0
  fi
  sleep 1
done
echo "still not accepting connections on $host:$port after ${deadline}s" >&2
exit 1
$ bash wait-for-port.sh lt-17-srv 8080 15      # server started 4 s after the probe began
open after 4s
$ bash wait-for-port.sh lt-17-srv 8001 5; echo "exit=$?"   # bound to loopback: never reachable
still not accepting connections on lt-17-srv:8001 after 5s
exit=1

The script is ShellCheck-clean, needs nothing but bash and coreutils, and treats refusals and timeouts alike — deliberately: from the grader's side both mean "not reachable yet".

In eval work · discuss

Failure accounting. A connection error in a grader log is an observation about the run; which column it belongs in depends on the cause, and the symptom table tells you what to check. Refused after the full deadline, and ss shows the agent's server on 127.0.0.1 or not at all → the agent's outcome (given a task statement that made the requirement clear). Timed out, No route to host, or Could not resolve host between the task's own containers → almost always the environment: a sidecar that did not start, a network that was not attached. Record those as infrastructure failures, report completed / scheduled beside correct / completed, and do not let them fall silently into "wrong answer" — or silently out of the denominator. A grader with no retry converts start-up jitter into a flaky score that varies with host load, which rises with concurrency: exactly the kind of noise that gets misread as a difference between models.

Check your understanding

A multi-container benchmark (an app service the agent works in, plus a db service) reports 61% for model A and 54% for model B. Reading failures, you find that 9% of B's rollouts and 2% of A's end with the agent's test command printing could not connect to server: Connection refused for db:5432 in the first minute, after which the agent thrashes and gives up. A colleague says B "is worse at databases". What do you establish first?

Reveal the reasoning

Observed vs supposed. Observed: an instant refusal on a name that resolved. So DNS worked and a route existed; something actively said no. "B is worse at databases" is a hypothesis about the model; the symptom is equally what you would see if db was not listening yet, had crashed, or listened only on its own loopback.

Discriminating evidence. (1) Timing: compare the timestamp of the first refused connection with the db container's log line announcing it is ready to accept connections. If the refusals all precede readiness, it is a start-up race — the harness hands control to the agent before the environment is up. (2) Why would it differ by model? Check whether B's runs were scheduled at higher concurrency or on a busier host (slower db start), and whether B simply issues its first command sooner. Either makes the race bite B more without B being worse. (3) In a live reproduction, docker exec db ss -tln: is 5432 on 0.0.0.0 or 127.0.0.1, and when does the line appear?

Bearing on the score. If it is a race, those rollouts are infrastructure failures: the agent was given a broken environment and partial credit for "should have retried" is a different eval. Report them separately (completed / scheduled), fix the harness to wait for db with a deadline (a Compose healthcheck or the script above) before the agent starts, and rerun. A seven-point gap with a seven-point difference in infrastructure failures is not yet a finding about either model.

Lab

Container lab, run from your Mac's terminal with the lt-net:local image from page 16's lab. Setup — a network, a server container with two web servers, and a client:

$ docker network create lt-ports
$ docker run -d --name lt-srv --network lt-ports -w /tmp lt-net:local sleep 3600
$ docker exec -d lt-srv python3 -m http.server 8000
$ docker exec -d lt-srv python3 -m http.server 8001 --bind 127.0.0.1
$ docker run -d --name lt-cli --network lt-ports lt-net:local sleep 3600

Clean up at the end with docker rm -f lt-srv lt-cli; docker network rm lt-ports.

  1. Reproduce. Run docker exec lt-srv ss -tlpn. For each line say: which process, which port, and who can connect.
    Solution 
    $ docker exec lt-srv ss -tlpn
State  Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
LISTEN 0      4096      127.0.0.11:43993      0.0.0.0:*
LISTEN 0      5            0.0.0.0:8000       0.0.0.0:*    users:(("python3",pid=7,fd=3))
LISTEN 0      5          127.0.0.1:8001       0.0.0.0:*    users:(("python3",pid=13,fd=3))

    8000: python3, any interface — reachable from lt-cli and from the host. 8001: python3, loopback only — reachable only from inside lt-srv. The 127.0.0.11 line is Docker's embedded DNS (random port, no visible process). Your PIDs and that port will differ.

  2. Predict, then verify. From lt-cli you will run curl -sS -m 5 -o /dev/null -w '%{http_code}\n' against http://lt-srv:8000/, http://lt-srv:8001/, and http://localhost:8000/. Write down the three results first.
    Solution

    200; then curl: (7) Failed to connect to lt-srv port 8001 after 0 ms; then curl: (7) Failed to connect to localhost port 8000 after 0 ms. The second is a live server bound to loopback; the third is lt-cli's own localhost, where nothing listens. Confirm the second server is fine: docker exec lt-srv curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8001/ prints 200.

  3. Predict the symptom and its speed. From lt-cli, with -m 5 each time: curl http://lt-srv:9999/, curl http://192.0.2.1/ (an address reserved for documentation — nobody owns it), curl http://no-such-host.invalid/. For each: which error, which exit code, and roughly how long?
    Solution 
    $ curl -sS -m 5 http://lt-srv:9999/; echo "exit=$?"
curl: (7) Failed to connect to lt-srv port 9999 after 1 ms: Couldn't connect to server
exit=7
$ curl -sS -m 5 http://192.0.2.1/; echo "exit=$?"
curl: (28) Connection timed out after 5006 milliseconds
exit=28
$ curl -sS -m 5 http://no-such-host.invalid/; echo "exit=$?"
curl: (6) Could not resolve host: no-such-host.invalid
exit=6

    Refused: instant. Dropped: exactly as long as -m allowed — without -m it would have been about two minutes. Name failure: instant, and a different layer altogether.

  4. No tools. Start a stock image on the same network: docker run --rm -it --network lt-ports ubuntu:24.04 bash. Confirm it has no curl, nc, ss or ip, then determine whether lt-srv ports 8000 and 8001 accept connections.
    Solution 
    # command -v curl nc ss ip; echo "exit=$?"
exit=1
# (echo > /dev/tcp/lt-srv/8000) 2>/dev/null && echo 8000 open
8000 open
# (echo > /dev/tcp/lt-srv/8001) 2>/dev/null || echo 8001 closed-or-filtered
8001 closed-or-filtered

    The honest label is "closed or filtered": from outside you cannot tell a loopback-bound server from no server from a REJECT rule. For an address that might silently drop, wrap the probe in timeout 3 bash -c '…'.

  5. Eval task: the grader says the service is down. A rollout's transcript ends with the agent running its server and printing Serving HTTP on 127.0.0.1 port 8001 (http://127.0.0.1:8001/) ...; the agent verified it with curl localhost:8001 (200). The grader, in another container, recorded Connection refused and scored 0. Using lt-srv (the agent's box) and lt-cli (the grader), gather the evidence for a two-sentence finding: what happened, and whose failure is it?
    Solution

    Evidence: docker exec lt-srv ss -tln shows 127.0.0.1:8001 (exercise 1); from lt-cli, nc -zv -w 3 lt-srv 8001 prints nc: connect to lt-srv (172.20.0.2) port 8001 (tcp) failed: Connection refused; inside lt-srv the same URL returns 200. Finding: "The service was running and correct but bound to loopback, so it was reachable only from inside the agent's container; the grader connects from a separate container and was refused." Whose failure depends on the task text: if it said the service must be reachable from other hosts (or named 0.0.0.0), it is the agent's. If it said only "start the server on port 8001", the requirement lived in the harness, not the task — fix the task statement or grade via docker exec, and re-score affected rollouts rather than reporting them as model failures.
