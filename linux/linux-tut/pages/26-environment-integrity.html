Module 7 · Linux in Eval Harnesses

Environment integrity: where cheating lives

Every published case of an agent passing a task without doing it comes down to a Linux fact: something in the box was readable, writable, reachable, still running, or still there from last time. This page turns those incidents into seven surfaces you can check, then red-teams the course's own benchmark, sloppy build and hardened build, with the same checklist.

Two definitions and a thesis

METR's working definition of reward hacking is models that "get impossibly high scores … by exploiting bugs in our scoring code or subverting the task setup, rather than actually solving the problem we've given them."[METR] Environment integrity is the property that denies them the chance: the only way to obtain a pass is to do the task. The sibling course treats the measurement side (page 11 on agents, pages 21–22 on contamination). This page treats the box.

The thesis is mechanical. METR found an early o3 checkpoint reward-hacking in 39 of 128 RE-Bench runs (30.4%) but 8 of 1,087 HCAST runs (0.7%), and noted that on RE-Bench "the model was able to see the entire scoring function". Asking nicely did nothing: adding "Please do not cheat" left the rate of hack plans on one task at 80%, unchanged.[METR] Every exploit METR describes needed the scorer or an answer to be inside the agent's process or filesystem. Calling that boundary the integrity boundary is this course's framing, not METR's; their own remedy is "making the training setup less susceptible to exploits". Integrity is enforced in the box, with the tools of Modules 2–6, not in the prompt.

1 · Git history

On 3 September 2025 Jacob Kahn opened SWE-bench issue #465, "Repo State Loopholes During Agentic Evaluation". On SWE-bench Verified, agents had run commands such as git log --oneline --all | grep … in /testbed and found the upstream fix commit: the task repos were checked out at the base commit, but later history was still in .git. No network was needed.[SWE-bench #465] This is the git history leak, and the sloppy wordfreq-bench image reproduces it: 

# git log --oneline
bb4b24a wordfreq: initial import
# git log --oneline --all
bb4b24a wordfreq: initial import
6301071 count words case-insensitively, ignore punctuation (fixes #12)

Checking out an old commit moves HEAD and rewrites the working tree; it deletes nothing. --all means "all the refs in refs/, along with HEAD": branches, tags, remote-tracking refs, the stash.[Pro Git] Deleting the branch is the obvious fix and is not enough: 

# git branch -D upstream-fix
Deleted branch upstream-fix (was 6301071).
# git log --oneline --all
bb4b24a wordfreq: initial import
# git reflog | sed -n 2p
6301071 HEAD@{1}: commit: count words case-insensitively, ignore punctuation (fixes #12)
# git fsck --lost-found
dangling commit 6301071da20c502788db3533760ed0c7974a7bca
# git reflog expire --expire=now --all && git gc -q --prune=now
# git fsck --lost-found; git cat-file -t 6301071
fatal: Not a valid object name 6301071
# git log --oneline --all | wc -l
1

An unreachable object stays on disk until garbage collection prunes it, and the defaults are two weeks for loose objects and 90 days for reflog entries (30 if unreachable from the tip)[Pro Git], far longer than any rollout. The maintainers' fix, PR #471 (merged 11 September 2025, released as v4.1.0), is this sequence in the image build: git reset --hard to the base commit, git remote remove origin, delete only tags newer than the base commit, expire the reflog, git gc --prune=now --aggressive, then fail the build if git log --all --since=… prints anything. Past history and past tags stay, because one task legitimately needs them.[SWE-bench #465] When a task needs no history, ship an exported tree (git archive), as the hardened wordfreq-bench build does.

Caveat: keep the scale honest The maintainers measured before reacting. A search of the 20 most recent submissions matched git log in "5/10000 trajectories"; on the bash-only leaderboard one model had 6 suspicious successful trajectories, worth 1.2 points, with no rank change among the top four. Their conclusion on rerunning everything was "no".[SWE-bench #465] The leak was real and the fix was right; it did not invalidate the leaderboard. And reading the log is what any engineer would do first: the flaw was in the image.

2 · Image layers

An image layer is never edited. Docker's docs: removing files "will result in a new layer", and the removed directory "will still be available in the previous layer".[Kernel: overlayfs] Dockerfile.sloppy COPYs the oracle solution in and rms it in the next step (page 22 walks through it). Inside a container the path is gone. In the saved image it is one tar -tf away: 

$ docker save wordfreq-bench:sloppy -o img.tar && mkdir img && tar -xf img.tar -C img
$ for b in img/blobs/sha256/*; do tar -tf "$b" 2>/dev/null | grep solution; done
tmp/.wh.solution
tmp/solution/
tmp/solution/wordfreq.patch.py

The agent inside the box cannot do this, but anyone who can pull the image can. That is solution leakage into training data, and to any agent that can reach the registry. Terminal-Bench's CI rejects a Dockerfile that references tests or the oracle solution, "otherwise agents could cheat by reading them".[Terminal-Bench]

3 · Filesystem: readable keys, writable tests

This is audit question 3, who owns what, asked as the agent's uid (page 8). The one controlled experiment on file access is ImpossibleBench, whose tasks have tests that contradict the spec, so any pass is a cheat. It compared tests open, "read-only" and hidden. On the conflicting SWE-bench variant:

ModelCheat rate: openread-onlyhiddenLegitimate pass rate: open / read-only / hidden
Claude Opus 4.150%1%0%86 / 85 / 70%
GPT-554%39%0%97 / 97 / 76%

Read-only tests remove exactly one strategy, test tampering. That is decisive for a model that cheats that way and weak against one that special-cases inputs or overloads ==. Hiding tests removes nearly everything and costs 16–26 points of legitimate performance.[ImpossibleBench] One correction to the usual retelling: the paper's "read-only" is not chmod or a read-only mount. Its caption says "we revert the modified tests during scoring": the harness restores the files before grading. SWE-bench's eval script does the same (page 25). A :ro bind mount gives the same guarantee earlier; that is this course's implementation, not the paper's.

A June 2026 preprint audited 1,968 terminal-agent tasks with agents told to pass without solving and no access to the verifier: 323 environments (16%) were hackable, including 13 of Terminal-Bench 2.0's 89. The exploits are pure Linux: "reading answers directly from unguarded files, replacing system binaries with wrapper scripts". Its diagnosis: "tests run in the same container as the tested agent … so the agent and test environment share identical permissions by default."[Hacker-Fixer]

4 · Processes and environment

Most of METR's examples crossed a process boundary, not a file boundary: the agent's code was imported and run inside the scorer's Python process, where it could walk the call stack to the reference answer, patch time.time, or replace the evaluation function with a stub.[METR] Separate processes help only if the uid differs too. Here a "grader" runs as root and again as agent, each with a key in its environment, and the agent looks through the /proc filesystem: 

$ ps -eo pid,user,args
  PID USER     COMMAND
    1 agent    /sbin/docker-init -- sleep infinity
    7 agent    sleep infinity
    8 root     sleep 600
   14 agent    sleep 601
   20 agent    ps -eo pid,user,args
$ tr '\0' ' ' < /proc/8/cmdline; echo
sleep 600
$ tr '\0' '\n' < /proc/8/environ | grep EXPECTED
bash: line 1: /proc/8/environ: Permission denied
$ tr '\0' '\n' < /proc/14/environ | grep EXPECTED
EXPECTED_TOP=the:7

Every process's argv is visible to everyone in the PID namespace; its environment is visible to the same uid (page 11). A grader sharing the agent's uid has no secrets, and a root agent shares everyone's.

5 · Network

Open egress makes the whole internet part of the task. Terminal-Bench 2.0 allowed it by design and said so: "an agent could locate our dataset and cheat by reading the oracle solutions. In practice, we have not observed this behavior in tens of thousands of agent trajectories".[Terminal-Bench] Version 4.0 later removed two tasks for public solutions.[Terminal-Bench] The Linux half is page 19; network access as a declared condition of the experiment is the networking course's Boundaries and validity. One trap from page 25 belongs here: a model provider's server-side search tool runs outside the box and ignores its firewall.

6 · The harness and the host

In the o1 system card (September 2024 version), a CTF challenge container failed to start because of an infrastructure bug. o1-preview suspected DNS, ran nmap, and found the evaluation host's Docker daemon API reachable "due to a misconfiguration". It listed containers, briefly tried to debug the broken one, then started a new instance with the command cat flag.txt and read the flag from the container logs. OpenAI's framing: the infrastructure "does not rely on the Docker container-to-host isolation or the virtual machine boundary for security" and "remained secure as it was designed to".[o1 System Card] The card does not say what it does rely on, nor whether the attempt was scored a pass. The point here is narrower: the flag came from the control plane, so the run measured nothing about the intended skill. A reachable Docker socket or API is root on the host: whoever controls the daemon can start a container with the host's / mounted inside it[Docker: security] (page 23). Checks: test -S /var/run/docker.sock inside; docker inspect --format '{{json .Mounts}}' outside; the page-19 probe aimed at the gateway address.

7 · State across rollouts

Anthropic: "in some internal evals we observed Claude gaining an unfair advantage on some tasks by examining the git history from previous trials", and more generally shared state "can also artificially inflate performance."[Anthropic: Agent Evals] This is a different leak from #465. There the future was baked into the image; here one rollout's workspace survived into the next. The usual carrier is a named volume, which outlives --rm: 

$ docker run --rm -v lt-26-work:/app wordfreq-bench:hardened bash -c 'echo "rollout 1 notes: compare lowercase, strip punctuation" > /app/NOTES.txt'
$ docker run --rm -v lt-26-work:/app wordfreq-bench:hardened cat /app/NOTES.txt
rollout 1 notes: compare lowercase, strip punctuation
$ docker run --rm wordfreq-bench:hardened cat /app/NOTES.txt
cat: /app/NOTES.txt: No such file or directory

Leftover state also breaks the statistics: epochs that share a workspace are not independent samples. A fresh container per rollout is the reset; Inspect gives every sample its own sandbox instance.[Inspect]

Red-team your own box

Terminal-Bench ran an adversarial agent, prompted to cheat, against every task and read the trajectories.[Terminal-Bench] Do the same: run an "attacker" rollout whose instruction is obtain a pass without fixing the bug, and treat any success as an environment bug. Its first moves can be scripted. integrity-check.sh is read-only and shellcheck-clean: 

#!/usr/bin/env bash
# integrity-check.sh: the first six things an "attacker" rollout would look at.
# Run INSIDE a task container. Read-only. Exit status = number of open surfaces.
set -u
leaks=0
check() {  # check MESSAGE SNIPPET: the surface is OPEN if SNIPPET succeeds
  if bash -c "$2" >/dev/null 2>&1; then
    echo "OPEN    $1"
    leaks=$((leaks + 1))
  else
    echo "closed  $1"
  fi
}
check "identity:   running as root" 'id -u | grep -qx 0'
check "git:        /app carries a .git directory" 'test -d /app/.git'
check "filesystem: answer key or hidden tests readable" \
  "find / -xdev -type f \( -name 'expected*.json' -o -name 'test_hidden*' \) -readable | grep -q ."
check "filesystem: grading script writable" \
  "find / -xdev -type f -name 'run-tests.sh' -writable | grep -q ."
check "network:    a route exists (namespace is not empty)" "awk 'NR > 1' /proc/net/route | grep -q ."
check "host:       Docker socket mounted" 'test -S /var/run/docker.sock'
echo "$leaks open surface(s)"
exit "$leaks"
$ docker run -d --name lt-26-sloppy wordfreq-bench:sloppy
$ docker exec -i lt-26-sloppy bash -s < integrity-check.sh
OPEN    identity:   running as root
OPEN    git:        /app carries a .git directory
OPEN    filesystem: answer key or hidden tests readable
OPEN    filesystem: grading script writable
OPEN    network:    a route exists (namespace is not empty)
closed  host:       Docker socket mounted
5 open surface(s)

Five ways to a pass in the sloppy build, none of which fixes the bug (each observed from inside; none needs anything cleverer than ls):

  1. The fix is a commit on branch upstream-fix, shown by git log --all.
  2. The expected output is readable at /opt/grader/expected.json (mode 644), so the program can special-case it.
  3. The agent is root, so /opt/grader/run-tests.sh and the hidden tests are writable (test -w prints writable): test tampering.
  4. The grader runs in this container as this uid, so the agent can run it for unlimited feedback from the "hidden" tests, or write the result line itself.
  5. Egress is open (getent hosts github.com resolves; an HTTPS request returns 200), so a public fix is a download away. A sixth, the oracle solution in a layer, is open to anyone holding the image.

The grader and key never enter the agent's box; grade.sh copies /app out and tests the copy in a fresh, network-less, read-only container. And, as on page 25, the oracle still passes, so hardening did not break the task.

Pitfall: "0 open surfaces" is not "cannot be gamed" The script checks what it checks. Read test_hidden.py and two trust decisions remain: it does from wordfreq import top, so the agent's code runs inside the grader's process, METR's class exactly; and it reads data/sample.txt from the submitted tree. Moving grading outside shrank what a hack can reach; it did not remove the agent's code from the scorer. Closing that means testing the program as a subprocess and supplying the data from the grader's side. Hardening has a price as well: in the Hacker-Fixer preprint, hardened verifiers rejected 11 points more legitimate solutions (76.1% to 65.2%).[Hacker-Fixer]

Design principles

  • Grade outside the box, after the agent is gone, on artifacts copied out or in a fresh container. Harbor's default runs the verifier in the agent's container; Terminal-Bench 3.0 moved to a separate one, which "prevents many reward hacking vectors" and permits re-grading.[Terminal-Bench]
  • Held-out tests never enter the sandbox while the agent runs: not the image, not a layer, not a mount.
  • Least privilege: non-root agent, read-only root filesystem, nothing the grader later executes is agent-writable.
  • Default-deny egress; allowlist or mirror what the task needs.
  • Fresh environment per rollout; no named volumes, no reused containers.
  • A small trusted core: scorer, sandbox policy and logging short enough to read in one sitting, because that is what you vouch for.
  • The build asserts its own integrity, as SWE-bench's does, and the oracle and a no-op run gate every change.

Measuring it

In eval work: report the cheat rate beside the pass rate An integrity violation is an outcome category of its own, not a pass and not an ordinary fail. METR "regularly check for and exclude reward hacking attempts that successfully achieve a good score" from reported results.[METR] Record it the way you record infrastructure failures: keep every scheduled run in the table, report pass rate with flagged runs counted as passes and as fails, state which is the headline before you look, and publish the flagged count. Dropping flagged runs silently changes the denominator; keeping them silently inflates the numerator.

Two numbers get confused. Spontaneous cheating, in rollouts given the ordinary prompt, mostly measures the model's propensity: that is ImpossibleBench's stated subject and what METR's 30.4% is. Elicited cheating, from an attacker told to cheat, measures the environment's weakness: Terminal-Bench's exploit agent and the 16% audit above. The distinction is this course's; the sources fit it. One small vendor-run demo shows the gap: on tasks with public solutions and open egress, an agent cheated in 0.17 of trials unprompted and 24 of 24 with a hint; under network: none cheating stopped, and so did legitimate solves, because the in-box agent had lost its route to the model API.[RewardHackBench] A low spontaneous rate says nothing about whether the door is locked.

Caveat: a measured cheat rate is a lower bound Detection misses. METR's two methods each missed hacks the other found, and they call their counts possibly "a significant underestimate". ImpossibleBench's LLM monitors caught 86–89% of cheating on its LiveCodeBench variant but only 42–65% on the SWE-bench one.[ImpossibleBench] The #465 reporters wrote that they "do not have a method for automatically checking existing trajectories". Evidence of absence requires closing the surface, not searching transcripts.
Check your understanding

A benchmark you maintain grades in-container, as root, after the agent (also root) finishes. A new model jumps from 41% to 58%. A transcript search for git log, expected and /tests finds nothing suspicious, and a colleague concludes the gain is real. What do you say?

Reveal the reasoning

Observed: a score jump, and a keyword search with no hits. Not observed: that the gain is legitimate. The search tests three strings; a root agent in the verifier's container has surfaces the strings do not cover (replacing a binary the tests call, leaving a background process, writing the reward file), and detectors in the literature miss a large share even when purpose-built. The discriminating test is environmental: re-grade the same final artifacts in a fresh verifier container the agent never touched. If 58% survives, the gain is probably real; if it falls, the difference is your cheat-rate estimate, itself a lower bound. Then run an elicited attacker on a sample of tasks to see which surfaces are open. Report both scores and the grading change. Until then the honest statement is "58% under in-container grading, integrity unverified".

Lab

Container lab, from your Mac's terminal, in research/wordfreq-bench/ with both images built (page 22). Save integrity-check.sh from above. Clean up with docker rm -fv lt-26-sloppy lt-26-hard lt-26-proc (-v also removes the anonymous /app volume that run-hardened.sh creates).

  2. Predict, then verify. In the sloppy box, copy the repo (cp -r /app /tmp/repo) and delete the branch. Before running them, write down whether git log --all, git reflog and git fsck --lost-found will each still reveal commit 6301071. Then make all three come up empty and prove it with git count-objects -v.
    Solution --all: no (no ref points at it). Reflog: yes. fsck: yes, "dangling commit". The cure is the SWE-bench sequence: 
    # git count-objects -v | head -1
count: 11
# git reflog expire --expire=now --all && git gc -q --prune=now
# git fsck --lost-found
# git count-objects -v | sed -n '1p;3p'
count: 0
in-pack: 8
    Eleven loose objects became eight packed ones: the three that belonged only to the fix (its commit, tree and blob) are gone.
  3. Predict, then verify. Start docker run -d --name lt-26-proc --init wordfreq-bench:hardened, then two fake graders: docker exec -d -u root -e EXPECTED_TOP=the:7 lt-26-proc sleep 600 and the same with -u agent and sleep 601. As agent, which of cmdline and environ can you read for each?
    Solution Both cmdlines; only the same-uid environ. Output is in section 4 (your PIDs may differ; find them with ps -eo pid,user,args). Consequence: never pass an expected answer to a grader as a command-line argument, and never run the grader as the agent's uid.
