Module 7 · Linux in Eval Harnesses

How harnesses drive a sandbox

Every agentic eval framework, however elaborate, talks to its Linux box through one narrow interface: run this argv as this user with this timeout, and hand back an exit code and two streams. This page shows that interface by hand, then reads Inspect, Terminal-Bench and SWE-bench as three sets of decisions about it, each one a Linux mechanism you have already met.

The universal loop

An eval harness is an ordinary program, usually Python, running on a machine you trust. The sandbox is a container or VM you do not trust, because a model decides what runs in it. AISI describe their design the same way: "Inspect itself sits outside of the sandbox and sends commands into it, as requested by the model being tested."[AISI: Sandboxing] Strip away the framework and every rollout is the same seven steps.

HOST (trusted) SANDBOX (untrusted) ┌───────────────────────┐ ┌────────────────────────┐ │ harness process │ 1 create │ container or VM │ │ · model API client ──┼─▶ LLM │ PID 1: sleep / tail │ │ · tool code │ 2 files ──▶│ /app (task repo) │ │ · scorer │ │ │ │ · log writer │ 4 exec ───▶│ argv, user, cwd, env, │ │ │ │ stdin, timeout │ │ │◀── 5 ──────│ exit code, stdout, │ │ │ │ stderr (truncated) │ └───────────────────────┘ └────────────────────────┘ 3 model emits a tool call ─▶ 4 ─▶ 5 ─▶ result goes back to the model as text ─▶ 3 … until it submits or a limit is hit 6 scorer execs checks / reads files 7 teardown (rm -f)

There is no long-lived terminal in this picture, and the model never "logs in". Each tool call is a separate process started from outside. You can play the harness yourself with the Docker CLI and the running example's image (page 22). The commands run on your Mac; everything after the container name runs in Linux. 

$ docker run -d --name lt-25-box --network none --init wordfreq-bench:hardened   # 1 create

$ docker exec lt-25-box id                                                     # 4 exec, 5 result

$ docker exec lt-25-box bash -c 'cd /tmp && export FOO=1 && pwd'

$ docker exec lt-25-box bash -c 'pwd; echo FOO=${FOO:-unset}'

$ docker exec --user root --workdir /tmp --env GREETING=hi lt-25-box bash -c 'id -un; pwd; echo $GREETING'

The second pair is the most common surprise in agent transcripts. The cd and the export happened inside a bash process that exited when the call returned; the next call is a new process starting from the image's WORKDIR with the container's original environment (page 2). The last command shows the four knobs every exec interface has: who (--user, page 7), where (--workdir), with what environment (--env, page 11), and the argv itself.

What comes back is three things, and a harness that drops any of them is blind:

$ docker exec lt-25-box python3 -m unittest discover -s tests >out.txt 2>err.txt; echo "exit=$?"
exit=0
$ wc -c out.txt err.txt
       0 out.txt
      98 err.txt
$ docker exec lt-25-box bash -c 'python3 nosuch.py'; echo "exit=$?"
python3: can't open file '/app/nosuch.py': [Errno 2] No such file or directory
exit=2
$ docker exec lt-25-box timeout 2 sleep 30; echo "exit=$?"
exit=124
$ docker exec lt-25-box timeout -s KILL 2 sleep 30; echo "exit=$?"
exit=137

Python's unittest writes its whole report, including the final OK, to stderr: stdout is zero bytes (page 4). docker exec passes the inner command's exit status through, so 124 and 137 mean exactly what they meant on page 10: timeout gave up, or something was killed with SIGKILL (128 + 9). Files go in over stdin or docker cp, and processes the agent backgrounds outlive the call that started them: 

$ docker exec -i lt-25-box bash -c 'cat > /app/notes.txt' <<< 'written over stdin'   # 2 files in
$ docker exec lt-25-box bash -c 'nohup sleep 300 >/dev/null 2>&1 & echo started'
started
$ docker exec lt-25-box ps -eo pid,ppid,user,args
  PID  PPID USER     COMMAND
    1     0 agent    /sbin/docker-init -- sleep infinity
    7     1 agent    sleep infinity

   97     0 agent    ps -eo pid,ppid,user,args
$ docker diff lt-25-box | grep -v pycache                                       # 6 what changed?

The orphaned sleep 300 was re-parented to PID 1 (page 9) and is still running when the scorer arrives. Each exec'd process shows PPID 0: its real parent is the container runtime, outside this PID namespace (page 20).

Key idea A harness's view of the box is exec(argv, user, cwd, env, stdin, timeout) → (exit code, stdout, stderr) plus read-file and write-file. Everything a framework adds is policy around that call.

Inspect: the interface made explicit

Inspect (the UK AI Security Institute's framework; the sibling course covers it as an eval tool on its page 24) names the interface directly. A tool gets the box with sandbox() and calls: 

async def exec(self, cmd: list[str], input: str | bytes | None = None,
               cwd: str | None = None, env: dict[str, str] = {},
               user: str | None = None, timeout: int | None = None,
               timeout_retry: bool = True, concurrency: bool = True) -> ExecResult[str]

ExecResult has exactly four fields: success, returncode, stdout, stderr.[Inspect] Beside it sit read_file() and write_file() (which creates parent directories). That is the same list you just drove by hand. The tool's Python code runs in the harness process on the host; only what it sends through sandbox() runs in the container. "Sandbox" is a plug-in: Docker is built in, Kubernetes, Proxmox VMs and cloud providers are external packages, and the built-in local provider is, in the docs' words, "no sandbox".[Inspect] Where each sits on the isolation ladder is page 24.

The bash tool is exec-per-call

The standard bash tool has the signature bash(timeout=None, user=None, sandbox=None, background=False). Its implementation runs sandbox.exec(cmd=["bash", "--login", "-c", command], …) and returns stderr followed by stdout as one string. The timeout is in seconds and defaults to none. Each call is a fresh shell, and several bash calls in one model message run concurrently.[Inspect] So FOO=unset above is Inspect's default behaviour too. The stateful alternative is bash_session(), where "the prompt, working directory, and environment variables are all retained across calls."[Inspect] Reading a transcript (page 27) starts with knowing which of the two the agent had.

On a timeout, exec() raises TimeoutError, which Inspect reports to the model as a tool error. By default it also retries timed-out commands (timeout_retry=True); pass False for commands that are not safe to run twice.[Inspect] Inspect also separates expected errors (timeout, permission, decode, output limit), which are handed to the model, from unexpected ones such as losing contact with the container runtime, which fail the sample with an error[Inspect]. That is this course's "model failed" versus infrastructure failure distinction, built in. Above the per-call timeout sit per-sample limits (time_limit is wall-clock); a sample that hits one is still scored, "albeit nearly always as 'incorrect'".[Inspect] So account for them yourself. A limit hit or an errored sample is an observation about the run; report correct/scheduled, correct/completed and completed/scheduled as three numbers, and choose the headline one before looking.

Caveat: silent truncation Inspect caps exec output at 10 MiB and file reads at 100 MiB (overridable with INSPECT_SANDBOX_MAX_EXEC_OUTPUT_SIZE and INSPECT_SANDBOX_MAX_READ_FILE_SIZE). Folklore says both raise an exception. Only read_file() does. In the built-in providers an oversized exec() result is truncated from the front, keeping the tail, and returned as a successful ExecResult.[Inspect] A scorer that parses JSON from a chatty command's stdout can be handed half a document with success=True. The docs' advice: write to a file and fetch it with read_file().

The Docker provider is Compose underneath

With no configuration, Inspect generates a Compose file. The docs only describe it; the source gives it exactly: 

services:
  default:
    image: "aisiuk/inspect-tool-support"
    command: "tail -f /dev/null"
    init: true
    network_mode: none
    stop_grace_period: 1s

Read it as Linux: tail -f /dev/null is a PID 1 that never exits, so the container stays up to be exec'd into; init: true adds a real init for signals and zombies (page 10); network_mode: none is an empty network namespace (page 19); a one-second grace period makes teardown effectively SIGKILL. There are no CPU or memory limits in it; the cpus: 1.0 and mem_limit: 0.5gb people remember are from the docs' example file.[Inspect] A Dockerfile or compose.yaml beside the task is discovered automatically. The agent's box is the service named default (else one marked x-default: true, else the first listed); other services are reached as sandbox("name"). Every sample gets its own sandbox instance, "so samples do not interfere with each other's sandboxes".[Inspect] At most max_sandboxes run at once, by default twice the CPUs available to the eval.[Inspect]

Pitfall: your compose file deletes the network policy "Supplying a custom Compose configuration … replaces the generated configuration rather than extending it, including its network_mode: none. Docker Compose's default is a project-scoped network with outbound Internet access."[Inspect] Add a compose.yaml to set a memory limit and your "offline" benchmark is online unless you wrote that line yourself. The same service, without and then with it: 
$ docker compose -p lt-25-net exec default python3 -c 'import urllib.request as u; print(u.urlopen("http://example.com", timeout=5).status)'
200
$ echo "    network_mode: none" >> compose.yaml && docker compose -p lt-25-net up -d
$ docker compose -p lt-25-net exec -T default python3 -c '…same…' 2>&1 | tail -1
urllib.error.URLError: <urlopen error [Errno -3] Temporary failure in name resolution>
The reverse trap: network_mode: none "applies only to processes inside the container"; tool code, scorers and the model provider keep their network.

A complete task for wordfreq-bench

Two files. The compose file gives the agent the hardened image and adds a second service; the scorer copies the one file under test out of the agent's box, into the grader box, uploads the held-out tests from the host, and execs them there. The hidden tests never enter the agent's container. 

# compose.yaml
services:
  default:                      # the agent's box: sandbox() with no name
    image: wordfreq-bench:hardened
    x-local: true               # built locally; do not try to pull it
    init: true
    command: tail -f /dev/null
    network_mode: none          # a custom compose file must say this itself
    mem_limit: 512m
    cpus: 1.0
    pids_limit: 128
  grader:                       # a second box the agent never touches
    image: wordfreq-bench:hardened
    x-local: true
    init: true
    command: tail -f /dev/null
    network_mode: none
# wordfreq_task.py
from pathlib import Path

from inspect_ai import Task, task
from inspect_ai.agent import react
from inspect_ai.dataset import Sample
from inspect_ai.scorer import CORRECT, INCORRECT, Score, Target, accuracy, scorer
from inspect_ai.solver import TaskState
from inspect_ai.tool import bash
from inspect_ai.util import sandbox

GRADER = Path(__file__).parent / "grader"   # hidden tests live on the host


@scorer(metrics=[accuracy()])
def hidden_tests():
    async def score(state: TaskState, target: Target) -> Score:
        # copy the one file the task is about OUT of the agent's box ...
        submission = await sandbox().read_file("/app/wordfreq.py")
        # ... and INTO a box the agent never had a shell in
        box = sandbox("grader")
        await box.write_file("/tmp/sub/wordfreq.py", submission)
        for name in ("test_hidden.py", "expected.json"):
            await box.write_file(f"/tmp/grader/{name}", (GRADER / name).read_text())
        result = await box.exec(
            ["python3", "-m", "unittest", "discover", "-s", "/tmp/grader", "-p", "test_hidden.py"],
            cwd="/tmp/sub",          # python -m puts the cwd first on sys.path
            env={"APP_DIR": "/app"},  # pristine data file from the image
            timeout=60,
        )
        return Score(
            value=CORRECT if result.success else INCORRECT,
            explanation=f"exit {result.returncode}\n{result.stderr[-800:]}",
        )

    return score


@task
def wordfreq():
    return Task(
        dataset=[Sample(input="Fix the bug in /app/wordfreq.py so that words are counted "
                              "case-insensitively and punctuation is ignored.")],
        solver=react(tools=[bash(timeout=120)]),
        scorer=hidden_tests(),
        sandbox=("docker", "compose.yaml"),
        message_limit=30,
        time_limit=900,
    )
What was and was not executed This task was run for real with inspect_ai 0.3.266 in a Python 3.12 virtual environment, but never against a real model. I ran it with Inspect's built-in mock (--model mockllm/model) and with a short oracle solver that applies the known fix through sandbox().exec(). Results: do-nothing agent 0.000, oracle 1.000. The react loop with a live model is the one path not exercised.

The oracle run earned its keep. My first scorer passed env={"PYTHONPATH": "/tmp/sub"} and no cwd, and the oracle scored 0.000. Inspect's debugging path found it in two minutes: 

$ inspect eval wordfreq_task.py --model mockllm/model --solver oracle.py@oracle --no-sandbox-cleanup
…
│ 1         │ 1     │ inspect-wordfreq-ifwpnc3-default-1 │
│           │       │ inspect-wordfreq-ifwpnc3-grader-1  │
Cleanup all containers  : inspect sandbox cleanup docker
$ docker exec inspect-wordfreq-ifwpnc3-default-1 grep -n "Counter(" /app/wordfreq.py
10:    return Counter(re.findall(r"[a-z]+(?:'[a-z]+)*", text.lower()))

The fix was in the agent's box, and ls showed the copy in the grader box, yet the score explanation showed the buggy output [('The', 3), ('the', 3), ('on', 2)]. The exec had started in the image's WORKDIR, /app, which holds the pristine buggy wordfreq.py, and python3 -m puts the working directory ahead of PYTHONPATH on the import path. The grader was testing its own copy. With a real model that harness bug would have been scored as a model failure. Container names follow inspect-<task>-<random>-<service>-1, and docker compose ls showed one Compose project per sample.[Inspect]

In eval work Run the oracle solution and a do-nothing agent through the full harness before any model: the oracle must score 1 and the no-op must score 0. Terminal-Bench makes both a condition of accepting a task (CI runs the oracle script; a no-op "dummy" agent must fail).[Terminal-Bench] SWE-bench's equivalent is --predictions_path gold; in the 2024 validation the gold patches resolved 2,289 of 2,294 tasks, 99.78%, so even a careful harness is not at 100%.[SWE-bench] Rerun both after every hardening step from page 23.

Terminal-Bench and Harbor: a terminal, then tests

A Terminal-Bench task is five things: an instruction, a Docker image, a set of tests, an oracle solution, and a time limit. Tests check the final container state, not what the agent typed or printed. Its harness since version 2.0 is Harbor, where a task is a directory: instruction.md, task.toml, environment/ (the Dockerfile), solution/solve.sh, tests/test.sh; the test script must write a number to /logs/verifier/reward.txt.[Terminal-Bench]

Two details are routinely misreported. First, the famous tmux mechanism belongs to the reference agent, Terminus 2, not to the harness. The model emits keystrokes, the agent types them with tmux send-keys into a bash --login session inside the container, and reads the screen back with tmux capture-pane. That is a real TTY, so vim, pagers and prompts work, where exec-per-call harnesses hang (page 27). Other agents (Claude Code, Codex CLI, OpenHands) are installed into the container and use their own tools.[Terminal-Bench] Second, "the tests are hidden" is half true. The image may not contain tests or solutions (CI rejects a Dockerfile that references them), and "the tests/ directory is uploaded to the environment at /tests/ after the agent runs". But "by default, the verifier runs in the same container as the agent", where the agent was typically root (an unset agent.user means the image default). Terminal-Bench 3.0 (July 2026) changed this: "We separate the agent container and verifier container."[Terminal-Bench] The task above has the same shape; page 26 explains why.

Harbor's other knobs are this course's modules respelled: network policy is public, no-network or an allowlist, per phase; agent.timeout_sec defaults to no timeout; cpus and memory_mb are a hard limit on Docker but only a request on some cloud providers, so the same task can be capped differently depending on where it runs.[Terminal-Bench]

SWE-bench: images in three layers, grading by patch

SWE-bench's harness (dissected as a benchmark in the sibling course's page 12) moved to Docker in June 2024 because conda environments left evaluation "sensitive to discrepancies originating from different platforms and user-specific configurations".[SWE-bench] Its task images come in three layers: a base image, about 60 environment images shared between instances, and one instance image per task with the repo at the right commit. The README asks for 120 GB of free disk, 16 GB RAM and 8 cores.[SWE-bench]

The agent is not in this harness at all. It receives a patch and, in a fresh instance container, applies it, runs the repo's tests, and parses the log: solved only if every FAIL_TO_PASS and PASS_TO_PASS test is found passing; a missing test counts as a fail; a patch that will not apply scores zero.[SWE-bench] The eval script re-checks-out the named test files and applies the official test patch before running, so edits to those files never reach grading. The current harness reports "instances with errors" and "likely infrastructure failures" separately from unresolved ones,[SWE-bench] and keeps test_output.txt, run_instance.log and the eval.sh it ran under logs/evaluation/: audit question 5, where are the logs, answered by design.

In eval work: five things to find in any benchmark repo Reading an unfamiliar agentic benchmark means locating five decisions. (1) The image definition: a Dockerfile, a compose file, or a registry name, and is it pinned? (2) The exec path: stateless exec, a session, or a TTY, and as which user? (3) Timeouts and limits: per call, per sample, per verifier, and is "none" the default? (4) The network policy, and whether a custom config quietly replaced it. (5) Where grading runs: inside the agent's box or outside, before or after the agent's processes are gone, as which user, reading which files. The first four tell you whether scores are comparable; the fifth tells you whether they are trustworthy.
In eval work: agents that live inside the box When the agent is a whole CLI program installed in the sandbox, it needs to reach a model API, which collides with network_mode: none. Inspect's sandbox_agent_bridge() solves it with the loopback interface: a proxy inside the container listens on localhost:13131, the agent is pointed at it (for example ANTHROPIC_BASE_URL=http://localhost:13131), and requests are relayed to the harness outside. The docs flag the hole this leaves: provider-side tools such as web search execute at the model provider, outside the sandbox, and would bypass the box's egress policy, so the bridge withholds them unless the eval grants them explicitly.[Inspect] "What can the box reach?" includes what the model's own tools can reach for it.
Check your understanding

A team moves a benchmark from Inspect's default sandbox to a custom compose.yaml "to add a memory limit". The pass rate rises four points and fewer samples hit the time limit. The write-up credits the new model checkpoint that shipped the same week. What would you ask before accepting that?

Reveal the reasoning

Observed: two things changed at once, the model and the environment. Hypotheses: (a) the model improved; (b) the custom file dropped network_mode: none, so the agent can now pip install or look things up; (c) the new memory limit differs from the old default (none) and changed which samples die. The discriminating test is cheap: rerun the old checkpoint under the new compose file. If its score also moves, the environment did it. Supporting evidence: docker inspect --format '{{.HostConfig.NetworkMode}}' on a live sample, and a grep of transcripts for network commands that now succeed. For the time-limit shift, ask whether limit hits are counted as incorrect or excluded: report correct/scheduled and completed/scheduled for both runs, so a change in the denominator cannot pass as a change in capability.

Lab

Container lab, driven from your Mac's terminal (the docker commands are the harness; what follows the container name runs in Linux). Setup, using the image built on page 22: docker run -d --name lt-25-box --network none --init wordfreq-bench:hardened. Finish with docker rm -f lt-25-box.

  1. Reproduce. Run the cd /tmp && export FOO=1 call and the follow-up. Then make one call that does change directory, set a variable and use both.
    Solution State lives only inside one process, so put the sequence in one call: 
    $ docker exec lt-25-box bash -c 'cd /tmp && export FOO=1 && pwd && echo FOO=$FOO'
/tmp
FOO=1
    This is why agents under exec-per-call harnesses learn to write cd /app && … at the start of every command.
  2. Predict, then verify. A harness logs only stdout. Before running it, write down how many bytes of docker exec lt-25-box python3 -m unittest discover -s tests it will record.
    Solution Zero. unittest reports on stderr: 
    $ docker exec lt-25-box python3 -m unittest discover -s tests >out.txt 2>err.txt; echo "exit=$?"; wc -c out.txt err.txt
exit=0
       0 out.txt
      98 err.txt
    The exit status is the only trustworthy signal in that log, which is why run-tests.sh on page 6 records it.
  3. Predict, then verify. What will echo $? print after docker exec lt-25-box timeout 2 sleep 30, and after the same with -s KILL? What after docker exec lt-25-box nosuchcmd?
    Solution 124, 137 and 127. The last one is produced by the container runtime, not by a shell, because there was no shell in the argv: 
    $ docker exec lt-25-box nosuchcmd; echo "exit=$?"
OCI runtime exec failed: exec failed: unable to start container process: exec: "nosuchcmd": executable file not found in $PATH: unknown
exit=127
  4. What survives a tool call? Start nohup sleep 300 >/dev/null 2>&1 & in one exec and list processes in the next. Who is its parent, and why does a scorer care?
    Solution 
    $ docker exec lt-25-box ps -eo pid,ppid,user,args
  PID  PPID USER     COMMAND
    1     0 agent    /sbin/docker-init -- sleep infinity
    7     1 agent    sleep infinity
   96     1 agent    sleep 300
   97     0 agent    ps -eo pid,ppid,user,args
    PPID 1: orphaned and adopted by init. Anything the agent leaves running is still running while an in-box scorer executes, with the agent's uid. Grading in a different container, or after the agent's container is stopped, removes that whole class of interference.
  5. Eval task: audit a compose file. A colleague's Inspect task ships this compose.yaml and the README says "runs offline". Prove or disprove it without reading any Python. 
    services:
  default:
    image: wordfreq-bench:hardened
    init: true
    command: tail -f /dev/null
    mem_limit: 512m
    Solution There is no network_mode, and a custom file replaces Inspect's generated one, so Compose's default network applies. Bring it up and test from inside: 
    $ docker compose -p lt-25-net up -d
$ docker compose -p lt-25-net exec default getent hosts example.com
2606:4700:10::ac42:93f3 example.com
2606:4700:10::6814:179a example.com
$ docker compose -p lt-25-net exec default python3 -c 'import urllib.request as u; print(u.urlopen("http://example.com", timeout=5).status)'
200
$ docker inspect --format '{{.HostConfig.NetworkMode}}' lt-25-net-default-1
lt-25-net_default
$ docker compose -p lt-25-net down
    DNS resolves and HTTP returns 200: the box is online. After adding network_mode: none, getent exits 2 with no output and docker inspect prints none. Report it as a validity finding: any score from this task was measured with open egress.
