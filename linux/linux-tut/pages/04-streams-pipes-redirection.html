Module 1 · The Shell

Streams, pipes, and redirection

Every program you run has three numbered channels open before its first line executes, and >, 2>&1 and | are nothing more than the shell re-plugging those channels. A harness reads an agent's commands through the same three channels — so which one an error travelled down decides whether your logs contain the evidence or an empty string.

Three numbered channels

When a process opens a file, the kernel hands back a small integer — a file descriptor, or fd — and the process uses that number for every later read and write. Think of a numbered row of sockets on the back of the process, each with a cable plugged into a file, a terminal, or another program. By convention, three are already plugged in when any program starts: fd 0 is standard input, fd 1 is standard output, fd 2 is standard error.[POSIX] A well-behaved program writes its results to 1 and its complaints — errors, warnings, progress chatter — to 2. It neither knows nor cares what is on the other end of either cable.

You can look at the cables. /proc/self/fd is a directory the kernel fabricates, with one symlink per open descriptor of whichever process reads it (more on /proc on page 9). In the container lab, as learner: 

$ ls -l /proc/self/fd
total 0
lrwx------ 1 learner learner 64 Sep 21 16:26 0 -> /dev/pts/1
lrwx------ 1 learner learner 64 Sep 21 16:26 1 -> /dev/pts/1
lrwx------ 1 learner learner 64 Sep 21 16:26 2 -> /dev/pts/1
lr-x------ 1 learner learner 64 Sep 21 16:26 3 -> /proc/483/fd

All three standard descriptors of that ls process lead to /dev/pts/1: the terminal you are typing into. That is why output and errors both show up on your screen, and why, looking at a screen, you cannot tell them apart. (fd 3 is ls itself holding the directory open in order to list it.) ls did not choose the terminal. It inherited those three cables from its parent, the shell — a child process starts with copies of its parent's open descriptors, a rule page 9 returns to.

Redirection: the shell re-plugs a cable before the program starts

Redirection is the shell taking one of those cables and plugging it in somewhere else before it starts the program. The program runs unmodified; it just finds a different thing on the end of fd 1. 

$ ls -l /proc/self/fd > fds.txt
$ cat fds.txt
total 0
lrwx------ 1 learner learner 64 Sep 21 16:26 0 -> /dev/pts/1
l-wx------ 1 learner learner 64 Sep 21 16:26 1 -> /home/learner/fds.txt
lrwx------ 1 learner learner 64 Sep 21 16:26 2 -> /dev/pts/1
lr-x------ 1 learner learner 64 Sep 21 16:26 3 -> /proc/484/fd

Nothing appeared on screen, because fd 1 no longer led to the screen. Proof that the shell — not the program — opens the file: try redirecting somewhere you are not allowed to write, and read who complains. 

$ echo hi > /etc/motd2
-bash: /etc/motd2: Permission denied

The error comes from bash; echo never ran. The working set of operators is small:

You writeThe shell does, before starting the command
cmd > filePlug fd 1 into file, emptying it first (creating it if needed).
cmd >> filePlug fd 1 into file, appending.
cmd < filePlug fd 0 into file: the program "types" the file's contents.
cmd 2> filePlug fd 2 into file. The number names the descriptor; with no number, > means 1 and < means 0.
cmd 2>&1Plug fd 2 into whatever fd 1 is plugged into right now.
cmd &> fileBash shorthand for > file 2>&1.[Bash Manual]

To watch them work you need a command that writes to both channels at once. Listing one file that exists and one that doesn't does it: 

$ ls /etc/hostname /nope
ls: cannot access '/nope': No such file or directory
/etc/hostname
$ ls /etc/hostname /nope > out.txt
ls: cannot access '/nope': No such file or directory
$ cat out.txt
/etc/hostname
$ ls /etc/hostname /nope 2> err.txt
/etc/hostname
$ cat err.txt
ls: cannot access '/nope': No such file or directory

The second command is the one that surprises people: you redirected "the output" to a file and an error still hit the screen. It was never on fd 1.

Why the order of redirections matters

Bash processes redirections left to right,[Bash Manual] and 2>&1 means "copy where fd 1 points at this moment" — not "tie 2 to 1 forever". Run both orders: 

$ ls /etc/hostname /nope > both.txt 2>&1
$ cat both.txt
ls: cannot access '/nope': No such file or directory
/etc/hostname
$ ls /etc/hostname /nope 2>&1 > wrong.txt
ls: cannot access '/nope': No such file or directory
$ cat wrong.txt
/etc/hostname
> both.txt 2>&1 2>&1 > wrong.txt start: 1 ─▶ terminal start: 1 ─▶ terminal 2 ─▶ terminal 2 ─▶ terminal step 1: 1 ─▶ both.txt step 1: 2 ─▶ (where 1 points:) step 2: 2 ─▶ (where 1 points:) terminal both.txt step 2: 1 ─▶ wrong.txt result: both streams in the file result: errors still on screen

You don't need to memorise "put 2>&1 last". Walk the cables left to right and the answer falls out — including for combinations you have never seen, like 2>&1 >/dev/null in the lab below.

Pitfall

> empties the target file before the command runs — the manual's wording is "if it does exist it is truncated to zero size".[Bash Manual] So reading and writing the same file in one command destroys it:

$ printf 'b\na\n' > names.txt; sort names.txt > names.txt; wc -c names.txt
0 names.txt

By the time sort opened its input, the shell had already emptied it. Agents do this to task files (jq . data.json > data.json) and then spend ten turns confused by an empty file. Write to a temporary name and mv it into place.

/dev/null: the cable to nowhere

/dev/null is a device file that discards whatever is written to it and is always empty when read. cmd 2> /dev/null therefore means "throw the complaints away": 

$ ls /etc/hostname /nope 2> /dev/null
/etc/hostname

It is legitimate when you have decided the errors are noise — find / run as a normal user prints a Permission denied for every directory it cannot enter. It is a bad reflex everywhere else, because stderr is where a program explains why it failed.

In eval work

Harnesses keep the two channels separate, and logs often don't keep both. Inspect's exec() returns an ExecResult with exactly four fields: success, returncode, stdout, stderr.[Inspect] Python's subprocess has the same shape. Here is a six-line model of a harness running an agent's test command in a box where pytest isn't installed:

$ cat harness.py
import subprocess
r = subprocess.run(["bash", "-c", "python3 -m pytest tests/"],
                   capture_output=True, text=True)
print("returncode:", r.returncode)
print("stdout:", repr(r.stdout))
print("stderr:", repr(r.stderr))
$ python3 harness.py
returncode: 1
stdout: ''
stderr: '/usr/bin/python3: No module named pytest\n'

A scorer or log line that records only r.stdout stores an empty string, and a missing package — an environment defect — is filed as "the model's tests failed". And if the agent itself wrote python3 -m pytest tests/ 2>/dev/null, the same run gives stderr: '' too: the agent has hidden the evidence from itself, from you, and from anyone doing error analysis later. When you audit a harness, find the line that stores tool output and check that both streams and the return code reach the transcript. (Inspect's own bash() tool hands the model stderr followed by stdout, as one string.[Inspect])

Pipes: stdout of one program into stdin of the next

A pipe, written |, is a small in-kernel buffer with a write end and a read end. a | b makes the shell create one, plug a's fd 1 into the write end and b's fd 0 into the read end, and start both programs at the same time. You can see it in the fd table: 

$ ls -l /proc/self/fd 2> /dev/null < /etc/hostname | cat
total 0
lr-x------ 1 learner learner 64 Sep 21 16:26 0 -> /etc/hostname
l-wx------ 1 learner learner 64 Sep 21 16:26 1 -> pipe:[145335]
l-wx------ 1 learner learner 64 Sep 21 16:26 2 -> /dev/null
lr-x------ 1 learner learner 64 Sep 21 16:26 3 -> /proc/486/fd

Every cable re-plugged at once: stdin from a file, stdout into a pipe, stderr to nowhere. Notice what a pipe does not touch: fd 2. Errors bypass the pipeline and go wherever stderr already pointed. 

$ ls /etc/hostname /nope | wc -l
ls: cannot access '/nope': No such file or directory
1
$ ls /etc/hostname /nope 2>&1 | wc -l
2

In the first command wc counted one line; the error went round it, straight to the screen. In the second, 2>&1 was applied after the pipe was set up, so "where fd 1 points" was the pipe, and both lines were counted. This is why cmd | grep error so often finds nothing: the errors were never in the pipe. Page 5 builds long pipelines on exactly this plumbing.

A pipeline's exit status is its last command's

Page 2 introduced the exit status. A pipeline runs several commands but reports one number, and by default it is the status of the last command only.[Bash Manual] 

$ false | true; echo $?
0
$ false | true; echo "${PIPESTATUS[*]}"
1 0
$ set -o pipefail; false | true; echo $?; set +o pipefail
1

Bash keeps every stage's status in the array PIPESTATUS. With set -o pipefail, the pipeline instead reports the last (rightmost) command that failed, or zero if none did.[Bash Manual] It is off by default. It entered the POSIX standard only in the 2024 edition, and /bin/sh on Ubuntu 24.04 (which is dash, not bash) still rejects it with Illegal option -o pipefail — so a script that needs it should start #!/bin/bash.[POSIX]

The everyday way this goes wrong involves tee, which copies its stdin both to stdout and to a file[Coreutils] — the natural way to watch a test run and keep a log: 

$ python3 -m pytest tests/ | tee test.log; echo "exit=$?"
/usr/bin/python3: No module named pytest
exit=0
$ cat test.log
$ set -o pipefail; python3 -m pytest tests/ 2>&1 | tee test.log; echo "exit=$?"
/usr/bin/python3: No module named pytest
exit=1

First version: pytest never started, the log file is empty (the error went round the pipe), and the status is 0 because tee was happy. Second version: both streams are in the log and the failure propagates.

In eval work

"Tests passed" with an empty log. A task's test script that ends in pytest … | tee /logs/test.log without pipefail exits 0 whether the tests pass, fail, or never start. A grader keyed on that exit status then passes every rollout. The signature in your results is a pass with no test output — and it is a harness defect, not a model success, so those passes cannot be counted as correct. When you read a benchmark's run-tests.sh (page 6 dissects the course's), look for a pipe on the test command and ask what the script's final status really reflects.

Here-documents, here-strings, and $(…)

Three more ways to plug text into a command. A here-document feeds the following lines, up to a delimiter word, to the command's stdin. Combined with cat > file it is how setup scripts — and agents, which have no text editor — write files: 

$ cat > greet.sh <<EOF
> echo "home is $HOME"
> EOF
$ cat greet.sh
echo "home is /home/learner"
$ cat > greet.sh <<'EOF'
> echo "home is $HOME"
> EOF
$ cat greet.sh
echo "home is $HOME"

The difference is one pair of quotes. With a bare delimiter the shell expands $variables and $(commands) inside the body as it writes; with a quoted delimiter the body is literal.[Bash Manual] A model that writes a Python or shell file through an unquoted <<EOF gets every $ silently rewritten, and the file on disk is not the file in the transcript. Page 27 treats this as a recurring failure mode. A here-string is the one-line version: wc -w <<< "three little words" prints 3.

Command substitution, $(cmd), goes the other way: the shell runs cmd with its fd 1 plugged into a pipe, reads everything, and pastes the text into the command line. Only fd 1: 

$ echo "today is $(date +%F), kernel $(uname -r)"
today is 2026-09-21, kernel 6.10.14-linuxkit
$ out=$(ls /nope); echo "captured: [$out]"
ls: cannot access '/nope': No such file or directory
captured: []
$ out=$(ls /nope 2>&1); echo "captured: [$out]"
captured: [ls: cannot access '/nope': No such file or directory]

Two caveats about what arrives, and in what order

Captured output can be reordered

Programs usually collect output in a memory buffer and write it in batches. The C library's rule: stdout is fully buffered whenever it is not a terminal, while stderr is never fully buffered.[POSIX] Python behaves the same way. So the moment output is captured — which is always, under a harness — the two streams stop being in time order: 

$ cat chatty.py
import sys
print("out: collected 3 tests")
print("err: warning, slow disk", file=sys.stderr)
print("out: 3 passed")
$ python3 chatty.py > run.log 2>&1; cat run.log
err: warning, slow disk
out: collected 3 tests
out: 3 passed
$ python3 -u chatty.py > run.log 2>&1; cat run.log
out: collected 3 tests
err: warning, slow disk
out: 3 passed

The warning was printed second and logged first. python3 -u (or PYTHONUNBUFFERED=1 in the environment — same result when we ran it) turns the buffering off. GNU's stdbuf -oL adjusts C-library buffering for programs that use it; on Python it changed nothing in our run. The consequence for reading transcripts: a traceback appearing before the line that caused it is an artefact of capture, not a clue. And when a process is killed, whatever sat unflushed in its stdout buffer is gone — "the last line of output" understates how far the program got.

Harnesses cap output — and may cut the front

Inspect limits the output of one exec() to 10 MiB. Past that, its built-in sandbox providers do not raise an error: they keep only the trailing part and return a normal, successful-looking result.[Inspect] Ten mebibytes is less than it sounds: 

$ seq 1 2000000 | wc -c
14888896
$ seq 1 2000000 | tail -n 2
1999999
2000000

A scorer that runs a command and parses JSON from its stdout can therefore receive a document with its head missing and no exception to say so. The docs' own advice is to have the command write to a file and fetch that with read_file(), which does raise when its limit is exceeded.[Inspect] For an agent the same limit is a skill test: a model that ends noisy commands in | tail -n 50 or | head keeps its context window and its evidence; one that cats a build log loses both.

head raises a last question: what happens to the program on the left when the reader on the right stops reading? 

$ yes | head -n 2; echo "${PIPESTATUS[*]}"
y
y
141 0

yes prints y forever. When head exits, the read end of the pipe closes, and the kernel sends the writer a signal, SIGPIPE, whose default action is to terminate it.[signal(7)] 141 is 128 + 13, SIGPIPE's number. It is how pipelines shut down cleanly, and it is a preview of page 10, where every exit code above 128 gets decoded this way. It is also a reason pipefail needs care: under it, yes | head "fails".

The first two rows are failures of the run, not observations about the model. Record them as harness or environment defects, keep them in the count of scheduled rollouts, and report them beside the pass rate: correct / scheduled and correct / completed are different quantities, and a rollout whose evidence was thrown away was never validly completed. Page 27 turns this into a coding scheme.

Depth triage. Learn to use: the six operators in the table above, |, pipefail and PIPESTATUS, quoted here-documents, $(…). Recognise when you meet them: exec 3>file and other descriptors above 2, process substitution <(cmd), named pipes. Leave alone: anything that needs those in a script longer than thirty lines — that is Python's job (page 6).

Check your understanding

A colleague's new runner shows model B at 71% on a terminal benchmark, up from 58% under the old runner. The diff is small: the agent's tool now runs each command as bash -c "$cmd" 2>&1 | tail -c 4000 "so the model sees errors and we save tokens". What do you ask in review before anyone quotes the 71%?

Reveal the reasoning

Observed: one change to the tool wrapper; a 13-point rise. Hypotheses: (a) the model genuinely does better because it now sees stderr — under the old runner it may have been shown stdout only and was flying blind; (b) the wrapper changed what the harness sees: the pipeline's status is now tail's, so every tool call "succeeds", and anything keyed on return codes — including a grader that runs the test command through the same wrapper — has started passing failures; (c) both.

Discriminating evidence: where does the pass/fail decision read its exit status — through this wrapper or through a separate path? Re-score a sample of new passes with the grader invoked directly. Count tool calls with non-zero return code before and after: if the count fell to zero, (b) is proven for the tool path. Check for pipefail, or a wrapper that captures ${PIPESTATUS[0]}. Then compare old and new transcripts of the same task to see whether the model's behaviour changed after error text appeared.

Bearing on the score: if grading goes through the wrapper, 71% is not a measurement. If only the agent's view changed, 71% may be the better number and 58% was depressed by a harness defect — which is worth saying in the report, because it changes what the old results mean. Note also that merging the streams before tail -c truncates by bytes from the front: long outputs lose their first lines, where compilers put the first, most useful error.

Lab

Container lab, as learner (su - learner), with python3 installed (apt-get install -y python3 as root). Do not install pytest: its absence is the point.

  1. Run ls -l /proc/self/fd. Then run it as ls -l /proc/self/fd 2> err.txt | cat. Before pressing Enter, write down where 1 and 2 will point.

    Solution 
    $ ls -l /proc/self/fd 2> err.txt | cat
total 0
lrwx------ 1 learner learner 64 Sep 21 16:29 0 -> /dev/pts/0
l-wx------ 1 learner learner 64 Sep 21 16:29 1 -> pipe:[193889]
l-wx------ 1 learner learner 64 Sep 21 16:29 2 -> /home/learner/err.txt
lr-x------ 1 learner learner 64 Sep 21 16:29 3 -> /proc/553/fd

    fd 1 is the pipe to cat; fd 2 is the file. The pipe number will differ on your machine. (If you run this through docker exec without -it, fd 0 shows /dev/null or a pipe instead of a terminal — which is what an agent's commands see.)

  2. Predict the number printed by ls /etc/hostname /nope 2>&1 >/dev/null | wc -l, by walking the cables left to right. Then run it.

    Solution 
    $ ls /etc/hostname /nope 2>&1 >/dev/null | wc -l
1

    The pipe is set up first, so fd 1 starts at the pipe. 2>&1 points fd 2 at the pipe; then >/dev/null moves fd 1 away. Only the error line reaches wc. This is the idiom for "pipe the errors, drop the output".

  3. Predict both numbers, then run: ls /nope | tee l.txt; echo "${PIPESTATUS[*]}". What would echo $? have printed in place of the second command?

    Solution 
    $ ls /nope | tee l.txt; echo "${PIPESTATUS[*]}"
ls: cannot access '/nope': No such file or directory
2 0

    ls failed with 2, tee succeeded with 0, and $? would have been 0 — the last command's. l.txt is empty: the error never entered the pipe.

  4. Write a file greet.sh containing the literal text echo "home is $HOME" using cat and a here-document. Check with cat greet.sh that the $HOME survived.

    Solution

    Quote the delimiter: cat > greet.sh <<'EOF', then the line, then EOF on its own line. With a bare EOF the file contains echo "home is /home/learner" instead (both shown in the here-documents section).

  5. Eval task. A benchmark reports every rollout of one task as passed, with empty test logs. Its test script is below. Create it, run it, and confirm it exits 0 although no test ran. Name the two separate mechanisms that hide the failure, then fix the script so the log holds the error and the exit status is the tests' status.

    #!/bin/bash
python3 -m pytest tests/ 2>/dev/null | tee /tmp/test.log
echo "tests finished"
    Solution 
    $ chmod +x run-tests.sh; ./run-tests.sh; echo "exit=$?"
tests finished
exit=0

    Mechanism one: 2>/dev/null discards the only message (No module named pytest). Mechanism two: the script's status is that of its last command, echo — and even without the echo it would be tee's, not pytest's. The fix (shellcheck-clean):

    #!/bin/bash
set -o pipefail
python3 -m pytest tests/ 2>&1 | tee /tmp/test.log
status=$?
echo "tests finished with status $status"
exit "$status"
    $ ./run-tests-fixed.sh; echo "exit=$?"
/usr/bin/python3: No module named pytest
tests finished with status 1
exit=1

    For the write-up: those "passes" were never measurements of the model. They are environment defects (pytest missing from the image) masked by a test-script defect, and the task's results should be withdrawn, not averaged in.
