Module 3 · Processes

Processes: what is running

Everything that happens on a Linux box happens inside a process, and every process has exactly one parent. That tree is the model; ps is just the command that prints it. This page answers the first question of the ten-minute audit — what is running? — and shows why "the agent started a server" is a claim about the process tree that you can check.

A program is a file; a process is a running instance

/usr/bin/python3 is a program: bytes on disk. Run it three times and you have three processes: three independent running instances, each with its own memory, its own open files, its own working directory, its own copy of the environment, and an identity (the uid from page 7). The kernel gives each one a number, the PID, and records which process created it: the parent, whose PID shows up as PPID. Follow the PPIDs upward and every process leads back to PID 1. That is the process tree.

In the container lab from page 1, open a second terminal as the non-root user (docker exec -it -u learner lt-lab bash), start something slow in the background, and look: 

$ echo $$                     # $$ = the PID of this shell
15
$ sleep 300 &
[1] 23
$ ps -ef --forest
UID        PID  PPID  C STIME TTY          TIME CMD
learner     15     0  0 16:29 pts/1    00:00:00 bash
learner     23    15  0 16:29 pts/1    00:00:00  \_ sleep 300
learner     24    15  0 16:29 pts/1    00:00:00  \_ ps -ef --forest
root         1     0  0 16:29 pts/0    00:00:00 bash
$ pstree -p $$
bash(15)-+-pstree(26)
         `-sleep(23)

Your shell (15) is the parent of both sleep and the ps that printed the listing (ps always catches itself). PID 1 is the bash that docker run started. -e means every process, -f the "full" columns, --forest draws the indentation; pstree (package psmisc) is the compact version.

If you're wondering why your shell's PPID is 0

A process started by docker exec has a parent that lives outside the container, where the container's ps cannot see, so the kernel reports PPID 0 (and plain pstree -p, which draws the tree under PID 1, prints only bash(1)). On a VM, your shell's ancestry runs through sshd up to PID 1. The mechanism behind this restricted view is the PID namespace, on page 20.

Where processes come from: fork, exec, wait, exit

Linux has no "start a program" operation. There are two smaller ones, and every process you will ever see was made with them (fork and exec):

  • fork duplicates the calling process. The child is "an exact duplicate" of the parent apart from a short list of differences — its own PID, its parent's PID as PPID — and it receives copies of the parent's open file descriptors.[fork(2)]
  • exec replaces the program running inside a process with a different one. The man page is blunt about a common misreading: "there is no new process; many attributes of the calling process remain unchanged (in particular, its PID)". File descriptors stay open across it unless marked close-on-exec.[execve(2)]
  • exit ends the process and leaves one small number behind, the exit status; wait is how the parent collects it.[wait(2)] What those numbers mean is page 10.
bash (PID 15) when you type: ls -l │ ├─ fork() ───────────▶ bash (PID 27) a copy: same fds, env, │ │ cwd, uid, limits │ │ exec("/usr/bin/ls") │ ▼ │ ls (PID 27) same process, new program │ │ │ wait() … blocked │ exit(0) ◀──── status 0 ──────────┘ │ prompt returns; $? is 0

You can watch both halves. A child has its own PID and knows its parent; exec changes the program but not the PID:

$ bash -c 'echo "child: I am $$, my parent is $PPID"'
child: I am 27, my parent is 15
$ bash -c 'echo "before exec: $$"; exec ps -o pid,ppid,comm -p $$'
before exec: 28
  PID  PPID COMMAND
   28    15 ps

PID 28 was bash when it printed the first line and ps when it printed the table. The split explains inheritance: whatever you set up in a shell — directory, exported variables, redirections, limits, identity — is copied by fork and survives exec, so the program you launch simply finds it there. 

$ cd /tmp; export COLOUR=plum; ulimit -Sn 512
$ bash -c 'pwd; echo $COLOUR; ulimit -Sn; id -un'

A process's starting conditions are its parent's, copied. So "why did the agent's command see that variable / run as root / write to that file?" is always answered by walking up the tree to whoever set it.

Reading ps and top

ps has two dialects you will meet in every transcript, because it accepts both Unix options (with a dash) and BSD options (without).[ps(1)] ps -ef gives you PPID but no memory or state; ps aux gives memory and state but no PPID. Here is aux with a small web server running in the background: 

$ cd /tmp; python3 -m http.server 8000 >/tmp/server.log 2>&1 &
[1] 30
$ ps aux
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root         1  0.0  0.0   4296  3488 pts/0    Ss+  16:29   0:00 bash
learner     15  0.0  0.0   4816  3936 pts/1    Ss   16:29   0:00 bash
learner     30  5.9  0.2  25744 18460 pts/1    S    16:29   0:00 python3 -m http
learner     32  0.0  0.0   7628  3532 pts/1    R+   16:29   0:00 ps aux

The state letters, from the man page: R running or runnable, S interruptible sleep (waiting for something — the normal state of nearly everything), D uninterruptible sleep (usually I/O), T stopped by a job-control signal, Z defunct ("zombie"). Modifiers: s session leader, + in the foreground process group, l multi-threaded, </N high/low priority.[ps(1)] So Ss+ on PID 1 reads: sleeping, session leader, foreground of its terminal.

The default columns rarely answer the question you have. Ask for the ones you want with -o; this is the form worth memorising: 

$ ps -eo pid,ppid,user,stat,rss,etime,time,args
  PID  PPID USER     STAT   RSS     ELAPSED     TIME COMMAND
    1     0 root     Ss+   3488       00:01 00:00:00 bash

   30    15 learner  S    18460       00:01 00:00:00 python3 -m http.server 8000
   33    15 learner  R+    3468       00:00 00:00:00 ps -eo pid,ppid,user,stat,r

top is the live view (htop is a friendlier one, rarely installed). Both are full-screen programs that a non-interactive tool call cannot drive, so in scripts and agent transcripts you will see the batch form top -bn1.[top(1)] Read the header before the table: 

$ top -bn1 | head -5
top - 16:29:41 up  4:53,  0 user,  load average: 1.08, 1.05, 0.68
Tasks:   5 total,   1 running,   4 sleeping,   0 stopped,   0 zombie

Line 2 counts tasks by state, including zombies. Line 3 splits CPU time: us user programs, sy kernel, id idle, wa waiting for I/O, st stolen by a hypervisor.[top(1)]

Caveat — the header is not about your container

The task list is the container's, but the memory and load lines are the whole machine's. This lab container was started with --memory 1g and top still reports 7837 MiB. Tools that read /proc do not see cgroup limits; the real budget is in /sys/fs/cgroup (page 12).

To find processes by name rather than by eye, use pgrep (and its sibling pkill, which signals what pgrep would list). One rule saves an hour of confusion: the name it matches is the process name, limited to 15 characters; to match the whole command line you need -f.[pgrep(1)] 

$ pgrep -a python
30 python3 -m http.server 8000
$ pgrep http.server; echo "rc=$?"
rc=1
$ pgrep -f http.server; echo "rc=$?"
30
rc=0

ps is just a /proc reader

Where does ps get all this? From the /proc filesystem: the kernel presents every process as a directory, /proc/PID/, whose files are generated when you read them. Take the server (PID 30): 

$ tr '\0' ' ' < /proc/30/cmdline; echo       # arguments are NUL-separated
python3 -m http.server 8000
$ ls -l /proc/30/cwd /proc/30/exe
lrwxrwxrwx 1 learner learner 0 Sep 21 16:29 /proc/30/cwd -> /tmp
lrwxrwxrwx 1 learner learner 0 Sep 21 16:29 /proc/30/exe -> /usr/bin/python3.12
$ ls -l /proc/30/fd
total 0
lrwx------ 1 learner learner 64 Sep 21 16:29 0 -> /dev/pts/1
l-wx------ 1 learner learner 64 Sep 21 16:29 1 -> /tmp/server.log
l-wx------ 1 learner learner 64 Sep 21 16:29 2 -> /tmp/server.log
lrwx------ 1 learner learner 64 Sep 21 16:29 3 -> 'socket:[191132]'
$ grep -E '^(Name|State|PPid|Uid|VmRSS)' /proc/30/status
Name:	python3
State:	S (sleeping)
PPid:	15
Uid:	1001	1001	1001	1001
VmRSS:	   18460 kB

Four files answer four questions about any process: what is it really? (exe — the binary, whatever the name claims), where is it working? (cwd), what is it holding open? (fd/: here the redirection to server.log from page 4, made visible, plus the listening socket of page 17), and who is it? (status). The fifth, environ, holds the environment the program was started with and gets page 11 to itself.

Access is uneven, and the unevenness matters. cmdline and status are readable by every user on the box; environ, cwd and fd/ are not: 

$ tr '\0' ' ' < /proc/1/cmdline; echo
bash
$ cat /proc/1/environ
cat: /proc/1/environ: Permission denied
In eval work — navigate

When ps is missing, /proc is not. Plenty of task images are built on slim bases with no procps. On debian:bookworm-slim, docker run --rm debian:bookworm-slim ps -ef fails with exec: "ps": executable file not found in $PATH and exit 127, and Alpine's BusyBox ps ignores -ef and prints only PID USER TIME COMMAND. An agent that concludes "nothing is running" from a failed ps is wrong, and so is an auditor. This loop needs nothing but a shell:

$ for p in /proc/[0-9]*; do echo "${p#/proc/} $(tr '\0' ' ' < "$p/cmdline")"; done
1 bash
15 bash
30 python3 -m http.server 8000

One limit on what it proves: cmdline is, in the man page's words, "the command line that the process wants you to see" — a process can rewrite it.[proc_pid_cmdline(5)] exe is the stronger evidence of what a process is.

Foreground, background, and what survives

A command normally runs in the foreground: the shell forks it and waits. Ending the line with & makes it a background process: the shell forks it, prints a job number and the PID, and gives you the prompt back. Job control is the shell's bookkeeping for moving work between the two. Ctrl+Z stops the foreground job (state T), bg resumes it in the background, fg brings a job to the foreground, and Ctrl+C interrupts whatever is in the foreground: 

$ sleep 600 &
[1] 59
$ sleep 700
^Z
[2]+  Stopped                 sleep 700
$ jobs -l
[1]-    59 Running                 sleep 600 &
[2]+    60 Stopped                 sleep 700
$ bg %2
[2]+ sleep 700 &
$ fg %1
sleep 600
^C
$ echo "rc=$?"
rc=130

Those keystrokes are signals sent by the terminal, and the 130 is how the shell reports a death by one (page 10). jobs is per-shell bookkeeping; for a whole-box view you need ps.

What happens to background jobs when their terminal goes away? The shell receives a hangup signal (SIGHUP), and "before exiting, an interactive shell resends the SIGHUP to all jobs, running or stopped";[Bash Manual] the default action of SIGHUP is to terminate. Two tools opt a job out: nohup cmd & starts the command ignoring SIGHUP, and disown removes a job from the shell's table so the shell never forwards the signal. To see it, this script opens a terminal with tmux, starts three background jobs in it, and closes it: 

#!/bin/bash
# Three background jobs in a terminal; then the terminal goes away.
tmux new-session -d -s demo
tmux send-keys -t demo 'sleep 800 &' Enter
tmux send-keys -t demo 'nohup sleep 900 >/dev/null 2>&1 &' Enter
tmux send-keys -t demo 'sleep 1000 & disown' Enter
sleep 1
ps -o pid,ppid,stat,args -C sleep
tmux kill-session -t demo
sleep 1
echo '--- after the terminal closed:'
ps -o pid,ppid,stat,args -C sleep
$ /tmp/hup-demo.sh
  PID  PPID STAT COMMAND
   97    90 S    sleep 800
   99    90 S    sleep 900
  100    90 S    sleep 1000
--- after the terminal closed:
  PID  PPID STAT COMMAND
   99     1 S    sleep 900
  100     1 S    sleep 1000

The plain & job died with its terminal; the other two survived — and their PPID changed from 90 to 1. Hold that thought for the next section. A daemon is this idea made permanent: a long-running process with no terminal at all (TTY shows ?), such as sshd or dockerd. On a real machine daemons are started and supervised by systemd (page 13); in a container, usually nothing supervises anything.

Pitfall — "&" does not mean the tool call returns

A harness that runs a command and captures its output is reading a pipe until every process holding the write end has closed it. A background child inherits that pipe as its stdout. So the call does not return when the shell exits; it returns when the last inheritor does. This is a 12-line stand-in for a harness tool call, run for real:

import subprocess, time

def tool_call(cmd, timeout=5):
    """What a harness does: run one command, capture both streams."""
    t0 = time.time()
    try:
        r = subprocess.run(["bash", "-c", cmd], capture_output=True,
                           text=True, timeout=timeout)
        out = f"exit={r.returncode} stdout={r.stdout!r}"
    except subprocess.TimeoutExpired:
        out = "TIMEOUT"
    print(f"{time.time() - t0:4.1f}s  {out}  <- {cmd}")

tool_call("sleep 3 & echo started")
tool_call("sleep 3 >/dev/null 2>&1 & echo started")
tool_call("sleep 30 & echo started")
$ python3 /tmp/toolcall.py
 3.0s  exit=0 stdout='started\n'  <- sleep 3 & echo started
 0.0s  exit=0 stdout='started\n'  <- sleep 3 >/dev/null 2>&1 & echo started
 5.0s  TIMEOUT  <- sleep 30 & echo started
$ ps -o pid,ppid,stat,etime,args -C sleep
  PID  PPID STAT     ELAPSED COMMAND
  114     1 S          00:05 sleep 30

The first call blocked for the background job's whole life. The second returned at once because the job's output was redirected away from the pipe — a correct background launch is cmd >log 2>&1 &. The third timed out, the timeout killed the shell, and the sleep is still there, re-parented to PID 1: a timed-out tool call can leave its children running.

Zombies, orphans, and the job of PID 1

Two things can go wrong at the end of the fork–wait cycle, and they are opposites.

An orphan is a live process whose parent has died. It cannot be left parentless — someone must eventually collect its exit status — so the kernel re-parents it to the init process of its PID namespace, PID 1 (or to a nearer ancestor that has volunteered as a "subreaper").[pid_namespaces(7)] That is the PPID 90 → 1 change you just saw, and the fate of the sleep 30 above. Orphans are normal; every daemon is one on purpose.

A zombie is the reverse: a process that has exited but whose parent has not yet called wait. The program is gone — its memory and open files are released — but the kernel keeps "a minimal set of information about the zombie process (PID, termination status, resource usage information)" so that the parent can still ask for it.[wait(2)] Here is one, made with ten lines of Python whose parent forks and then refuses to wait: 

import os, time

pid = os.fork()            # from here on there are two processes
if pid == 0:
    os._exit(7)            # the child: exits at once with status 7
print(f"parent {os.getpid()} made child {pid} and is not calling wait()")
time.sleep(60)             # the parent: alive, but never collects the status
$ python3 /tmp/zombie.py &
[1] 117
parent 117 made child 119 and is not calling wait()
$ ps -o pid,ppid,stat,args
  PID  PPID STAT COMMAND
   78     0 Ss   bash
  117    78 S    python3 /tmp/zombie.py
  119   117 Z    [python3] <defunct>
  120    78 R+   ps -o pid,ppid,stat,args
$ kill -9 119; echo "rc=$?"; ps -o pid,stat,args -p 119
rc=0
  PID STAT COMMAND
  119 Z    [python3] <defunct>

You cannot kill a zombie: it is already dead, and kill -9 "succeeds" without effect. What removes it is its parent calling wait — or its parent dying, at which point the zombie is adopted by init, and "init automatically performs a wait to remove the zombies".[wait(2)] Kill the parent (kill %1) and both rows vanish. A zombie costs almost nothing — but not nothing: each one "will consume a slot in the kernel process table, and if this table fills, it will not be possible to create further processes".[wait(2)] In a container with a --pids-limit, that table is small.

So PID 1 has a job: adopt orphans and reap them. A real init such as systemd does it. In a container, PID 1 is whatever command the image runs, and most programs were never written to reap children that are not theirs. Run the same command twice — it orphans a one-second sleep, then becomes a long sleep as PID 1 — the second time with Docker's --init flag, which puts a tiny init (docker-init, backed by tini) at PID 1 to do "the usual responsibilities of an init system, such as reaping zombie processes":[Docker: run] 

$ docker run -d --name lt-z1 ubuntu:24.04 sh -c '(sleep 1 &); exec sleep 120'
$ docker run -d --init --name lt-z2 ubuntu:24.04 sh -c '(sleep 1 &); exec sleep 120'
$ docker exec lt-z1 ps -eo pid,ppid,stat,args
  PID  PPID STAT COMMAND
    1     0 Ss   sleep 120
    8     1 Z    [sleep] <defunct>
    9     0 Rs   ps -eo pid,ppid,stat,args
$ docker exec lt-z2 ps -eo pid,ppid,stat,args
  PID  PPID STAT COMMAND
    1     0 Ss   /sbin/docker-init -- sh -c (sleep 1 &); exec sleep 120
    7     1 S    sleep 120
   10     0 Rs   ps -eo pid,ppid,stat,args

Without an init, the zombie stays for the life of the container, and an agent that launches many short-lived background commands accumulates them. The other half of the PID 1 problem — that it shrugs off signals — is on page 10.

What ps shows inside a container

On a VM, ps -ef runs to many lines: systemd at PID 1, kernel threads in square brackets, daemons, login sessions. Inside a container it is startlingly short: 

$ docker run --rm ubuntu:24.04 ps -ef
UID        PID  PPID  C STIME TTY          TIME CMD
root         1     0  0 16:31 ?        00:00:00 ps -ef

One process, and it is PID 1; nothing was "booted". Container processes are ordinary processes on the host, shown to themselves through a restricted view: from the host side, docker top lt-z2 listed the same two processes as PIDs 61490 and 61503. One consequence is a gift to eval engineering: when PID 1 of a PID namespace exits, the kernel kills every other process in the namespace with SIGKILL.[pid_namespaces(7)] Removing a container therefore removes every process the agent ever started, however well hidden. A bare VM or a shared host gives you no such guarantee. Page 20 takes the mechanism apart.

In eval work — design

Leftover processes are shared state. Anthropic's guidance on agent evals asks that each trial be "isolated" by starting from a clean environment, because "unnecessary shared state between runs (leftover files, cached data, resource exhaustion) can cause correlated failures due to infrastructure flakiness rather than agent performance".[Anthropic: Agent Evals] Processes are the form of shared state people forget. In a container reused across two rollouts, the first agent's server is still there when the second agent starts its own:

$ docker exec -u learner lt-lab bash -c 'cd /tmp; python3 -m http.server 8000 2>&1 | tail -1'
OSError: [Errno 98] Address already in use
$ docker exec lt-lab ps -eo pid,ppid,user,etime,args
  PID  PPID USER         ELAPSED COMMAND
    1     0 root           01:52 bash
  158     1 learner        00:01 python3 -m http.server 8000

The second rollout fails on a port, not on the task — or, worse, passes because the grader's probe is answered by the first rollout's server. Design: a fresh container per rollout (page 22). Audit: ps -ef --forest in a fresh sandbox should show PID 1 and nothing you cannot explain.

In eval work — discuss

What happens to the agent's background server depends on the harness, and you should know which you have. Inspect's bash() tool runs each call in a fresh shell, and its documentation notes that "a detached process keeps running between bash() calls" — and that its background=True option only changes the tool's description to suggest nohup … & and polling.[Inspect] A harness that drives a persistent terminal instead (page 25) keeps jobs alive as long as that terminal lives. Either way, two rules follow. A verifier that needs the agent's service must check the process and probe the port, never trust the transcript's "Server started": the outcome is the state of the environment, not what the agent says about it.[Anthropic: Agent Evals] And a grader process that runs inside the sandbox as the agent's user is itself a row in the agent's ps output, with a readable command line (page 26).

Check your understanding

A web-app benchmark reuses one long-lived container per task to save start-up time, running git reset --hard && git clean -fdx between rollouts. Its pass rate is 71%. A colleague moves it to a fresh container per rollout and the pass rate falls to 64%. They propose reverting, "since the new setup clearly breaks tasks". What would you want to establish before agreeing?

Reveal the reasoning

Observed: two numbers under two reset policies. Hypotheses: (a) the fresh setup is broken — slower start, a missing warm cache, so more timeouts; (b) the old setup was inflated — git clean resets files, not processes, so a server left running by an earlier, successful rollout could answer the grader's probe for a later rollout that never got its own server working. Shared state "can also artificially inflate performance", in Anthropic's words. Both are plausible; neither is proven by the numbers.

Discriminating evidence: in the old setup, run ps -eo pid,ppid,user,etime,args at the start of a rollout. Any process whose ELAPSED exceeds the rollout's age is leaked state. Then take rollouts that passed in the old setup and check whether the listening process at grading time was started during that rollout (its start time against the rollout's first timestamp). In the new setup, look at how the extra failures ended: if they are timeouts during environment start-up, that is an infrastructure outcome to fix and to count separately, not a reason to bring the shared state back.

Bearing on the score: if (b) holds, 71% was never a measurement of the model — and the rollouts were not independent, so its error bar was wrong as well. The fresh container is the valid instrument even if its number is less flattering.

    kill -9 <zombie> returns 0 and changes nothing: there is no program left to kill. Kill the parent (kill %1); the zombie is adopted by PID 1. In this lab PID 1 is bash, which does reap, so the row vanishes — as it did in the session shown on this page. If PID 1 were sleep, it would not.

  5. Eval task: the agent says the server is up. The transcript's last tool call is below. It exited 0 and printed Server started on port 8000; the grader's HTTP probe then failed. Reproduce it, and establish from the box — not from the transcript — what happened. 
    cd /tmp
python3 -m http.server 8000 --bind 10.9.9.9 >/dev/null 2>&1 &
echo "Server started on port 8000"
    Solution 
    $ pgrep -af http.server; echo "rc=$?"     # typed immediately after
216 python3 -m http.server 8000 --bind 10.9.9.9
rc=0
$ python3 -c 'import urllib.request as u; print(u.urlopen("http://127.0.0.1:8000/", timeout=3).status)' 2>&1 | tail -1
urllib.error.URLError: <urlopen error [Errno 111] Connection refused>
[1]+  Exit 1                  python3 -m http.server 8000 --bind 10.9.9.9 > /dev/null 2>&1
$ python3 -m http.server 8000 --bind 10.9.9.9 2>&1 | tail -1
OSError: [Errno 99] Cannot assign requested address

    The echo ran unconditionally; it reports that a line of the script was reached, not that a server exists. The server died within a fraction of a second (the box has no address 10.9.9.9) and its error went to /dev/null. Notice the trap in the first command: a process check made immediately after launch can still catch the doomed process alive. A sound check waits and then probes the port — and an in-script pgrep -f needs care, because bash -c 'pgrep -af http.server' matches its own command line (we got 222 bash -c pgrep -af http.server…, rc=0, with no server running); pgrep -af '[h]ttp.server' avoids the self-match and correctly returned rc=1. For scoring, this is a genuine agent failure, but one you can only classify correctly because you looked at the process table rather than the agent's claim.
