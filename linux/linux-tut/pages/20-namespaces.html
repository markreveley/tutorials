Module 6 · Containers & Isolation

Namespaces: what a container really is

"Container" sounds like a thing. On Linux it is a recipe: an ordinary process, started with a restricted view of the system. This page builds that view by hand, one namespace at a time, so that "what can the agent see?" becomes a question you answer by reading numbers out of /proc rather than by trusting the word "sandbox".

A container is a process with four things done to it

Here is this course's framing, and it is a framing rather than a quotation: the kernel has no object called a container. Look through the kernel interfaces in this module and you will find namespaces, cgroups, capabilities, seccomp filters and mounts — and no "create container" call. What the primary sources do say fits that reading. The Linux manual: "One use of namespaces is to implement containers."[namespaces(7)] The Open Container Initiative's runtime specification defines a container as "An environment for executing processes with configurable isolation and resource limitations. For example, namespaces, resource limits, and mounts are all part of the container environment."[OCI Runtime Spec] Docker's beginner docs: "A container is simply an isolated process with all of the files it needs to run."[Docker: what-is-a-container] And its security page: "When you start a container with docker run, behind the scenes Docker creates a set of namespaces and control groups for the container."[Docker: security]

an ordinary process (bash, python, the agent's shell) │ ┌──────────────────┬───────────────┴──┬───────────────────┐ │ (a) NAMESPACES │ (b) CGROUPS │ (c) ROOT │ (d) REDUCED │ a restricted │ a restricted │ FILESYSTEM │ PRIVILEGE │ VIEW: which PIDs,│ BUDGET: memory, │ a different "/" │ capabilities, │ mounts, network, │ CPU, number of │ unpacked from │ seccomp, LSM, │ hostname exist │ processes │ an image │ no_new_privs ├──────────────────┼──────────────────┼───────────────────┼────────────── │ this page │ page 21 │ this page, 14, 22 │ page 21 └──────────────────┴──────────────────┴───────────────────┴────────────── all of it enforced by ONE shared kernel (page 24)

The practical pay-off of dissolving the word: each ingredient can be inspected separately, and each can be missing separately. A task definition that says pid: host has quietly removed one wall while the thing is still called a container.

Namespaces: the kernel's eight views

A namespace "wraps a global system resource in an abstraction that makes it appear to the processes within the namespace that they have their own isolated instance of the global resource."[namespaces(7)] Global resource means things like "the list of process IDs" or "the hostname": normally there is one per machine, held by the kernel. There are exactly eight types:[namespaces(7)]

The last column is not from a man page; it is what two running default containers show, below, and it matches Docker's statement that user namespaces are "available but not enabled by default."[Docker: security] Every process is always in one namespace of each type. "Not in a container" just means "in the initial ones".

Reading a process's namespaces

Each process has a directory /proc/PID/ns of symbolic links, one per type. The link text is type:[inode number], and the number is the namespace's identity. Set up this page's lab first — a throwaway container with full privileges, because creating namespaces needs a capability that default containers lack (more below). Never use --privileged for a task container; here it is your workbench. 

$ docker run -d --name lt-ns --privileged --hostname lab ubuntu:24.04 sleep infinity
$ docker exec lt-ns bash -c 'apt-get update -qq && apt-get install -y -qq --no-install-recommends procps iproute2 iputils-ping'
$ docker exec -it lt-ns bash
# ls -l /proc/self/ns
total 0
lrwxrwxrwx 1 root root 0 Sep 21 16:27 cgroup -> cgroup:[4026532963]
lrwxrwxrwx 1 root root 0 Sep 21 16:27 ipc -> ipc:[4026532961]
lrwxrwxrwx 1 root root 0 Sep 21 16:27 mnt -> mnt:[4026532959]
lrwxrwxrwx 1 root root 0 Sep 21 16:27 net -> net:[4026532964]
lrwxrwxrwx 1 root root 0 Sep 21 16:27 pid -> pid:[4026532962]
lrwxrwxrwx 1 root root 0 Sep 21 16:27 pid_for_children -> pid:[4026532962]
lrwxrwxrwx 1 root root 0 Sep 21 16:27 time -> time:[4026531834]
lrwxrwxrwx 1 root root 0 Sep 21 16:27 time_for_children -> time:[4026531834]
lrwxrwxrwx 1 root root 0 Sep 21 16:27 user -> user:[4026531837]
lrwxrwxrwx 1 root root 0 Sep 21 16:27 uts -> uts:[4026532960]

The test for "are these two processes in the same namespace?" is official: "If two processes are in the same namespace, then the device IDs and inode numbers of their /proc/pid/ns/xxx symbolic links will be the same."[namespaces(7)] Here are two default containers running at the same time, read from inside each: 

$ docker run -d --name lt-a ubuntu:24.04 sleep 300; docker run -d --name lt-b ubuntu:24.04 sleep 300
$ docker exec lt-a bash -c 'for n in pid net mnt uts ipc cgroup user time; do readlink /proc/1/ns/$n; done | paste -sd" "'
pid:[4026533772] net:[4026533774] mnt:[4026533769] uts:[4026533770] ipc:[4026533771] cgroup:[4026533773] user:[4026531837] time:[4026531834]
$ docker exec lt-b bash -c '…same…'
pid:[4026533907] net:[4026533909] mnt:[4026533904] uts:[4026533905] ipc:[4026533906] cgroup:[4026533908] user:[4026531837] time:[4026531834]

Six walls each, and two shared rooms: both containers — and the lab above, and the host — are in the same user and time namespaces.

Pitfall — comparing a live process with a dead one

The inode number of a namespace that has been freed can be handed to the next namespace created. Run two containers one after the other and they may print identical numbers while never having shared anything. Only compare processes that are alive at the same moment.

Building the view by hand

unshare runs a program in newly created namespaces; nsenter runs one inside the namespaces of an existing process.[nsenter(1)] Those two commands, plus lsns to list, are the whole toolkit.

PID: a private process list

# unshare --pid --fork --mount-proc bash
# echo $$
1
# ps aux
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root         1  0.0  0.0   4032  2896 ?        S    16:30   0:00 bash
root         2  100  0.0   7628  3532 ?        R    16:30   0:00 ps aux
# exit

In a new PID namespace numbering starts again at 1, and the first process is that namespace's PID 1, with the init duties and signal quirks from page 10.[pid_namespaces(7)] Two flags need explaining. --fork: the process that calls unshare stays in its old PID namespace; only its children land in the new one (that is the pid_for_children link above), so unshare must fork before running bash. --mount-proc: ps reads /proc, and a /proc "shows … only processes visible in the PID namespace of the process that performed the mount."[pid_namespaces(7)] Without a fresh mount you are PID 1 staring at the old list (the lab has you try it).

Visibility is one-way. A process "can see … only processes contained in its own PID namespace and in descendants of that namespace."[pid_namespaces(7)] So the outside sees in, under different numbers. Start a box in the background and look at it from the lab shell: 

# unshare --pid --fork --mount-proc --uts --net --ipc bash -c 'hostname box; sleep 600 & sleep 600 & exec sleep 900' &
# ps -eo pid,ppid,args --forest
  PID  PPID COMMAND
  335     0 unshare --pid --fork --mount-proc --uts --net --ipc bash -c hostname box; …
  341   335  \_ sleep 900
  343   341      \_ sleep 600
  344   341      \_ sleep 600
    1     0 sleep infinity
# grep NSpid /proc/341/status
NSpid:	341	1
lab's PID namespace pid:[4026532962] box's pid:[4026532692] ┌─────────────────────────────────────┐ ┌──────────────────────┐ │ 1 sleep infinity │ │ │ │ 335 unshare … │ │ │ │ 341 sleep 900 ──── same process ──┼────▶│ 1 sleep 900 (init) │ │ 343 sleep 600 ────────────────────┼────▶│ 3 sleep 600 │ │ 344 sleep 600 ────────────────────┼────▶│ 4 sleep 600 │ └─────────────────────────────────────┘ └──────────────────────┘ sees and can signal everything ──▶ sees only itself

This is the geometry of every agent sandbox: the harness side can watch and kill the agent's processes; the agent's side cannot even list the harness's — provided the grader really is outside (page 26).

UTS, network, mount

# unshare --uts bash -c 'hostname sandbox-7; hostname; readlink /proc/self/ns/uts'
sandbox-7
uts:[4026534037]
# hostname; readlink /proc/self/ns/uts
lab
uts:[4026532960]

The UTS namespace holds two strings, hostname and NIS domain name, and nothing else — remember that for the end of the page. A new network namespace is more dramatic: it has its own devices, addresses, routing table, firewall rules and port numbers,[network_namespaces(7)] and it starts with no usable connectivity at all: 

# unshare --net bash
# ip -br addr
lo               DOWN
tunl0@NONE       DOWN
…
ip6gre0@NONE     DOWN
# ip route                      # prints nothing: no routes
# ping -c1 -W1 127.0.0.1
ping: connect: Network is unreachable
# ip link set lo up; ping -c1 -W1 127.0.0.1 | tail -2
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 0.268/0.268/0.268/0.000 ms
# exit

A loopback device that is down, no addresses, no routes: even 127.0.0.1 is unreachable until someone brings lo up. (The tunl0…ip6gre0 lines are unused "fallback tunnel" devices that some kernels, including Docker Desktop's, create in every network namespace; a stock server may show only lo.[Kernel: sysctl/net]) This is what --network none gives a container (page 19). Everything a normal container has beyond it was added from outside by the runtime: one end of a virtual cable — veth devices "are always created in interconnected pairs"[veth(4)] — pushed into the namespace, an address, a default route (page 16; concepts in Networking for LLM Evals, lesson 14). 

# unshare --mount bash -c 'mount -t tmpfs tmpfs /mnt; echo secret > /mnt/note; ls /mnt; findmnt /mnt'
note
TARGET SOURCE FSTYPE OPTIONS
/mnt   tmpfs  tmpfs  rw,relatime
# ls /mnt; findmnt /mnt; echo "exit=$?"
exit=1

A mount namespace is a private copy of the mount table from page 14: it starts as a copy of the creator's, then diverges.[mount_namespaces(7)] The tmpfs and its file existed for the processes inside and for nobody else. That is why findmnt inside a task container lists only the container's mounts, and why audit question 2 must be asked from inside each box.

Entering: what docker exec amounts to

# nsenter -t 341 -a bash -c 'hostname; ps -eo pid,ppid,args'
box
  PID  PPID COMMAND
    1     0 sleep 900
    3     1 sleep 600
    4     1 sleep 600
    5     0 ps -eo pid,ppid,args

-t 341 -a means "join all the namespaces of process 341" (the kernel call is setns(2)[namespaces(7)]). Note the newcomer's parent: PPID 0, because its real parent is outside and has no number in here. Docker documents docker exec only as "runs a new command in a running container";[Docker: run] what you can observe is the same signature — in lt-a, an exec'd ps shows PPID 0 and the same pid: and mnt: inode numbers as the container's PID 1. When you debug a rollout with docker exec, you are a process injected into the agent's view, not a login to a machine.

Teardown for free

# kill -9 341; sleep 1; pgrep -a sleep
1 sleep infinity
# bash -c 'sleep 601 & sleep 601 & sleep 1'; sleep 2; pgrep -a sleep   # same thing, no namespace
1 sleep infinity
387 sleep 601
388 sleep 601
# pkill -f 'sleep 601'            # clean up by hand — which is the point

"If the 'init' process of a PID namespace terminates, the kernel terminates all of the processes in the namespace via a SIGKILL signal."[pid_namespaces(7)] Killing one process took both background sleeps with it. Without the namespace the same children were simply orphaned (page 9) and kept running.

In eval work — why container rollouts don't leak processes

An agent starts a dev server on port 8000, forgets it, and the episode ends. On a bare-process runner that server survives into the next rollout, which then fails with "Address already in use" — shared state between samples that were supposed to be independent, scored as a model failure. With one container per rollout, removing the container ends PID 1 and the kernel kills everything else in the namespace. If you ever see leftovers, that is evidence the processes were started outside the rollout's PID namespace; record those runs as infrastructure failures, not as wrong answers.

A different root: chroot, then pivot_root

Ingredient (c) is older than namespaces. chroot changes what / means for a process. With a static BusyBox (apt-get install busybox-static) a "root filesystem" can be two files: 

# mkdir -p /jail/bin && cp /usr/bin/busybox /jail/bin/ && echo "hello from the jail" > /jail/README
# chroot /jail /bin/busybox sh -c '/bin/busybox ls -l /; /bin/busybox ls /etc; /bin/busybox hostname'
total 8
-rw-r--r--    1 0        0               20 Sep 21 16:27 README
drwxr-xr-x    2 0        0             4096 Sep 21 16:27 bin
ls: /etc: No such file or directory
lab

An image is this idea scaled up: a directory tree with a distribution's files in it. But look at the last line — same hostname, because chroot changed nothing except path lookup. Its man page is blunt: "This call changes an ingredient in the pathname resolution process and does nothing else. In particular, it is not intended to be used for any kind of security purpose, neither to fully sandbox a process nor to restrict filesystem system calls."[chroot(2)] Container runtimes use pivot_root instead, which swaps the root mount of a mount namespace so the old root can be unmounted and become unreachable; its man page notes "A modern use is to set up a root filesystem during the creation of a container,"[pivot_root(2)] and runc labels its opt-out flag "may be unsafe from the security standpoint."[runc] A "chroot sandbox" in a home-grown harness is a finding for your audit.

User namespaces: root inside, nobody outside

Why did the lab need --privileged? Creating namespaces "in most cases requires the CAP_SYS_ADMIN capability"; "User namespaces are the exception: since Linux 3.8, no privilege is required."[namespaces(7)] Default containers lack that capability (page 21): there unshare --uts true prints unshare: unshare failed: Operation not permitted. A user namespace maps user IDs, so a process can have "a normal unprivileged user ID outside a user namespace while at the same time having a user ID of 0 inside the namespace."[user_namespaces(7)] As an unprivileged user (useradd -m learner, then docker exec -it -u learner lt-ns bash): 

$ id
uid=1001(learner) gid=1001(learner) groups=1001(learner)
$ unshare --user --map-root-user bash
# id; cat /proc/self/uid_map; grep CapEff /proc/self/status
uid=0(root) gid=0(root) groups=0(root)
         0       1001          1
CapEff:	000001ffffffffff
# hostname x; touch /etc/x
hostname: you must be root to change the host name
touch: cannot touch '/etc/x': Permission denied

uid_map reads "ID 0 in here is ID 1001 out there, for a range of 1." The full capability mask is real but applies "only on resources governed by that namespace"[user_namespaces(7)]: the hostname belongs to a UTS namespace owned by the outer user namespace, and /etc belongs to the real root, so both refuse. (With Docker's own seccomp profile active, even this unshare is refused.)

Caveat — Docker does not do this by default

The identical user:[4026531837] everywhere on this page is the point: a default Docker container shares the host's user namespace, and "The default user within a container is root (uid = 0)."[Docker: run] Remapping container root "to a non uid-0 user outside the container" exists, but "is available but not enabled by default."[Docker: security] So root in a default container is the host's uid 0, held back only by the privilege reductions of page 21. The daemon-level fixes (userns-remap, rootless) are on page 23.

What is not namespaced

$ for i in ubuntu:24.04 debian:bookworm-slim alpine:3.20; do docker run --rm $i uname -r; done
6.10.14-linuxkit
6.10.14-linuxkit
6.10.14-linuxkit
$ docker run --rm --memory 256m --cpus 1 ubuntu:24.04 bash -c 'cat /proc/uptime; nproc; grep MemTotal /proc/meminfo'
17487.79 173670.87
10
MemTotal:        8025424 kB
$ docker run --rm ubuntu:24.04 date -s 2030-01-01
Tue Jan  1 00:00:00 UTC 2030
date: cannot set date: Operation not permitted

Three "distributions", one kernel: the UTS namespace covers the hostname, not the kernel release. Docker says it plainly — containers "all share the same kernel"[Docker: what-is-a-container] (on a Mac, the kernel of Docker Desktop's hidden Linux VM). A container born a second ago reports almost five hours of uptime, ten CPUs and 8 GB of RAM despite its limits, because much of /proc describes the machine, not the namespace (page 12). And the wall clock is global: time namespaces "do not virtualize the CLOCK_REALTIME clock,"[time_namespaces(7)] so you cannot give an agent a fake date with a namespace; the refusal above is a missing capability protecting a shared clock. Namespaces restrict what a process can name. Every system call still lands in the one kernel, with all its bugs — which is why page 24 exists.

Reading the walls of someone else's task

The OCI spec gives the rule that makes this auditable: "If a namespace type is not specified in the namespaces array, the container MUST inherit the runtime namespace of that type."[OCI Runtime Spec] A wall exists only if someone asked for it, and Docker's flags can un-ask: --pid=host is "use the host's PID namespace inside the container,"[Docker: run] and Compose's network_mode: host "Gives the container raw access to the host's network interface."[Compose] 

$ docker run --rm ubuntu:24.04 bash -c 'ls -d /proc/[0-9]* | wc -l; readlink /proc/self/ns/net; hostname'
3
net:[4026534044]
4dc01296fbee
$ docker run --rm --pid=host ubuntu:24.04 bash -c 'ls -d /proc/[0-9]* | wc -l'
264
$ docker run --rm --network=host ubuntu:24.04 bash -c 'readlink /proc/self/ns/net; hostname'
net:[4026531840]
docker-desktop

264 processes instead of 3: every process on the (VM) host, other rollouts and the container runtime included. And 4026531840 is the network namespace of the host's own PID 1: every listening port on the host is now on the agent's localhost.

In a task's run line or compose fileWall removedWhat the agent gains
--pid=host / pid: hostPIDSees (and as root may signal) every host process, including other rollouts and graders
--network=host / network_mode: hostnetworkThe host's interfaces, routes and localhost services; egress rules aimed at the container's network no longer apply
--pid/--network container:X, service:Xbetween two containersDeliberate sharing (sidecars). Fine — unless X is the grader
--privileged / privileged: truenone directlyThe power to make and enter namespaces and mount things: the walls stand but the door is open (page 23)
In eval work — navigate: "what can the agent see?" has a numeric answer

From outside, without trusting the task author: docker inspect X --format 'pid={{.HostConfig.PidMode}} net={{.HostConfig.NetworkMode}} privileged={{.HostConfig.Privileged}}' printed pid= net=bridge privileged=false for lt-a (empty means private) and privileged=true for this page's lab. For proof rather than configuration, compare inode numbers: if the grader's pid:[…] equals the agent's, the agent can see the grader. On a real Linux host, sudo lsns -t pid lists every PID namespace with its first process; on a Mac the nearest equivalent is an auditor container, docker run --rm --pid=host --cap-add SYS_PTRACE ubuntu:24.04 lsns -t pid — exactly the flags you would reject in a task, used here on your own machine to look in. Sharing matters in practice: in a test for this page, a second container started with --pid container:lt-a showed the same pid: inode as lt-a, and root in lt-a ended it with one kill -9 (exit 137).

Depth triage

Learn to use: /proc/PID/ns, lsns, nsenter, the docker inspect mode fields, and the grep in the lab. Recognize: user namespaces and uid_map, pivot_root, the IPC, cgroup and time namespaces. Leave to a specialist: writing a container runtime, mount propagation, configuring userns-remap across a fleet.

Check your understanding

A team runs a 300-task web-dev benchmark on a big bare-metal box: each rollout is a fresh working directory and a fresh Unix user, no containers. Pass rate is 58% for the first hundred tasks run and 44% for the last hundred; many late transcripts contain "Address already in use". A colleague proposes reporting the first-hundred figure as "the clean number". What do you establish first?

Reveal the reasoning

Observed: a pass rate that falls with run order, and a port-conflict message. Supposed: that processes leaked by earlier rollouts hold the ports — plausible, since nothing on this runner kills a rollout's descendants, but not yet shown; later tasks might just be harder. Discriminating evidence: on the host, ss -ltnp and ps -eo pid,user,lstart,args — listeners owned by earlier rollouts' users, started before the failing rollout began, confirm the leak; re-running the last hundred first, on a rebooted box, separates order from difficulty. If confirmed, those failures are infrastructure outcomes: report correct/scheduled, correct/completed and completed/scheduled separately rather than picking the flattering subset, fix the runner (a PID and network namespace per rollout — i.e. a container — makes the teardown a kernel guarantee), and re-run. The first-hundred number is not clean either: it is a different, order-selected sample.

Lab

Container lab, using the privileged lt-ns container from above (root shell: docker exec -it lt-ns bash). Finish with docker rm -f lt-ns lt-a lt-b.

  1. Reproduce the PID namespace. Then predict: without --mount-proc, what does echo $$ print, and does ls /proc | grep -c '^[0-9]' give the same count as with it?
    Solution 
    # unshare --pid --fork --mount-proc bash -c 'echo $$; ls /proc | grep -c "^[0-9]"'
1
3
# unshare --pid --fork bash -c 'echo $$; ls /proc | grep -c "^[0-9]"'
1
7

    Still PID 1 — the namespace is real — but the old /proc was mounted by a process in the outer namespace, so it lists the outer processes (your count will differ). ps may even fail with fatal library error, lookup self, because /proc/self cannot resolve a process the old mount has no number for.

  2. Give a process its own hostname, and prove by inode number that it left your UTS namespace but not your network namespace.
    Solution 
    # readlink /proc/self/ns/uts /proc/self/ns/net
uts:[4026532960]
net:[4026532964]
# unshare --uts bash -c 'hostname sandbox-7; hostname; readlink /proc/self/ns/uts /proc/self/ns/net'
sandbox-7
uts:[4026534037]
net:[4026532964]

    Your numbers will differ; the pattern — uts changed, net identical — will not.

  3. Predict before running: in a fresh network namespace, does ping -c1 127.0.0.1 work? Make it work with one command.
    Solution

    No: ping: connect: Network is unreachable, because lo is DOWN and there are no routes. ip link set lo up fixes it (full session in the network section). A task that tests a local server under --network none works only because the runtime brings lo up.

  4. Start the three-sleep "box" from the PID section, find the outside PID of its init with pgrep -f '^sleep 900', enter it with nsenter, then kill its PID 1 from outside and show nothing survives.
    Solution 
    # P=$(pgrep -f '^sleep 900'); echo $P
465
# nsenter -t $P -a bash -c 'hostname; ps -eo pid,ppid,args'
box
  PID  PPID COMMAND
    1     0 sleep 900
    3     1 sleep 600
    4     1 sleep 600
    5     0 ps -eo pid,ppid,args
# kill -9 $P; sleep 1; pgrep -f 'sleep [69]00'; echo "exit=$?"
exit=1

    pgrep finds nothing (exit status 1): both sleep 600 processes died with their namespace's init.

  5. Eval task. You are reviewing a contributed task. Save this as compose.yaml and write one grep that flags every line that removes a wall or opens a door. Which finding is worst? 
    services:
  default:
    image: task-netdebug:1.4
    command: sleep infinity
    network_mode: host
    pid: host
    mem_limit: 2g
  grader:
    image: task-netdebug-grader:1.4
    privileged: true
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    Solution 
    $ grep -nE 'privileged|(pid|ipc|network_mode|userns_mode): *"?host|docker\.sock' compose.yaml
5:    network_mode: host
6:    pid: host
10:    privileged: true
12:      - /var/run/docker.sock:/var/run/docker.sock

    Lines 5–6 are on the agent's service: it shares the host's network and process list, so other rollouts and host services are visible and reachable, and any egress policy attached to a container network does not apply. That is the worst for validity. Lines 10–12 are on the grader — dangerous for the host (the socket is covered on page 23) but not directly in the agent's hands. Ask the author what the task actually needs; "debug the network" tasks usually need one capability (page 21), not the host's namespaces. A grep is a first pass — confirm with docker inspect on the running containers.
