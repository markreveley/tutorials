Capstone: the ten-minute audit

The whole course as one timed procedure: dropped into a benchmark's task container with a shell, answer the five audit questions from inside, finish the picture from outside, and write down whether scores from this box can be trusted — then defend an environment design of your own.

The scenario

A team hands you shell access to one of their task containers and asks: can we trust scores from this? Ten minutes is not enough to prove a box is safe. It is enough to find every problem this course has named, or to show it isn't there, and to say what you did not check. The procedure is five blocks of about two minutes each, after a thirty-second orient. Each block answers one of the five audit questions, and each question exists because a wrong answer changes what the score means.

inside the box (audit.sh, ~1 min) outside the box (~3 min) --------------------------------- ------------------------------ 0 orient who am I? container or VM? docker inspect (the policy) 1 running processes, listeners docker history (the layers) 2 mounted ro/rw, writable dirs docker logs (PID 1 output) 3 owns caps, setuid, answer keys where does grading run? 4 reach routes, DNS, TCP connects 5 logs cgroup limits, OOM counts => write-up: finding, impact, fix, residual risk

The procedure, block by block

On a full distribution you would use the commands in the second column. Task images are rarely full: ubuntu:24.04 has ps but ships without ss, ip, curl or even python3 (Appendix A lists which package provides each), and installing them changes the box you were asked to audit — and may be impossible with no network. So the third column reads the same facts from the kernel's own files, which are always there (page 9, /proc).

audit.sh

The course's rule is that shell scripts stay under thirty lines and anything longer becomes Python (page 6). This one is 61 lines and stays in bash on purpose: it must run in boxes that have bash, coreutils, util-linux and getent and nothing else — and a stock ubuntu:24.04 has no Python. It is read-only: it reads files and /proc, and its only side effect is three outbound TCP connection attempts. It passes shellcheck. Because the box's root may be read-only, you feed it on stdin rather than copying it in: docker exec -i NAME bash -s < audit.sh. 

#!/usr/bin/env bash
# audit.sh: the inside half of the ten-minute audit. READ-ONLY: it reads files and /proc and
# attempts three outbound TCP connections; it writes nothing. Works in minimal images (no ps, ss,
# ip or curl needed). The root may be read-only, so feed it on stdin:
#   docker exec -i NAME bash -s < audit.sh
set -u
sec() { printf '\n== %s\n' "$1"; }
st() { awk -v k="$1:" '$1 == k { print $2 }' /proc/self/status; }
cg() { cat "/sys/fs/cgroup/$1" 2>/dev/null || echo n/a; }
prune=(\( -path /proc -o -path /sys -o -path /dev -o -path /usr \) -prune -o)

sec "0 orient: who am I, on what?"
echo "id:      $(id)"
echo "os:      $(sed -n 's/^PRETTY_NAME=//p' /etc/os-release | tr -d '"'), kernel $(uname -r) $(uname -m)"
echo "box:     /.dockerenv $([ -e /.dockerenv ] && echo present || echo absent); /proc/1/cgroup $(cat /proc/1/cgroup)"
echo "pid 1:   $(tr '\0' ' ' </proc/1/cmdline)"

sec "1 running: processes (read from /proc) and listening TCP ports"
for d in /proc/[0-9]*; do
  cmd=$(tr '\0' ' ' <"$d/cmdline" 2>/dev/null | cut -c1-60) || continue
  [ -n "$cmd" ] && printf '%6s %-8s %s\n' "${d#/proc/}" "$(stat -c %U "$d" 2>/dev/null)" "$cmd"
done
while read -r _ local _ state _; do
  [ "$state" = 0A ] && echo "listening: TCP port $((16#${local##*:}))"
done < <(tail -q -n +2 /proc/net/tcp /proc/net/tcp6 2>/dev/null)

sec "2 mounted: filesystems, and where this user can write"
findmnt -rn -o TARGET,FSTYPE,OPTIONS | awk '$1 !~ /^\/(proc|sys|dev)\// { split($3, o, ","); print "  " o[1], $2, $1 }'
w=$(find / "${prune[@]}" -type d -writable -print 2>/dev/null)
echo "writable directories: $(grep -c . <<<"$w"), first few: $(head -4 <<<"$w" | tr '\n' ' ')"

sec "3 owns: privilege, and answers within reach"
echo "CapEff=$(st CapEff) CapBnd=$(st CapBnd) NoNewPrivs=$(st NoNewPrivs) Seccomp=$(st Seccomp)"
echo "setuid: $(find / -xdev -perm -4000 -type f 2>/dev/null | tr '\n' ' ')"
command -v sudo >/dev/null && echo "sudo: installed"
find / "${prune[@]}" -type f -readable \( -iname '*expected*' -o -iname '*solution*' \
  -o -iname '*answer*' -o -iname 'test_hidden*' -o -iname 'run-tests*' \) -print 2>/dev/null |
  sed 's/^/readable, answer-like: /'
find / "${prune[@]}" -name .git -type d -print 2>/dev/null | while read -r g; do
  echo "git repo ${g%/.git}: $(git -C "${g%/.git}" log --all --oneline 2>/dev/null | wc -l) commits on all refs"
done
[ -S /var/run/docker.sock ] && echo "DOCKER SOCKET MOUNTED: root on the host"

sec "4 reach: routes, DNS, three TCP connects (2 s each)"
for f in /sys/class/net/*/operstate; do  # skip DOWN devices (e.g. fallback tunnels)
  s=$(cat "$f"); i=${f%/operstate}; [ "$s" != down ] && echo "interface ${i##*/}: $s"
done
echo "IPv4 routes: $(($(wc -l </proc/net/route) - 1))"
echo "resolver: $(grep -m1 '^nameserver' /etc/resolv.conf 2>/dev/null || echo none)"
if timeout 3 getent hosts example.com >/dev/null; then echo "DNS: external names resolve"; else echo "DNS: no"; fi
for t in example.com:443 1.1.1.1:443 169.254.169.254:80; do
  if timeout 2 bash -c "exec 3<>/dev/tcp/${t%:*}/${t#*:}" 2>/dev/null; then r=OPEN; else r=closed; fi
  echo "tcp $t: $r"
done

sec "5 logs and limits"
echo "memory.max=$(cg memory.max) cpu.max=$(cg cpu.max | tr ' ' /) pids.max=$(cg pids.max)"
echo "memory.events: $(cg memory.events | tr '\n' ' ')"
echo "/var/log: $(find /var/log -mindepth 1 -maxdepth 1 -printf '%f ' 2>/dev/null)"
if [ -d /run/systemd/system ]; then echo "init: systemd, read journalctl"
else echo "init: not systemd; the main process's output is in 'docker logs' (outside)"; fi

Three details worth reading closely. The listening-port loop decodes /proc/net/tcp, where state 0A is LISTEN and the port is hex after the colon — exactly what ss -tln does for you. The reach block uses bash's /dev/tcp/HOST/PORT, a path bash intercepts and turns into a TCP connection, so a box with no curl can still be probed; it answers "can a TCP connection be made", not "does HTTP work", which is enough for an egress question. And the answer-key search matches names, so it finds careless layouts, not determined hiding — a limit to state in the write-up.

Read them side by side and each difference is a page of this course. Root with a full capability set against uid 1001 with none and NoNewPrivs=1, which makes the eight setuid binaries still present in both inert (page 21). A writable root with 133 writable directories against a read-only root with four, all of them places the task expects writes. A grader and a git history in reach against none. An open route to the internet against an empty routing table. No budgets against 512 MiB, one CPU and 128 processes.

Caveat — read your own report critically

Seccomp=0 in both reports is a property of this authoring machine, whose Docker Desktop daemon runs containers unconfined; a stock Linux Docker Engine applies its default profile and shows 2 (page 21). On a real audit that line would be a finding. Likewise resolver: nameserver 192.168.65.7 in the network-less box is just a file; with zero routes nothing can reach it. An audit report is evidence, and evidence still needs interpreting.

Also check from outside: Env for secrets (page 11); the image ID or digest the runs used, so the audit is tied to a specific build (page 15); and — the question no command answers — where grading runs: in this container after the agent, or in a fresh one on copied-out files (page 25). Ask, and read the harness config.

In eval work — navigate

The inside and outside views check each other. docker inspect shows what was requested; the inside report shows what the process actually got. They should agree — CapDrop=[ALL] and CapEff=0000000000000000, NetworkMode=none and zero routes. When they don't, the harness is not launching containers the way its config says, and that is the most important finding of the audit, because every other number rests on it. Run the inside half from the harness's own exec path too, as the agent's user, not only from your terminal as root.

The write-up

An audit is only useful once someone who wasn't there can act on it. One row per finding: the finding (evidence, quoted), its effect on the validity of scores, the fix, and the residual risk after the fix. Filled for the sloppy build:

Close with what you did not check: kernel version against known vulnerabilities, the image's supply chain, anything behind the harness. Saying where your evidence ends is part of the result, not a weakness in it.

Pitfall — auditing the image instead of the rollout

Auditing docker run IMAGE from your terminal audits the defaults you typed, not the harness's. The sloppy and hardened reports above come from the same kind of image launched two ways; half of what differs is flags, not Dockerfile. Audit a container the harness itself started, mid-rollout if you can (Inspect's --no-sandbox-cleanup leaves them running for this, page 25).

Design and defend

The audit is the navigate skill. The job also asks you to design an environment policy and defend it in review. This section is modelled on the networking course's readiness review; do it with a colleague or out loud.

The design brief

A team runs a 150-task agentic coding benchmark, 5 epochs per model. Each task image is built FROM ubuntu:24.04 with apt-get install at build time; the agent runs as root with open internet "so it can pip install"; the harness grades by running /tests/run.sh inside the agent's container after the agent stops; all rollouts run on one 64-core host with no per-container limits. Current problems: 7% of rollouts end in 137 with no pattern anyone has found; a new model's score jumped 11 points and nobody can say whether it cheated; last month's re-run of an old model scored 4 points lower with no code change; and a quarter of one model's failures begin with command not found. Propose and defend a revised environment.

Bring five artifacts

ArtifactWhat it must include
Environment diagramHost, runtime, sandbox, grader, harness; every mount, network path and credential; the trust boundaries — what the agent controls, what it can read, what it can reach (page 24)
Sandbox policyThe exact docker run or compose; user, capabilities, read-only paths, network policy, limits with the reason for each value; the inside-out check that proves it (page 23)
Rollout record schemaIDs, image digest, model, epoch, exit code, timed_out, oom_killed (from memory.events or State.OOMKilled), duration, limits applied, outcome category and failure code (page 27), integrity flag
Incident reportOne failure from the brief reproduced in your lab: evidence → hypothesis → the next discriminating test → result. The 137s are the obvious candidate (page 10)
Measurement policyHow timeouts, kills and environment defects enter the denominator; correct/scheduled, correct/completed, completed/scheduled; how integrity violations are detected and reported beside the pass rate; which is the headline, decided before the run

Questions to answer aloud

  • Why does the 11-point jump need an integrity check before a capability claim, and which two surfaces in this design make it most urgent?
  • What evidence would separate "7% OOM kills" from "7% harness timeouts" — and what if it is both?
  • The 4-point drop on re-run: list three environment differences that could cause it without a model change, and how the new design pins each.
  • The command not found failures: model fluency or environment defect? What rule decides, and who writes it?
  • What does removing internet access cost this benchmark, and what do you offer instead?

An observable readiness rubric

SkillReady enough to build onPractice more if…
ExplainYou can say, in plain words, how a mount, a uid, a capability or a route changes what a score meansYour explanations stop at "it's more secure"
DiagnoseYou reproduce a failure with the same argv and user, name the last thing that worked, and choose a test that tells causes apartYour only move is raising the timeout or re-running
DesignYour policy names each knob, the threat it answers, its cost to the task, and how it's verified from insideThe policy is a list of flags copied from somewhere, with no check that they took effect

This rubric is the course's own self-assessment, not an industry certification or a hiring standard. A good answer in review can be "I don't know yet; this observation would distinguish the two possibilities."

The finish line

If you can do this page's audit on a box you have never seen, you can demonstrate — not just claim — concrete things: that you can say what is running, what is mounted and whether it is read-only, who owns what, what the box can reach and where its logs are, from inside, with no tools installed, in ten minutes; that you can decode an exit status into a cause and name the counter that confirms it; that you can turn a default docker run into a sandbox and prove each setting from inside; and that you can read a transcript and say whether the model or the environment failed, with the evidence. Those are observable. Show them with artifacts: an audit write-up of a public benchmark's task image, your audit.sh and its two reports, a coded sample of transcripts. None of this guarantees a job; it gives an interviewer something real to look at.

Check your understanding

You run audit.sh through the harness's own exec path mid-rollout and get uid=1001, CapEff=0000000000000000, a read-only root and IPv4 routes: 0. The benchmark's owner says: "So the environment is clean and the scores are trustworthy." What do you agree with, and what do you still need before you say that?

Reveal the reasoning

Established: during the agent phase, this rollout's agent was unprivileged, couldn't write outside its allowed paths, and had no network — so the privilege, tampering and fetch-the-answer surfaces are closed for this rollout. Not established: (1) where and how grading runs — if it runs later in this container as root with tests copied in, anything the agent left in /app or /tmp (a shadowing module, a background process) is inside the grader's reach; (2) what the image contains that the agent couldn't see but others can (docker history); (3) whether every rollout is launched this way — one audited container is a sample of one; (4) whether the limits cause infrastructure failures, which needs the outcome table, not the audit; (5) what the task text itself leaks. "Clean" is a claim about isolation; "trustworthy scores" also needs grading design, failure accounting and an integrity rate. Agree with the first, ask for the rest.

    Solution
