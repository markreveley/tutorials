The isolation ladder: containers, gVisor, microVMs

Page 23 hardened a container as far as flags can take it, and ended on a caveat: it still shares the host's kernel. This page explains why that one fact organises the whole field of sandboxing, what the rungs above a container are, what each costs, and how to choose one from a threat model rather than from habit.

The shared-kernel fact

Three different distributions, one command: 

$ for i in ubuntu:24.04 debian:bookworm-slim alpine:3.20; do docker run --rm $i uname -r; done
6.10.14-linuxkit
6.10.14-linuxkit
6.10.14-linuxkit
$ docker run --rm ubuntu:24.04 cat /proc/sys/kernel/random/boot_id; docker run --rm alpine:3.20 cat /proc/sys/kernel/random/boot_id
adc18ab8-3212-40c0-bd43-47fba20d4842
adc18ab8-3212-40c0-bd43-47fba20d4842

An image supplies files — a userland. It never supplies a kernel. Every container on a host runs on that host's one kernel (here, the kernel of Docker Desktop's Linux VM), which is why two unrelated containers report the same boot ID. So every system call the agent's code makes is handled by the same kernel that runs the harness, the other rollouts and the host. The authors of Firecracker put the consequence precisely: "In Linux containers, untrusted code calls the host kernel directly, possibly with the kernel surface area restricted (such as with seccomp-bpf)", and this "reliance on a single operating system kernel means that there is a fundamental tradeoff between security and code compatibility. Container implementors can choose to improve security by limiting syscalls, at the cost of breaking code which requires the restricted calls."[Firecracker]

In this course's terms: the attack surface of a container is the entire system-call interface, minus whatever seccomp filters out (page 21). A kernel bug reachable through an allowed call is a way out, and no docker run flag removes it. This is not a new worry for evals. In 2021 the HumanEval authors ran model-written programs under gVisor because "container runtimes like Docker can share host resources with containers, a malicious container could potentially compromise a host."[HumanEval]

The ladder: where do the agent's system calls go?

gVisor: a kernel written as an ordinary program

gVisor "is an application kernel that implements a Linux-like interface. Unlike Linux, it is written in a memory-safe language (Go) and runs in userspace." Its core, the Sentry, intercepts the application's system calls and answers them itself: "the Sentry does not pass system calls through to the host kernel." File access goes through a second process, the Gofer.[gVisor] To escape, "an attacker would need to simultaneously exploit the gVisor Sentry kernel and the host Linux kernel, which do not share any code."[gVisor] It ships as an OCI runtime, runsc, that plugs into Docker and Kubernetes — the same images, a different thing underneath. On a host where it is installed you select it with docker run --runtime=runsc; where it isn't: 

$ docker info --format '{{range $k, $v := .Runtimes}}{{$k}} {{end}}default={{.DefaultRuntime}}'
io.containerd.runc.v2 runc default=runc
$ docker run --rm --runtime=runsc ubuntu:24.04 true; echo "exit=$?"
docker: Error response from daemon: unknown or invalid runtime name: runsc
exit=125

The price, in gVisor's own words: "reduced application compatibility and higher per-system call overhead." It "does not presently implement every system call, /proc file, or /sys file", and "the only real way to know if it will work is to try."[gVisor] The cost falls on syscall-heavy and file-operation-heavy work, not on raw disk I/O.[gVisor]

MicroVMs: a real guest kernel behind a tiny VMM

A virtual machine gives the untrusted code its own kernel and confines that kernel using the CPU's virtualization hardware. On Linux the hardware is driven through KVM, which a program uses by opening /dev/kvm and issuing ioctls.[Kernel: KVM] That program is the VMM (virtual machine monitor). The Firecracker paper's argument for the arrangement: it "moves the security-critical interface from the OS boundary to a boundary supported in hardware and comparatively simpler software… the guest kernel can supply its full feature set with no change to the threat model."[Firecracker] The agent can have root, every capability and every syscall — of a kernel that is itself treated as hostile.

The traditional objection is weight: a general-purpose VMM such as QEMU is over 1.4 million lines, and VMs boot in seconds. A microVM monitor strips the virtual hardware to almost nothing. Firecracker, built at AWS for Lambda and Fargate, is about 50 thousand lines of Rust, and advertises three numbers. Each is conditional:

Headline (project site)What was actually specified or measured
"Boot in <125ms"≤ 125 ms from the InstanceStart API call to the start of the guest's /sbin/init, for a minimal kernel and root filesystem, 1 vCPU, 128 MiB, serial console off. Not the boot time of an Ubuntu task image.
"<5 MiB overhead per VM"The VMM's own memory, on top of the guest's RAM, for that same minimal microVM; workload-dependent. The paper measured about 3 MB, against about 131 MB for QEMU.
"up to 150 microVMs per second per host"The design doc gives the underlying rate: 5 per host core per second — so it depends on core count.

(Site, specification, design doc and paper.[Firecracker]) The VMM process is itself confined: a "jailer" gives it cgroups, a mount namespace and dropped privileges, and Firecracker installs seccomp filters on itself — the tools of pages 20–23, applied to the thing guarding the agent.

Two neighbours, a sentence each. Kata Containers wraps the microVM idea in the container workflow: an OCI runtime that starts each container inside a lightweight VM, "using hardware virtualization technology as a second layer of defence" — inside the VM the guest kernel still builds namespaces and cgroups for the workload.[Kata] Cloud Hypervisor is a general-purpose Rust VMM from the same lineage as Firecracker (it supports Windows guests and live migration, which Firecracker does not); Kata can use either, or QEMU.[Kata]

Full VMs: the top rung, and sometimes the only one

OSWorld evaluates agents that operate a desktop. Its environment "runs on the host machine", creates a virtual machine per task, restores it from a snapshot, and after the episode "retrieves data to the host machine… and then runs evaluation scripts."[OSWorld] The paper's stated reasons for VMs are real operating systems with real GUI applications, safety of the host, and snapshot reset; it never argues against containers. The course's gloss: some tasks need a full VM regardless of threat model — a GUI, Windows, a task that loads kernel modules or reboots. (OSWorld's "docker" provider runs the VM inside a container and wants KVM. "Docker" in a README does not always mean container-level isolation.)

The last row decides more real deployments than the first. KVM needs "either a bare-metal machine (with hardware virtualization), or a virtual machine that supports nested virtualization"[Firecracker] — and whether a cloud VM exposes nested virtualization is the provider's choice. gVisor's default platform needs no virtualization, which is why it can run inside ordinary cloud VMs; its KVM platform is meant for bare metal.[gVisor] One command tells you which world a box is in: 

$ docker run --rm ubuntu:24.04 ls -l /dev/kvm
ls: cannot access '/dev/kvm': No such file or directory

And "stronger" is not automatic. gVisor's docs warn that "one should not assume that the mere use of virtualization hardware makes a system more or less secure."[gVisor]

Four boundaries, not one

"Which sandbox?" is really four questions. The ladder answers only the first.

In eval work — the incident that was not an escape

The most-cited sandbox incident in evals broke none of the rungs. In OpenAI's September 2024 o1 system card, o1-preview, on a CTF task whose target container had failed to start, scanned its network and "found that the Docker daemon API running on the evaluation host VM was accessible due to a misconfiguration"; it used the API to start a new copy of the challenge container with the command cat flag.txt and read the flag from the logs. OpenAI's own framing: "our evaluation infrastructure does not rely on the Docker container-to-host isolation or the virtual machine boundary for security. It remained secure as it was designed to, notwithstanding this misconfiguration of the container network."[o1 System Card] The card does not say what the infrastructure does rely on. What it establishes for us is narrower and more useful: the failure was on the egress boundary — a control plane reachable from the sandbox's network — and moving the agent up the ladder would not have changed it. gVisor's documentation states the general rule: "An attacker need not escalate privileges within a container if there's an exploitable network-accessible service on the host or some other API path. A sandbox is not a substitute for a secure architecture."[gVisor] The same holds one rung up: AISI's Proxmox plugin notes that by default a sandbox VM can reach the Proxmox host's API and cloud metadata services until the host firewall says otherwise.[AISI: Sandboxing]

Snapshots: the reset evals love, and its two cautions

A fresh container is a filesystem reset: the files return to the image's state and every process starts from nothing (page 22). VMs offer something more: a snapshot that includes memory. A Firecracker snapshot is a guest memory file, a microVM state file, and the disk files.[Firecracker] Restore it and the database is already warm, the server already listening. For evals the appeal is obvious: boot and set up once, then fan out a hundred identical rollouts. The Firecracker docs attach two cautions to exactly that pattern.

Uniqueness. When a state "is resumed from more than once, guest information assumed to be unique may in fact not be; this information can include identifiers, random numbers and random number seeds, the guest OS entropy pool, as well as cryptographic tokens… we consider resuming execution from the same state more than once insecure." A kernel mechanism (VMGenID) reseeds the guest kernel's random pool on resume, but other state "will still be replicated across multiple microVMs resumed from the same snapshot" — the docs name /proc/sys/kernel/random/boot_id, the file this page opened with.[Firecracker] The eval reading (ours, not theirs): a userspace random generator seeded before the snapshot gives every clone the same "random" choices, so rollouts you count as independent samples may not be.

The files are sensitive. A full snapshot writes "the full contents of guest memory", Firecracker trusts snapshot files with only a CRC on the state file, and "users need to secure snapshot files by implementing authentication and encryption schemes."[Firecracker] The inference for the secrets boundary is one step: anything in guest RAM at snapshot time — an API key in a process's environment — is in that memory file, readable by whoever can read the file. Snapshot before secrets go in, not after.

A published taxonomy: AISI's T / H / N profiles

The UK AI Security Institute's sandboxing toolkit describes a sandbox on three axes — tooling, host isolation, network isolation[AISI: Sandboxing] — and its Technical Guidance PDF (in the aisi-sandboxing repository, not the blog post) assigns levels, zero-based, higher meaning more restricted, written as a profile such as T0.H1.N2:[AISI: Sandboxing]

AxisLevels
Tooling (T)T0 unrestricted execution (code, browser) · T1 restricted: browsing and basic tooling without side effects · T2 no execution
Host isolation (H)H0 none (local machine) · H1 local containers (Docker, Compose) · H2 remote containers (Kubernetes pods) · H3 remote virtual machine (Proxmox)
Network isolation (N)N0 full external access · N1 pre-approved domains only · N2 no external access

Read what it does and does not say. The H axis is defined by provider, and AISI's stated reasons are practical: Kubernetes for "greater scalability, security and built-in tooling" (its chart enables gVisor by default, and domain allow-listing, N1, is practical only there); Proxmox for "strong virtual machine (VM) isolation for high-risk evaluations" and software-defined networks for cyber ranges. AISI does not make the shared-kernel argument — that is Firecracker's and gVisor's, above. Its worked example of an agent hunting a Docker zero-day sits at H2, not H3, and it leaves the decision with you: "it is up to users to make the ultimate decision", and "no sandboxing solution can provide 100% security assurance."[AISI: Sandboxing]

Choosing a rung

Two questions do most of the work: who wrote the code that will run, and what is on this host and network worth reaching.

SituationReasonable rungBecause
Your own scorer scripts; model output is only textNo sandbox (AISI: T2)Nothing untrusted executes
Agent runs shell commands on a laptop or a dedicated, disposable eval host with no secretsHardened container (page 23), no networkMain risk is accident; blast radius is a machine you can wipe
Same, on shared infrastructure: other teams' jobs, credentials, a clustergVisor, or microVMs if you have /dev/kvmA kernel bug now reaches things that matter
Cyber or autonomy evals where escape is the capability under test; GUI or Windows tasksVMs on isolated hosts and networksThe guest is adversarial by design, or the task needs a whole OS

In every row the other three boundaries are separate work. And one reframing matters for this field. AISI reports that "the primary current concern is agents accidentally damaging infrastructure", but that it increasingly runs evaluations that deliberately test escaping sandboxes.[AISI: Sandboxing] A reward-hacking agent is an adversarial guest; a threat model that assumes cooperative guests does not cover it.

Depth triage

Learn to use: the four-boundary checklist; telling which rung you are on (uname -r against the host, docker info runtimes, /dev/kvm); reading a harness's sandbox config. Recognise: the names and one-line mechanisms — runc, runsc/Sentry, Kata, Firecracker, Cloud Hypervisor, QEMU, KVM, nested virtualization. Leave to a platform or security specialist: operating gVisor or Firecracker fleets, jailer and hypervisor configuration, snapshot encryption, and the sign-off that a rung is adequate for a given model. Your job is to ask for that sign-off and to know what evidence it should rest on.

In eval work — the rung is part of the instrument

Discuss: changing isolation can change scores. AISI's Kubernetes sandbox docs say gVisor's behavioural differences "may make some Cyber misuse evals harder or impossible to solve."[AISI: Sandboxing] A task that fails under runsc and passes under runc is an observation about the environment, so account for it that way: run each task's oracle solution under the runtime you will report, exclude tasks the runtime makes unsolvable for every model, and publish the runtime with the score. VM boot time, similarly, lands in wall-clock timeouts and in cost per rollout. Design: Inspect makes the rung a configuration choice — built-in docker and local, plus external k8s, daytona, modal, ec2, proxmox and vagrant providers — behind one interface: exec() takes a command list, stdin, working directory, environment, user and timeout and returns exit code, stdout and stderr; plus read_file and write_file.[Inspect] That interface is the portable skill; everything in it is a page of this course (page 25).

Pitfall

Buying a higher rung to fix a lower-rung problem. If the answer key is in the image, the Docker API is on the network, or an API key is in the environment, a microVM faithfully isolates an agent that already has everything it needs. Fix the four boundaries first; climb the ladder for the threat that remains — kernel exploits.

Check your understanding

Your team moves a 300-task terminal benchmark from Docker on dedicated hosts to a shared Kubernetes cluster running gVisor. Pass rate for the same model falls from 54% to 49%, and mean rollout time rises by 40%. The platform team says: "It's more secure, and five points is noise." What do you need to establish before the new numbers replace the old?

Reveal the reasoning

Observed: a score drop and a slowdown coinciding with a runtime change. Supposed: noise. Three hypotheses predict different evidence. (a) Noise: then per-task flips go both ways in similar numbers, and repeated runs on the old setup show a comparable spread — check the run-to-run variance before calling anything noise. (b) Compatibility: flips are one-directional and concentrated in a few tasks; transcripts show unimplemented-syscall or /proc errors, Operation not permitted, tools behaving differently. (c) Time: flips concentrate in tasks near the timeout; failures are exit 124/137 or harness timeouts, not wrong answers. The discriminating test needs no model: run all 300 oracle solutions under gVisor with the production timeout. Oracle failures are environment defects — fix or exclude those tasks for all models; if slower rollouts hit the limit, recalibrate the timeout with headroom and say so. Then report completed / scheduled and correct / completed alongside the headline, and name the runtime. "More secure" and "same measurement" are separate claims, and only the first has been shown.

Lab

Container lab (from your Mac's terminal). This page's higher rungs need a Linux host with KVM, which a Mac's Docker VM does not offer, so the lab is about identifying rungs and reasoning about them.

  1. Reproduce. Show that three images share one kernel and one boot ID. Then find the kernel's name for your Docker host and explain the linuxkit (or other) suffix.
    Solution 
    $ for i in ubuntu:24.04 debian:bookworm-slim alpine:3.20; do docker run --rm $i uname -r; done
6.10.14-linuxkit
6.10.14-linuxkit
6.10.14-linuxkit

    The suffix is the kernel build of Docker Desktop's hidden Linux VM (page 1). Note what that means for a Mac user: your containers are already inside a VM, but all of them share that VM's kernel, so between containers nothing has changed.

  2. Predict, then verify. Which rungs could this Docker host offer? Predict the output of docker info's runtime list, of ls -l /dev/kvm inside a container, and the exit code of docker run --runtime=runsc ….
    Solution 
    $ docker info --format '{{range $k, $v := .Runtimes}}{{$k}} {{end}}default={{.DefaultRuntime}}'
io.containerd.runc.v2 runc default=runc
$ docker run --rm ubuntu:24.04 ls -l /dev/kvm
ls: cannot access '/dev/kvm': No such file or directory
$ docker run --rm --runtime=runsc ubuntu:24.04 true; echo "exit=$?"
docker: Error response from daemon: unknown or invalid runtime name: runsc
exit=125

    Only runc; no KVM device in the container. 125 is Docker's own failure code (page 22): in a results file this is an infrastructure failure — the rollout never started.

  3. Predict, then verify. AISI's docs suggest dmesg | grep gvisor to tell whether a container runs under gVisor.[AISI: Sandboxing] What happens when you run dmesg in a default runc container as root, and why?
    Solution 
    $ docker run --rm ubuntu:24.04 bash -c 'dmesg | head -2'
dmesg: read kernel buffer failed: Operation not permitted

    The kernel log belongs to the shared host kernel; reading it is a privileged operation, and Docker's default capability set does not include CAP_SYSLOG (page 21). The refusal is itself a small piece of evidence that you are talking to the real host kernel through Docker's policy.

  4. Eval task: write the profile. Give the AISI-style profile (Tx.Hx.Nx) for (a) run-hardened.sh from page 23; (b) a multiple-choice benchmark scored by string match; (c) an Inspect task whose author supplied a compose.yaml with no network_mode line.
    Solution

    (a) T0.H1.N2: unrestricted shell, local Docker, --network none. (b) T2, and H/N are moot — nothing executes. (c) T0.H1.N0 — and probably by accident: Inspect's generated default sets network_mode: none, but a user-supplied compose file replaces it, and Compose's own default has outbound access.[Inspect] The audit step: run the reachability probe from page 19 inside a live sample rather than trusting either file.

  5. Eval task: four boundaries. A vendor says: "Every rollout runs in its own Firecracker microVM, restored from one golden snapshot taken after we log the agent's tools in to our package mirror." Write one question per boundary.
    Solution

    Isolation: is the VMM started through the jailer, and what on the host can the VMM's user reach? Egress: Firecracker filters nothing — what host-level rules apply to the guest's network device, and can a guest reach the host's API, the metadata address, or other guests? Tenancy: every clone shares the snapshot's identifiers and any userspace random state; are rollouts seeded after restore, and is anything written back to shared storage? Secrets: the login happened before the snapshot, so the mirror credential is in every guest's memory and in the memory file on disk — who can read that file, is it encrypted, and can the credential be scoped read-only or injected after restore instead?
