Module 2 · Identity & Permissions

Users, groups, and root

Every process on a Linux box runs as somebody, and that identity decides what it may read, change, and kill. This page explains who a process "is", what makes root different, and why the identity your agent runs under is one of the first things to check in any eval environment.

The kernel knows numbers; names are a lookup

This page begins the third audit question, who owns what? Start by asking who you are. The examples use the course's running example: a container started from the hardened wordfreq-bench image, in which the agent's commands run as a user called agent. 

$ whoami
agent
$ id
uid=1001(agent) gid=1001(agent) groups=1001(agent)
$ grep -E '^(Uid|Gid|Groups):' /proc/self/status
Uid:	1001	1001	1001	1001
Gid:	1001	1001	1001	1001
Groups:	1001

The second command is the honest one. A process carries a set of integers: a user ID, a group ID, and a list of supplementary group IDs.[credentials(7)] The kernel's view, in /proc/self/status, contains no names at all. (The four columns are the real, effective, saved and filesystem IDs. They differ only in special situations such as setuid programs; the filesystem ID, which shadows the effective one, is what file permission checks use.[credentials(7)]) The word agent comes from a text file that tools like id and ls consult to make their output readable: 

$ getent passwd agent
agent:x:1001:1001::/home/agent:/bin/bash
$ head -n 3 /etc/passwd
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
bin:x:2:2:bin:/bin:/usr/sbin/nologin

The /etc/passwd file has one line per account and exactly seven colon-separated fields:[credentials(7)]

agent : x : 1001 : 1001 : : /home/agent : /bin/bash │ │ │ │ │ │ │ │ │ │ │ │ │ └ login shell │ │ │ │ │ └ home directory (sets $HOME) │ │ │ │ └ comment / full name (empty here) │ │ │ └ primary GID (other groups: /etc/group) │ │ └ UID: the number the kernel actually uses │ └ "x": the password hash lives in /etc/shadow └ login name: a label for humans

getent passwd NAME is the lookup itself; prefer it to grepping the file. Because names are only a lookup, a file can be owned by a number that has no name, and ls then shows the bare number. As root: 

# touch /srv/orphan && chown 4242:4242 /srv/orphan && ls -l /srv/orphan
-rw-r--r-- 1 4242 4242 0 Sep 21 21:16 /srv/orphan
# ls -l /app/wordfreq.py; ls -ln /app/wordfreq.py
-rw-r--r-- 1 agent agent 765 Sep 21 06:08 /app/wordfreq.py
-rw-r--r-- 1 1001 1001 765 Sep 21 06:08 /app/wordfreq.py

ls -n skips the lookup and prints what is really stored. Make it a habit in containers, for a reason that arrives in a few sections.

The other two files: /etc/shadow and /etc/group

$ ls -l /etc/passwd /etc/shadow /etc/group
-rw-r--r-- 1 root root   517 Sep 21 06:29 /etc/group
-rw-r--r-- 1 root root   929 Sep 21 06:29 /etc/passwd
-rw-r----- 1 root shadow 529 Sep 21 06:29 /etc/shadow
$ cat /etc/shadow; echo "exit status: $?"
cat: /etc/shadow: Permission denied
exit status: 1

/etc/passwd must be readable by everyone, because every ls -l needs it. Password hashes were therefore moved to the shadow file, which "must not be readable by regular users".[credentials(7)] Read as root, the interesting field is the second: 

# grep -E '^(root|ubuntu|agent):' /etc/shadow
root:*:20707:0:99999:7:::
ubuntu:!:20707:0:99999:7:::
agent:!:20717:0:99999:7:::

A * or ! there is not a valid hash, so no password will ever match: nobody can log in to these accounts with a password.[credentials(7)] That is normal for a container, which nobody logs in to. It is also why an agent that tries su - to become root gets su: Authentication failure.

A group is a named GID with a member list, stored in /etc/group as name:password:GID:user_list. Each user has one primary group (the GID field in passwd) and any number of supplementary ones. Groups exist so that a file can be shared with some users and not others; page 8 puts them to work. 

$ getent group agent sudo shadow
agent:x:1001:
sudo:x:27:ubuntu
shadow:x:42:
Background — why is agent 1001 and not 1000?

The ubuntu:24.04 image ships with a ready-made ordinary account, ubuntu, at UID 1000, so the first user you add gets 1001. Look at the sudo line above: that account is already a member of group sudo, even though the image contains no sudo program. Debian's slim image has no UID-1000 user at all. A harness configured to "run as uid 1000" is therefore a different identity with different group memberships on the two base images (both observations from running the images).

Root is UID 0, and what that buys

One UID is special. The account with user ID 0, conventionally named root, is the superuser: traditionally, a process with effective UID 0 bypasses all kernel permission checks.[capabilities(7)] The agent made itself a private file; watch who can read it: 

$ echo "agent private notes" > ~/private.txt; chmod 600 ~/private.txt; ls -l ~/private.txt
-rw------- 1 agent agent 20 Sep 21 21:17 /home/agent/private.txt
$ docker exec -u 1000 lt-07-box cat /home/agent/private.txt    # from the Mac, as user ubuntu
cat: /home/agent/private.txt: Permission denied
$ docker exec -u 0 lt-07-box cat /home/agent/private.txt       # as root
agent private notes

The mode 600 means "owner only", and root is not the owner. Root simply is not subject to the question. The same goes for killing other users' processes, changing any file's owner, installing packages, editing /etc/passwd, and binding low ports.

Since Linux 2.2 that all-or-nothing privilege has been split into separate units called capabilities, such as "bypass file permission checks" or "change file ownership".[capabilities(7)] Root is powerful because a root process normally holds them. Take them away and UID 0 is just another number: 

$ docker run --rm --user 0 --cap-drop ALL wordfreq-bench:hardened \
    bash -c 'id; cat /home/agent/.bashrc | head -n 1; ls /home/agent'
uid=0(root) gid=0(root) groups=0(root)
cat: /home/agent/.bashrc: Permission denied
ls: cannot open directory '/home/agent': Permission denied

Depth triage: at this point you need only recognize the word "capabilities" and the idea that root's power is itemised and removable. Page 21 teaches how to read and set them. Docker gives a container's root a reduced default set of 14, which still includes the file-permission bypass (DAC_OVERRIDE),[Docker: run] so inside an ordinary container, root reads everything, as the docker exec -u 0 above showed.

Accounts that are not people

Most lines in /etc/passwd belong to nobody you could meet: 

$ grep -c nologin /etc/passwd
16
$ getent passwd www-data
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin

These are service accounts: identities created so that a piece of software (a web server, the package downloader _apt) can run as something other than root and own only its own files. Their shell is /usr/sbin/nologin, a program that refuses interactive logins. This is least privilege as ordinary practice: a bug in the web server can then damage only what www-data may touch. An eval environment's agent user is the same idea applied to a model.

Creating users, becoming users

Account management is root's job. The four commands that cover what eval images need:

# useradd -m -s /bin/bash reviewer      # -m: create /home/reviewer   -s: login shell
# id reviewer
uid=1002(reviewer) gid=1002(reviewer) groups=1002(reviewer)
# groupadd graders
# usermod -aG graders reviewer          # -aG: append to supplementary groups
# id reviewer
uid=1002(reviewer) gid=1002(reviewer) groups=1002(reviewer),1003(graders)
# passwd -l reviewer                    # lock: no password login
passwd: password changed.
# su - reviewer -c 'whoami; pwd; id'
reviewer
/home/reviewer
uid=1002(reviewer) gid=1002(reviewer) groups=1002(reviewer),1003(graders)

useradd edited /etc/passwd, /etc/shadow and /etc/group for you (here it also created a group named after the user). Forgetting the -a in usermod -aG replaces the user's supplementary groups instead of adding one. su - USER ("substitute user") starts a login shell as that user: the dash gives you their home directory and environment, where plain su USER keeps your current directory. Root may su to anyone without a password; anyone else is asked for the target's password, which, as you saw, these accounts do not have. In an unprivileged account the same commands fail, and the error messages are worth recognising in a transcript: 

$ useradd eve; echo "exit status: $?"
useradd: Permission denied.
useradd: cannot lock /etc/passwd; try again later.
exit status: 1
$ apt-get install -y sudo 2>&1 | tail -n 1
E: Unable to acquire the dpkg frontend lock (/var/lib/dpkg/lock-frontend), are you root?

sudo: borrowed root, by policy

sudo "allows a permitted user to execute a command as the superuser or another user, as specified by the security policy";[sudo(8)] the policy lives in /etc/sudoers and /etc/sudoers.d/. On your Mac or a cloud VM it is how you become root. In a minimal container image it usually does not exist: 

$ sudo -l; echo "exit status: $?"
bash: sudo: command not found
exit status: 127

None of the course's three base images ships sudo; their default user is already root.[sudo(8)] So sudo: command not found in a transcript is a fact about the environment, not a mistake by the model (although an agent that keeps retrying it is telling you something). When an image builder does install it, the question is what the policy grants. Here root has installed sudo and written one rule for agent: 

# echo 'agent ALL=(ALL) NOPASSWD: /usr/bin/apt-get' > /etc/sudoers.d/agent && chmod 440 /etc/sudoers.d/agent
$ sudo -l
…
User agent may run the following commands on 5a3a9ce9e54f:
    (ALL) NOPASSWD: /usr/bin/apt-get
$ sudo apt-get --version | head -n 1
apt 2.8.3 (arm64)
$ sudo -n cat /etc/shadow; echo "exit status: $?"
sudo: a password is required
exit status: 1

sudo -l lists what the invoking user may run: the audit command. NOPASSWD removes the authentication step for the listed commands;[sudo(8)] anything else demands a password the account does not have. -n (non-interactive) makes sudo fail at once instead of prompting, which is what you want in any script or agent tool. With the rule widened to NOPASSWD: ALL, which is what image builders write when they want the agent to "be able to install things", the account is root in all but name: 

$ sudo id
uid=0(root) gid=0(root) groups=0(root)
$ sudo cat /etc/shadow | head -n 1
root:*:20707:0:99999:7:::
Pitfall — a narrow-looking sudo rule is rarely narrow

A rule that allows only a package manager, an editor, or an interpreter as root allows running arbitrary code as root, because those programs run other programs. Treat any NOPASSWD line in an agent's sudo -l output as "the agent is root" unless you can argue otherwise for that specific command. If the agent needs a package, install it when the image is built.

How does sudo do it? It is an ordinary program file with a special mode bit, setuid, that makes it start with its owner's UID (root) rather than the caller's; page 8 covers the bit. That has a useful consequence. Linux has a per-process flag, no_new_privs, under which executing a file can no longer grant privileges: setuid bits are ignored, and the flag is inherited by all children and cannot be unset.[seccomp(2)] Docker sets it with --security-opt no-new-privileges. Same image, same blanket sudo rule, one extra flag: 

$ docker run --rm --user agent --security-opt no-new-privileges lt-07-sudo-img \
    bash -c 'sudo id; echo "exit status: $?"; grep NoNewPrivs /proc/self/status'
sudo: The "no new privileges" flag is set, which prevents sudo from running as root.
sudo: If sudo is running in a container, you may need to adjust the container configuration to disable the flag.
exit status: 1
NoNewPrivs:	1

The sudo manual names this exact situation as the likely cause of that message.[sudo(8)] The course's run-hardened.sh sets the flag (page 23), so even a sloppy sudoers file in the image could not hand the agent root.

Identity is inherited, and Docker's default is root

A new process gets copies of its parent's user and group IDs.[credentials(7)] Everything the agent's shell starts is agent, all the way down: 

$ id -u; bash -c 'id -u; sh -c "id -u"'
1001
1001
1001

So the identity of a whole rollout is decided once, by whoever starts the first process. In a container that is Docker, and "the default user within a container is root (uid = 0)"; an image can change the default with a USER line in its Dockerfile, and --user overrides both at run time.[Docker: run] 

$ docker run --rm ubuntu:24.04 id
uid=0(root) gid=0(root) groups=0(root)
$ docker run --rm wordfreq-bench:hardened id                # Dockerfile says USER agent
uid=1001(agent) gid=1001(agent) groups=1001(agent)
$ docker run --rm --user 0 wordfreq-bench:hardened id       # …and the caller can still override it
uid=0(root) gid=0(root) groups=0(root)
$ docker inspect -f '{{.Config.User}}' wordfreq-bench:hardened
agent
$ docker inspect -f '{{.Config.User}}' wordfreq-bench:sloppy

An empty Config.User means root. That one-line docker inspect is the fastest identity check you can run on a task image without starting it. Notice also that USER is a default, not a lock: anyone who controls the docker run or docker exec command line chooses the UID. That is a feature, as the next box explains. --user accepts raw numbers, which produces a process whose UID has no name: 

$ docker run --rm --user 12345 ubuntu:24.04 bash -c 'id; whoami; echo "HOME=$HOME"'
uid=12345 gid=0(root) groups=0(root)
whoami: cannot find name for user ID 12345
HOME=/

Everything works, since the kernel never needed the name, but tools that want a home directory or a username may misbehave. Look at the highlighted part: a bare --user UID left the group as 0. Group root owns a lot of files. Write --user 12345:12345 (which printed uid=12345 gid=12345 groups=12345).

In eval work — design

If the agent is root, every file-permission protection in the box is void: hidden tests, an answer key, the grader's scripts, other users' files, all readable and writable regardless of their mode bits. Yet tasks routinely require installing software, which needs root. The standard resolutions, in order of preference: (1) install everything at image build time, where RUN lines execute as root, then drop to a non-root USER — Docker's own guidance is to use USER when a service can run without privileges and to avoid installing sudo in images;[Docker: Dockerfile] (2) if the task genuinely is system administration, let the agent be root, and move everything you need to protect out of the box: grade from outside (page 26). What does not work is root agent plus in-box secrets plus hope.

The harness can also use two identities in one box. Inspect's bash() tool and its sandbox exec() both take a user parameter ("User to execute commands as"),[Inspect] so agent commands can run as agent while setup and scoring commands run as root: the equivalent of the docker exec -u 0 used on this page. Terminal-Bench's current harness has the same pair of settings, agent.user and verifier.user, and if they are not set it uses the container's default, "typically root".[Terminal-Bench] When you read a benchmark's config, find these settings first.

UIDs across boundaries: same number, different name

Each container image brings its own /etc/passwd, but files store only numbers. When storage is shared between boxes — a Docker volume, a bind mount of a host directory, files copied out with docker cp — the numbers travel and the names do not. Here the agent writes a file to a volume, and two other containers look at it: 

$ docker run --rm -v lt-07-shared:/work wordfreq-bench:hardened \
    bash -c 'id -un; echo "patched" > /work/notes.txt; ls -l /work/notes.txt'
agent
-rw-r--r-- 1 agent agent 8 Sep 21 21:17 /work/notes.txt
$ docker run --rm -v lt-07-shared:/work alpine:3.20 ls -l /work/notes.txt
-rw-r--r--    1 1001     1001             8 Sep 21 21:17 /work/notes.txt
$ docker run --rm -v lt-07-shared:/work debian:bookworm-slim \
    bash -c 'useradd -u 1001 mallory; ls -l /work/notes.txt; ls -ln /work/notes.txt'
-rw-r--r-- 1 mallory mallory 8 Sep 21 21:17 /work/notes.txt
-rw-r--r-- 1 1001 1001 8 Sep 21 21:17 /work/notes.txt

One file, three answers to "who owns this?": agent, nobody, and mallory. Only ls -n is stable. And ownership is not cosmetic: in the third container, mallory really does have the owner's rights over that file, because the kernel compares numbers. (The volume's root directory had to be chowned to agent first, as root; a fresh volume belongs to root and the agent's write failed with Permission denied until then.)

Caveat — your Mac is not a Linux host

The brief for this experiment would normally use a bind mount of a host directory. On Docker Desktop for Mac there is a file-sharing layer between macOS and the Linux VM that rewrites ownership: on the authoring machine a file owned by Mac UID 501 appeared inside the container as owned by 0 0. Use a volume, as above, to see the real Linux behaviour, and expect the numeric-UID rule to apply in full when your harness runs on a Linux server.

In eval work — navigate

A recurring infrastructure failure: the harness bind-mounts a results directory created by the host user (say UID 1000 on a Linux CI runner), the agent runs as UID 1001, and every attempt to write its output fails with Permission denied. Every rollout scores zero, identically for every model. Observed: a permission error on a mounted path. Hypothesis: UID mismatch across the mount. Discriminating test: id -u and ls -ldn on the mount point from inside the box; if the numbers differ and the mode has no write bit for "other", that is the cause. Record such rollouts as infrastructure failures, not model failures: they belong in completed / scheduled, and should not silently drag down correct / scheduled. The reverse failure is quieter: the mounted directory is writable by the agent, and it contains something the agent should not be able to change.

The identity audit, in six commands

QuestionCommandWhat to look for
Who am I, really?iduid=0; membership of sudo, docker, root groups; a bare number with no name
Who will the agent be?docker inspect -f '{{.Config.User}}' IMAGEempty = root; then check the harness's own user setting
Can I become root?sudo -n -lany NOPASSWD line; "command not found" is the good answer
Would setuid work at all?grep NoNewPrivs /proc/self/status1 means sudo and every other setuid program are disarmed
Which accounts can log in?getent passwd | grep -v nologinunexpected accounts with real shells
Who owns this, really?ls -ln PATHnumbers, compared with id -u
Check your understanding

A benchmark paper says: "hidden tests are stored in /opt/tests with mode 700, owned by root, so the agent cannot access them." You are reviewing it. The released Dockerfile has no USER line, and the harness config does not mention a user. The authors add that they searched all transcripts for /opt/tests and found nothing. What is established, what is not, and what do you ask for?

Reveal the reasoning

Established: the mode bits are as described. Not established: that they constrain the agent. With no USER line and no harness-level user, Docker's default applies and the agent's commands run as UID 0, for which mode 700 is no barrier. The protection claimed in the paper is void as described.

The transcript search is weak evidence. It shows no agent typed that literal path in a logged command. It does not cover find / -name 'test_*', grep -r over the filesystem, a Python script that walks directories, or output truncated by the harness. Absence of a string is not absence of access.

Ask for: the output of id from inside a live rollout (one command settles who the agent is); whether the harness sets a user at exec time; whether no-new-privileges is set; and, better than any of these, a rerun of a sample of tasks with the tests absent from the box and grading done outside. If scores drop materially when the tests are removed, some passes depended on seeing them. Until then the reported score is an upper bound on capability, and the paper should say so.

Lab

Container lab. Exercises 1–3 work in your lt-lab container (root shell via docker exec -it lt-lab bash; learner from page 1 plays the part of agent, and has the same UID, 1001). Exercises 4–5 run docker commands from your Mac's terminal.

  1. Reproduce. As learner, run id, getent passwd learner, and grep -E '^(Uid|Gid):' /proc/self/status. Then try cat /etc/shadow. As root, read the learner line of /etc/shadow: can this account log in with a password?
    Solution

    id prints uid=1001(learner) gid=1001(learner) groups=1001(learner); cat /etc/shadow fails with Permission denied (the file is -rw-r----- root shadow). As root, grep '^learner:' /etc/shadow shows learner:!:…: the ! is not a valid hash, so no password login is possible.

  2. Predict, then verify. As root: touch /srv/orphan && chown 4242:4242 /srv/orphan. Before running ls -l /srv/orphan, write down what the owner column will show. Then run useradd -u 4242 ghost and look again.
    Solution

    First 4242 4242 (no name to look up); after the useradd, the owner column reads ghost and the group column ghost, because useradd also created group 4242. The file did not change. Only the lookup table did. ls -ln shows 4242 4242 both times. (Verified form of this on the page: mallory in the volume demo.) Clean up with userdel ghost.

  3. Groups. As root, create a group graders and a user reviewer who belongs to it as a supplementary group. Show the membership two ways. Then remove both.
    Solution 
    # useradd -m -s /bin/bash reviewer; groupadd graders; usermod -aG graders reviewer
# id reviewer
uid=1002(reviewer) gid=1002(reviewer) groups=1002(reviewer),1003(graders)
# grep -E '^(graders|reviewer):' /etc/group
reviewer:x:1002:
graders:x:1003:reviewer
# userdel -r reviewer; groupdel graders; id reviewer
userdel: reviewer mail spool (/var/mail/reviewer) not found
id: 'reviewer': no such user

    Note the primary group appears in /etc/passwd (field 4), not in the member list of /etc/group.

  4. Predict, then verify. From your Mac: what will docker run --rm --user 1000 ubuntu:24.04 id print? What about the same command with debian:bookworm-slim?
    Solution

    On Ubuntu: uid=1000(ubuntu) gid=1000(ubuntu) groups=1000(ubuntu),4(adm),20(dialout),24(cdrom),25(floppy),27(sudo),29(audio),30(dip),44(video),46(plugdev). Docker looked UID 1000 up in the image's own files and found the preinstalled ubuntu account with all its groups, including sudo. Debian's slim image has no UID-1000 entry, so you get a nameless uid=1000 with gid=0(root), like the --user 12345 example above. Same harness setting, different identity.

  5. Eval task: who is the agent? You are handed two task images, wordfreq-bench:sloppy and wordfreq-bench:hardened (build them from research/wordfreq-bench/; the README says how). Without reading the Dockerfiles, determine for each the identity agent commands would get by default, and whether the agent could become root. State which check would change if the harness ran containers with --security-opt no-new-privileges.
    Solution 
    $ docker inspect -f '{{.Config.User}}' wordfreq-bench:hardened
agent
$ docker inspect -f '{{.Config.User}}' wordfreq-bench:sloppy

$ docker run --rm wordfreq-bench:hardened bash -c 'id; sudo -n -l; echo "exit status: $?"'
uid=1001(agent) gid=1001(agent) groups=1001(agent)
bash: line 1: sudo: command not found
exit status: 127

    Sloppy: empty user, so the agent is root already and nothing in the box is protected from it. Hardened: agent, no sudo, locked passwords, so no route to root via these mechanisms; the remaining check is setuid programs (page 8). Under no-new-privileges, grep NoNewPrivs /proc/self/status prints 1 and setuid-based routes (including any sudo an image might contain) stop working, but it does nothing for the sloppy image, where the agent does not need to gain anything.
