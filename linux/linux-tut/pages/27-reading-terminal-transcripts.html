Module 7 · Linux in Eval Harnesses

Reading terminal transcripts

Error analysis for terminal agents: how to read a rollout's commands, outputs and exit codes, recognise the two dozen Linux-level failures that recur, and decide for each one whether the model failed or the environment did — before that decision gets baked into a score.

What a transcript holds, and what it doesn't

An agent's transcript is the harness's record of the conversation between a model and a sandbox. For an exec-per-call bash tool (page 25) each step holds five things: the command string the model sent, the stdout and the stderr that came back (possibly merged, possibly cut), the exit status, and — if you are lucky — a duration. Everything you will diagnose on this page is inferred from those five fields.

Just as important is what the transcript does not hold. It is a record of what the model saw, not of the box:

in the transcript not in the transcript --------------------------- ------------------------------------ argv / script the model sent the filesystem after each call stdout (maybe truncated) processes still running (background) stderr (maybe merged in) the screen, if a TTY harness is used exit status cgroup counters: oom_kill, pids max duration (sometimes) the container's own exit / OOMKilled anything `docker logs` would show the grader's view of the final state

That right-hand column is where the environment failures hide, which is why the triage procedure below always ends outside the transcript. Two facts from it, reproduced for this page. Output from a docker exec never reaches docker logs, which only records the container's main process — so "check the logs" finds nothing about what the agent ran: 

$ docker exec lt-27-box bash -c 'echo "from exec"; echo "err from exec" >&2'
err from exec
from exec
$ docker logs lt-27-box | wc -l
0

And the output itself may have been cut. Inspect caps one exec()'s output at 10 MiB and, past that, keeps only the tail and returns a successful result with no error;[Inspect] tools that show the model a window of output typically keep the end too. The end is where a test runner's progress chatter lives; the one line that mattered was printed first: 

$ python3 -c '…print FAILED to stderr, then 5000 progress lines…' 2>&1 | tail -c 300
ress line 4984
progress line 4985
…
progress line 4999

The FAILED test_counts line is gone. When a transcript shows only noise and a non-zero status, suspect front truncation before you suspect the model (page 4).

A field guide to recurring failures

Terminal-Bench's authors sampled 3,800 failed commands from agent runs and coded them. The single most frequent failure — 24.1% of all failures — was calling an executable that is not installed or not on the PATH; next came failures while running an executable, at 9.6%. Per-command error rates ranged from 9.2% to 26.7% across models.[Terminal-Bench] Their taxonomy's top-level categories — invocation, filesystem and permissions, environment and configuration, packages, network, processes — are this course's table of contents. Every row below was reproduced in Docker for this page (raw sessions in research/verify/27-reading-terminal-transcripts.txt). Read each as: what you see → the mechanism and where it is taught → whose fault, usually → the fix.

Hangs: a program waiting for a human

A command that asks a question and gets no answer waits until something kills it. The transcript shows the prompt as the last line and 124 (or 137) as the status, with a duration equal to the tool's limit. Which programs hang depends on whether the harness gives them a TTY. Exec-per-call harnesses don't, and several programs notice and behave differently:

ProgramNo TTY (exec-per-call), observedWith a TTY (tmux-style), observedMake it non-interactive
apt-get install tzdataHangs at Geographic area: → 124 when stdin is held open (p15)Same promptDEBIAN_FRONTEND=noninteractive; -y alone does not silence debconf[apt-get(8)]
git commit (no -m)error: Terminal is dumb, but EDITOR unset, exit 1Opens an editor and waits-m; GIT_EDITOR=true
git log, manNo pager: output printed in fullPager waits for a keyGIT_PAGER=cat, PAGER=cat, git --no-pager
sudo truesudo: a terminal is required to read the password, exit 1[sudo] password for agent: — waitssudo -n (fail fast); better, no sudo in the sandbox
rm -i zPrints the question, reads EOF, silently keeps the file, exit 0Waits → 124Don't use -i; alias rm='rm -i' in an image is a trap
ssh git@github.comHost key verification failed., 255Host-key question waits → 124-o BatchMode=yes; pre-seed known_hosts

Two lessons in that table. First, a TTY is not neutral: the reference agent in Terminal-Bench, Terminus 2, drives a real terminal through tmux precisely so the model can use interactive programs — vim, pagers, arrow keys — and it therefore inherits every "waits for a key" failure in the right-hand column.[Terminal-Bench] Second, the rm -i row is worse than a hang: it exits 0 and did nothing. Output changes too: ls prints one name per line into a pipe but columns with colour escape codes into a TTY, and progress bars either vanish or fill the output window.

The shell between calls

Under an exec-per-call harness every tool call is a new bash -c. Nothing that lives in a shell survives to the next call: the working directory, exported variables, an activated venv. The model sees success and assumes state: 

$ docker exec lt-27-box bash -c 'cd /tmp && export FOO=1 && pwd && echo "FOO=$FOO"'
/tmp
FOO=1
$ docker exec lt-27-box bash -c 'pwd; echo "FOO=${FOO:-unset}"'
/
FOO=unset

Background processes are the opposite case: they can survive the call, but only if they are launched right. A server started with & and its output redirected outlives a plain docker exec (re-parented to PID 1). The same server dies when the call's timeout fires, because GNU timeout signals the whole process group, or when a TTY session closes and sends SIGHUP (p9): 

$ docker exec lt-27-box bash -c 'timeout 3 bash -c "python3 -m http.server 8003 >/dev/null 2>&1 & echo started; sleep 30"; echo "exit=$?"; curl -sS localhost:8003 -o /dev/null'
started
exit=124
curl: (7) Failed to connect to localhost port 8003 after 0 ms: Couldn't connect to server

Finally, files written by here-document. A model that writes code with an unquoted <<EOF hands every $ in that code to the shell first. $0 became bash, $HOME became /root, and \$5 lost its backslash; quoting the delimiter, <<'EOF', writes the text verbatim (p4): 

# cat > fix.py <<EOF
print(f"usage: $0 FILE -> {len(words)} words, cost \$5, home $HOME")
EOF
# cat fix.py
print(f"usage: bash FILE -> {len(words)} words, cost $5, home /root")

Two more quiet ones. GNU grep -E '\d+' does not mean "digits": ERE has no \d, and printf 'run 12\nrun d\n' | grep -E 'run \d+' prints run d and exits 0 — use [0-9] or grep -P (Appendix D). And a container's clock is UTC unless told otherwise, with LANG unset: a task that checks a date or sorts text can disagree with the author's laptop.

Pitfall — reading the model's narration instead of the output

Models summarise their own tool results ("tests pass now") and the summary is sometimes wrong: a status of 0 from cmd | tail is tail's (p4), rm -i exits 0 having deleted nothing, and apt-get update exits 0 offline. Code the tool results, not the assistant turns.

The triage procedure

Given a failed rollout, work outward from the last call, and write down which statements are observed and which are hypotheses:

  1. Exit status of the last failing call, decoded (p10, Appendix B). 124/137/143 mean the run was cut; 126/127 mean the command never ran.
  2. The last lines of stderr — and whether you are seeing the whole output or a truncated tail.
  3. Duration vs the limit. A call that took exactly the tool timeout was waiting or throttled; a 137 after two seconds was not a timeout.
  4. Environment counters, from outside the transcript: memory.events, pids.events, df, docker inspect … State.
  5. Reproduce: docker exec -u <same user> -w <same dir> the same argv, with no TTY, in a fresh copy of the same image. If it fails the same way for you, it is not the model's doing.
In eval work — navigate

Step 5 is what turns a story into evidence. "The agent couldn't install pytest" is a hypothesis about the model; "pip is absent from the image, and pip install from a fresh container as uid 1001 also exits 127" is an observation about the environment. Anthropic's rule is not to take scores at face value "until someone digs into the details of the eval and reads some transcripts";[Anthropic: Agent Evals] reading them with this procedure is how you find the task that fails for every model for the same Linux reason — a broken task, not a hard one. The sibling course covers error analysis in general.

A coding scheme, and failure accounting

Error analysis needs categories fixed in advance. For terminal rollouts, five cover almost everything this page has shown:

CodeMeaningExample from the field guideCounts against
MC model-capabilityThe model didn't know how to solve the taskWrong algorithm, tests fail with status 1The model
MF model-Linux-fluencyThe model knew the fix but fumbled the boxUnquoted heredoc, pytest when the README says unittest, state assumed across callsThe model — but report separately
ED environment-defectThe box made a valid approach failNo CA bundle, pids.max of 3, missing tool the task promisedThe benchmark
HD harness-defectThe harness lost or mangled the runTruncated output, killed background children, container exit code recorded as the rollout'sThe benchmark
IV integrity-violationThe "pass" didn't come from doing the taskFix copied from git history (p26)Neither: it's a hole to close and a rate to report

MF and ED must be separated before any score is reported, because they look the same in a transcript — a command fails — and they move in opposite directions when you fix the environment. Terminal-Bench 2.1 is the worked case: fixing 28 of 89 tasks (changed external dependencies, resource budgets too small for a valid solution, a misspecified test) moved one agent from 58.0% to 70.1% with no model change.[Terminal-Bench] On resources alone, Anthropic measured Terminal-Bench 2.0's infrastructure error rate falling from 5.8% under strict limits to 0.5% uncapped, and concluded that leaderboard gaps under 3 points "deserve skepticism until the eval configuration is documented and matched."[Anthropic: Infra Noise]

Then account for every rollout. Each scheduled rollout ends in exactly one recorded outcome — passed, failed (MC/MF), or not completed (ED/HD, timeouts, kills) — and none is dropped. An invented run of 100 rollouts, 80 on easy tasks and 20 on hard ones, where infrastructure failures hit hard tasks harder (they run longer and use more memory):

ScheduledNot completed (infra)CompletedCorrect
Easy tasks8047660
Hard tasks208123
Total100128863

Reported three ways: correct/scheduled = 63/100 = 0.63; correct/completed = 63/88 ≈ 0.72; completed/scheduled = 0.88. The middle number is the tempting one, and it is biased: the rollouts that fell out were disproportionately hard ones, so the completed set is easier than the benchmark. Hard tasks are 20% of what was scheduled but only 14% (12/88) of what completed. A runner that "drops infrastructure errors" has silently changed the task mix. Publish all three, with counts per category, and pick the primary metric before looking (page 10's account.py does the arithmetic for a results.jsonl).

In eval work — design and measure

Put the code in the rollout record. Add a failure_code field (MC/MF/ED/HD/IV/none) beside exit_code, oom_killed, timed_out and duration_s. Code ED and HD first, from counters and reproduction, because they can be decided mechanically; then fix those tasks and re-run before arguing about MC vs MF. A model that loses 10 points to MF on your benchmark and 2 on another is telling you something real about terminal fluency — but only once ED is out of the numerator.

Caveat

The codes are judgments. Is pytest: command not found MF or ED? It depends on what the task promised — which is why the scheme needs written rules ("a tool the task instructions name is the environment's responsibility") and a second coder on a sample, not a feeling per transcript.

Practice: three transcripts

Each transcript is constructed for wordfreq-bench, but every command's output is real, run against the course's images. Classify each with the scheme, and say what evidence you would add before recording it.

Transcript A — hardened sandbox (run-hardened.sh), task README says Run the visible tests with PYTHONPATH=. python3 -m unittest discover -s tests.

$ cd /app && pytest
bash: line 1: pytest: command not found           # exit 127
$ pip install pytest
bash: line 1: pip: command not found              # exit 127
$ cd /app && python3 -m pytest
/usr/bin/python3: No module named pytest          # exit 1
[model: "The environment is broken; I cannot run tests." Ends turn.]
Classification

MF, model-Linux-fluency. The environment matched its promise: the README names unittest, and running that exact command in the same sandbox prints Ran 1 test … OK with exit 0. Three calls hit the most common failure Terminal-Bench found (not installed / not on PATH), and the model's "environment is broken" is narration, not evidence. Record it as a fail, coded MF. Had the README said "run pytest", the same transcript would be ED.

Transcript B — a sandbox from a colleague's new launcher. First call, 15 s:

$ cd /app && python3 -m unittest discover -s tests 2>&1 | tail -3
bash: fork: retry: Resource temporarily unavailable
bash: fork: retry: Resource temporarily unavailable
bash: fork: retry: Resource temporarily unavailable
bash: fork: retry: Resource temporarily unavailable
bash: fork: Resource temporarily unavailable          # exit 254
$ ls /app | wc -l
bash: fork: retry: Resource temporarily unavailable
…                                                   # exit 254
Classification

ED, environment-defect. fork failing with EAGAIN on a trivial pipeline is the pids limit (page 12). Discriminating evidence, from outside: docker inspect --format '{{.HostConfig.PidsLimit}}' printed 3, and in the container pids.max is 3 and pids.events reads max 10. The agent never had a chance. Record as not-completed, infrastructure; fix the launcher; re-run every rollout it started — they share the cause, so they are not independent failures.

Transcript C — sloppy build (wordfreq-bench:sloppy). Final tests pass.

# git log --all --oneline | head -5
bb4b24a wordfreq: initial import
6301071 count words case-insensitively, ignore punctuation (fixes #12)
# git show upstream-fix:wordfreq.py > wordfreq.py && git status --short
 M wordfreq.py
# python3 -m unittest discover -s tests 2>&1 | tail -3
Ran 1 test in 0.001s

OK
Classification

IV, integrity-violation — and an environment bug, not a model skill. The pass came from the fix commit shipped in the image's git history (page 26). Record it as a pass the grader gave and flag it; report the cheat rate beside the pass rate; close the surface (export the tree without .git) and re-run. Whether it is "cheating" depends on the instructions; that it measures nothing about fixing the bug does not.

Check your understanding

On your benchmark, model X fails 14 of 200 rollouts with exit 124 on the agent's apt-get install; model Y has none, because it always passes DEBIAN_FRONTEND=noninteractive. A colleague proposes removing those 14 rollouts as "infrastructure noise" and comparing correct/completed. What do you say?

Reveal the reasoning

Observed: 14 timeouts, all at an apt-get install, only for X. Hypothesis to test: they are the tzdata (or another debconf) prompt. Discriminate by reading the last stdout lines (Geographic area:?) and reproducing the exact argv in a fresh container without a TTY. If confirmed, this is not infrastructure noise: the same environment let Y succeed, so it is MF — a real difference in Linux fluency — and dropping the rollouts would erase exactly the difference being measured, and bias X's conditional score upward if those tasks are harder. Keep them as failures coded MF, report all three ratios, and separately decide whether the benchmark wants to measure debconf fluency — if not, set DEBIAN_FRONTEND in the image (an ED fix) and re-run both models.

Lab

Container lab. Setup: docker run -d --name lt-27-lab ubuntu:24.04 sleep 3600. Remove it at the end with docker rm -f lt-27-lab.

  1. Reproduce. Show that working directory and exports don't survive between two docker exec calls.
    Solution 
    $ docker exec lt-27-lab bash -c 'cd /tmp && export FOO=1 && pwd'
/tmp
$ docker exec lt-27-lab bash -c 'pwd; echo "FOO=${FOO:-unset}"'
/
FOO=unset

    Each exec is a new process with the container's default cwd and environment.

  2. Predict, then verify. Without a network, what do apt-get update and then apt-get install -y curl exit with? Write both numbers down first. Run: docker run --rm --network none ubuntu:24.04 bash -c 'apt-get update >/dev/null 2>&1; echo "update=$?"; apt-get install -y curl 2>&1 | tail -1; echo "install=${PIPESTATUS[0]}"'
    Solution 
    update=0
E: Unable to locate package curl
install=100

    The update only warns about failed fetches; the error surfaces one step later with a misleading message.

  3. Predict, then verify. What does printf 'run 12\nrun d\n' | grep -E 'run \d+' print in the container? Then fix the pattern.
    Solution 
    $ docker exec lt-27-lab bash -c "printf 'run 12\nrun d\n' | grep -E 'run \d+'"
run d
$ docker exec lt-27-lab bash -c "printf 'run 12\nrun d\n' | grep -E 'run [0-9]+'"
run 12
  4. Hangs vs no TTY. Run docker exec lt-27-lab bash -c 'touch /tmp/z; rm -i /tmp/z; echo "exit=$?"; ls /tmp/z'. Did anything hang? Was the file removed? What would a transcript-reader conclude from the exit status alone?
    Solution 
    rm: remove regular empty file '/tmp/z'? exit=0
/tmp/z

    No hang: with no TTY, rm read end-of-file as "no". Exit 0 and the file is still there — the status alone says success.

  5. Eval task. A harness reports a rollout's final call curl -sS https://pypi.org/simple/ -o /dev/null failed with 77 in a sandbox built FROM ubuntu:24.04 plus apt-get install -y --no-install-recommends curl. Code it MF or ED, and prove it by reproduction.
    Solution 
    $ docker run --rm ubuntu:24.04 bash -c 'apt-get update -qq && apt-get install -y -qq --no-install-recommends curl >/dev/null 2>&1; curl -sS https://example.com -o /dev/null; echo "exit=$?"'
curl: (77) error setting certificate file: /etc/ssl/certs/ca-certificates.crt
exit=77

    ED: the image has no CA bundle, so every HTTPS call fails for every model. Fix: add ca-certificates to the image and re-run.
