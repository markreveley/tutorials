Packages and reproducible environments

Software gets into a Linux box through package managers, and every one of them, by default, installs "whatever is current today". This page teaches the apt and pip mechanics you will read in Dockerfiles and transcripts, and then the part that matters for measurement: why the same Dockerfile builds a different environment next month, and how to pin, fingerprint and publish an environment so a score can be reproduced.

What a package manager does

A package manager does four jobs. It knows a set of repositories — servers holding packages. It keeps a local index of what those servers offer. Asked to install something, it resolves dependencies — the other packages that one needs — into a consistent set. Then it downloads, unpacks, and runs each package's install scripts as root. On Debian and Ubuntu the work is split: dpkg installs and records individual .deb files, and apt sits above it handling repositories, the index and dependency resolution.

The apt workflow, and the errors it produces

Official Docker images ship with the index deleted to save space, so the first install in a fresh container fails in a way that looks like a typo: 

# ls /var/lib/apt/lists/ | wc -l
0
# apt-get install -y curl; echo "exit=$?"
Reading package lists...
Building dependency tree...
Reading state information...
E: Unable to locate package curl
exit=100

The package exists; the box has no index to find it in. apt-get update "is used to resynchronize the package index files from their sources"[apt-get(8)] — it upgrades nothing, it only downloads the catalogue (22 files, 54 MB here). Hence the idiom you saw in the wordfreq-bench Dockerfile (page 22): 

RUN apt-get update && apt-get install -y --no-install-recommends python3 \
    && rm -rf /var/lib/apt/lists/*
PieceWhat it does
apt-get, not aptapt(8) says of itself that it "is designed as an end-user tool and it may change behavior between versions", and that scripts should prefer apt-get and apt-cache, which "keep backward compatibility as much as possible".[apt(8)] Run apt in a pipe and it prints "WARNING: apt does not have a stable CLI interface."
-y"Automatic yes to prompts" — apt's own "Do you want to continue?".[apt-get(8)] It does not answer questions asked by packages (next section).
--no-install-recommends"Do not consider recommended packages as a dependency for installing" — only hard dependencies. Smaller image, fewer moving parts.
update && install in one RUNDocker caches a RUN by its command string, so a separate RUN apt-get update layer is reused forever and later installs meet a stale index.[Docker: Dockerfile]

The prompt that hangs a build

Some packages ask configuration questions through a system called debconf. With nobody to answer, the install waits forever. Executed in a fresh container with stdin held open and a 45-second timeout: 

# timeout 45 apt-get install -y tzdata; echo "exit=$?"
…
Setting up tzdata (2026c-0ubuntu0.24.04.1) ...
debconf: unable to initialize frontend: Dialog
debconf: (TERM is not set, so the dialog frontend is not usable.)
debconf: falling back to frontend: Readline
…
debconf: falling back to frontend: Teletype
Configuring tzdata
------------------
Please select the geographic area in which you live. …
  1. Africa      4. Arctic    7. Australia  10. Pacific
  2. America     5. Asia      8. Europe     11. Etc
  3. Antarctica  6. Atlantic  9. Indian     12. Legacy
Geographic area: 
exit=124

Exit 124 is timeout's, not apt's (page 10). tzdata is not in the ubuntu:24.04 image, and it arrives as a dependency of python3 — so the most ordinary install an agent can attempt walks into this. The fix is debconf's noninteractive frontend, which "never interacts with you at all, and makes the default answers be used for all questions":[debconf(7)] write DEBIAN_FRONTEND=noninteractive apt-get install -y …, per command. Docker's reference advises against baking it in with ENV, because it persists into the running container and "may confuse users of your image".[Docker: Dockerfile]

In eval work — navigate

In a transcript this looks like a tool call that never returns and is eventually killed by the harness's timeout, often consuming the agent's whole time budget. Whether it counts against the model is a design decision to make before the run: either the task image sets the agent up to succeed (tools preinstalled, or the variable set for the agent's shell), or handling interactive prompts is declared part of the skill under test. What you must not do is discover it afterwards and quietly drop those samples.

Pitfall — apt-get update fails with exit 0

In a --network none container, apt-get update printed four "Failed to fetch" warnings and the line "Some index files failed to download. They have been ignored, or old ones used instead." — and exited 0. The following apt-get install -y curl then said E: Unable to locate package curl, exit 100. An agent (or you) reading only the last error concludes the package name is wrong. The evidence that discriminates is one command up: read the W: lines.

Alpine: a different userland

Many task images are built on Alpine, which "is built around musl libc and busybox" and "uses its own package manager called apk".[Alpine] The idiom is apk add --no-cache python3 — index fetched, used and not kept (/var/cache/apk was empty afterwards). No bash unless you add it (page 2). The deeper difference is the C library, musl rather than glibc. Ubuntu's ls binary, copied into an Alpine container: 

# ls -l /x/ls-glibc
-rwxr-xr-x    1 root     root        199464 Sep 21 16:28 /x/ls-glibc
# /x/ls-glibc /; echo "exit=$?"
sh: /x/ls-glibc: not found
exit=127
# ls /lib/ld-*
/lib/ld-musl-aarch64.so.1

The file is there and executable; what is "not found" is the glibc loader the binary names as its interpreter. For Python the same split means prebuilt wheels tagged manylinux do not apply: musl-based distributions "cannot use the existing manylinux platform tags" and have their own musllinux tag.[PEP 656] A project that publishes no such wheel leaves pip with only the source distribution to build from, on an image that may have no compiler. Recognise "exit 127 on a file that exists" and "pip is suddenly compiling C" as Alpine symptoms, not model errors.

The Python layer: pip, venvs, and PEP 668

On Ubuntu 24.04 the system Python belongs to apt, and pip refuses to touch it: 

# pip install requests; echo "exit=$?"
error: externally-managed-environment

× This environment is externally managed
╰─> To install Python packages system-wide, try apt install
    python3-xyz, where xyz is the package you are trying to
    install.

    If you wish to install a non-Debian-packaged Python package,
    create a virtual environment using python3 -m venv path/to/venv.
    Then use path/to/venv/bin/python and path/to/venv/bin/pip. Make
    sure you have python3-full installed.
    …
note: If you believe this is a mistake, please contact your Python installation or OS distribution provider. You can override this, at the risk of breaking your Python installation or OS, by passing --break-system-packages.
hint: See PEP 668 for the detailed specification.
exit=1

The mechanism is a marker file, /usr/lib/python3.12/EXTERNALLY-MANAGED: PEP 668 says an installer that is not in a virtual environment and finds that file "should exit with an error message", and the helpful text is the distribution's, read from the file.[PEP 668] The PEP lets single-application container images omit the marker, so whether an agent hits this depends on the base image — check, don't assume. The intended route is a virtual environment: a directory with its own site-packages. "Activating" it is less magic than it looks — it "will prepend that directory to your PATH"[Python: venv] (page 2's lookup rule does the rest), and you can skip it by calling /tmp/v/bin/pip directly: 

# python3 -m venv /tmp/v; . /tmp/v/bin/activate; echo "PATH=$PATH"
PATH=/tmp/v/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
# echo "requests==2.32.3" > requirements.txt; pip install -q -r requirements.txt; pip freeze
certifi==2026.7.22
charset-normalizer==3.5.1
idna==3.20
requests==2.32.3
urllib3==2.8.0

One line went in; five came out. The file pinned requests with == (version pinning), but its four transitive dependencies were chosen by PyPI on the day of the install. The pip freeze output is the real environment, and pip's docs recommend it as the requirements file for exactly that reason: it "would pin not only the top-level packages, but also all of their transitive dependencies."[pip] A fully pinned file of this kind is a lockfile. One step stronger is hash-checking, which also guards against a file changing under the same version number. It is all-or-nothing, as pip told us when only one line carried a hash: 

# cat hashed.txt
requests==2.32.3 --hash=sha256:70761cfe03c773ceb22aa2f671b4757976145175cdfca038c02654d061d6dcc6
# /tmp/v2/bin/pip install -r hashed.txt
…
ERROR: In --require-hashes mode, all requirements must have their versions pinned with ==. These do not:
    charset-normalizer<4,>=2 from https://files.pythonhosted.org/…

Depth triage: use venvs, == pins and pip freeze; recognise --hash lines and the PEP 668 error; leave wheel tags and build backends to whoever packages the task's dependencies.

Drift: same Dockerfile, different environment

A Dockerfile is a recipe that names three moving targets. Rebuild it next month and each may have moved.

Moving partWhy it movesHow to hold it still
The base image tag "Image tags are mutable, meaning a publisher can update a tag to point to a new image."[Docker: Dockerfile] Pin the digest: FROM ubuntu:24.04@sha256:…. Cost, per the same page: "you're opting out of automated security fixes".
The distro repositoryThe -updates and -security pockets are replaced in place.A dated snapshot of the archive.
PyPIUnpinned (usually transitive) dependencies resolve to today's newest.pip freeze lockfile, optionally with hashes.
 
$ docker image inspect --format '{{index .RepoDigests 0}}' ubuntu:24.04
ubuntu@sha256:008173c23f95b170204355c12626cb5a965d779a7e1283b09e9cffbb1bf33ca3

The repository is the part people underestimate. This ubuntu:24.04 image was built ten days before these commands ran, and already apt list --upgradable showed perl-base one security update behind. No documentation I can cite promises that old versions disappear, so here is the behaviour instead. The policy output above offered two versions of curl. Asking for one that existed in between: 

# apt-get install -y curl=8.5.0-2ubuntu10.4; echo "exit=$?"
…
E: Version '8.5.0-2ubuntu10.4' for 'curl' was not found
exit=100
# apt-get install -y curl=8.5.0-2ubuntu10 2>&1 | tail -2    # the release version IS still listed…
 curl : Depends: libcurl4t64 (= 8.5.0-2ubuntu10) but 8.5.0-2ubuntu10.13 is to be installed
E: Unable to correct problems, you have held broken packages.

So a Dockerfile that pins curl=… does not reproduce; it breaks, the first time that version is superseded — and pinning one package is not enough anyway, because its dependencies are version-locked to it. The tool that works is an archive snapshot. Ubuntu's service covers "any date and time after 1 March 2023", promises retention of "at least 2 years in the past", and on 24.04 needs no configuration beyond the --snapshot (-S) option.[Ubuntu snapshots] Debian's equivalent, snapshot.debian.org, has imports "from 2005 until the present".[Debian snapshots] Executed today against the archive as of 1 June 2024: 

# apt-get update -q >/dev/null; apt-get install -y -q --no-install-recommends ca-certificates >/dev/null
# apt-get update -q --snapshot 20240601T000000Z | tail -3
Get:17 https://snapshot.ubuntu.com/ubuntu/20240601T000000Z noble-security/universe arm64 Packages [40.7 kB]
Fetched 22.1 MB in 36s (621 kB/s)
Reading package lists...
# apt-get install -y -q --no-install-recommends --snapshot 20240601T000000Z curl | tail -2
Setting up curl (8.5.0-2ubuntu10.1) ...
Processing triggers for libc-bin (2.39-0ubuntu8.9) ...

June 2024's curl, with its matching libcurl, installed in September 2026. Two things the quick start does not tell you, both observed. The snapshot server is HTTPS, and the stock image has no CA certificates: without the first line the update fails with "No system certificates available. Try installing ca-certificates." And in a fresh container, apt-get update --snapshot … as the very first command fetched the live archive from ports.ubuntu.com and exited 0; only a second update went to the snapshot server. (apt documents that it detects snapshot support from a repository's Release file, which a fresh image does not yet have — a plausible cause, not one I verified.) Either way: after a snapshot install, check the versions you got.

Fingerprint the environment

You cannot eyeball drift, but you can diff it. This script (shellcheck-clean) prints one sorted line per installed thing: 

#!/usr/bin/env bash
# Print a sorted, diffable fingerprint of this environment. Usage: fingerprint.sh [VENV]
set -euo pipefail
venv=${1:-}
grep -E '^(ID|VERSION_ID)=' /etc/os-release
uname -m
dpkg-query -W -f='deb ${Package}=${Version}\n' | sort
if [ -n "$venv" ]; then
  "$venv/bin/pip" freeze | sed 's/^/pip /'
fi
$ diff fp-fresh.txt fp-lab.txt | grep -E 'perl|tzdata|pip '
< deb perl-base=5.38.2-3.2ubuntu0.4
> deb perl-base=5.38.2-3.2ubuntu0.6
> deb tzdata=2026c-0ubuntu0.24.04.1
> pip certifi==2026.7.22
> pip charset-normalizer==3.5.1
…

A fresh ubuntu:24.04 had 92 packages; this page's lab container, 116 plus five pip lines — 30 added lines in all, including a changed perl-base nobody asked for by name. Store the fingerprint (or its SHA-256) with every results file.

In eval work — discuss and design

SWE-bench moved its harness to Docker for this reason. The maintainers wrote that they had "hypothesized that conda environments would be enough to enforce reproducible evaluation. In hindsight, it is underspecified", and that evaluation "remained sensitive to discrepancies originating from different platforms and user-specific configurations, leading to inconsistent results." Even containerised, the reference patches resolved 99.78% (2289/2294) of tasks — five tasks fail with the correct answer.[SWE-bench] A benchmark whose images rebuild differently next month is a different benchmark. So: build once, push, and publish image digests with results; treat a rebuild as a new version of the instrument and re-run the oracle solutions against it before trusting any score.

In eval work — failure accounting

An agent with network access that runs pip install pandas gets today's pandas: two rollouts of the same task a month apart ran in different environments (nondeterminism you did not intend), and pip's own docs note that installing "involves running arbitrary code from distributions" — a supply-chain surface inside your sandbox.[pip] The standard design is build with network, run without: everything the task needs is installed at image build time, and the run-time container gets --network none or an allowlist (page 19). Then installs fail at run time, and you must recognise them: Temporary failure in name resolution followed by pip's misleading No matching distribution found, or apt's Unable to locate package. If the task was solvable without the install, that is the model's problem. If the image lacked something the task requires, or a mirror was down during a networked run, it is an infrastructure failure: record it with its own status, keep it in scheduled, and report correct / scheduled alongside correct / completed rather than silently re-running until it passes.

Caveat

Pinning makes an environment repeatable, not correct or safe: a digest-pinned image keeps its known vulnerabilities, and Ubuntu promises only about two years of snapshots. For long-lived benchmarks the durable artifact is the built image in a registry you control, not the recipe.

Check your understanding

A team re-runs a published agentic benchmark six months later with the same model and the same harness commit. The score drops four points. Their explanation: "the API model must have been silently updated." The task images are built from Dockerfiles in the repo at the start of each run. What would you ask for before accepting that explanation?

Reveal the reasoning

Observed: a score change between two runs. Supposed: that the model changed. At least three other things changed for certain, because the images were rebuilt: the base image behind the tag, the distro packages, and any unpinned Python dependencies. The instrument is not the same instrument.

Discriminating evidence. (1) Image digests or package fingerprints from both runs; if the old ones were never recorded, say so — that is itself the finding. (2) Run the oracle solutions on the new images: if reference patches now fail some tasks, those tasks broke independently of any model. (3) Diff per-task outcomes: drift typically shows as the same tasks failing for every model with import errors, changed test output or install failures in the logs; a model change shows as diffuse differences with healthy environments. (4) If old images still exist in a registry, re-run the current model on them.

Bearing on the score. Tasks whose oracle fails are instrument failures: report them separately and give the score over the tasks that are still valid, stating the denominator. Only what remains after that can be attributed to the model — and the fix going forward is to publish digests with results.

Lab

Container lab. Start a scratch box: docker run -it --rm --name lt-pkg ubuntu:24.04 bash. Installs here need network and a few minutes.

  1. Reproduce. Before apt-get update, try to install curl. Then update, and use apt-cache policy curl to say which version would be installed and from which pocket.
    Solution

    E: Unable to locate package curl, exit 100, because /var/lib/apt/lists/ is empty. After the update, policy shows Candidate: 8.5.0-2ubuntu10.13 from noble-updates and noble-security, with 8.5.0-2ubuntu10 from the frozen noble pocket beneath it (your candidate will be newer — that is the point of the page).

  2. Reproduce. Which package owns /usr/bin/ls? How many packages are installed?
    Solution 
    # dpkg -S /usr/bin/ls
coreutils: /usr/bin/ls
# dpkg -l | grep -c '^ii'
92
  3. Predict, then verify. In docker run --rm --network none ubuntu:24.04 bash, what is the exit status of apt-get update? What does the following apt-get install -y curl print?
    Solution 
    # apt-get update 2>&1 | tail -2; echo "exit=${PIPESTATUS[0]}"
W: Failed to fetch http://ports.ubuntu.com/ubuntu-ports/dists/noble-security/InRelease  Temporary failure resolving 'ports.ubuntu.com'
W: Some index files failed to download. They have been ignored, or old ones used instead.
exit=0
# apt-get install -y curl 2>&1 | tail -1
E: Unable to locate package curl

    Exit 0 for a total failure; then an error that blames the package name. A script with set -e would not stop at the update either.

  4. Predict, then verify. Install python3-pip python3-venv (use DEBIAN_FRONTEND=noninteractive and --no-install-recommends). Run pip install requests and read the error. Then create a venv, install from a one-line requirements.txt (requests==2.32.3), and predict how many lines pip freeze prints.
    Solution

    The install adds 24 packages (12.6 MB), tzdata among them — without the variable you meet the "Geographic area:" prompt. pip install requests gives error: externally-managed-environment, exit 1. In the venv, pip freeze prints five lines: requests==2.32.3 plus certifi, charset-normalizer, idna and urllib3 at whatever versions PyPI serves on the day you run it. Yours will differ from this page's; save both outputs and diff them.

  5. Eval task. Save fingerprint.sh from this page. Produce a fingerprint of a fresh ubuntu:24.04 and one of your lab container after exercise 4, and diff them. Which differences did you ask for, and which did you not?
    Solution 
    $ docker run --rm -v "$PWD/fingerprint.sh":/f.sh:ro ubuntu:24.04 bash /f.sh > fp-fresh.txt
$ docker cp fingerprint.sh lt-pkg:/f.sh; docker exec lt-pkg bash /f.sh /tmp/v > fp-lab.txt
$ diff fp-fresh.txt fp-lab.txt | grep -c '^>'
30

    You asked for two apt packages and one pip package. You got 24 apt packages and five pip packages; the four transitive pip versions and every apt version were decided by the date. (This page's container also shows a changed perl-base, from a reinstall during the lock demo — a reminder that any apt operation can move versions.) Those unrequested lines are what a results file needs to record.
