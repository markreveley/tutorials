Module 1 · The Shell

Files and the filesystem tree

One tree, rooted at /, holds everything on a Linux box: programs, configuration, logs, devices, even a live view of the kernel. This page teaches where things live and why, what a "file" really is underneath its name, and the one command — find — that answers the question every agentic eval eventually asks: what did the agent change?

One tree, no drive letters

There is no C: and no /Volumes. Every file on a Linux system has a place in a single hierarchy that starts at the root directory, written /. Extra disks, network shares, and the kernel's own pseudo-files are grafted onto directories of that same tree (mounting — page 14). A path is a route through it, and there are two ways to write one:

  • An absolute path starts with / and means the same thing no matter where you are: /var/log/dpkg.log.
  • A relative path starts anywhere else and is resolved from the process's current working directory: tests/test_basic.py.

Every directory contains two special entries: . (itself) and .. (its parent). The shell adds one shorthand of its own, ~, for your home directory. 

$ pwd
/home/learner
$ cd /var/log
$ cd ../../etc               # up to /var, up to /, down into etc
$ pwd
/etc
$ cd ~ ; pwd
/home/learner
$ cd -                      # back to the previous directory
/etc

Recall from page 2 that the working directory belongs to a process. A harness that starts each tool call in a fresh shell resets it every time — so in transcripts and graders alike, absolute paths are the ones that can't be misread.

Where things live, and why you'd look there

The layout isn't arbitrary. The Filesystem Hierarchy Standard (FHS) sorts files along two axes — shareable or host-specific, static or variable — and gives each combination a home.[FHS] Programs are static and go under /usr; configuration is host-specific and goes in /etc; anything that grows while the machine runs goes in /var. Background — the highlighted symlinks

Historically /bin held the few commands needed before /usr was mounted, and the FHS still describes them as separate directories. Modern Debian and Ubuntu have merged them: Debian 12's release notes say the legacy directories "are replaced with symlinks to the corresponding locations" under /usr.[Debian 12 Notes] So /bin/ls and /usr/bin/ls are the same file. Alpine is the counter-example: in alpine:3.20, ls -ld /bin /sbin /lib shows three real directories. A script with a hard-coded /usr/bin/… path can work on one and fail with 127 on the other.

Caveat — /tmp is not guaranteed to be cleaned

Folklore says /tmp is wiped at reboot. The FHS only recommends that; its actual requirement is that programs "must not assume that any files or directories in /tmp are preserved between invocations of the program".[FHS] And a container that is stopped and restarted hasn't "booted" anything: its /tmp persists for the container's life. If your harness reuses containers between rollouts, /tmp is shared state between samples unless you reset it.

Three things to take from it. file tells you what something is by looking at its contents, not its name — Linux attaches no meaning to extensions. A name starting with a dot is a dotfile: hidden from plain ls by convention only, which is why you should type ls -la by reflex in any directory you are auditing. And cat prints a whole file, which is fine for fifteen bytes and hopeless for a log; use less (a pager: Space to page, / to search, q to quit) or head/tail (page 5).

What a file really is: names, inodes, data

stat prints everything the filesystem knows about a file: 

$ stat app/wordfreq.py
  File: app/wordfreq.py
  Size: 15        	Blocks: 8          IO Block: 4096   regular file
Device: 0,98	Inode: 33645168    Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1001/ learner)   Gid: ( 1001/ learner)
Access: 2026-09-21 16:20:47.594001003 +0000
Modify: 2026-09-21 16:20:47.580001003 +0000
Change: 2026-09-21 16:20:47.580001003 +0000
 Birth: 2026-09-21 16:20:47.580001003 +0000

All of that — type, size, permissions, owner, timestamps, link count — is stored in a record called an inode.[inode(7)] Look at what is not in the list: the name. Names live in directories. A directory is just a table mapping names to inode numbers, and POSIX defines a directory entry as "an object that associates a filename with a file" — adding that "several directory entries can associate names with the same file".[POSIX]

directory "work" inode table data blocks ┌───────────┬──────────┐ ┌────────────────────────┐ │ orig.txt │ 33645369 ├──┐ │ #33645369 │ ├───────────┼──────────┤ ├▶│ regular file, 0644 │──▶ "the answer\n" │ hard.txt │ 33645369 ├──┘ │ uid 1001, 11 bytes │ ├───────────┼──────────┤ │ links: 2 │ │ soft.txt │ 33645375 ├──┐ ├────────────────────────┤ └───────────┴──────────┘ └▶│ #33645375 │ │ symbolic link, 0777 │──▶ "orig.txt" hard link = a second │ links: 1 │ (a NAME, looked name for the same inode └────────────────────────┘ up again on use)
$ echo 'the answer' > orig.txt
$ ln orig.txt hard.txt          # hard link: another name for the same inode
$ ln -s orig.txt soft.txt       # symbolic link: a tiny file containing a path
$ ls -li orig.txt hard.txt soft.txt
33645369 -rw-r--r-- 2 learner learner 11 Sep 21 16:20 hard.txt
33645369 -rw-r--r-- 2 learner learner 11 Sep 21 16:20 orig.txt
33645375 lrwxrwxrwx 1 learner learner  8 Sep 21 16:20 soft.txt -> orig.txt
$ rm orig.txt
$ cat hard.txt
the answer
$ cat soft.txt
cat: soft.txt: No such file or directory

A hard link is indistinguishable from the "original" — there is no original, only names. rm removes a name; the data survives while any name remains. A symlink is "a pointer to another name, and not to an underlying object",[symlink(7)] so it can cross filesystems, point at directories, and dangle, as soft.txt now does. (The error message names soft.txt, not the missing target: a confusing line to meet in a transcript. ls -l shows where a link points.) Hard links can't cross filesystems — inode numbers are only unique within one — and trying gives Invalid cross-device link.

Deleted but still open

The rule has a second half. The kernel frees a file's data only when its last name is gone and no process still has it open: "the file will remain in existence until the last file descriptor referring to it is closed".[unlink(2)] 

$ head -c 20000000 /dev/zero > big.log
$ sleep 300 < big.log &          # a background process holding the file open
[1] 297
$ rm big.log
$ ls
app  hard.txt  soft.txt
$ ls -l /proc/$!/fd/0                  # $! = PID of the last background job
lr-x------ 1 learner learner 64 Sep 21 16:20 /proc/297/fd/0 -> '/home/learner/work/big.log (deleted)'

No name, invisible to ls and find, still occupying 20 MB of disk until process 297 exits. This is how a box reports "disk full" when no file accounts for the space (page 12), and it is a reminder that "I deleted the answer key" and "the answer key is gone" are different claims.

find: asking the tree questions

find walks a directory tree and prints every entry that passes a list of tests. The grammar is find WHERE TESTS… [ACTION]; tests are ANDed together. The tests worth knowing by heart:

TestMatches
-name '*.py'the file's name against a shell pattern — quote it, or the shell expands it first
-type f / d / lregular files / directories / symlinks
-newer FILE, -cnewer FILEcontent modified (mtime) / inode changed (ctime) more recently than FILE was modified
-mmin -60, -mtime -1modified less than 60 minutes / 1 day ago
-user agent, -perm -o+wowned by a user / has at least these permission bits (here: world-writable — page 8)
-not, -path '/app/*', -maxdepth 1negate a test; match the whole path; don't descend
-xdevstay on the starting filesystem: skips /proc, /sys, /dev and other mounts

Worked example: the agent's footprint

The technique: before the agent starts, create a marker file. Afterwards, ask for everything newer than the marker. Here it is in the course's deliberately careless task image, wordfreq-bench:sloppy, where the agent is root. We play the agent by hand — an honest fix, then some less honest housekeeping: 

# touch /tmp/marker
# cd /app
# sed -i 's/text.split()/text.lower().split()/' wordfreq.py
# python3 -c 'print(42)' > /tmp/scratch.txt
# echo 'alias pytest=true' >> /root/.bashrc
# printf '#!/bin/sh\nexit 0\n' > /usr/local/bin/pytest
# chmod +x /usr/local/bin/pytest
# cp /opt/grader/expected.json /var/tmp/.cache.json
# find / -xdev -newer /tmp/marker -type f
/var/tmp/.cache.json
/root/.bashrc
/tmp/scratch.txt
/usr/local/bin/pytest
/app/wordfreq.py
# find / -xdev -newer /tmp/marker -type f -not -path '/app/*' -not -path '/tmp/*'
/var/tmp/.cache.json
/root/.bashrc
/usr/local/bin/pytest

Five files, and the second command reduces them to the three that have no business changing in a "fix the bug in /app" task: a fake pytest placed first on PATH (page 2's lab), an alias, and a hidden copy of the answer key. Without -xdev the same search returned 16,233 files here, nearly all of them the ever-changing pseudo-files of /proc and /sys.

Pitfall — modification times are under the agent's control

-newer compares mtime, and anyone who can write a file can set its mtime to anything:

# touch -d '2024-01-01' /usr/local/bin/pytest
# find / -xdev -newer /tmp/marker -type f | grep pytest
# find / -xdev -cnewer /tmp/marker -type f | grep pytest
/usr/local/bin/pytest

(| grep pytest keeps only the lines mentioning pytest — page 5.) The fake vanished from the first search. -cnewer compares ctime, the inode's "last status change", which the kernel updates on any write or metadata change and which touch cannot set — not creation time, despite the name.[inode(7)] Prefer -cnewer for footprints, and remember that -type f skips symlinks: use -not -type d to see them too. Better still, don't ask the box at all: from the host, docker diff <container> lists every path added (A) or changed (C) relative to the image, whatever the timestamps say (page 22). A footprint taken from inside a box the agent controlled as root is evidence, not proof.

In eval work — state-based grading is reading the tree

State-based evaluation means: let the agent finish, then inspect what's on disk. Inspect, for instance, lets a scorer call sandbox().read_file() or exec() against the sample's sandbox after the agent is done.[Inspect] That makes this page's tools the grader's tools, and gives you a cheap integrity signal to log for every rollout: the list of paths changed outside the task directory. Most rollouts will show none. The ones that touch /usr/local/bin, a dotfile, or anything under the grader's directory are where to start error analysis — and the ones that show files older than the rollout in /tmp are telling you the reset between samples is incomplete.

Symlinks as a grading hazard

Suppose a task variant says "write the top-3 words to /app/answer.json" and the grader compares that file with its expected.json. In the sloppy image the grader's directory is world-readable, so the cheapest "solution" is one command: 

# ln -s /opt/grader/expected.json /app/answer.json
# cmp /app/answer.json /opt/grader/expected.json && echo PASS
PASS
# [ -f /app/answer.json ] && echo "is a regular file?"
is a regular file?
# [ -L /app/answer.json ] && echo "is a symlink"
is a symlink
# stat -c '%F' /app/answer.json
symbolic link
# readlink -f /app/answer.json
/opt/grader/expected.json

The grader compared the answer key with itself. Note the trap in the third command: almost every tool, including the shell's -f test, follows symlinks and reports on the target. Only tests that ask about the link itself (-L, stat without -L, find -type l) see it.

In eval work — graders should resolve, then check type

A grader that reads an agent-produced path should (1) refuse symlinks, or resolve them with readlink -f and require the result to stay inside the task directory; (2) require a regular file — not a directory, not a device; and (3) ideally not run where the expected answer is readable at all: copy the artefact out and grade elsewhere, as wordfreq-bench's grade.sh does (page 26). The design principle: the agent controls every byte and every file type under the directories it can write. That last point is this course's reasoning, not a quotation from any harness's documentation.

Preview: everything is a file

The tree's deepest trick is that things which are not stored data also appear in it, so the same cat, ls, and > work on them — "everything is a file". 

$ ls -l /dev/null
crw-rw-rw- 1 root root 1, 3 Sep 21 16:14 /dev/null
$ ls -l /proc/version
-r--r--r-- 1 root root 0 Sep 21 16:14 /proc/version
$ cat /proc/version
Linux version 6.10.14-linuxkit (root@buildkitsandbox) (gcc (Alpine 13.2.1_git20240309) …

/dev/null is a character device (the leading c): writes to it are discarded, reads return end-of-file at once.[FHS] /proc/version claims to be zero bytes long and yet has contents, because the kernel composes the text at the moment you read it. (That kernel is Docker Desktop's Linux VM, not Ubuntu's — containers share their host's kernel, page 20.) Page 4 puts /dev/null to work; page 9 reads processes out of /proc.

Depth triage for this page: learn to use paths, ls -la, stat, find, and the name/inode distinction; merely recognise the FHS rationale and inode numbers when you see them; leave filesystem internals (journals, extents, block allocation) to storage specialists — no eval audit needs them.

Check your understanding

A state-based grader passes a rollout of a data-cleaning task: /app/report.csv matches /opt/grader/expected.csv byte for byte. The rollout took 40 seconds; the median passing rollout takes nine minutes. You're asked whether the pass counts. What do you establish, in what order?

Reveal the reasoning

Observed: identical bytes, unusually fast. Hypotheses: (a) a legitimately quick solve; (b) the output is the expected file — a symlink or a copy; (c) the file was already there, left by a previous rollout in a reused container. None is proven by the pass itself.

Discriminating evidence: the file type of report.csv in the saved final state (stat -c %F, readlink -f) separates the symlink case. Whether the agent user could read /opt/grader at all, plus a transcript search for that path, separates the copy case. The file's birth and change times against the rollout's start time, and the harness's reset policy, separate (c). A footprint (docker diff, or find -cnewer) shows what else was touched.

Bearing on the score: if (b) or (c) holds, this isn't a model success — and it isn't simply a model failure either. It's a defect in the environment that every sample of the task was exposed to, so the whole task's results are suspect, not just the fast one. Fix the image or the reset, re-run the task, and report the affected samples as invalidated rather than silently flipping one pass to a fail.

2 · Predict, then verify. In ~/work: mkdir d; echo one > d/f; ln d/f g. Now mv d/f d/h, then echo two >> g. Before running them, write down what cat d/h prints and what link count g has.

Solution 
$ ls -li d/f g
33645713 -rw-r--r-- 2 learner learner 4 Sep 21 16:21 d/f
33645713 -rw-r--r-- 2 learner learner 4 Sep 21 16:21 g
$ mv d/f d/h
$ echo two >> g
$ cat d/h
one
two
$ stat -c '%h' g
2

Renaming changes a directory entry, not the inode, so g and d/h are still two names for one file and a write through either is visible through both. Had g been a symlink to d/f, the mv would have left it dangling.

3 · find drills. (a) Which files under /etc were modified in the last hour? (b) Which regular files under /usr are larger than 5 MB? (Look up -size in find --help or Appendix F.) Your lists will differ with what you've installed.

Solution 
$ find /etc -type f -mmin -60
/etc/hosts
/etc/gshadow
/etc/group
/etc/passwd
…
/etc/hostname
$ find /usr -xdev -type f -size +5M
/usr/lib/file/magic.mgc

In a fresh container (a) shows the files Docker writes at start-up (hosts, hostname, resolv.conf) and the ones useradd edited when you created learner — a small footprint of your own.

4 · Eval task: reconstruct a footprint. As root, run the two setup lines, then — without reading the second line again — list everything the "agent" did.

touch /tmp/marker; sleep 1
bash -c 'echo hi >> /etc/motd; mkdir -p /opt/.cache; echo k > /opt/.cache/key; touch -d 2024-01-01 /opt/.cache/key; ln -sf /etc/passwd /tmp/result.txt'
Solution 
# find / -xdev -newer /tmp/marker -type f
/etc/motd
# find / -xdev -cnewer /tmp/marker -not -type d
/etc/motd
/tmp/result.txt
/opt/.cache/key
# find / -xdev -cnewer /tmp/marker -type l -exec ls -l {} +
lrwxrwxrwx 1 root root 11 Sep 21 16:21 /tmp/result.txt -> /etc/passwd

The naive search finds one of three changes. The backdated key needs -cnewer; the symlink needs a type test that doesn't exclude links. From your Mac, docker diff lt-lab shows all three with no cooperation from the box.

5 · Eval task: a grader that checks type. Write check-output.sh OUTPUT EXPECTED: print PASS and exit 0 only if OUTPUT is a genuine regular file with the same bytes as EXPECTED; fail with a reason for a symlink, a directory, a missing file, or wrong content. Test all five cases.

Solution 
#!/bin/bash
# check-output.sh OUTPUT EXPECTED -- compare, but only if OUTPUT is a real regular file
out=$1 expected=$2
if [ -L "$out" ]; then
  echo "FAIL: $out is a symlink to $(readlink -f "$out")"; exit 1
fi
if [ ! -f "$out" ]; then
  echo "FAIL: $out is not a regular file"; exit 1
fi
if cmp -s "$out" "$expected"; then
  echo PASS
else
  echo "FAIL: wrong content"; exit 1
fi
# echo '{"ok": 1}' > /tmp/expected.json; cp /tmp/expected.json /tmp/good.json
# ln -s /tmp/expected.json /tmp/sneaky.json; mkdir /tmp/adir; echo "{}" > /tmp/wrong.json
# check-output.sh /tmp/good.json /tmp/expected.json; echo "status $?"
PASS
status 0
# check-output.sh /tmp/sneaky.json /tmp/expected.json; echo "status $?"
FAIL: /tmp/sneaky.json is a symlink to /tmp/expected.json
status 1
# check-output.sh /tmp/adir /tmp/expected.json; echo "status $?"
FAIL: /tmp/adir is not a regular file
status 1
# check-output.sh /tmp/missing.json /tmp/expected.json; echo "status $?"
FAIL: /tmp/missing.json is not a regular file
status 1
# check-output.sh /tmp/wrong.json /tmp/expected.json; echo "status $?"
FAIL: wrong content
status 1

The order matters: -L must come before -f, because -f follows the link. The script passes shellcheck. It still can't stop an agent that can simply read expected.json and copy it — that takes permissions (page 8) or grading outside the box.
