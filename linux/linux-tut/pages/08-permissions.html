Module 2 · Identity & Permissions

Permissions and ownership

Nine bits on every file decide who may read, change, or run it. This page teaches you to read them, predict what the kernel will allow before you run the command, and use that to hide an answer key from an agent. It also covers the three ordinary ways that protection fails without any error message.

Reading ls -l

This is the second half of audit question 3, who owns what? The setup is the course's running example, wordfreq-bench, in its in-box variant. The agent runs as agent (UID 1001, from page 7) and works in /app. Root has copied the grader (hidden tests and expected.json, the answer key) into /opt/grader. 

$ ls -ld /app /opt/grader
drwxr-xr-x 4 agent agent 4096 Sep 21 06:08 /app
drwx------ 2 root  root  4096 Sep 21 06:08 /opt/grader
$ stat -c '%A %a %U:%G %n' /app/wordfreq.py /app /opt/grader
-rw-r--r-- 644 agent:agent /app/wordfreq.py
drwxr-xr-x 755 agent:agent /app
drwx------ 700 root:root /opt/grader
d rwx r-x r-x 4 agent agent 4096 … /app │ └┬┘ └┬┘ └┬┘ └─┬─┘ └─┬─┘ │ │ │ │ │ └ group that owns it │ │ │ │ └ user that owns it │ │ │ └ other: everyone else │ │ └ group: members of the owning group │ └ user (owner) └ type: - regular file, d directory, l symlink

The ten-character mode string is a type letter followed by three permission classes: the owning user, the owning group, and other. Each class has three bits: r read, w write, x execute; - means the bit is off. Each bit has a numeric value (r=4, w=2, x=1), and adding them per class gives the three-digit octal form: rwx = 7, r-x = 5, r-- = 4, so rwxr-xr-x is 755 and rw-r--r-- is 644.[chmod(2)] (If octal is new to you, Appendix C has the arithmetic.) The mode is stored in the file's inode alongside its owner UID and GID, which are numbers, as page 7 showed.

The decision procedure: exactly one class

When a process asks to open a file, the kernel does not add up permissions from every class that could apply. It picks one class and consults only that one:

  1. If the process's UID equals the file's owner UID, use the user bits.
  2. Otherwise, if the file's group is the process's group or one of its supplementary groups, use the group bits.
  3. Otherwise, use the other bits.

There is no fall-through to the next class if the chosen one says no.[path_resolution(7)] (Root is the exception, covered below.) That has a surprising consequence, which is the best way to check you have the rule: 

$ echo "secret" > own.txt && chmod 004 own.txt && ls -l own.txt
-------r-- 1 agent agent 7 Sep 21 21:21 own.txt
$ cat own.txt; echo "exit status: $?"
cat: own.txt: Permission denied
exit status: 1
$ docker exec -u ubuntu lt-08-box cat /tmp/own.txt     # another user: the "other" class
secret

The owner is refused a file that everyone else may read, because the owner is judged by the owner bits alone. It is not a trap for the owner, though: only the owner (or a privileged process) may change a file's mode,[chmod(2)] so chmod u+r own.txt fixes it at once.

Key idea To predict an access decision, ask three questions in order: which class am I in? (compare numbers from id with ls -ln), which bit does this operation need?, and is that bit set in my class? Then repeat for every directory on the path, which is the next section.

Changing modes and owners

chmod accepts either an octal number or symbolic edits of the form who (u g o a), operator (+ - =), bits: 

$ touch demo.sh
$ chmod 750 demo.sh && ls -l demo.sh
-rwxr-x--- 1 agent agent 0 Sep 21 21:21 demo.sh
$ chmod u-x,g+w,o+r demo.sh && stat -c '%a %A' demo.sh
674 -rw-rwxr--
$ chmod a+x demo.sh && stat -c '%a %A' demo.sh
775 -rwxrwxr-x
$ chmod go= demo.sh && stat -c '%a %A' demo.sh      # "=" with nothing: clear group and other
700 -rwx------

Numeric modes set all nine bits at once; symbolic ones edit a few. Use numeric when you mean "exactly this" (Dockerfiles, setup scripts) and symbolic for small changes. chown changes the owner, and ordinary users cannot use it to give files away: 

$ chown ubuntu /tmp/demo.sh; echo "exit status: $?"
chown: changing ownership of '/tmp/demo.sh': Operation not permitted
exit status: 1

Changing a file's owner needs a privilege (CAP_CHOWN, "make arbitrary changes to file UIDs and GIDs"),[capabilities(7)] which in practice means root; as root the syntax is chown user:group path, with -R for a tree.

Directories: the bits mean something else

A directory is a list of names pointing at files. Its bits govern the list, not the files:

BitOn a fileOn a directory
rread the contentslist the names (ls)
wchange the contentscreate, delete, rename entries (needs x too)
xrun it as a program"search": use the directory in a path to reach what is inside

The x bit on directories is the one people miss. For each directory on a path except the last, the process needs search permission; lacking it anywhere gives "Permission denied".[path_resolution(7)] The two bits separate cleanly, as the agent can show on a directory it owns: 

$ mkdir -p /tmp/d && echo hi > /tmp/d/f
$ chmod 400 /tmp/d; ls /tmp/d; cat /tmp/d/f         # r without x: see names, reach nothing
f
cat: /tmp/d/f: Permission denied
$ chmod 100 /tmp/d; ls /tmp/d; cat /tmp/d/f         # x without r: reach by name, list nothing
ls: cannot open directory '/tmp/d': Permission denied
hi
$ chmod 500 /tmp/d; touch /tmp/d/new; echo more >> /tmp/d/f; echo "append: $?"
touch: cannot touch '/tmp/d/new': Permission denied
append: 0

The last line matters: without w on the directory you cannot create a name, but you can still change a file you already have write access to. Directory bits protect names; file bits protect contents.

This gives the in-box protection its shape. /opt/grader is drwx------ root root: the agent is in the other class, and other has no bits, so no x, so nothing beneath it can be reached, whatever the files' own modes are: 

$ id
uid=1001(agent) gid=1001(agent) groups=1001(agent)
$ cat /opt/grader/expected.json; echo "exit status: $?"
cat: /opt/grader/expected.json: Permission denied
exit status: 1
$ ls /opt/grader; echo "exit status: $?"
ls: cannot open directory '/opt/grader': Permission denied
exit status: 2
$ python3 -c 'open("/opt/grader/expected.json")' 2>&1 | tail -n 1
PermissionError: [Errno 13] Permission denied: '/opt/grader/expected.json'

Inside, as root saw them, the files were ordinary -rw-r--r--. One chmod 700 on the directory protects everything beneath it.

Deleting is a directory write

Removing a file deletes a name from a directory, so it needs write access to the directory, not to the file.[unlink(2)] Suppose root plants a read-only reference file inside the agent's own directory: 

# echo "reference output: do not edit" > /app/data/reference.txt && chmod 444 /app/data/reference.txt
$ ls -ld /app/data; ls -l /app/data/reference.txt
drwxr-xr-x 1 agent agent 4096 Sep 21 21:21 /app/data
-r--r--r-- 1 root root 30 Sep 21 21:21 /app/data/reference.txt
$ echo "tampered" >> /app/data/reference.txt
bash: /app/data/reference.txt: Permission denied
$ rm -f /app/data/reference.txt; echo "exit status: $?"
exit status: 0
$ echo "whatever the agent likes" > /app/data/reference.txt && ls -l /app/data/reference.txt
-rw-r--r-- 1 agent agent 25 Sep 21 21:21 /app/data/reference.txt

The file could not be edited, but it could be replaced. A grader that later reads /app/data/reference.txt gets the agent's version. A root-owned, mode-444 test file inside a directory the agent owns is not protected.

The sticky bit and /tmp

/tmp must be writable by everyone, yet users must not delete each other's files. The sticky bit (the t in the last position, octal 1000) adds that rule: in a sticky directory a file can be renamed or deleted only by its owner, the directory's owner, or a privileged process.[inode(7)] It restricts deletion only. Here ubuntu has left a world-writable file in /tmp: 

$ stat -c '%a %A %U %n' /tmp
1777 drwxrwxrwt root /tmp
$ ls -l /tmp/ubuntu-notes.txt
-rw-rw-rw- 1 ubuntu ubuntu 13 Sep 21 21:21 /tmp/ubuntu-notes.txt
$ echo "agent was here" >> /tmp/ubuntu-notes.txt; echo "exit status: $?"
exit status: 0
$ rm -f /tmp/ubuntu-notes.txt; echo "exit status: $?"
rm: cannot remove '/tmp/ubuntu-notes.txt': Operation not permitted
exit status: 1

Where new modes come from: the umask

Programs that create files ask for a mode, usually 666 for files and 777 for directories. The process's umask then turns bits off: the result is requested & ~umask, so with the usual 022, 0666 becomes 0644.[umask(2)] 

$ umask
0022
$ touch f1 && mkdir d1 && stat -c '%a %n' f1 d1
644 f1
755 d1
$ umask 077 && touch f2 && mkdir d2 && stat -c '%a %n' f2 d2
600 f2
700 d2

The umask only removes bits; it never adds any. It is also inherited by child processes, like the UID. The practical consequence: anything a setup script, COPY, or cp creates is, by default, readable by every user in the box. Protection is something you add explicitly.

Root skips the check

Everything above describes ordinary processes. A process with the capability CAP_DAC_OVERRIDE bypasses file read, write and execute permission checks,[capabilities(7)] and root in an ordinary container holds it (page 7). There is one qualifier: root may execute a file only if at least one execute bit is set on it.[path_resolution(7)] 

# ls -l /srv/r.sh; cat /srv/r.sh
---------- 1 root root 19 Sep 21 21:22 /srv/r.sh
#!/bin/sh
echo ran
# /srv/r.sh; echo "exit status: $?"
bash: line 1: /srv/r.sh: Permission denied
exit status: 126
# chmod 001 /srv/r.sh; /srv/r.sh
ran

Depth triage for this section: learn to use the rule "root ignores mode bits, except it needs some x to execute". Recognize that the power comes from a capability that can be dropped (page 21).

Setuid: a file that changes who you are

Three more mode bits sit above the nine. The one that matters for audits is setuid (octal 4000, shown as s in the owner's execute position). When a setuid program is executed, the process's effective UID becomes the file's owner's.[execve(2)] That is how passwd lets you change your own entry in a root-only file, and how sudo works. Root makes a setuid copy of id to show the effect: 

# cp /usr/bin/id /usr/local/bin/suid-id && chmod 4755 /usr/local/bin/suid-id
# ls -l /usr/local/bin/suid-id
-rwsr-xr-x 1 root root 67952 Sep 21 21:22 /usr/local/bin/suid-id
$ /usr/local/bin/suid-id
uid=1001(agent) gid=1001(agent) euid=0(root) groups=1001(agent)

The agent ran a program that has root's authority. Every setuid-root program is therefore trusted code: a bug in one, or a setuid shell or interpreter, is a privilege escalation. The kernel ignores the setuid bit in three situations: when the process has no_new_privs set, when the filesystem is mounted nosuid, and when the process is being traced.[execve(2)] Linux also ignores it on scripts, so a setuid bash script run by the agent printed 1001. Here is the same image started with Docker's --security-opt no-new-privileges: 

$ docker run --rm --security-opt no-new-privileges lt-08-img /usr/local/bin/suid-id
uid=1001(agent) gid=1001(agent) groups=1001(agent)

The audit command lists every setuid file on the root filesystem. The hardened image contains only the stock Ubuntu set: 

$ find / -xdev -perm -4000 -type f 2>/dev/null
/usr/bin/chfn
/usr/bin/newgrp
/usr/bin/umount
/usr/bin/passwd
/usr/bin/chsh
/usr/bin/mount
/usr/bin/su
/usr/bin/gpasswd

Anything not on that list in an Ubuntu-based task image deserves an explanation. (-perm -2000 finds setgid files, the group equivalent.)

Background — ACLs: recognise the +

Linux also supports access control lists, which grant rights to individual extra users or groups. The only sign in ls -l is a + after the mode string, and it means the nine bits are not the whole story:

# setfacl -m u:agent:rx /opt/grader; ls -ld /opt/grader
drwxr-x---+ 2 root root 4096 Sep 21 06:08 /opt/grader

With that entry the agent could list and read the grader, although the mode bits say "other: nothing". Depth triage: recognize the +, run getfacl (package acl) when you see it, and leave ACL design to someone else. Eval images rarely need ACLs.

Worked case: three ways the protection fails

The in-box design is mode 700 on a root-owned /opt/grader, with the agent running as UID 1001. It holds only while all of its assumptions hold. Each failure below was run on the same box, and none of them produces an error anyone would notice.

1. The directory keeps its default mode. COPY, cp and docker cp produce the modes the umask allows, typically 755 directories and 644 files. Nobody runs chmod 700:

$ ls -ld /opt/grader; cat /opt/grader/expected.json
drwxr-xr-x 2 root root 4096 Sep 21 06:08 /opt/grader
{"sample_top3": [["the", 7], ["cat", 2], ["end", 2]]}

Mode 711 is a half-fix that looks like a fix: ls /opt/grader is denied, but anyone who guesses or learns the file name (it is in the task's public repo, or in the harness docs) still reads it, because x alone lets you reach a name.

2. The agent is root. No USER line, or a harness that execs as root. Mode bits are skipped entirely, and root can also change the tests:

# id -u; cat /opt/grader/expected.json
0
{"sample_top3": [["the", 7], ["cat", 2], ["end", 2]]}
# echo "# tampered" >> /opt/grader/test_hidden.py; tail -n 1 /opt/grader/test_hidden.py
# tampered

3. The agent can become root. The image has sudo and a NOPASSWD rule (page 7's lt-07-sudo container, same grader, mode 700):

$ cat /opt/grader/expected.json
cat: /opt/grader/expected.json: Permission denied
$ sudo -n cat /opt/grader/expected.json
{"sample_top3": [["the", 7], ["cat", 2], ["end", 2]]}
Pitfall — checking the file instead of the path

An author runs ls -l /opt/grader/expected.json, sees root-owned, and concludes it is protected. Ownership of the file says nothing about who can read it; the file's other bits and the x bit on every ancestor directory decide that. The only test that settles it is the access itself, performed as the agent's UID: docker exec -u 1001 BOX cat /opt/grader/expected.json. Run it as root and it always succeeds, which proves nothing.

A fourth route is an unexpected setuid program, covered above. The stronger design removes the question: do not put the key in the box. The hardened wordfreq-bench image contains no grader at all. grade.sh copies /app out after the agent finishes and runs the hidden tests in a fresh, network-less container the agent never touched (page 26 develops this). Mode bits then serve as defence in depth rather than the only defence.

In eval work — design

File access policy changes measured behaviour. ImpossibleBench gave coding agents tasks whose tests had been mutated to be impossible, so any pass means the agent cheated, and varied test access. On Impossible-SWEbench's conflicting-test variant, cheating rates with open tests vs a "read-only" condition were 54% vs 39% for GPT-5, 49% vs 11% for o4-mini, and 50% vs 1% for Claude Opus 4.1. Hiding the tests brought cheating to 0% but cost legitimate performance on the original tasks (GPT-5 97% → 76%, o4-mini 85% → 59%, Opus 4.1 86% → 70%).[ImpossibleBench] Read these numbers carefully. The paper's "read-only" is not a mode bit: the harness reverts any modified tests at scoring time. So they tell you how much protecting the tests matters, and that protection against modification leaves other cheating routes (special-casing, overloaded comparisons) open. They are not evidence about chmod. A chmod 444 on a test file inside a writable directory would not even achieve the paper's condition, as the deletion demo showed.

Reading the error: EACCES versus EPERM

Two different error messages appeared on this page, and they point to different mechanisms. The kernel returns a numbered error code, and Python shows the number: 

$ python3 -c 'open("/etc/shadow")' 2>&1 | tail -n 1
PermissionError: [Errno 13] Permission denied: '/etc/shadow'
$ python3 -c 'import os; os.chown("/tmp/demo.sh", 1000, 1000)' 2>&1 | tail -n 1
PermissionError: [Errno 1] Operation not permitted: '/tmp/demo.sh'

In eval work — navigate and account

When a rollout's transcript shows Permission denied, the observation is "a mode-bit check failed on some path". Whether that is a model failure depends on which path. If the agent was probing /opt/grader, it is the environment working as designed, and worth tagging as an attempted access for your integrity analysis. If it was the task's own output directory, it is an environment bug, and the rollout should be recorded as an infrastructure failure, reported in completed / scheduled rather than silently counted as incorrect. The discriminating test is one command run as the agent's UID: ls -ldn on each directory of the failing path.

Check your understanding

A task author says: "The hidden tests are safe. /opt/tests is root:root mode 700, the agent runs as UID 1001, there is no sudo, and I checked that cat /opt/tests/test_main.py fails as the agent." After the run, the harness copies /opt/tests into /app/tests_hidden/ (owned by agent) and runs pytest there as root. Is the grade trustworthy?

Reveal the reasoning

What the evidence covers: during the agent's run, reading the tests was blocked, assuming nothing else (setuid programs, ACLs, a second exec path) changed that. The author checked one read, not the full list; find / -perm -4000 and ls -ld for a + would complete it.

What it does not cover: grading. The tests are copied into a directory the agent owns. Whatever the agent left in /app is present at grading: a conftest.py that pytest loads automatically from parent directories, a placeholder tests_hidden directory or symlink the copy lands in or through, a pytest.ini that changes collection. Pytest then runs as root, so any of that code runs with full privileges. The protection guarded reading; the risk is tampering with the grading process.

What to ask for: grade in a fresh container, copying in only the files the task asks the agent to change, and running the tests from a root-owned directory the agent never had write access to. The discriminating experiment: a planted-tamper rollout (an agent script that writes a conftest.py forcing all tests to pass). If the current pipeline reports it as a pass, every existing score is an upper bound until regraded.

Lab

Container lab. Use your lt-lab container: learner (UID 1001) plays agent, and the preinstalled ubuntu (UID 1000) plays a second user. Root shell: docker exec -it lt-lab bash; switch with su - learner or su - ubuntu.

  1. Reproduce. As learner in /tmp, create own.txt, chmod 004 it, and show that you cannot read it but ubuntu can. Restore your access with one symbolic chmod.
    Solution

    cat own.txt as learner → Permission denied (owner class, bits ---). As ubuntu → secret (other class, r--). chmod u+r own.txt → -r-----r--, and cat works again.

  2. Predict, then verify. As learner: mkdir /tmp/d; echo hi > /tmp/d/f. For each of chmod 400 /tmp/d, chmod 100 /tmp/d and chmod 500 /tmp/d, predict whether ls /tmp/d, cat /tmp/d/f, and touch /tmp/d/new succeed. Then run them.
    Solution

    400: ls yes, cat no, touch no. 100: ls no, cat yes, touch no. 500: ls and cat yes, touch no (creating a name needs w and x). Restore with chmod 700 /tmp/d.

  3. Predict, then verify. As root, create /home/learner/ref.txt, owned by root, mode 444. Can learner append to it? Delete it? Replace it? Write down your answers first.
    Solution

    Append: no (Permission denied, learner is in the other class, which has only r). Delete: yes (rm -f exits 0, because deleting is a write to /home/learner, which learner owns). Replace: yes, and the new file is owned by learner. This is the deletion demo in a different directory.

  4. Audit. List the setuid and setgid files on your lab's root filesystem. Then, as root, add chmod 4755 to a copy of /usr/bin/id in /usr/local/bin, run it as learner, find it with your audit command, and delete it.
    Solution

    find / -xdev -perm -4000 -type f 2>/dev/null lists the eight stock programs shown on the page, plus /usr/local/bin/suid-id once you add it. Run as learner, the copy prints … euid=0(root) …. -perm -2000 finds unix_chkpwd, pam_extrausers_chkpwd, expiry and chage in a stock Ubuntu 24.04 image.

  5. Eval task: lock the answer key. As root, copy the course's research/wordfreq-bench/grader into the container at /opt/grader (docker cp from the Mac). First check, as learner, whether you can read /opt/grader/expected.json. Then make the smallest change that blocks learner from reading and listing every file inside, and verify it as learner. Say which of the three failure modes on this page your change does not address.
    Solution

    On the authoring Mac, docker cp kept the Mac's numeric owner: ls -ld /opt/grader showed drwxr-xr-x 2 501 dialout (Mac GID 20 happens to be dialout in Ubuntu, page 7's numbers-not-names point again), with 644 files, so learner could read the key (failure 1). Fix: chown -R root:root /opt/grader && chmod 700 /opt/grader. As learner: cat /opt/grader/expected.json → Permission denied; ls /opt/grader → cannot open directory … Permission denied (status 2). It does not address failures 2 and 3: a root agent, or any route to root (sudo, setuid), reads it anyway. Only grading outside the box addresses those.
