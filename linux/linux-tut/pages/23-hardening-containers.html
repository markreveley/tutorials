Module 6 · Containers & Isolation

Locking down a container

A default docker run is built for convenience: root user, fourteen capabilities, writable filesystem, open network, no resource limits. This page turns it into a defensible agent sandbox one flag at a time — and for every flag asks the two questions an evals engineer must: how do I verify it from inside, and which legitimate task behaviour did I just break?

Start from what the agent could do

Hardening without a list of threats is cargo cult. For an agent sandbox, the threat model is short, and every item is something a capable model might do while honestly trying to finish its task:

#ThreatWhat it does to the evalRungs that address it
1Tamper with the grader or testsPass without solving (page 26)grade outside; non-root; read-only
2Read the answer keySamekeep it out of the box; non-root
3Reach the networkFetch the fix; leak data; abuseno network
4Exhaust the hostNeighbouring rollouts fail for no reason of their ownmemory / CPU / pids limits
5Escape to the hostEverything above, for every rolloutcapabilities, no-new-privileges, the never-list; then page 24
6Persist between rolloutsSamples stop being independentfresh container, no shared volumes (page 22)

The starting point is the course's running example. wordfreq-bench:hardened already does the image-level work (page 22): non-root default user, no grader, no solution, no git history. What follows is the run-time half.

The hardening ladder

Rung 1 — not root: --user

Root inside a default container is host uid 0 wearing a restricted set of capabilities: Docker can map container root to an unprivileged host user, but that facility "is available but not enabled by default."[Docker: security] Inside the box, root also owns nearly every file. One flag changes that: 

$ docker run --rm -u root wordfreq-bench:hardened bash -c 'echo pwned >> /etc/passwd && echo root-wrote-it'
root-wrote-it
$ docker run --rm wordfreq-bench:hardened bash -c 'echo pwned >> /etc/passwd'
bash: line 1: /etc/passwd: Permission denied

Verify inside: id -u is not 0. Cost: the agent can no longer install software, and it will try: 

$ docker run --rm wordfreq-bench:hardened bash -c 'apt-get install -y git 2>&1 | tail -2'
E: Could not open lock file /var/lib/dpkg/lock-frontend - open (13: Permission denied)
E: Unable to acquire the dpkg frontend lock (/var/lib/dpkg/lock-frontend), are you root?

If the task needs a tool, install it at build time. Don't hand the agent sudo — that is rung 1 undone (page 7).

Rung 2 — no capabilities: --cap-drop ALL

A capability is one slice of root's power (page 21). Docker's own advice: "The best practice for users would be to remove all capabilities except those explicitly required for their processes."[Docker: security] Read the masks from /proc/self/status — CapEff is what the process can use now, CapBnd (the bounding set) is the ceiling on what it could ever regain: 

$ docker run --rm -u root wordfreq-bench:hardened grep -E 'CapEff|CapBnd' /proc/self/status
CapEff:	00000000a80425fb
CapBnd:	00000000a80425fb
$ docker run --rm wordfreq-bench:hardened grep -E 'CapEff|CapBnd' /proc/self/status   # user agent
CapEff:	0000000000000000
CapBnd:	00000000a80425fb
$ docker run --rm --cap-drop ALL wordfreq-bench:hardened grep -E 'CapEff|CapBnd' /proc/self/status
CapEff:	0000000000000000
CapBnd:	0000000000000000

The middle case is the subtle one. A non-root user has no effective capabilities, which looks safe — but the ceiling is still Docker's default fourteen,[Docker: run] so anything that turns the agent into root (a setuid binary, a misconfigured sudo) gets them all back. --cap-drop ALL empties the ceiling. Even root is then nearly powerless: 

$ docker run --rm -u root --cap-drop ALL wordfreq-bench:hardened bash -c 'id -u; chown agent /etc/hostname'
0
chown: changing ownership of '/etc/hostname': Operation not permitted
$ docker run --rm -u root --cap-drop ALL --cap-add CHOWN wordfreq-bench:hardened bash -c 'chown agent /etc/hostname && echo chown-ok'
chown-ok

Verify inside: CapEff and CapBnd all zeros. Cost: tasks that legitimately need a capability — a networking task that uses raw sockets needs NET_RAW; a service binding port 80 needs NET_BIND_SERVICE[capabilities(7)] — fail with a permission error. Add back per task family with --cap-add, as above, and write down why.

Rung 3 — no way back up: --security-opt no-new-privileges

The classic route from user to root is a setuid-root program: the kernel runs it as root no matter who starts it (page 8). The stock image ships eight (su, mount, passwd, …; find / -xdev -perm -4000 lists them). The kernel's no_new_privs bit switches the mechanism off for a process and all its descendants: "the setuid and setgid bits will no longer change the uid or gid", and once set it "cannot be unset."[seccomp(2)] To see it, I planted a setuid-root copy of id in two containers (as root, beforehand) and ran it as agent: 

$ docker exec lt-23-nnp0 ls -l /usr/local/bin/rootid
-rwsr-xr-x 1 root root 67952 Sep 21 16:14 /usr/local/bin/rootid
$ docker exec -u agent lt-23-nnp0 /usr/local/bin/rootid          # default container
uid=1001(agent) gid=1001(agent) euid=0(root) groups=1001(agent)
$ docker exec -u agent lt-23-nnp1 /usr/local/bin/rootid          # --security-opt no-new-privileges
uid=1001(agent) gid=1001(agent) groups=1001(agent)
$ docker exec -u agent lt-23-nnp1 grep NoNewPrivs /proc/self/status
NoNewPrivs:	1

Verify inside: NoNewPrivs: 1. Cost: Docker says it plainly — "commands that raise privileges such as su or sudo no longer work."[Docker: run] For an agent sandbox that is the point.

Rung 4 — a read-only root: --read-only, --tmpfs, one volume

Make the whole root filesystem a read-only mount, then add back exactly the writable places the task needs: a size-capped tmpfs at /tmp and a fresh anonymous volume at /app (Docker copies the image's /app into an empty volume, so the task files are there[Docker: storage]). Unlike file permissions, a read-only mount binds root too, short of CAP_SYS_ADMIN — which rung 2 removed (page 14). 

$ docker exec lt-23-rollout bash -c 'touch /app/ok && echo app-writable; touch /etc/x; touch /home/agent/x'
app-writable
touch: cannot touch '/etc/x': Read-only file system
touch: cannot touch '/home/agent/x': Read-only file system
$ docker exec lt-23-rollout bash -c 'grep -E " / | /app | /tmp " /proc/mounts | cut -c1-60'
overlay / overlay ro,relatime,lowerdir=/var/lib/desktop-contai
tmpfs /tmp tmpfs rw,nosuid,nodev,noexec,relatime,size=65536k
/dev/vda1 /app ext4 rw,relatime,discard 0 0

Verify inside: findmnt -n -O ro / prints a line. Cost: the largest of any rung, because so much software assumes a writable home directory. Observed here: 

$ docker run --rm --read-only --tmpfs /tmp:size=64m wordfreq-bench:hardened bash -c 'python3 -m venv /home/agent/venv 2>&1 | tail -1'
Error: [Errno 30] Read-only file system: '/home/agent/venv'
$ docker run --rm --read-only --tmpfs /tmp:size=64m wordfreq-bench:hardened bash -c 'head -c 100m /dev/zero > /tmp/big'
head: error writing 'standard output': No space left on device
$ docker cp fix.py lt-23-rollout:/tmp/fix.py
Error response from daemon: container rootfs is marked read-only

The last one bites the harness: docker cp into a read-only container is refused, even when the target is the writable tmpfs. Copy into the volume (docker cp fix.py NAME:/app/ works), or stream over stdin: docker exec -i NAME bash -c 'cat > /tmp/fix.py' < fix.py. Note too that the tmpfs is noexec (lab exercise 3) and that its contents count against the container's memory limit.[Docker: storage]

Rung 5 — no network: --network none

The container gets its own network namespace with only a loopback interface.[Docker: run] No route, no DNS, nothing to misconfigure: 

$ docker run --rm --network none wordfreq-bench:hardened bash -c 'cat /proc/net/route; python3 -c "import socket; socket.create_connection((\"1.1.1.1\", 443), 3)" 2>&1 | tail -1'
Iface	Destination	Gateway 	Flags	RefCnt	Use	Metric	Mask		MTU	Window	IRTT
OSError: [Errno 101] Network is unreachable

Verify inside: the routing table is a header and nothing else. Cost: every pip install, git clone and curl fails. When a task truly needs some network, the next step is an internal network plus an allowlisting proxy — page 19 has the Linux side, and Networking for LLM Evals, lesson 14 the concepts. A pass rate with network and one without are different measurements; say which you ran.

Rung 6 — budgets: --memory, --cpus, --pids-limit

Docker's default is no limit at all, so one runaway rollout can starve the host and fail its neighbours. The cgroup controllers enforce ceilings (page 21); Docker's security page calls them "essential to fend off some denial-of-service attacks."[Docker: security] The one people forget is processes. With pids.max set, fork() "will return -EAGAIN if the creation of a new process would cause a cgroup policy to be violated"[Kernel: cgroup-v2] — a fork bomb stalls instead of taking the host down. A safe demonstration — one hundred harmless sleeps against a limit of fifty: 

$ docker run --rm --pids-limit 50 --memory 128m wordfreq-bench:hardened \
    bash -c 'for i in $(seq 1 100); do sleep 3 & done 2>&1 | sort | uniq -c; cat /sys/fs/cgroup/pids.events'
      4 bash: fork: retry: Resource temporarily unavailable
max 4

(Use --pids-limit, not --ulimit nproc: Linux applies nproc "to a user, not to a container."[Docker: run]) Verify inside: memory.max, cpu.max and pids.max under /sys/fs/cgroup are numbers, not max. Cost: this is the rung that most directly moves scores. Too little memory and capable rollouts die with exit 137; too little CPU and they time out. Terminal-Bench 2.1 found eight tasks whose resource budgets were insufficient "for at least one valid approach" to finish consistently.[Terminal-Bench]

The never-list

Four things no agent sandbox should have, whatever the task author says:

  • --privileged. Docker: "A container with --privileged is not a securely sandboxed process. Containers in this mode can get a root shell on the host and take control over the system."[Docker: run] (The course's lab uses it for namespace demos on a throwaway container. A lab is not a sandbox.)
  • The Docker socket (-v /var/run/docker.sock:…) or a reachable Docker API. Mounting the socket gives "the full access to create and manipulate the host's Docker daemon"[Docker: run], and daemon access is host root: "The docker group grants root-level privileges to the user."[Docker: security] The network variant is the one that has actually happened. Docker warns that a TCP API endpoint "can be still accessible from containers, and it can easily result in the privilege escalation."[Docker: security] In OpenAI's September 2024 o1 system card, o1-preview — facing a challenge container that had failed to start — scanned its network and "found that the Docker daemon API running on the evaluation host VM was accessible due to a misconfiguration", then used it to start a new container with the command cat flag.txt and read the flag from its logs.[o1 System Card] No kernel boundary was broken; the front door was on the network (page 17).
  • Writable bind mounts of host paths. "Bind mounts have write access to files on the host by default."[Docker: storage] If you must mount, add readonly.
  • --pid=host, --network=host. Each deletes one namespace wall (page 20).

The check that you haven't — from outside, against a live sandbox:

$ docker inspect --format 'privileged={{.HostConfig.Privileged}} pid={{.HostConfig.PidMode}} net={{.HostConfig.NetworkMode}} binds={{json .HostConfig.Binds}} capdrop={{json .HostConfig.CapDrop}} secopt={{json .HostConfig.SecurityOpt}} ro={{.HostConfig.ReadonlyRootfs}} user={{.Config.User}}' lt-23-h
privileged=false pid= net=none binds=null capdrop=["ALL"] secopt=["no-new-privileges"] ro=true user=agent

and, for task definitions you were handed, grep -rnE 'privileged|docker\.sock|pid: *"?host|network_mode: *"?host' over the compose files. Terminal-Bench runs a check of this kind — no privileged containers — in CI on every submitted task.[Terminal-Bench]

The daemon-level upgrade: userns-remap and rootless

Everything so far configures one container. Two settings change the daemon. userns-remap maps container root to an unprivileged host uid using a user namespace; Docker positions it for "containers whose processes must run as the root user", noting the best defence is still unprivileged users.[Docker: security] Rootless mode goes further: "both the daemon and the container are running without root privileges."[Docker: security] Its documented limitations include resource limits only with cgroup v2 and systemd, and no AppArmor.[Docker: security]

Depth triage

Learn to use: the six rungs, the never-list, the verification script below — you should be able to write and defend this policy. Recognise: seccomp profiles (keep Docker's default; check Seccomp: in /proc/self/status), AppArmor's docker-default, userns-remap and rootless — know what they are and ask whether they are on. Leave to a security specialist: custom seccomp or AppArmor profiles, kernel CVE assessment, and the decision that containers are enough isolation for a given model (page 24).

Assembled: run-hardened.sh

The whole ladder as one command — research/wordfreq-bench/run-hardened.sh, verbatim:

#!/usr/bin/env bash
# Start one hardened rollout sandbox. Usage: run-hardened.sh NAME
set -euo pipefail
name=${1:?usage: run-hardened.sh NAME}
docker run -d --name "$name" \
  --user agent \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --read-only --tmpfs /tmp:size=64m \
  --mount type=volume,dst=/app \
  --network none \
  --memory 512m --cpus 1 --pids-limit 128 \
  --init \
  wordfreq-bench:hardened

(--init is not security: it gives the box a real PID 1 that reaps zombies and forwards signals, so teardown is prompt — page 10.) Every flag has a Compose key, which is the form harnesses like Inspect consume:[Compose] 

services:
  default:
    image: wordfreq-bench:hardened
    user: agent
    cap_drop: [ALL]
    security_opt: [no-new-privileges]
    read_only: true
    tmpfs: ["/tmp:size=64m"]
    volumes: ["/app"]            # anonymous volume: writable, removed by `down -v`
    network_mode: none
    mem_limit: 512m
    cpus: 1.0
    pids_limit: 128
    init: true

Trust nothing you haven't checked from inside

A flag in a script is an intention. The property is what the kernel reports to a process in the box. This script (29 lines, ShellCheck-clean) checks each rung from inside and exits non-zero if any fails: 

#!/usr/bin/env bash
# Inside-out check of a hardened sandbox. Run INSIDE the box: exits 0 only if every line is PASS.
# Usage (read-only root, so feed it on stdin): docker exec -i NAME bash -s < verify-sandbox.sh
set -u
fails=0
check() { # check DESCRIPTION COMMAND...
  local desc=$1; shift
  if "$@" >/dev/null 2>&1; then echo "PASS  $desc"; else echo "FAIL  $desc"; fails=$((fails + 1)); fi
}
status() { awk -v k="$1:" '$1 == k { print $2 }' /proc/self/status; }
cg() { cat "/sys/fs/cgroup/$1"; }

check "not root (uid $(id -u))"               test "$(id -u)" -ne 0
check "effective capabilities empty"          test "$(status CapEff)" = 0000000000000000
check "bounding set empty"                    test "$(status CapBnd)" = 0000000000000000
check "no_new_privs set"                      test "$(status NoNewPrivs)" = 1
check "root filesystem mounted read-only"     findmnt -n -O ro /
check "/etc, /usr, /home not writable"        bash -c '[ ! -w /etc ] && [ ! -w /usr ] && [ ! -w /home ]'
check "/tmp writable"                         touch /tmp/.probe
check "/app writable"                         touch /app/.probe
check "no route off the box"                  test "$(wc -l </proc/net/route)" -le 1
check "memory limit set ($(cg memory.max))"   test "$(cg memory.max)" != max
check "pids limit set ($(cg pids.max))"       test "$(cg pids.max)" != max
check "cpu limit set ($(cg cpu.max))"         bash -c '! grep -q "^max" /sys/fs/cgroup/cpu.max'
check "no Docker socket in the box"           test ! -e /var/run/docker.sock
check "no grader directory in the box"        test ! -e /opt/grader
rm -f /tmp/.probe /app/.probe
echo "$fails check(s) failed"
exit "$((fails > 0))"

Against the hardened sandbox, and against a plain docker run -d wordfreq-bench:sloppy:

$ docker exec -i lt-23-h bash -s < verify-sandbox.sh

PASS  effective capabilities empty
PASS  bounding set empty

PASS  root filesystem mounted read-only
PASS  /etc, /usr, /home not writable
PASS  /tmp writable
PASS  /app writable
PASS  no route off the box
PASS  memory limit set (536870912)
PASS  pids limit set (128)
PASS  cpu limit set (100000 100000)
PASS  no Docker socket in the box

0 check(s) failed

Pitfall — a check that cannot fail

My first draft of the last check was bash -c '! ls -d /opt/grader /tmp/solution'. It printed PASS on the sloppy image, where /opt/grader plainly exists: ls exits non-zero if either path is missing, and ! turned that into success. A verification script is a grader, with a grader's bugs (page 6). Always run it against a box you know is bad and confirm it says so.

Hardening is a measurement decision

The sandbox is now part of the instrument, so changing it can change scores. The discipline that catches this is Terminal-Bench's "solvability" criterion: every task ships an oracle solution, and CI runs it to confirm all tests pass.[Terminal-Bench] Do the same under your policy: apply the oracle fix inside the hardened sandbox, then grade from outside with grade.sh (page 26 explains the design): 

$ ./run-hardened.sh lt-23-oracle
$ docker exec -i lt-23-oracle bash -c 'cat > /tmp/fix.py' < fix.py && docker exec lt-23-oracle python3 /tmp/fix.py
$ ./grade.sh lt-23-oracle results.jsonl; cat results.jsonl
{"exit_code": 0, "passed": true, "stderr_tail": "Ran 2 tests in 0.002s  OK "}
In eval work — what the oracle run caught here

When I first ran that sequence for this page, the oracle failed ("passed": false … FAILED (failures=2)), although python3 wordfreq.py data/sample.txt inside the sandbox printed the right answer. Observed: correct in the box, failing grade outside it. Hypotheses: docker cp missed the volume, or the grader imported the wrong code. Discriminating tests: grep the copied-out file (the fix was there); run the hidden tests by hand from another directory (they passed). The cause: the grading container's working directory was the image's WORKDIR /app, which holds the image's own buggy wordfreq.py, and python3 -m puts the working directory first on the import path — the grader graded the image, not the submission. Every model would have scored zero. The fix in grade.sh is one flag, --workdir /tmp. An oracle that must pass and a no-op that must fail are the two cheapest tests an environment can have.

In eval work — ship the self-test

Design: run the verification script in a fresh sandbox before every eval and abort if it fails; record the policy (the docker inspect line above) with the results. When a hardened run puts Read-only file system, Operation not permitted or Network is unreachable into transcripts, those are effects of your policy. A task unsolvable under the policy is an environment defect: exclude it for every model and say so. Don't leave it in the denominator as a model failure, and don't drop it for some models only.

Caveat — this is still one shared kernel

Docker's security page lists four areas to review: the kernel's namespace and cgroup support, "the attack surface of the Docker daemon itself", "loopholes in the container configuration profile", and the kernel's hardening features.[Docker: security] This page closed the third and kept the agent away from the second. It did nothing about the first: every system call the agent makes still lands in the host's kernel, and a kernel bug is a way out that no flag here addresses. Two machine-specific notes: a stock Linux Docker Engine applies a default seccomp profile (you'd see Seccomp: 2), but the Docker Desktop daemon used for this page runs unconfined (Seccomp: 0), so check docker info on the hosts you measure on; and Docker Desktop has no AppArmor. Whether a shared kernel is acceptable is a threat-model question — page 24.

Check your understanding

Your team hardens a 200-task benchmark with exactly this page's policy. The headline pass rate for the same model drops from 61% to 48%. A colleague says: "Good — 13 points of that score were cheating." What would you need to see before agreeing?

Reveal the reasoning

Observed: a 13-point drop after a policy change. Supposed: that the lost passes were illegitimate. At least three causes produce the same drop: (a) the old passes used the network or root to shortcut tasks — integrity gain; (b) tasks legitimately need something the policy removed (pip install, a writable home, a capability, more than 512 MB) — validity loss, the benchmark now measures the sandbox; (c) the harness itself broke (docker cp into a read-only root, a grader bug like the one above). Discriminating evidence: run every oracle solution under the new policy — any oracle that fails identifies (b) or (c) with no model involved; diff the per-task results and read transcripts of tasks that flipped, looking for Read-only file system, Network is unreachable, Operation not permitted, exit 137; check memory.events for OOM kills. For the old passes, look for the shortcut in the trajectory. Only flips where the old transcript shows a shortcut count as "cheating removed". Report tasks unsolvable under the policy as excluded (for all models), report infrastructure deaths separately from wrong answers, and state the policy next to the score.

Lab

Container lab, from your Mac's terminal in research/wordfreq-bench/ with both images built. Save the verification script above as verify-sandbox.sh.

  1. Reproduce. Start a sandbox with ./run-hardened.sh h1 and run the verification script in it. Then confirm two properties by hand: read CapBnd, and try to create /etc/x.
    Solution 
    $ ./run-hardened.sh h1
$ docker exec -i h1 bash -s < verify-sandbox.sh | tail -1
0 check(s) failed
$ docker exec h1 grep -E 'CapEff|CapBnd|NoNewPrivs' /proc/self/status
CapEff:	0000000000000000
CapBnd:	0000000000000000
NoNewPrivs:	1
$ docker exec h1 touch /etc/x
touch: cannot touch '/etc/x': Read-only file system
  2. Predict, then verify. Run the image with only --user agent (the default) and no other flag. Before looking: will CapEff be zero? Will CapBnd? What does the difference mean?
    Solution 
    $ docker run --rm wordfreq-bench:hardened grep -E 'CapEff|CapBnd' /proc/self/status
CapEff:	0000000000000000
CapBnd:	00000000a80425fb

    Effective is empty, the bounding set is not: a setuid-root binary would hand the agent Docker's default capabilities. --cap-drop ALL closes the ceiling; no-new-privileges closes the route.

  3. Predict, then verify. In h1, write a two-line shell script to /tmp/t.sh, chmod +x it, and run it as /tmp/t.sh. Then run it as sh /tmp/t.sh. Predict both outcomes from the /tmp line of /proc/mounts shown in rung 4.
    Solution 
    $ docker exec h1 bash -c 'printf "#!/bin/sh\necho ran\n" > /tmp/t.sh; chmod +x /tmp/t.sh; /tmp/t.sh; sh /tmp/t.sh'
bash: line 1: /tmp/t.sh: Permission denied
ran

    The tmpfs is mounted noexec: the kernel refuses to execute files from it whatever their mode bits say, but sh (which lives on /) can still read the script and interpret it. In a transcript this is a Permission denied that chmod cannot fix — an effect of the sandbox policy, not a model error. An agent that compiles a binary into /tmp will hit it; have it build in /app, or mount the tmpfs with exec and say so in the policy.

  4. Eval task: the hardened rollout, end to end. Apply a fix inside h1 without docker cp to /tmp (it is refused — try it), grade from outside with ./grade.sh h1 results.jsonl, then grade a fresh, untouched sandbox h2. You should get one pass and one fail. Clean up with docker rm -f -v h1 h2.
    Solution

    Any correct edit works; the oracle is in solution/wordfreq.patch.py. For example, stream a small Python patch script in over stdin as the page did, or edit with docker exec h1 sed -i …. Then:

    $ ./grade.sh h1 results.jsonl; echo "exit=$?"
exit=0
$ ./run-hardened.sh h2 >/dev/null; ./grade.sh h2 results.jsonl; echo "exit=$?"
exit=1
$ cat results.jsonl
{"exit_code": 0, "passed": true, "stderr_tail": "Ran 2 tests in 0.001s  OK "}
{"exit_code": 1, "passed": false, "stderr_tail": "Ran 2 tests in 0.001s  FAILED (failures=2) "}

    The oracle passes and the no-op fails: the two cheapest tests of an environment. -v on docker rm removes the anonymous /app volume; without it, volumes pile up on the host.

  5. Eval task: audit from outside. You are handed a running sandbox (docker run -d --name s1 wordfreq-bench:sloppy). Using only docker inspect, list which rungs of this page are missing.
    Solution 
    $ docker inspect --format 'privileged={{.HostConfig.Privileged}} net={{.HostConfig.NetworkMode}} capdrop={{json .HostConfig.CapDrop}} secopt={{json .HostConfig.SecurityOpt}} ro={{.HostConfig.ReadonlyRootfs}} user={{.Config.User}} mem={{.HostConfig.Memory}} pids={{.HostConfig.PidsLimit}}' s1
privileged=false net=bridge capdrop=null secopt=null ro=false user= mem=0 pids=<nil>

    Empty user means root; no cap drop; no no-new-privileges; writable root; bridge network; mem=0 and pids=<nil> mean no limit. Rungs 1–6 are all missing. The one thing in its favour: not privileged.
