Mounts and filesystems

The directory tree you see in a Linux box is stitched together from many separate filesystems, and the list of stitches — the mount table — says which parts are on disk, which are in RAM, which come from the host, and which can be written. This page teaches you to read that table, because "what is mounted, and is it read-only?" is audit question 2, and a read-only mount is the strongest protection against test tampering you can give a sandbox from the inside.

One tree, many filesystems

Page 3 showed a single tree rooted at /. What it did not say is that the tree is a composite. A filesystem is one self-contained store of files and directories — a formatted disk partition, a chunk of RAM, a view into the kernel. To mount a filesystem is to attach it to the tree at some existing directory, the mount point. From then on, paths below that directory lead into the attached filesystem. mount(8) opens with exactly this picture: "All files accessible in a Unix system are arranged in one big tree, the file hierarchy, rooted at /. These files can be spread out over several devices. The mount command serves to attach the filesystem found on some device to the big file tree."[mount(8)]

what you see: one tree what it is made of / overlay image layers + a scratch layer ├── app/ ◀── graft ────── ext4 a Docker volume (disk) ├── tmp/ ◀── graft ────── tmpfs RAM ├── tests/ ◀── graft ────── (host) a host directory, read-only ├── proc/ ◀── graft ────── proc the kernel, pretending to be files ├── sys/ ◀── graft ────── sysfs the kernel again ├── dev/ ◀── graft ────── tmpfs device files └── etc/ └── hosts ◀── graft ────── ext4 a single file from the host the mount table = the list of grafts: (where, what, type, options)

Two properties of grafting explain most surprises later. First, a mount covers whatever the directory held before: "The previous contents (if any) and owner and mode of dir become invisible."[mount(8)] Nothing is deleted; it is hidden until the mount is removed. Second, every mount carries its own options, so "can I write here?" has a different answer in different parts of the same tree.

The mount table is not global. Each mount namespace (page 20) has its own, which is how a container gets a different / from its host: the kernel file /proc/pid/mountinfo "contains information about mounts in the process's mount namespace".[proc_pid_mountinfo(5)] That file is the ground truth; every tool below is a reader of it.

Read it as four groups.

LinesWhat they areWhat to notice
/ — overlay The container's root: the image's layers plus a private scratch layer, merged by overlayfs (below). rw: by default a container can write anywhere in its own root.
/proc, /sys, /sys/fs/cgroup Pseudo-filesystems: no disk behind them, the kernel answers reads directly — the proc filesystem, sysfs, and the cgroup tree. Docker mounts the dangerous parts ro (/proc/sys, /sys) and hides others by mounting /dev/null or an empty tmpfs over them (/proc/kcore, /proc/keys). Covering, used as a safety device.
/dev, /dev/shm tmpfs: filesystems held in memory. /dev/shm is writable, world-accessible and 64 MB here — remember it when you think you have made a container read-only.
/etc/resolv.conf, /etc/hostname, /etc/hosts Three single files mounted from the host's ext4 disk — bind mounts. The SOURCE column's device[/path] form means "this sub-path of that filesystem". It is how Docker injects per-container DNS and host names.

The three invocations worth memorising:

# findmnt -T /usr/bin/env -o TARGET,FSTYPE     # which filesystem holds this path?
TARGET FSTYPE
/      overlay
# findmnt -n -o FSTYPE -T /etc/hostname
ext4
# findmnt -O ro -o TARGET,FSTYPE               # every mount that has the ro option
TARGET              FSTYPE
/proc/bus           proc
…
/sys                sysfs
|-/sys/firmware     tmpfs
`-/sys/fs/cgroup    cgroup2

-T path walks up from a path to the mount that contains it — the right question when you care about one file ("is expected.json on a read-only mount?"). -O ro filters by option. In scripts always name your columns with -o: the default output "is subject to change".[findmnt(8)]

You will meet three older readers in transcripts. mount with no arguments prints the same table as source on target type fstype (options); its man page says this mode "is maintained for backward compatibility only" and points to findmnt.[mount(8)] df -hT answers a different question — how full is each filesystem (page 12) — and omits the pseudo-filesystems. lsblk lists block devices (disks and partitions); inside a container it shows the host's disks, which is rarely what you want. And if findmnt is missing (minimal images), cat /proc/self/mountinfo always works: 

# head -2 /proc/self/mountinfo
388 258 0:82 / / rw,relatime - overlay overlay rw,lowerdir=/var/lib/desktop-containerd/…
390 388 0:149 / /proc rw,nosuid,nodev,noexec,relatime - proc proc rw

Field 5 is the mount point, field 6 the per-mount options, and after the lone - come the filesystem type, the source, and the filesystem-wide options.[proc_pid_mountinfo(5)] "Read-only" can differ between field 6 and the last field: one mount of a filesystem can be read-only while the filesystem itself is writable. That distinction returns below. findmnt's VFS-OPTIONS column shows the per-mount half.

The four options that matter

Optionmount(8) saysWhy you care
ro"Mount the filesystem read-only."Nothing under this mount can be created, changed, deleted, chmod-ed or chown-ed — by anyone.
nosuid"Do not honor set-user-ID and set-group-ID bits or file capabilities when executing programs from this filesystem."Closes the setuid route to privilege escalation (page 8) on writable scratch space.
nodev"Do not interpret character or block special devices on the filesystem."A device file created here does nothing.
noexec"Do not permit direct execution of any binaries on the mounted filesystem."Note the word direct: sh script.sh and python3 x.py still run, because the program being executed is the interpreter, which lives elsewhere.

All four wordings are from mount(8).[mount(8)] The noexec line matters in transcripts: Docker's --tmpfs applies nosuid,nodev,noexec by default, so an agent that writes a script into such a /tmp and runs it as /tmp/s.sh gets Permission denied with exit status 126, while sh /tmp/s.sh works (both executed in the lab below). The mode bits are fine; the mount said no.

tmpfs: files that are really memory

A tmpfs keeps its files in virtual memory. It "consumes only as much physical memory and swap space as is required to store the current contents", its contents vanish when it is unmounted, and if you give no size, "the default… is size=50%" of physical RAM.[tmpfs(5)] Docker's --tmpfs inherits that default — "50% of the host's total RAM".[Docker: storage] It is the natural choice for a sandbox's /tmp: fast, private, and gone at reset. Two caveats. It is not strictly "memory only": tmpfs "can employ swap space", so Docker warns the data "may be written to a swap file, and thereby persisted". And the size option is not the limit that bites. The kernel charges tmpfs pages to the memory cgroup of whoever wrote them,[Kernel: cgroup-v2] and Docker says so plainly: "that usage counts against the container's memory cgroup limit… filling the mount can still OOM the container."[Docker: storage]

So which failure do you get when a tmpfs fills — "disk full" or the OOM killer? It depends on which limit is smaller. Tmpfs smaller than the memory limit:

$ docker run --rm --memory 256m --tmpfs /scratch:size=32m ubuntu:24.04 \
    bash -c 'dd if=/dev/zero of=/scratch/big bs=1M count=100; echo exit=$?'
dd: error writing '/scratch/big': No space left on device
33+0 records in
32+0 records out
33554432 bytes (34 MB, 32 MiB) copied, 0.0370601 s, 905 MB/s
exit=1

Tmpfs (200 MB) larger than the memory limit (64 MB), same write:

$ docker run --name lt-14-oom --memory 64m --memory-swap 64m --tmpfs /scratch:size=200m \
    ubuntu:24.04 bash -c 'dd if=/dev/zero of=/scratch/big bs=1M count=100; echo exit=$?'
$ echo $?
137
$ docker inspect --format 'OOMKilled={{.State.OOMKilled}} ExitCode={{.State.ExitCode}}' lt-14-oom
OOMKilled=true ExitCode=137

No output at all: not even exit=. The kernel killed the container's main bash, and with PID 1 gone the container ended with 137 (128 + 9, page 10). When the same command ran under the much smaller sh, dd was the victim instead: the script printed Killed, exit=137, shmem 64823296 and oom_kill 1, then finished — and the container's own exit code was 0 with OOMKilled=true. That much is observed. A likely explanation — tmpfs pages belong to no process, so the killer chooses among processes by their own size — is a hypothesis this page has not tested. The practical rule does not depend on it: the victim of a tmpfs-driven OOM need not be the process that wrote the files, and the container's exit code alone will not tell you an OOM happened.

In eval work — navigate, then account

An agent that unpacks a dataset into a tmpfs /tmp can get its test runner killed minutes later, with a transcript that shows only Killed or a tool call that never returns. Evidence to collect before blaming anyone: docker inspect's OOMKilled, oom_kill in /sys/fs/cgroup/memory.events, shmem in memory.stat, and df -h /tmp (page 12). If those show the box ran out of room, the outcome is an infrastructure failure: a fact about the run. Record it as its own status (oom, enospc), keep it in the scheduled count, and report correct / scheduled, correct / completed and completed / scheduled separately. Quietly re-running only the killed samples, or dropping them, changes the denominator after you have seen the results. And if one model hits the limit far more than another, that is a finding about how the environment's budget interacts with behaviour — report it, don't average it away.

Bind mounts: one directory, two places

A bind mount attaches something already in the tree at a second location: "the same contents are accessible in two places", and the man page stresses that nothing marks it as special — "The 'bind' is just another operation to attach a filesystem."[mount(8)] It works for single files too, which is what the three /etc lines above were. This is the mechanism behind docker run -v /host/dir:/ctr/dir: "a file or directory on the host machine is mounted from the host into a container." A Docker volume is the same thing with Docker choosing and managing the host directory.[Docker: storage]

Mounting needs privilege — mount(2) is one of the operations gated by CAP_SYS_ADMIN,[capabilities(7)] which Docker does not grant by default (page 21) — so this demo runs in a throwaway container started with --cap-add SYS_ADMIN: 

# mkdir -p /srv/tests /mnt/view; echo secret-test > /srv/tests/t.py
# mount --bind /srv/tests /mnt/view
# mount -o remount,bind,ro /mnt/view
# findmnt -n -o TARGET,SOURCE,VFS-OPTIONS /mnt/view
/mnt/view overlay[/srv/tests] ro,relatime
# echo tamper >> /mnt/view/t.py
bash: line 8: /mnt/view/t.py: Read-only file system
# echo tamper >> /srv/tests/t.py; echo "exit=$?"
exit=0
# cat /mnt/view/t.py
secret-test
tamper

The read-only view refused the write; the original path accepted it, and the change showed up through the "read-only" view. The man page warns of exactly this: "the olddir will be writable, but the newdir will be read-only." (The one-step form mount -o bind,ro olddir newdir also works on current systems; it is implemented as the same two calls and "is not atomic". Either way, mounts nested under the bound directory are not made read-only by the classic call.)[mount(8)]

Key idea

Read-only is a property of a mount — one path into the data — not of the data. Auditing "are the tests read-only?" means checking every path by which the box can reach them.

Overlayfs: why a container can scribble on an image

The overlay line for / is how one read-only image serves a thousand containers. Overlayfs merges directory trees: one or more read-only lower directories (the image's layers, colon-separated in lowerdir=) and one writable upper directory (the container's scratch layer). "When a name exists in both filesystems, the object in the 'upper' filesystem is visible"; writing to a lower file first copies the whole file up; deleting one leaves a marker, a whiteout, in the upper directory.[Kernel: overlayfs] Built by hand, after echo changed >> merged/a.txt; rm merged/b.txt; echo new > merged/c.txt: 

# ls -l upper
total 8
-rw-r--r-- 1 root root   17 Sep 21 16:18 a.txt     # copied up, then appended to
c--------- 2 root root 0, 0 Sep 21 16:18 b.txt     # whiteout: "b.txt is deleted"
-rw-r--r-- 1 root root    4 Sep 21 16:18 c.txt     # new file
# ls merged; cat lower/a.txt lower/b.txt
a.txt
c.txt
original
keep

The lower directory never changed. That is the whole consequence you need: deleting a file hides it; the layer underneath still has it. At image-build level the same rule means a solution removed by a later Dockerfile instruction is still inside the image (page 22, page 26). Depth triage: learn to use findmnt and recognise the overlay line; recognise lower, upper, copy-up and whiteout; leave the rest (opaque directories, metacopy, snapshotter internals) to whoever maintains the container runtime. One dated detail to recognise: older material says Docker's storage driver is overlay2 with layers under /var/lib/docker/overlay2; Docker's docs now make the containerd image store the default for fresh installs of Engine 29.0 and later, and the paths above (…/io.containerd.snapshotter.v1.overlayfs/snapshots/…) are what that looks like.[Kernel: overlayfs] Same kernel mechanism either way.

Background — what about chroot?

chroot changes what / means for a process, and old tutorials call it a jail. Its own man page says it "is not intended to be used for any kind of security purpose, neither to fully sandbox a process nor to restrict filesystem system calls."[chroot(2)] Containers get their root from a mount namespace instead (page 20).

Audit question 2: is it read-only?

Here is a sandbox with the typical eval layout — root filesystem read-only, a writable volume for the task repo, a tmpfs /tmp, hidden tests bind-mounted read-only — using the course's wordfreq-bench:hardened image: 

$ docker run -d --name lt-14-box --read-only --tmpfs /tmp:size=64m \
    --mount type=volume,dst=/app \
    --mount type=bind,src="$PWD/tests",dst=/tests,readonly wordfreq-bench:hardened
$ for t in / /app /tmp /tests; do docker exec lt-14-box findmnt -n -o TARGET,FSTYPE,VFS-OPTIONS $t; done
/      overlay ro,relatime
/app   ext4   rw,relatime
/tmp   tmpfs  rw,nosuid,nodev,noexec,relatime
/tests fakeowner ro,nosuid,nodev,relatime

(fakeowner is Docker Desktop's Mac file-sharing layer; on a Linux host you would see the host disk's type, such as ext4.) The table says what should be writable. Never stop at the table — try it, first as the agent's user, then as root: 

$ touch /etc/x; touch /tests/x; touch /app/x; echo "exit=$?"
touch: cannot touch '/etc/x': Read-only file system
touch: cannot touch '/tests/x': Read-only file system
exit=0
# touch /tests/x
touch: cannot touch '/tests/x': Read-only file system
# chmod 777 /tests
chmod: changing permissions of '/tests': Read-only file system
# mount -o remount,rw /tests; echo "exit=$?"
mount: /tests: permission denied.
       dmesg(1) may have more information after failed mount system call.
exit=32
# cat /tests/expected.json
{"the": 3}

Root could not write, could not chmod its way in, and could not remount, because remounting is a mount(2) call and the container's root lacks CAP_SYS_ADMIN. This is why a read-only mount beats mode bits (page 8) as tamper protection: mode bits are waived for root; mount options are not. The last command is the limit of the technique — root read the answer key without difficulty.

In eval work — design

Read-only protects against tampering, not reading. Mounting the hidden tests ro stops test tampering — an agent rewriting test_hidden.py to assert True — even if the agent is root. It does nothing about solution leakage: cat /tests/expected.json worked. Answer keys need absence: keep them out of the box and grade from outside, as wordfreq-bench's grade.sh does (page 23, page 26). The usual layout is therefore: reference data the task legitimately needs mounted ro; the work directory writable; scratch on a sized tmpfs; everything else read-only; graders and answers not mounted at all.

Pitfall — the writable host mount

Docker's default is the dangerous one: "Bind mounts have write access to files on the host by default."[Docker: storage] A harness that runs -v "$PWD":/workspace for convenience has cut a hole in the sandbox wall: a root agent can rewrite the harness's own files, results included. Add :ro (or readonly) unless the agent must write there, and check from outside with docker inspect --format '{{range .Mounts}}{{.Destination}} RW={{.RW}}{{"\n"}}{{end}}'. Note that --tmpfs mounts are listed separately, under .HostConfig.Tmpfs.

Pitfall — volumes outlive rollouts

A named volume survives --rm and container deletion; Docker removes only anonymous ones.[Docker: storage] Executed: rollout 1 ran docker run --rm -v lt-14-work:/work … 'echo answer-from-rollout-1 > /work/notes.txt'; a fresh container with the same -v then printed answer-from-rollout-1. Epoch 2 starting with epoch 1's files is cross-contamination, and two concurrent rollouts sharing a volume can overwrite each other's work. One volume per rollout, removed at reset — run-hardened.sh uses an anonymous volume for exactly this reason.

Check your understanding

A benchmark maintainer says: "Hidden tests are bind-mounted read-only at /tests, so agents can't game them." The harness copies the tests into the container's /opt/grader at start-up as well, "for speed", and runs them from there after the agent finishes. Two models' pass rates differ by six points. What would you establish before trusting the comparison?

Reveal the reasoning

What to establish. Read-only is per mount, so the question is which path the grader actually uses and whether that path is writable by the agent. findmnt -T /opt/grader will almost certainly answer / overlay rw: an ordinary copy in the writable layer. Then who owns it and with what mode, and what user the agent runs as — root ignores mode bits. Separately: both locations are readable, so the tests and any expected outputs can be read regardless.

Discriminating evidence. The claim "agents can't game them" is a hypothesis; test it. From the agent's identity, touch /opt/grader/x and cat a test file. Then search transcripts for commands touching /opt/grader or /tests, and compare checksums of /opt/grader at grading time against the originals for every rollout. Modified files are proof of tampering; reads are evidence of leakage; neither appearing is evidence, not proof, that it did not happen.

Bearing on the score. If one model edits or reads the grader more often, part of the six points measures willingness to exploit the environment, not task skill. Report tampered rollouts as their own category rather than as passes, fix the layout (grade from outside, or at least from the ro mount), and re-run before comparing.

Lab

Container lab. Most exercises are docker run lines typed in your Mac's terminal, because mounts are decided when a container starts.

  1. Reproduce. Print the mount table of a default ubuntu:24.04 container. Which filesystem type holds /etc/hostname? List only the read-only mounts.
    Solution 
    $ docker run --rm ubuntu:24.04 findmnt -n -o FSTYPE -T /etc/hostname
ext4
$ docker run --rm ubuntu:24.04 findmnt -O ro -o TARGET,FSTYPE
TARGET              FSTYPE
/proc/bus           proc
/proc/fs            proc
/proc/irq           proc
/proc/sys           proc
/proc/sysrq-trigger proc
/proc/scsi          tmpfs
/sys                sysfs
|-/sys/firmware     tmpfs
`-/sys/fs/cgroup    cgroup2

    Not the overlay you might have guessed: /etc/hostname is a single-file bind mount from the Docker host's disk. Everything read-only in a default container is kernel interface; the root itself is writable.

  2. Predict, then verify. Start a container with --read-only --tmpfs /tmp. Before running anything, write down which of touch /x, /tmp/x, /dev/shm/x, /var/tmp/x succeed. Then write a two-line script to /tmp/s.sh, chmod +x it, and predict what /tmp/s.sh and sh /tmp/s.sh do.
    Solution 
    $ docker run --rm --read-only --tmpfs /tmp ubuntu:24.04 bash -c 'for p in /x /tmp/x /dev/shm/x /var/tmp/x; do touch $p 2>&1; echo "$p exit=$?"; done
printf "#!/bin/sh\necho ran\n" > /tmp/s.sh; chmod +x /tmp/s.sh; /tmp/s.sh; echo "exit=$?"; sh /tmp/s.sh'
touch: cannot touch '/x': Read-only file system
/x exit=1
/tmp/x exit=0
/dev/shm/x exit=0
touch: cannot touch '/var/tmp/x': Read-only file system
/var/tmp/x exit=1
bash: line 2: /tmp/s.sh: Permission denied
exit=126
ran

    /dev/shm is a second writable tmpfs you did not ask for. The Permission denied is noexec, not mode bits: findmnt /tmp shows rw,nosuid,nodev,noexec,relatime.

  3. Predict, then verify. A container has --memory 256m and --tmpfs /scratch:size=32m. A process writes 100 MB to /scratch. ENOSPC or OOM kill? What single change flips the answer?
    Solution

    ENOSPC — the tmpfs limit (32 MB) is reached before the memory limit: dd: error writing '/scratch/big': No space left on device, exit 1, 32 MiB copied (full output in the tmpfs section). Make the tmpfs larger than the memory limit (--memory 64m --memory-swap 64m --tmpfs /scratch:size=200m) and the same write ends in an OOM kill: docker inspect reports OOMKilled=true. Always pass --memory when trying this.

  4. Reproduce. In docker run --rm -it --cap-add SYS_ADMIN ubuntu:24.04 bash, make a read-only bind mount of /srv/tests at /mnt/view and show that the data can still be changed.
    Solution

    The commands and output are the session in Bind mounts: mount --bind, then mount -o remount,bind,ro /mnt/view; a write via /mnt/view fails with Read-only file system, the same write via /srv/tests exits 0 and is visible through /mnt/view. mount -o bind,ro /srv/tests /mnt/two gives the same result in one step (findmnt -n -o TARGET,VFS-OPTIONS /mnt/two → /mnt/two ro,relatime).

  5. Eval task. A harness starts task containers with -v "$PWD/tests":/tests. Make a tests/test_hidden.py containing one assertion, show that a container can neutralise it, then fix the flag and bring three independent pieces of evidence that the fix holds.
    Solution 
    $ mkdir tests; echo 'assert count("The the") == {"the": 2}' > tests/test_hidden.py
$ docker run --rm -v "$PWD/tests":/tests ubuntu:24.04 bash -c 'echo "assert True" > /tests/test_hidden.py'
$ cat tests/test_hidden.py
assert True
$ echo 'assert count("The the") == {"the": 2}' > tests/test_hidden.py
$ docker run --rm -v "$PWD/tests":/tests:ro ubuntu:24.04 bash -c \
    'echo "assert True" > /tests/test_hidden.py; echo "exit=$?"; findmnt -n -o TARGET,VFS-OPTIONS /tests'
bash: line 1: /tests/test_hidden.py: Read-only file system
exit=1
/tests ro,nosuid,nodev,relatime
$ docker inspect --format '{{range .Mounts}}{{.Destination}} RW={{.RW}}{{"\n"}}{{end}}' container
/tests RW=false

    Evidence: the write attempt fails with EROFS as root; the mount table says ro; the runtime's record says RW=false; and the host file is unchanged. The file on your Mac really was rewritten in the first run — that is the hole. The tests are still readable; this fix addresses tampering only.
