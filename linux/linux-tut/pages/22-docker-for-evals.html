Module 6 · Containers & Isolation

Docker for eval environments

Pages 20 and 21 took the container apart into kernel features. This page puts it back together with the tool everyone actually types: Docker, organised around the life of one task environment — build it, run it, drive it, inspect it, throw it away. The running example is the real wordfreq-bench Dockerfile.

Who does what when you type docker run

Docker is not one program. The docker command you type is a client; it sends requests to a long-running daemon, dockerd, which owns the images and containers. The daemon in turn delegates: "Docker Engine uses containerd for managing the container lifecycle… By default, containerd uses runc as its container runtime."[OCI Runtime Spec] runc is the small program that finally makes the namespace, cgroup and capability system calls from pages 20–21, then gets out of the way.

you the Docker host (on a Mac: a Linux VM) ┌──────────┐ API ┌─────────┐ ┌────────────┐ ┌──────┐ │ docker │────────▶│ dockerd │─▶│ containerd │─▶│ runc │ │ (client) │ over a │ (daemon)│ │ lifecycle, │ └──┬───┘ └──────────┘ unix │ images, │ │ images │ │ namespaces, socket │ networks│ └────────────┘ │ cgroups, caps, └────┬────┘ ▼ rootfs; exec() │ ┌──────────────────────┐ registry ◀─ pull / push ─┘ │ container = ordinary │ (Docker Hub, …) │ Linux process(es) │ └──────────────────────┘

Two consequences follow from the picture. First, the client and the host can be different machines — on your Mac they always are: Docker Desktop runs the daemon inside a Linux virtual machine, and paths you bind-mount are resolved on "the Docker daemon host, not the client."[Docker: storage] Second, whoever can talk to the daemon's socket can start any container with any privileges, which is why the socket is the most dangerous file on the machine (page 23).

Images and containers: class and instance

An image is a read-only filesystem plus a little metadata (default command, user, environment). A container is a running instance of an image: the same files, plus a thin writable layer on top, plus a process. "All changes made to the running container… are written to this thin writable container layer."[Kernel: overlayfs] One image, a thousand containers, each with a private scratch layer — that is the whole reason containers suit evals, and the mechanism is the overlayfs mount from page 14.

The image itself is a stack of layers: "Each layer is only a set of differences from the layer before it."[Kernel: overlayfs] docker history lists them, newest first:

Background — "overlay2" or "overlayfs"?

Older tutorials say Docker's storage driver is overlay2. Docker's docs now say the containerd image store is the default for Docker Engine 29.0 and later on fresh installs, using the overlayfs snapshotter; hosts upgraded from earlier versions keep overlay2.[Kernel: overlayfs] Docker Desktop here reports overlayfs too. The kernel mechanism is identical either way; run docker info --format '{{.Driver}}' to see which you have.

Tags move; digests don't

ubuntu:24.04 is a tag: a human-friendly label that the publisher re-points whenever they rebuild. Docker's docs say it flatly: "Image tags are mutable." An image digest is the SHA-256 of the image's content; pinning to one means "you're guaranteed to always use the same image version, even if a publisher replaces the tag with a new image."[Docker: Dockerfile] 

$ docker image inspect --format '{{index .RepoDigests 0}}' ubuntu:24.04
ubuntu@sha256:008173c23f95b170204355c12626cb5a965d779a7e1283b09e9cffbb1bf33ca3

You can use that whole string anywhere an image name goes — docker run, a Dockerfile's FROM, a compose file. (Why this matters for drift: page 15.)

Build: the wordfreq-bench Dockerfile, line by line

A Dockerfile is the recipe for an image. This is the hardened task image for the course's running example, verbatim from research/wordfreq-bench/Dockerfile: 

# wordfreq-bench, hardened build. The grader and the oracle solution never enter this image:
# grading happens outside, after the agent exits (see grade.sh).
FROM ubuntu:24.04
RUN apt-get update && apt-get install -y --no-install-recommends python3 \
    && rm -rf /var/lib/apt/lists/*
RUN useradd --create-home --uid 1001 --shell /bin/bash agent
# exported tree only: no .git, so no history to mine
COPY --chown=agent:agent app /app
WORKDIR /app
USER agent
CMD ["sleep", "infinity"]
LineWhat it doesWhy it is written this way
FROM ubuntu:24.04Start from a base image. A tag, for readability in a teaching file. A published benchmark should use ubuntu:24.04@sha256:… — tag and digest.
RUN apt-get update && … install …Run a command at build time; its file changes become a layer. One RUN, not two. Docker's rule: "Always combine RUN apt-get update with apt-get install in the same RUN statement", because a cached update layer goes stale and later installs fail.[Docker: Dockerfile] The rm -rf is in the same RUN for a reason you'll see below.
RUN useradd … --uid 1001 … agentCreate the non-root user. Explicit uid so ownership is predictable across hosts (page 7); 1001 because Ubuntu's image already has ubuntu at 1000.
COPY --chown=agent:agent app /appCopy the task repo from the build context into the image. Only app/. The grader and solution directories sit beside it on the host and are never copied. No .git (page 26).
WORKDIR /appDefault working directory for later instructions and for the container.So the agent's first ls shows the task.
USER agentDefault user for the container's processes. Without it, "the default user within a container is root (uid = 0)."[Docker: run]
CMD ["sleep", "infinity"]The default command: do nothing, forever. The harness will exec the agent's commands into this idle container. JSON-array ("exec") form runs the program directly; the string ("shell") form wraps it in /bin/sh -c, and for an ENTRYPOINT the docs warn that the wrapped program "will not be the container's PID 1, and will not receive Unix signals."[Docker: Dockerfile] That is the ten-second docker stop hang from page 10.

Build it from the directory that holds the Dockerfile (the final . is the build context — the files COPY can see):

$ docker build -t wordfreq-bench:hardened .
…
#7 [2/5] RUN apt-get update && apt-get install -y --no-install-recommends python3     && rm -rf /var/lib/apt/lists/*
#7 CACHED
#8 [3/5] RUN useradd --create-home --uid 1001 --shell /bin/bash agent
#8 CACHED
#9 [4/5] COPY --chown=agent:agent app /app
#9 CACHED
…
#11 naming to docker.io/library/wordfreq-bench:hardened done

CACHED is the build cache: a step is reused if its inputs are unchanged. For RUN, "just the command string itself is used to find a match" — Docker does not know that the Ubuntu archive changed since yesterday — and once one step misses, every step after it rebuilds.[Docker: Dockerfile] So the same Dockerfile built today on my machine (cached apt layer from last month) and on yours (fresh) yields different package versions.

In eval work

Treat a task image as a measured artifact, not a recipe. When I rebuilt this Dockerfile with every step CACHED, the resulting image ID still differed from the first build (82e0a1d2… vs 0375d1f7…), because the ID covers build metadata as well as layers. "We used the same Dockerfile" is therefore not evidence of the same environment. Build once, push to a registry, and write the image digest into every results file next to the model name and the score.

Run: the flags that define a sandbox

docker run [flags] IMAGE [command] creates a container and starts it. The image supplies defaults; flags override them: 

$ docker run --rm wordfreq-bench:hardened id
uid=1001(agent) gid=1001(agent) groups=1001(agent)
$ docker run --rm -u root -w /tmp -e SEED=42 wordfreq-bench:hardened bash -c 'id -un; pwd; echo $SEED'
root
/tmp
42

Note what the second command shows: USER agent in the image is a default. Anyone who controls the docker run line — the harness — can be root. The agent, who only controls what runs inside, cannot. The working set of flags (semantics from the CLI reference[Docker: run]):

--rmRemove the container, and its anonymous volumes, when it exits—
-it-i keep stdin open, -t allocate a pseudo-TTY: an interactive shellTTY (27)
-d, --name NRun in the background; give it a name you can refer to—
-e K=V, -u, -wEnvironment variable, user, working directoryenv (11), uid (7)
--mount type=bind,src=…,dst=…,readonlyGraft a host directory into the container. Without readonly: "Bind mounts have write access to files on the host by default."[Docker: storage]bind mount (14)

The last run is root, inside the container, failing to modify a read-only mount — but happily listing it. Read-only stops tampering, not reading; an answer key needs absence (page 14, page 26).

When docker run itself fails: 125, 126, 127

The exit status of docker run is normally the contained command's. Three values are Docker's own: 125 "the error is with Docker daemon itself", 126 "the specified contained command can't be invoked", 127 "the contained command can't be found."[Docker: run] 

$ docker run --rm --nosuchflag wordfreq-bench:hardened true; echo "exit=$?"
unknown flag: --nosuchflag
…
exit=125
$ docker run --rm wordfreq-bench:hardened /app/wordfreq.py; echo "exit=$?"
docker: Error response from daemon: … exec: "/app/wordfreq.py": permission denied: unknown
exit=126
$ docker run --rm wordfreq-bench:hardened nosuchcmd; echo "exit=$?"
docker: Error response from daemon: … exec: "nosuchcmd": executable file not found in $PATH: unknown
exit=127

126 and 127 mean the same as they do in bash (Appendix B), so the number alone does not say which layer produced it. The text does: Error response from daemon means the container never started. That is an observation about the run, not about the model: record it as an infrastructure failure, keep it in scheduled, leave it out of completed — and never quietly out of the report.

Drive and inspect: one rollout, start to post-mortem

Here is the loop a harness performs, by hand. Start an idle sandbox, then exec commands into it — docker exec "runs a new command in a running container",[Docker: run] as the container's user unless you say otherwise: 

$ docker run -d --name lt-22-rollout --init wordfreq-bench:hardened
d3ee5d716b8f6f03f411e01145107222bcca37f9b17e12cea72e6d0443756e65
$ docker exec lt-22-rollout ps -ef
UID        PID  PPID  C STIME TTY          TIME CMD
agent        1     0  0 10:53 ?        00:00:00 /sbin/docker-init -- sleep infinity
agent        7     1  0 10:53 ?        00:00:00 sleep infinity
agent        8     0  0 10:53 ?        00:00:00 ps -ef
$ docker exec lt-22-rollout python3 wordfreq.py data/sample.txt
3 The
3 the
2 on

That is the bug: "The" and "the" counted separately. Now the "agent" works. I copied in a small script that applies the fix (docker cp moves files across the boundary in either direction), ran it, and left some debris, as agents do: 

$ docker cp fix.py lt-22-rollout:/tmp/fix.py
$ docker exec lt-22-rollout python3 /tmp/fix.py
$ docker exec lt-22-rollout python3 wordfreq.py data/sample.txt
7 the
2 cat
2 end
$ docker exec lt-22-rollout bash -c 'echo notes > /app/NOTES.txt; rm /app/README.md; echo hi > /home/agent/.bash_history'

Now the post-mortem. docker diff compares the container's writable layer with its image: A added, C changed, D deleted. 

$ docker diff lt-22-rollout
C /app
A /app/NOTES.txt
A /app/__pycache__
A /app/__pycache__/wordfreq.cpython-312.pyc
C /app/tests
A /app/tests/__pycache__
A /app/tests/__pycache__/test_basic.cpython-312.pyc
C /app/wordfreq.py
D /app/README.md
C /home
C /home/agent
A /home/agent/.bash_history
C /tmp
A /tmp/fix.py
C /usr
C /usr/sbin
A /usr/sbin/docker-init

That is "what did the agent change?" answered exhaustively, from outside, without trusting anything inside the box. (The last three lines are not the agent: --init places the docker-init binary there. Know your runtime's own footprint so you can subtract it.) It sees only the writable layer — files written to volumes, bind mounts or tmpfs do not appear. Three more reads complete the picture: 

$ docker logs lt-22-rollout
$ docker inspect --format '{{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}} user={{.Config.User}} image={{.Image}}' lt-22-rollout
running exit=0 oom=false user=agent image=sha256:82e0a1d29453139ac5067345ff29b98d2e34d7b07603d9a692546a4973a0dec3
$ docker stats --no-stream --format 'table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.PIDs}}' lt-22-rollout
NAME            CPU %     MEM USAGE / LIMIT     PIDS
lt-22-rollout   0.01%     1.309MiB / 7.654GiB   2
Pitfall — docker logs is empty and that is correct

docker logs "shows the command's STDOUT and STDERR"[Docker: logs] — the container's main command, here sleep infinity, which prints nothing. Everything the agent did arrived via exec, and exec output goes back to whoever called exec, not to the container log. In an exec-driven harness the transcript is the only record of the agent's output; if the harness didn't save both streams (page 4), they are gone. docker logs is useful when the container's command is the work:

$ docker run --name lt-22-once wordfreq-bench:hardened python3 wordfreq.py nosuchfile
Traceback (most recent call last):
…
FileNotFoundError: [Errno 2] No such file or directory: 'nosuchfile'
$ docker ps -a --filter name=lt-22 --format 'table {{.Names}}\t{{.Status}}\t{{.Command}}'
NAMES           STATUS                              COMMAND
lt-22-once      Exited (1) Less than a second ago   "python3 wordfreq.py…"
lt-22-rollout   Up 25 seconds                       "sleep infinity"
$ docker logs lt-22-once 2>/dev/null | wc -l      # stdout only
0
$ docker logs lt-22-once 2>&1 >/dev/null | tail -1  # stderr only
FileNotFoundError: [Errno 2] No such file or directory: 'nosuchfile'

Note docker ps -a: without -a you see only running containers, and the exited one — the one you need to debug — is invisible.

In eval work

The minimal post-mortem of any rollout is four reads from outside the box: exit code and OOMKilled (docker inspect), main-process output (docker logs), filesystem footprint (docker diff), and the image ID it ran from. Collect them before removing the container — a harness that runs everything with --rm destroys the evidence that would tell a model failure from an infrastructure failure.

Reset: throw the container away

There is no "undo" command, and none is needed. Containers should be "as ephemeral as possible… stopped and destroyed, then rebuilt and replaced with an absolute minimum set up and configuration."[Docker: Dockerfile] Removing a container deletes its writable layer; a new container from the same image starts from the image's exact bytes: 

$ docker rm -f lt-22-rollout lt-22-once
$ docker run -d --name lt-22-rollout --init wordfreq-bench:hardened
$ docker exec lt-22-rollout python3 wordfreq.py data/sample.txt
3 The
3 the
2 on

The bug is back. That is a reset, and it cost under a second. The exception is anything stored outside the writable layer. A named volume survives both docker rm and --rm (only anonymous volumes die with a --rm container[Docker: storage]): 

$ docker run --rm --mount type=volume,src=lt-22-cache,dst=/cache -u root wordfreq-bench:hardened \
    bash -c 'echo rollout-1-was-here > /cache/note'
$ docker run --rm --mount type=volume,src=lt-22-cache,dst=/cache wordfreq-bench:hardened cat /cache/note
rollout-1-was-here
In eval work

A fresh container per rollout is what makes samples independent. A shared pip cache volume, a reused container, a bind-mounted work directory: each lets rollout 1 influence rollout 2, and then one early accident (a corrupted cache, a half-applied fix) produces a streak of failures or passes. Error bars assume independent samples (Understanding LLM Evals, page 16); correlated rollouts make them too narrow. Audit for it with docker inspect --format '{{json .Mounts}}' on a live sandbox.

Two things an image never forgets

Deleted files. Layers are append-only differences. Docker's docs, about a directory removed by a later instruction: it "will still be available in the previous layer."[Kernel: overlayfs] The deliberately sloppy build of the running example does exactly this (Dockerfile.sloppy: COPY solution /tmp/solution then RUN rm -rf /tmp/solution). In a container the directory is gone. In the image it is not: 

$ docker run --rm wordfreq-bench:sloppy ls /tmp/solution
ls: cannot access '/tmp/solution': No such file or directory
$ docker save wordfreq-bench:sloppy -o img.tar && tar -xf img.tar
$ for l in blobs/sha256/*; do tar -tf "$l" 2>/dev/null | grep solution && echo "   ^ in ${l:0:28}…"; done
tmp/.wh.solution
   ^ in blobs/sha256/84eb90d2670f6cf…
tmp/solution/
tmp/solution/wordfreq.patch.py
   ^ in blobs/sha256/88440700ca8c404…

One layer holds the file; the next holds only a .wh. "whiteout" marker saying "hide it". Anyone who can pull the image can read the oracle solution — this is solution leakage through the image, and it is why the hardened Dockerfile never copies the solution at all, and why rm -rf /var/lib/apt/lists/* sits in the same RUN as the install: deletion only saves space within one layer.

Build arguments and ENV. "Build arguments and environment variables are inappropriate for passing secrets to your build, because they persist in the final image."[Docker: Dockerfile] Proof, with a four-line Dockerfile (ARG HF_TOKEN, ENV JUDGE_API_KEY=sk-judge-999, a RUN that uses the token): 

$ docker build -q --build-arg HF_TOKEN=hf_secret_777 -t lt-22-arg:1 .
$ docker history --no-trunc --format '{{.CreatedBy}}' lt-22-arg:1 | head -3
RUN |1 HF_TOKEN=hf_secret_777 /bin/sh -c echo "downloading with $HF_TOKEN" > /dev/null # buildkit
ENV JUDGE_API_KEY=sk-judge-999
ARG HF_TOKEN=hf_secret_777
$ docker run --rm lt-22-arg:1 env | grep -E 'TOKEN|KEY'
JUDGE_API_KEY=sk-judge-999

The ARG is not in the container's environment, but it is in the history forever; the ENV is handed to the agent directly. The documented fix is RUN --mount=type=secret; the better fix for an eval is that the secret never goes near the task image (page 11).

Compose: tasks with more than one box

Some tasks need a database or an API beside the agent's box. Docker Compose describes several containers and their networks in one YAML file; harnesses such as Inspect take a compose file as the sandbox definition (page 25). A two-service variant of the running example: 

# wordfreq-bench, two-service variant: the agent's box plus a cache it must talk to.
name: lt-22-task
services:
  default:                        # the service the harness execs into
    image: wordfreq-bench:hardened
    init: true
    user: agent
    mem_limit: 512m
    cpus: 1.0
    pids_limit: 128
    networks: [tasknet]
    depends_on:
      db:
        condition: service_healthy
  db:
    image: redis:7-alpine
    networks: [tasknet]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 2s
      timeout: 2s
      retries: 10
networks:
  tasknet:
    internal: true                # services reach each other; nothing reaches out

Every docker run flag has a compose key (init, user, mem_limit, pids_limit; the full hardening set is on page 23). Two keys deserve comment. depends_on in its short form gives start order only; the long form with condition: service_healthy waits for the healthcheck [Compose] — otherwise the agent's first command races the database's startup and you get a flaky task. And internal: true "lets you create an externally isolated network."[Compose] 

$ docker compose up -d
 …
 Container lt-22-task-db-1  Healthy
 Container lt-22-task-default-1  Started
$ docker compose exec default getent hosts db
172.18.0.2      db
$ docker compose exec default python3 -c "import socket; s=socket.create_connection(('db',6379),3); s.sendall(b'PING\r\n'); print(s.recv(16))"
b'+PONG\r\n'
$ docker compose exec -T default python3 -c 'import socket; socket.create_connection(("1.1.1.1", 443), 3)'
…
OSError: [Errno 101] Network is unreachable
$ docker compose down -v

The service name db resolves because Compose registers service names with Docker's internal DNS server[Compose] (page 18); the outside world is unreachable because an internal network has no route out (page 19; for the concepts behind container networking see Networking for LLM Evals, lesson 14). down -v removes containers, network and volumes — the compose-level reset. Forget -v and the database's volume carries state into the next rollout.

Caveat — Docker Desktop is a VM

On your Mac the "host" in every Docker sentence is a hidden Linux VM: "for Docker Desktop, the daemon runs inside a Linux VM, not directly on the native host."[Docker: storage] So the 7.654GiB limit in the docker stats output above is that VM's memory, not the Mac's; bind mounts cross a macOS-to-VM boundary; and on Apple Silicon uname -m in these containers prints aarch64, not the x86_64 of most benchmark hosts. Develop on the Mac; take measurements on the Linux hosts you will report (Appendix E).

Check your understanding

A teammate's harness launches every sandbox with docker run --rm and reports 412 of 500 rollouts correct. Of the 88 failures, 31 have an empty transcript and exit code 137 or 125. They propose reporting 412/469, "since those 31 never really ran". What would you ask in review?

Reveal the reasoning

Observed: two exit codes and empty transcripts. Supposed: that all 31 are infrastructure faults. The codes do not mean the same thing. 125 with Error response from daemon means the container never started — a fact about the run. 137 means SIGKILL, which could be an OOM kill, a harness timeout, or docker stop; an agent that allocates 10 GB is arguably a model failure under a stated budget. The discriminating evidence is State.OOMKilled, the harness's timeout log, and timing — and --rm has already deleted the first of these, so ask for the harness to stop using --rm (collect inspect/diff, then remove) and re-run the 31. For the report: never drop them silently. Give correct / scheduled (412/500), completed / scheduled, and correct / completed as three separate numbers, with the rule for what counts as "completed" fixed before looking at results — a denominator chosen afterwards can be steered to any score.

  2. Predict, then verify. Before running it: what will docker logs wf print, given everything you just did in wf? Then: remove wf, start it again, and predict whether /app/NOTES.txt exists.
    Solution

    Nothing: the log holds the main command's streams (sleep infinity), not exec'd commands'. After docker rm -f wf and a new docker run, the file is gone (ls: cannot access '/app/NOTES.txt': No such file or directory) — the writable layer died with the container.

  3. Predict, then verify. Run the two --mount type=volume,src=lt-22-cache… commands from the reset section. Both containers used --rm. Does the note survive? Clean up with docker volume rm lt-22-cache.
    Solution 
    $ docker run --rm --mount type=volume,src=lt-22-cache,dst=/cache wordfreq-bench:hardened cat /cache/note
rollout-1-was-here
$ docker volume ls --filter name=lt-22
DRIVER    VOLUME NAME
local     lt-22-cache

    It survives: --rm removes anonymous volumes only. Named volumes are cross-rollout state until someone runs docker volume rm.

  4. Eval task: whose failure? A rollout "failed with no output". Recreate it, then decide from outside the box whether to score it as a model failure: docker run --name pm --memory 64m --memory-swap 64m wordfreq-bench:hardened python3 -c 'x = bytearray(200*1024*1024)'
    Solution 
    $ docker ps -a --filter name=pm --format '{{.Names}}\t{{.Status}}'
pm	Exited (137) Less than a second ago
$ docker logs pm
$ docker inspect --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}} mem={{.HostConfig.Memory}}' pm
exit=137 oom=true mem=67108864
$ docker rm pm

    137 = killed by SIGKILL (page 10); empty logs because a SIGKILLed process prints nothing; oom=true with a 64 MiB limit says the kernel's OOM killer did it (page 12). Whether that is "the model's fault" depends on whether 64 MiB is the benchmark's stated budget — but it must be counted as an OOM, not as a wrong answer.

  5. Eval task: audit an image you were handed. Without starting a container, find out whether wordfreq-bench:sloppy ever contained a solution directory. (Hint: docker history.)
    Solution 
    $ docker history --format '{{.CreatedBy}}\t{{.Size}}' wordfreq-bench:sloppy | head -6
CMD ["sleep" "infinity"]	0B
WORKDIR /app	4.1kB
RUN /bin/sh -c rm -rf /tmp/solution # buildk…	8.19kB

    A COPY followed by an rm of the same path is the signature. The history also shows the grader being copied into the image — the second finding.
