Module 1 · The Shell

Shell scripts under thirty lines

Eval environments are held together by small bash scripts: entrypoints, setup scripts, and the run-tests.sh whose exit status is the score. This page teaches you to read them critically and write them safely — and to recognise the point where you should stop and open Python instead.

A script is a file of commands plus two facts

A script is a text file containing the commands you would otherwise type. Two facts turn that file into something you can run like a program: its first line, and one permission bit. Create a two-line script as the learner user in your container lab and try to run it: 

$ mkdir -p ~/scripts && cd ~/scripts
$ printf '%s\n' '#!/usr/bin/env bash' 'echo "hello from $0, running as $(whoami)"' > hello.sh
$ ls -l hello.sh
-rw-r--r-- 1 learner learner 63 Sep 21 16:31 hello.sh
$ ./hello.sh
bash: ./hello.sh: Permission denied
$ echo $?
126
$ bash hello.sh
hello from hello.sh, running as learner
$ chmod +x hello.sh
$ ./hello.sh
hello from ./hello.sh, running as learner

Exit status 126 is the shell's code for "found, but not executable"; 127 is "not found".[Bash Manual] (Both were introduced on page 2.) The file had no x in its mode string, so the kernel refused to execute it. bash hello.sh worked anyway because there the program being executed is bash, and the script is merely a file it reads. chmod +x adds the execute bit; page 8 explains the bits properly.

The first line, #!/usr/bin/env bash, is the shebang. When the kernel is asked to execute a file that starts with the two bytes #!, it runs the named interpreter instead and hands it the script's path. /usr/bin/env bash means "whichever bash is first on PATH". The shebang is a promise about which language the file is written in, and it matters more than it looks:

Pitfall — sh is not bash

On Ubuntu and Debian, /bin/sh is a smaller, faster shell called dash. A script that says #!/bin/sh but uses bash features fails there:

$ ls -l /bin/sh
lrwxrwxrwx 1 root root 4 Mar 31  2024 /bin/sh -> dash
$ sh -c 'set -o pipefail; echo ok'; echo "exit status: $?"
sh: 1: set: Illegal option -o pipefail
exit status: 2

pipefail (below) was added to the POSIX standard in its 2024 edition, but dash on Ubuntu 24.04 still rejects it, as do arrays and [[ ]].[POSIX] The opposite failure happens on Alpine images, which ship no bash at all: running this course's grader script there prints env: can't execute 'bash': No such file or directory and exits 127. If a script uses bash features, say bash in the shebang, and make sure the image has it.

Variables and the one quoting rule

Assign with name=value (no spaces around =), read with $name. The trap is what bash does after substituting the value. An unquoted expansion is split into separate words at spaces, tabs and newlines, and each word is then treated as a glob pattern; inside double quotes neither happens.[Bash Manual] A filename with a space in it shows the damage: 

$ mkdir q && cd q
$ touch "run 1.log" run.log 1.log
$ f="run 1.log"
$ rm $f
rm: cannot remove 'run': No such file or directory
$ ls -1
run 1.log
run.log

rm received two arguments, run and 1.log. One did not exist; the other did, and it is gone: the wrong file was deleted, and the one you meant survived. With quoting, rm "$f" passes one argument and removes run 1.log. The same applies to a script's own arguments. $1, $2… are the positional parameters, $# their count, and "$@" means "all of them, each as its own word, exactly as received": 

#!/usr/bin/env bash
echo "got $# arguments"
printf '  unquoted: <%s>\n' $@
printf '  quoted:   <%s>\n' "$@"
$ ./args.sh "run 1.log" other.log
got 2 arguments
  unquoted: <run>
  unquoted: <1.log>
  unquoted: <other.log>
  quoted:   <run 1.log>
  quoted:   <other.log>
Key idea Put double quotes around every "$var", every "$(command)", and always write "$@". You do not need to remember when it is safe to omit them; it is never wrong to include them. Single quotes are for text that must not be expanded at all.

$(…) is command substitution from page 4: run the command, substitute its output. n=$(wc -l < results.jsonl) is how a script gets a value out of a program.

Exit codes are the control flow

In most languages if tests a boolean. In the shell, if runs a command and branches on its exit status: 0 is true, anything else is false. 

$ if grep -q learner /etc/passwd; then echo "found"; else echo "missing"; fi
found
$ if grep -q nosuchuser /etc/passwd; then echo "found"; else echo "missing"; fi
missing
$ type [ [[
[ is a shell builtin
[[ is a shell keyword

That is why the square brackets look odd: [ is a command (a builtin) whose job is to evaluate a test and exit 0 or 1, and ] is just its last argument. [[ … ]] is bash's improved version, built into the grammar, so it does not word-split its contents. The tests you will meet in eval scripts are few: -f path (is a regular file), -d path (is a directory), -z "$s" (string is empty), -n "$s" (non-empty), == for strings, and -eq -ne -lt -gt for integers. The difference between the two bracket forms is again quoting: 

$ w="two words"
$ [ -n $w ] && echo non-empty
bash: [: two: binary operator expected
$ [[ -n $w ]] && echo non-empty
non-empty

In a bash script use [[ ]]; in a #!/bin/sh script you only have [ ], so quote everything. a && b runs b only if a succeeded, a || b only if it failed — hence the idiom cd "$dir" || exit 1.

Loops and functions

Two loops cover nearly everything: for over a glob, and while read -r over the lines of a file (-r stops read from interpreting backslashes). A function is a named group of commands with its own $1, $2; its "return value" is the exit status of its last command, and its output is captured with $(…) like any program's. 

$ printf 'task-a 0\ntask-b 137\ntask-c 1\n' > codes.txt
$ while read -r task code; do
>   if [[ $code -ne 0 ]]; then echo "$task failed with $code"; fi
> done < codes.txt
task-b failed with 137
task-c failed with 1
$ fail_count() { grep -cv ' 0$' "$1"; }
$ echo "failures: $(fail_count codes.txt)"
failures: 2

Loop over ./*.log, never over $(ls *.log): the glob hands you each filename intact, while the output of ls gets word-split.

Strict mode, and how far to trust it

By default bash treats a script like a person typing: when a command fails, it shrugs and runs the next line. For automation that default is dangerous. 

#!/usr/bin/env bash
cd /nonexistent/build
echo "cleaning $(pwd)"
grep -c PASS "$RESULTS" | tee count.txt
echo "done"
$ ./nostrict.sh; echo "exit status: $?"
./nostrict.sh: line 2: cd: /nonexistent/build: No such file or directory
cleaning /home/learner/scripts
grep: : No such file or directory
done
exit status: 0

Three things went wrong and the script reported success. The cd failed, so the "cleaning" step ran in the wrong directory (imagine that line were rm -rf ./*). $RESULTS was never set, so it silently became an empty string. grep failed, but it was on the left of a pipe, and a pipeline's status is its last command's (page 4). And a script's own exit status is simply that of the last command it ran[Bash Manual] — here, a successful echo. Strict mode is one line that changes all three defaults: 

set -euo pipefail
OptionEffectObserved
-e (errexit)Exit immediately when a command fails. The script above stops at the cd with exit status 1.
-u (nounset)Expanding an unset variable is an error, not an empty string. RESULTS: unbound variable; the script exits (bash 5.2 used status 127).
-o pipefailA pipeline fails if any command in it fails; the status is that of the rightmost failing command.[Bash Manual] false | true gives 0 without it, 1 with it.

Strict mode is necessary, and it is not sufficient. set -e has documented exceptions: the shell does not exit when the failing command is the condition of an if, while or until; is anywhere in an &&/|| list except after the last operator; is in a pipeline but not last (without pipefail); or is negated with !. The one that surprises people: when a function is called from one of those contexts, -e is switched off for everything inside the function.[Bash Manual] Every line of the following script runs, under full strict mode: 

#!/usr/bin/env bash
set -euo pipefail

check() {
  false
  echo "check: still running after false"
}

if check; then echo "1. check 'succeeded'"; fi

load() {
  local v=$(false)
  echo "2. load: still running after a failed \$(...)"
}
load

false || echo "3. left side of || may fail"
echo "4. reached the end"
$ ./e-exceptions.sh; echo "exit status: $?"
check: still running after false
1. check 'succeeded'
2. load: still running after a failed $(...)
3. left side of || may fail
4. reached the end
exit status: 0

Case 1: check was called as an if condition, so the false inside it was ignored, the function's status became that of its final echo, and a check that failed reported success. Case 2: local v=$(false) is one command, local, which succeeds at declaring a variable; the substitution's failure is discarded.[ShellCheck] (Write local v and v=$(…) on separate lines.) Case 3 is the exception working for you, and the real grader below relies on it.

In eval work — discuss

When you review a task's test script, "it has set -e" is not the end of the review. Ask what the script's exit status is on each path: tests fail, tests crash on import, tests time out, a setup step fails. A verification function called as if verify_output; then runs with errexit off; if its last line is a log message, it always "passes". The exit status is the measurement, so trace it as carefully as you would trace a metric computation in Python.

Cleaning up: mktemp and trap … EXIT

Scripts need scratch space. mktemp -d creates a fresh directory with an unpredictable name under /tmp, readable only by you (mode 700), and prints its path. The coreutils manual explains why not to invent a name like /tmp/grade.$$: a predictable name lets another user pre-create a symbolic link there, so your script writes through it into a file of their choosing.[Coreutils] In a sandbox the "other user" may be the agent. trap 'commands' EXIT registers commands to run when the script exits, for any reason, including a set -e abort: 

#!/usr/bin/env bash
set -euo pipefail
work=$(mktemp -d)
trap 'rm -rf "$work"; echo "cleaned up $work"' EXIT
echo "working in $work"
ls -ld "$work"
false
echo "never printed"
$ ./cleanup.sh; echo "exit status: $?"
working in /tmp/tmp.QKEsTntb3f
drwx------ 2 learner learner 4096 Sep 21 16:31 /tmp/tmp.QKEsTntb3f
cleaned up /tmp/tmp.QKEsTntb3f
exit status: 1

ShellCheck: the linter that knows all of this

ShellCheck is a static analysis tool for sh/bash scripts; it reads the shebang to decide which dialect to check.[ShellCheck] Install it in the lab as root with apt-get install -y shellcheck (on your Mac: brew install shellcheck). Here is a script of the kind that accumulates in eval repos, and what the tool says about it: 

#!/bin/bash
# Copy every rollout log into one directory and count failures.
dir=$1
cd $dir
for f in $(ls *.log); do
  cp $f /tmp/collected/
done
local_count=$(grep -l FAIL *.log | wc -l)
echo "failures: $local_count"
$ shellcheck collect.sh; echo "exit status: $?"

Every finding is a mechanism from this page, and each code has a wiki page explaining it. The warnings are not pedantry. Run the script on a directory whose name contains a space:

ShellCheck exits 1 when it has findings, so it drops straight into CI.[ShellCheck]

Worked example: the grader script, line by line

The course's running example, wordfreq-bench, asks an agent to fix a bug in /app/wordfreq.py. After the agent finishes, the harness runs this script, the benchmark's verifier. It is 22 lines and passes ShellCheck. Read it the way you would read any task's run-tests.sh: asking, at each line, what is the exit status now? 

 1  #!/usr/bin/env bash
 2  # Grade one rollout. Usage: run-tests.sh APP_DIR RESULT_FILE
 3  # Exit status = the hidden tests' exit status (0 pass, non-zero fail, 124 timeout).
 4  set -euo pipefail
 5
 6  app_dir=${1:?usage: run-tests.sh APP_DIR RESULT_FILE}
 7  result_file=${2:?usage: run-tests.sh APP_DIR RESULT_FILE}
 8  grader_dir=$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)
 9  work=$(mktemp -d)
10  trap 'rm -rf "$work"' EXIT
11
12  status=0
13  APP_DIR="$app_dir" PYTHONPATH="$app_dir" PYTHONDONTWRITEBYTECODE=1 \
14    timeout -k 5 60 python3 -m unittest discover -s "$grader_dir" -p 'test_hidden.py' \
15    >"$work/stdout" 2>"$work/stderr" || status=$?
16
17  passed=false
18  if [[ $status -eq 0 ]]; then passed=true; fi
19  tail_text=$(tail -n 3 "$work/stderr" | tr '\n' ' ' | tr -d '"\134')
20  printf '{"exit_code": %d, "passed": %s, "stderr_tail": "%s"}\n' \
21    "$status" "$passed" "$tail_text" >>"$result_file"
22  exit "$status"
  • Lines 1–4. A bash shebang, a comment that states the exit-status contract (the most useful comment a test script can have), and strict mode.
  • Lines 6–7. ${1:?message} expands to $1, or, if it is missing, prints the message and exits. Run with no arguments, the script prints 1: usage: run-tests.sh APP_DIR RESULT_FILE and exits 1.
  • Line 8. The directory the script itself lives in, as an absolute path. The hidden tests sit beside it, so the grader works wherever it is mounted.
  • Lines 9–10. Private scratch space, removed on every exit path.
  • Lines 13–15 are the measurement. NAME=value command sets environment variables for that one command. timeout -k 5 60 sends SIGTERM after 60 seconds and SIGKILL 5 seconds after that if the process is still there; when the time limit is hit, GNU timeout exits 124.[Coreutils] Both streams go to separate files (page 4), so nothing is lost and nothing is interleaved. Then || status=$?: failing tests are an expected outcome, not a script error, so the command sits on the left of || — the documented set -e exception — and its status is captured instead of killing the script.
  • Lines 17–21. One JSONL line is appended to the result file: the raw exit code, a boolean, and the last three lines of stderr (unittest writes its report to stderr). Line 19 flattens newlines and deletes double quotes and backslashes (\134 is the backslash in octal) so the hand-built JSON stays valid.
  • Line 22. The script exits with the tests' status. This line is the score.
$ cd ~/wordfreq-bench
$ grader/run-tests.sh app /tmp/result.jsonl; echo "exit status: $?"    # the unfixed repo
exit status: 1
$ grader/run-tests.sh /tmp/fixed /tmp/result.jsonl; echo "exit status: $?"    # oracle fix applied
exit status: 0
$ time grader/run-tests.sh /tmp/hang /tmp/result.jsonl; echo "exit status: $?"    # wordfreq.py sleeps forever

real	1m0.040s
…
exit status: 124
$ cat /tmp/result.jsonl
{"exit_code": 1, "passed": false, "stderr_tail": "Ran 2 tests in 0.001s  FAILED (failures=2) "}
{"exit_code": 0, "passed": true, "stderr_tail": "Ran 2 tests in 0.001s  OK "}
{"exit_code": 124, "passed": false, "stderr_tail": ""}
$ ls -d /tmp/tmp.*
ls: cannot access '/tmp/tmp.*': No such file or directory

Three outcomes, three distinct records, no scratch directories left behind. Note what the script does not do: it does not collapse 124 into 1.

In eval work — failure accounting

The third record says passed: false, but it is not the same observation as the first. Exit 1 means the tests ran and the code was wrong. Exit 124 means the grader gave up after 60 seconds: perhaps the agent's code loops forever (a model failure), perhaps 64 graders were sharing four cores (an infrastructure failure). The record is evidence of a timeout; the cause is a hypothesis until you re-grade that rollout on an idle machine and see whether it still takes 60 seconds. Keep the raw code in the log so the analysis can report passed / scheduled, passed / completed and completed / scheduled separately (page 10 decodes the codes; page 12 covers the starved box). And if the task image is Alpine, BusyBox's timeout returned 143 on expiry when tested, not 124[Coreutils] — a harness that counts timeouts with == 124 will find none.

The variant that passes everything

Now the script someone writes in a hurry. It is shorter and its output is friendlier: 

#!/usr/bin/env bash
# Grade one rollout. Usage: run-tests-broken.sh APP_DIR
app_dir=$1
grader_dir=$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)

echo "running hidden tests..."
APP_DIR="$app_dir" PYTHONPATH="$app_dir" python3 -m unittest discover -s "$grader_dir" -p 'test_hidden.py' 2>&1 | tail -n 3
echo "tests finished"
$ grader/run-tests-broken.sh app; echo "exit status: $?"
running hidden tests...
Ran 2 tests in 0.001s

FAILED (failures=2)
tests finished
exit status: 0
$ grader/run-tests-broken.sh /nonexistent; echo "exit status: $?"
running hidden tests...
Ran 1 test in 0.000s

FAILED (errors=1)
tests finished
exit status: 0
$ shellcheck grader/run-tests-broken.sh; echo "exit status: $?"
exit status: 0

The unfixed repo passes. A directory that does not exist passes. There are two independent bugs, and either alone is enough: the test command's status is thrown away by the pipe into tail (no pipefail), and the script's last command is an echo, which always succeeds. A human watching the terminal sees FAILED; a harness reads only the exit status and records a pass. Note the last command too: ShellCheck is silent. It checks shell hazards, not whether your script means what you intended.

In eval work — navigate

This bug inflates every model's score equally, so no leaderboard comparison will reveal it. The discriminating test is cheap: run the grader against the unsolved task and demand a failure, then against the oracle solution and demand a pass. Terminal-Bench's task review requires exactly this pair (the oracle must pass; a no-op agent must fail),[Terminal-Bench] and in its current harness a task's tests/test.sh reports by writing a number to /logs/verifier/reward.txt.[Terminal-Bench] Whatever the channel — exit status or reward file — a grader should key off something the script cannot produce by accident, and you should read every task's test script for the path where it does.

The thirty-line rule

Line 19 of the grader is where bash starts to strain: it builds JSON by deleting the characters that would break it. That works for three lines of unittest output and would not survive arbitrary text. The course's rule of thumb: when a script passes about thirty lines, or needs real data structures, JSON, arithmetic beyond counting, or error handling with more than one path, write it in Python. The same grader: 

#!/usr/bin/env python3
"""The same job as run-tests.sh, in Python. Usage: grade.py APP_DIR"""
import json
import os
import subprocess
import sys

app_dir = sys.argv[1]
grader_dir = os.path.dirname(os.path.abspath(__file__))
env = {**os.environ, "APP_DIR": app_dir, "PYTHONPATH": app_dir, "PYTHONDONTWRITEBYTECODE": "1"}
try:
    proc = subprocess.run(
        ["python3", "-m", "unittest", "discover", "-s", grader_dir, "-p", "test_hidden.py"],
        capture_output=True, text=True, timeout=60, check=False, env=env,
    )
    status, stderr = proc.returncode, proc.stderr
except subprocess.TimeoutExpired:
    status, stderr = 124, "timed out after 60 s"
print(json.dumps({"exit_code": status, "passed": status == 0,
                  "stderr_tail": " ".join(stderr.splitlines()[-3:])}))
sys.exit(status)
$ python3 grader/grade.py app; echo "exit status: $?"
{"exit_code": 1, "passed": false, "stderr_tail": "Ran 2 tests in 0.001s  FAILED (failures=2)"}
exit status: 1
$ python3 grader/grade.py /tmp/hang; echo "exit status: $?"
{"exit_code": 124, "passed": false, "stderr_tail": "timed out after 60 s"}
exit status: 124

Each argument maps to a mechanism you already know: capture_output=True collects stdout and stderr separately, timeout= replaces the timeout command, check=False says "a non-zero status is data, don't raise", and json.dumps does the escaping correctly. The most important detail is that the command is a list. Each element reaches the program as exactly one argument; no shell is involved, so there is no word splitting and no quoting to get wrong. Compare passing a string with shell=True: 

import subprocess
name = "x; echo INJECTED"
subprocess.run("echo grading " + name, shell=True, check=False)
subprocess.run(["echo", "grading", name], check=False)
$ python3 inject.py
grading x
INJECTED
grading x; echo INJECTED

With shell=True the string is parsed by a shell, so a value containing ; became a second command. In a harness, values like filenames, branch names and task IDs can be chosen by the agent. Use list arguments.

Caveat — what a script inherits

A script started by a harness runs in a non-interactive shell: it reads no ~/.bashrc, so aliases, PATH additions and virtualenv activation from your interactive session are absent (page 2; its remedies section shows why even bash -lc does not pick up a PATH line in Ubuntu's .bashrc). A setup script that "works on my machine" and exits 127 in the harness is usually this. Set what the script needs inside the script.

Check your understanding

You inherit a benchmark of 120 terminal tasks. Pass rates for every model you try sit between 88% and 94%, far above what the authors reported a year ago with weaker models, and the ranking between models is noisy. A teammate says the tasks are saturated and proposes retiring the benchmark. Each task has its own run-tests.sh, written by different contributors. What do you establish before agreeing?

Reveal the reasoning

Observed: high, compressed scores. Hypotheses: (a) the models really solve the tasks; (b) some graders cannot fail, which adds the same constant to every model and compresses differences exactly like this.

Discriminating test: run every task's grader against the untouched starting state, with no agent at all. Under (a) every task fails; under (b) some pass. Any task that passes with no work done has a broken verifier, typically a script whose last command is an echo, a test command piped into tee or tail without pipefail, or a check function called inside if. Then run the oracle solutions and confirm they pass, which catches graders that cannot succeed. Also grep -L 'pipefail' */run-tests.sh and read the shebangs, but treat that as a way to prioritise reading, not as proof.

Effect on the score: if 30 of 120 graders always pass, a model that solves 60% of the remaining 90 reports (30 + 54) / 120 = 70%, and one that solves 70% reports 77.5%: a ten-point gap shrinks to 7.5 and every number is inflated. Fix the graders, re-grade stored final states if you have them (a verifier change, not a rerun), and report which tasks changed. Only then is "saturated" a claim about the models.

broken  app -> 0
real    app -> 1
broken  /tmp/fixed -> 0
real    /tmp/fixed -> 0

    The first row: a grader that returns 0 for the unsolved task. On the solved repo the two graders agree, which is why this bug survives casual testing: people check that their solution passes and never check that the absence of a solution fails.
