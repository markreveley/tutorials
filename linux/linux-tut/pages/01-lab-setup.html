Lab setup: a Linux box you can break

Two places to type, from a Mac: a disposable Ubuntu container for almost every page, and a small real virtual machine for the few pages that need a kernel of their own. The loop you learn here — start a box, look around as root, wreck it, throw it away — is the same loop you will use to debug a benchmark's task image.

What Docker on a Mac really is

A container is a Linux process that the Linux kernel has been told to isolate (page 20 takes that sentence apart). macOS is not Linux and has no such kernel. So Docker on a Mac quietly runs a small Linux virtual machine, and your containers live inside it. Docker's documentation says so in passing: "For Docker Desktop, the daemon runs inside a Linux VM, not directly on the native host."[Docker: storage]

┌─ your Mac · macOS (Darwin kernel) ─────────────────────────────┐ │ │ │ Terminal ── docker CLI ──┐ │ │ │ talks to the daemon │ │ ┌─ Linux VM (one Linux kernel) ─────────────────────────────┐ │ │ │ ▼ │ │ │ │ Docker daemon ── creates ──▶ ┌─ container: lt-lab ────┐ │ │ │ │ │ Ubuntu 24.04 files │ │ │ │ │ │ bash, your commands │ │ │ │ │ └────────────────────────┘ │ │ │ │ ┌─ container: another ───┐ │ │ │ │ │ Alpine files … │ │ │ │ │ └────────────────────────┘ │ │ │ └───────────────────────────────────────────────────────────┘ │ └────────────────────────────────────────────────────────────────┘

You can see the seams from your Mac's terminal:

$ uname -sm
Darwin arm64
$ docker run --rm ubuntu:24.04 uname -srm
Linux 6.10.14-linuxkit aarch64
$ docker run --rm alpine:3.20 uname -srm
Linux 6.10.14-linuxkit aarch64

uname reports the kernel. The Mac's is Darwin. Inside a container it is Linux — and the same Linux, release and all, whether the container's files are Ubuntu or Alpine. An image supplies files (programs, libraries, configuration); it does not supply a kernel. Every container borrows the kernel of whatever machine runs it, which here is the hidden VM. (aarch64 is Linux's name for what Apple calls arm64; on an Intel Mac you will see x86_64. Your kernel version will differ from this page's.)

The VM also sets the ceiling on resources. On the 10-core, 16 GB Mac this page was written on:

# nproc
10
# free -h | head -2
               total        used        free      shared  buff/cache   available
Mem:           7.7Gi       738Mi       5.1Gi       924Ki       2.1Gi       6.9Gi

The container sees 7.7 GiB because that is what the VM was given in Docker Desktop's settings, not what the Mac has.

In eval work

A Mac is a fine place to learn and to debug one task; it is a different instrument from the Linux server a benchmark was validated on. The kernel is the VM's, memory is the VM's allotment shared by every container, and on Apple Silicon the images are arm64. SWE-bench's maintainers recommend an x86_64 machine with at least 120 GB of free storage, 16 GB of RAM and 8 cores, and call arm64 support experimental.[SWE-bench] If you report a score, report what it ran on — architecture, kernel, memory and CPU per sandbox, concurrency — and do not compare numbers across machines that differ in those (page 12).

The container lab

1. Get Docker

Install Docker Desktop for Mac and start it. (OrbStack and Colima are alternatives some people prefer; the course assumes only that the docker command works.) Check it from Terminal: 

$ docker version --format 'client {{.Client.Os}}/{{.Client.Arch}} · server {{.Server.Os}}/{{.Server.Arch}}'
client darwin/arm64 · server linux/arm64

Two halves, two operating systems: the docker command is a Mac program, and the daemon it talks to — the thing that actually creates containers — is a Linux program in the VM. If the server half is missing, Docker Desktop is not running.

2. Start the box

$ docker run -it --name lt-lab ubuntu:24.04 bash
root@3b1f0c2d9a7e:/#

Read the command left to right. docker run creates a new container from an image and starts it. ubuntu:24.04 is the image (downloaded the first time). bash is the program to run inside. --name lt-lab gives the container a name you can refer to later. -i keeps your keyboard connected to the program's input and -t allocates a pseudo-TTY, so that bash behaves as it would in a real terminal window.[Docker: run] The prompt changed: you are root, on a machine that calls itself by a random hex name, in the directory /, and the trailing # is the traditional sign for root. You did not type a password, because the default user within a container is root (uid 0).[Docker: run] Convenient in a lab; a problem in an eval, as page 7 explains.

3. Install the course's tools

The Ubuntu image is deliberately minimal. Software comes from Ubuntu's package manager, apt. Try the obvious thing first, because its failure is one you will meet in agent transcripts: 

# apt-get install -y curl
Reading package lists...
Building dependency tree...
Reading state information...
E: Unable to locate package curl
# echo $?
100

Nothing is wrong with the name. apt installs from a local index of what exists, the image ships with that index emptied to save space, and apt-get update is the command that "resynchronize[s] the package index files from their sources".[apt-get(8)] So the working sequence is always update, then install: 

# apt-get update
…
Reading package lists...
# apt-get install -y --no-install-recommends procps iproute2 curl ca-certificates \
    dnsutils jq less man-db file tree psmisc libcap2-bin util-linux findutils
…
0 upgraded, 50 newly installed, 0 to remove and 1 not upgraded.
Need to get 21.6 MB of archives.
After this operation, 78.7 MB of additional disk space will be used.
…

-y answers "yes" to the confirmation prompt, and --no-install-recommends skips packages that are merely suggested alongside the ones you asked for.[apt-get(8)] The package names rarely match the commands they provide, which is its own small source of "command not found":

4. Notice that the manual is missing

# man ls
This system has been minimized by removing packages and content that are
not required on a system that users do not log into.

To restore this content, including manpages, you can run the 'unminimize'
command. You will still need to ensure the 'man-db' package is installed.

Even with man-db installed you get this message. The image was built with a rule that tells the package system to discard every file under /usr/share/man, so the man pages of the packages you just installed were thrown away on arrival (the rule is in /etc/dpkg/dpkg.cfg.d/excludes; go and read it). Task images built on this base inherit the rule, so an agent that runs man inside one gets the same message. You have two choices: read manuals online at man7.org, which is what the course's citations link to, or restore them. The unminimize script asks for confirmation twice, so feed it answers: 

# yes | unminimize
…
Documentation has been restored successfully.
# man -w ls
/usr/share/man/man1/ls.1.gz

On a slow connection this takes several minutes: it reinstalls every package that lost files. yes prints y forever and the pipe delivers it to each prompt — a first sighting of the problem that a program waiting for a keypress is a program that hangs when no human is there (page 27).

5. Create an ordinary user

Root bypasses permission checks, so anything the course teaches about permissions has to be tried as somebody else. Make that somebody: 

# useradd -m -s /bin/bash learner
# id learner
uid=1001(learner) gid=1001(learner) groups=1001(learner)
# getent passwd 1000
ubuntu:x:1000:1000:Ubuntu:/home/ubuntu:/bin/bash

-m creates the home directory /home/learner; -s sets the login shell. The new user got uid 1001, not the 1000 that most tutorials promise, because the Ubuntu 24.04 image already contains a user called ubuntu at 1000. The kernel only ever sees the number; this matters as soon as files cross between containers and hosts (page 7). Become learner with su - learner and try to overstep: 

# su - learner
$ whoami
learner
$ touch /etc/oops
touch: cannot touch '/etc/oops': Permission denied
$ apt-get install -y cowsay
E: Could not open lock file /var/lib/dpkg/lock-frontend - open (13: Permission denied)
E: Unable to acquire the dpkg frontend lock (/var/lib/dpkg/lock-frontend), are you root?
$ which sudo; echo $?
1
$ exit

The prompt's last character changed to $; the course uses the same convention. There is no sudo in the image, so learner has no route back to root from inside. You do not need one: root is a docker exec away.

6. Leave, come back, throw away

Type exit (or Ctrl+D) at the root prompt. Bash was the container's main program, so when it ends the container stops — but it is not gone: 

$ docker ps -a --filter name=lt-lab
NAMES    IMAGE          STATUS
lt-lab   ubuntu:24.04   Exited (0) 1 second ago
$ docker run -it --name lt-lab ubuntu:24.04 bash
docker: Error response from daemon: Conflict. The container name "/lt-lab" is already in use by container "5c68345b7dc1…". You have to remove (or rename) that container to be able to reuse that name.
$ echo $?
125

docker run always means "make a new container", and the name is taken. (Status 125 is Docker's code for "the error is with Docker itself", as opposed to the program you asked it to run.[Docker: run]) To return to the box you already have, with your installed tools and files intact: 

$ docker start lt-lab                     # wake it up
lt-lab
$ docker exec -it lt-lab bash             # a root shell inside it
$ docker exec -it -u learner lt-lab bash  # or a shell as learner

docker exec runs an additional program inside a running container. Open two Terminal tabs and exec into the same container twice: one as root, one as learner. Most labs use exactly that arrangement. When you are done for the day, or have broken something beyond repair: 

$ time docker stop lt-lab
lt-lab
docker stop lt-lab  0.01s user 0.01s system 0% cpu 10.362 total
$ docker ps -a --filter name=lt-lab
NAMES    IMAGE          STATUS
lt-lab   ubuntu:24.04   Exited (137) Less than a second ago
$ docker rm lt-lab
lt-lab

Two details here are previews, not problems. docker stop took ten seconds and the container's exit status was 137, the "killed" number from page 0. Docker asks the main process to finish with a polite signal and, after a grace period — 10 seconds by default — kills it.[Docker: run] Bash, running as the first process in a container, never reacted to the polite signal. Page 10 explains why, and why a harness that tears down a thousand sandboxes this way, one after another, spends nearly three hours waiting.

Pitfall

docker rm deletes the container's filesystem: every tool you installed, every file you made. That is the feature. But it means a lab container is not a place to keep anything. Notes and scripts you care about live on your Mac; rebuilding the lab should be one command. The next step makes it so.

7. Make rebuilding one command

Put the setup in a Dockerfile — a recipe for building your own image on top of Ubuntu's (page 22 covers the format). In an empty folder on your Mac, save this as Dockerfile: 

FROM ubuntu:24.04
ARG DEBIAN_FRONTEND=noninteractive
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
      procps iproute2 curl ca-certificates dnsutils jq less man-db manpages \
      file tree psmisc libcap2-bin util-linux findutils \
 && yes | unminimize
RUN useradd -m -s /bin/bash learner
CMD ["bash"]

Then build it once, and start the lab from it whenever you like:

$ docker build -t lt-lab .
…
#6 369.8 Documentation has been restored successfully.
#6 DONE 370.0s
…
#8 naming to docker.io/library/lt-lab:latest done
$ docker rm -f lt-lab                      # discard the hand-built container, if any
$ docker run -dit --name lt-lab lt-lab
b3f56181d276…
$ docker ps --filter name=lt-lab
NAMES    IMAGE    STATUS
lt-lab   lt-lab   Up Less than a second
$ docker exec -it -u learner lt-lab bash

The build took six minutes on the slow connection this page was written on, nearly all of it downloads, and produced a 387 MB image; it is paid once. -d starts the container in the background, so it keeps running with no terminal attached and you enter and leave it with docker exec as often as you like. ARG DEBIAN_FRONTEND=noninteractive tells package installation never to stop and ask a question during the build (page 15).

From now on, "reset the lab" is docker rm -f lt-lab followed by that docker run. Break things freely: delete /usr, fill the disk, chmod everything to nothing. The worst outcome is thirty seconds of rebuilding, and the Mac outside is untouched.

In eval work

This is the loop for debugging a benchmark's task image: start a shell in the same image the agent gets, as the same user, and look. With the course's running example:

$ docker run --rm -it wordfreq-bench:hardened bash
$ id
uid=1001(agent) gid=1001(agent) groups=1001(agent)
$ pwd; ls
/app
README.md  data  tests  wordfreq.py

When a transcript shows a task failing at command not found or Permission denied, thirty seconds in that shell tells you whether the agent erred or the image is missing something the task needs. That is the navigate ability from page 0: reproduce from inside the environment and bring what you observed, not what you suppose. --rm removes the container when you exit,[Docker: run] so your poking cannot leak into a later run.

The VM lab

A container borrows a kernel and usually runs one program. Some pages need the whole machine: a real systemd as process 1 managing services and logs, firewall rules you are free to get wrong, and a host's-eye view of containers. Docker Desktop's hidden VM is not that machine: it is managed by Docker Desktop, not by you. Get an Ubuntu 24.04 VM of your own, one of two ways:

  • A small cloud server. Any provider's cheapest Ubuntu 24.04 instance is enough (1 CPU, 1–2 GB of memory). This is closest to where evals really run, and it has a real network position, which pages 16–19 use. Delete it when you are not using it.
  • A local VM on the Mac. Lima, Multipass and UTM each run Linux VMs on macOS; follow the tool's own instructions to create an Ubuntu 24.04 machine.

Either way you reach it with SSH, the standard way to get a shell on a remote Linux machine: 

ssh ubuntu@203.0.113.10        # user@address — your provider tells you both

SSH can check a password, but servers are normally set up to accept a key pair instead: a private key file that never leaves your Mac and a public key you hand to the server (cloud providers ask for it when you create the instance). Anyone may see the public half; holding the private half is what proves you are you. Create a pair once: 

$ ssh-keygen -t ed25519 -C "lt-lab"
Generating public/private ed25519 key pair.
…
Your identification has been saved in /Users/you/.ssh/id_ed25519
Your public key has been saved in /Users/you/.ssh/id_ed25519.pub
$ ls -l ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.pub
-rw-------  1 you  staff  399 Sep 21 09:21 /Users/you/.ssh/id_ed25519
-rw-r--r--  1 you  staff   89 Sep 21 09:21 /Users/you/.ssh/id_ed25519.pub

The .pub file is the one you paste into a provider's form. Look at the left-hand column: the private key is readable by you alone, the public key by everyone. That is the permission system of page 8 doing real work, and the same notation exists on macOS and Linux. Once logged in, two commands confirm you have a whole machine rather than a container: ask what process 1 is with ps -p 1 -o comm=. In the container lab the answer is bash; on an Ubuntu VM it should be systemd (page 13).

Caveat

A cloud VM is on the internet. Use key login only, keep nothing on it you would mind losing, and delete it when the module is done. The systemd and firewall pages quote documentation rather than showing this course's own runs where a container cannot reproduce them; your VM is where you check those for yourself.

Why not just use the Mac's terminal?

macOS looks like Linux from a distance — a shell, ls, grep, ssh — and that resemblance wastes more beginner hours than any real difference. Its command-line tools come from the BSD family, not the GNU family Linux uses, so the same command name takes different options. And the things this course is about are absent: 

$ ls /proc
ls: /proc: No such file or directory
$ sed --version
sed: illegal option -- -
usage: sed script [-EHalnru] [-i extension] [file ...]
$ which ip ss timeout
ip not found
ss not found
timeout not found

No /proc, so no way to inspect processes the way Linux does; no ip or ss; no timeout; and no namespaces or cgroups underneath, which is why Docker needed a VM in the first place. Use the Mac's terminal to run docker and ssh. Run everything else inside the lab. Appendix E lists the differences that bite.

Lab hygiene

  • Name things. --name lt-lab, not whatever Docker invents. A name is what lets you find, re-enter, and delete a container a week later.
  • Clean up. docker ps -a shows stopped containers too; they hold disk until removed. Remove your own by name. Avoid sweeping commands such as docker system prune on any machine you share — evals in progress are other people's containers.
  • Never paste secrets. No API keys, tokens or passwords into a lab box, a Dockerfile, or a docker run -e line. They end up in shell history, image layers and docker inspect output (page 11 shows each leak for real).
  • Keep your work outside. Scripts and notes live in a folder on the Mac; containers are for running things, not for keeping them.
Check your understanding

A teammate validates a new benchmark's forty task images on an M-series MacBook with Docker Desktop: the reference solution passes every task. On the x86 Linux cluster, five tasks fail during setup before the agent does anything, and the teammate proposes dropping those five "flaky" tasks from the score. What would you establish first?

Reveal the reasoning

Observed: the same task definitions behave differently in two environments, and the failures happen before the model acts — so they are observations about the run, not about any model. Not yet known: which difference matters. The laptop and the cluster differ in at least four ways this page showed you how to read: CPU architecture (uname -m: aarch64 vs x86_64, so the images and every compiled package differ), kernel (uname -r), memory and CPU available per container (nproc, free, and the limits the cluster applies), and when each image was built (package versions drift; page 15).

The discriminating step is to open a shell in one failing task's image on the cluster, run its setup by hand, and read the actual error and exit status. "Validated on my Mac" is evidence about a different instrument. As for dropping tasks: removing failures after seeing results changes the denominator in the score's favour. Record the five as infrastructure failures, report completed / scheduled alongside correct / completed, fix the images, and rerun the reference solution where the eval will really run.

Lab

Where: your Mac's terminal and the container lab you are building. Output will differ from the page in hostnames, dates, kernel version and — on an Intel Mac — architecture. The checklist in exercise 2 tells you what shape to expect.

1. Build it. Follow steps 1–7 above, typing the commands rather than pasting them. End with a running container named lt-lab made from your own lt-lab image.

Solution

The whole sequence, from the Mac, once the Dockerfile from step 7 is saved in the current folder:

$ docker build -t lt-lab .
$ docker run -dit --name lt-lab lt-lab
$ docker ps --filter name=lt-lab
NAMES    IMAGE    STATUS
lt-lab   lt-lab   Up Less than a second

If docker run reports a name conflict, an earlier lt-lab still exists: docker rm -f lt-lab, then run again.

3. Predict, then verify. In the learner shell, create a file: echo draft > ~/notes.txt. Now, from the Mac, run docker stop lt-lab then docker start lt-lab, and look for the file. Then run docker rm -f lt-lab, start a new lt-lab from your image, and look again. Before each look, write down whether you expect the file to be there.

Solution 
$ docker stop lt-lab; docker start lt-lab
lt-lab
lt-lab
$ docker exec -u learner lt-lab cat /home/learner/notes.txt
draft
$ docker rm -f lt-lab; docker run -dit --name lt-lab lt-lab
lt-lab
0527dbc58087…
$ docker exec -u learner lt-lab cat /home/learner/notes.txt
cat: /home/learner/notes.txt: No such file or directory

Stop/start keeps the container's filesystem: a stopped container is a paused thing, with your changes in it. Remove/run makes a new container from the image, which never contained the file. Hold on to the distinction — it is the difference between a harness that reuses a sandbox for the next attempt (leftover files are visible to it) and one that starts fresh.

4. Break it on purpose. As root in the container, run rm /usr/bin/ls. Confirm ls is gone, note the exact error and the value of $?, then restore the lab to working order in the cheapest way you can.

Solution 
# rm /usr/bin/ls
# ls
bash: ls: command not found
# echo $?
127
# exit
$ docker run --rm ubuntu:24.04 ls /usr/bin/ls
/usr/bin/ls

Exit status 127 again: the shell looked through the directories on its search path and found no file called ls. You could repair it (apt-get install --reinstall coreutils), but the cheapest fix is the disposable one: docker rm -f lt-lab and run a new container. Nothing you do inside a container changes the image it came from.

5. An eval-flavoured one. A benchmark you have been asked to review ships its tasks as Docker images. Using alpine:3.20 as a stand-in, start a shell in it and answer from inside: which user would the agent be, is bash available, is curl, and what would an agent's apt-get install curl produce? (There is no bash, so ask for sh.)

Solution 
$ docker run --rm -it alpine:3.20 sh
# whoami
root
# bash --version
sh: bash: not found
# curl --version
sh: curl: not found
# apt-get install curl
sh: apt-get: not found
# echo $?
127
# exit
$ docker run --rm alpine:3.20 bash -c id
docker: Error response from daemon: failed to create task for container: … exec: "bash": executable file not found in $PATH: unknown
$ echo $?
127

Root; no bash; no curl; and apt-get does not exist because Alpine is not a Debian-family system — its package manager is apk. An agent that assumes Ubuntu will burn steps here, and a harness that launches bash -c … in this image fails before the model has done anything. Whether that is "the model's Linux fluency" or "an environment defect" depends on what the task promised; either way you found it in a minute with the loop from this page.
