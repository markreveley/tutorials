Module 3 · Processes

Signals, exit codes, and timeouts

Every command in an agent's transcript ends with a small number, and every rollout ends because something stopped it. This page teaches you to decode both: how processes are told to stop, how they report the way they ended, and why the most famous number of all — 137 — does not mean what most people think it means.

A process ends in one of two ways

Either it exits, handing its parent an exit status, or it is killed by a signal. The kernel records these as different outcomes — the parent's wait (page 9) can ask "did it exit, and with what status?" or "was it signalled, and by which signal?".[wait(2)] The shell then flattens both into the single number you see in $? and in harness logs. Decoding that number means un-flattening it, so we take the two halves in turn.

Signals: the kernel's tap on the shoulder

A signal is a tiny asynchronous message delivered to a process: no payload, just a number. A process chooses, per signal, one of three behaviours: take the default action, ignore it, or catch it with a handler function.[signal(7)] The exceptions are the point of the design: "The signals SIGKILL and SIGSTOP cannot be caught, blocked, or ignored."[signal(7)] The working set, with numbers as they are on x86 and ARM (a few other architectures number them differently):[signal(7)]

SignalNo.DefaultWho sends it, and why
SIGHUP1terminateThe terminal went away (page 9)
SIGINT2terminateCtrl+C: "interrupt from keyboard"
SIGQUIT3core dump"Quit from keyboard"; like INT but dumps core
SIGKILL9terminateThe last resort. Cannot be caught: the process gets no chance to clean up
SIGSEGV11core dumpThe kernel: "invalid memory reference" — a crash in native code
SIGPIPE13terminateThe kernel: you wrote to a pipe nobody is reading (yes | head, page 4)
SIGTERM15terminateThe polite request to stop. What kill, docker stop, timeout and systemd send first
SIGCHLD17ignoreThe kernel, to a parent: one of your children changed state (time to wait)
SIGCONT / SIGSTOP18 / 19continue / stopResume or freeze a process. SIGSTOP cannot be caught; Ctrl+Z sends its catchable cousin SIGTSTP (20)

"Core dump" means terminate and, if allowed, write a memory image for debugging; for reading transcripts, treat it as "terminate". You send signals with kill, which despite its name sends any signal and sends TERM unless told otherwise.[kill(1)] In the container lab, as learner: 

$ sleep 300 &
[1] 25
$ kill %1; wait %1; echo "status=$?"       # %1 = job 1; a PID works too
[1]+  Terminated              sleep 300
status=143
$ sleep 300 &
[1] 26
$ kill -KILL %1; wait %1; echo "status=$?"  # same as kill -9
[1]+  Killed                  sleep 300
status=137
$ sleep 300 &
[1] 27
$ kill -STOP %1; ps -o pid,stat,args -C sleep
  PID STAT COMMAND
   27 T    sleep 300
$ kill -CONT %1; ps -o pid,stat,args -C sleep
  PID STAT COMMAND
   27 S    sleep 300
$ kill -0 27; echo "rc=$?"                  # signal 0: send nothing, just check
rc=0

Remember the words bash prints — Terminated, Killed, Segmentation fault, Stopped — because they turn up in transcripts' stderr and each names a signal. pkill is kill by name (page 9). You may signal only your own processes unless you are privileged: as learner, kill -TERM 1 against root's PID 1 prints Operation not permitted.[kill(2)]

Catching signals, and the TERM → wait → KILL protocol

Because TERM can be caught, a well-behaved program uses it to finish up: flush buffers, remove temporary files, write its results. In bash the handler is installed with trap: 

#!/bin/bash
# A worker that cleans up when asked politely.
workdir=$(mktemp -d)
cleanup() { rm -rf "$workdir"; echo "cleaned up $workdir"; }
trap cleanup EXIT
trap 'echo "got SIGTERM, finishing"; exit 0' TERM
echo "working in $workdir (pid $$)"
sleep 300 &
wait $!
$ /tmp/graceful.sh &
[1] 30
working in /tmp/tmp.SbI72fGeHE (pid 30)
$ kill -TERM 30; sleep 1; ls -d /tmp/tmp.*
got SIGTERM, finishing
cleaned up /tmp/tmp.SbI72fGeHE
[1]+  Done                    /tmp/graceful.sh
ls: cannot access '/tmp/tmp.*': No such file or directory
$ /tmp/graceful.sh &
[1] 37
working in /tmp/tmp.HDTxiUmqGS (pid 37)
$ kill -KILL 37; sleep 1; ls -d /tmp/tmp.*
[1]+  Killed                  /tmp/graceful.sh
/tmp/tmp.HDTxiUmqGS

With TERM the script cleaned up and exited 0. With KILL nothing ran: the directory is still there, and anything the process held only in memory — unflushed log lines, a half-written result file — is gone. (The script runs sleep in the background and waits because bash delays a trap until the current foreground command finishes.[Bash Manual])

Every supervisor on Linux therefore stops things the same way: send TERM, wait a grace period, then send KILL. kill(1) itself recommends the order.[kill(1)] Only the grace period differs:

SupervisorFirst signalGrace periodThen
timeout -k 5 60 cmdTERM at 60 s5 s (the -k value, counted from the first signal)[Coreutils]KILL. Without -k, never
docker stopTERM (or the image's STOPSIGNAL) to the container's main process10 s by default for Linux containers; -t changes it[Docker: run]KILL
systemd stopping a serviceTERM to the unit's processesTimeoutStopSec, whose default comes from DefaultTimeoutStopSec: 90 s[systemd]KILL

The exit status, decoded

A program that exits hands back an integer of which only the low 8 bits reach the parent, so the range is 0–255.[exit(3)] Zero is success and everything else is failure, so that there is "one well-defined way to indicate success and a variety of ways to indicate various failure modes".[Bash Manual] What 1, 2 or 3 mean is up to each program (its man page has an EXIT STATUS section): 

$ grep -q root /etc/passwd; echo $?          # found
0
$ grep -q nosuchuser /etc/passwd; echo $?    # ran fine, found nothing
1
$ grep -q root /etc/nofile; echo $?          # could not do the job
grep: /etc/nofile: No such file or directory
2
$ bash -c 'exit 256'; echo $?                # only 8 bits survive
0

Above 125 the shell reserves values for things that happened around the program rather than in it. If a command is not found the status is 127; if it is found but cannot be executed, 126; and "when a command terminates on a fatal signal whose number is N, Bash uses the value 128+N as the exit status".[Bash Manual] 

$ nosuchcmd; echo $?
bash: nosuchcmd: command not found
127
$ touch /tmp/notexec; /tmp/notexec; echo $?
bash: /tmp/notexec: Permission denied
126
$ python3 -c 'import ctypes; ctypes.string_at(0)'; echo $?    # read address 0
Segmentation fault
139
Key idea

Don't memorise 130, 137, 139, 143. Subtract 128 and look up the signal: 2 is INT, 9 is KILL, 11 is SEGV, 15 is TERM. The number tells you which signal. It never tells you who sent it or why — that takes other evidence.

128+N is a shell convention, not a kernel fact, so other layers spell the same death differently. Python's subprocess reports a signalled child as a negative number (we got -9 from Popen.kill() and -15 from terminate()), but 137 when a shell sat in between. Docker reports 137 and 143. Appendix B has the full tables.

timeout: a deadline for one command

timeout DURATION cmd runs a command and signals it if it is still going at the deadline. It is the simplest timeout there is, and its exit statuses are documented: 124 if the command timed out, 125 if timeout itself failed, 126/127 as in the shell, 137 if KILL was sent, and otherwise the command's own status.[Coreutils] 

$ timeout 2 sleep 10; echo "status=$?"
status=124
$ timeout 2 bash -c 'exit 42'; echo "status=$?"
status=42
$ timeout -s KILL 2 sleep 10; echo "status=$?"
Killed
status=137
$ timeout --preserve-status 2 sleep 10; echo "status=$?"
status=143

Now a command that ignores TERM (stubborn.sh is trap '' TERM, then four seconds of work), first without and then with a kill-after: 

$ time timeout 2 /tmp/stubborn.sh; echo "status=$?"
stubborn: started
stubborn: finished anyway

real	0m4.016s
status=124
$ time timeout -k 1 2 /tmp/stubborn.sh; echo "status=$?"
stubborn: started
Killed

real	0m3.024s
status=137
Pitfall — three ways a timeout check lies

A timeout without -k is a suggestion. The first run above overran its two-second limit, completed its work, and was still reported as 124. 124 is GNU-only. Alpine's BusyBox timeout returned 143 for timeout 1 sleep 3 when we ran it, so a harness that detects timeouts with == 124 misses every one on an Alpine task image. And 137 from timeout is ambiguous by its own manual: it is returned whether KILL went to the command or to timeout itself, and in the latter case the command may still be running.[Coreutils] The running example's run-tests.sh (page 6) uses timeout for exactly this reason: a hung test must become a recorded outcome, not a hung grader.

The PID 1 problem

The kernel protects PID 1, because a machine whose init dies is a dead machine. Inside a PID namespace, "only signals for which the 'init' process has established a signal handler can be sent to the 'init' process by other members of the PID namespace. This restriction applies even to privileged processes".[pid_namespaces(7)] In a container, PID 1 is your application, and most applications install no handlers. Watch what that does — as root, inside a container whose PID 1 is a plain sleep: 

$ docker run -d --name lt-pid1 ubuntu:24.04 sleep 300
$ docker exec lt-pid1 sh -c 'id -u; grep SigCgt /proc/1/status; kill -TERM 1; echo "rc=$?"; kill -KILL 1; echo "rc=$?"; sleep 1; ps -o pid,stat,args -p 1'
0
SigCgt:	0000000000000000
rc=0
rc=0
  PID STAT COMMAND
    1 Ss   sleep 300

SigCgt is the mask of caught signals: all zeros, no handlers. Both kills report success and neither does anything — even kill -9, even as root. From outside the namespace the rule is slightly different: unhandled signals are still dropped, except that KILL and STOP are forcibly delivered.[pid_namespaces(7)] So docker stop's TERM vanishes, the daemon waits out its grace period, and only the KILL lands: 

$ time docker stop lt-pid1
lt-pid1
… 10.211 total
$ docker inspect lt-pid1 --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}'
ExitCode=137 OOMKilled=false

Ten seconds per teardown, a 137 on every container, and no cleanup ever runs. There are two fixes. docker run --init puts a minimal init at PID 1 that "forwards signals and reaps processes";[Docker: run] your application becomes an ordinary PID 7, where TERM's default action applies: 

$ docker run -d --init --name lt-init ubuntu:24.04 sleep 300
$ docker exec lt-init ps -eo pid,ppid,stat,args
  PID  PPID STAT COMMAND
    1     0 Ss   /sbin/docker-init -- sleep 300
    7     1 S    sleep 300
    8     0 Rs   ps -eo pid,ppid,stat,args
$ time docker stop lt-init
lt-init
… 0.090 total
$ docker inspect lt-init --format 'ExitCode={{.State.ExitCode}}'
ExitCode=143

The other fix is an application that handles TERM and actually is PID 1. Run graceful.sh directly as the container's command and docker stop took 0.12 s, exit code 0, with cleaned up in the logs. Wrap the same script in a shell — /bin/sh -c '/graceful.sh', which is what a Dockerfile's shell-form CMD /graceful.sh produces (page 22) — and PID 1 is sh, the script is PID 7, the TERM goes to a shell with no handler, and we were back to 10.2 s and 137. Exec-form CMD ["/graceful.sh"] avoids the wrapper.

137: one number, four stories

137 means exactly one thing: this process died of SIGKILL. Folklore says "137 = out of memory", because the kernel's OOM killer uses SIGKILL. But so does everything else that gives up on being polite. Three containers, run for real; the first two with a 64 MB memory limit and a command that eats memory: 

# (1) the OOM victim is a child; PID 1 (sh) carries on
$ docker run --name lt-oom1 --memory 64m --memory-swap 64m ubuntu:24.04 \
    sh -c 'tail /dev/zero; echo "tail exit=$?"; grep oom_kill /sys/fs/cgroup/memory.events'
Killed
tail exit=137
oom_kill 1
$ docker inspect lt-oom1 --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}'
ExitCode=0 OOMKilled=true

# (2) the OOM victim is PID 1
$ docker run --name lt-oom2 --memory 64m --memory-swap 64m ubuntu:24.04 tail /dev/zero
$ docker inspect lt-oom2 --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}'
ExitCode=137 OOMKilled=true

# (3) no memory problem at all: a supervisor ran out of patience
$ docker run -d --name lt-to ubuntu:24.04 sleep 300; sleep 2; docker kill lt-to
$ docker inspect lt-to --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}'
ExitCode=137 OOMKilled=false

Case 1 is the one that catches people, and it is the common shape in agentic evals: the agent's test run or compiler is OOM-killed, the agent's shell sees Killed and 137 for that one command, the shell carries on, and the container exits 0. Case 3 is byte-for-byte what the PID 1 teardown above produced. A fourth source needs no container at all: ulimit -t 1 sets a CPU-time rlimit, and because bash sets the soft and hard limits together, the process gets SIGKILL at the hard limit — 137 again. Set only the soft limit (ulimit -St 1) and it dies of SIGXCPU instead:[getrlimit(2)] 

$ (ulimit -t 1; while :; do :; done); echo "status=$?"
Killed
status=137
$ (ulimit -St 1; while :; do :; done); echo "status=$?"
CPU time limit exceeded
status=152
In eval work — navigate

Observed: 137. Hypotheses: OOM kill, harness timeout, normal teardown, CPU rlimit. Each has a discriminating test, and each means something different for scoring.

OOM killoom_kill > 0 in the sandbox's memory.events; State.OOMKilled=true; duration well short of any limit (page 12)Infrastructure failure — unless the task is about memory-efficient code
Harness or tool timeoutOOMKilled=false; duration equals the configured limit to within a second; the harness log has a timeout eventA run outcome: "did not finish in the budget". Report it as its own category

Exit code plus timing plus one counter from outside the transcript is usually enough. None of the three alone is.

Failure accounting: a kill is an observation about the run

An exit code of 1 from the test suite is a statement about the agent's answer. A 124 or a 137 is a statement about the run: it did not finish, and you do not know what the answer would have been. Scoring both as "failed" mixes two quantities. Here is the running example's results.jsonl (page 5), first by exit code, then through a twenty-line script that keeps the run outcomes separate: 

$ grep -o '"exit_code": [0-9]*' results.jsonl | sort | uniq -c | sort -rn
    106 "exit_code": 0
     56 "exit_code": 1
      9 "exit_code": 127
      8 "exit_code": 124
      5 "exit_code": 137
      4 "exit_code": 2
      4 "exit_code": 126
$ python3 account.py results.jsonl
scheduled 192  completed 179  correct 106
  timeout (124): 8
  killed (137): 5
correct/scheduled   = 0.552
correct/completed   = 0.592
completed/scheduled = 0.932
import json, sys

rows = [json.loads(line) for line in open(sys.argv[1])]
RUN_OUTCOMES = {124: "timeout", 137: "killed"}   # about the run, not the answer

scheduled = len(rows)
not_completed = [r for r in rows if r["exit_code"] in RUN_OUTCOMES]
completed = scheduled - len(not_completed)
correct = sum(r["passed"] for r in rows)

print(f"scheduled {scheduled}  completed {completed}  correct {correct}")
for code, name in RUN_OUTCOMES.items():
    print(f"  {name} ({code}): {sum(r['exit_code'] == code for r in rows)}")
print(f"correct/scheduled   = {correct / scheduled:.3f}")
print(f"correct/completed   = {correct / completed:.3f}")
print(f"completed/scheduled = {completed / scheduled:.3f}")
In eval work — discuss and design

Three ratios, three meanings. correct/scheduled (55.2%) is what a user of this whole system would experience. correct/completed (59.2%) is closer to the model's ability when the infrastructure holds. completed/scheduled (93.2%) is the health of the instrument. Per model the gap matters more: model-c completed 58 of 64 and model-a 62 of 64, so part of their difference is infrastructure, and if kills cluster on particular tasks the affected trials are not independent.[Anthropic: Agent Evals] Rules that follow: choose the primary metric before looking at results; publish all three numbers with the timeout and kill counts; never drop non-completed rollouts silently, because a runner that discards its timeouts will always look more accurate; and treat a timeout as a finding to investigate (slow model? throttled CPU? a command waiting on a prompt?), not as a wrong answer. Inspect draws a related line inside the harness: a tool-call TimeoutError is an "expected" error that is reported to the model, which may try something else, while unexpected errors (a failure talking to the container runtime, say) fail the sample with an error.[Inspect] Its bash() tool has no timeout unless you set one, and its docs suggest setting one so that "a single wayward bash command doesn't consume the entire time_limit".[Inspect] The concept of timeouts and retries across a whole system is the subject of Networking for LLM Evals, lesson 11.

Depth triage: learn to use kill, timeout -k, trap, the 128+N arithmetic and docker inspect's State. Recognise SIGPIPE's 141, SIGXCPU's 152, process groups, and the word "subreaper". Leave to specialists real-time signals, signal masks, and writing async-signal-safe handlers in C.

Check your understanding

A new runner is proposed for your team's agentic benchmark. Its summary says: "Accuracy improves from 61% to 68%. We also fixed flakiness: samples whose container exits 137 are now automatically retried, up to three times, and samples that still fail to complete are excluded from the denominator." What would you ask in review?

Reveal the reasoning

What is observed vs supposed. Observed: containers exit 137. Supposed: that 137 means a transient infrastructure fault. 137 only says SIGKILL. Ask for the breakdown: how many had OOMKilled=true or oom_kill > 0, how many died at exactly the time limit, how many were teardown artefacts.

Why it matters which. If they are timeouts, a retry gives a slow agent a second draw: the metric has silently become "best of up to three", which is a pass@k-style quantity, not the accuracy it is being compared against. If they are OOM kills that recur on the same tasks, they are deterministic properties of task × memory limit; retrying will not help, and excluding them removes the memory-hungry (probably harder) tasks from the denominator — accuracy rises because the test got easier. And case 1 on this page says some OOM-affected samples never show 137 at all: the container exits 0 and the sample is scored as an ordinary wrong answer, so the rule is also applied unevenly.

What to require. The old and new runs reported as correct/scheduled, correct/completed and completed/scheduled, with counts by cause; the 61% and 68% recomputed on the same denominator; retries, if kept, only for causes shown to be independent of the agent's behaviour, and counted. Until then the honest summary is "the denominator changed", not "accuracy improved".

Lab

Container lab (page 1) as learner for exercises 1–3; exercises 4–5 are run from your Mac's terminal with docker. Save graceful.sh from this page to /tmp and chmod +x it.

  1. Reproduce. Start sleep 300 &, end it with plain kill, and read its status with wait. Repeat with kill -9, and with fg followed by Ctrl+C. Subtract 128 from each.
    Solution

    143 (TERM, 15), 137 (KILL, 9), 130 (INT, 2) — the sessions on this page and on page 9.

  2. Predict, then verify. Create /tmp/stubborn.sh: 
    #!/bin/bash
# Ignores SIGTERM, the way a badly behaved test runner might.
trap '' TERM
echo "stubborn: started"
sleep 4
echo "stubborn: finished anyway"
    Before running each, write down the exit status and the elapsed time: time timeout 2 /tmp/stubborn.sh and time timeout -k 1 2 /tmp/stubborn.sh.
    Solution

    First: 124 after about 4 s — TERM at 2 s was ignored (by the script and by the sleep it started, since ignored signals stay ignored across exec[signal(7)]), the script finished its work, and timeout still reports 124. Second: 137 after about 3 s — TERM at 2 s, KILL one second later. Real output is in the timeout section. A grader that reads 124 as "no work was done" is wrong in the first case.

  3. Cleanup or not? Run /tmp/graceful.sh & twice; end one with kill and one with kill -9. Which leaves a directory in /tmp? What exit status does each report via wait?
    Solution

    TERM: the handler runs, the EXIT trap removes the directory, status 0 (the handler says exit 0, so no 143 — a handled signal is not a death by signal). KILL: no handler runs, the directory remains, status 137.

  4. The ten-second stop. From your Mac: docker run -d --name lt-s1 ubuntu:24.04 sleep 300 and docker run -d --init --name lt-s2 ubuntu:24.04 sleep 300. Predict, then measure time docker stop for each, and read both exit codes with docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}}'. Before stopping lt-s1, try docker exec lt-s1 kill -9 1. Remove both.
    Solution

    We measured 10.2 s and 137 false without --init; 0.09 s and 143 false with it. The kill -9 1 returns 0 and does nothing: inside its namespace, PID 1 receives only signals it has handlers for. Full output is in the PID 1 section.

  5. Eval task: three 137s. A results file shows three rollouts of the same task, all "exit 137, failed". The harness's time limit is 300 s and the memory limit is 64 MB. The evidence you can pull: rollout A, duration 94 s, OOMKilled=true; rollout B, duration 300.0 s, OOMKilled=false; rollout C, duration 41 s, OOMKilled=false, tests passed in the transcript, and the container's FinishedAt is 10 s after the harness logged "stopping sandbox". Classify each, say how it should be recorded, and recreate A and C's signatures with the commands from this page.
    Solution

    A: OOM kill — infrastructure outcome (unless the task specifies a memory budget); not completed. Recreate with case 2 of the 137 section (ExitCode=137 OOMKilled=true). B: killed at the time limit — a timeout; not completed; then look at the transcript's last command for a hang. C: the agent succeeded; the 137 is the teardown of a PID 1 with no TERM handler, recorded by a harness that confused the container's exit code with the rollout's result. That is a harness defect, and the rollout should be scored from its tests. Recreate with the first docker stop in the PID 1 section (ExitCode=137 OOMKilled=false after 10.2 s). One "failure rate" of 3/3 was hiding one environment problem, one budget problem and one bug in the runner.
