Module 5 · Networking for Sandboxes

Firewalls and egress control

This page finishes audit question 4, what can it reach? You will learn the menu of ways to limit a sandbox's outbound traffic, how each one is enforced from outside, and a 30-line probe that proves from inside what a box can actually reach. Its output belongs in the eval config next to the score.

Why egress is the question

Egress is traffic leaving the box; ingress is traffic arriving. For an eval sandbox, egress is the one that decides what you are measuring. Tasks are often built from public repositories, so the upstream fix may be public too, and a box that can reach the internet can look for it. The same route carries data out and lets the sandbox send traffic to third parties. Nearby are the host's own services and, on a cloud VM, the instance metadata service, whose data "is not protected by authentication or cryptographic methods" and can include the machine's temporary role credentials.[AWS: IMDS] Docker's starting position is permissive: containers "have networking enabled by default, and they can make outgoing connections".[Docker: networking] The conceptual side — what a network boundary protects and why it bears on validity — is Networking for LLM Evals, lesson 22. This page covers the Linux and Docker side.

The enforcement menu

From simplest and strongest to most flexible. Every option is enforced outside the sandbox's control: a default container lacks the NET_ADMIN capability, so even root inside it cannot change the rules (shown below).

1. No network

"Within the container, only the loopback device is created."[Docker: none] With no interface to send from, there is nothing for a firewall to do. This is also the default of the most widely used open-source harness: Inspect's generated compose configuration "sets network_mode: none".[Inspect] You will see the --network none output in the probe below.

2. An internal network

docker network create --internal NAME gives containers an interface and each other, but "no default route is configured and firewall rules are set up to drop all traffic to or from other networks". The same sentence continues with the caveat people miss: "Communication with the gateway IP address (and thus appropriately configured host services) is possible".[Docker: network create] On the authoring machine the internal network's gateway answered a ping and refused port 8000 instantly. Refusing is itself an answer: the host is there, and it simply had nothing listening on that port: 

$ docker network create --internal lt-int
$ docker run --rm --network lt-int lt-tools bash -c \
    'ping -c1 -W2 172.19.0.1 | grep transmitted; curl -sS -m5 -o /dev/null http://172.19.0.1:8000/; dig example.com | grep status'
1 packets transmitted, 1 received, 0% packet loss, time 0ms
curl: (7) Failed to connect to 172.19.0.1 port 8000 after 1 ms: Couldn't connect to server
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL, id: 4158

The last line matters too. On this Docker version the embedded resolver on an internal network did not forward external names, so DNS was not an escape route here. That is an observation of one version, not a documented guarantee, so the probe tests it every time.

3. Internal network plus an allowlisting proxy

When a task legitimately needs some internet (a package index, say), give the sandbox exactly one door: a proxy container attached to both the internal network and a normal one, which forwards only to hosts on its allowlist. How clients find the proxy, and how a refusal looks, is on page 18.

network "sandbox" network "outside" (internal: true, no route out) (normal bridge, NAT to internet) ┌─────────────────────┐ │ default (the agent) │ │ https_proxy= │ │ http://proxy:8888 │ └─────────┬───────────┘ │ CONNECT pypi.org:443 ▼ ┌────────────────────────────────────────────┐ │ proxy: one container, an interface on each │──▶ NAT ──▶ internet │ network; forwards only allowlisted hosts │ (pypi.org, └────────────────────────────────────────────┘ files.pythonhosted.org)

In Compose, an internal network is internal: true, which "lets you create an externally isolated network".[Compose] This sketch was run as written. The proxy is tinyproxy, built inline from ubuntu:24.04, so no extra image is pulled. The service is named default because Inspect treats a service with that name as the primary sandbox: 

services:
  default:                       # the agent's sandbox
    image: ubuntu:24.04
    command: tail -f /dev/null
    init: true
    networks: [sandbox]          # internal only: no route out
    environment:
      http_proxy: http://proxy:8888
      https_proxy: http://proxy:8888
      no_proxy: localhost,127.0.0.1
  proxy:                         # the only door, on both networks
    build:
      dockerfile_inline: |
        FROM ubuntu:24.04
        RUN apt-get update && apt-get install -y --no-install-recommends tinyproxy \
         && rm -rf /var/lib/apt/lists/*
        RUN printf '%s\n' 'Port 8888' 'Timeout 30' 'FilterDefaultDeny Yes' \
              'Filter "/etc/tinyproxy/allow"' 'FilterType ere' > /etc/tinyproxy/egress.conf \
         && printf '%s\n' '^pypi\.org$' '^files\.pythonhosted\.org$' > /etc/tinyproxy/allow
        CMD ["tinyproxy", "-d", "-c", "/etc/tinyproxy/egress.conf"]
    networks: [sandbox, outside]
networks:
  sandbox:
    internal: true
  outside: {}
$ docker compose -p lt-egress up -d --build
$ docker compose -p lt-egress exec default apt-get update
…
E: Failed to fetch http://ports.ubuntu.com/ubuntu-ports/dists/noble-security/InRelease  403  Filtered [IP: 172.18.0.3 8888]

apt honours http_proxy, the Ubuntu mirror is not on the list, and the proxy said no. From a tools container on the same internal network, pypi.org returns 200, github.com fails with CONNECT tunnel failed, response 403, and bypassing the proxy with --noproxy '*' dies at DNS with exit 6. The proxy is the only way out.

Caveat

A proxy allowlist of hostnames is only as tight as its hosts. Allowing a site that serves arbitrary user content (a code host, a paste site, a general search engine) re-opens most of what you closed. And note what the proxy config does not say: nothing here restricts the host gateway, which the internal network leaves reachable. That is a job for the host firewall.

4. Host firewall rules: nftables

The kernel's packet filter is netfilter, and its current front end is nftables, which "replaces the popular {ip,ip6,arp,eb}tables".[nftables] The model has three nouns. A table is a container for chains, and the inet family covers IPv4 and IPv6 in one ruleset.[nftables] A base chain attaches to a hook, a point in the kernel's packet path — input (to this machine), output (from local processes), forward (passing through, which is where a container's traffic crosses the host) — and has a policy, accept or drop, applied to whatever no rule decides.[nftables] A default-deny chain is policy drop plus explicit accepts. The one rule every such chain needs is ct state established,related accept: connection tracking remembers flows, so replies to connections you allowed get back in.[nftables]

Host-side rules could not be run on the authoring machine (Docker Desktop hides its Linux VM), so what follows is adapted from the documentation, not executed output. On a Linux host using Docker's default iptables backend, rules for container traffic go in the DOCKER-USER chain, "a placeholder for user-defined rules that will be processed before rules in the DOCKER-FORWARD and DOCKER chains". Rules appended to FORWARD instead run after Docker's own and may never see the packet.[Docker: iptables] AWS documents this shape for cutting processes off from the metadata service:[AWS: IMDS] 

# adapted from Docker's DOCKER-USER docs and AWS's IMDS guidance -- NOT executed here
iptables -I DOCKER-USER -i docker0 -d 169.254.169.254 -j REJECT     # no metadata from containers
iptables -I DOCKER-USER -i docker0 ! -d 172.17.0.0/16 -j DROP       # nothing else leaves docker0

Docker 29's nftables backend is experimental and has no DOCKER-USER chain; instead, "rules can be added in separate tables, with base chains that have the same types and hook points as Docker's base chains".[Docker: nftables] Depth triage: reading a ruleset and knowing which chain Docker consults is recognize level for this course. Writing a host's production firewall is a specialist's job. What you must be able to do yourself is test the result from inside, which is the probe.

Drop versus reject, seen from inside

You can feel the two firewall verdicts without a VM by filtering the container's own network namespace, which needs --cap-add NET_ADMIN. Without it, even uid 0 is refused. This is the property that makes outside enforcement trustworthy: 

$ docker run --rm lt-tools bash -c 'apt-get install -y -qq nftables >/dev/null; nft add table inet sandbox'
Error: Could not process rule: Operation not permitted
$ docker run --rm -it --cap-add NET_ADMIN lt-tools bash
# nft add table inet sandbox
# nft 'add chain inet sandbox egress { type filter hook output priority 0; policy accept; }'
# nft add rule inet sandbox egress ip daddr 1.1.1.1 tcp dport 80 drop
# curl -sS -o /dev/null --connect-timeout 3 http://1.1.1.1/
curl: (28) Failed to connect to 1.1.1.1 port 80 after 3008 ms: Timeout was reached
# nft flush chain inet sandbox egress
# nft add rule inet sandbox egress ip daddr 1.1.1.1 tcp dport 80 reject
# curl -sS -o /dev/null --connect-timeout 3 http://1.1.1.1/
curl: (7) Failed to connect to 1.1.1.1 port 80 after 0 ms: Couldn't connect to server

drop discards the packet "on the floor"; reject sends back an error, by default ICMP port unreachable.[nftables] So a reject fails in 0 ms, and a drop fails only when the client's timeout runs out. With no timeout set, the same dropped connection held curl for 136 seconds (after 136238 ms) before the kernel gave up. A default-deny egress chain, listed back by nft: 

# nft list ruleset
table inet sandbox {
	chain egress {
		type filter hook output priority filter; policy drop;
		oif "lo" accept
		ct state established,related accept
		ip daddr 1.1.1.1 tcp dport 443 accept
	}
}
# curl -sS -o /dev/null -w '%{http_code}\n' --connect-timeout 3 https://1.1.1.1/
301
# curl -sS -o /dev/null --connect-timeout 3 http://1.0.0.1/
curl: (28) Failed to connect to 1.0.0.1 port 80 after 3006 ms: Timeout was reached
# curl -sS -o /dev/null --connect-timeout 3 https://example.com/
curl: (6) Could not resolve host: example.com

The third result shows one of the two classic holes, here closed: the policy dropped DNS too, so names fail at exit 6. A rules-plus-proxy design that leaves the resolver open leaves a channel open (page 18). The other hole is IPv6. An ip-family table, or iptables without ip6tables, filters only IPv4, which is one reason the inet family exists. The probe checks both.

The reachability probe

Whatever enforces the policy, you prove it the same way: from inside, against a fixed list of targets, with timeouts. Five questions, in order: what network am I on (ip -br addr; ip route, page 16)? Do external names resolve? Does the internet answer (by name, by IP, over IPv6)? Does the host gateway answer? Does the metadata address or a neighbour container answer? As a script (shellcheck-clean, 30 lines, saved in the course repo as research/verify/19-probe.sh): 

#!/usr/bin/env bash
# probe.sh [HOST_PORT] [PEER_IP:PORT] -- from inside a sandbox: what can this box reach?
set -u
host_port=${1:-8000}; peer=${2:-}
echo "== interfaces (fallback tunnel devices hidden) and routes"
ip -br addr | grep -v '@NONE'; ip route
gw=$(ip route | awk '/^default/ {print $3; exit}')  # no default route? assume .1 of the subnet
[ -n "$gw" ] || gw=$(ip route | awk '/proto kernel/ {split($1, a, "[./]"); print a[1] "." a[2] "." a[3] ".1"; exit}')
echo "== targets"
try() {  # try LABEL URL [curl options...]: any HTTP answer counts as reachable
  local label=$1 url=$2 code rc v; shift 2
  code=$(curl -sS -o /dev/null -m 5 --connect-timeout 3 -w '%{http_code}' "$@" "$url" 2>/dev/null)
  rc=$?
  case $rc in
    0)  v="REACHABLE (HTTP $code)" ;;
    7)  v="no: refused, rejected or no route (exit 7)" ;;
    28) v="no: dropped or timed out (exit 28)" ;;
    *)  v="no (curl exit $rc)" ;;
  esac
  printf '%-34s %s\n' "$label" "$v"
}
if getent ahosts example.com >/dev/null; then v="REACHABLE (external names resolve)"; else v="no"; fi
printf '%-34s %s\n' "DNS for external names" "$v"
try "internet https://example.com" https://example.com/
try "internet by IP 1.1.1.1" http://1.1.1.1/
try "internet over IPv6" https://example.com/ -6
if [ -n "$gw" ]; then try "host gateway $gw:$host_port" "http://$gw:$host_port/"
else printf '%-34s %s\n' "host gateway" "no: no interface but lo"; fi
try "metadata 169.254.169.254" http://169.254.169.254/
if [ -n "$peer" ]; then try "neighbour $peer" "http://$peer/"; fi

Read it as evidence, with the hypotheses kept separate. Observed: under none, nothing. Under --internal, only the neighbour. On the default bridge, the internet and the neighbour (the default bridge lets containers reach each other by IP;[Docker: bridge] another rollout's sandbox is a neighbour too). Not established: that the gateway is safe. Exit 7 there means a host answered "nothing on port 8000". Probe the ports your host actually serves (ss -tlnp on the host, page 17). Likewise, "metadata: no" on a laptop proves nothing about a cloud VM, where that address answers unless something blocks it. Run the probe where the eval runs.

Pitfall

Run the probe with the proxy variables set and it lies. Inside the compose sandbox above, with https_proxy inherited, it reported internet by IP 1.1.1.1 REACHABLE (HTTP 403) and the same for the gateway and the metadata address. Every "answer" was the proxy saying 403 Filtered. Probe twice: once with env -u http_proxy -u https_proxy to test the network policy, and once through the proxy with -f to test the allowlist. And never write a probe without timeouts: a dropped connection with none set held curl for 136 seconds.

In eval work · design

Inspect's default is network_mode: none, but "supplying a custom Compose configuration … replaces the generated configuration rather than extending it, including its network_mode: none", and Compose's own default "is a project-scoped network with outbound Internet access".[Inspect] So the day someone adds a compose.yaml to give a task a database, its sandbox silently goes from no network to the open internet, and the scores move for a reason nobody wrote down. Two defences. Write network_mode: none (or an internal: true network) into every compose file yourself. And run probe.sh inside a freshly built sandbox in CI, failing the build if any line differs from the expected policy — an eval of the environment itself. Remember the boundary's scope as well: network_mode: none "applies only to processes inside the container", not to tool, scorer or model-provider code running outside.[Inspect]

In eval work · discuss and failure accounting

"Pass rate with open network" and "pass rate with no network" are different measurements. With a route out, the agent may download the fix rather than write it. Report the network policy as part of the eval configuration, as you would the model version, and paste the probe output into the run record. When a sample fails because of the policy — pip install gets a 403 from the proxy, a task needs a host the allowlist forgot — that is an observation about the run and the task, not the model. Log it as an infrastructure or task-validity failure with the probe line that explains it, and keep correct / scheduled and completed / scheduled as separate numbers. Decide before the run whether policy-blocked samples count against the model; don't decide after seeing which way it moves the score.

Check your understanding

A team moves its agentic coding benchmark from its own runner to a harness whose default is no network. To support two new tasks that need a Postgres container, they add a compose.yaml to the task directory. The next release's pass rate rises from 38% to 47%, and the two new tasks account for only 1 point. The team credits a better model. What do you check, and how would the answer change what gets reported?

Reveal the reasoning

Observed: a rise, mostly on old tasks, coinciding with a compose file. Hypothesis to rule out: the compose file replaced the harness's generated config, the sandbox lost network_mode: none, and old tasks became solvable by fetching. Evidence that discriminates: (1) read the compose file for network_mode or an internal: true network; (2) run probe.sh in a sandbox built from this release and from the previous one (if the diff is "internet: REACHABLE", the configs differ); (3) search transcripts of newly passing tasks for pip download, git clone, curl or wget to outside hosts, and check whether the fetched content contains the fix; (4) rerun the old tasks with the new model under the old network policy. If the gain disappears in (4), the 9 points measured the environment change. Report both runs, label the network policy of each, and restore the intended policy (with probe.sh in CI) before any comparison with earlier releases.

  3. Drop versus reject. In docker run --rm -it --cap-add NET_ADMIN lt-tools bash, install nftables, add the drop rule from the page, and time curl -sS -o /dev/null --connect-timeout 3 http://1.1.1.1/. Replace it with a reject rule and time it again. Then try nft add table inet x in a container without --cap-add.
    Solution

    Drop: curl: (28) … after 3008 ms: Timeout was reached. Reject: curl: (7) … after 0 ms. Without NET_ADMIN: Error: Could not process rule: Operation not permitted, as root. That is why a sandboxed agent cannot loosen its own firewall, and why a task image that asks for NET_ADMIN deserves a question in review.

  4. VM lab: close the metadata hole. On a cloud Linux VM with Docker (iptables backend), run probe.sh in a default container and note the metadata line. Add the DOCKER-USER REJECT rule for 169.254.169.254 from the page and probe again.
    Solution

    Not executed for this course (no cloud VM was used), so no output is shown. What to expect from the documentation: before the rule, the metadata line may report REACHABLE (HTTP 200, or 401 when the instance requires IMDSv2 tokens — any HTTP answer means the service is reachable). After it, the line should read no: refused, rejected or no route (exit 7), since REJECT answers immediately. Check that the rule is there with sudo iptables -L DOCKER-USER -n. If your Docker uses the nftables backend, there is no DOCKER-USER chain; add a separate table instead.

  5. Eval-flavoured: make the policy a test. Write expect-none.sh, which runs probe.sh and exits non-zero if any target line says REACHABLE. Show it passing under --network none and failing on the default bridge. That is your CI check for "this task image has no egress".
    Solution 
    #!/usr/bin/env bash
# expect-none.sh: fail if probe.sh finds anything reachable
out=$(env -u http_proxy -u https_proxy bash /probe.sh "$@")
printf '%s\n' "$out"
if printf '%s\n' "$out" | grep -q 'REACHABLE'; then
  echo "POLICY VIOLATION: sandbox has egress" >&2; exit 1
fi
echo "policy ok: nothing reachable"
    $ docker run --rm --network none -v "$PWD:/w:ro" lt-tools bash -c 'cp /w/probe.sh /; bash /w/expect-none.sh >/dev/null; echo "exit=$?"'
exit=0
$ docker run --rm -v "$PWD:/w:ro" lt-tools bash -c 'cp /w/probe.sh /; bash /w/expect-none.sh >/dev/null; echo "exit=$?"'

exit=1

    env -u strips inherited proxy variables, so the check tests the network and not a proxy's 403s. The violation message goes to stderr, which is why it still shows with stdout discarded, while "policy ok" (stdout) does not.
