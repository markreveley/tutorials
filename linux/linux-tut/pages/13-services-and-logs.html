Services, init, and logs

This page answers audit question 5 — where are the logs? — for the two kinds of machine you will meet: a real VM, where systemd supervises long-running software and keeps a journal, and a container, where there is usually no supervisor and the only log is whatever the main process printed. When a rollout dies and the transcript doesn't say why, the answer is in one of these places.

Two worlds

A daemon or service is a program meant to run indefinitely in the background: a web server, the Docker daemon, your eval harness's worker. Something must start it at boot, restart it if it crashes, stop it cleanly, and keep what it prints. On a VM that something is the init system. In a container, by design, it is mostly nothing.

VM / bare metal container ─────────────── ───────── kernel boots runtime starts ONE command └─ PID 1 = systemd └─ PID 1 = your app (or a shell) ├─ ssh.service └─ its children ├─ docker.service ├─ eval-worker.service no supervisor, no restart policy └─ systemd-journald ◀── logs inside; nobody collects files in /var/log logs: journalctl, /var/log/* logs: PID 1's stdout + stderr, dmesg (kernel) captured OUTSIDE by the runtime → docker logs
Depth triage

systemd is a large system. For evals work, sort it like this:

The aim is to read a sandbox host's state and pull evidence from it, not to administer it.

On a VM: systemd

When a Linux machine boots, the kernel initialises hardware, mounts the root filesystem, and starts exactly one user-space program as PID 1. Everything else descends from it (page 9). On Ubuntu 24.04 that program is systemd, version 255: "a system and service manager for Linux operating systems" which, when run as PID 1, "acts as init system that brings up and maintains userspace services."[systemd]

systemd manages units, each described by a small text file. There are eleven unit types (service, socket, timer, mount, target…); you will deal almost only with .service units. Unit files installed by packages live in /usr/lib/systemd/system; ones an administrator writes go in /etc/systemd/system, which takes priority.[systemd]

Caveat — nothing in this section was run in the container lab

systemd needs to be PID 1 of a real machine, and Docker Desktop cannot provide that reliably. So this section shows no systemd output: commands are described from the manual, and the exercises that use them are marked VM lab. What the container lab can show is the failure you get when you try anyway — worth recognising when an agent tries it:

# systemctl status
System has not been booted with systemd as init system (PID 1). Can't operate.
Failed to connect to bus: Host is down
# journalctl --no-pager -n 3
No journal files were found.
-- No entries --

That is from a container where the systemd package had been installed by hand. In a stock ubuntu:24.04 image the commands do not exist at all (exit 127). An agent that answers "start the server" with systemctl start nginx in a container has made a Linux-fluency error; the fix is to run the program directly.

The systemctl working set

CommandWhat it does
systemctl status UNITShows "runtime status information … followed by most recent log data from the journal":[systemd] whether it is active or failed, its main PID, its cgroup's process tree, the last log lines. The first command to run on any service.
systemctl start | stop | restart UNITChange the running state now.
systemctl enable | disable UNITChange whether it starts at boot. enable "does not have the effect of also starting" the unit; add --now for both.[systemd]
systemctl list-units --type=service --state=runningWhat is running — audit question 1 at the service level.

The enable/start split is the classic trap: a worker you started by hand runs fine until the host reboots for a kernel update at 02:00, and the next morning's eval has half its capacity.

Reading a unit file

You will more often read unit files than write them. Here is one for a hypothetical eval worker (it passes systemd-analyze verify on systemd 255 once the user and paths it names exist): 

[Unit]
Description=Eval worker (pulls rollouts from the queue, drives sandboxes)
After=network-online.target docker.service
Wants=network-online.target

[Service]
User=evalworker
WorkingDirectory=/opt/eval-worker
EnvironmentFile=/etc/eval-worker/env
Environment=LC_ALL=C TZ=UTC
ExecStart=/opt/eval-worker/venv/bin/python -m worker --concurrency 8
Restart=on-failure
RestartSec=5
TimeoutStopSec=120

[Install]
WantedBy=multi-user.target
LineMeaningWhy an evals engineer reads it
ExecStart=The command run when the service starts.[systemd] An absolute path, no shell: no PATH lookup, no .bashrc.The real concurrency and flags, as opposed to what the README says.
User=The user the processes run as. For system services the default is root.[systemd]A missing User= means the harness is root on the sandbox host (page 7).
WorkingDirectory=The directory the process starts in; if unset, /.[systemd]Where relative paths in its config and its result files resolve.
Environment=, EnvironmentFile=The service's environment variables, inline or from a file of NAME=value lines.[systemd] Nothing from your login shell is inherited.Where the API keys are. systemd's manual itself warns that "environment variables are not suitable for passing secrets", for the reasons on page 11.
Restart=on-failureRestart after a non-zero exit, a fatal signal, or a timeout — not after a clean exit. The default is no.[systemd]A worker that crashes and silently restarts mid-run may re-queue or drop rollouts. Restarts show in the journal; look for them.

The manager-wide default is 90 s.[systemd]The same TERM-wait-KILL protocol as docker stop's 10 s (page 10). Rollouts in flight when the worker is restarted die with 137 or 143 — teardown, not model failure.
WantedBy=What enable hooks the unit into, so it starts at boot.

The journal

systemd starts every service "with standard output and standard error connected to the journal by default",[systemd] and the journal also collects kernel messages and classic syslog messages. One store, indexed by unit, time, and priority, read with journalctl:

FlagSelects
-u UNITOne service's output: journalctl -u eval-worker
--since, --untilA time window: --since "03:00" --until "03:30", --since yesterday, --since "2 hours ago"
-p errThat priority and more important (levels run emerg 0 … debug 7)
-kKernel messages only, current boot — where OOM kills are
-b, -b -1The current boot; the previous boot
-fFollow, like tail -f
--no-pager, -o jsonFor scripts and agents: journalctl opens a pager by default, which hangs a non-interactive caller

All of these are documented in journalctl(1).[systemd] Flags combine: journalctl -u docker -p warning --since "03:00" --no-pager. Reading the system journal requires root or membership of the systemd-journal or adm group.[systemd]

Pitfall — the journal that forgets, and the journal that drops

Persistence. On systemd 255 the Storage= setting defaults to auto: logs are kept on disk under /var/log/journal only if that directory exists; otherwise they live in /run/log/journal and are lost at reboot.[systemd] (Ubuntu 24.04's shipped /etc/systemd/journald.conf shows the commented default #Storage=auto; newer upstream releases default to persistent, so check the version you are on.) If a sandbox host rebooted after an incident, ls /var/log/journal tells you whether the evidence survived, and journalctl -b -1 retrieves it.

Rate limiting. By default journald drops a service's messages beyond 10,000 in 30 seconds.[systemd] A harness that logs every tool call of 200 concurrent rollouts to stdout can exceed that, and the missing lines will be the busy moments you wanted.

Text logs in /var/log, and the kernel's own log

Older than the journal, and still present, is the convention of plain text files under /var/log. Where the rsyslog package is installed (Ubuntu 24.04's archive marks it Priority: important), its shipped rules read: 

# grep -vE '^\s*(#|$)' /etc/rsyslog.d/50-default.conf
auth,authpriv.*			/var/log/auth.log
*.*;auth,authpriv.none		-/var/log/syslog
kern.*				-/var/log/kern.log
…

So: logins, sudo use and SSH attempts go to auth.log; kernel messages to kern.log; nearly everything else to syslog. If those files are absent the machine is journal-only, and journalctl is the whole story. Applications add their own subdirectories (/var/log/nginx, /var/log/apt).

Text logs would grow forever, so logrotate renames, compresses, and eventually deletes them on a schedule. Its per-package rules are short enough to read; this is what bounds how far back your evidence goes: 

# cat /etc/logrotate.d/dpkg
/var/log/dpkg.log {
	monthly
	rotate 12
	compress
	delaycompress
	missingok
	notifempty
	create 644 root root
}

Twelve monthly files for dpkg.log; the rsyslog-managed files above are rotated weekly and only four are kept. Rotated logs appear as syslog.1, syslog.2.gz… (zcat or zgrep reads the compressed ones).

Beneath all of this sits the kernel's own log, a fixed-size ring buffer in memory that dmesg "is used to examine or control."[dmesg(1)] This is where the OOM killer from page 12 writes its report. A default container may not read it — Docker's default capability set lacks CAP_SYSLOG, which the kernel can require for dmesg[Kernel: sysctl] — but from the host, or a container granted that one capability, the record is there: 

$ docker run --rm ubuntu:24.04 dmesg
dmesg: read kernel buffer failed: Operation not permitted
$ docker run --name lt-13-oom --memory 64m --memory-swap 64m ubuntu:24.04 tail /dev/zero
$ docker run --rm --cap-add SYSLOG ubuntu:24.04 bash -c 'dmesg | grep -oE \
    "oom-kill:constraint=[A-Z_]+|oom_memcg=[^,]+|Killed process [0-9]+ \([^)]+\)" | tail -3'
oom-kill:constraint=CONSTRAINT_MEMCG
oom_memcg=/docker/fbc75245f11e…
Killed process 72523 (tail)

The full lines are long (the grep -o keeps the three useful fragments): the record names the victim's command and its PID as the host sees it, its memory at death, and — in oom_memcg — the full 64-character ID of the container whose limit was hit. CONSTRAINT_MEMCG says a cgroup limit caused it, rather than the whole machine running out. On a VM the same lines are in journalctl -k and /var/log/kern.log. Two cautions: dmesg -T timestamps "could be inaccurate"[dmesg(1)] after a suspend, so match on container ID rather than the clock; and the ring buffer is shared by the whole machine — that same command also showed kills from other containers — so CAP_SYSLOG is not something to hand a sandbox.

In a container: stdout is the log

A stock task container has none of the above: 

$ docker run --rm ubuntu:24.04 bash -c 'command -v systemctl journalctl; echo "status=$?"; cat /proc/1/comm; ls /var/log'
status=1
bash
alternatives.log
apt
bootstrap.log
btmp
dpkg.log
faillog
lastlog
wtmp

No service manager, PID 1 is the command you gave, and /var/log holds only what the package manager wrote while the image was built. Docker's model is that a container's main process is its ENTRYPOINT/CMD, and that its log is that command's output: "By default, docker logs shows the command's STDOUT and STDERR."[Docker: logs] 

$ docker run -d --name lt-13-app ubuntu:24.04 bash -c 'echo "worker started";
    echo "WARN: retrying API call" >&2; echo "detail only in a file" > /var/log/app.log; sleep 300'
$ docker logs lt-13-app
WARN: retrying API call
worker started
$ docker logs lt-13-app 2>/dev/null
worker started
$ docker logs -t --since 10m lt-13-app
2026-09-21T21:09:04.753795677Z WARN: retrying API call
2026-09-21T21:09:04.753821302Z worker started

Three things to take from that, and a fourth that matters more:

  • The two streams are kept separate (page 4), and their relative order is not guaranteed — stderr arrived first here although it was written second. Use -t timestamps, not line order, across streams.
  • The line written to /var/log/app.log is not there. An application that logs to a file is invisible to docker logs; you must docker exec … cat or docker cp it out before the container is removed. (The official nginx image avoids this by symlinking its log files to /dev/stdout and /dev/stderr.[Docker: logs])
  • docker logs takes --since, --until, --tail N, -f and -t — the same questions journalctl answers.
$ docker exec lt-13-app bash -c 'echo "agent ran this via exec"'
agent ran this via exec
$ docker logs lt-13-app 2>&1 | grep -c "agent ran"
0
Key idea

docker logs records what PID 1 and the processes that inherited its stdout/stderr wrote. A process started by docker exec has its own streams, returned to whoever called exec. Since harnesses drive agents through exec (page 25), and the usual PID 1 of a task container is sleep infinity or tail -f /dev/null, the container log of a typical rollout is empty. The agent's commands and their output exist only in the harness's transcript.

Caveat — the default log driver never rotates

Docker's default logging driver is json-file, and "by default, no log-rotation is performed", which "can lead to disk space exhaustion";[Docker: logs] Docker recommends the local driver, or set limits per container: --log-opt max-size=10m --log-opt max-file=3 (check with docker inspect --format '{{json .HostConfig.LogConfig}}'). A container whose PID 1 is chatty — a server under test with debug logging, a build — can fill the sandbox host's disk over a long run, and then every rollout on that host starts failing with No space left on device (page 12).

The package logs as a forensic record

Two files in /var/log are useful in every container, because apt and dpkg write them whoever is supervising: /var/log/apt/history.log records each apt command line with its start and end time, and /var/log/dpkg.log records every package state change. Together they answer "what did the agent install, and when?": 

# grep -E '^(Start-Date|Commandline)' /var/log/apt/history.log | tail -4
Start-Date: 2026-09-21  11:11:30
Commandline: apt-get install -y -qq --no-install-recommends procps sudo locales tzdata python3
Start-Date: 2026-09-21  21:09:29
Commandline: apt-get install -y -qq --no-install-recommends rsyslog logrotate systemd
# awk '$3=="install"{print $1,$2,$4,$6}' /var/log/dpkg.log | tail -3
2026-09-21 21:09:29 logrotate:arm64 3.21.0-2build1
2026-09-21 21:09:29 ucf:all 3.0043+nmu1
2026-09-21 21:09:29 rsyslog:arm64 8.2312.0-3ubuntu9.3

Entries dated at image-build time are the image; entries dated during the rollout are the agent. The exact versions let you ask whether two rollouts of the "same" task ran against the same software (page 15). The limits of this evidence: both files are ordinary root-owned files, so an agent running as root can edit them; they see only apt and dpkg, not pip install or a curl | tar; and they vanish with the container. docker diff (page 22) is the broader tool.

Three evidence streams

In eval work

Every rollout leaves evidence in three places, written by three different observers, and each is blind to something the others see:

StreamSeesBlind to
Transcript (harness)Each command the agent ran, its stdout, stderr, exit code, durationWhy a process died; anything between tool calls; background processes; the box's state
Container state and logs (runtime)PID 1's output, exit code, OOMKilled, start and finish times, resource configWhat exec'd commands printed; anything after docker rm
Host logs (journal, kernel log)OOM kills with container ID, Docker daemon errors, disk-full and network errors, the harness worker's own crashes and restartsWhat the agent was trying to do

A rollout whose transcript ends in Killed is an observation. "The model wrote a memory-hungry solution", "the limit is too low for this task", and "the host ran out because 40 neighbours spiked" are hypotheses, and only the second and third streams discriminate between them. Design consequence: collect streams two and three before teardown — per rollout, save docker inspect output and docker logs next to the transcript, and keep host journals persistent and time-synchronised — because a harness that removes containers on completion destroys the evidence at the moment it becomes interesting. The sibling courses go further on this: Understanding LLM Evals, page 26 and Networking for LLM Evals, lesson 18. (Navigate, then design.)

In eval work

Harness workers and sandbox hosts are services. When 5% of last night's rollouts failed and the failures cluster between 03:00 and 03:20, the transcripts will show twenty different symptoms. The host shows one cause. On the sandbox host: journalctl --since "02:55" --until "03:25" -p warning --no-pager, then -u docker, then -k. Candidates worth checking first are mundane: a scheduled job saturating the disk, a package upgrade restarting the Docker daemon, the worker itself being OOM-killed and restarted by Restart=on-failure. Each is a hypothesis until a log line with a matching timestamp confirms it. Whatever it turns out to be, those rollouts are infrastructure failures: they count in scheduled, not in completed, and they are reported, not quietly re-run (page 12).

Check your understanding

Your team's harness runs each rollout in a container started with --rm, PID 1 is sleep infinity, and the agent is driven through exec calls. A reviewer of your benchmark paper asks: "Of the 412 failed rollouts, how many were environment failures rather than wrong answers?" Your colleague proposes grepping the transcripts for Killed and No space left and reporting that count. What is wrong with that as an answer, and what would you change before the next run?

Reveal the reasoning

What the grep can and cannot establish. It finds rollouts where an environment symptom reached the agent's stdout or stderr. That is a lower bound, and a biased one. It misses kills of background processes the agent never waited on, a harness timeout firing on a CPU-starved box (the transcript shows a timeout, not a cause), the Docker daemon restarting under the rollout, and anything that happened during grading. It also over-counts: Killed after the agent's own kill -9 or timeout -s KILL is not an environment failure.

What evidence would discriminate — and whether it still exists. For each failure you want State.OOMKilled, exit code and timing, and the host's kernel and Docker logs for that window. With --rm the container state is gone; docker logs would have been empty anyway (exec output never enters it). The host journal is the only remaining second source — if it is persistent (ls /var/log/journal) and has not rotated. journalctl -k for oom_memcg=/docker/<id> lines can be joined to rollouts only if the harness logged container IDs. Establish these facts before promising the reviewer a number.

What to report now, and change next. Report the grep count explicitly as a lower bound with its method, plus whatever the host journal adds; do not present it as "the" environment-failure count. For the next run: drop --rm in favour of inspect-then-remove; save docker inspect JSON and container ID per rollout; make the host journal persistent; record harness-initiated kills (timeouts, teardown) as such in the harness log, so that 137s can be attributed; and fix the accounting categories before looking at results.

Lab

Exercises 1–3 are container lab. Exercises 4–5 are VM lab: they need a machine whose PID 1 is systemd (the Ubuntu VM from page 1). VM-lab solutions describe what to look for rather than showing output, because this course only prints output its authors produced, and the authoring machine has no systemd host.

  1. Reproduce. Start docker run -d --name lt-13-x ubuntu:24.04 bash -c 'echo out; echo err >&2; echo hidden > /var/log/app.log; sleep 120'. Using only docker logs and redirection on your Mac, print just the stdout line, then just the stderr line. Where is "hidden"?
    Solution 
    $ docker logs lt-13-x 2>/dev/null
out
$ docker logs lt-13-x 2>&1 >/dev/null
err
$ docker exec lt-13-x cat /var/log/app.log
hidden

    docker logs replays the container's stdout on its own stdout and stderr on its own stderr, so page 4's redirections select between them. The file is only inside the container.

  2. Predict, then verify. In the same container, run docker exec lt-13-x bash -c 'echo "from exec"'. Will docker logs contain it? Then find a way, from inside an exec'd shell, to make a line appear in docker logs anyway. (Hint: page 9's /proc/PID/fd.)
    Solution 
    $ docker logs lt-13-x 2>&1 | grep -c "from exec"
0
$ docker exec lt-13-x bash -c 'echo "to pid1 stdout" > /proc/1/fd/1'
$ docker logs lt-13-x 2>&1 | tail -1
to pid1 stdout
$ docker rm -f lt-13-x

    The log is whatever is written to the pipe that PID 1's fd 1 and 2 point at. Opening /proc/1/fd/1 writes into that same pipe. This worked because the exec'd shell ran as root, the same user as PID 1. It is also a reminder that container logs are not tamper-proof evidence: a root agent can write anything into them.

  3. Eval task (container lab). In your lab container, as root, run apt-get update && apt-get install -y --no-install-recommends tree. Then, pretending you are auditing a finished rollout, answer from the logs alone: what command line installed software, at what time, and which package versions arrived?
    Solution 
    # grep -E '^(Start-Date|Commandline)' /var/log/apt/history.log | tail -2
# awk '$3=="install"{print $1,$2,$4,$6}' /var/log/dpkg.log | tail -3

    The first prints the last apt run's start time and exact command line; the second prints date, time, package and version for the most recent installs (the page shows real output of both for a different install). Compare the dates with the image's build-time entries at the top of the same files: everything after the container's start time is the "agent".

  4. VM lab — reproduce. On your Ubuntu VM: find the state of the SSH service, list running services, list failed units, and show the SSH service's log lines from the last hour without a pager.
    Solution

    systemctl status ssh — look for the Active: line (active (running) and a since-time), the Main PID, the CGroup tree, and the journal excerpt at the bottom, which should include your own login. systemctl list-units --type=service --state=running; systemctl --failed (expect zero units on a fresh VM); journalctl -u ssh --since "1 hour ago" --no-pager. Also run systemctl cat ssh (which prints the unit file) and find its ExecStart= and Restart= lines, and ls /var/log/journal to learn whether this VM's journal survives reboots. If a unit name differs on your distribution, systemctl list-units 'ssh*' finds it.

  5. VM lab — eval task. With Docker installed on the VM, run page 12's docker run --memory 64m --memory-swap 64m ubuntu:24.04 tail /dev/zero. Then, as if you had only the host and a rough time, find the kernel's record of the kill and extract the container ID from it. Which of the three evidence streams did you just use, and what would you need in the harness log to join it to a rollout?
    Solution

    sudo journalctl -k --since "10 minutes ago" --no-pager | grep -iE "oom-kill|Killed process" (or sudo dmesg -T | grep -i oom). Expect the two line shapes shown on this page: an oom-kill:constraint=CONSTRAINT_MEMCG … oom_memcg=/…/<id> line and a Memory cgroup out of memory: Killed process … (tail) line; on a systemd host the cgroup path is laid out differently from Docker Desktop's /docker/<id> but still contains the 64-character container ID, which docker ps -a --no-trunc confirms. That is the host-log stream. To join it to a rollout, the harness must have logged the container ID (or name) with the sample ID — otherwise you are matching on timestamps, which is a hypothesis, not evidence.
