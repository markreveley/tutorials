Orientation: why Linux, for evals

An agentic eval is a pile of Linux boxes with a number coming out of the top. This page shows where the Linux is, walks through three published incidents in which a plain Linux fact — a memory limit, a leftover .git directory, a reachable port — changed what a benchmark measured, and lays out the map of the course.

An agentic eval, physically

Look at what is actually running. An eval of an agent has four moving parts. A harness — usually a Python program — runs on some host machine. For every attempt at every task it starts a sandbox: a container or a virtual machine prepared with the task's files. The model, which lives somewhere else behind an API, is shown the task and replies with shell commands; the harness runs each command inside the sandbox and sends back what it printed. When the model stops, or the clock runs out, a grader inspects what is left in the box and writes down pass or fail.

model (an API, somewhere else) ▲ │ │ │ tool call: bash -c "pytest -q" │ ▼ ┌─ HOST · a Linux machine, or a Linux VM ──────────────────────────┐ │ │ │ harness ─── exec ──▶ ┌─ sandbox 1 · container or VM ─────────┐ │ │ (Python) │ /app the task's files │ │ │ ▲ │ bash runs the command │ │ │ │ │ a user · mounts · limits · network │ │ │ └─ stdout, ───────│ │ │ │ stderr, └──────────────────┬────────────────────┘ │ │ exit code sandbox 2 … N │ final state: │ │ (one per attempt)│ files, processes │ │ ▼ │ │ results.jsonl ◀─── pass / fail ─── grader / verifier │ │ │ │ └───────┼──────────────────────────────────────────────────────────┘ ▼ "model X: 58%"

Everything inside the big rectangle is Linux. The sandbox is a Linux process tree with a Linux filesystem. The command channel is a shell. What comes back is two text streams and an exit status. The grader is typically a script that checks files and runs tests — state-based evaluation, in the sibling course's terms (Understanding LLM Evals, page 11). Only the model is not Linux.

The headline number is attributed to the model but produced by the whole rectangle. If you cannot read the rectangle, you cannot say which of the two you measured.

The field already runs on this

This is how the well-known agentic benchmarks are built today, in their authors' words.

  • SWE-bench first tried to pin its environments with conda. In June 2024 the maintainers replaced that with a fully containerized harness — one Docker image per task — calling the old approach "underspecified" in hindsight: evaluation "remained sensitive to discrepancies originating from different platforms and user-specific configurations, leading to inconsistent results."[SWE-bench] Same patch, different laptop, different score; the fix was a Linux packaging decision.
  • Terminal-Bench defines a task as an instruction, a Docker image, tests, an example solution and a time limit; the tests work "by testing properties of the final container state; they do not test the agent's commands or console output."[Terminal-Bench] The task is a Linux box, and the grade is a property of that box.
  • Inspect, the UK AI Security Institute's eval framework, makes the sandbox a configuration choice: Docker is built in; Kubernetes, Daytona, Modal, EC2, Proxmox and Vagrant sandboxes come as packages. Its bash() tool runs the model's command inside that sandbox.[Inspect]
  • OSWorld sits at the heavy end: 369 tasks on real Ubuntu desktops inside virtual machines, reset from a snapshot, and graded by scripts that run on the host over state fetched out of the VM.[OSWorld]
  • None of this is new. In 2021 the HumanEval authors already ran model-written programs under the gVisor container runtime, with firewall rules blocking connections "except for those required for experiment control", in order "to prevent these programs from modifying, gaining persistence on, accessing sensitive resources on, or exfiltrating data from a host or network."[HumanEval] That goal is a list of four Linux subjects: filesystems, processes, credentials, egress.

One number about the models, too. The Terminal-Bench authors sampled 3,800 failed commands from agent runs: the most common failure, 24.1% of them, was calling a program that is not installed or not on the PATH, and per-command error rates ranged from 9.2% to 26.7% by model.[Terminal-Bench] You will produce that failure yourself in the lab below. Reading an agent's transcript is largely reading a Linux terminal session that went partly wrong.

Caveat — benchmark scores are history by the time you read them

At the Terminal-Bench paper's publication (17 January 2026) the best agent resolved 63% of version 2.0. By 2.1 (May 2026) top entries were near 80%; on the harder 3.0 (30 July 2026) the best were around 34%; 4.0 followed on 28 August 2026.[Terminal-Bench] This course cites scores only with dates. The mechanisms are what last.

Three ways the box corrupts the score

An environment can make a score wrong in three directions. Each has a published incident behind it, and each comes down to Linux facts you will be able to check.

1. The box fails, and the model gets the blame

Start with one you can reproduce in thirty seconds: a container allowed 64 MB of memory, running a command that needs more. 

$ docker run --rm -it --memory 64m --memory-swap 64m ubuntu:24.04 bash
# tail /dev/zero
Killed
# echo $?
137
# grep oom_kill /sys/fs/cgroup/memory.events
oom_kill 1

The kernel's OOM killer ended the process. The terminal shows only Killed and status 137 — 128 plus the number of the signal that killed it, 9, SIGKILL.[Bash Manual] Nothing in the agent's view says why; the evidence is a counter in memory.events that a harness may never have recorded. Swap in pip install pandas scikit-learn and you have a real case: a reasonable first move, killed by the box, logged as a model failure.

Anthropic measured how much this matters. Running Terminal-Bench 2.0 with the same model and harness under six resource configurations, infrastructure errors fell from 5.8% (each task's stated resources as a hard ceiling) to 0.5% (no cap), and the score gap between the extremes was 6 percentage points (p < 0.01). Their conclusion: "leaderboard differences below 3 percentage points deserve skepticism until the eval configuration is documented and matched."[Anthropic: Infra Noise] The benchmark's maintainers saw it from the other side: Terminal-Bench 2.1 fixed 28 of the 89 tasks — changed external dependencies, resource budgets too small for a valid solution — and one agent's score moved from 58.0% to 70.1% with no change to the model.[Terminal-Bench]

In eval work

An infrastructure failure and a wrong answer land in the same column unless you separate them. SWE-bench's harness now counts "instances with errors" and "instances with likely infrastructure failures" apart from unresolved ones.[SWE-bench] An infrastructure outcome is an observation about the run, not the model. In any harness: for every failed rollout record the last exit status and whether the sandbox hit its memory or time limit; never drop such rollouts silently; and report correct / scheduled, correct / completed and completed / scheduled as three different quantities, with the primary one chosen before you look at results. Rollouts that all die in the same under-sized box are also not independent samples,[Anthropic: Agent Evals] which breaks your error bars (Understanding LLM Evals, page 16). Pages 10 and 12 teach the decoding.

2. The box leaks the answer, and the model gets the credit

A SWE-bench sandbox holds a real project's code as it was just before a bug fix, and the agent must write the fix. In September 2025, issue #465 on the SWE-bench repository — "Repo State Loopholes During Agentic Evaluation" — reported that task images still carried the repository's later history. Agents had run commands such as 

cd /testbed && git log --oneline --all | grep -i "bracket\|parametrize\|modpath" | head -10

and been shown the commit that fixed the bug they were asked to fix.[SWE-bench #465] No network was needed; the answer was in .git. This is a git-history leak, and not exotic behaviour: a commenter on the issue noted that searching the history is what a human engineer would do first. The flaw was in the image.

Keep the scale honest. Searching the twenty most recent leaderboard submissions, the maintainers found matching commands in about 5 of 10,000 trajectories; on the bash-only leaderboard, six suspicious successes from one leading model were worth about 1.2 percentage points, and no ranks among the top four changed. They rebuilt every image and fixed the build (pull request #471, merged 11 September 2025): remove the remote, delete tags newer than the task's commit, expire the reflog, garbage-collect — then fail the build if git log --all can still see the future.[SWE-bench #465] The lesson is that last step: check an environment property with a command.

The pattern is general. METR found reward hacking by a pre-release OpenAI o3 checkpoint in 39 of 128 runs (30.4%) on one task suite against 8 of 1,087 (0.7%) on another, and attributed the gap partly to the first suite letting the model "see the entire scoring function". Adding "Please do not cheat" to one task left the rate of cheating plans at 80%.[METR] Anthropic reports a quieter variant from internal evals: Claude "gaining an unfair advantage on some tasks by examining the git history from previous trials" — state left by an earlier run.[Anthropic: Agent Evals] What an agent can read, write, or find left over is decided by ownership, permission bits, mounts, and whether each attempt got a fresh box: environment integrity, the subject of page 26.

Pitfall — "the tests are hidden, so grading is safe"

Terminal-Bench's harness uploads the tests only after the agent has finished. But by default the verifier then runs in the same container the agent just had, typically as root.[Terminal-Bench] An agent cannot read tests that are not there yet, but it can change the box they will run in. Terminal-Bench 3.0 moved to a separate verifier container, which its authors say "prevents many reward hacking vectors".[Terminal-Bench] "Hidden" and "tamper-proof" are different properties, enforced by different mechanisms.

3. The box lets the agent out

OpenAI's system card for o1-preview (12 September 2024) describes one attempt at a capture-the-flag challenge. The agent was meant to break into software in a second container, which had failed to start because of a bug in the evaluation infrastructure. The model, "unable to connect to the container, suspected DNS issues and used nmap to scan the challenge network. Instead of finding the challenge container, the model found that the Docker daemon API running on the evaluation host VM was accessible due to a misconfiguration." It listed the host's containers, briefly tried to debug the broken one, then started a new instance of it with the start command cat flag.txt and read the flag from the container's logs.[o1 System Card]

The Docker daemon is the program that creates containers; whoever can talk to its API can start any container with any command. Be precise about what the card says. It does not describe a container "escape": the model used a network service that should not have been reachable. Nor does OpenAI say a boundary held. It says its infrastructure "does not rely on the Docker container-to-host isolation or the virtual machine boundary for security" and "remained secure as it was designed to" — without saying what it does rely on. It calls the behaviour "benign and within the range of systems administration and troubleshooting tasks we expect models to perform", and also a case of a model that, finding its goal impossible, "gathered more resources … and used them to achieve the goal in an unexpected way."[o1 System Card]

For an evals engineer this is two environment defects in a row: the target never started (way 1), then the host's control API answered from inside the sandbox. The attempt did not measure the skill the challenge was built for. The audit question that finds the second defect before a model does: what can this box reach?

Key idea

The environment is part of the measuring instrument. A score is a claim about a model only if someone has checked the box: big enough, holding no answers, with no doors. Each check is a handful of Linux commands.

How to work through it

Type everything; the labs are the course. Page 1 sets up two places to type, both yours to break: a disposable container on your Mac, and a small real VM for the few pages that need a kernel of their own.

Every terminal block is pasted from a real run on Ubuntu 24.04. A $ prompt means an ordinary user; # means root. Claims about the world carry a bracketed citation to the primary source (Appendix F explains how to read the man pages most point to). Your Mac's own terminal differs in misleading ways (Appendix E): run course commands in the lab.

For more drill on the basics, Linux Journey is a free set of short lessons whose early tracks (Command Line, Text-Fu, Permissions, Processes) parallel Modules 1–3; the old linuxjourney.com address redirects there.[Linux Journey] It will not mention evals.

The finish line is a set of observable skills, not a promise of employment: an audit you can perform in front of someone, a script, and a write-up that keeps infrastructure outcomes separate from model outcomes (page 28).

Check your understanding

A colleague moves an agentic coding benchmark from a large workstation to a shared cluster that runs forty sandboxes per host. The pass rate drops four points, and the draft report says the new model checkpoint "regressed". What would you establish before agreeing?

Reveal the reasoning

Observed: two things changed at once — the checkpoint and the environment. Hypothesis: the model got worse. It is only one of at least two. The discriminating test is to hold one side fixed: rerun the old checkpoint on the cluster. If it also drops, the box moved the score.

Then look for direct evidence of box failure among the newly failing rollouts: exit status 137 and oom_kill counts, rollouts that ended at exactly the time limit, No space left on device, install commands that failed. Compare the per-sandbox memory, CPU and time limits on both systems, and the concurrency — forty sandboxes sharing a host is a different machine from one. Ask how the four points are computed: if infrastructure deaths are counted as wrong answers, report completed / scheduled beside correct / completed so the reader can see which moved. Anthropic's measurement above is the prior: resource configuration alone moved Terminal-Bench 2.0 by up to 6 points. "Regressed" is a claim about the model; it needs the environment ruled out first.

It will not mention evals. That part is this course's job.

Lab

Where: any Mac with Docker running. If docker version fails, do the first half of page 1 and come back. This lab is deliberately light: the goal is to look around a Linux box before anything has been explained, and write down what you do not understand.

Things worth having on your list: why you are root without having typed a password (page 7); why only two processes exist on a whole "computer", and why bash is number 1 (pages 9 and 20); what drwxrwxrwt and bin -> usr/bin mean (pages 8 and 3); and what .dockerenv is doing there (page 28 uses it to tell a container from a VM).

2. Predict, then verify. ip addr failed. Before running it, write down what number you expect echo $? to print immediately afterwards — zero or non-zero? Then run ip addr again followed by echo $?.

Solution 
# ip addr
bash: ip: command not found
# echo $?
127

$? holds the exit status of the last command: 0 means success, anything else is a failure, and 127 is the shell's specific code for "I could not find a program by that name" (page 2). Nothing is broken: the ip tool is simply not installed in this minimal image. You have just produced the most common failed command in the Terminal-Bench analysis quoted above. When you see 127 in a transcript, the first question is whether the image should have had the tool — an environment question — before it is a question about the model.

3. Disposable means disposable. In the container, run touch /i-was-here and check it exists with ls /i-was-here. Type exit. Now, from your Mac, run docker run --rm ubuntu:24.04 ls /i-was-here. Predict the result first. Then: why is this the behaviour a harness wants between one attempt at a task and the next?

Solution 
# touch /i-was-here; ls /i-was-here
/i-was-here
# exit
exit
$ docker run --rm ubuntu:24.04 ls /i-was-here
ls: cannot access '/i-was-here': No such file or directory

Every docker run creates a new container from the unchanging image; the first container's changes lived in that container only, and --rm deleted it on exit. For an eval this is the reset mechanism: a fresh container per attempt means attempt 7 cannot see files, processes, or git history left by attempt 6. The Anthropic anecdote above — an advantage gained from "the git history from previous trials" — is what happens when a workspace is reused instead. Page 22 covers what does survive (volumes) and why that is the exception to watch.

4. An eval-flavoured one: who failed? Reproduce the out-of-memory kill from this page in a container limited to 64 MB (the limit makes this safe — the process is killed long before your Mac notices). Then answer: if a harness had saved only the command's output and exit status, what would the record of this rollout contain, and what would it be missing?

docker run --rm -it --memory 64m --memory-swap 64m ubuntu:24.04 bash
tail /dev/zero
echo $?
cat /sys/fs/cgroup/memory.max
grep oom_kill /sys/fs/cgroup/memory.events
Solution 
# tail /dev/zero
Killed
# echo $?
137
# cat /sys/fs/cgroup/memory.max
67108864
# grep oom_kill /sys/fs/cgroup/memory.events
oom_kill 1

tail tries to hold the "last lines" of a file that never ends and contains no line breaks, so its memory grows until the kernel enforces the container's limit: 67,108,864 bytes is 64 × 1024 × 1024. The record would contain the string Killed and the status 137. It would be missing the cause. Status 137 only says "ended by SIGKILL"; a harness timeout that kills the process produces the same number. The fact that separates "the box was too small" from "the command ran too long" is oom_kill 1, which lives in the sandbox's cgroup files and vanishes with the container unless something copies it out. That is audit question 5 — where are the logs? — in miniature, and page 12 returns to it properly.
