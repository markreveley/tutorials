Module 5 · Networking for Sandboxes

DNS, HTTP, and TLS

Between "a hostname" and "a response" sit three layers, and each fails with its own signature. This page shows where each layer lives on a Linux box — the resolver files, the trust store, the proxy variables — and how to make curl tell you which one broke, so that a network failure in a transcript gets charged to the right account.

The concepts themselves — what DNS is, what a TLS handshake does, what an HTTP status means — are taught in the sibling course Networking for LLM Evals (DNS, TLS, HTTP). Here each gets a sentence, and the words go to the Linux side: which files decide the answer, which command reads them, and what a broken one looks like from inside a sandbox.

curl https://example.com/ │ 1. NAME libc resolver ─ /etc/nsswitch.conf ─┬─ files: /etc/hosts │ └─ dns: /etc/resolv.conf ─▶ nameserver 2. CONNECT TCP to 104.20.23.154:443 (routes, firewalls: pages 16, 17, 19) │ 3. TLS handshake; verify certificate against /etc/ssl/certs/ca-certificates.crt │ 4. HTTP > GET / … < HTTP/2 200 (with https_proxy set, steps 1–2 aim at the PROXY, which does the rest)

Layer 1: how a name becomes an address on this box

DNS is the distributed database that maps names to addresses. But programs on Linux do not "do DNS"; they call the C library's resolver, and the resolver reads a small stack of files to decide where to look. The first is /etc/nsswitch.conf, whose hosts: line lists sources in query order, tried "until a result is found".[nsswitch.conf(5)] Ubuntu 24.04 ships files dns: first the hosts file /etc/hosts (lines of address name), then DNS, using the servers named in /etc/resolv.conf — up to three nameserver lines, tried in order, each with a default timeout of 5 seconds and 2 attempts.[resolv.conf(5)] That last number explains a transcript pattern: with an unreachable nameserver, every lookup stalls for around ten seconds before failing. 

# grep ^hosts /etc/nsswitch.conf
hosts:          files dns
# cat /etc/resolv.conf
# Generated by Docker Engine.
…
nameserver 192.168.65.7

# Based on host file: '/etc/resolv.conf' (legacy)

That is a container on Docker's default bridge: Docker wrote the file, copying the host's nameserver (192.168.65.7 is Docker Desktop's; on a Linux host you will see the host's upstream). On a user-defined network the file is different: 

$ docker network create lt-net
$ docker run -d --rm --name lt-db --network lt-net lt-tools sleep 300
$ docker run --rm --network lt-net lt-tools bash -c 'cat /etc/resolv.conf; getent hosts lt-db'
…
nameserver 127.0.0.11
options ndots:0
…
# ExtServers: [host(192.168.65.7)]
172.19.0.2      lt-db

127.0.0.11 is Docker's embedded DNS server. It answers for container names on that network and "forwards external DNS lookups to the DNS servers configured on the host".[Docker: networking] On the default bridge the same getent hosts lt-db prints nothing and exits 2: containers there "can only access each other by IP addresses".[Docker: bridge] (lt-tools is a small image with curl, dig and ip baked in; the lab builds it.) On a real Ubuntu VM you will meet a third address, 127.0.0.53: the local stub of systemd-resolved, with the true upstream servers listed in /run/systemd/resolve/resolv.conf.[systemd-resolved(8)] Three addresses, one reading habit: cat /etc/resolv.conf tells you who this box asks.

Two tools that answer different questions

getent asks the C library, so it walks the whole nsswitch path, as your programs do. dig speaks DNS directly to the servers in resolv.conf and never looks at /etc/hosts.[dig(1)] Put a name only in the hosts file and they disagree: 

# echo "203.0.113.8 grader.internal" >> /etc/hosts
# getent hosts grader.internal
203.0.113.8     grader.internal
# dig grader.internal | grep -E 'status|SERVER'
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 20394
;; SERVER: 192.168.65.7#53(192.168.65.7) (UDP)
# dig +short grader.internal; echo "exit=$?"
exit=0

Three lines of dig output carry most of the information. status: is the server's verdict: NOERROR, NXDOMAIN (the name does not exist) or SERVFAIL (the server could not find out).[RFC 1035] The ANSWER SECTION holds the records. SERVER: says who answered — the quickest way to learn which resolver a box really uses. Note the exit status: dig returns 0 for any DNS response, "including NXDOMAIN", so dig name && … in a script tests nothing. getent exits 2 when a name is not found.

Pitfall

getent hosts can appear to ignore /etc/hosts. It tries an IPv6 lookup first;[getent(1)] if your override has only an IPv4 line and the name has real IPv6 records, the hosts file has nothing to offer for that family and DNS answers instead: 

# echo "203.0.113.7 example.com" >> /etc/hosts
# getent hosts example.com
2606:4700:10::6814:179a example.com
2606:4700:10::ac42:93f3 example.com
# getent ahosts example.com | head -1
203.0.113.7     STREAM example.com
# curl -sv --connect-timeout 2 http://example.com/ 2>&1 | grep Trying
*   Trying 203.0.113.7:80...

getent ahosts uses getaddrinfo(3), the call curl and most modern programs make. Use it as the faithful "what will my program get?" check.

In eval work · navigate

A multi-container task fails with Could not resolve host: db. Before blaming the agent, read /etc/resolv.conf in the sandbox. nameserver 127.0.0.11 means a user-defined network where service names should resolve, so the peer is probably not running. A copied host nameserver means the default bridge, where names never resolve and the environment is misbuilt. Either way it is a fact about the run, not the model. And check the other direction: a sandbox that can resolve arbitrary external names has a working channel to the outside even if HTTP is blocked, because the embedded resolver makes lookups on the container's behalf, and data can be carried in DNS queries themselves.[MITRE T1071.004] It depends on the setup: on the --internal network tested for page 19, external names returned SERVFAIL. Test it; don't assume.

Layers 2–4 in one screen: reading curl -v

HTTP is a request (method, path, headers) answered by a response (status code, headers, body); TLS wraps it in an encrypted, authenticated channel. curl -v narrates every layer. Its line prefixes: * is curl's commentary, > a header sent, < a header received.[curl(1)] 

$ curl -v -o /dev/null https://example.com
* Host example.com:443 was resolved.                  # 1 NAME: done
* IPv6: 2606:4700:10::6814:179a, 2606:4700:10::ac42:93f3
* IPv4: 104.20.23.154, 172.66.147.243
*   Trying 104.20.23.154:443...
* Connected to example.com (104.20.23.154) port 443   # 2 CONNECT: TCP is up
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
*  CAfile: /etc/ssl/certs/ca-certificates.crt        # 3 TLS: the trust store
…

*  subject: CN=example.com
*  start date: Jul 29 22:10:08 2026 GMT
*  expire date: Oct 27 22:17:21 2026 GMT

*  issuer: C=US; O=SSL Corporation; CN=Cloudflare TLS Issuing ECC CA 3

When a request fails, the last layer that did print is your evidence: "was resolved" but no "Connected" is a connection problem, not DNS. Status codes come in five classes — 1xx informational, 2xx successful, 3xx redirection, 4xx client error, 5xx server error.[RFC 9110] The working set of flags is short: -sS (silent, but still show errors — -s alone mutes error messages too), -f (turn HTTP ≥ 400 into exit 22), -L (follow redirects), -o FILE, -I (headers only), -m SECONDS (cap the whole transfer), --connect-timeout (cap only DNS + TCP + TLS), and -w '%{http_code}\n' to print just the status.

curl's exit code as a layer decoder

An agent's transcript usually shows you only the error line and the exit status. curl's exit codes map onto the layers, which makes them a decoder. Every row below was produced for real in an ubuntu:24.04 container; the meanings are from the man page.[curl(1)]

Caveat

The decoder is a first cut, not a verdict. Code 7 cannot distinguish "nothing is listening" from "a firewall rejected me"; 28 cannot distinguish a dropped packet from a slow server; and any proxy variable in the environment moves 5 and 7 from the target to the proxy. Treat the code as the observation, the cause as a hypothesis, and name the test that would separate the candidates: curl -v to see the last layer reached, env | grep -i proxy, ip route get ADDRESS (page 16). The method is the subject of Networking for LLM Evals, lesson 17. And never leave out a timeout: without -m, a dropped connection holds a tool call for minutes (page 10; lesson 11).

TLS on the box: the trust store

TLS promises three things about a channel: the server is authenticated, the contents are confidential, and they arrive unmodified.[RFC 8446] Authentication normally rests on a certificate: the server presents a signed statement binding its name to its key, and curl checks that the name matches the URL and that the signature chains to a certificate authority (CA) "present in the cert store".[curl(1)] On Debian and Ubuntu that store is a file, /etc/ssl/certs/ca-certificates.crt, generated by update-ca-certificates from the ca-certificates package.[update-ca-certificates(8)] The ubuntu:24.04 base image does not contain it, and the Dockerfile idiom --no-install-recommends keeps it out: 

# apt-get update -qq && apt-get install -y --no-install-recommends curl
…
Recommended packages:
  ca-certificates krb5-locales libldap-common publicsuffix libsasl2-modules
…
# curl -sS -o /dev/null https://example.com; echo "exit=$?"
curl: (77) error setting certificate file: /etc/ssl/certs/ca-certificates.crt
exit=77
# curl -sS -o /dev/null -w '%{http_code}\n' http://example.com
200
# apt-get install -y ca-certificates
…
Updating certificates in /etc/ssl/certs...
121 added, 0 removed; done.
# curl -sS -o /dev/null -w '%{http_code}\n' https://example.com
200

Exit 77 is "I have no list of authorities at all". Exit 60 is different: a store exists but does not vouch for this server. Both halves of "not valid" are about dates as well as issuers, which is why a wrong clock breaks HTTPS. Here faketime lies to curl about the date: 

$ curl -sS -o /dev/null https://self-signed.badssl.com/
curl: (60) SSL certificate problem: self-signed certificate
$ faketime '2031-01-01 00:00:00' curl -sS -o /dev/null https://example.com
curl: (60) SSL certificate problem: certificate has expired
$ faketime '2020-01-01 00:00:00' curl -sS -o /dev/null https://example.com
curl: (60) SSL certificate problem: certificate is not yet valid
Pitfall

curl -k makes all of these "work" by skipping verification entirely — the man page says it "makes the transfer insecure". In an environment it hides the real defect (a missing package, a skewed clock in a restored VM snapshot), and the next tool — pip, git, apt — fails anyway. Fix the store: install ca-certificates; for a private CA, drop its PEM file with a .crt extension into /usr/local/share/ca-certificates/ and run update-ca-certificates.[update-ca-certificates(8)]

Proxies: the variables, the tunnel, the refusals

A proxy is a server that makes requests on a client's behalf (lesson 12 there covers the species). On Linux, clients are pointed at one by environment variables, inherited like any others (page 11), and the rules have sharp edges:[Everything curl]

  • https_proxy / HTTPS_PROXY, ALL_PROXY: either case works; lowercase wins if both are set.
  • http_proxy is lowercase only. curl ignores HTTP_PROXY, because web servers running CGI scripts turn a client's Proxy: header into exactly that variable.
  • NO_PROXY is a comma-separated list of hosts and domains to reach directly, and it overrides even an explicit -x.[curl(1)]
$ http_proxy=http://127.0.0.1:3128 curl -sS -o /dev/null http://example.com/   # nothing listens there
curl: (7) Failed to connect to 127.0.0.1 port 3128 after 0 ms: Couldn't connect to server
$ HTTP_PROXY=http://127.0.0.1:3128 curl -sS -o /dev/null -w '%{http_code}\n' http://example.com/
200                                                  # uppercase ignored: went direct
$ NO_PROXY=example.com curl -sS -o /dev/null -w '%{http_code}\n' -x http://127.0.0.1:3128 https://example.com/
200                                                  # NO_PROXY beat -x

These are curl's rules; other clients read the same variables with their own variations, so test the client the task actually uses. For HTTPS, the client asks the proxy to open a tunnel with the CONNECT method, after which the proxy does "blind forwarding of data, in both directions".[RFC 9110] The proxy sees the hostname and port, not the contents — enough to enforce an allowlist. Below, a sandbox on a network with no route out, plus a small filtering proxy allowing only example.com and pypi.org (built on page 19): 

$ export https_proxy=http://proxy:8888 http_proxy=http://proxy:8888
$ curl -sS -m 10 -o /dev/null -w '%{http_code}\n' https://pypi.org/simple/
200
$ curl -sS -m 10 -o /dev/null https://github.com/; echo "exit=$?"
curl: (56) CONNECT tunnel failed, response 403
exit=56
$ curl -sv -m 10 -o /dev/null https://github.com/ 2>&1 | grep -E '^[<>] '
> CONNECT github.com:443 HTTP/1.1
> Host: github.com:443
< HTTP/1.1 403 Filtered
$ curl -sS -m 10 -o /dev/null -w '%{http_code}\n' http://github.com/    # plain HTTP: no tunnel
403
$ getent hosts github.com; echo "exit=$?"
exit=2

The same refusal shows up two ways: for HTTPS as exit 56 with the 403 inside the error text, for plain HTTP as an ordinary 403 with exit 0. And the sandbox could not resolve github.com itself — the proxy does the lookups. Other proxy-made answers to recognise: 407 (the client must authenticate to the proxy) and 502 / 504 (the proxy could not get a usable or timely answer upstream).[RFC 9110] A proxy that wants to read HTTPS contents must terminate TLS itself and present its own certificate. Since clients verify against the local store, that only works if the proxy's CA has been installed in the sandbox; otherwise every HTTPS request fails the way an untrusted issuer does, with exit 60.

In eval work · discuss and design

"No direct route, plus an allowlisting proxy" is the standard controlled- egress design, and you must know its signatures on sight: pip install works while git clone https://github.com/… dies with CONNECT tunnel failed, response 403. That is the policy working, not a flaky network and not a model failure. Whether it is fair depends on the task: if the task can only be solved with a GitHub download, the environment makes it impossible and the item is invalid. Relatedly, an agent given a web-search tool and an agent with raw network in its sandbox are different threat models: the tool's requests leave from the harness or the model provider, outside any rule you set on the container (page 25).

In eval work · failure accounting

Exit 77 in a task image, Could not resolve host during a registry outage, a 503 from a package mirror: each is an observation about the run. Record it as an infrastructure failure with the layer attached, never as "incorrect", and never by silently dropping the sample. Report correct / scheduled, correct / completed and completed / scheduled as separate numbers, and choose the primary one before looking. A benchmark whose score moves when PyPI has a bad afternoon is measuring PyPI; the durable fix is an image that needs no network at run time (page 15) — see also lesson 22, boundaries and validity.

Check your understanding

Overnight, a 500-task run's pass rate fell from 46% to 31%. A colleague greps the transcripts, finds SSL certificate problem in about a hundred of them, and proposes re-running those tasks with PIP_TRUSTED_HOST set and curl aliased to curl -k, "since the model obviously can't be blamed for certificates". What do you say?

Reveal the reasoning

Observed: a score drop and an error string in ~100 transcripts. Not yet observed: which certificate problem, where, or whether those 100 tasks account for the drop. The colleague is right about the accounting and wrong about the fix. First establish the exact message: "has expired" / "not yet valid" point at the clock (run date in a fresh sandbox — a VM restored from a snapshot can wake up with a stale clock); "unable to get local issuer" or "self-signed certificate in chain" point at an intercepting proxy introduced overnight (read the issuer: line in curl -v); exit 77 points at a rebuilt image that lost ca-certificates. Each has a different discriminating test and a different owner. Then check the join: did the failing-TLS tasks pass before, and do the other 400 score as yesterday? If so the drop is infrastructure. Disabling verification changes the environment under test (and would let any interceptor rewrite downloads), so the rerun would not be the same benchmark. Fix the cause, rerun the affected tasks under the unchanged configuration, and report the first run's ~100 as infrastructure failures: completed / scheduled was about 80%, stated alongside the score rather than folded into it.

Lab

Container lab (page 1), as root in lt-lab, which has curl and dnsutils installed. Exercise 3 uses a second, throwaway container started from your Mac.

  1. Reproduce. Add 203.0.113.8 grader.internal to /etc/hosts. Resolve the name with getent hosts, with dig +short, and with dig | grep status. Which of the three would a Python program agree with, and why?
    Solution 
    # echo "203.0.113.8 grader.internal" >> /etc/hosts
# getent hosts grader.internal
203.0.113.8     grader.internal
# dig +short grader.internal
# dig grader.internal | grep status
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 20394

    Programs call the C library, which follows nsswitch.conf (files before dns), so they agree with getent. dig only speaks DNS, and DNS has never heard of the name.

  2. Predict, then verify. Write down the exit code you expect from each, then run them with ; echo "exit=$?" appended: curl -sS -o /dev/null https://no-such-host.invalid/, curl -sS -o /dev/null http://127.0.0.1:81/, curl -sS -o /dev/null --connect-timeout 3 http://192.0.2.1/, curl -sS -o /dev/null https://example.com:80/, curl -sS -o /dev/null https://example.com/nope, and the last one again with -f.
    Solution 
    curl: (6) Could not resolve host: no-such-host.invalid                                    exit=6
curl: (7) Failed to connect to 127.0.0.1 port 81 after 0 ms: Couldn't connect to server   exit=7
curl: (28) Failed to connect to 192.0.2.1 port 80 after 3012 ms: Timeout was reached      exit=28
curl: (35) OpenSSL/3.0.13: error:0A00010B:SSL routines::wrong version number              exit=35
(no message: the 404 page was fetched successfully)                                       exit=0
curl: (22) The requested URL returned error: 404                                          exit=22

    The fifth is the one people get wrong: to curl, an HTTP error is a successful transfer unless you pass -f. A setup script that downloads with plain curl -o will happily save a 404 page as model.bin.

  3. Break and fix the trust store. From your Mac, start docker run --rm -it ubuntu:24.04 bash. Install curl with --no-install-recommends, request https://example.com, note the exit code, then fix the image properly and confirm.
    Solution 
    # apt-get update -qq && apt-get install -y --no-install-recommends curl
# ls /etc/ssl/certs
ls: cannot access '/etc/ssl/certs': No such file or directory
# curl -sS -o /dev/null https://example.com; echo "exit=$?"
curl: (77) error setting certificate file: /etc/ssl/certs/ca-certificates.crt
exit=77
# apt-get install -y ca-certificates
# ls -l /etc/ssl/certs/ca-certificates.crt
-rw-r--r-- 1 root root 182140 Sep 21 21:19 /etc/ssl/certs/ca-certificates.crt
# curl -sS -o /dev/null -w '%{http_code}\n' https://example.com
200

    In a Dockerfile the fix is one word: add ca-certificates to the install line. 77, not 60: the file is absent, rather than present and unconvinced.

  4. Eval-flavoured: a pre-flight layer check. Before a run starts, you want each sandbox to report whether the endpoints a task needs are usable, and if not, at which layer they fail — so the failure is logged as infrastructure before any model is involved. Write layer.sh URL… (under 25 lines, shellcheck-clean) that prints one line per URL with curl's exit code and the layer. It must never hang.
    Solution 
    #!/usr/bin/env bash
# layer.sh URL... : say which layer a request died at, from curl's exit code
for url in "$@"; do
  code=$(curl -sS -f -o /dev/null -m 10 --connect-timeout 3 -w '%{http_code}' "$url" 2>/dev/null)
  rc=$?
  case $rc in
    0)     layer="ok (HTTP $code)" ;;
    5|6)   layer="name resolution (5 = the proxy's name, 6 = the host's)" ;;
    7)     layer="connect: refused, rejected, or no route (or the proxy is down)" ;;
    28)    layer="timeout: dropped packets or a slow transfer" ;;
    35)    layer="TLS handshake" ;;
    60|77) layer="TLS trust (60 = issuer/name/date not accepted, 77 = no CA file)" ;;
    22)    layer="HTTP status $code" ;;
    56)    layer="receive failure (a proxy refusing CONNECT lands here)" ;;
    *)     layer="other: see EXIT CODES in man curl" ;;
  esac
  printf '%-40s exit=%-3s %s\n' "$url" "$rc" "$layer"
done
    # bash layer.sh https://example.com/ https://example.com/nope https://no-such-host.invalid/ \
    http://127.0.0.1:81/ http://192.0.2.1/ https://self-signed.badssl.com/ https://example.com:80/
https://example.com/                     exit=0   ok (HTTP 200)
https://example.com/nope                 exit=22  HTTP status 404
https://no-such-host.invalid/            exit=6   name resolution (5 = the proxy's name, 6 = the host's)
http://127.0.0.1:81/                     exit=7   connect: refused, rejected, or no route (or the proxy is down)
http://192.0.2.1/                        exit=28  timeout: dropped packets or a slow transfer
https://self-signed.badssl.com/          exit=60  TLS trust (60 = issuer/name/date not accepted, 77 = no CA file)
https://example.com:80/                  exit=35  TLS handshake

    rc=$? must be the very next command after the substitution (page 6). The two timeouts are what make it safe to run in a harness. The wording of each verdict keeps the decoder's ambiguity visible instead of pretending to a diagnosis.
