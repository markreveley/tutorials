Resources, limits, and the OOM killer

A sandbox has a budget of CPU, memory, disk, and process slots, and each one fails in its own way when it runs out: a kill, a slowdown, an error message. This page teaches you to read the budget, recognise each kind of exhaustion in a transcript, and prove — with evidence rather than an exit code — that the box failed and not the model.

Four resources, two kinds of limit

Everything a program consumes falls into four buckets. Each has a command that reads it and a characteristic way of failing.

ResourceRead it withWhen it runs out
CPUnproc, uptime, topNothing dies. Everything is slow, then something times out.
Memoryfree -h, topThe kernel kills a process: Killed, exit 137.
Disk (space and inodes)df -h, df -i, du -shWrites fail: No space left on device.
Process and file slotsulimit -a, pids.maxCreation fails: Resource temporarily unavailable, Too many open files.

Limits on these come from two separate mechanisms, and confusing them is the root of most mistakes on this topic.

An rlimit ("resource limit", what ulimit shows) is a per-process attribute. Each has a soft value, which the kernel enforces, and a hard value, which is the ceiling for the soft one; an unprivileged process can raise its soft limit up to the hard limit and can lower its hard limit, irreversibly.[getrlimit(2)] Rlimits are inherited across fork and exec like the environment on page 11, and like the environment each child gets its own copy: a limit of 64 open files means 64 each, not 64 shared.

A cgroup ("control group") limit is a shared budget for a whole group of processes — in practice, a whole container. Memory used by any process in the group counts against the one memory.max. This is the mechanism behind docker run --memory, and page 21 covers it fully. Here you only need to read it. Note that memory has no usable rlimit at all: the one that sounds right limits virtual address space, not real memory,[getrlimit(2)] so real memory caps are always cgroups.

Reading the budget — and the trap in it

Start a container with explicit limits. (lt-12-base:1 is ubuntu:24.04 plus the procps and python3 packages; your page-1 lab image works the same.) By default a container "has no resource constraints and can use as much of a given resource as the host's kernel scheduler allows",[Docker: run] so the flags are the policy: 

$ docker run -d --name lt-12-lim --memory 256m --memory-swap 256m --cpus 1.5 \
    --pids-limit 100 lt-12-base:1 sleep infinity
$ docker exec -it lt-12-lim bash
# nproc
10
# free -h
               total        used        free      shared  buff/cache   available
Mem:           7.7Gi       985Mi       4.1Gi       980Ki       2.8Gi       6.7Gi
Swap:          1.0Gi          0B       1.0Gi
# uptime
 21:02:39 up  8:42,  0 user,  load average: 1.01, 0.37, 0.24

Ten CPUs and 7.7 GiB — in a container that was given one and a half CPUs and 256 MiB. These tools read /proc, and /proc/meminfo, /proc/loadavg and the CPU count describe the machine (here, Docker Desktop's Linux VM), not the container's cgroup. Docker's documentation warns about exactly this for free.[Docker: run] The real budget is in the cgroup filesystem, mounted read-only at /sys/fs/cgroup: 

# cd /sys/fs/cgroup
# cat memory.max memory.current memory.peak
268435456
2883584
5304320
# cat cpu.max
150000 100000
# cat pids.max pids.current
100
3

memory.max is the hard limit in bytes (268435456 = 256 MiB); memory.current is what the group uses now and memory.peak the most it has ever used.[Kernel: cgroup-v2] cpu.max reads "quota period" in microseconds: the group may consume up to 150 ms of CPU time in every 100 ms window, i.e. 1.5 CPUs.[Kernel: cgroup-v2] An unlimited container shows max in place of each number (cpu.max reads max 100000).

Pitfall — programs that size themselves from the wrong number

python3 -c 'import os; print(os.cpu_count())' in that container also prints 10. Anything that picks its parallelism or cache size from the machine's totals — a test runner starting one worker per CPU, a build tool, a data loader — will plan for ten CPUs and 7.7 GiB, then be throttled to 1.5 and killed at 256 MiB. The agent's pytest -n auto (one worker per CPU it can count) dying with Killed should make you check this first: it would be a property of the box, not of the model's code.

Three reading notes for the host-level tools, which you will still use on VMs:

  • Load average counts jobs that are running or runnable plus those in uninterruptible disk wait, averaged over 1, 5 and 15 minutes,[proc_loadavg(5)] and is not normalised by CPU count: a load of 1 saturates a one-CPU machine and leaves a four-CPU machine idle 75% of the time.[uptime(1)] Compare it with nproc. A sandbox host running 40 rollouts on 8 cores with load 35 is oversubscribed; every rollout on it is slower than the same rollout yesterday.
  • free: read available, not free. Linux uses spare memory as file cache, so free is usually small on a healthy machine. available is the "estimation of how much memory is available for starting new applications, without swapping."[free(1)]
  • top (batch form for scripts and agents: top -b -n 1) heads its output with the same load average and a CPU line where id is idle, wa is waiting for I/O, and st is time "stolen from this vm by the hypervisor"[top(1)] — a noisy-neighbour indicator on cloud VMs.

Memory: the kill

When a cgroup's usage reaches memory.max and cannot be reduced, "the OOM killer is invoked in the cgroup."[Kernel: cgroup-v2] The OOM (out-of-memory) killer picks a process in the group and kills it; it never kills tasks outside that cgroup.[Kernel: cgroup-v2] Inside the 256 MiB container, ask for 400 MiB: 

# python3 -c 'b = bytearray(400 * 1024 * 1024); print("allocated")'
Killed
# echo $?
137
# grep -E '^oom' /sys/fs/cgroup/memory.events
oom 1
oom_kill 1
oom_group_kill 0
# cat /sys/fs/cgroup/memory.peak
268435456

No traceback, no MemoryError: the program was not told, it was removed. Killed is bash reporting that its child died of SIGKILL, and 137 is 128 + 9 (page 10). The evidence is memory.events: oom_kill is "the number of processes belonging to this cgroup killed by any kind of OOM killer",[Kernel: cgroup-v2] and a peak exactly equal to the limit says the group hit its ceiling.

Notice what did not happen: the container is still running. The victim was a child; the shell carried on. From outside: 

$ docker inspect --format 'Status={{.State.Status}} ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' lt-12-lim
Status=running ExitCode=0 OOMKilled=true

That independence is worth seeing in all three combinations:

# (a) victim is a child; PID 1 carries on and exits normally
$ docker run --name lt-12-oomchild --memory 256m --memory-swap 256m lt-12-base:1 \
    bash -c 'python3 -c "bytearray(400*1024*1024)"; echo "test step exit=$?"; echo "agent carries on"'
test step exit=137
agent carries on
bash: line 1:     6 Killed                  python3 -c "bytearray(400*1024*1024)"
$ docker inspect --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' lt-12-oomchild
ExitCode=0 OOMKilled=true

# (b) victim is PID 1
$ docker run --name lt-12-oompid1 --memory 256m --memory-swap 256m lt-12-base:1 \
    python3 -c "bytearray(400*1024*1024)"
$ docker inspect --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' lt-12-oompid1
ExitCode=137 OOMKilled=true

# (c) no memory problem at all: docker stop, 10 s grace, then SIGKILL
$ docker run -d --name lt-12-stop --memory 256m lt-12-base:1 sleep infinity
$ docker stop lt-12-stop
$ docker inspect --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' lt-12-stop
ExitCode=137 OOMKilled=false
Key idea

Exit 137 means "died of SIGKILL". It does not mean "out of memory". The OOM killer, a harness timeout, docker stop, and a human with kill -9 all produce it. The evidence for an OOM kill is oom_kill in memory.events and State.OOMKilled from docker inspect — and those can be true while the container exits 0, because the victim may have been the agent's test run rather than the container's main process.

Caveat — swap changes the demo

--memory-swap is the total of memory plus swap. If it is unset, the container may use as much swap again as its --memory value, if the host has swap configured;[Docker: run] setting it equal to --memory means no swap. That is why every example here sets both: with swap available, an over-budget program slows to a crawl before it dies, and your timeout may fire first.

CPU: the slowdown

A CPU limit never kills. The group "may consume up to $MAX in each $PERIOD";[Kernel: cgroup-v2] when the quota is spent its processes simply do not run until the next period. This script starts four CPU-bound workers, waits for them, and prints the elapsed time and the cgroup's throttling counters: 

#!/bin/bash
work() { python3 -c 'sum(i*i for i in range(12_000_000))'; }
start=$(date +%s.%N)
work & work & work & work &
wait
end=$(date +%s.%N)
python3 -c "print('4 workers wall:', round($end - $start, 1), 's')"
cat /sys/fs/cgroup/cpu.max
grep -E 'nr_periods|nr_throttled|throttled_usec' /sys/fs/cgroup/cpu.stat

Run it uncapped, then with half a CPU (-v "$PWD/cpu.sh:/cpu.sh:ro" mounts it in; omitted below for width):

$ docker run --rm lt-12-base:1 bash /cpu.sh
4 workers wall: 0.7 s
max 100000
nr_periods 0
nr_throttled 0
throttled_usec 0
$ docker run --rm --cpus 0.5 lt-12-base:1 bash /cpu.sh
4 workers wall: 6.7 s
50000 100000
nr_periods 69
nr_throttled 68
throttled_usec 22924227

Same work, same CPU time, roughly ten times the wall-clock time. cpu.stat records why: the group was throttled in 68 of 69 periods, for a cumulative 22.9 seconds of enforced waiting across its processes. Now put the same job under a timeout, as every harness does: 

$ docker run --rm --cpus 0.5 lt-12-base:1 bash -c 'timeout 5 bash /cpu.sh; echo "exit=$?"'
exit=124
$ docker run --rm lt-12-base:1 bash -c 'timeout 5 bash /cpu.sh; echo "exit=$?"'
4 workers wall: 0.6 s
…
exit=0

Identical code passes or "times out" depending on a flag the model never saw. A CPU shortage reaches your results table disguised as a timeout, and nr_throttled is how you unmask it.

Disk: the error message

Disk exhaustion is the polite one: the write fails with the error ENOSPC and the program is told. To fill a disk safely, use a small RAM-backed tmpfs (page 14): 

$ docker run --rm -it --memory 256m --tmpfs /scratch:size=8m lt-12-base:1 bash
# head -c 20M /dev/zero > /scratch/big
head: error writing 'standard output': No space left on device
# df -h /scratch
Filesystem      Size  Used Avail Use% Mounted on
tmpfs           8.0M  8.0M     0 100% /scratch
# echo '{"passed": true}' > /scratch/result.json; echo "exit=$?"
bash: line 3: echo: write error: No space left on device
exit=1
# ls -l /scratch/result.json
-rw-r--r-- 1 root root 0 Sep 21 21:04 /scratch/result.json

Look at the last line. Creating the file succeeded; writing its content failed. A full disk leaves behind empty files with the right names — and a grader that checks "does result.json exist?" or treats unparseable output as "no tests failed" is about to record something untrue.

Two tools, two questions. df -h ("disk free") asks each mounted filesystem how full it is. du -sh DIR ("disk usage") walks a directory and adds up the files it can see. They disagree when a file has been deleted while a process still holds it open (page 3): the name is gone, so du cannot count it, but the space is not freed until the last file descriptor closes. 

# head -c 5M /dev/zero > /scratch/log; tail -f /scratch/log > /dev/null &
# rm /scratch/log
# du -sh /scratch; df -h /scratch | tail -1
0	/scratch
tmpfs           8.0M  5.0M  3.0M  63% /scratch
# ls -l /proc/$!/fd | grep deleted
lr-x------ 1 root root 64 Sep 21 21:03 3 -> /scratch/log (deleted)

Killing the tail returned df to 0%. On a sandbox host the usual culprit is a long-running daemon holding a deleted, still-growing log.

The second way to be "full" is to run out of inodes, the per-file records. Each file costs one regardless of size, and a filesystem has a fixed supply. With a tmpfs capped at 20 inodes: 

# for i in $(seq 1 30); do touch f$i || break; done
touch: cannot touch 'f20': No space left on device
# df -h /scratch | tail -1; df -i /scratch
tmpfs           8.0M     0  8.0M   0% /scratch
Filesystem     Inodes IUsed IFree IUse% Mounted on
tmpfs              20    20     0  100% /scratch

Same error text, zero bytes used. When df -h says there is room and writes still fail with No space left, run df -i. Millions of tiny cache files (node_modules, pip and apt caches, per-rollout temp directories never cleaned) are how real hosts get there.

Process and file slots

A cgroup's pids.max caps the number of processes and threads in the group; at the limit, fork fails with EAGAIN.[Kernel: cgroup-v2] Bash words that error like this: 

$ docker run --rm --pids-limit 20 lt-12-base:1 bash -c \
    'for i in $(seq 1 30); do sleep 5 & done 2>&1 | sort | uniq -c; cat /sys/fs/cgroup/pids.events'
      1 bash: fork: Interrupted system call
      3 bash: fork: retry: Resource temporarily unavailable
max 3

The kernel documentation gives the reason the controller exists: "a fork bomb is likely to exhaust the number of tasks before hitting memory restrictions."[Kernel: cgroup-v2] Use this, not the ulimit -u rlimit, to contain an agent: that rlimit counts processes per user ID across the whole system and is not enforced for root.[getrlimit(2)]

Open files, by contrast, are a genuine per-process rlimit (ulimit -n). Exceeding it yields the error EMFILE:[getrlimit(2)] 

# ulimit -n 20
# python3 -c '
fs = []
for i in range(100):
    fs.append(open("/etc/hostname"))' 2>&1 | tail -1
OSError: [Errno 24] Too many open files: '/etc/hostname'

The lab container's default here was 1048576, so you rarely hit this in Docker; you are more likely to hit it on VMs and in harness processes, where the limit may be far lower and a harness holding hundreds of sandbox connections and log files can reach it. ulimit -a lists every rlimit of the current shell; /proc/PID/limits shows soft and hard values for any process. SWE-bench's harness exposes an --open_file_limit option.[SWE-bench]

Accounting for failures the box caused

In eval work

An under-provisioned sandbox converts rollouts a model would have passed into failures, and the score drops for reasons unrelated to the model. Anthropic measured the size of the effect on Terminal-Bench 2.0 with the same model, harness and tasks: moving from strict per-task resource limits to uncapped resources cut the infrastructure error rate from 5.8% to 0.5% and raised the score by 6 percentage points (p < 0.01), and they conclude that "leaderboard differences below 3 percentage points deserve skepticism until the eval configuration is documented and matched."[Anthropic: Infra Noise] The same post names the mechanism from this page: with the limit set equal to the expected need, "a momentary memory fluctuation can OOM-kill a container that would otherwise have succeeded." (Discuss.)

So treat an OOM kill, a throttling-induced timeout, and a full disk as observations about the run, not about the model, and keep them visible in the arithmetic. Suppose 200 rollouts were scheduled, 14 ended in an infrastructure failure (9 OOM kills, 5 timeouts with heavy throttling), and 120 of the rest were correct:

QuantityValueWhat it answers
correct / scheduled120 / 200 = 60.0%How did the whole system — model and box — do? The conservative headline.
correct / completed120 / 186 = 64.5%How did the model do when the box held up? Only meaningful if failures are unrelated to task difficulty — and they rarely are: memory-hungry tasks are both harder and likelier to be killed.
completed / scheduled186 / 200 = 93.0%How healthy was the infrastructure? If this differs between two models' runs, fix that before comparing anything else.

Choose the primary metric before looking at results, publish all three, and never let a runner drop failed rollouts silently: the second row can be pushed upward just by making the box worse. Re-running infrastructure failures is legitimate if the rule is fixed in advance and applied to every model alike.

In eval work

Concurrency is a resource setting. Running N sandboxes on one host divides that host. Inspect's Docker provider defaults max_sandboxes to twice the number of processors available to the eval;[Inspect] SWE-bench recommends at least 16 GB of RAM and 8 cores, and fewer than min(0.75 * os.cpu_count(), 24) workers.[SWE-bench] Inspect's default sandbox configuration sets no CPU or memory limits at all,[Inspect] so by default every rollout competes with its neighbours for the whole machine, and the same eval on a bigger host, or at a lower concurrency, is a slightly different eval. Per-sandbox limits, concurrency, and host size therefore belong in the reported configuration, beside the model name and the prompt (Understanding LLM Evals, page 19). (Design: set --memory, --cpus and --pids-limit explicitly per task, with headroom above the oracle solution's measured memory.peak; record OOM and timeout counts next to every pass rate.)

Check your understanding

A nightly run of a coding benchmark drops from 62% to 55% with no change to the model or the tasks. The runner's summary shows 31 rollouts with exit code 137, up from 4. A colleague says: "137 is OOM — the new tasks-per-host setting is starving containers of memory. Let's exclude those 31 and report 60%." What do you ask for before agreeing to either the diagnosis or the number?

Reveal the reasoning

Observed vs supposed. Observed: more SIGKILL deaths, a lower score, a concurrency change. Supposed: that the kills were OOM kills. 137 is equally what a harness timeout's kill -9 and docker stop produce — and raising concurrency makes both memory pressure and slowness more likely, so the hypothesis is plausible but untested.

Discriminating evidence. For the 31: State.OOMKilled from docker inspect (or oom_kill in each container's memory.events, and the host kernel log — page 13). Note that if the containers set no --memory limit, an OOM kill would be a host-level one and only the host's kernel log records it. Then duration: do the 31 cluster at the harness timeout value? That says timeout kill; check nr_throttled or host load for the cause. Also look for the inverse case the exit code hides: rollouts that exited 0 with OOMKilled=true, where the agent's test run was killed and the agent gave up.

Bearing on the score. Excluding the 31 reports correct/completed and hides that the infrastructure got worse; the excluded tasks are probably the heavy ones, so 60% is biased upward. Report 55% as correct/scheduled with the 31 shown as infrastructure failures and completed/scheduled alongside; then fix the box (restore concurrency or set per-container limits with headroom) and re-run the whole night, not just the failures, since slow-but-completed rollouts were affected too.

Lab

Container lab. All exercises are docker run lines typed on your Mac, using the stock ubuntu:24.04 image. Every memory demo carries a --memory limit: never run an allocator without one.

  1. Reproduce. Start a container with --memory 128m --cpus 0.5 --pids-limit 50 and print, side by side, what nproc and /proc/meminfo claim and what the cgroup files say.
    Solution 
    $ docker run --rm --memory 128m --cpus 0.5 --pids-limit 50 ubuntu:24.04 sh -c \
    'nproc; grep MemTotal /proc/meminfo; cd /sys/fs/cgroup; cat memory.max cpu.max pids.max'
10
MemTotal:        8025424 kB
134217728
50000 100000
50

    Your first two numbers will be your own machine's. The last three are the policy.

  2. Predict, then verify. tail /dev/zero reads an endless line into memory. Before running this, write down the container's exit code and the value of OOMKilled: docker run --name lt-oom --memory 64m --memory-swap 64m ubuntu:24.04 sh -c 'tail /dev/zero; echo "still here: $?"'
    Solution 
    Killed
still here: 137
$ echo $?
0
$ docker inspect --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' lt-oom; docker rm lt-oom
ExitCode=0 OOMKilled=true

    The child was killed; PID 1 (sh) finished normally. A harness that looks only at the container's exit code sees a clean run.

  3. Predict, then verify. In docker run --rm -it --tmpfs /scratch:size=8m,nr_inodes=20 ubuntu:24.04 bash, create files in /scratch until it fails. What will df -h /scratch report as used?
    Solution 
    # cd /scratch; for i in $(seq 1 30); do touch f$i || break; done
touch: cannot touch 'f20': No space left on device
# df -h /scratch | tail -1; df -i /scratch | tail -1
tmpfs           8.0M     0  8.0M   0% /scratch
tmpfs              20    20     0  100% /scratch

    Zero bytes used, 100% of inodes. (Nineteen files plus the directory itself.)

  4. Eval task. Make three dead containers, then classify each death using only docker inspect: 
    docker run --name lt-a --memory 64m --memory-swap 64m ubuntu:24.04 tail /dev/zero
docker run -d --name lt-b ubuntu:24.04 sleep 600; sleep 2; docker stop lt-b
docker run --name lt-c ubuntu:24.04 timeout -s KILL 2 sleep 60
    All three exit 137. Which was an infrastructure failure, which a timeout, which a normal teardown — and what would you still need the harness log for?
    Solution 
    $ for c in lt-a lt-b lt-c; do docker inspect --format \
    '{{.Name}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}} mem={{.HostConfig.Memory}} {{.State.StartedAt}} {{.State.FinishedAt}}' $c; done
/lt-a exit=137 oom=true mem=67108864 …T21:04:23.09Z …T21:04:23.21Z
/lt-b exit=137 oom=false mem=0 …T21:04:23.35Z …T21:04:35.54Z
/lt-c exit=137 oom=false mem=0 …T21:04:35.75Z …T21:04:37.84Z
$ docker rm lt-a lt-b lt-c

    lt-a: oom=true with a 64 MiB limit, dead in a tenth of a second — OOM kill, an infrastructure outcome (or a task whose limit is set too low). lt-b and lt-c are indistinguishable by flags: both oom=false. Timing separates them only if you know the configuration: lt-c lived 2.08 s, matching its 2 s timeout; lt-b lived 12 s = 2 s of life plus Docker's 10 s stop grace period. To be sure who sent the SIGKILL you need the harness's own record of "I timed this out" or "I stopped this" — which is why harness logs are a separate evidence stream from container state.
