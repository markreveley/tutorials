Module 1 · The Shell

The shell and the command line

What happens between pressing Enter and output appearing: how a line of text becomes a running program, how the shell finds that program, and how it reports success or failure. An agent's every tool call goes through this machinery — in a mode that behaves differently from the shell you type into — and the most common error in agent transcripts, command not found, is a question about it.

Three things that look like one

When you open Terminal on your Mac and type ls, three separate pieces of software cooperate, and beginners reasonably experience them as one thing called "the command line". Pull them apart.

  • The terminal is the window. It turns keystrokes into bytes and bytes into glyphs. It knows nothing about files or commands.
  • The shell is a program that reads a line of text, works out which program you meant, starts it, waits for it, and then prompts again. POSIX, the standard that Unix-like systems share, calls it simply "the standard command language interpreter".[POSIX] On Ubuntu the interactive shell is bash; your Mac's is zsh (Appendix E).
  • The program — ls, python3, pytest — is a file on disk that the shell asks the kernel to run as a new process.
you ──keys──▶ TERMINAL ──bytes──▶ SHELL (bash) (a window) │ 1. split the line into words ▲ │ 2. find the program for word one │ │ 3. start it as a child process │ ▼ └──── output ── PROGRAM (/usr/bin/ls) │ └─ exit status ─▶ back to the shell ($?) an agent: HARNESS ──"bash -c '…'"──▶ SHELL ──▶ PROGRAM (no terminal at all)

The last line of the diagram is why this page exists. An agent in a sandbox has no terminal. Its harness starts a shell, hands it one string, collects what comes back, and the shell exits. Same shell program, different mode, different behaviour — we'll get to exactly how different below.

Everything on this page was run in the container lab from page 1, as the non-root user learner.

Anatomy of a command line

The shell splits your line on spaces into words. The first word is the command; the rest are handed to it, untouched, as its arguments. By convention — and it is only a convention that each program implements for itself — arguments starting with a dash are options that change behaviour, and the others name the things to operate on.

ls -l -a /etc/hostname │ │ │ command options (flags) argument (operand)
$ ls -l -a /etc/hostname
-rw-r--r-- 1 root root 13 Sep 21 10:55 /etc/hostname
$ ls -la /etc/hostname                          # short flags can be bundled
-rw-r--r-- 1 root root 13 Sep 21 10:55 /etc/hostname
$ ls --all --human-readable -l /etc/hostname    # long flags: two dashes, a whole word
-rw-r--r-- 1 root root 13 Sep 21 10:55 /etc/hostname

Short flags are one dash and one letter and can be bundled (-la is -l -a). Long flags are two dashes and a word. Most GNU tools offer both spellings; prefer the long one in scripts, where a reader has to understand it later.

Because "starts with a dash" is the only thing that marks an option, data that happens to start with a dash gets misread. The escape hatch is a bare --, which means "no more options after this point": 

$ grep --timeout config.txt
grep: unrecognized option '--timeout'
Usage: grep [OPTION]... PATTERNS [FILE]...
Try 'grep --help' for more information.
$ grep -- --timeout config.txt
--timeout 30

The same trick deletes a file unluckily named -rf (rm -- -rf). You will see agents discover this the hard way when they search logs for strings like --verbose.

How the shell finds a program

You typed ls, not /usr/bin/ls. The shell filled in the rest using the PATH variable: a colon-separated list of directories, searched left to right, first match wins. 

$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

But PATH is the last place bash looks. For a name with no slash in it, bash checks for a shell function of that name, then a builtin, and only then walks PATH; it remembers where it found each program in a hash table so it doesn't search twice. If the name contains a slash, no search happens at all — it's taken as a path to a file.[Bash Manual] (In an interactive shell, aliases are substituted even before that.) The command that shows you what bash will actually do with a name is type: 

$ type ls
ls is aliased to `ls --color=auto'
$ type cd
cd is a shell builtin
$ type -a echo                 # -a: every match, in priority order
echo is a shell builtin
echo is /usr/bin/echo
echo is /bin/echo
$ which ls
/usr/bin/ls
$ which cd; echo "exit status: $?"
exit status: 1

Note the disagreement. which is a separate program that only searches PATH; it cannot know about your shell's aliases, functions, or builtins, so it told you ls is /usr/bin/ls when this shell will really run ls --color=auto, and it found no cd at all. Use type when you're at a bash prompt, and command -v (the POSIX-portable spelling) in scripts.

Why cd isn't a program

If you're wondering why some commands live inside the shell: a few have to. Every process has its own working directory, and a child process cannot change its parent's. Watch a child shell try: 

$ pwd
/home/learner
$ bash -c 'cd /tmp; pwd'      # a child process changes ITS directory…
/tmp
$ pwd                          # …and ours hasn't moved
/home/learner

A /usr/bin/cd would change its own directory and exit, achieving nothing. The bash manual says it directly: "cd, break, continue, and exec cannot be implemented outside of the shell because they directly manipulate the shell itself."[Bash Manual] Others — pwd, kill, echo — are builtins merely for convenience, which is why type -a echo showed both a builtin and a file. Hold on to the principle, because it returns all course long: a child process cannot alter its parent — not its directory, not its variables.

A worked example: 127, 126, and success

The running example of this course is a toy benchmark, wordfreq-bench. Here we install a stand-in for its command-line tool and watch every stage of lookup fail in turn. 

$ wordfreq
bash: wordfreq: command not found
$ echo $?
127
$ mkdir ~/tools
$ printf '#!/bin/bash\necho "wordfreq 1.0"\n' > ~/tools/wordfreq
$ ~/tools/wordfreq                  # has a slash: no PATH search, run this file
bash: /home/learner/tools/wordfreq: Permission denied
$ echo $?
126
$ chmod +x ~/tools/wordfreq         # mark it executable (page 8)
$ ~/tools/wordfreq
wordfreq 1.0
$ wordfreq                          # exists, executable — but not on PATH
bash: wordfreq: command not found
$ PATH=$HOME/tools:$PATH
$ wordfreq
wordfreq 1.0
$ type wordfreq
wordfreq is hashed (/home/learner/tools/wordfreq)
Key idea

"Command not found" does not mean "not installed". It means this shell, with this PATH, found no function, builtin, or file by that name. The program was on disk the whole time in the example above. The question to ask is never "is it installed?" but "what is PATH in the shell that ran it?"

The exit status: how a program says how it went

Every process, when it ends, hands one small integer back to whoever started it: its exit status. Zero means success; anything else means failure, and the program chooses which non-zero number. The bash manual admits this looks backwards and gives the reason: "so there is one well-defined way to indicate success and a variety of ways to indicate various failure modes."[Bash Manual] The shell keeps the most recent one in the special variable $?. 

$ true; echo $?
0
$ false; echo $?
1
$ ls /nope; echo $?
ls: cannot access '/nope': No such file or directory
2
$ grep learner /etc/passwd; echo $?
learner:x:1001:1001::/home/learner:/bin/bash
0
$ grep nobody-here /etc/passwd; echo $?       # no error message, no output…
1

That last one matters: grep exits 1 for "I ran fine and found nothing". A non-zero status is a program's own vocabulary, and you have to know the program to read it. A few values, though, are set by the shell and mean the same everywhere. The status is one byte, 0–255 (a program that calls exit(300) is seen as 300 modulo 256, i.e. 44[POSIX]), and bash reserves the top of that range:[Bash Manual]

StatusWho sets itMeaningFirst question to ask
0the programsuccess—
1–125the programfailure, in the program's own dialect (grep 1 = no match; ls 2 = serious trouble)What does this program mean by it? (man, Appendix F)
2bash builtinsincorrect usage: bad option or missing argumentWas the command line malformed?
126the shellfound, but not executableMissing chmod +x? A directory?
127the shellcommand not foundWhat is PATH in the shell that ran it?
128+Nthe shellkilled by signal N (137 = 128+9, SIGKILL)Timeout? Out of memory? → page 10

The full tables are in Appendix B. The status is also what the shell's two "short-circuit" operators test: A && B runs B only if A succeeded; A || B runs B only if A failed. 

$ mkdir /tmp/demo && echo "made it"
made it
$ mkdir /tmp/demo || echo "could not make it"
mkdir: cannot create directory '/tmp/demo': File exists
could not make it
$ cd /nope && rm -f *.log          # the rm never runs: good
bash: cd: /nope: No such file or directory
Pitfall — ; is not &&, and $? is only the last command

A semicolon runs the next command regardless. cd /nope; rm -f *.log deletes log files in whatever directory you were already in. And a line's status is its last command's status:

$ ls /nope; echo "done"
ls: cannot access '/nope': No such file or directory
done
$ echo $?
0

A harness that runs run_tests; echo finished and checks the status will record success every time. $? is also overwritten by every command, including the echo you used to look at it — capture it immediately (rc=$?) if you need it twice.

Interactive and non-interactive shells

Now the part that separates your experience of a box from an agent's. Bash runs in different modes, and which mode it's in decides which startup files it reads — and those files are where PATH additions, aliases, and virtual-environment activations live. Two independent questions define the mode:

  • Interactive? A shell is interactive if it was started without a command to run and is connected to a terminal (or was forced with -i).
  • Login? A shell is a login shell if it was started as one — by ssh, by su -, or with --login/-l.
How bash was startedExampleStartup files it reads
Login shellssh box, bash --login, bash -lc '…'/etc/profile, then the first that exists of ~/.bash_profile, ~/.bash_login, ~/.profile
Interactive, non-logintyping bash; docker exec -it box bash~/.bashrc
Non-interactivebash -c '…', bash script.shonly the file named by $BASH_ENV, if that variable is set — normally nothing

That table is the bash manual's rule.[Bash Manual] To see it bite, make the PATH change from the last section "permanent" the way every tutorial tells you to — append it to ~/.bashrc — along with an alias: 

$ echo 'export PATH=$HOME/tools:$PATH' >> ~/.bashrc
$ echo "alias t='wordfreq --test'" >> ~/.bashrc
$ bash                              # a fresh interactive shell reads ~/.bashrc
$ wordfreq
wordfreq 1.0
$ echo $-                           # this shell's option letters: "i" = interactive
himBHs

Works for you. Now do what a harness does: from outside the box, ask for one command to be run. (mac$ is your Mac's prompt; lt-lab is the lab container.) 

mac$ docker exec -u learner lt-lab bash -c 'wordfreq'; echo "[exit status $?]"
bash: line 1: wordfreq: command not found
[exit status 127]
mac$ docker exec -u learner lt-lab bash -c 'echo $-; echo $PATH'
hBc
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
mac$ docker exec -u learner lt-lab bash -c 't'
bash: line 1: t: command not found

No i in $-: non-interactive, so ~/.bashrc was never read, so PATH is the container's bare default and the alias doesn't exist. Same box, same user, same file on disk, and the command that works when you look fails when the harness runs it.

Remedies, and one that doesn't work

The obvious fix is "make it a login shell". On Ubuntu that is not enough, and the reason is instructive: 

mac$ docker exec -u learner lt-lab bash -lc 'wordfreq'
bash: line 1: wordfreq: command not found

A login shell reads ~/.profile, and Ubuntu's ~/.profile does source ~/.bashrc — but Ubuntu's ~/.bashrc opens with a guard that bails out of non-interactive shells before reaching the line we appended at the bottom: 

# If not running interactively, don't do anything
case $- in
    *i*) ;;
      *) return;;
esac

(Pointing BASH_ENV at ~/.bashrc fails for the same reason; we tried.) What a login shell does pick up is anything set in ~/.profile itself. The stock Ubuntu one adds ~/.local/bin to PATH if that directory exists — which is where pip install --user puts command-line tools: 

mac$ docker exec -u learner lt-lab bash -c 'mkdir -p ~/.local/bin && cp ~/tools/wordfreq ~/.local/bin/wf2'
mac$ docker exec -u learner lt-lab bash -c 'wf2'
bash: line 1: wf2: command not found
mac$ docker exec -u learner lt-lab bash -lc 'wf2'
wordfreq 1.0
mac$ docker exec -u learner lt-lab bash -lc 'echo $PATH'
/home/learner/.local/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

The remedies that don't depend on anyone's dotfiles are the ones to build an environment on:

mac$ docker exec -u learner lt-lab bash -c '/home/learner/tools/wordfreq'     # absolute path: no search
wordfreq 1.0
mac$ docker exec -u learner lt-lab bash -c 'PATH=/home/learner/tools:$PATH; wordfreq'
wordfreq 1.0
mac$ docker exec -u learner \
       -e PATH=/home/learner/tools:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
       lt-lab bash -c 'wordfreq'                                           # set PATH in the environment
wordfreq 1.0

The last form is the general one: put PATH in the process's environment from outside (in a Dockerfile, that's an ENV PATH=… line — page 22), so every shell in the box inherits it no matter its mode. Page 11 explains inheritance properly.

In eval work — 127 is a PATH question first

When a transcript shows pytest: command not found with exit status 127, and you docker exec -it into the same task image and pytest runs fine, nothing is missing: your interactive shell read a startup file that the agent's non-interactive shell did not. Typical culprits are tools installed under ~/.local/bin, a virtual environment "activated" in ~/.bashrc, and version managers (conda, nvm, pyenv) that work by editing startup files. If the agent burns ten turns rediscovering python3 -m pytest, the benchmark measured your image's PATH, not the model — an infrastructure failure scored as a model failure. Audit by reproducing the harness's exact invocation, never by opening an interactive shell. And account for it honestly: a rollout crippled by the image's PATH is an observation about the run. Don't quietly drop those samples (that shrinks the denominator from scheduled to completed and flatters the score) and don't leave them in as model failures; fix the image, re-run, and say so.

In eval work — every tool call is a fresh, non-interactive shell

Inspect's standard bash() tool executes each call as bash --login -c <command> in the sandbox, and each call is a fresh shell: no working directory and no variables carry over from the previous call. Its bash_session() tool is the stateful alternative that keeps one shell alive.[Inspect] The consequence is the cd lesson again, one level up — the shell that did the cd has exited:

mac$ docker exec -u learner lt-lab bash --login -c 'cd /tmp && export RUN_ID=42 && pwd'
/tmp
mac$ docker exec -u learner lt-lab bash --login -c 'pwd; echo "RUN_ID=$RUN_ID"'
/
RUN_ID=

So in a stateless harness a capable agent writes cd /app && pytest in every call, and a transcript where the agent runs cd /app alone and then is confused by "No such file" is showing you a mismatch between the agent's mental model and the harness, not an inability to fix the bug. Also implied by non-interactive: no aliases, no one to answer prompts (run that way, read -p "Continue? [Y/n] " x gets end-of-file at once: status 1, empty answer), and no terminal for programs that want one. Know which kind of tool your harness provides before you read its transcripts; page 25 goes through the interfaces.

Alpine: when bash itself is the missing command

Many task images are built on Alpine, a tiny distribution where nearly every command is one multi-purpose binary, BusyBox, and the shell is BusyBox's ash. There is no bash unless someone installs it: 

mac$ docker run --rm alpine:3.20 sh -c 'bash -c "echo hi"; echo "exit status: $?"; ls -l /bin/sh /bin/ls'
sh: bash: not found
exit status: 127
lrwxrwxrwx    1 root     root            12 Apr 15 16:14 /bin/ls -> /bin/busybox
lrwxrwxrwx    1 root     root            12 Apr 15 16:14 /bin/sh -> /bin/busybox
mac$ docker run --rm alpine:3.20 bash -c 'echo hi'
docker: Error response from daemon: … exec: "bash": executable file not found in $PATH: unknown
Caveat — sh is not bash on Ubuntu either

On Ubuntu 24.04, /bin/sh is a symlink to dash, a small, strictly POSIX shell — not bash. A harness or Dockerfile that runs commands with sh -c gets dash on Ubuntu and ash on Alpine, and bash-only syntax ([[ … ]], arrays) fails there. A harness hard-wired to call bash cannot start at all in a stock Alpine image. Which shell runs the agent's commands is a property of the environment you should be able to state. Page 6 returns to this.

The interactive conveniences, in one card

These exist only in an interactive shell — they're for you, not for agents.

  • Tab completes a command or file name; twice lists the candidates. Use it constantly: a name that won't complete doesn't exist.
  • ↑ / ↓ walk through previous commands; Ctrl+R searches them; history prints them.
  • Ctrl+C interrupts the running program (it sends a signal, SIGINT — page 10). The shell survives.
  • Ctrl+D means "end of input". At an empty prompt it ends the shell, like typing exit. If that shell was the container's main process, the container stops with it.
Check your understanding

A maintainer changes a benchmark's harness from bash -c to bash -lc "to fix some environment issues". With the same model, the pass rate goes from 41% to 58%. You are asked which number to publish. What do you ask first?

Reveal the reasoning

What is observed: one flag changed and the score moved. What is only supposed: that the old failures were PATH problems. The discriminating evidence is in the old transcripts: count the rollouts with exit status 127 or command not found, and see whether they cluster on tasks whose tools live where only a login shell looks (~/.local/bin, anything set in ~/.profile). Then reproduce one: run the harness's exact old invocation in that task image and print $PATH. If the flipped tasks are the 127 tasks, the 41% was partly measuring the image, and those failures were infrastructure outcomes — observations about the run, not the model. If they aren't, something else changed too, and you don't yet know what.

Two further questions bear on the published number. First, accounting: state which harness version produced it, and don't splice old and new runs into one denominator. Second, integrity: a login shell reads ~/.profile, a file the agent's user can write. If the grader also runs under -lc as that user, the fix opened a door (lab exercise 5). The better repair is a PATH set in the image, which needs no startup file at all.

Lab

Container lab, as learner (docker exec -it -u learner lt-lab bash). Exercises 4 and 5 also use your Mac's prompt.

1 · Reproduce. Ask bash what each of these is: cd pwd echo [ ls grep if. Which would still work if PATH were empty?

Solution 
$ type cd pwd echo [ ls grep if
cd is a shell builtin
pwd is a shell builtin
echo is a shell builtin
[ is a shell builtin
ls is aliased to `ls --color=auto'
grep is aliased to `grep --color=auto'
if is a shell keyword

The builtins and the keyword need no PATH. ls and grep are aliases that expand to programs found through PATH, so they would fail with 127. (type -a pwd shows there is also a /usr/bin/pwd; the builtin wins.)

2 · Predict, then verify. Write down what each line prints before running it: bash -c 'exit 3'; echo $? · bash -c 'exit 300'; echo $? · false && echo A || echo B, then echo $?.

Solution 
$ bash -c 'exit 3'; echo $?
3
$ bash -c 'exit 300'; echo $?
44
$ false && echo A || echo B
B
$ echo $?
0

300 doesn't fit in one byte: 300 − 256 = 44. In the third line false fails, so echo A is skipped and || echo B runs; the line's status is that of echo B, which succeeded — the original failure is gone from $?.

3 · Reproduce the mode gap. Do the ~/tools/wordfreq walkthrough and the ~/.bashrc edit from this page. Then, from your Mac, run wordfreq via bash -c, bash -lc, and bash -ic. Which work, and why does -ic complain?

Solution 
mac$ docker exec -u learner lt-lab bash -c 'wordfreq'
bash: line 1: wordfreq: command not found
mac$ docker exec -u learner lt-lab bash -lc 'wordfreq'
bash: line 1: wordfreq: command not found
mac$ docker exec -u learner lt-lab bash -ic 'wordfreq'
bash: cannot set terminal process group (-1): Inappropriate ioctl for device
bash: no job control in this shell
wordfreq 1.0

Only -i gets past the "if not running interactively" guard in ~/.bashrc. The two complaints are bash noticing that it was told to be interactive but has no terminal (we didn't pass -t). Forcing -i is a hack, not a remedy: that noise lands in the agent's output on every call.

4 · Eval task: the 127 that isn't. A colleague reports: "the agent's first call, wf2, fails with exit 127, but when I go into the container and su - learner, it works." Using the ~/.local/bin/wf2 setup from this page, find the single flag in the harness's invocation that explains the difference, and name a fix that doesn't depend on that flag.

Solution 
mac$ docker exec -u learner lt-lab bash -c 'wf2; echo $?; shopt login_shell; echo $PATH'
bash: line 1: wf2: command not found
127
login_shell    	off
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
mac$ docker exec -u learner lt-lab bash -lc 'wf2; shopt login_shell; echo $PATH'
wordfreq 1.0
login_shell    	on
/home/learner/.local/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

The harness used bash -c; ~/.local/bin only joins PATH in ~/.profile, which only login shells read — and su - starts a login shell (su - learner -c 'wf2; shopt login_shell' prints wordfreq 1.0 and login_shell on), so your colleague never saw the agent's PATH. Robust fix: set PATH in the image's environment (ENV PATH=/home/learner/.local/bin:$PATH) or install the tool into /usr/local/bin, which is on the default PATH in every mode.

5 · Eval task: who answers to the name pytest? The container has no pytest. Create an executable /tmp/fake/pytest that prints ===== 5 passed in 0.01s ===== and exits 0, put /tmp/fake first in PATH, and run pytest; echo $?. What does this imply about a grader that runs bare pytest in a shell whose environment the agent could influence?

Solution 
$ mkdir -p /tmp/fake
$ printf '#!/bin/bash\necho "===== 5 passed in 0.01s ====="\nexit 0\n' > /tmp/fake/pytest
$ chmod +x /tmp/fake/pytest
$ pytest; echo $?
bash: pytest: command not found
127
$ PATH=/tmp/fake:$PATH
$ pytest; echo $?
===== 5 passed in 0.01s =====
0
$ type -a pytest
pytest is /tmp/fake/pytest

A bare command name means "whatever PATH finds first". If the grader's shell reads a startup file the agent can write (a login-shell grader reads the agent user's ~/.profile), or searches a directory the agent can write, the agent decides what "pytest" is — a form of test tampering that never touches a test file. Graders should call interpreters by absolute path, run as a different user with a fixed PATH, and ideally run outside the agent's box altogether (page 26).
