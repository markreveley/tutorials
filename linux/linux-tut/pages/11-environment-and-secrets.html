Module 3 · Processes

Environment variables and secrets

Configuration and credentials reach a program as a small list of strings handed to it when it starts. That list is copied down the process tree, and it is visible from more places than most people expect. In an agentic eval the agent has a shell inside the box, so anything in its environment, or readable by its user, is something the agent can see — API keys and expected answers included.

The model: a list of strings, copied downwards

Every process carries an array of strings of the form NAME=value: its environment. An environment variable is one entry in that array. The kernel attaches no meaning to it; programs look names up by convention (PATH, HOME, OPENAI_API_KEY). Two rules from page 9's fork-and-exec story govern everything else on this page. When a process forks, the child "inherits a copy of its parent's environment."[environ(7)] And when a process execs a new program, the new program receives exactly the array the caller passes to execve; it looks "inherited" only because callers conventionally pass their own.[execve(2)]

harness (env: API_KEY, RUN_ID) │ fork+exec ── copy ──▶ ▼ bash (env: API_KEY, RUN_ID) copies flow DOWN only. │ fork+exec ── copy ──▶ a child editing its copy ▼ changes nothing above it. python (env: API_KEY, RUN_ID, MODEL) │ ▼ pytest (env: API_KEY, RUN_ID, MODEL) ◀── every descendant holds the secret

"Copy" has two consequences. Children see what the parent had at the moment they were started, and nothing a child does to its copy travels back up. Watch both, in the container lab as user learner: 

$ GREETING=hello
$ bash -c 'echo "child sees: [$GREETING]"'
child sees: []
$ export GREETING
$ bash -c 'echo "child sees: [$GREETING]"'
child sees: [hello]
$ bash -c 'GREETING=changed; export NEWVAR=1; echo "child has: $GREETING $NEWVAR"'
child has: changed 1
$ echo "parent still has: [$GREETING] [$NEWVAR]"
parent still has: [hello] []

The first surprise: GREETING=hello alone creates a shell variable, private to this shell. It is not in the environment array, so the child never receives it. export marks the variable for inclusion in the array handed to every future child. The second surprise is the last line: the child changed its copy and exited, and the parent is untouched.

That is why source exists. A setup script that you run is a child; its export and cd die with it. source file (or . file) reads the lines into the current shell instead, with no child involved: 

$ printf 'export MODEL=demo-1\ncd /tmp\n' > ~/setup.sh
$ bash ~/setup.sh; echo "after running: [$MODEL] $PWD"
after running: [] /home/learner
$ source ~/setup.sh; echo "after sourcing: [$MODEL] $PWD"
after sourcing: [demo-1] /tmp

This is the whole mechanism behind source venv/bin/activate: activation is an edit to PATH in the current shell (page 15).

In eval work

A transcript shows the agent running export FLASK_ENV=test in one tool call and the app ignoring it in the next. Under a harness that starts a fresh shell per call, each call is a new child of the harness, and the previous call's shell — with its exports, its cd, its activated venv — has already exited. Inspect's bash() tool "executes each command in a fresh session", while bash_session() retains "the prompt, working directory, and environment variables" across calls.[Inspect] Which one a benchmark uses decides whether "the agent forgot to set the variable" is a model error or a property of the harness. (Discuss.)

The one-shot form is the man page's own idiom[environ(7)] and the cleanest way to vary one setting in an experiment. env -i is the reproducibility tool: it shows what a program does when it inherits nothing from you. (PWD, SHLVL and _ in that output were added by bash itself on start-up.)

Locale and time zone are hidden inputs

Two environment variables change the output of ordinary commands, which makes them inputs to any grader that compares text. 

$ printf 'banana\nApple\ncherry\napple\nBanana\n' > words.txt
$ LC_ALL=C sort words.txt | tr '\n' ' '
Apple Banana apple banana cherry
$ LC_ALL=en_US.UTF-8 sort words.txt | tr '\n' ' '
apple Apple banana Banana cherry
$ date -d @1767225600 +%F
2026-01-01
$ TZ=America/Los_Angeles date -d @1767225600 +%F
2025-12-31

Same file, two orders; same instant, two dates. (The second sort needed the en_US.UTF-8 locale generated first; a stock ubuntu:24.04 image ships only C, C.utf8 and POSIX, so a developer's laptop and the task image disagree by default.) For a task like the course's wordfreq-bench, where a grader might compare a sorted word list against an expected file, that is the difference between pass and fail. Pin both in anything whose output is compared: LC_ALL=C and TZ=UTC.

Pitfall — a time zone that fails silently

Minimal images do not ship the time-zone database (package tzdata). Setting TZ there produces no error — just the wrong answer with a convincing label:

$ docker run --rm ubuntu:24.04 bash -c 'TZ=America/Los_Angeles date -d @1767225600'
Thu Jan  1 00:00:00 America 2026

That is UTC, labelled "America". With tzdata installed the same command prints Wed Dec 31 16:00:00 PST 2025. A task about log timestamps behaves differently in the two images, and neither the agent nor the grader is told why.

Where a container's environment comes from

A container's first process is started by the runtime, not by your shell, so it inherits nothing from your terminal. Its environment is assembled from four declared sources: the image's ENV lines, which "persist when a container is run from the resulting image";[Docker: Dockerfile] -e NAME=value and --env-file on docker run;[Docker: run] Compose's environment: key, which does the same job;[Compose] and a few values Docker adds itself. 

$ cat Dockerfile
FROM ubuntu:24.04
ARG BUILD_TOKEN
ENV APP_MODE=eval
ENV GRADER_KEY=sk-grader-999
RUN echo "fetching with $BUILD_TOKEN" > /dev/null
$ docker build -q --build-arg BUILD_TOKEN=sk-build-777 -t lt-11-env:1 .
$ printf 'RUN_ID=r-0042\nSEED=7\n' > run.env
$ docker run --rm -e MODEL=demo-1 --env-file run.env lt-11-env:1 env
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
HOSTNAME=62dfcfc85d53
RUN_ID=r-0042
SEED=7
MODEL=demo-1
APP_MODE=eval
GRADER_KEY=sk-grader-999
HOME=/root

No USER, no LANG, no TERM, none of your Mac's variables. Note also what docker exec does: it starts a new process in the container and gives it this same declared list, whichever user you ask for. Hold on to that; it matters below.

Every place the environment leaks

A secret is any value whose disclosure changes what someone can do: a provider API key, a grader token, the expected answer. Putting one in an environment variable feels private because you cannot see it on screen. Here are the places it can be read, each demonstrated. The lab container for this section was started with -e API_KEY=sk-demo-12345.

1. /proc/PID/environ

The /proc filesystem exposes each process's starting environment as a file, entries separated by NUL bytes.[proc_pid_environ(5)] Start a stand-in for a checker as learner, with the expected answer in its environment and (for the next section) a token on its command line; then, as a different process of the same user — the position of an agent that shares a UID with the checker — go and look: 

$ pgrep -u learner -a python3
1041 python3 -c import time; time.sleep(600) --token=hunter2
$ tr '\0' '\n' < /proc/1041/environ | grep EXPECTED
EXPECTED=the:42,of:17

Who is allowed to do that? The file's mode is -r--------, but the real gate is a kernel check shared with debuggers: access is granted if the target's real, effective and saved user IDs all match the caller's (and likewise the group IDs), or if the caller holds the CAP_SYS_PTRACE capability.[ptrace(2)] "Same user or root" is the folk version, and the second half of it is wrong in exactly the place you work: 

$ id -un                         # a different ordinary user
ubuntu
$ cat /proc/1041/environ
cat: /proc/1041/environ: Permission denied

# id -un                         # root, in a default Docker container
root
# cat /proc/1041/environ
cat: /proc/1041/environ: Permission denied

Root was refused because Docker's default capability set does not include CAP_SYS_PTRACE; started with --cap-add SYS_PTRACE, the same read succeeds. (Root can of course still read its own processes, including PID 1 if PID 1 runs as root.) Capabilities get their own treatment on page 21.

One more property: the file holds the initial environment, fixed at exec. If the program later changes its variables, "this file will not reflect those changes."[proc_pid_environ(5)] 

$ export LATER=xyz; API_KEY=rotated
$ tr '\0' '\n' < /proc/$$/environ | grep -E 'API_KEY|LATER'
API_KEY=sk-demo-12345

So a program that reads its key and then "clears" it with unset has cleared nothing that matters: the original is still on display for the life of the process.

2. Command-line arguments: public to every user

Arguments are worse. /proc/PID/cmdline is mode -r--r--r--, and with the default /proc mount options everybody may read every process's entry;[proc(5)] the kernel's own documentation describes the hidepid option as protection for "poorly written programs passing sensitive information via program arguments."[Kernel: procfs] Docker's /proc is mounted without it. The same ubuntu user who was just refused the environment: 

$ ps -eo user,pid,args
USER       PID COMMAND
root         1 sleep infinity
learner   1041 python3 -c import time; time.sleep(600) --token=hunter2
ubuntu    1057 ps -eo user,pid,args

ps is a /proc reader (page 9); for your own processes ps e prints their environments too. Never pass a secret as an argument: curl -H "Authorization: Bearer $KEY" typed by the harness puts the expanded key in the process list for as long as curl runs.

3. From outside: docker inspect and image history

Anyone who can talk to the Docker daemon can read a container's declared environment, running or stopped. The Docker docs say of ENV values: "You can view the values using docker inspect."[Docker: Dockerfile] The same holds for -e: 

$ docker inspect --format '{{json .Config.Env}}' lt-11-lab
["API_KEY=sk-demo-12345","PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"]

And the image remembers its build. Docker's guidance is blunt: "Build arguments and environment variables are inappropriate for passing secrets to your build, because they persist in the final image."[Docker: Dockerfile] The image built above proves it to anyone who pulls it: 

$ docker history --no-trunc --format '{{.CreatedBy}}' lt-11-env:1 | head -4
RUN |1 BUILD_TOKEN=sk-build-777 /bin/sh -c echo "fetching with $BUILD_TOKEN" > /dev/null # buildkit
ENV GRADER_KEY=sk-grader-999
ENV APP_MODE=eval
ARG BUILD_TOKEN=sk-build-777
$ docker run --rm lt-11-env:1 bash -c 'echo "[$BUILD_TOKEN] [$GRADER_KEY]"'
[] [sk-grader-999]

An ARG "is not embedded in the image and is not available in the final container"[Docker: Dockerfile] as a variable, which is why the first bracket is empty, yet its value sits in the history. The documented remedy for build-time credentials is a secret mount (RUN --mount=type=secret); page 22 uses it.

4. Logs, shell history, and dumps

The remaining surfaces are copies that programs make of their own environment. The commonest is bash's trace mode, beloved for debugging entrypoints: set -x prints every command after variable expansion, to stderr, which the container runtime records. 

$ docker run --name lt-11-trace -e API_KEY=sk-demo-12345 ubuntu:24.04 \
    bash -c 'set -x; : curl -H "Authorization: Bearer $API_KEY" https://api.example/v1'
+ : curl -H 'Authorization: Bearer sk-demo-12345' https://api.example/v1
$ docker logs lt-11-trace 2>&1 | grep -c sk-demo
1

The key is now in docker logs, and in whatever log store the harness ships container output to. The same happens when an error handler helpfully prints os.environ with the traceback, when a CI system echoes commands, and when a human types export OPENAI_API_KEY=… at an interactive prompt: bash appends it to ~/.bash_history on exit, where it outlives the session. A core dump — the memory image some systems write when a program crashes — contains the environment too, since the environment lives in the process's memory.

Key idea

An environment variable is not a vault. It is readable by every process of the same user, by every descendant, by anyone with the Docker API, and by anyone who reads the logs; an argument is readable by everyone on the box. Ask of every secret: which processes hold a copy, and who shares a UID with any of them?

The agent's observation space

In eval work

The agent runs inside the environment with a shell. Its first exploratory commands are often env and ls. Three things commonly found there:

  • Provider keys. A harness that runs the agent scaffold inside the box and passes ANTHROPIC_API_KEY with -e has given the key to the model under test, and — by inheritance — to every program the model runs, including anything it downloads. With open egress that is a spending and abuse risk, not just a validity one.
  • The answer. A checker started as the agent's user with EXPECTED=… in its environment, or --expected=… on its command line, is readable exactly as shown above. The exploits METR documents in its reward-hacking report have this shape: the agent's code ran inside the scorer's process (one walked the Python call stack to find the reference answer the scorer had already computed), or the scoring script was readable in the agent's filesystem.[METR]
  • Grader configuration. GRADER_URL, TASK_ID, HIDDEN_TESTS_DIR: not secrets by themselves, but a map.

And remember docker exec: a variable set with -e at docker run is handed to every exec'd process, whatever --user says. Running the agent as a non-root user does not hide the container's declared environment from it. (Navigate: the audit is env, cat /proc/1/environ | tr '\0' '\n', ps -eo user,pid,args from inside, and docker inspect plus docker history from outside.)

The mitigation ladder

From strongest to weakest. Use the highest rung the task allows.

  1. Don't put the secret in the sandbox. The model's API calls do not need to originate in the box. In Inspect, "model tool calls are executed within the main process running the evaluation task" and only the work they request runs in the sandbox,[Inspect] so the provider key stays on the host. Even when a third-party CLI agent must run inside the container, Inspect's sandbox agent bridge points it at a proxy on the container's own loopback address that relays requests to the model provider from outside.[Inspect] The same logic applies to answers: grade from outside, on artefacts copied out (page 26).
  2. If a credential must go in, make it cheap to lose. Scoped to one capability, short-lived, spend-capped, unique per run so a leak is attributable.
  3. A file, mode 0400, owned by a different user than the agent — and hand it to the program on stdin or by path, never as an argument: 
    # ls -ld /run/grader; ls -l /run/grader/expected
drwx------ 2 grader grader 4096 Sep 21 16:28 /run/grader
-r-------- 1 grader grader 13 Sep 21 16:28 /run/grader/expected
$ cat /run/grader/expected       # as learner
cat: /run/grader/expected: Permission denied
$ ps -eo user,pid,args | grep grader; cat /proc/1167/environ
grader    1167 sleep 300
cat: /proc/1167/environ: Permission denied
    The grader process read the file; nothing about it shows in its arguments or environment. This rung collapses if the agent is root, which ignores permission bits (page 8).
  4. Per-exec environment, not per-container. If the scorer needs a variable, pass it to the scorer's own exec call (Inspect's exec() takes env and user parameters[Inspect]) and run the scorer as a user the agent is not. The container's declared environment stays clean and docker inspect shows nothing.
Caveat — sudo and su - change the environment

The opposite problem also shows up in transcripts: a variable that is set, yet missing. With its default env_reset policy, sudo runs the command in a minimal environment of TERM, PATH, HOME, MAIL, SHELL, LOGNAME, USER and SUDO_*.[sudo(8)] In the lab, sudo env showed neither API_KEY nor a test variable MYTOKEN; sudo -E env showed both. su - user likewise starts a fresh login environment, while plain su user keeps the caller's. "It works without sudo but not with it" is an environment symptom before it is anything else.

Check your understanding

A team runs a coding benchmark with the agent scaffold inside each container. The container is started with -e ANTHROPIC_API_KEY=… and -e TASK_ANSWER_HASH=… (the grader compares the agent's final answer against the hash). The agent runs as non-root user agent; the grader runs afterwards as root. "The agent can't read root's environment, so we're fine," says the author. A new model scores eight points above the previous one. What would you establish before reporting the comparison?

Reveal the reasoning

What to establish. The author's claim is about /proc/PID/environ of root's processes, and on that narrow point it holds. But the variables were declared on the container, so every process started in it — including every shell the agent runs — receives them. env as agent prints both. The question is not whether the agent can see them (it can) but what that did to the measurement.

Discriminating evidence. Observation first: search all transcripts, both models, for env, printenv, /proc/, TASK_ANSWER_HASH, and the hash value itself. A hash is not the answer, so check whether the answer space is small enough to brute-force against it (a test-name list, a small integer) — that turns a "harmless" hash into an oracle. Then compare pass rates on the rollouts that touched the variable against those that did not. Until that is done, "the new model is better" and "the new model looks at its environment more often" are both hypotheses consistent with the eight points.

Bearing on the score. If any passing rollout used the hash, the two numbers measure different mixtures of skill and exploitation; report the exploit rate next to the pass rate and re-run with the variable removed (pass it to the grader's exec only). Separately, the API key is a live incident regardless of scores: rotate it, and move model calls outside the box.

Lab

Container lab. Exercises 1–2 run inside your lab container as learner; 3–4 are docker commands typed on your Mac.

  1. Reproduce. Predict the four lines this prints, then run it: COLOR=red; bash -c 'echo [$COLOR]'; COLOR=blue bash -c 'echo [$COLOR]'; echo "[$COLOR]"; export COLOR; bash -c 'echo [$COLOR]'
    Solution 
    []
[blue]
[red]
[red]

    Unexported, so the first child gets nothing. The one-shot form gives the second child blue without touching the shell's own variable, which is still red. After export, children receive it.

  2. Predict, then verify. A container is started with -e SECRET=abc; the shell inside immediately runs SECRET=changed. What does the shell's own /proc/$$/environ show? Write down your answer first.
    Solution 
    $ docker run --rm -e SECRET=abc ubuntu:24.04 bash -c \
    'SECRET=changed; echo "shell says: $SECRET"; tr "\0" "\n" < /proc/$$/environ | grep SECRET'
shell says: changed
SECRET=abc

    environ is the exec-time snapshot. Overwriting or unsetting a secret inside the program does not remove the original from /proc.

  3. Predict, then verify. In a stock ubuntu:24.04 container, what does TZ=America/Los_Angeles date -d @1767225600 print? Then install tzdata and run it again.
    Solution 
    # TZ=America/Los_Angeles date -d @1767225600
Thu Jan  1 00:00:00 America 2026
# apt-get update -qq && DEBIAN_FRONTEND=noninteractive apt-get install -y -qq tzdata >/dev/null
# TZ=America/Los_Angeles date -d @1767225600
Wed Dec 31 16:00:00 PST 2025

    No zone database, no error: UTC with a made-up label. An unknown zone name does the same even with tzdata installed (TZ=Mars/Olympus printed … 00:00:00 Mars 2026).

  4. Eval task. A task container is started like this: docker run -d --name lt-leaky -e EXPECTED_SHA=9f2c1ab7 ubuntu:24.04 sleep 600. The agent runs as uid 1000. (a) Show that uid 1000 cannot read PID 1's environment. (b) Show that it does not need to. (c) Show the third place the value is visible. (d) Restructure so that the grader still gets the value and none of the three show it.
    Solution 
    $ docker exec -u 1000 lt-leaky bash -c 'cat /proc/1/environ; env | grep EXPECTED'
cat: /proc/1/environ: Permission denied
EXPECTED_SHA=9f2c1ab7
$ docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' lt-leaky
EXPECTED_SHA=9f2c1ab7
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
$ docker rm -f lt-leaky
$ docker run -d --name lt-leaky ubuntu:24.04 sleep 600
$ docker exec -u 1000 lt-leaky bash -c 'env | grep -c EXPECTED'
0
$ docker exec -e EXPECTED_SHA=9f2c1ab7 lt-leaky bash -c 'echo "grader sees $EXPECTED_SHA"'
grader sees 9f2c1ab7
$ docker inspect --format '{{json .Config.Env}}' lt-leaky
["PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"]
$ docker rm -f lt-leaky

    The value now exists only in the grader's own process, which runs as root while the agent is uid 1000 — and, better, after the agent has exited. Stronger still: compare the hash outside the container and never send it in.
