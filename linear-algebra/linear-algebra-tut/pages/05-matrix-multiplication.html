Module 1 · Linear maps

Matrix multiplication as composition and as batching

Multiplying two matrices composes two maps. Multiplying a matrix of row vectors by a weight matrix applies the map to every token at once. einsum writes down which axes are summed so you cannot confuse the two.

The rule and the shape

For A of shape (n, k) and B of shape (k, m), the product AB has shape (n, m) and entry (i, j) is the dot product of row i of A with column j of B. The inner dimensions must match; the outer dimensions survive. That is all of matrix multiplication. The number of arithmetic operations is n·k·m, which for a (302, 768) activation matrix and a (768, 64) weight is about fifteen million multiplications, trivial on any machine.

(AB)ᵢⱼ = Σₖ Aᵢₖ Bₖⱼ
(n, k) · (k, m) → (n, m)
(AB)C = A(BC), but in general AB ≠ BA

Two readings of the same product matter here. If A is a batch of row vectors, one per token, then AB applies the map B to every row: batching. If A and B are both maps, then AB is the map “apply A, then B” in the row-vector convention: composition. The 3Blue1Brown chapter on matrix multiplication as composition shows why composition has this formula; the point for you is that both readings produce the same arithmetic and the same shape rule, so a line of code does not say which one it is. You have to know.

Both readings on the real head

Q = X W_Q applies W_Q to all 302 activations: batching. W_QK = W_Q W_Kᵀ composes the query map with the transposed key map into a single (768, 768) matrix: composition. And Q Kᵀ, the (302, 302) matrix of dot products between every query and every key, is the raw attention score matrix. The lab checks that batching then composing agrees with composing then batching, which is the associativity line in the formula box applied to X W_Q W_Kᵀ Xᵀ.

python3 labs/linalg_lab.py matmul
X (302, 768) @ W_Q (768, 64) = Q (302, 64); row 12 of Q equals X[12] @ W_Q: True
scores = Q @ K.T: shape (302, 302); entry [i, j] = q_i . k_j
W_QK = W_Q @ W_K.T: shape (768, 768); X @ W_QK @ X.T equals Q @ K.T (composition): True
einsum nd,dh->nh matches X @ W_Q: True ; einsum nh,mh->nm matches Q @ K.T: True

The two forms agree because matrix multiplication is associative: (X W_Q)(X W_K)ᵀ = X (W_Q W_Kᵀ) Xᵀ. You can compute the 302×302 score matrix either by forming the two 64-dimensional projections and dotting them, or by forming the 768×768 composite and sandwiching it. The first is what a model does, because it is cheaper; the second is what the transformer-circuits framework recommends thinking with, because W_QK is a single object whose geometry can be studied. [Elhage et al. 2021] The two are the same map.

The scores are shown without normalisation or softmax, and the first line of the ranking shows why the real model normalises: token 0, with its enormous norm, has a raw score of 23,652 against token 12 where the next largest is 139. Any downstream softmax would put all of its weight on token 0. Whether that is what attention in this head actually does on this text depends on the layer norm and biases the lab omits, so the output makes no claim about it; it shows only that a dot product with a vector thirty-six times longer is about thirty-six times larger.

einsum: name the axes

The expression np.einsum('nd,dh->nh', X, W_Q) says: X has axes n and d, W_Q has axes d and h, the output has axes n and h, and any letter that does not appear in the output is summed over. That is matrix multiplication with the summed axis named. 'nh,mh->nm' is Q Kᵀ: the h axis is summed, n and m survive, and no explicit transpose is needed because the letters say which axis of K pairs with which axis of Q. The numpy documentation states the convention and gives 'ij,jk' for a matrix product and 'i,i' for a dot product. [numpy: einsum] The ARENA prerequisites section spends a morning on einsum and einops for this reason: in code with four-axis tensors (batch, position, head, dimension) the letters are the only reliable way to say which dimension is being contracted. [ARENA]

A habit worth forming: before writing a product, write its einsum string in a comment even if you then call @. The string is a type annotation for the contraction, and a mismatch between the string and the shapes is a bug found before it runs.

Order matters

W_Q W_Kᵀ has shape (768, 64)·(64, 768) = (768, 768). W_Kᵀ W_Q has shape (64, 768)·(768, 64) = (64, 64). Both are legal products of the same two matrices and they are different objects of different sizes. In two dimensions, rotating by 90° and then reflecting in the x-axis is not the same as reflecting and then rotating; try it with (1, 0). Because composition has an order, so does multiplication, and the shape rule usually tells you which order was intended.

In interpretability work

“Virtual weights” between two components, the QK and OV circuits, and the path from embedding to logit are all products of weight matrices: compositions. Reading a paper’s product, write the shapes and the einsum, decide whether each factor is batching or composing, and the diagram will usually draw itself.

Pitfall

Forming the composite (768, 768) matrix in code when you only needed its action on a batch. X (W_Q W_Kᵀ) Xᵀ costs far more than (X W_Q)(X W_K)ᵀ, and for the vocabulary-sized matrices in lesson 12 the composite does not fit in memory. Compose on paper; batch in code.

Check your understanding

A colleague computes np.einsum('nd,md->nm', X, X) on the activation matrix and calls the result “the similarity matrix”. What are its shape and entries, and what is missing from the word “similarity”?

Reveal the reasoning

The shape is (302, 302) and entry (i, j) is xᵢ · xⱼ, the dot product of two tokens’ activations, since d is summed. It is a matrix of dot products, not cosines: row 0 and column 0 are dominated by token 0’s norm, and no entry is comparable across tokens without dividing by both norms. To get cosines, normalise each row of X first, or divide entry (i, j) by ‖xᵢ‖ ‖xⱼ‖. Lesson 02 showed the two rankings differ.

Practice

Compute the scaled scores of token 60 against the tokens before it. Does token 0 still dominate?

python3 labs/linalg_lab.py matmul --token 60
What to look for

Yes, and it would for any query token: the score against token 0 is a dot product with a vector of norm about 3,047, and nothing about the query changes that. The other two tokens in the list are informative about the query, token 0 is informative about token 0. Comparing scores across keys without accounting for key norm compares norms.
